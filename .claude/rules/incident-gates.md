# 每个事故都要有自动门槛

每个事故都必须以一项自动检查结束，同一个错误出现两次就必须用硬门槛（会自动拦下的测试或可执行逻辑）挡住（Andy 2026-11-27 从三次改为两次）。次数界限只写在 `scripts/check-incident-gates.mjs` 的 `REPEAT_LIMIT` 一处，其他检查都从那里读。云端线程（在 claude.ai 云端运行的工作线程）会加载本文件，所以每个会话都是通过这里知道这条规则的。它在快速模式和完整模式下都适用。

<a id="when-a-thread-starts"></a>
## 线程开始时

运行 `node scripts/check-incident-gates.mjs --open`，它只打印还没有关闭的条目的编号、状态、日期和一句话现象：未结条目（状态为 `缺门槛` 或 `等 Andy`），以及 `仓库外` 的条目（原因在仓库之外，门槛一栏写着线程要照办的替代做法）。如果这次工作涉及其中某条的领域，打开 [docs/incidents-and-gates.md](../../docs/incidents-and-gates.md) 读那一行；未结条目在计划里说明，`仓库外` 的条目照它的替代做法办。开工时不通读整份清单：它记的是全部事故的完整经过，大多数已经关闭，通读一次要占几万 token 的上下文。只有命令打印 `INCIDENT_OPEN unavailable` 时，才直接打开清单查看，并先修好清单：清单有任何一处通不过 `npm run check:incident-gates`（找不到清单、表格格式坏了、某行状态写错、已关闭条目的门槛文件不存在等，具体错误打印在标准错误里），它就不打印未结条目，因为这时列出来的可能不全。

<a id="what-counts"></a>
## 什么算数

- 事故是指：生产故障、失败或被回滚的发布、直到上线包生成后期才被拦下的问题，或者用户发现的、本可以由检查发现的缺陷。
- 门槛是指自己会运行、失败时会拦下的检查：`deploy.sh` 的上线前检查、上线包检查（`run-packet-checks.py`、`make-packet.py` 的拒绝）、测试、`npm run check` 的一个步骤、提交或推送钩子（hook，在提交或推送时自动运行的脚本），或者每次使用时都会自检的脚本。文档、案例库案例、记忆笔记或提醒都不是门槛。
- 一个事故只有在它的门槛已经存在、并且已证明它在事故的复现上会失败、在原因去除后会通过时，才算关闭。把这份证据写进提交说明。
- 同一个错误第二次出现时，无论是事故还是代理自己的失误，在继续处理这个错误的工作之前都需要一道硬门槛。当只有用户能做这项改动时，把它准备好，带着具体方案问一次，并把该条目标为 `等 Andy`。

<a id="incident-line-in-every-commit"></a>
## 每个提交写明是哪个事故，次数从提交记录里算

次数不靠线程自己记得加：每个提交（合并提交和 GitHub 生成的提交除外）的提交说明都要有一行事故标记，三种写法任选其一：

- `Incident: I-<编号>`：这个提交修的是这个事故又出现的一次。每个这样的提交算一次。
- `Incident-follow-up: I-<编号>`：同一次事故的后续修改（例如同一个 PR 里的第二个提交），不再算一次。
- `Incident: none`：和任何事故无关。只要这次修改起因于上面“什么算数”里的任何一种情况（包括一次失败的自动上线），就不得写 `none`，先在清单里新加一行或找到原有那一行。

修的是一个事故第二次或更晚出现（也就是这条事故在清单里的次数已经到 2）时，提交说明还要再写一行 `Premise: <当初哪个想法错了>`。例如 `Premise: 以为重试时会读到新配置`。写下错的前提，下一次才能对着它查，而不是只修眼前这一处。

程序门槛：

- 提交钩子 `scripts/git-hooks/commit-msg` 运行 `node scripts/check-incident-gates.mjs --commit-msg`：没有事故标记、写法不对、写的编号清单里没有，或者修第二次及以后的出现却没有 `Premise:` 行，提交直接失败。
- `npm run check:incident-gates`（CI 每次都跑）读完整的提交记录：规则生效之后的提交缺标记、标记的编号不在清单里、清单里的次数少于提交记录里 `Incident:` 指向它的提交数，都失败；次数一到 2，原有的“没有硬门槛就失败”随之生效；`Premise:` 规则生效之后，提交时清单次数已到 2、却没写 `Premise:` 行的 `Incident:` 提交，也失败。浅克隆读不全记录，直接失败，先运行 `git fetch --unshallow origin`。
- main（默认分支）上失败的运行也由程序自动数，不靠人发现：CI 的 `ci/required` 在每个 PR 上运行 `node scripts/check-incident-runs.mjs`，向 GitHub 读这条规则生效以来 main 上结论为失败的全部运行（自动上线、main 上的 CI、iPhone 作业等所有工作流）。同一个工作流有 2 次或以上失败没有被认领时，改到这个工作流或它运行的文件（工作流文件本身，以及工作流里写到的仓库路径所在的目录，例如上线工作流的 `scripts/delivery-mode/`）的 PR 合不进去；没碰它的 PR 不拦，只在日志里列出来，免得一个工作流的失败卡住全仓库。每天 09:17 JST 还有一个定时作业（`.github/workflows/incident-runs-report.yml`）把全部没认领的失败列在运行摘要里。认领的写法是在提交说明里加一行 `Incident-run: <运行编号> [<运行编号> ...] I-<编号>`（运行编号是 Actions 网址里 `runs/` 后面的数字），并且这条事故的次数不少于认领到它名下的运行数；次数到 2 时，上面的门槛规则同样生效。读不到 GitHub 时检查直接失败。
- 一个 PR 自己的 CI 红了 2 次或以上，也要复盘：`ci/required` 运行 `node scripts/check-pr-reflection.mjs`，向 GitHub 数这个 PR 开出以后、它的分支上结论为失败、而且除 `ci/required` 以外还有作业失败的运行（只因草稿或上游被取消而失败的不算）。到 2 次时，PR 说明里必须有 `## 复盘` 一节，写出每一次红的运行编号，并且有一行 `共同前提：`（这几次失败背后共同的那个错误想法）和一行 `验证：`（怎么确认修好了）；没有这一节、漏了编号或缺了这两行，PR 就合不进去。复盘里写清每次为什么红、现在靠什么挡住；同一原因已经出现两次的，按本文件记进事故清单并落门槛。补好说明后重跑失败的 `ci/required` 作业即可。读不到 GitHub 时检查直接失败。
- 次数达到 2 的“已落门槛”条目，门槛一栏至少要有一个会自动运行的文件：测试文件，或者 `package.json`、`scripts/git-hooks/`、`.github/workflows/` 里会调用的脚本；只点名一个没有任何东西运行的文件，检查失败。

<a id="keeping-the-list"></a>
## 维护清单

- 每一行：编号、日期（JST，日本标准时间）、症状、根本原因、出现次数、门槛（文件用反引号括起，或写命令）、状态。状态：`已落门槛`、`缺门槛`、`等 Andy`、`仓库外`（原因在本仓库之外，并写下替代做法）。
- 新事故加一行；重复发生时，提高次数并扩充原有那一行，不另加新行，修它的提交写 `Incident: I-<编号>`（见上一节）。判断是不是重复发生时，按领域、文件名或报错关键词搜整份清单（包括已关闭的行：已关闭的事故又出现，说明它的门槛漏了），不必通读。
- `npm run check:incident-gates`（属于 `npm run check` 的一部分）会拒绝：门槛文件不存在的已关闭行、次数达到 2 或以上却没有硬门槛的行，以及格式不对的行。
- 代理犯错的详细历史保存在 `docs/lessons.md`；只有当这类错误造成了事故时，才在这里加一行。

<a id="delivery-reports"></a>
## 交付报告

写明线程处理的每个事故、加上的门槛（文件或命令）或为什么不需要门槛，以及更新了清单中的哪一行。

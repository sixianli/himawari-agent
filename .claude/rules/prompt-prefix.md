# 发给模型的内容：怎样最大化 KV 缓存命中

这份规则约束所有会话，包括协调者和云端线程，快速模式和完整模式都适用。凡是组装或修改发给模型的内容，都要先读它。“发给模型的内容”包括系统提示、工具定义、历史、资料块、遮盖和压缩。

KV 缓存，也叫提示缓存（prompt cache），指模型服务方把“请求开头完全相同的部分”缓存起来：下一次请求的开头只要和上一次逐字节相同，这部分就不用重新计算，速度更快，费用通常只有正常价的一成左右（[Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)、[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)、[DeepSeek](https://api-docs.deepseek.com/guides/kv_cache)）。匹配是逐字节的：开头任何一处变了，从那里往后全部按全价重算。

每条做法的理由、一手来源和本项目的落实情况，见项目文档 [模型请求的 KV 缓存规范](../../docs/kv-cache-guide.md)；这份规则只写必须遵守的条目。

这份规则的起因是 [I-66](../../docs/incidents-and-gates.md#incidents)：每轮存历史时，上一轮的用户消息被改写了，网页上显示“缓存命中 0%”。相关决定见 [ADR 0149](../../docs/adr/0149-append-only-model-requests.md)（只追加）、[ADR 0164](../../docs/adr/0164-move-changing-values-out-of-the-request-head.md)（把会变的值挪到最后）、[ADR 0165](../../docs/adr/0165-freeze-the-request-head-per-conversation.md)（按对话冻结）。

<a id="order"></a>
## 一、请求怎样排

1. **固定的在前，会变的在后。**顺序是：工具定义 → 系统提示 → 历史 → 最后一条用户消息。越靠前的越不能变，因为前面一处变了，后面全部重算。
2. **每轮都会变的内容只放在最后一条用户消息里。**例如当前时间、本轮选中的记忆、本轮资料、工具状态、运行环境说明。系统提示和工具定义里不得出现会变的值，例如时间、日期、路径、服务商名、额度、版本号、哈希。
3. **要告诉模型新情况时，追加一条消息，不改系统提示。**例如工具循环停止、后台命令结束、运行环境变了，都以追加消息的方式告诉模型。

<a id="rules"></a>
<a id="append-only"></a>
## 二、已经发出的内容

4. **已经发给过模型的内容，不得改动、重排或删除，只能在末尾追加。**这包括系统提示、工具定义、历史里的每一条消息（用户的话、回答、工具调用、工具结果）。
5. **存历史时存实际发出去的那一条。**不得在存之前把它换成别的版本，例如去掉资料块、换回原话、缩短搜索结果。

<a id="stable"></a>
## 三、同一对话里保持不变的东西

6. **系统提示和工具按对话冻结**（[ADR 0165](../../docs/adr/0165-freeze-the-request-head-per-conversation.md)）。同一对话一直沿用第一次发出时的字节。只有下面这些情况才换新一次，并且每次都留记录：工具集合（工具名和参数结构）变了、模型变了、推理强度变了、回答语言变了、数据分类变低了，或者手动执行了 `thread prompt rebuild`。
   - 改了提示词文字，**只对新对话生效**。要让老对话也用上，必须手动换新。
7. **工具集合尽量不变。**业界的首选是让工具一直在列表里，不能用的时候由执行端拒绝，而不是把工具删掉或加进来（[Claude Code](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)、[OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching)、[Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)）。本项目目前的取舍：工具集合变了就换新一次；只有手里有执行句柄才会出现的工具不冻结，接在冻结工具的后面，并记日志统计它们出现的频率。要改变这个取舍，先出方案。
8. **同一对话中途不换模型、不换推理强度。**每个模型的缓存是分开的，推理强度在多数模型上也会影响缓存。确实要换的话，在对话开头换，或者用单独的辅助调用来做。
9. **同一对话的请求送到同一个服务方。**缓存存在各服务方自己的机器上，换一家服务方就要整段重算。路由（Magpie、OpenRouter 一类）要按对话保持同一个去向；服务方支持缓存路由键的（例如 OpenAI 的 `prompt_cache_key`），按对话传一个固定的键。

<a id="deterministic"></a>
## 四、字节必须确定

10. **同样的内容，每次都要序列化成同样的字节。**JSON 的键顺序、工具的顺序、列表的顺序（命令清单、服务商、记忆）都要固定，不能依赖对象遍历顺序或数据库返回顺序。
11. **遮盖敏感信息必须是确定的。**同一条消息，每次都遮成同样的字节；已经发过的历史，不因为后来的消息而被遮成别的样子。
    - 例外：主人在一条消息里点名的秘密（例如“482910 是验证码”），会在这条消息里所有出现的地方都遮掉。这是为了不漏掉秘密，这条消息本身每次遮出来的结果仍然相同，所以不影响缓存。

<a id="compaction"></a>
## 五、压缩和清理

12. **必须缩短历史时，集中做、少做，并在 ADR 里写明。**不得每轮都做。是否值得压缩，要比较压缩前后的**总输入费用**，不能只看命中率：压缩后命中率下降，但输入变少，总费用可能更低。
13. **压缩请求应当沿用原对话的系统提示和工具**，只在末尾追加“请总结”的指令，这样压缩请求本身也能命中缓存（[Claude Code](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)）。
    - 已知差距：Pi 现在的压缩是把整段对话序列化成一条新消息，系统提示也换成它自己的一份，所以每次压缩整段历史都按全价计算。要修，先出方案。
14. **清理旧的工具结果要成批、少做、能恢复。**一次清理足够多，才值得付一次缓存失效的代价；被清理的内容要能找回（例如保留网址或文件路径）。这一条要等第二步之后另出方案，在那之前不做。

<a id="side-calls"></a>
## 六、后台调用

15. **后台调用也是固定的在前、会变的在后。**整理记忆、判断邮件、起对话标题这类调用，先放固定的指令，再放这次的数据，最后放当前时间这类每次都变的值。
16. **需要分叉出去做的辅助计算，尽量沿用父对话的开头。**例如摘要、压缩这类要读整段对话的辅助调用。
17. **并发发出、开头相同的请求，要等第一个请求开始返回，再发后面的。**缓存要等第一个请求的结果开始返回后才可用。

<a id="gate"></a>
## 七、检查和监控

- **阻断检查：**`npm run check:prompt-prefix`（属于 `npm run check` 的一步）。它用真实的 Pi 适配器和真实的出口遮盖，对本机回环服务跑多轮对话：包括工具调用、搜索结果、银行卡号遮盖、附件长文本、每轮变化的记忆和时间，以及冻结、换新、运行中压缩补发运行环境说明。每次都逐字节检查后一次请求是否以前一次请求开头。它还带反向用例：改写历史里的用户消息、让系统提示带上每轮变化的值、关掉冻结，检查都必须报告失败。测试在 `packages/runtime-pi/test/prompt-prefix.compat.test.ts`，名字带 `[I-66]`。
- **端到端：**`test/integration/production-http-composition-process.test.ts` 里的 `[PR-A]`、`[PR-B]` 用例，用真实服务和 SQLite 抓取原始请求体来比对。
- **生产监控：**
  - 后续轮次的请求命中率低于 50% 时，服务日志写一行 `cache.follow_up_low_hit`。
  - `node scripts/operations/cache-hit-report.mjs <product.sqlite> --by turn` 按“第 1 轮 / 第 2 轮及以后”“首次请求 / 同轮后续”分开给出命中率。
  - 命中率要当作可用性指标来看，掉下来要查原因。排查时先排除这几种：缓存过期（两次请求隔了太久）、按规则换新、换了服务方。

<a id="before-you-change"></a>
## 八、改动前先问自己

- 这个改动会不会让模型已经见过的请求开头变化？会，就停下来出方案，Andy 同意才动工。
- 我加的值每轮都一样吗？不一样，它只能放在最后一条消息里。
- 我是不是在存历史之前处理了消息？处理后的结果必须和发出去的完全一样。
- 我加进去的列表或 JSON，顺序是不是固定的？
- 这个改动会不会让同一对话换模型、换服务方，或者增删工具？

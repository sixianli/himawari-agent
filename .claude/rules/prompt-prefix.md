# 发给模型的内容只追加，不改写

这条规则约束每个会话，包括协调者和云端线程，在快速模式和完整模式下都适用。起因是 [I-66](../../docs/incidents-and-gates.md#incidents)：每轮存历史时把上一轮的用户消息改写，下一轮请求的开头就和上一轮对不上，上一轮的回答和搜索结果全部按全价重算，网页上显示「缓存命中 0%」。决定和理由见 [ADR 0149](../../docs/adr/0149-append-only-model-requests.md)。

<a id="rules"></a>
## 硬规则

1. 已经发给过模型的内容，不得改动、不得重排、不得删除，只能在末尾追加。这包括系统提示、工具定义、历史里每一条消息（用户的话、回答、工具调用、工具结果）。
2. 每轮都会变的内容放在最末尾，不得放在任何已发内容之前：当前时间、本轮选中的记忆、工具状态、本轮资料块，都只能写进最后一条用户消息。系统提示和工具定义里不得出现会变的值。
3. 存历史存的是实际发出去的那条消息，不得在存之前换成别的版本（例如去掉资料块、换回原话、缩短搜索结果）。
4. 遮盖敏感信息必须是确定的：同一段文字永远遮成同样的字节，不得依赖它前面或后面的内容。
5. 必须缩短历史时（超过窗口的压缩），集中做、少做，并在 ADR 里写明；不得每轮都做。
6. 要改变已发内容的做法，先出方案、讨论，Andy 同意才动工，因为它会让所有进行中的对话缓存整段失效一次。

<a id="gate"></a>
## 自动检查

`npm run check:prompt-prefix`（`npm run check` 的一步）用真实的 Pi 适配器、真实的出口遮盖，对本机回环服务跑多轮对话，包括工具调用、搜索结果、银行卡号遮盖、附件长文本、每轮变化的记忆和时间，逐字节检查后一次请求是以前一次请求为开头的。它还带反向用例：把历史里的用户消息改写、让系统提示里带每轮变化的值，检查必须报告失败。测试在 `packages/runtime-pi/test/prompt-prefix.compat.test.ts`，名字带 `[I-66]`，少于 8 条通过就失败。

生产上，一次后续轮次的请求命中率低于 50% 时，服务日志写一行 `cache.follow_up_low_hit`；`node scripts/operations/cache-hit-report.mjs <product.sqlite> --by turn` 按「第 1 轮 / 第 2 轮及以后」和「首次请求 / 同轮后续」分别给出命中率。

<a id="before-you-change"></a>
## 改动前先问自己

- 这个改动会不会让模型已经见过的请求开头变化？会，就停下来出方案。
- 我加的值每轮都一样吗？不一样，它只能在最后一条消息里。
- 我是不是在存历史之前处理了消息？处理的结果必须和发出去的完全一样。

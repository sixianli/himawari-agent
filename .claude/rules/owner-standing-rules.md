# Andy 定的长期规则

这些规则原先只写在 claude.ai 项目的项目指令（项目设置里写给每个新线程的一段说明）或项目记忆里。只有项目里新开的线程能读到项目指令，Andy 在 Mac 终端直接开的 Claude Code 会话读不到，所以写进仓库。它们在快速模式和完整模式下都适用，约束所有代理。

<a id="money-and-models"></a>
## 钱和模型

- 花钱先问：任何评测、测试、实验或批量模型调用，预计要花 Andy 的钱超过 0.5 美元时，先在项目聊天报出预计费用和用途，等 Andy 明确同意再开跑；费用说不准时，按会超过处理。例外：用 OpenCode 做的合并前代码复核和方案说法核对（`plan-claims`，把方案里关于代码现状的每句话对着代码核一遍），一个 PR 或一件方案的已花的加上这一轮预计的不超过 1 美元、全项目当天合计不超过 5 美元时不用问，超了才问；费用说不准时同样按会超过处理（Andy 2026-11-14 同意；见[代码复核](../../.agents/instructions/model-review.md#code-review)）。脚本只拦一个 PR 或一件方案的 1 美元，拦不了全项目每天 5 美元：每天的复核和核对花费由协调者汇总报给 Andy，当天合计会超过 5 美元时由协调者先问。
- 评测用哪个 key（API 密钥），评测之前先问 Andy。评测和测试绝不和生产共用预算：曾有一次评测花光了 Vercel 账号的预算，生产因此中断。
- 禁用贵模型：任何场景（生产、评测、裁判、测试、实验、后台任务）都不得通过按 token 付费的渠道（例如 Vercel、OpenRouter）调用 Claude、OpenAI 或同价位的模型；按量付费只用 DeepSeek V4.1 Flash 这类低价模型或免费额度。代码和评测脚本里不得写死 `anthropic/`、`openai/` 开头的模型名。
- Andy 已付费套餐里的 token（例如 Claude Max 附带的 API 额度、OpenCode Go）不在禁用之列，而且要优先用。生产经 Magpie（装在生产机上的模型路由程序）调用模型，顺序是套餐内 token、免费额度、最后才是 Vercel 上的低价模型。

<a id="fixing-bugs-and-new-features"></a>
## 修 bug 和做新功能

- 修 bug 先查根因，不许只修表面。修法要先上网查当前的做法（官方文档、成熟开源项目，附一手来源），已有成熟方案就采用，拿不准的拿出来和 Andy 讨论；不得凭记忆或过时的训练数据决定修法。PR 和案例里写清“业界怎么做、我们为什么这样做、放弃了什么”。
- 大改动先出方案、讨论后再动工：
  - 什么算大改动：改动较大的模块或功能，或者动到项目的核心特性，例如记忆系统、模型调用和路由、Agent 循环（模型一步步调用工具的那套流程）、权限和授权、系统主动提醒、数据存储结构；新增 Andy 不熟悉的功能、改机制或规则也算。拿不准算不算的，按大改动处理，先问 Andy。修小 bug 不用走这条。
  - 写方案时，先上网搜最新资料，参考各大 AI 公司（例如 Anthropic、OpenAI、Google）公开的做法，以及 GitHub 上成熟的开源实现，附一手来源；不从零写。
  - 方案先和 Andy 讨论，他同意之后才能改代码、改文件或开 PR。

<a id="numbers-and-acceptance-in-the-ui"></a>
## 界面上的数字和验收

- 界面上给 Andy 看的每个数字和判断词（例如“找到 3 条相关记忆”“命中”“推荐”“成功 N 条”）都要有可以验证的定义和门槛，没有就不显示（起因是界面上“找到 3 条相关记忆”永远凑满 3 条）。
- 线程说一个界面功能“做完了”时，要附上在真实网页上的正向和反向两种验收结果。反向验收是给一个不该命中、不该触发的输入，期望结果为空或不触发。没有反向验收的不算完成。判断类功能的发布验收（`release-walkthrough`）必须有反向用例。
- UI/UX 意见攒批：Andy 在项目聊天一条条提界面问题时，协调者每条只回“记下了”，等 Andy 说“提完了”，再把全部意见打包交给对应线程。Andy 明说“不是 UI 问题”的，不进攒批。

<a id="authorization-deploys-and-merges"></a>
## 授权、上线和合并

- Andy 尽量只和协调者沟通。所以他在项目聊天里对协调者说的话，由协调者附上他那条原话转给对应线程，就算他的授权。上线、回滚、停服、改配置、合并 PR 都是这样，不要让他再去别的线程重说一遍。上线和回滚的细节见[交付模式](../../.agents/instructions/delivery-mode.md#fast-mode)。
- 唯一的例外是删除 Andy 的 Mac 上的文件：只认他在 Mac 线程（通过 Remote Control 在他 MacBook 上运行的那个线程）里亲手打的字。需要时，协调者在项目聊天里直接告诉他“去 Mac 线程打什么”和为什么，不说“在这里说也行”。
- 会删东西的上线，所有要 Andy 选的选项先选完，再上线。
- 合并 PR 一律由做这个 PR 的线程执行，不让 Andy 自己去 GitHub 操作。复核没有中、高严重度的“会出错”意见，并且过了[交付模式](../../.agents/instructions/delivery-mode.md#fast-mode)写的合并条件，线程就自己合并，不等 Andy 说“合并”（Andy 2026-11-14 同意）。只有这几类要等 Andy 说“合并”（在那个线程或项目聊天里说都算）：动生产或上线的、改数据库表的、改模型调用的大改动，以及 Andy 点名要过目的。等 Andy 的时候，先做不依赖这一步的其他工作。线程执行合并的方式是给 PR 加 `merge-queue` 标签，由合并队列完整测过后合进 `main`；改了 CI 自身文件的 PR 仍由线程直接合并（[ADR 0268](../../docs/adr/0268-merge-queue-and-related-tests-on-prs.md)）；Andy 临时放宽 CI 门禁期间怎么合，见交付模式。
- 合并前的模型复核由 Andy 控制：他说跳过就跳过（不论复核了几轮），说停就停，说这次用哪家服务方就用哪家；线程怎么做见[Andy 怎样控制复核](../../.agents/instructions/model-review.md#owner-control)。

<a id="prompt-layout-for-the-kv-cache"></a>
## 模型上下文的排列

- KV 缓存最大化是原则。KV 缓存是模型服务方对重复出现的开头内容做的缓存，开头完全一样的部分不用重新计算，更快也更便宜。组装发给模型的上下文时，固定不变的内容放前面，会变的内容（例如时间戳、本轮输入）放后面；不得以“收益小”为由不这样排。

<a id="independent-judgment"></a>
## 独立判断，不盲从

- 每个线程和协调者都要有自己的判断，不得盲从 Andy 的指示、决定，或他已经同意的方案。动手之前先核对它和现有功能、测试、已有规则有没有冲突。
- 判断 Andy 的决定不对，或者有更好的做法时，必须明确指出：哪里不对、会出什么问题、建议怎样做，然后等他定；不得默默照做。
- 例：让“结果未知”的轮次提前收尾，会抢掉“迟到结果恢复”。实施前只要问一句“会不会抢掉恢复”并跑一遍相关测试就能发现，却没有人问。

<a id="meaning-goes-to-the-model"></a>
## 理解用户的意思交给模型，不写词表

- Andy 2026-11-12 定、2026-11-13 补充（[ADR 0249](../../docs/adr/0249-the-model-judges-meaning-where-word-lists-guessed-it.md)）：判断用户一句话的意图、时效、是否明说、两句话是不是同一件事，一律交给模型，程序只做校验（原话是否逐字出自主人、格式、额度、白名单）。不得用关键词表、正则、停用词表或写死的词典去猜用户的意思，也不得“先放词表，以后再改”。
- 门槛：`npm run check:meaning-word-lists` 找出新增的词表形状，每一处必须在 [词表登记表](../../docs/meaning-word-lists.md) 登记类别和理由。登记表里没有“理解用户意思”这一类；要加新类别，先问 Andy。
- 做法参考 PR 423、467 和 ADR 0249、ADR 0252：独立裁判提示词、严格解析、失败走安全默认、用本机回环模型桩写自动测试，再用真模型小批量评测（花钱先按本文件“钱和模型”一节问）。
- 起因：[I-104](../../docs/incidents-and-gates.md#incidents)，这类词表已经出现三次。

# Himawari 网页设计规范

<a id="contents"></a>

这份文档记三样东西，供协调者和以后每个做界面设计的线程参考：

- **好的设计规范**：从下面两类例子里总结出的规则，改界面时照着做。
- **优秀设计**：Andy 批准过、而且明确说喜欢的设计。
- **不良设计**：做出来后被 Andy 指出、或被检查拦下的问题，写清原因和改法。

这里的“Himawari 网页”指 Andy 日常聊天用的网页，代码在 `apps/control-center`。文档由 Andy 在 2026-10-29 提出：“任何我们遇到的 UI 和 UX 的问题，都记入到本项目的 UI UX 设计的‘不良设计’中，而把我们确定下来的、我很喜欢的设计记入本项目的‘优秀设计’中，并维护一个适合本项目的《好的设计规范》”，目的是尽可能做出优秀的设计。

**怎么用。** 改界面之前先读完[好的设计规范](#rules)。交付时，把这次遇到的新问题补进[不良设计](#bad)，把 Andy 新批准的设计补进[优秀设计](#good)；新问题如果能归纳成一条新规则，也补进规范。视觉基线（定稿的原型截图）仍以 [AGENTS.md 的“Approved Web Design Baselines”](../AGENTS.md#approved-web-design-baselines) 列出的版本为准，本文不替代基线。

## 好的设计规范

每条规则后面括号里是它的出处：界面意见编号（第一批 1–22，第二批 23–41）、事故编号（见[事故与门槛清单](incidents-and-gates.md)）或 ADR（架构决策记录，记下一个长期决定和理由的文档）。

### 显示什么

1. **站在主人的角度决定显示什么。** 只放 Andy 下一步要用的信息，不放实现细节。收起时一句话说清做了什么，细节放进点开才看到的第二层。例如“运行命令”展开后只显示“✓ 成功”或“✕ 失败 · 出错代码 1”，命令本身收进“命令详情”；快捷键提示也不常驻在控件旁边，例如编辑框下不写“⌘↵ 保存 · Esc 取消”，快捷键照常可用（第 30、35 条；[ADR 0105](adr/0105-ui-batch-2026-10-28-show-what-the-owner-needs.md)）。
2. **数字和判断词必须有定义。** 页面上的每个数字都要能说清是怎么算出来的，并且和主人点进去看到的对得上。例如筛选按钮上的数字，必须等于“其他筛选不变、点它之后能看到的条数”（I-13）。“找到 N 条相关记忆”里的“相关”必须有相似度门槛；没有门槛、凑够 3 条就叫“相关”，是不良设计（I-23，记忆召回线程，2026-10-29）。
3. **空结果不显示过程。** 什么都没找到时，不要在步骤里写“没有相关记忆”这种话，否则就是此地无银三百两（2026-10-29，记忆召回线程）。
4. **内容优先，元信息放进第二层。** 打开文件先看到内容；类型、大小、第几轮、时间、来自哪个对话，以及网页文件的安全说明，都收进“文件信息”按钮（第 29、38 条）。
5. **不给主人看系统用语和错误码。** 例如空白新对话中间不写“尚无已提交消息”，而是欢迎问候；错误要用一句话说明发生了什么、要不要他做什么（第 27 条自查）。
6. **不写死会变的名字。** 例如联网搜索的说明不写某家厂商的名字，而是列出服务器配置里真正会收到数据的网址，换厂商时页面不用改（第 26 条批注）。
7. **新动作要让人明白后果。** 例如“分出新对话”：提示里写清会开一个新对话、带上到这一轮为止的全部内容、原对话不受影响；新对话顶部写“从「原标题」第 N 轮分出 · 打开原对话”，原内容颜色稍淡地显示在分隔线上方（第 28 条，I-17）。

### 布局和对齐

8. **同一组元素对齐到同一条线。** 空状态的图标、标题、说明和底部提示整体居中；同一列里的返回箭头、标题和正文用同一个左边线（第 27 条）。
9. **不让任何东西超出屏幕或被挡住。** 不出现横向滚动条，按钮不被别的元素盖住，文字放不下时换行或用省略号，不被挤成竖排（第 23、36 条；I-14）。
10. **三种语言一起排版。** 同一个意思在中英日里长度不同，按钮和标签不写死宽度，放不下时换行（[ADR 0105](adr/0105-ui-batch-2026-10-28-show-what-the-owner-needs.md) 第 7 条）。
11. **弹窗固定大小、内部滚动。** 设置弹窗在电脑和手机上都是固定外框，内容多时在框内滚动，关闭按钮始终在框内可见（第 23 条）。
12. **相邻的按钮分开放。** 顶栏每个按钮是单独的圆形按钮，之间留出空隙，不把两个按钮挤在同一个胶囊里，免得误触（第 33 条批注）。
13. **浮在内容上的按钮要小。** 例如“回到最新消息”是输入框正上方居中的小圆形箭头，不挡聊天内容（第 34 条）。

### 控件

14. **不用浏览器自带的控件外观。** 下拉菜单用页面自己画的，颜色、圆角、阴影和其他组件一致，不出现系统深色菜单（第 25 条）。按钮的提示用页面自己的提示框（`data-tip`），不用浏览器的 `title` 提示（第 28 条）。
15. **编辑控件一个规则。** 没改动时“保存”是灰色不能点，改了才变成实心；“取消”是描边按钮；“编辑”是图标加文字的轻按钮；“删除”是红字，放在最左边和“保存”隔开；输入框和按钮同高、同圆角（第 35 条）。
16. **焦点描边只给键盘用户。** 用 `:focus-visible`，鼠标和手指点击不画描边；弹窗打开时焦点放在弹窗本身，不放在关闭按钮上（第 37 条，I-18）。
17. **能点开的才给箭头。** 没有内容可看的步骤不能点，也不显示箭头（[ADR 0105](adr/0105-ui-batch-2026-10-28-show-what-the-owner-needs.md) 第 2 条）。
18. **按钮的悬停底色和按钮一样大。** 全站按钮默认有 44px 最小高度；图标按钮要显式取消这个最小高度，否则 28px 的图标外面会出现一个又高又窄的悬停底色（第 28 条自查）。

### 文字、颜色和语言

19. **日期、时间、数字跟着界面语言走。** 所有格式化都传界面语言，中文界面不出现“Thu, October 29”或“11:55 AM”（第 39 条，I-15）。
20. **正文字重 400。** 不用 430 这类中间值，苹方会把它取成 500，整段看起来像加粗（I-12）。
21. **颜色只表达含义。** 红色表示需要主人处理，琥珀色表示看一下或已自行恢复，紫色（主题色）只用在能点的东西上（[ADR 0106](adr/0106-proactive-loop-v1-gmail-read-only.md)）。

### 手机

22. **手机上的输入框字号至少 16px。** 否则 iPhone 一点输入框整页放大不回弹；弹窗高度要扣掉状态栏和底部安全区（I-14）。
23. **手机上的点按区域够大。** 顶栏按钮在手机上是 40px 的圆，回答下方的操作按钮是 36px。

### 数据

24. **主人的设置在所有设备上一致。** 称呼、界面语言、主题色存在服务器上，换设备打开看到的一样（第 24 条，I-16）。

### 文件预览

27. **文件在页面里看起来要像它本来的样子。** PDF、Word、Excel 直接在预览栏里显示，保留分页、颜色、表格边框、数字格式；文档和表格的“纸面”在深色主题下也是白底，外框跟随主题；显示不出来时用一句话说“可以下载后打开”，不显示错误码（第 31 条，[ADR 0114](adr/0114-file-preview-pdf-word-excel-in-browser.md)）。

## 自动检查

规范里能自动检查的部分，已经变成每次 `npm run check` 都会跑的检查。规则写进本文不算完成，能检查的要落成检查（[ADR 0107](adr/0107-every-incident-gets-an-automatic-gate.md)）。

| 检查 | 命令 | 拦什么 |
| --- | --- | --- |
| 真浏览器全站自查 | `npm run check:layout`（`scripts/check-layout-audit.mjs`） | 10 个页面在中英日三语、1280 和 390 两种宽度、浅色深色下：横向滚动、元素超出屏幕、按钮被挡住、文字被挤成竖排、文字被截断却没有省略号、原生下拉框、没点过就出现的焦点描边、中日界面里的英文月份星期和 AM/PM。每次运行先用一页故意做坏的页面自检，8 类问题都要认出来才继续 |
| 日期时间语言 | `npm run check:locale` | 代码里不传界面语言的日期、时间、数字格式化（I-15） |
| 手机排版 | `npm run check:phone-layout` | 手机输入框字号、弹窗安全区、视口设置（I-14） |
| 文件预览 | `node scripts/test-file-preview-browser.mjs chromium`（和 `webkit`），不在 `npm run check` 里 | 在生产安全策略下，PDF、Word、Excel 在三语、1280 和 390 宽下都能显示：PDF 有文字层，Word 有样式、图片和项目符号，Excel 填充色和数字格式对，页面不横向滚动 |
| 界面走查脚本 | `npm run check:release-walkthrough` | 上线前走查脚本里的选择器和页面一致 |
| 回答字重 | `npm run check:answer-weight` | 回答正文字重（I-12） |

还不能自动检查、要靠人看的：同一组元素的视觉对齐（第 8 条）、信息该不该显示（第 1 条）、颜色含义（第 21 条）。改界面时用三语截图自己看一遍。

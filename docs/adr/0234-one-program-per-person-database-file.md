# ADR 0234：一个程序，每人一个数据库文件；模型用 Andy 已有的套餐、不用 Vercel 按量付费，每人上限由 Andy 配置

## 背景

[ADR 0083](0083-isolated-instance-per-person-with-owner-entry.md) 定的做法是“每人一套独立实例”（每人各有一套程序、系统服务、端口和数据目录，叫 silo）。2026-11-11 Andy 给出两个新前提：生产机只有一台、不想在服务器上多花钱；目标是 10 到 20 人长期用。每人一套完整实例，内存和磁盘要乘以人数，8 GB 的生产机大概率放不下（推断，没有实测），每次上线还要升级 N 份。所以 ADR 0083 的第 2 条（独立实例）和第 5 条（每个别人一把 Vercel key、每月 10 美元）已经站不住。

线程出了新方案，由 DeepSeek V4.1 Flash 和 GLM 5.3 Flash 各自独立出方案、DeepSeek 审核后整合，全文见 `/mnt/project-files/multi-user-plan/integrated-plan.md`（不入库，下面逐条引用）。2026-11-11T10:27Z Andy 回复：“行吧，我同意你这个一个程序，然后每人一个数据库文件这个方案”。2026-11-11T11:05Z Andy 又说：

> 第二个我不同意：我现在只有一个 opencode go 的套餐可以用，而且我也不想再用那个 Vercel 的 key 了，因为他们的 key / API 很贵，我宁愿用 opencode 套餐内的
>
> 第三条，每人每月的上限由我自己灵活配置.而不是在代码里面写死，因为这样写真的很傻逼，知道吧？
>
> 其余的我都同意按照你的建议

“其余的”指方案第 2 节列出的 7 件事里其他几件：生产机上只读测量；邀请时明说 Andy 技术上能读所有人的文件，Andy 承诺不读，管理页只显示用量数字；接受两个剩余风险；做聊天记录导出；先做不碰生产机的部分。

本 ADR 取代 ADR 0083。它保留 ADR 0083 里仍然成立的几条（每人一个只属于自己的 Himawari、只邀请不开放注册、Cloudflare Access 登录、Andy 的手机也走这个入口），把实例隔离改成“一个程序、每人一个数据库文件”，把费用上限改成“Andy 配置、按人按月”。

<a id="premises"></a>

## 前提和来源

- 前提：生产机只有一台，不另租机器。来源：Andy 2026-11-11 的话，记在项目记忆里：“服务器只有一台生产机，不想在服务器上多花钱”；整合方案开头也引了它 `/mnt/project-files/multi-user-plan/integrated-plan.md`。
- 前提：所有人的模型都用 Andy 已有的套餐、不用 Vercel 按量付费（对话模型具体走哪一家，按 ADR 0117 的顺序，可能先用 CodeBuddy 免费额度再用 OpenCode Go，见决定第 7 条）。来源：上面引用的 2026-11-11T11:05Z 原话。
- 前提：上限由 Andy 配置，不写死。来源：同一条原话的第二段。
- 前提：Magpie（生产机上的模型路由程序）只在本机监听时不检查 key，所以按人的上限只能做在程序里。来源：整合方案 1.8 节引用的 [ADR 0117](0117-magpie-routes-models-through-owned-subscriptions.md#consequences)（整合方案标为 P16，当时写的是 `ADR 0117:114`）。
- 前提：OpenCode Go 的条款是 “Go and Go Plus are for workspaces with a single member”。来源：整合方案 1.8 节的 W16。这一条是风险，不是依据，见[后果](#consequences)。
- 未核实，不从它们出发推理：一个人常驻占多少内存和整机还剩多少内存、磁盘；gVisor 能否和现有沙箱同用；Cloudflare Access 同一个人用邮箱验证码和 Google 登录时身份编号是否相同；Access 名单能否用接口自动增删；生产机文件系统能否按目录设配额；Magpie 能否在本机也强制检查 key；OpenCode Go 的具体用量限制。来源：整合方案 1.3 节“未核实”清单。

## 决定

1. **方向不变：每人一个只属于自己的 Himawari。** 不做几个人共用一份记忆或私人状态。每人那一份仍然只效忠那个人，服务器和程序由 Andy 管。沿用 ADR 0083 第 1 条。
2. **只跑一套程序，每人一个数据库文件。** 程序启动一次，然后为每个人各组装一次：
   - 全程序共用的：网页入口和登录校验；一份很小的“名册”（只记谁是谁、状态、到期时间、费用上限，不存任何私人内容）；并发和排队（全机一个总数，每人一个上限，排队时轮流、前台对话优先于后台任务，给 Andy 留一个保底名额，各人的邮件检查错开时间；数字按测量定）；本机向量模型（P3-1 合并后，放在单独进程里所有人排队用）。
   - 每人一份的：一个目录，里面是这个人的数据库、密钥、恢复点、缓存、日志；自己的记忆、对话、邮件授权、推送订阅、后台任务；自己的模型配置；自己的工作目录和执行账号。
   - 每人那一份代码看到的“主人”永远是他自己，所以 [ADR 0003](0003-single-logical-agent-authority.md) 和 [ADR 0027](0027-built-in-owner-authentication.md)（已取代 ADR 0020，内置账号与外部身份两类入口）在每人那一份里照旧成立。
3. **三道防线防止写错代码读到别人的数据**（防的是代码写错，不是防主程序被攻破）：每人那一份代码手里只有自己的数据库对象，“所有人的列表”只在共用层；每个库里记着主人，打开时核对，不是期望的人就拒绝打开；记忆正文用每人自己的密钥加密。
4. **每个人执行命令时用自己专属的系统账号和沙箱。** 数据库和密钥归主程序账号，别的账号进不去；工作目录归本人的执行账号；执行进程不再直接读整个密钥目录，主程序只把这一次运行要用的密钥交给它；每个执行账号有内存、CPU、进程数的硬上限，每人的目录有磁盘配额，全机另设磁盘警戒线；磁盘配额必须做成硬上限，生产机文件系统做不到时不给别人开通（它能否做到还没核实）；所有在用账号的配额之和（含恢复点、缓存、日志）必须低于可用磁盘并留安全余量，只读测量要同时给出每人和合计的数字。这是对 [ADR 0069](0069-trust-unprotected-runtime-like-claude-code.md) 的补充：多人以后，使用者不再都是主人，所以沙箱不只防误改，还要防一个人读到另一个人的东西。gVisor 作为单独一项实测，能和现有沙箱同用就对所有人开。
5. **登录：一个网址、一个 Cloudflare Access 应用，名单里放所有受邀邮箱。** 名册里没有或已停用的人，程序立即拒绝，不等登录会话过期。只邀请，不开放注册，给谁开、什么时候停都由 Andy 决定。体验者用单独一条 Access 策略、会话设短。Gmail 授权回调所有人共用一个地址，发起授权时记下“这次授权是谁的”，回调时按记录找人，这个记录要从内存挪到共用层。现有 Gmail 设计里的安全约束照旧、并且要加强：`state` 不可猜、一次性、10 分钟有效、只认发起授权的同一台已登录设备，回调时除了查记录还要核对当前登录身份，不能只凭记录里的人名绑定；为此要加自动检查（A 的回调绑不到 B）。Andy 自己的入口沿用 ADR 0083 第 4 条（手机也走 Cloudflare 入口，见 [ADR 0082](0082-mobile-pwa-push-before-native-app.md)、[ADR 0089](0089-web-push-only-owner-entry.md)）。
6. **改表结构时：先停服，逐个文件做快照，再逐个迁移，全部做完才接请求。** 某个人的文件迁移失败，只有这个人显示“维护中”，其他人照常，同时告警给 Andy。回滚要把每个已迁移的文件恢复到快照，只换回旧版本程序不行。备份和恢复按人做。
7. **模型走 Andy 的套餐，不用 Vercel 的按量付费（Andy 2026-11-11 定）。** 这里的意思是不额外付费：对话模型照 ADR 0117 的现有顺序，可能先用排在前面的 CodeBuddy 免费额度，再用 OpenCode Go 套餐。
   - 所有人（包括 Andy）走同一条路：经本机的 Magpie，按 ADR 0117 的现有顺序选。套餐内的用量不额外花钱。
   - **同一个对话中途不换模型、不换服务方（`.agents/instructions/prompt-prefix.md` 第 8、9 条）：额度用完或路由切换只对新对话生效，已开始的对话沿用原来的路由，具体怎样按对话固定路由，实现前另出方案并加检查。别人的请求不允许落到任何按量付费的路上**（包括 Vercel AI Gateway），除非 Andy 在配置里明确打开。本 ADR 不新增、也不允许新增任何给别人用的 Vercel key。
   - 记忆向量现在走 Vercel，P3-1（向量改成本机算）上线之前不给别人开通。
   - 执行账号用防火墙按系统账号挡住，连不到 Magpie，否则从沙箱逃出来的人能绕过上限直接用套餐。
8. **每人每月的上限由 Andy 配置，代码里不写任何固定的额度数字（Andy 2026-11-11 定）。**
   - 上限存在名册里，Andy 在管理页（或命令行）按人修改，改完立刻生效，不用上线。
   - 可配的项：每人每月上限；新加的人的默认上限；其他所有人加起来的总上限（给 Andy 自己留出套餐额度）。Andy 本人默认不设上限。
   - 程序按人按月记用量，每次调用前先核对，超了就拒绝，界面显示“本月已用多少，上限多少”，本人和 Andy 都能看到。套餐内的调用没有真实账单，所以按“调用次数”和“按公开单价折算的金额”两种口径都记，Andy 配上限时选用哪种。
   - 上限只能做在程序里，因为 Magpie 在本机监听时不检查 key（见[前提](#premises)）。能让它在本机也强制检查，再把它当第二道。
   - 套餐额度用完时 Magpie 顺着现有路由往后走，但按第 7 条，别人的请求不落到按量付费的路上。
   - 自动检查里加一条反向用例：代码里出现写死的额度数字，检查必须失败。
9. **费用上限的关系。** 取代 ADR 0083 第 5 条（每个别人一把 Vercel key、每月 10 美元）。[ADR 0076](0076-no-model-cost-budget-limits.md) 删掉的是“累计总额、永不清零”的上限，仍然成立；这里加的是“按人、按月、会重置、看得见、Andy 可改”的上限，Andy 本人默认不设上限，0076 不变。
10. **删除、导出、体验。** 彻底删除一个人，按顺序、每步可重试：名册停用并断开连接和后台任务；撤销 Gmail 授权；删目录和执行账号；删名册和 Access 名单里的邮箱；逐项核对并出回执，回执写明 Cloudflare、Google 和模型服务方各自保留的日志我们删不了。含私人内容的日志写在本人目录里，随目录一起删，系统日志只留编号。导出按人做，并补上聊天记录（[ADR 0200](0200-portable-export-of-memories-and-decisions.md) 只导记忆和决定，不含对话）。体验者：开体验就是加一个人再导入示范数据，7 天到期或 3 天没人用，自动走删除流程，界面一直显示“体验到哪天结束”。
11. **Andy 的数据原样搬进新结构。** 数据库和密钥不转换。系统提示、工具定义、用的模型和服务方、数据密钥、已存的历史消息和遮盖后的输出，迁移前后必须逐字节相同，并自动比对。验收分两部分：现有 `npm run check:prompt-prefix` 只验证“只追加”的规则；“用 Andy 的旧库回放、迁移前后逐字节比对”是要新建的检查，实现时一起做。比对不过就不上线，因为 Andy 已有对话发给模型的开头一变，缓存全部失效（见 `.agents/instructions/prompt-prefix.md`）。
12. **透明和承诺。** Andy 是管理员，技术上能读所有人的文件。邀请时要明说，并告诉对方：对话内容会经过 Andy 的套餐账号，有时会走到 CodeBuddy（服务器在新加坡，ADR 0117）。Andy 承诺不读；管理页只显示用量数字，不显示任何内容。
13. **接受的剩余风险（Andy 2026-11-11 同意）：** 主程序崩了所有人一起断几十秒；Linux 内核出漏洞并被利用时，有人可能读到别人的数据；主程序内部的三道防线防不了“主程序自己被攻破”。
14. **开工顺序和条件。** 第一步是在生产机上做只读测量（内存、磁盘、各进程占用），做到能给出“这台机器最多放几个人”的数字和依据；最多几个人在量完之前不定。先做不碰生产机的部分（共用层和每人一份的拆分、执行账号和硬上限、按人迁移和恢复、费用和公平、加人删人和体验、示范数据、聊天记录导出）。ADR 0083 第 6 条的四项条件（第十一版事故修好、新版真实网页验收通过、生产连续 7 天没有“用不了”级别的事故、上线脚本按参数生成）继续约束“把 Andy 的数据迁进新结构并上线”这一步和给别人开通。ADR 0083 第 6 条原来写“条件没满足前不动代码和生产机”；这里把它缩窄为只约束碰生产机和给别人开通的步骤，依据是 Andy 2026-11-11T11:05Z 的“其余的我都同意按照你的建议”，其中就包含“先做不碰生产机的部分”。Andy 豁免剩下的条件时，在 ADR 或 Backlog 里记原话。
15. **以后的两档。** 如果测量显示 20 个人放不下一个程序的内存，或者需要更强的崩溃隔离，改成“共用入口 + 每人一个独立进程”。每人那一份的边界本来就划清了，换过去不用推倒重来。对陌生人开放注册的 SaaS 现在不做。

## 比较过的方案

- **一个程序，每人一个数据库文件（选中）**：不多花服务器钱，一次上线、一份程序；隔离靠三道防线加系统账号。代价是主程序崩了所有人一起断，内核漏洞可能越界，见第 13 条。
- **每人一套独立实例（ADR 0083）**：隔离最彻底，但内存和磁盘乘以人数、每次上线升级 N 份，生产机大概率放不下 20 份（推断），也违反“不多花服务器钱”。
- **共用入口、每人一个独立进程**：崩溃和内存超限只影响一个人。每个进程要带自己的运行环境和数据库线程，20 份大概率放不进 8 GB（推断，没有实测）。作为测量之后的备选，见第 15 条。
- **一个库按 `owner_id` 隔离（pool）**：任何一个查询漏带 `owner_id` 就泄露别人的记忆，SQLite 没有行级安全策略兜底。不采用。
- **别人每人一把 Vercel key、按月预算（ADR 0083 第 5 条）**：Andy 2026-11-11 否决，理由是 Vercel 的 API 很贵，他只用套餐内的额度。
- **上限写在代码里的固定数字**：Andy 2026-11-11 否决。上限必须由他在管理页配置。
- **让 Magpie 按 key 做上限**：Magpie 在本机监听时不检查 key，设了也拦不住；能否强制检查未核实，只作为第二道。

<a id="consequences"></a>

## 后果

- 好处：不增加服务器；一次上线；10 到 20 人的数据在文件、密钥、执行账号层面分开；别人的模型费用不产生额外账单。
- 风险（Andy 承担，说一次）：OpenCode Go 的条款写明套餐只给单人使用，多人共用不符合；如果 OpenCode 因此限制或停掉这个账号，受影响的不只是其他人，Andy 自己的 Himawari 和开发时的模型复核走的也是这个套餐，会一起停。套餐有用量限制，人多更容易碰到，碰到时所有人包括 Andy 一起变慢或被拒，所以要配“其他人加起来的总上限”。
- 代价：改表要逐个文件迁移，上线和回滚比现在复杂；每个库的读线程要改成按需启动并设全程序总上限（现在每库最多 4 个线程，20 人就是 80 个），具体数字等测量后定；浏览器里存的草稿和偏好要改成按人分开，换人登录时重新登记推送。
- 未验证的内容见[前提](#premises)的未核实清单；这些结论出来后，最多几个人、并发上限、每人资源上限的具体数字再记进 ADR 或运行手册，不在本 ADR 里写死。
- 要新增的自动检查（每条配正向和反向用例）：两个人并排访问互相隔离；文件认主人和密钥不同；每人那一份代码引用“所有人的列表”时失败；后台任务、推送、Gmail 回调不串人；沙箱和执行账号读不到别人的目录和数据库；额度和公平（含改上限不用重启、别人不落到按量付费路上、执行账号连不到 Magpie、写死额度失败）；按人迁移和回滚；彻底删除逐项核对；Andy 的对话开头迁移前后逐字节相同；新人第一次登录能绑定、别的邮箱绑不上、换人后看不到上一个人的草稿。
- 受影响的文档：ADR 0083 改为被取代；[PRD v0.2](../prd-v0.2.md) 的“目标用户”和“本版本不包含”改写；ADR 0076、0069、0117、0106、0145、0032、0200、0086、0084 各加一条指向本 ADR 的后续说明，ADR 0209 的关联条目、Idea IDEA-20261026-001 也加了说明；Backlog [BL-20261026-003](../backlog/BL-20261026-003-isolated-instance-per-person.md) 和[案例库对应案例](../engineering-casebook.md#case-multi-user)更新为新方向。[产品愿景](../product-vision.md)只有 Andy 能改，不改正文：每人那一份仍然只属于一个人，PRD 里写清“服务器由 Andy 管”。

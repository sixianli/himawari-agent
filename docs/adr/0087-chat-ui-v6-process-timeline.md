## 背景

Andy 要求把整个对话界面重做得“简洁、高级、一目了然”，标杆是最新版 ChatGPT 和 Claude；并特别要求“每一步的时间一定一定要准确”，让人一眼看出时间主要花在哪。v6 原型（`docs/assets/control-center/2026-10-26-v6/index.html`，原型里的消息、模型、耗时都是演示数据）经过 Andy 逐条批注后，他在 2026-10-26 做了下面这些决定。原话保留如下：

- 过程区样式：“我可以确定的是，呃，过程去样式这里选时间条，”（语音转写，“过程去”即“过程区”）。
- 标志：在候选页上批注“最终我决定选这一个”，并在线程里截图 A 葵盘说“最终我决定选这个”。
- 前端体积上限：“把这个体积上限去掉，不需要这个限制。”
- 语言：“用户界面 必须要完美的支持中英日三种语言。”
- 每一步的“最久”标签：“把这个醉酒去掉，没有意义啊。你既然都写，都通过图展示出来了，用户当然知道是哪一个是跑的最久的。”（“醉酒”即“最久”）
- 步骤文字：他问“这些文本是模型动态生成的吗？还是固定的？……下一个问题我说你写代码，那这里是不是要换人写代码？”，于是步骤文字改成“每类步骤一个固定动词 + 真实数据”，不写任何示例性内容。

这些是长期有效的产品决定，所以写成 ADR。原型里其余部分（回答框、输入区、侧栏、右侧文件预览）属于第二、三期，另行审核和记录。

<a id="decision"></a>

## 决定

1. **过程区用时间条。** 一轮结束后，过程区收成一行：总用时、一条按“模型 / 工具 / 等你确认 / 准备与衔接”四种颜色叠起来的细条、最久的一步。展开后每一步一行：图标、步骤文字、对齐到同一时间轴的时间条、这一步的用时；同时进行的工具调用标“同时”；模型在调用工具前说的那句话放在“思考”下面作为引文。步骤行上不再标“最久”。展开区底部列出四类各用了多久和合计，并说明“各项相加等于合计，同时进行的步骤只算一次”。运行中的一轮保持展开，当前那一步的图标和文字有动效，总用时每 0.1 秒刷新；结束后自动收起，用户自己点开或收起过就按用户的选择。
2. **步骤文字不由模型生成。** 每类步骤一个固定说法（如“搜索网页”“思考”“写回答”“等你确认”），后面跟真实数据（搜索词、文件名、记忆条数、回答字数）。由模型写意译另列待办 [BL-20261026-010](../backlog/BL-20261026-010-model-written-step-summary.md)。
3. **标志换成葵盘。** 96 个小圆点按黄金角排成向日葵花盘，界面里用内联 SVG（不再打包图片），侧栏、回答头像和新对话大图共用；回答运行时花盘缓慢转动、光从花心向外涌，系统设置“减少动态效果”时都关掉。品牌素材另存为 `assets/brand/himawari/v2/`，v1 原样保留。
4. **去掉前端体积上限。** `scripts/check-control-center-build.mjs` 不再因为压缩后体积超过 150 KiB（入口）或 192 KiB（总计）而失败，只在输出的 `sizes` 里报告体积；其余检查（不带调试映射文件、单一入口和样式文件、语言包分包、不许内联脚本和样式、不许 `eval`）全部保留。
5. **界面三语。** 所有新增和改动的界面文字都在 `zh-CN`、`en`、`ja` 三份语言包里给出，并用测试分别按三种语言渲染整个过程区，检查没有漏翻的文字。

<a id="timing"></a>

## 时间怎么算

- 起点是 Andy 按下发送（运行的 `createdAt`），终点是回答提交（运行结束时的 `updatedAt`），中间每个时刻都来自服务端在事件发生时记下的 `occurredAt`，不用浏览器收到事件的时间。
- 每一毫秒只归到一类：同一时刻有多步在进行时，按“等你确认 > 工具 > 模型 > 准备与衔接”取一类；没有任何步骤覆盖的空档算“准备与衔接”。所以同时进行的两次搜索只算一次，四类相加一定等于总用时，测试用 2026-10-26 生产上新闻那一轮（run `61268ba2`）的事件时间验证了这一点。
- 一次模型调用拆成：等模型开始回应、推理、输出。为了知道“开始输出”的准确时刻，Pi 适配器不再把 `text_start`、`toolcall_start` 两个流式事件和其他增量合并（以前合并会把时间改成最后一个增量的时间），并在消息内容里带上 `outputBoundary`；执行记录投影把它变成 `runtime.text.started`、`runtime.tool_call.started` 两种记录。旧记录没有这两种时，退回用第一段文字出现的时间。
- 一次工具调用拆成：排队和启动、执行（来自沙箱记下的 `executionTiming`）。
- **已知限制：** 执行记录里还没有“你点了允许”的时刻，所以“等你确认”目前从暂停一直算到模型重新开始，其中混着点允许之后约 1–2 秒的恢复运行。补记录的工作见 [BL-20261026-009](../backlog/BL-20261026-009-approval-click-time.md)。

时间线由前端的纯函数 `apps/control-center/src/execution-timeline.ts` 从执行记录算出，服务端不另存一份；以后如果要在别处（比如手机推送、用量页）复用，再挪到服务端。

<a id="pi-reuse"></a>

## Pi 复用与 Himawari 负责的部分

- 复用 Pi：`@earendil-works/pi-ai` 的流式事件类型（`AssistantMessageEvent` 里的 `thinking_start`、`text_start`、`toolcall_start` 等）原样使用，Pi 的执行循环和事件不改。
- Himawari 负责：事件合并策略（合并多少、哪些事件单独保留）、执行记录投影、时间线计算和界面展示。这些是产品自己的展示与审计职责，Pi 没有对应能力，也不需要在 Pi 里加。

<a id="options"></a>

## 比较过的方案

- **过程区样式：** 原型里同时给过时间条、泳道、地铁线、圆环四种画法，Andy 选了时间条；其余三种从原型里删掉。
- **步骤文字由模型写：** 读起来更自然，但每步多花 token 和时间，而且可能写错；第一期先用固定文字加真实数据，模型意译放进待办。
- **在服务端算好时间线再发给网页：** 网页更省事，但要改执行记录合同和存储；前端已经拿到全部带时间的记录，第一期在前端算。
- **体积上限放宽而不是去掉：** 能继续防止误把大依赖打进包，但 Andy 明确说不需要这个限制。体积仍在每次构建输出里报告，变大时看得到。

<a id="consequences"></a>

## 后果

- 好处：每一轮的时间花在哪一眼可见，数字与服务端记录一致，四类相加等于总用时；标志不再是图片文件；界面三语有测试保证。
- 代价：前端包不再有体积硬约束，体积变大只会在构建输出里看到，不会拦下提交；本次构建后压缩总体积 200885 字节，已超过旧上限 196608 字节。“等你确认”在补上点击时间前会多算 1–2 秒恢复运行。
- 后续：[BL-20261026-009](../backlog/BL-20261026-009-approval-click-time.md)（记录点允许的时刻）、[BL-20261026-010](../backlog/BL-20261026-010-model-written-step-summary.md)（模型写步骤意译）、[BL-20261026-011](../backlog/BL-20261026-011-edit-and-resend.md)（编辑后重新发送，属第二期）；v6 第二、三期（回答框与输入区、侧栏和文件预览）审核后另记。

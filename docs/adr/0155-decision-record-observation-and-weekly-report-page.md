## 背景

任务块 P0-8（Andy 2026-10-31 写，2026-11-03 定稿）要求：完成生产机上的“连续运行验收”，决策记录（数据库表 `decision_ledger`，记录 Himawari 每次拿主意的那张表，[ADR 0143](0143-decision-ledger-for-model-gate-decisions.md)）上线即数据起点；验收失败照修、数据照记；记下起始日期与版本。做到什么算完：生产机运行、决策记录持续写入、首份校准周报可生成。注意事项：验收失败不重置数据起点。

仓库里原来没有“连续运行验收”：Andy 在 2026-09-04 取消了连续运行天数门槛（[生产资格规格](https://github.com/sixianli/himawari-agent/blob/34de855ff109a53391cfc0d59706bcf44ba7f4a5/docs/execution/specs/2026-08-26-production-qualification-upgrade-design.md)第 182 行）。2026-11-03 Andy 在云端线程里选定：

- “连续运行验收” = 上线 + 7 天观察期 + 到期出首份校准周报。
- 周报网页和 P0-8 一起做：放在提醒页的“校准周报”标签里；数字由服务从数据库实时计算；每天的写入检查由服务自己做，结果显示在网页上。
- 不用“命中率、误扰率、已审漏报率”（词表禁用“误扰”“漏报”，[词表](../glossary.md)第 8 条）。看原型后 Andy 指出通用的“做对了 / 不该做 / 该做没做”套到具体一行上读不懂，定为每一行用自己的说法（见[决定](#decision)第 6 条）。
- 设置里“提醒检查记录”的四个统计搬到校准周报标签里，名字和算法不变（第二个 PR 做）。
- P0-8 完成 = 首份校准周报出来，且有一段连续 7 天全部通过；有失败日时起点不动，从修好后的那天重新数。
- Gmail 主动检查关掉或断开算“受阻”，不算通过；记忆暂停算受阻，不算失败；观察期内可以清除 Gmail 记录，那天会标出来。
- 起点最早是新版本第一次启动后的第二天，可以选将来的日期。

方案经过 OpenCode 两个模型（`opencode-go/deepseek-v4.1-flash`、`opencode-go/glm-5.3-flash`）两轮独立出方案和审核。审核核实了三处线程最初方案的错误，已改正：用连接记录的修改时间判断“全天连着”不成立（每次检查都会刷新它，`packages/persistence-sqlite/src/sqlite-proactive-operations.ts`）；整理记忆失败且没有改动时运行记录会被删掉，事后看不见（`sqlite-memory-consolidation-operations.ts`）；用 `node` 直接运行的脚本无法加载 `node_modules` 下的 TypeScript 包（https://nodejs.org/api/typescript.html#type-stripping-in-dependencies），但工作区包解析到仓库里的真实路径，Node 22 的类型剥离可以处理，线程实测通过。

## 决定

1. **迁移 0074 新建 4 张表**（`packages/persistence-sqlite/src/migrations/0074_ledger_observation.sql`）：
   - `ledger_observation_start`：每个 Agent 一行，记 Andy 选的起点日（日本时间）、选定时间、当时的服务版本、新版本第一次启动的时间。数据库触发器拒绝任何修改；拒绝删除，只有删除 Agent 或整个账户时随之删除。
   - `service_heartbeats`：服务运行的每个小时一行（心跳，表示“这个小时服务在跑”）。
   - `ledger_observation_checks`：每天检查的结果，只能追加，触发器拒绝修改和删除（删除 Agent 或整个账户时随之删除）。
   - `observation_events`：只追加的变化记录：Gmail 主动检查开关、Gmail 连接状态、记忆暂停、清除 Gmail 记录（含删掉的行数）、没留下运行记录的整理记忆失败。这些记录和对应的写入在同一个数据库事务里完成，只记代码和数字，不记正文。服务第一次启动时写一条当时状态的快照。
2. **服务每 15 分钟做一次**（`apps/agent-service/src/production-observation.ts`）：写当前小时的心跳；对“起点之后、已经结束超过 1 小时、还没有结果或结果是待复查”的每一天做检查，追加一条结果。服务停过，重启后会补查漏掉的日子。
3. **每天检查六项**（`packages/application/src/services/ledger-observation.ts`），每项结果是通过、失败、受阻、待复查或不适用：

   | 检查 | 失败的条件 | 其他结果 |
   | --- | --- | --- |
   | 服务一直在运行 | 当天缺了 2 个小时以上的心跳（允许 1 个小时，给重启和上线） | |
   | Gmail 检查按时写了记录 | 全天开着且连着，但从 0 点（当天清除过 Gmail 记录则从清除那一刻）到第一条、相邻两条、最后一条到 24 点之间，最长的间隔超过 2 × max(检查间隔, 单次检查上限) + 10 分钟 | 当天任何时候关掉或断开为受阻；没配置 Gmail 提醒为受阻；检查间隔超过 1 小时为受阻；当天结束后、检查前清除过 Gmail 记录，当天已无法判断，记为通过并写明清除时间 |
   | 记忆没有暂停 | | 当天任何时候暂停了自动记忆为受阻 |
   | 整理记忆和决策记录对得上 | 整理失败；整理卡在运行中超过 12 小时；整理改了 N 条记忆，决策记录却不是 N 行 | 还在运行且不到 12 小时为待复查；当天没整理为不适用 |
   | 已检查过的日子没有少记录 | 之前检查过的日子（最近 60 天），某类决策的行数比当时少，又不能由之后的“清除 Gmail 记录”解释 | 少的只是 Gmail 那一类，且之后清除掉的行数够解释少掉的行数（一次清除的行数按时间顺序分给检查得早的日子，同一行不重复使用），记为通过并写明解释了多少行 |
   | 时间格式正确 | 当天有不是 UTC 毫秒加 Z 的时间 | |

   开关、连接、记忆暂停的状态按变化记录重放推算，从服务第一次启动时写下的状态快照开始（是否要写快照只看有没有快照，不看有没有别的记录）。检查时读取截至检查时刻的所有变化记录，所以当天结束后、检查前发生的整理失败和清除也会被看到。同一时刻的多条记录按写入时分配的顺序号重放。受阻的原因取当天第一次受阻时的状态（先关掉后又打开，原因仍是“关掉过”）。清除 Gmail 记录时删掉 0 行就不写记录。一天的状态取最严重的一项：失败 > 待复查 > 受阻 > 通过。网页上另有“没有检查记录”（已经结束一小时以上却没有结果）和“未到”两种状态，由服务读取时算出，不存表。
4. **数据起点由 Andy 在网页上设置一次**：命令 `proactive.observation.start`，执行前用已有的近期身份验证（和删除对话同一套，`RecentAuthenticationGuardPort`）再确认一次。起点不能早于新版本第一次启动（最早一条心跳）的下一个日本时间日，不能晚于今天之后 30 天。第二次设置被拒绝（`LEDGER_OBSERVATION_START_ALREADY_SET`）。
5. **观察期和验收**：观察窗口是从起点开始的 7 个日本时间日；首份校准周报在起点后第 7 天 0 点之后可以生成。验收通过 = 首份校准周报可生成，且检查结果里有连续 7 天“通过”（失败、受阻、没有检查记录都会让连续天数归零，待复查不算中断）。失败照事故规则处理（`.claude/rules/incident-gates.md`），起点不动。
6. **一套统计定义，网页和脚本共用**：周报的计算和查询语句搬进新的工作区包 `packages/calibration`（TypeScript，零依赖）；`scripts/calibration-report/` 改为调用它，并加 `--revision` 参数。按决策类型的行和“每天打分”的分组一致，每一行只列它可能出现的两种情况，用自己的说法：

   | 行 | 比例 |
   | --- | --- |
   | 读完邮件提醒了你 | 提醒得对 · 不该提醒 |
   | 读完邮件没提醒 | 不提醒是对的 · 该提醒没提醒 |
   | 系统没存下的记忆 | 不存是对的 · 该存没存 |
   | 已存的记忆 | 存对了 · 不该存 |
   | 整理记忆 | 整理得对 · 不该整理 |

   其余类型折叠。Gmail 主动检查拆成两行，因为提醒了和没提醒是两种决定，合在一起时“提醒得对”会把“不提醒是对的”也算进去。这两行的单位是“一次读邮件”（Himawari 每 15 分钟读一次新邮件），Andy 看原型后指出原来的“这次检查没提醒”看不出是关于什么的，改为“读完邮件提醒了你 / 读完邮件没提醒”，“每天打分”的标签同步改名。比例 = 这种情况的条数 ÷ 你评过的条数。历史记录格式升为 `himawari-calibration-week.v2`（以前没有生产数据，不需要迁移旧记录）。
7. **网页读取接口**：`proactive.weekly.read`（返回前按合同校验，不合格就报错，不把不合格的数据交给网页）返回观察期卡片（起点、最早可选日、第几天、7 个格子和每格的检查明细、连续通过天数、是否已验收）和校准周报（默认是观察窗口；窗口没结束时 `ratesWithheld` 为真，不返回任何比例）。
8. **服务版本**：上线打包时把提交号写进 `agent-service` 包的 `build-info.json`（与网页的版本号同一来源 `apps/control-center/build-info.mjs`），服务启动时读取，读不到记为 `development`。版本号只写进数据库和网页，不进入发给模型的内容。

<a id="options"></a>

## 放弃的做法

- **Mac 线程每天在生产机上跑检查脚本**（本 PR 的第一版方案）：Andy 选择服务自己算、显示在网页上；也省掉把脚本带上生产机的问题。
- **在服务里给决策记录写“心跳决策”**：会混进周报的分母，心跳单独一张表。
- **按“每种决策每天至少一行”判定**：记忆候选、整理、截断都只在发生时写，没有对话就没有行是正常的。
- **在数据库之外再写一份带哈希链的日志，防止整库被换**：同一台机器上两份可以一起被换，备份和 Runbook 的核对已覆盖。
- **不删除失败的整理运行记录**：会让当天无法重试（每天一行的唯一约束），改为删除前写一条失败事件。
- **起点只能用命令行设置**：Andy 平时只用网页和云端线程。

<a id="consequences"></a>

## 后果

- 门槛（会自动拦下的测试）：
  - `test/integration/ledger-observation-store.test.ts`：起点只能写一次，直接改、删起点和检查结果被触发器拒绝；开关、连接、记忆暂停只在真的变化时写事件；清除 Gmail 记录写下删掉的行数。
  - `packages/application/test/ledger-observation.unit.test.ts`：正常的一天通过；服务停 3 小时失败；Gmail 中途关掉为受阻而不是通过；记忆暂停为受阻；没有状态记录时不被无关记录带偏；当天或检查前清除 Gmail 记录不判 Gmail 断档；清除的行数少于丢失的行数仍判失败；整理改了 3 条只记了 2 行失败；整理失败但没留运行记录失败；跨午夜还在跑的整理为待复查，超过 12 小时失败；之前检查过的日子行数变少失败，清除过 Gmail 记录则通过；连续通过天数在失败后归零。
  - `test/integration/ledger-observation-service.test.ts`：起点早于第一次启动后的第二天、晚于 30 天、第二次设置都被拒绝；服务停了两天后补查出三条结果；网页接口的返回通过合同校验，窗口没结束时不返回比例；没有近期身份验证时网关拒绝设置起点（删掉这段校验，这条测试失败，已实测）。
  - `test/integration/calibration-report.test.ts`：原有手算数字不变；用 `node` 单独运行脚本能出报告并把 `--revision` 写进历史。
- 生产上线后，服务第一次启动就开始写心跳；起点要等 Andy 在网页上设置之后才开始检查。网页的“校准周报”标签在第二个 PR 里实现，在那之前只能通过接口读取。
- 每天检查读到的“当前开关状态”只在没有任何事件时作为后备；有事件后按事件重放，第一条是服务启动时的快照。
- 已知盲区：整理记忆对记忆本身的修改和写决策记录不在同一个事务里（[ADR 0143](0143-decision-ledger-for-model-gate-decisions.md) 后果一节），崩在两步之间时检查看不出来。
- 观察期失败要按事故规则加门槛；本 ADR 不新增事故行。

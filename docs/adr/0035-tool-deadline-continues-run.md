# ADR 0035：工具超过期限后，模型收到确定的超时错误，本轮继续

<a id="context"></a>

## 背景

一轮对话（下称 Run，即用户发出一条消息后 Agent 处理并回答的整个过程）里，模型可以多次调用工具，例如读文件、运行命令。每次工具调用有自己的执行期限（下称工具期限）；整轮对话另有一个更长的期限（下称 Run 期限）。

工具在沙箱里由 Job Host（为每次工具调用单独启动的监督进程）运行。工具超过期限时，Job Host 会终止它并完成清理。2026-09-28 的工具执行排查（编号 TE-09）发现：Agent（负责对话的服务进程）等待工具结果的截止时间恰好等于工具期限，Job Host 还没来得及报告“已按期限终止并清理”，Agent 就先放弃等待，把结果记成“不知道成没成功”。于是这一轮一直停在“核对中”，最长要等到 Run 期限才以失败结束。

要修复这个问题，必须先决定：一次工具超时之后，这一轮对话是继续还是结束。这是用户能直接感受到的产品行为，以后的工具类型、执行后端也都要遵守，所以单独记录。

<a id="decision"></a>

## 决定

1. **工具超时是这次工具调用的失败，不是整轮对话的失败。** 工具超过期限、Job Host 确认已终止并完成经过认证的清理后，模型只收到一次固定说明（原因码 `SANDBOX_TOOL_DEADLINE_EXCEEDED`）：“工具运行超过期限，已被终止并完成清理，没有重新执行。它在终止前可能已经修改了工作区，部分输出不可用；请先检查当前状态再决定下一步。”然后由模型在这一轮剩余的时间里决定下一步。
2. **不重新执行，不把部分输出当成功。** 超时前产生的输出只作为受保护的证据保存，不交给模型。命令和写入的效果按“未知”处理，不能说成“确认没有修改”。
3. **期限不延长，授权检查不放宽。** 工具期限和 Run 期限都不改。Agent 只把等待清理汇报的截止时间放宽到“工具期限 + 已有的清理汇报余量”，并且不超过 Run 期限。结果交给模型之前，对授权撤销、Run 权限等的检查，不因为工具期限已过而跳过。
4. **Run 期限是最后的兜底。** 如果到 Run 期限仍没有确定结果，那么只有在所有资源都确认释放之后，才把这一轮结束为失败。

用户在 2026-09-29 确认采用本决定。

<a id="options"></a>

## 比较过的方案

### 方案 A：工具超时后本轮继续（采用）

- 好处：一个慢命令（例如一次较慢的测试）不会让整轮对话作废；模型能看到明确的超时原因，可以换个办法或者向用户说明。常见的编码助手也是这样处理的。
- 代价：模型继续工作时，工作区可能已经被超时的命令改了一部分。固定说明要求模型先检查当前状态，但不能保证模型一定做对。

### 方案 B：工具超时后整轮直接失败

- 好处：实现简单，不存在“超时后继续操作半改过的工作区”的情况。
- 代价：任何一次超时都让用户这一轮的等待白费，需要重新发消息；对经常运行测试、构建的编码场景不合理。

<a id="consequences"></a>

## 后果

- 好处：工具超时不再让这一轮卡在“核对中”，也不会让整轮对话作废。
- 代价：超时的写入或命令可能留下部分修改，只能靠固定说明提醒模型先检查，产品不自动回滚。
- 后续：新增的工具类型和执行后端（例如以后的远端执行）也必须遵守这个规则：超时的是这次工具调用，确认终止并清理后交回确定错误，不重新执行，不延长期限。

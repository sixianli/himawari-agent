# ADR 0038：按层级和触发条件安排本机测试，完整测试按交付批次运行

<a id="context"></a>

## 背景

本项目的完整测试（先构建安装包，再运行 `npm test` 里的 unit 单元测试、contracts 接口约定测试、integration 集成测试、e2e 端到端测试、pi-compat Pi 兼容测试五组，共约 4,900 条）在开发 Mac 上每次要 12–15 分钟，其中 100 个集成测试文件串行运行，约占 11 分钟。

2026-09-28 起的工具执行排查第二轮要求“每个独立缺陷在完整测试通过后单独提交”。统计第二轮证据：每个缺陷的定向测试（只跑复现缺陷的测试和直接相关的测试文件）合计 1–3 分钟，静态检查 `npm run check` 每次约 0.4 分钟，而完整测试每个缺陷要 12–28 分钟（缺陷 F 因为跑完才发现新问题，跑了两次）。修缺陷 F 共用了 76 分钟，完整测试占 28 分钟。完整测试成了交付速度的主要瓶颈，而它发现的问题大多本可以更早用定向测试或受影响模块的测试发现。

这条规则决定以后所有开发任务什么时候跑哪一层测试，需要长期遵守，所以单独记录。

<a id="decision"></a>

## 决定

用户在 2026-09-29 确认：按改动风险逐层扩大测试范围；完整测试按交付批次运行，不再每个缺陷各跑一次；这是项目的长期规则。

<a id="layers"></a>

### 测试层级和触发条件

| 层级 | 内容 | 什么时候运行 |
| --- | --- | --- |
| 第 0 层：定向测试 | 能复现缺陷或验证新行为的测试，以及直接相关的测试文件，例如用测试运行工具 Vitest 执行 `vitest run --project integration <文件> -t <用例名>` | 改生产代码之前先运行，证明它失败；之后每次修改都运行同一测试 |
| 第 1 层：静态检查 | `npm run check`（格式、代码规范、类型、模块边界等） | 每次提交之前 |
| 第 2 层：受影响模块测试 | 改动所在的整个测试组（例如整个 unit 组约 1.4 分钟），以及引用了被改模块的集成测试文件 | 一个缺陷或功能修稳定、准备提交时 |
| 第 3 层：完整测试 | 构建安装包，再运行完整 `npm test` | 一批改动准备交付审核或验收时；推送、开 PR（合并请求）或合并之前；一轮工作结束时；以及[提前运行完整测试的情况](#early-full) |
| 第 4 层：Mac 真实产品路径 | 在本机真实安装后，按用户操作走一遍产品场景 | 改动影响安装、升级、进程管理或沙箱运行时行为时，只运行相关场景；运行全部场景、不加筛选的完整版本，只在一轮工作结束或发布之前运行 |
| 第 5 层：Linux/Hermes 服务器验证 | 在 Hermes 服务器上安装并验证 | 部署之前，并且每次都要先得到用户同意 |

补充规则：

- **一批**指一起交付审核或验收的一组改动，通常不超过 3 个互相独立的缺陷，这样完整测试失败时容易定位原因。
- **先自查，再跑完整测试。** 启动第 3 层之前，先完成第 0–2 层、自查代码和相关文档，避免完整测试跑完后又改生产代码而不得不重跑。
- **完整测试失败时**，回到第 0 层复现并修复，通过第 0–2 层后，只对这一批的最终版本再跑一次第 3 层。
- **只改文档**时，只运行文档校验和 Runbook（操作手册）的封存检查，不运行产品测试。

<a id="early-full"></a>

### 提前运行完整测试的情况

改动涉及下列公共部分时，影响范围很难只靠定向测试判断，这一次改动就要单独跑第 3 层，不等到一批结束：

- 产品数据库（SQLite）的表结构或迁移；
- Agent Service（负责对话和数据库的服务进程）与 Execution Worker（执行工具的进程）之间的通信协议、认证或握手；
- 构建和打包配置、依赖声明或锁文件；
- 测试运行方式本身，例如 Vitest 的配置、`scripts/ci/` 下的测试脚本或 `ci/policy.json`。

<a id="commits"></a>

### 提交与结果复用

- 每个独立缺陷仍然单独提交，提交前必须通过第 0–2 层。提交说明和交付记录只能写实际跑过的层级；中间提交没有单独跑过完整测试时，不能说它“通过了完整测试”，而要写明完整测试覆盖的是哪个版本。
- 代码、依赖、测试配置和相关环境都没有变化时，已有的测试结果可以继续使用；只补写结果说明不会让产品测试结果失效。生产代码又改动时，要重新判断哪些结果已经失效。
- 本决定只规定本机开发时的测试时机。GitHub 上合并 PR 之前，CI（代码推送后在 GitHub 上自动运行的检查）必须通过的检查集合仍由 `ci/policy.json` 规定，不因本决定减少。

<a id="options"></a>

## 比较过的方案

### 方案 A：每个缺陷提交前都跑完整测试（原做法）

- 好处：每个提交都单独经过完整测试，出问题时立刻知道是哪个改动引起的。
- 代价：每个缺陷至少多花 13–15 分钟；多数时间用在反复确认与本次改动无关的功能上。

### 方案 B：按层级扩大，完整测试按交付批次运行（采用）

- 好处：开发时反馈快；一批 3 个缺陷大约能省下 2 次完整测试（约 30 分钟）；改到公共部分时仍提前跑完整测试，不会把大范围风险拖到最后。
- 代价：中间提交没有单独跑过完整测试；如果一批最后的完整测试失败，需要多花一些时间判断是哪个改动引起的。每个缺陷都经过第 2 层测试，可以降低这种情况出现的概率。

### 方案 C：只在一轮工作结束时跑一次完整测试

- 好处：最快。
- 代价：一轮里可能积累了很多改动，失败后定位成本最高，问题也发现得最晚。

<a id="consequences"></a>

## 后果

- 好处：完整测试次数明显减少，开发过程中的反馈更快；各层测试什么时候跑有明确条件，不再靠每次临时判断。
- 代价：交付记录要说清楚完整测试覆盖的是哪个版本；“一批”的范围需要在任务说明或交接里写明。
- 后续：
  - 集成测试串行运行约占完整测试的 11 分钟。2026-09-29 用户要求立即研究能否安全地并行运行（2026-09-03 的 CI 计划曾因并行出现超时而保持串行），结论和实现由单独的任务记录。
  - 进行中的工具执行排查第二轮从缺陷 B1 起按本决定执行。

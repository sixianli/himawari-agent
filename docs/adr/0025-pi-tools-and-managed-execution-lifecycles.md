# ADR 0025：复用 Pi 并分离工具、任务与执行环境生命周期

## 背景

Owner 在审查通用工具与沙箱的官方实践、Pi 固定版本工具接口和本项目接入之后，于 2026-09-09 批准本方案并要求落入架构、Spec 和 Plan。决定的核心是采用分离的执行合同：工具调用报告操作事实，后台任务与服务保有明确所有者，执行环境独立报告监管与清理。不能只为读取文件增加特殊成功条件，也不能用一个命令的退出码代表全部副作用和环境已清理。

Pi 提供工具定义、执行算法及 Operations 注入点，并提供 SRT、SSH、Gondolin 示例。Operations 并未覆盖全部 I/O：搜索器启动、读取路径探测和长输出临时文件仍可发生在工具实现中。因此执行整个工具实现的位置也是安全边界。示例体现扩展模式，不等于具备产品授权、故障恢复或平台资格。

本决定替代 ADR 0024 的单一作业生命周期表达；按仓库治理要求，0021/0022/0024 的当前替代指针都指向本文，0024 曾替代 0021/0022 的事实保留在其原正文，完整承接其 SRT 本地主机路线和首批能力，不恢复已否决的 Mac helper/Apple container 强制分层。ADR 0023 的通用审批与恢复继续有效。accepted 表示设计已获批准，不表示新合同、后台任务、服务监管或平台资格已实现。

## 决定

采用以 Pi 为工具实现、以 Himawari 为授权与持久权威、以合格执行后端为隔离边界的统一治理合同，分别表达工具调用、受管理任务/服务及执行环境生命周期。

1. 模型侧复用 Pi 工具定义和 Agent loop，只提交操作意图；实际 coding tool 实现运行在目标 Worker 管理的受限 runner 中。Operations 用于授权衔接和执行路由，不能作为唯一 I/O 隔离证明。优先复用、配置或薄适配 Pi，不建设第二套工具框架、模型循环或 MCP 协议。
2. 沿现有 Capability invocation、Grant/Handle、受保护 Payload、认证通道及 SQLite 作业观察扩展。工具调用身份、输入和权限不从命令、环境变量或子进程输出推导；准入与启动均检查当前权威，不重复消费同一授权。
3. 执行合同区分一次性操作、受管理后台任务和持续连接服务。前台命令保留 Pi Bash 语义；后台操作通过 Pi 扩展机制返回产品任务句柄；MCP 请求与 server 连接分别管理。持续运行必须具有冻结范围、期限、资源责任和停止入口，不等于任意脱离子进程获准存活。
4. 工具结果、副作用证据、监管状态及清理状态分别保存。命令正常退出可成为命令结果；业务成功遵守操作自身可核实的后置条件。结果可被保存并在披露许可内呈现，不意味着环境可复用或 Run 可正常结束。未知副作用、监管失联和未满足的必要后置条件继续阻止依赖动作及未经证实的成功声明。
5. SRT 继续是直接操作已授权宿主目录的首选后端。每个权限固定的环境使用独立 Job Host 和一次初始化的 manager；一次性作业默认独占环境。持续任务/服务仅在同一 Run、同一冻结授权范围内保有自己的环境，不跨 Grant 合并权限，不共享全局可变 manager。
6. 平台资格分别证明文件/网络限制、监管、停止、资源观测与清理。Mac 的尽力停止和脱离后代可能存活限制继续如实披露；不把未知改成已确认，也不因此降低其他平台保证。需要更强隔离时可以评估 Gondolin、容器或远端后端；未通过资格不得启用或自动回退，不把 VM 安装变成本地功能的统一前置条件。
7. 取消是停止请求，不是副作用未发生的证明。采用有界停止、结果核查和持久隔离；重启、重新审批、换主机、换 attempt 都不得成为未知操作的自动重放通道。逻辑隔离只阻止产品调度，不能宣称已撤回仍存活进程的 OS 权限。
8. 保留原目录读写/编辑/搜索、Shell、MCP、授权联网与依赖安装、真实 Web Search 和 GitHub 已有 commit 推送的首批范围。高风险动作及披露独立检查。push 仍绑定仓库/ref/OID，复用标准 Git，凭据只交给专用传输，监控仍只读；不隐含创建 commit、强推、发布或修改账户权限。

## 比较过的方案

### 给读取文件增加清理未知时的成功例外

能处理局部返回值，却不能解释写入、Shell、后台服务和 MCP 的完成语义，也无法形成一致的恢复规则。不采用。

### 每次工具调用必须销毁完整执行环境后才返回任何结果

对独占的一次性环境容易理解，但把操作事实与资源回收混在一起，无法自然支持开发服务器和持续 MCP；清理故障还会掩盖已经发生的外部效果。不作为通用合同。独占环境仍有清理义务，未知环境仍不得复用。

### 直接安装 Pi 沙箱示例或所有工具共用一个 Run 沙箱

能复用示例代码，但 Bash 包装遗漏其他 I/O，示例回退和默认权限不满足产品要求；共享可变权限会把不同审批累积成更宽的能力。不采用这些默认行为。

### 全部迁移到 Gondolin 或云端沙箱

对独立工作区有价值，但不是宿主原目录权限和远端 API 授权的替代品，挂载仍可能写回宿主，平台和恢复资格也需单独验证。不作为无条件替换 SRT 的方案。

### Pi 工具复用与分离的执行生命周期

保留成熟工具行为和现有权威，以受限 runner 覆盖工具内部 I/O，并让任务/服务持有可观测生命周期。采用；代价是需要版本化完成语义、持久任务句柄、核查与升级规则，而非只改一个成功条件。

## 影响

- 工具语义保持一致；Himawari 增加的是产品授权、受管理资源和证据责任。
- 旧完成回执按旧版本解释；旧 unknown 不会因新设计自动转为成功。迁移只增加新合同和观察，不重写历史。
- 结果发布、后续动作准入、环境复用和 Run 完成各有明确判断；UI 必须能表达“已有结果但资源待核查”。
- 强保证依赖后端真实能力，不能靠新增枚举值获得。后台任务只在已经批准的范围和期限内存活；跨 Run 长期服务并未由本决定自动授权。
- 执行原目录会产生真实修改；保护已有变更与并发冲突，取消后禁止自动 reset。凭据及远端副作用继续由狭窄产品适配控制。
- 实施、实际主机测试、外部服务验收及 Runbook 变更分别按 Plan 完成；本次设计不自动启用新执行能力。

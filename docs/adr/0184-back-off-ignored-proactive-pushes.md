# ADR 0184：同一类主动推送连续被忽略时自动降频

<a id="context"></a>

## 背景

任务块 PA-6（Andy 2026-11-08 写，同日回“同意”变更清单，N 取 3）。周报是事后的；同一类提醒一旦被误扰，会一直打扰到下次有人改规则。业界对通知的做法是连续几次没回应就拉长间隔，再没回应就暂停。依据的是用户主权（Andy 的注意力归他控制，系统自己退让、一键恢复）和边界与可逆性（只降频，不删规则，可恢复）。

对着代码核对的现状（main 01873f5）：

- 主动检查只有两种情况发网页推送：高优先级、48 小时内到期的“要你做事”，以及命中地板规则的“可能重要，请看原信”。其余提醒只进提醒页。
- 点开记录在 `web_push_feedback.opened_at`（迁移 0061），隐式信号在 `decision_signals`（ADR 0182，迁移 0080）。
- 发件人和标题加密存放，库里没有明文发件人，所以按发件人分类要在检查时记下分类键。

<a id="decision"></a>

## 决定

1. **“同一类”= 推送理由类型 + 发件人域名**，键形如 `due:service.example.com`。目前可降频的理由类型只有“到期提醒”（`due`）。键存在新列 `source_insights.push_class`，只在该提醒真的排进推送时写入（迁移 0081）。域名明文存放，和重要发件人设置同级（迁移 0086 之前存在 `proactive_settings.important_senders`，之后存在 `rule_book_rules` 里的 `floor_important_sender` 规则，见 [ADR 0209](0209-rule-book-with-cel-expressions-and-judge.md)），不存邮件地址、标题或正文。
2. **地板规则命中的提醒不分类、不计数、不降频**：命中重要发件人、go.jp/lg.jp/ac.jp/ed.jp 或金钱词的提醒，`push_class` 为空，不进入下面的任何计算。
3. **什么算一次“被忽略”**：这一类的一条推送，满足任一条：Andy 把对应提醒评为“不需要”；或推送发出满 24 小时仍没点开。一条推送只算一次，不管它带了几条同域名提醒（同一条推送里只要有一条被点开就算被点开，点开优先于“不需要”）；只数推送服务返回成功（2xx）、推送反馈表里有发送记录的推送，没有订阅或发送失败的不计。从最近一条往前数连续的被忽略数，遇到一条被点开的就停（计数清零）；发出不满 24 小时且未被评价的先不计。只数本台阶开始之后发出的推送。
4. **降频台阶**（N = `runPolicy.proactive.backoffThreshold`，缺省 3，范围 0 到 10，0 表示关闭）：连续被忽略 N 次进入第 1 台阶：这一类最多每 24 小时推送 1 条；在第 1 台阶上再连续被忽略 N 次进入第 2 台阶：暂停推送，直到恢复。进入台阶的那次检查本身就被压（所以“第 N+1 次被降频”）。被压的提醒仍写进提醒页，不删任何规则。
5. **记录**：进入台阶的那次检查，如果没有别的推送发出，决策记录的 `reason_code` 为 `PUSH_BACKED_OFF`；之后被压的检查为 `PUSH_SUPPRESSED`，结论用已有的 `silent`，不改决策记录表。同一次检查里还有别的推送发出时，沿用原来的 `URGENT`、`QUIET_HOURS`，台阶变化只记在状态表里。每一类的台阶、起算时间、触发时被忽略的次数、触发那次检查的编号存在新表 `proactive_push_backoff`，和这次检查的记录在同一个事务里写；写入时核对读取时的台阶、起算时间和更新时间，对不上（比如读取之后 Andy 点了恢复）就不写，恢复优先。`ignored_count` 最多记 1000。断开 Gmail 或清除全部主动记录时一并清掉这张表。
6. **恢复**：网页提醒页每个被降频的类别一个“恢复推送”按钮，命令 `proactive.backoff.restore`；恢复后台阶清零、从恢复时刻重新数，下一条立即推送。
7. **不新增模型调用、不新增提示词、不改系统提示和工具定义**，所以不影响请求开头的缓存。

<a id="options"></a>

## 放弃的做法

- **按单个发件人地址分类**：一直换地址的通知永远数不到 N。
- **只按理由类型分类**：一个误扰源会拖累所有到期提醒。
- **让模型判断“这一类是否该降频”**：要新增模型调用和提示词，结果不稳定，也违背“规则写进程序、必定执行”。
- **把台阶状态现算而不存**：恢复和台阶起点需要持久标记，现算会让“恢复后立即生效”做不到。
- **聊天里一句话恢复**：需要新增一个工具，会改工具定义，使已冻结的对话请求开头失效一次（`.agents/instructions/prompt-prefix.md` 第 7 条）。本次不做，网页按钮已满足；要做另出方案。
- **恢复也写一条决策记录**：恢复没有对应的检查，写进决策记录会出现一条没有检查的“沉默”行，污染周报的沉默样本。恢复时间存在状态表的 `restored_at`。

<a id="consequences"></a>

## 后果

- 门槛（会自动拦下的测试）：
  - `test/integration/proactive-mail-check.test.ts` 的 `[PA-6]` 一组：连续 3 次忽略后第 4 次被压且有 `PUSH_BACKED_OFF` 记录；第 1 台阶每天放行 1 条，再忽略 3 次后暂停；评“不需要”算忽略；恢复后立即推送；反向：差 1 次、中间点开过、别的发件人域名、地板规则命中（含发件人域名在重要名单里）、阈值 0 都照常推送。
  - `test/integration/proactive-production.test.ts` 的 `[PA-6]`：总览里能看到被降频的类别，恢复命令生效，恢复不存在的类别被拒绝。
  - `apps/control-center/test/proactive-interactions.unit.test.ts` 的 `[PA-6]`：有降频类别时显示说明和按钮，没有时什么都不显示。
  - `packages/platform-node/test/startup-configuration.unit.test.ts`：缺省 3，范围外被拒绝。
- 上线后数据库最低可写版本变成 81，回退到旧程序会被拒绝。
- 已知局限：被忽略只看网页推送的点开和提醒评价，没有订阅或发送失败的推送不计（见决定第 3 条）；一条提醒被后来的检查更新后，只有最近一次推送算数；清除全部主动记录时一并清掉降频状态。
- 真实环境验收要等上线后在 Hermes 做：用真实账号让一类提醒连续被忽略，确认被压和恢复。

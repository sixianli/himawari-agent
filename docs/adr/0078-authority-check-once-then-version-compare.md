# ADR 0078：沙箱运行中的授权核对先完整做一次，之后按版本号比对，最长 60 秒重新完整核对

<a id="context"></a>

## 背景

沙箱（用操作系统机制限制程序能访问的文件和网络的隔离环境）里的命令运行时，Worker（受限执行进程）每 250 毫秒向服务进程发一次 `resolve`（重新确认本次执行仍被允许的请求）；出口代理（替沙箱转发网络请求、并检查目标是否被允许的程序）每建立一个连接也要确认两次。每次 `resolve` 都在服务进程里做一遍完整授权核对：读部署快照、核验宿主安装（`verifySandboxHost`）、读执行范围、重新判断授权（目录授权、联网授权、设置）、确认工作区身份。

2026-10-25 生产机日志（受保护安装，37 次样本）里，一次完整核对的中位数约 150 毫秒：宿主核验中位 76 毫秒（最长 1257 毫秒），授权判断中位 59 毫秒（最长 603 毫秒）。一个运行几秒的命令要做几十次，出口连接越多次数越多。

2026-10-26 我们按主流做法给了方案：开头完整核对一次，之后只比对“授权有没有变过”的版本号，最长 60 秒必须重新完整核对一次。Andy 在方案文档里的决定（原话）：

问题：授权核对方案 A（开头完整核对一次，之后在内存里按版本号比对，最长 60 秒必须重新完整核对；撤销时主动通知正在跑的任务立刻停）是否采用？

<a id="decision"></a>

## 决定

1. **只对已经启动的执行复用核对结果。** 执行的准入、绑定和启动（`verifyStart`）仍然每次完整核对。只有记录已进入 `bound`（已绑定、正在运行）阶段时，`resolve` 的结果才会被记在服务进程内存里，按执行身份、资源序号和操作修订号区分；不写磁盘，服务重启后全部作废。
2. **每次 `resolve` 都先做实时回执检查。** 回执（本次工具调用被允许执行的凭据记录）每次都从数据库实时读取，会检查运行仍在进行、调用句柄未被撤销、能力状态、授权本身和部署栅栏（防止旧服务实例继续操作的编号）。这一步不复用。
3. **版本号由两部分组成，变了就重新完整核对。**
   - 授权版本：数据库里新增一个计数器 `authority_revision`，由触发器（数据库在写入时自动执行的语句）维护。`grants`（授权）、`approval_requests`（审批请求）、`authorization_reservations` 和 `authorization_usage`（授权的预占和用量）、`capability_declarations` 和 `capability_handles`（能力声明和调用句柄）、`product_state_records`（设置、目录授权等产品状态）任何一行新增、修改或删除，计数器都加一。
   - 宿主身份：`sandboxHostIdentity` 对私有目录、工作区根目录、只读工具链路径、运行时根目录、可执行文件和 runner 逐个取文件自身信息（设备号、inode 编号、权限、所有者），受保护安装还加上保护清单文件的状态变更时间，算出一个摘要。工作区根目录里新建文件不会改变它，根目录或程序文件被替换会改变它。
4. **完整核对前后各取一次版本号，两次相同才记下结果。** 核对过程中授权被改了，这次结果不保存，下一次照常完整核对。
5. **记下的结果最长用 60 秒**（`RESOLVED_AUTHORITY_REUSE_MS`）。超过 60 秒，或者时钟往回走，下一次 `resolve` 重新完整核对。
6. **撤销靠 Worker 原有的 250 毫秒轮询发现。** 撤销授权或调用句柄会改变计数器或让实时回执检查失败，下一次轮询（最长约 250 毫秒后）就会走完整核对并失败，Worker 照原有逻辑停止命令。

<a id="deviation"></a>

## 与原方案的差别

方案文档里写的是“撤销时通过 `work.cancel` 主动通知，再每 2 秒查一次版本号”。实现时没有另建主动通知，而是保留现有的 250 毫秒轮询，原因是：

- 原方案加主动通知，是因为每次轮询要做约 150 毫秒的完整核对，只能把轮询放慢到 2 秒，再用主动通知弥补变慢的那部分。
- 复用之后，一次轮询只剩实时回执读取和版本号计算（一次数据库单行读取加十几次 `lstat`），250 毫秒轮询的开销已经很小，发现撤销的时间（约 250 毫秒）比“2 秒轮询加主动通知”的兜底更短。
- 不新增通知通道，就不用处理通知丢失、重复和重启后重连这些新的故障情况。

“撤销后正在跑的任务立刻停”这一要求不变，由 250 毫秒轮询满足。

<a id="amendments"></a>

## 与 ADR 0069 的关系

[ADR 0069](0069-trust-unprotected-runtime-like-claude-code.md) 第 3 条规定每次调用都检查各路径（绝对路径、规范路径、不是符号链接、组和其他用户不能写、所有者合格、工作区根目录设备号和 inode 与登记一致）。本 ADR 起：

- 执行准入、绑定和启动时，这些检查照旧每次完整执行。
- 执行运行中的 `resolve`，60 秒内只要宿主身份摘要没变，就不再逐项重做这些检查。摘要用到的权限、所有者、设备号和 inode 编号正好覆盖“是否被替换、是否变成符号链接、是否能被别人写、所有者是否合格”；通过上层目录换掉路径的情况由 60 秒的完整重查兜底。

ADR 0067 里否决的“按时间缓存核验结果”已由 ADR 0069 取代，本 ADR 不按时间单独信任结果：复用要求版本号不变，60 秒只是复用的上限。

<a id="options"></a>

## 比较过的方案

- **每次 `resolve` 都完整核对（原做法）**：不采用。生产中位约 150 毫秒一次，运行中的命令和出口连接会反复付这笔开销。
- **只按时间缓存，不比对版本号**：不采用。撤销授权后要等缓存过期才能发现。
- **主动通知加 2 秒版本号轮询（方案文档原写法）**：不采用，理由见[与原方案的差别](#deviation)。
- **启动时核对一次，之后完全不再核对**：不采用。撤销授权后正在运行的命令停不下来。

<a id="consequences"></a>

## 后果

- 好处：运行中的命令和每次出口连接的授权确认，从一次完整核对（生产中位约 150 毫秒）降到一次实时回执读取加版本号计算。实际耗时在上线后实测记录。
- 限制：工作区根目录内部的子目录在 60 秒内被替换，运行中的确认不会立刻发现，最晚在 60 秒的完整重查时发现；执行启动时的核对不受影响。
- 限制：以后的迁移如果重建上述任一张表，SQLite 会一起删掉表上的触发器。`packages/persistence-sqlite/test/sqlite-worker-protocol.unit.test.ts` 里带 `[NL-4]` 标签的测试会在全部迁移之后检查每张表的三个触发器都在，缺少时测试失败。
- 测试：复用、撤销、版本变化、60 秒过期、时钟回退、核对中版本变化和未启动执行不复用的测试在 `apps/agent-service/test/production-payload-broker-handler.unit.test.ts`；宿主身份摘要的测试在 `packages/platform-node/test/sandbox-host-verifier.unit.test.ts`，都带 `[NL-4]` 标签。

## 背景

[ADR 0041](0041-test-hosts-and-production-server.md)（它取代了 [ADR 0038](0038-test-layer-trigger-timing.md)）决定：开发 Mac 不跑测试，测试在 Hermes（局域网里的 Linux 服务器）上跑，所有测试数据都放在 `/data`；生产环境是云服务器 `84.247.157.41`。

2026-09-30 按这个决定在 Hermes 上第一次跑整组单元测试时，2,144 项里有 67 项因为超时失败。核查发现：

- `/data` 是一块 2.5 英寸笔记本机械硬盘（WD5000LPCX）。连续做 200 次 4 KB 同步写入用了 13.9 秒，平均每次约 70 毫秒。
- 根盘是 NVMe 固态盘，同样的写入用了 0.6 秒，平均每次约 3 毫秒。
- 超时的测试使用真实 SQLite 数据库，每一步迁移和写入都要同步写盘。测试时限（5 秒、10 秒）是按固态盘的速度定的。

项目规则不允许靠放宽超时来让测试通过。测试运行时真正需要快的，只是运行中产生的临时数据：SQLite 文件、socket、测试安装。源码、依赖、构建产物、日志和证据写得少、体积大，放在机械硬盘上没有问题。

<a id="decision"></a>

## 决定

用户在 2026-09-30 确认：

<a id="hosts"></a>

### 测试和部署的位置

沿用 ADR 0041，不变：

1. **开发 Mac 不跑测试。** 用户的 MacBook 只用来编辑代码、审核和提交。构建、`npm run check`、`npm test`、各组 Vitest 测试和产品路径资格都不在 Mac 上跑。
2. **测试在 Hermes 上跑。** 第 0–3 层和 Linux 产品路径验证，通过 SSH 在 Hermes 上运行。按这个决定在 Hermes 上跑测试，不需要每次再问用户；需要 sudo 或改动 Hermes 上的服务时，仍按现有做法先给用户脚本，由用户执行。
3. **Mac 仍是支持的产品平台，Mac 专属验证按需进行。** 只有改动影响 Mac 专属部分，或者发布之前，才在 Mac 上跑 Mac 专属验证；每次都要先说明要跑什么、大约多久，得到用户同意，时间由用户决定。
4. **生产环境是云服务器 `84.247.157.41`。** 在这台服务器上的任何部署或改动，都是生产操作，每次都要用户明确授权。

<a id="storage"></a>

### Hermes 上的存放位置

这是本 ADR 相对 ADR 0041 唯一的变化：

| 内容 | 放在哪里 |
| --- | --- |
| 源码检出、npm 依赖、固定工具链、浏览器、构建产物、日志、测试报告、保留的失败现场和其他证据 | `/data` 下属于本任务的目录（机械硬盘） |
| 测试**运行中**产生的临时数据：SQLite 文件、socket、产品路径测试安装、测试进程的 `TMPDIR` | 根盘（NVMe）上属于本任务的临时目录，通过 `HIMAWARI_TEST_TEMP_ROOT` 指定 |

根盘空间紧张，所以使用根盘临时目录时必须满足：

1. **跑之前查空间。** 每次运行前用 `df` 检查根盘；可用空间低于 10 GiB 就不启动这次运行，写停止文件说明。
2. **记录峰值。** 运行期间记录临时目录的最大占用和根盘的最低可用空间，写进这次运行的证据。
3. **跑完就收走、删掉。** 需要保留的失败现场（数据库、日志、trace）先复制到 `/data` 下的证据目录，再删除这次运行的临时目录；删除前按 `AGENTS.md` 的 “Disk Space Hygiene” 核对没有进程还在用它。
4. **只用本任务的目录。** 目录权限 0700，不写 `/tmp` 下的其他位置，不动其他程序的文件。

<a id="layers"></a>

### 测试层级和触发条件

沿用 ADR 0041（其内容来自 ADR 0038），不变：

| 层级 | 内容 | 在哪里跑 | 什么时候运行 |
| --- | --- | --- | --- |
| 第 0 层：定向测试 | 能复现缺陷或验证新行为的测试，以及直接相关的测试文件 | Hermes | 改生产代码之前先运行，证明它失败；之后每次修改都运行同一测试 |
| 第 1 层：静态检查 | `npm run check`（格式、代码规范、类型、模块边界等） | Hermes | 每次提交之前 |
| 第 2 层：受影响模块测试 | 改动所在的整个测试组，以及引用了被改模块的集成测试文件 | Hermes | 一个缺陷或功能修稳定、准备提交时 |
| 第 3 层：完整测试 | 构建安装包，再运行完整 `npm test` | Hermes | 一批改动准备交付审核或验收时；推送、开 PR（合并请求）或合并之前；一轮工作结束时；以及[提前运行完整测试的情况](#early-full) |
| 第 4 层：真实产品路径 | 真实安装后，按用户操作走一遍产品场景 | Linux 版在 Hermes 上；Mac 版按上面第 3 条在 Mac 上 | 改动影响安装、升级、进程管理或沙箱运行时行为时，只运行相关场景；不加筛选的完整版本，只在一轮工作结束或发布之前运行 |
| 第 5 层：生产部署 | 部署到云服务器 `84.247.157.41` | 云服务器 | 每次部署都要用户明确授权 |

补充规则：

- **一批**指一起交付审核或验收的一组改动，通常不超过 3 个互相独立的缺陷。
- **先自查，再跑完整测试。** 启动第 3 层之前，先完成第 0–2 层、自查代码和相关文档。
- **完整测试失败时**，回到第 0 层复现并修复，通过第 0–2 层后，只对这一批的最终版本再跑一次第 3 层。
- **只改文档**时，只运行文档校验和 Runbook（操作手册）的封存检查，不运行产品测试。

<a id="early-full"></a>

### 提前运行完整测试的情况

改动涉及下列公共部分时，这一次改动就要单独跑第 3 层，不等到一批结束：

- 产品数据库（SQLite）的表结构或迁移；
- Agent Service（负责对话和数据库的服务进程）与 Execution Worker（执行工具的进程）之间的通信协议、认证或握手；
- 构建和打包配置、依赖声明或锁文件；
- 测试运行方式本身，例如 Vitest 的配置、`scripts/ci/` 下的测试脚本或 `ci/policy.json`。

<a id="commits"></a>

### 提交与结果复用

- 每个独立缺陷单独提交，提交前必须通过第 0–2 层。提交说明和交付记录只能写实际跑过的层级和运行位置；中间提交没有单独跑过完整测试时，要写明完整测试覆盖的是哪个版本。
- 代码、依赖、测试配置和相关环境都没有变化时，已有的测试结果可以继续使用。在 Mac 上得到的结果不能当作 Linux 的结果，反之亦然。临时目录放在 `/data` 时得到的失败结果，不能当作放在根盘时的结果。
- GitHub 上合并 PR 之前 CI（代码推送后在 GitHub 上自动运行的检查）必须通过的检查集合，仍由 `ci/policy.json` 规定。

<a id="options"></a>

## 比较过的方案

### 方案 A：运行时临时数据放根盘的任务目录，加空间保护（采用）

- 好处：测试在真实的固态盘上运行，同步写入的行为和以前在 Mac 上一致；体积大的内容仍然在 `/data`。
- 代价：要占用根盘的一部分空间；每次运行都要检查空间、记录峰值、跑完清理。

### 方案 B：放在内存盘 `/dev/shm`

- 好处：最快，不占根盘。
- 代价：占用 Hermes 的内存（当时可用约 6 GB，上面还运行着别的服务）；同步写入在内存盘上不起作用，测不到真实磁盘的行为。

### 方案 C：仍然全部放 `/data`，先逐项查慢在哪里

- 好处：不改变 ADR 0041 的存放规则。
- 代价：已经确认机械硬盘每次同步写入约 70 毫秒，继续排查多半还是要回到方案 A 或 B；也不允许用放宽超时来解决。

<a id="consequences"></a>

## 后果

- 测试代码要支持 `HIMAWARI_TEST_TEMP_ROOT`：不设置时行为不变（仍用 `/tmp`，Mac 不受影响）；设置时，所有运行时临时数据都放在这个目录下。
- 在 Hermes 上运行测试的记录，要写明临时目录的位置、峰值占用和根盘最低可用空间。
- 机械硬盘上的超时，不能证明产品在慢盘上的表现可以接受，也不能证明不可以接受；本决定只解决测试环境的问题。
- 需要在 Hermes 上准备固定版本的 Node 和 npm、Linux 原生依赖和浏览器；下载新依赖仍要用户同意。
- 在 Mac 上已经得到的历史测试结果仍然有效，但只代表 Mac。

# ADR 0033：默认用进程级沙箱执行工具，容器改为可选的严格模式

## 背景

Himawari 计划作为 Agent 产品分发给其他用户，其中包括 macOS 用户。

[ADR 0031](0031-isolated-tool-execution.md) 决定：会执行代码、改文件或访问网络的工具，默认在每轮对话一个的隔离环境（第一阶段是 Docker 兼容的容器）里运行；macOS 上新的执行方式必须能证明整个任务已经停止；隔离环境不可用时，这些工具明确不可用，不能退回宿主执行。按这个决定，macOS 用户必须先安装一个 Docker 类的容器运行时（例如 OrbStack），工具才能使用。这类运行时要常驻后台、占用较多内存和磁盘，对产品分发不利。

现有的另一条执行路线（下称“SRT 模式”）是：Worker（负责执行工具的后台服务）为每次工具调用启动一个独立的 Job Host 进程（产品自己的监督进程），Job Host 再用 SRT（`@anthropic-ai/sandbox-runtime`，在宿主上限制单个进程能访问哪些文件和网络的进程级沙箱）运行已登记的工具程序。它不需要安装容器运行时。它的已知限制见 [P0 现状基线](../../test/qualification/evidence/isolated-tool-execution/p0-baseline-01/README.md#baselines)：

- 在 Mac 上，任务里用 `setsid`（让程序脱离原来的进程组、不再随它一起被结束的系统调用）启动的后代程序，在停止后又写入了 28 字节。
- Job Host 对已经启动过的任务，一律把进程树清理结果记为“未确认”（`unknown`），对应的目录占用会一直挡住有冲突的新任务，直到恢复流程处理完。

截至 2026-09-26，容器路线只接入了前台的 `read`、`bash`、`find`、`grep`、`ls`，默认关闭；其余工具都只在 SRT 模式下可用。

用户在 2026-09-26 作出以下决定：接受 macOS 上无法可靠保证停止后所有后台程序都已停止；否决由产品自带轻量虚拟机；远端执行是产品需求之一，但现在不做，要预留接入口。

## 决定

1. **macOS 和 Linux 都默认使用 SRT 模式。** 会执行代码、改文件或访问网络的工具，默认由独立的 Job Host 进程在 SRT 限制下运行，仍然不在 Agent 主进程里运行。ADR 0031 [最小权限与失败关闭](0031-isolated-tool-execution.md#security)里对文件、网络、凭据和权限的限制继续适用；SRT 做不到的限制，按现有资格记录如实报告，不宣称已经做到。
2. **SRT 模式下的停止与释放。** 一次调用结束或被停止后，只要宿主确认这个任务的进程组（任务主进程及仍留在同一组里的子进程）已经全部消失，就结束这次调用的目录占用，界面显示“停止未经严格确认”。释放记录要写明依据是“进程组已消失”，不能写成严格停止证明。用 `setsid`、两次 fork（进程复制出子进程，再由子进程复制一次后自己退出）等方式脱离进程组的后代程序不跟踪，也不作为继续挡住目录的条件。只有停止这一步本身失败，例如无法向进程组发出停止、进程组仍然存在，或无法确认它是否还在，才继续挡住目录，交给现有的恢复流程处理。
3. **容器是可选的严格模式，只在配置里明确打开时使用。** 打开方式是 `taskEnvironments` 配置段，默认关闭；即使用户装了容器运行时，也不自动切换。打开严格模式后，所有工具都必须在容器里运行；容器还不支持的工具在严格模式下显示“不可用”，不借用 SRT 模式执行。严格模式下 ADR 0031 的全部规则不变：同一轮对话共用一个环境、整体停止并取得停止证明后才释放占用、隔离环境不可用时明确报错。两个模式之间都不能静默回退：打开了严格模式而容器不可用时，不能改用 SRT 模式执行，反之亦然。严格模式的配置项要尽量少，能自动发现或有安全默认值的项不要求用户填写，具体在 Spec 中规定。
4. **同一时间只有一种模式在工作。** 由上一条，一个安装要么全部用 SRT 模式，要么全部用严格模式。切换模式时，旧模式留下的占用可能还没释放完，所以同一个目录上，SRT 模式的调用和严格模式任务环境的占用继续互相排斥，同一轮对话内也一样。
5. **SRT 模式不额外限制高风险用法，但必须向用户说清当前状态。** 后台任务（一次调用启动、之后持续运行的程序，例如文件监视程序）、服务类任务（占用端口对外服务的后台任务，例如本地网页开发服务器）和无人值守任务（定时或自动触发、运行时没人在看的任务）照常允许。产品界面必须让用户看清：当前用的是哪种模式；哪些后台或服务类程序还在运行；停止之后是“停止未经严格确认”，也就是脱离进程组的程序可能仍在运行、改文件或联网。
6. **切换到新的释放规则时，直接删除旧的未确认记录。** SRT 模式以前留下的、至今仍挡住目录的“未确认”记录，由所有者授权后从数据库中删除，不逐条核查。删除通过管理命令完成：先列出并记录将被删除的记录和关联的数据，再执行删除，不做备份；不能手工改数据库。所有者已在 2026-09-26 授权在所有机器上执行这项删除，执行前不再逐台询问。
7. **远端执行以后实现，现在只预留接入口。** 执行后端的接口由产品自己定义，不依赖某个容器产品；每个工具操作单独指定使用哪个后端。已知在接入远端之前必须补上的两处：Agent 目前只能配置一个非 SRT 的后端，需要改为按名称选择多个后端；容器路线默认工作目录就在同一台机器上，远端执行需要先传入工作目录，结束后核对版本再写回。这两处现在不改代码。
8. **不由产品自带虚拟机。**

## 与 ADR 0031、0030 的关系

本 ADR 只部分修正 ADR 0031 和 ADR 0030，不整份替代；两份 ADR 的其余决定继续有效，ADR 0032 对原目录模式的修正也不变。

| 原要求 | 继续有效 | 本决定修正的范围 |
| --- | --- | --- |
| ADR 0031 [背景与决定](0031-isolated-tool-execution.md#decision)：这类工具默认在独立隔离环境执行，默认一轮任务一个环境 | 工具不在 Agent 主进程或控制平面（负责调度、授权和审计的可信部分）里运行；严格模式下一轮任务一个环境 | 默认执行方式改为每次调用一个 Job Host 进程的 SRT 模式；一轮任务一个环境只适用于严格模式 |
| ADR 0031 [两个互补安全边界](0031-isolated-tool-execution.md#boundaries)：SRT 不能单独承担严格的任务生命周期边界，不得作为宿主执行的回退 | SRT 模式不宣称严格的生命周期边界；两个模式之间不能回退 | SRT 模式成为默认执行方式本身，不再只是历史路线 |
| ADR 0031 [与既有 ADR 的关系](0031-isolated-tool-execution.md#amendments)中对 ADR 0025 决定 6 的修正：macOS 新执行方式必须有任务级停止证明；容器不再只是可选增强；本地隔离运行时可以成为必要前置条件 | 严格模式的停止证明要求 | macOS 和 Linux 默认都不需要容器运行时；容器恢复为可选增强 |
| ADR 0031 [工作区与停止证明](0031-isolated-tool-execution.md#release)：未可靠确认不能继续产生副作用之前不得释放占用；主进程消失不是释放证据 | 严格模式完全照旧 | SRT 模式下，进程组全部消失即可释放，并如实标明“停止未经严格确认” |
| ADR 0030 [决定](0030-durable-workspace-release-facts.md) 第 3 条及其影响：真正仍可写的旧资源在得到隔离证明前，仍然挡住冲突操作；真实旧写入方仍可写时不能放行 | 释放事实持久保存、不因时间推进撤销；通知迟到不反锁；进程组仍在或停止失败时照旧挡住 | SRT 模式下，脱离进程组的后代程序不作为挡住目录的条件 |
| ADR 0030 [决定](0030-durable-workspace-release-facts.md) 第 5 条：不批量生成释放证明；旧记录的迁移与恢复要现场核验、只读预览、逐条条件更新 | 严格模式的任务环境记录照旧逐条处理；生产数据的写入要有具体授权 | SRT 模式以前留下的未确认记录，经所有者授权后整批删除，删除前列出记录，不做备份 |

<a id="consequences"></a>

## 比较过的方案与后果

| 方案 | 判断 |
| --- | --- |
| 维持 ADR 0031：两个平台都要求容器运行时 | 未采用；macOS 用户要额外安装常驻的容器运行时，不利于分发 |
| 产品自带轻量虚拟机 | 否决；安装包变大，工程量大，还要自己维护虚拟机镜像和更新 |
| 以远端执行为主 | 暂不采用；本机很轻，但依赖网络和服务端，还有成本和隐私问题。它是以后要做的需求，现在只预留入口 |
| 默认 SRT 模式，容器作为明确打开的严格模式 | 采用 |

**后果**：

- SRT 模式下，脱离进程组的后代程序可能在释放之后继续改文件或访问网络，而下一个任务可能已经在用同一个目录，两者会同时修改。固定目标文件的发布前版本比较能发现一部分冲突；任意命令造成的修改发现不了。用户已在 2026-09-26 明确接受这个风险，产品界面和文档必须如实说明，不能表述为严格停止。
- 需要严格保证的用户，要自己安装容器运行时并打开严格模式。
- 严格模式下，写入、另存副本、移动目录的发布由宿主一侧完成，并且登记在本轮任务环境名下，不能借用 SRT 模式的调用来发布，否则违反上面第 3 条和第 4 条。
- “删除 SRT 执行路线”不再是目标。
- 删除旧的未确认记录后，这些记录不再保存。历史对话里对应的工具步骤可能显示不出来，界面要能正常处理这种缺失，不能报错或显示成成功。删除前不做备份，删除后无法找回；删除命令如果选错范围，误删的数据也无法恢复，所以删除范围必须由测试严格验证。
- 严格模式在容器支持全部工具之前，功能少于 SRT 模式，例如暂时不能写文件；界面要说明哪些工具在严格模式下不可用。
- [实施 Plan](../execution/plans/2026-09-24-isolated-tool-execution-plan.md) 中以容器为默认前提的阶段（例如 macOS 上的容器资格验证、默认切换到容器、以及把 SRT 只当作历史路线的迁移步骤）需要按本决定调整。

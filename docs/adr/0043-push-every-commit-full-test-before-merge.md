# ADR 0043：测试在 Hermes 上运行，每个提交立即推送，完整测试在开 PR 和合并前把关

## 背景

[ADR 0042](0042-hermes-test-scratch-on-root-disk.md) 决定了测试在哪里跑、Hermes（局域网里的 Linux 服务器）上的数据放在哪里，以及各层测试什么时候运行。它的层级表写着：第 3 层完整测试要在“推送、开 PR（合并请求）或合并之前”运行，也就是没跑完整测试的提交不推送到 GitHub。

2026-09-30 用户决定：**每个提交创建后都立即推送到远程仓库**，并把这条规则写进了 Claude 和 Codex 的全局指令文件。原因是用户希望远程仓库随时反映最新进展，不再让本地积压大量未推送的提交（当时本地已领先远程 13 个提交）。

这和 ADR 0042 “完整测试通过后才推送”的规则冲突，所以用本 ADR 取代 ADR 0042。除了推送规则，ADR 0042 的其余内容（测试位置、Hermes 上的存放位置、各层内容、提前运行完整测试的情况）原样保留在下面。ADR 0042 选择根盘临时目录的原因和比较过的方案，见它自己的“背景”和“比较过的方案”两节。

同一天用户还决定：**无限期推迟 Mac 上的定向验证**，在用户重新安排之前不在 Mac 上跑任何验证。这没有改变下面“Mac 专属验证须经用户同意”的规则，只是用户目前不同意任何一次 Mac 验证；具体影响的项目记录在各自的 Backlog 和计划里。

<a id="decision"></a>

## 决定

用户在 2026-09-30 确认：

<a id="hosts"></a>

### 测试和部署的位置

沿用 ADR 0042，不变：

1. **开发 Mac 不跑测试。** 用户的 MacBook 只用来编辑代码、审核和提交。构建、`npm run check`、`npm test`、各组 Vitest 测试和产品路径资格都不在 Mac 上跑。
2. **测试在 Hermes 上跑。** 第 0–3 层和 Linux 产品路径验证，通过 SSH 在 Hermes 上运行。按这个决定在 Hermes 上跑测试，不需要每次再问用户；需要 sudo 或改动 Hermes 上的服务时，仍按现有做法先给用户脚本，由用户执行。
3. **Mac 仍是支持的产品平台，Mac 专属验证按需进行。** 只有改动影响 Mac 专属部分，或者发布之前，才在 Mac 上跑 Mac 专属验证；每次都要先说明要跑什么、大约多久，得到用户同意，时间由用户决定。
4. **生产环境是云服务器 `84.247.157.41`。** 在这台服务器上的任何部署或改动，都是生产操作，每次都要用户明确授权。

<a id="storage"></a>

### Hermes 上的存放位置

沿用 ADR 0042，不变：

| 内容 | 放在哪里 |
| --- | --- |
| 源码检出、npm 依赖、固定工具链、浏览器、构建产物、日志、测试报告、保留的失败现场和其他证据 | `/data` 下属于本任务的目录（机械硬盘） |
| 测试**运行中**产生的临时数据：SQLite 文件、socket、产品路径测试安装、测试进程的 `TMPDIR` | 根盘（NVMe）上属于本任务的临时目录，通过 `HIMAWARI_TEST_TEMP_ROOT` 指定 |

根盘空间紧张，所以使用根盘临时目录时必须满足：

1. **跑之前查空间。** 每次运行前用 `df` 检查根盘；可用空间低于 10 GiB 就不启动这次运行，写停止文件说明。
2. **记录峰值。** 运行期间记录临时目录的最大占用和根盘的最低可用空间，写进这次运行的证据。
3. **跑完就收走、删掉。** 需要保留的失败现场（数据库、日志、trace）先复制到 `/data` 下的证据目录，再删除这次运行的临时目录；删除前按 `AGENTS.md` 的 “Disk Space Hygiene” 核对没有进程还在用它。
4. **只用本任务的目录。** 目录权限 0700，不写 `/tmp` 下的其他位置，不动其他程序的文件。

<a id="layers"></a>

### 测试层级和触发条件

沿用 ADR 0042，只有第 3 层的触发条件去掉了“推送之前”：

| 层级 | 内容 | 在哪里跑 | 什么时候运行 |
| --- | --- | --- | --- |
| 第 0 层：定向测试 | 能复现缺陷或验证新行为的测试，以及直接相关的测试文件 | Hermes | 改生产代码之前先运行，证明它失败；之后每次修改都运行同一测试 |
| 第 1 层：静态检查 | `npm run check`（格式、代码规范、类型、模块边界等） | Hermes | 每次提交之前 |
| 第 2 层：受影响模块测试 | 改动所在的整个测试组，以及引用了被改模块的集成测试文件 | Hermes | 一个缺陷或功能修稳定、准备提交时 |
| 第 3 层：完整测试 | 构建安装包，再运行完整 `npm test` | Hermes | 一批改动准备交付审核或验收时；开 PR（合并请求）或合并之前；一轮工作结束时；以及[提前运行完整测试的情况](#early-full) |
| 第 4 层：真实产品路径 | 真实安装后，按用户操作走一遍产品场景 | Linux 版在 Hermes 上；Mac 版按上面第 3 条在 Mac 上 | 改动影响安装、升级、进程管理或沙箱运行时行为时，只运行相关场景；不加筛选的完整版本，只在一轮工作结束或发布之前运行 |
| 第 5 层：生产部署 | 部署到云服务器 `84.247.157.41` | 云服务器 | 每次部署都要用户明确授权 |

补充规则：

- **一批**指一起交付审核或验收的一组改动，通常不超过 3 个互相独立的缺陷。
- **先自查，再跑完整测试。** 启动第 3 层之前，先完成第 0–2 层、自查代码和相关文档。
- **完整测试失败时**，回到第 0 层复现并修复，通过第 0–2 层后，只对这一批的最终版本再跑一次第 3 层。
- **只改文档**时，只运行文档校验和 Runbook（操作手册）的封存检查，不运行产品测试。

<a id="early-full"></a>

### 提前运行完整测试的情况

改动涉及下列公共部分时，这一次改动就要单独跑第 3 层，不等到一批结束：

- 产品数据库（SQLite）的表结构或迁移；
- Agent Service（负责对话和数据库的服务进程）与 Execution Worker（执行工具的进程）之间的通信协议、认证或握手；
- 构建和打包配置、依赖声明或锁文件；
- 测试运行方式本身，例如 Vitest 的配置、`scripts/ci/` 下的测试脚本或 `ci/policy.json`。

<a id="commits"></a>

### 提交、推送与结果复用

- 每个独立缺陷单独提交，提交前必须通过第 0–2 层。
- **每个提交创建后立即推送**到远程仓库同名分支，第一次推送时设置上游分支。不强制推送，不改写已推送的历史，不绕过钩子；推送被拒绝或失败时停下报告。推送不等于完整测试通过：只跑过第 0–2 层的提交也会被推送，所以提交说明必须如实写明跑过的层级。提交说明和交付记录只能写实际跑过的层级和运行位置；中间提交没有单独跑过完整测试时，要写明完整测试覆盖的是哪个版本。
- 代码、依赖、测试配置和相关环境都没有变化时，已有的测试结果可以继续使用。在 Mac 上得到的结果不能当作 Linux 的结果，反之亦然。临时目录放在 `/data` 时得到的失败结果，不能当作放在根盘时的结果。
- GitHub 上合并 PR 之前 CI（代码推送后在 GitHub 上自动运行的检查）必须通过的检查集合，仍由 `ci/policy.json` 规定。

<a id="options"></a>

## 比较过的方案

### 方案 A：每个提交立即推送，完整测试在开 PR 和合并前把关（采用）

- 好处：远程仓库随时有最新提交，本地不再积压；本地磁盘或机器出问题时不会丢工作。
- 代价：远程分支上会出现只跑过第 0–2 层的提交；每次推送都可能触发 GitHub 上的 CI（代码推送后自动运行的检查），CI 失败要如实报告。

### 方案 B：保持 ADR 0042，完整测试通过后再推送

- 好处：远程分支上的每个版本都跑过完整测试。
- 代价：一批改动要等几个小时甚至更久才推送，本地积压多个提交；用户已明确不采用。

<a id="consequences"></a>

## 后果

- Claude 和 Codex 的全局指令文件已写入“每个提交立即推送”，Codex 的任务说明不再写“不 push”。开分支、打标签、开 PR、合并仍要用户单独要求。
- 远程分支上的提交不保证跑过完整测试；要判断某个版本是否跑过完整测试，看提交说明和交付记录写的层级。
- 合并到 `main` 之前，仍要在要合并的版本上跑第 3 层，GitHub CI 的必需检查仍由 `ci/policy.json` 规定。
- ADR 0042 关于根盘临时目录的后果继续有效：测试代码支持 `HIMAWARI_TEST_TEMP_ROOT`，运行记录写明临时目录位置、峰值和根盘最低可用空间。
- Mac 定向验证无限期推迟期间，Mac 上的行为（包括 Mac 与 Linux 共用、但在 Mac 上表现可能不同的代码）只能写成“未在 Mac 上验证”，不能用 Linux 的结果代替。

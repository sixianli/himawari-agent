## 方案正文（导出原文）

## 结论摘要

推荐：**自研记忆引擎，全部放进现有的 SQLite 主库，去掉 Mem0。** 不上图数据库、不上 Postgres，而是把业界验证过的几个做法组合起来：常驻的「主人档案」、带时间有效期的事实、按日期的情景摘要、混合检索加打分、后台定期整理、以及把承诺和计划变成主动提醒。

为什么这是现阶段的最佳方案：

- **Mem0 在我们这里已经只剩一层薄壳。** 代码核对发现，提炼、去重、更新、敏感审批、加密存储都是 PR #16/#17 自己写的；Mem0 只负责调嵌入接口和存向量。它的 SQLite 向量库检索是把整张表读进内存逐条算余弦（mem0ai 3.3.1 源码 `SELECT * FROM vectors`），没有关键词检索。换掉它几乎不损失能力，还少一份要双写同步、要验证删除的数据。
- **Mem0 新算法的方向和我们相反。** 它 2026 年 4 月的新算法改成「只新增、不更新不删除」，而 Himawari 要的是能更正、能审批、能追溯的记忆。
- **好成绩来自结构，不来自某个库。** LongMemEval 论文、Zep、Mastra、ChatGPT 的公开做法指向同一组要点：把事实抽出来做索引键、给事实加时间、问到时间时按时间过滤、常驻一份压缩过的用户画像、后台整理。这些都能在 SQLite 里实现。
- **单用户、本地优先。** 一个人一辈子的记忆是几万条量级，SQLite 加 sqlite-vec 暴力检索足够快，数据只有一个文件，备份、加密、删除验证都沿用现有机制。

需要你决定的三件事（详见 风险与需要决定的事）：是否同意去掉 Mem0；嵌入模型先继续用云端 Qwen3-Embedding-8B 还是尽快换本地小模型；第一阶段是否先做「常驻档案 + 混合检索 + 评测集」。

总工作量估计 3 到 4 周，分 4 个阶段，每个阶段都能单独上线、单独回滚。这是我的估算，没有实测依据。

没有哪一家能整套拿来用，但每家都有一个值得抄的做法。下表按「对 Himawari 的借鉴价值」排序。

| 方案 | 核心做法 | 公开成绩 | 为什么不整套用 | 我们抄什么 |
| --- | --- | --- | --- | --- |
| [LongMemEval 论文](https://github.com/xiaowu0162/LongMemEval) | 评测 5 项能力：信息提取、跨会话推理、知识更新、时间推理、拒答；提出事实增强索引键、时间感知查询扩展、先摘记再作答 | 500 题基准，已成行业标准 | 是评测不是产品 | 用它的 5 项能力建我们自己的中文评测集；抄三条优化 |
| [Zep / Graphiti](https://github.com/getzep/graphiti) | 时序知识图：每条事实有有效期，新事实矛盾时把旧的标失效而不删；语义 + BM25 + 图遍历混合检索 | Zep 论文报 DMR 94.8%（MemGPT 93.4%），LongMemEval 最多提升 18.5%、延迟降 90%（厂商自报） | Python，要 Neo4j 或 FalkorDB 服务；每条消息多次模型调用；与我们 TypeScript + SQLite 不合 | 双时间有效期、失效不删、来源归到「情景」、混合检索 |
| [Mastra Observational Memory](https://mastra.ai/research/observational-memory) | 不做向量检索：观察者把对话压成带日期的观察日志常驻上下文，超过阈值（默认 4 万 token）由反思者再压缩 | LongMemEval 94.87%（gpt-5-mini，厂商自报） | 观察同步运行会卡对话；单靠压缩日志不支持删除单条和敏感审批 | 「常驻、可缓存的压缩画像」这一层 |
| [Mem0](https://github.com/mem0ai/mem0) | 2026-04 新算法：只新增不更新、实体链接、语义 + BM25 + 实体三路融合、检索时做时间判断 | LoCoMo 92.5、LongMemEval 94.4，每问约 7K token；README 说明这是付费云平台成绩，开源版达不到 | 开源版 BM25 要 Python spaCy；TS 版 SQLite 存储是全表暴力余弦；只新增与我们的更正语义冲突 | 三路融合检索、实体链接 |

| Generative Agents（斯坦福 2023） | 记忆流 + 召回打分 = 相关度 + 新近度（指数衰减）+ 重要度（模型 1–10 打分）；重要度累计到阈值触发「反思」生成高层认识 | 仿真实验，无基准分 | 学术原型 | 召回打分公式、反思 |
| ChatGPT 记忆 | 两层：用户可见的「已保存记忆」+「参考聊天记录」；新版自动维护一份记忆摘要；临时对话不读不写 | 未公开 | 闭源 | 「画像摘要 + 历史对话检索」的产品形态、临时对话开关 |

关于基准分数：各家在 LoCoMo / LongMemEval 上都是 90 分以上且多为自报，LoCoMo 还被独立审计指出约 6.4% 答案有误。分数只能说明「结构对了就能达到高分」，不能用来挑库；我们要用自己的评测集说话。

## 推荐架构

五层记忆、一个数据库、三条流水线（写入、召回、整理），再加一个出口通向主动行动。

### 五层记忆

| 层 | 存什么 | 什么时候写 | 什么时候用 | 借鉴 |
| --- | --- | --- | --- | --- |
| 主人档案 | 一份约 1500–2000 字的分节画像：身份、偏好、人际、长期目标、进行中的事 | 后台整理时重建，主人可在记忆页直接改 | 每轮常驻系统提示，内容稳定可命中提示缓存 | Letta 记忆块、Mastra、ChatGPT 记忆摘要 |
| 事实 | 一句话一条的长期事实，带类别、主题、实体、重要度、把握分、有效期 | 每轮提炼（现有流程） | 混合检索后注入 | Zep、Mem0 |
| 情景 | 每个对话或每天一份带日期的摘要，列出发生的事件 | 对话空闲或每晚 | 问到「上次」「上周」「那时候」时检索 | LongMemEval、ChatGPT 参考聊天记录 |
| 规矩 | 主人对 Himawari 的要求与纠正（「用简体中文」「别罗嗦」） | 提炼到 decision 类且指向 Himawari 时；改动需确认 | 常驻，排在档案前 | LangMem 程序性记忆 |
| 待办与承诺 | 带时间的计划、承诺、纪念日、「下周提醒我」 | 提炼到 commitment 类或含未来时间时 | 到点由调度器触发行动 | Himawari 独有，对应「主动」原则 |

### 数据模型

- `memory_records` 加字段：类别、主题、重要度（0–1000）、`valid_from` / `valid_to`（事实在现实中何时成立）、`superseded_by`（被哪条更正）、使用次数。录入时间已有。
- 新表 `entities`（人、地点、项目及别名）和 `memory_entities`。这就是「轻量图」，需要时用 SQLite 递归查询做一两跳关联，不引入图数据库。
- 新表 `memory_episodes`（日期范围、摘要、来源线程）、`memory_profile`（档案各节及版本）、`memory_intents`（待办与承诺的到期时间和状态）。
- 索引表：sqlite-vec 的 `vec0` 向量表 + FTS5 全文表。中文分词用 Node 内置的 `Intl.Segmenter`，已在 Node 22 实测：「主人对青霉素过敏，下个月要搬到杭州」切成「主人 | 对 | 青霉素 | 过敏 | 下个月 | 要 | 搬到 | 杭州」，零依赖。

### 写入：在现有提炼上改四处

1. 更正不再覆盖：旧条写上 `valid_to` 和 `superseded_by`，新增一条。记忆页可以显示「以前是……」，也能回答「我以前喜欢什么」。
2. 同一次模型调用里多要三个字段：重要度、实体列表、时间表达（按消息发送时间换算成日期）。不增加调用次数。
3. 含未来时间的承诺和计划同时写一条 `memory_intents`。
4. 嵌入和全文索引在同一个后台任务里写，沿用现有的 projection job 和重试机制。

### 召回：三路检索加打分

1. 查询解析：用规则把「上周」「去年春节」换算成日期范围，并识别问句里的实体。这是 LongMemEval 的「时间感知查询扩展」。
2. 三路并行：向量前 50、全文前 50、实体命中；默认只取当前有效的事实，问历史时才带上已失效的。
3. 用倒数排名融合（RRF）合并，再加三个信号：新近度（按最近使用按半衰期衰减）、重要度、把握分。权重用评测集调，不凭感觉定。
4. 按 token 预算注入：档案和规矩常驻，事实和情景按分数填充。
5. 给智能体一个 `recall` 工具（参数：问题、可选时间范围），自动注入不够时可以自己去翻情景和历史，对应 Claude memory tool 的「按需读取」。

### 整理：每晚或空闲时跑一次

- 合并近乎重复的事实；发现矛盾时让旧的失效，拿不准的放进「待你确认」。
- 把当天的对话压成情景摘要；反复出现的情景内容升级为事实。
- 重建主人档案，并把变化写进审计，记忆页可看「本周档案变化」。
- 反思：从近期事实推出高层认识（例如「主人最近在准备融资」），一律标「推测」，按现有规则不自动存，只在把握够高时请你确认。
- 衰减：长期没用到且重要度低的只降权或归档，不删除；删除只由主人发起。

### 主动：让记忆变成行动

`memory_intents` 到期时，由现成的 `SchedulerService` 创建一个后台运行，读档案和相关记忆，经 `SuggestionService` 生成提醒或建议，推到各端。同一套机制也能做每日简报。这些服务已写好未接入生产，工作量主要在接线和提醒界面。

## Mem0 去留与存储选型

建议用 sqlite-vec + FTS5 替换 Mem0，放在现有 SQLite 里。替换走 ADR 0005 已有的记忆端口，只换适配器，产品层代码不动。

| 选项 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **sqlite-vec 0.1.9 + FTS5（推荐）** | 和主库同一引擎；向量和全文可以一条 SQL 里组合；备份、删除验证沿用现有机制；npm 包可与 better-sqlite3 配合 | 仍是 v1 前版本；近似索引（DiskANN / IVF）只在 0.1.10 alpha，稳定版只有暴力检索 | 采用。单用户几万条暴力检索在 C 里是毫秒级，用不到近似索引 |
| 继续用 Mem0 3.3.1 | 不用改 | 实际只用到嵌入调用和全表余弦；没有关键词检索；第二份数据要双写、要验证删除；新算法只新增不更新 | 不采用 |
| Postgres + pgvector | 成熟、功能全 | 要多跑一个数据库服务，与「本地优先、单文件状态」不符；主库是 SQLite，要大迁移 | 不采用 |
| Graphiti + Neo4j / FalkorDB | 时序图做得最完整 | Python 服务 + 图数据库；每条消息多次模型调用；官方 MCP 参考服务注明没有鉴权 | 只借鉴设计 |
| Letta 服务 | 记忆块、睡眠时整理都现成 | 自带智能体运行时，和 Pi 重复；核心开发已转到 letta-code | 只借鉴设计 |

嵌入模型：先继续用云端 Qwen3-Embedding-8B，维度默认保持 4096。官方确认该模型支持 32–4096 自定义维度，但没公布 1024 维的得分，降维会有损失、幅度未知；单用户几万条时 4096 维也只占几百 MB，省下的不值得冒这个险。阶段一用评测集对比 4096 与 1024，确实没有损失才降。想完全本地时可换 Qwen3-Embedding-0.6B 本地跑，属于可选的第四阶段。

## 分阶段路线与工作量

先换检索底座并建评测集，再一层层加功能。按快速迭代模式估计合计约 3.5 到 4 周，工作量是我的估算。

**图 2 分阶段路线（文字版）：四个阶段约 4 周，每个阶段过关口才进下一步**

| 阶段 | 时间 | 内容 |
| --- | --- | --- |
| 阶段一 检索换底 | 约 1.5 周 | 中文评测集约 100 题，按 LongMemEval 5 项能力，先跑 Mem0 基线；sqlite-vec + FTS5 + 实体三路检索，RRF 加时间和重要度打分；记忆表加新字段；常驻主人档案和规矩层；写入核对原话；迁移现有记忆并重算嵌入，去掉 Mem0 |
| 关口 1 | | 评测分不低于 Mem0 基线才上线 |
| 阶段二 档案与情景 | 约 1 周 | 记忆页可查看、编辑档案，并显示档案变化；更正改为旧条失效、新增一条，记忆页显示历史；按天生成情景摘要，支持「上周」「去年」这类时间查询；给智能体加 recall 工具，可自己翻历史 |

| 关口 3 | | 一周真实使用没有误改、误归档 |
| 阶段四 主动行动 | 约 1 周 | 承诺、计划、纪念日写入待办表，到点触发；接上现成的调度与建议服务，提醒推到各端；可选：换本地嵌入模型，做到完全本地 |

## 参考项目：Cindy 的记忆系统

[Cindy](https://github.com/makecindy/cindy) 的记忆偏「编程助手式笔记」，底座不如我们的方案，但它在「防模型乱记、后台整理怎么做才安全」上踩过的坑很值钱。以下基于 2026-10-25 的 main（b7e46bcb）源码和产品规则文档。

它怎么做：

- 存储是 Markdown 文件，分 user / feedback / project / reference 四类（照搬 Claude Code 的自动记忆规范），一份 `MEMORY.md` 索引整份常驻系统提示，索引软上限 4KB、单条软上限 2KB。
- 写入主要靠智能体自己调 `memory_write` 工具；检索是 FTS5（中文靠 LIKE 兆底），没有向量。
- 聊天记录另有一套 FTS5 + sqlite-vec 的 RRF 混合检索，向量不可用时自动退回纯全文，命中时带上前后几条消息。
- Pi 压缩上下文时，把压缩摘要存成 `digest` 记忆：可检索，但不常驻。
- 「夜间学习」：每天 3:30 用辅助模型读上次之后的对话，模型只提议、宿主逐条校验后落盘。

| 做法 | 结论 | 理由 |
| --- | --- | --- |
| 每条新记忆必须附主人原话引文（至少 8 字）+ 消息编号，宿主核对原文里确实有这句才存 | **采用** | 成本几乎为零，直接拦住模型编造。我们现在只靠提示词要求「只从主人话里提取」，没有代码校验 |
| 夜间整理用「水位」：只读上次之后的对话，没有新对话就不调模型；读不完分批，成功才推进水位 | **采用** | 省钱、可重试、不重复处理 |
| 整理前登记本次运行，每改一条存前后内容，可逐条撤销；模型思考期间被主人改过的记录一律跳过 | **采用** | 整理是自动改你的记忆，必须可追溯、可撤销，并且不覆盖你的手动修改 |
| 做事方法先「观察」后「转正」：只出现一次的放进观察列表（不进提示词），再出现一次或主人点头才生效 | **采用** | 正好补上我们「规矩层」怎么学的问题 |
| 把 Pi 的压缩摘要存成可检索、不常驻的记录 | **采用** | 我们也在 Pi 上，符合 Pi 优先原则；作为情景摘要的现成素材 |
| 向量不可用时退回纯全文；命中历史时带前后消息；工具输出不进索引 | **采用** | 云端嵌入挂了也不影响记忆；它也证实 sqlite-vec 在桌面产品里可用 |
| 常驻索引和单条设软硬上限，超了就提示合并 | 已有类似 | 我们的档案已定 1500–2000 字预算，照此加上硬上限 |
| Markdown 文件存储、智能体自己决定记什么 | 不采用 | 没法加密、做敏感审批和时间查询；我们的自动提炼更适合「记忆是产品」 |
| 中文用 unicode61 + LIKE 兆底 | 不采用 | 我们用 Node 内置分词，效果更好 |

一条重要教训：Cindy 曾在每次回复后再调一次辅助模型复盘，并维护一本「工作记忆账本」（进行中的事、答应过的事、在等谁、最新纠正），2026-10-23 已停用，整理全部收归到夜间一次（见其 `docs/product-rules/cindy-bots-runtime.md` 3.2 节）。文档没写停用原因。对我们的启示：每轮只保留现有的一次提炼调用，不再加第二次；「答应过的事」放进待办表，其余整理都留给夜间。

方案据此调整：阶段一的写入加上「原话引文校验」，阶段二的情景摘要优先复用 Pi 压缩摘要，阶段三的整理采用水位、逐条撤销和「观察后转正」。总工作量约多 1–2 天。

## 风险与需要决定的事

需要你决定：

- [ ] 同意去掉 Mem0，改用 SQLite 内的 sqlite-vec + FTS5（我推荐同意）。这会取代 ADR 0005 里「不自建完整记忆引擎」的判断，实施线程会新写一篇 ADR，端口边界保留。
- [x] 嵌入模型：先留云端并降到 1024 维（我推荐），还是第一阶段就换本地模型。
- [x] 第一阶段范围：评测集 + 混合检索 + 常驻档案（我推荐），还是只做检索。

2026-10-25 Andy 批注同意并要求「全都要」：四个阶段全部实施，不缩范围；三项按推荐执行：去掉 Mem0；嵌入继续用云端（维度默认 4096，评测无损失才降到 1024）；常驻档案移入第一阶段（路线图已同步，第一阶段约 1.5 周）。

风险：

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 自研检索效果不如预期 | 召回变差反而倒退 | 先建评测集，用现在的 Mem0 跑出基线，新方案不超过基线不上线 |
| 全文索引和向量是明文衍生物 | 正文加密了，索引仍可反推内容；现在 Mem0 的向量库本来就存了明文，不是新增风险 | 索引不收 sensitive 以上的原文关键词；之后可评估整库加密 |
| 更正和失效判断出错 | 对的记忆被标失效 | 失效不删，记忆页可一键恢复；低把握的冲突进「待你确认」 |
| 整理和反思增加模型费用 | 每晚一次批量调用 | 用便宜模型（DeepSeek 级别），纳入现有预算控制 |
| 常驻档案写错一句，每轮都错 | 影响面大 | 档案每句链回来源事实；主人可直接改；变化可见 |
| sqlite-vec 仍是 v1 前 | 升级可能有不兼容 | 锁定 0.1.9；向量可从正文重算，索引随时可重建 |

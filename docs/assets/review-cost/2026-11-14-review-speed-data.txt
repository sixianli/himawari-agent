# 复核提速分析的数据（2026-11-14）

ADR 0270 背景一节的数字都出自这里。统计脚本是线程的临时脚本，不在仓库里；下面写明取法，换人可以重算。

## 取法

- 数据源：2026-10-31 起合并或在途的 PR 在 `.agents/reviews/pr-*/` 下的 `usage.jsonl` 和各轮的 `verdicts.jsonl`，按 PR 目录、时间、模型、轮次去重。
- 轮的时长：从上一轮结束到这一轮结束。

## 复核轮次

- 统计范围：178 个 PR、665 轮代码复核。
- 每个 PR 平均 3.7 轮，中位 3 轮，最多 13 轮。
- 每轮时长中位 21 分钟；其中 DeepSeek 一次运行 8 到 12 分钟，开跑前自检约 70 秒。
- 2026-11-08 起，增量轮（带 `--previous`）中位 47 步、0.091 美元；全量轮（第 1 轮）中位 36 步、0.081 美元。

## 第 2 轮起为什么还要再跑一轮

- 第 2 轮起共 658 轮。
- 44% 因为上一轮有成立的中高意见。
- 15% 因为上一轮只剩低意见，却用不了 `--accept-low`。
- 其余是首轮之外的别的原因。

## 增量轮里的中高意见落在哪里

- 增量轮里成立的中高意见，能定位到行号的有 233 条，其中 79% 落在上一轮刚改过的行附近。
- 抽查 30 条，约四分之三是正常使用或并发就会碰到的真问题。

## ADR 核对（`plan-claims`）

- 同一份 ADR 每次核对，模型列出的条数在 21 到 63 条之间波动。
- 被标“不一致”或“找不到”的条目，线程判为模型看错的有 64 条，方案真写错的有 27 条。
- 因为只认当前提交里的代码，讲“本 PR 删掉的旧代码原来如何”的句子永远核不过。靠 Andy 说跳过才合并的有 PR 423（`.agents/reviews/pr-423/usage.jsonl` 里 2026-11-12 的 `override` 记录）和 PR 481（`.agents/reviews/pr-481/usage.jsonl` 里 2026-11-13 的两条 `override` 记录）。

## 自检耗时

- 2026-11-14 在云端容器里实测，不带 Magpie 的自检，没有缓存时 22 秒，命中缓存时 11 秒。

## 留下的数据和对比报告（2026-11-14 加）

- 每一轮复核的步数、token、费用、时长都在 `.agents/reviews/pr-N/usage.jsonl`，成立的中高意见在 `pr-N/round-M/verdicts.jsonl`。自检耗时（`selfCheckMs`）、自检缓存命中（`selfCheckCache`：`hit`、`miss`、`off`）和 DeepSeek 一次运行时长（`runMs`）只有新记录有，旧记录没有。
- 优化前的逐轮数据存在 `2026-11-14-review-rounds-baseline.csv`（2026-11-14 14:38 UTC，即 PR 496 合并之前的 941 轮，比上面 665 轮的统计范围大，因为后来又复核了更多 PR），之后不再改。
- 重算对比表：`node scripts/model-review/review-speed-report.mjs --cut <分界时间>`；按 PR 或日期查逐轮数据：`--csv`。脚本只读账本，不花钱。
- 对比表里“优化后”一列按分界时间划分，跨过分界的 PR 只有分界之后的轮算进去，所以每个 PR 平均轮数在样本少时偏低，要等 5 个以上的 PR 从头到尾走完新流程再下结论。

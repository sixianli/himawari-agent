# Himawari 的身体：实施计划

**来源：** [SOURCE: docs/execution/specs/2026-11-11-apple-device-body-design.md]、[SOURCE: docs/adr/0229-native-apple-clients-and-device-api.md]、[SOURCE: docs/adr/0230-perception-records-and-memories-inferred-from-perception.md]、[SOURCE: docs/adr/0247-apple-clients-are-fully-native-with-a-capability-table.md]、[SOURCE: docs/adr/0258-each-apple-device-plays-to-its-strength.md]

**目标：** 按详细设计，把 iPhone、Apple Watch、Mac 三个客户端和服务器端的设备接口、感知记录、苹果推送、设备工具分批做出来。

**做法：** 一批一个 PR（改表的单独一个 PR，按项目的改表队列排）。服务器端每批都能只靠测试客户端验收，不等 App；客户端在 Andy 的 Mac 上用 Xcode 构建。每批合并前按项目规则做模型复核。

Andy 2026-11-11 21:32（日本时间）同意开工：“那这样，我们先做，等需要我开的时候，我再开”。苹果开发者账号先不开，做到第 4 批（苹果推送）时再请他开。

谁来做（Andy 2026-11-11 21:32）：写这份计划的线程“设计环境感知和 iOS App”只做方案、ADR 和设计，不写代码；每一批由协调者另开编码线程去做（Andy 2026-11-11 21:34：设计线程用的模型推理强度高，编码交给推理强度较低的线程）。编码线程发现设计行不通或有缺口时，回到设计线程改详细设计和 ADR，不在编码线程里自己改设计。

## 要先知道的三件事

1. **每人一个数据库文件。** [ADR 0234](../../adr/0234-one-program-per-person-database-file.md) 在这份计划写的同一天合并：以后一套程序服务多个人，每人一个数据库文件，共用层只有一份“名册”。设备相关的表（设备、感知记录等）都是私人数据，放在每人自己的库里；设备接口收到请求时要先知道“这是谁的设备”。第 1 批按现在的单人结构做，但设备编号里不带任何“只有一个主人”的假设，并在接口层留一处“按设备找到是谁”的入口（现在直接返回主人）。ADR 0234 的实现落地后，这个入口查共用层的设备索引表（“设备编号对应哪个人”“配对码的哈希对应哪个人”），见详细设计“设备身份和配对”。
2. **改表要排队。** 这份计划里改表的批次是第 1、3、4、5、7、9 批。每次开工前向协调者要迁移编号，同一时间只有一个改表的 PR。
3. **两个新工具和全部新提示词文字必须在同一个版本上线**（详细设计“发给模型的路径”一节的硬要求）。所以它们集中在第 5 批，哪怕对应的功能后面才开。

## 第 1 批的任务

**范围：** 详细设计的“设备身份和配对”“设备接口”里和感知无关的部分，以及“连接和传输”里服务器这一侧。

**会动到的地方：**

- 新建：一份迁移（`paired_devices`、`device_pairing_codes`、`device_request_nonces` 三张表；`devices` 这个名字已被网页登录的浏览器设备表占用）；设备身份的服务和存储；按 RFC 9421 验签的模块；设备接口的路由；测试客户端（用真的 P-256 密钥签名，放在 `packages/testing`）；`test/integration/device-api.test.ts`、`test/integration/device-connection.test.ts`。
- 修改：`packages/platform-node/src/http-gateway-server.ts`（挂上 `/api/device/v1/`，这组路径不走浏览器的同源检查，走设备验签）；表结构目录和数据导出（设备的名字和种类导出，凭据类不导出）；配置解析（签名容许的时间差、心跳间隔、连接最长寿命）；网页“设置”里加“设备”页（三种语言）。
- 不动：对话、记忆、审批的现有逻辑；发给模型的任何内容（这一批不加工具、不加提示词）。

**任务：**

1. 先读：`docs/pi-development-guide.md` 不涉及（这批不碰 Pi）；读 `packages/platform-node/src/identity-gateway.ts` 和现有事件流的身份核对，确认设备身份接在哪一层。读 RFC 9421 第 2、3、7 节原文，确认要覆盖的字段和验签步骤；查有没有维护良好的 Node 实现可以直接用，没有再自己写，并在 PR 里写明选了什么、为什么。
2. 写失败的测试：配对码过期、用过、错的都被拒；配对后是“等确认”，网页确认后才可用；签名正确的请求通过；重放、改正文、改查询参数、换主机名、时间差过大、设备被吊销、路径不在白名单，都被拒；设备吊销后它的内部会话一起失效。（不做 `web-session` 路由：App 里不嵌网页，原生页面走第 11 批的 `POST gateway`。）
3. 实现迁移、存储和服务，让上面的测试通过。
4. 写失败的测试：设备发的消息进现有对话，重复的唯一编号只认一次；事件流只发和这台设备有关的事件；断线后从编号续传不丢不重，记的位置指向一个没发给它的事件时也一样；编号太旧返回“整份重取”；吊销后连接最迟在下一次心跳时断开。
5. 实现路由和事件过滤，让测试通过。
6. 网页“设备”页：添加设备（显示二维码）、确认、改名、吊销。Playwright 测试覆盖正反两种（确认后出现在列表里；吊销后标成已移除、测试客户端连不上）。
7. 表结构目录、导出校验和导出的反向断言（配对码、随机值不出现在导出文件里），用例名带 `[P1-6]` 并同步改 `scripts/check-data-export.mjs` 的条数。
8. 自查一遍：新值清单里属于这一批的每个值，两端都校验了吗；有没有新加代码注释（不许有）。
9. 按项目规则做模型复核，修到没有中、高的“会出错”意见。

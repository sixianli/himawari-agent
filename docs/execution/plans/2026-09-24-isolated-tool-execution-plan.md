# Agent 任务级隔离工具执行实施计划

**Source Spec：** [SOURCE: docs/execution/specs/2026-09-24-isolated-tool-execution-design.md]

**继承的产品合同：** [SOURCE: docs/execution/specs/2026-09-16-workspace-authorization-lifecycle-design.md]

**架构决定：** [SOURCE: docs/adr/0031-isolated-tool-execution.md]

**目标：** 从现在“每次工具调用各起一套进程级沙箱（SRT / Job Host）”的方式，迁移到“一轮对话一个隔离环境”；不破坏现有的授权、结果和永久释放记录，并以“整个环境确实已停止”的证明，决定何时把工作目录交给别的任务。

**状态：** 隔离执行改造待实施；2026-09-24 已完成旧计划的任务和验收责任转交。本 Plan 是两个来源 Spec 的唯一后续实施入口。旧计划已有局部实现与证据继续有效，见[逐项转交表](#transfer-tasks)；新增阶段的未勾选项表示适配或剩余验证，不表示从零重建全部能力。本次整合仅修改文档，不启动代码实施、真实服务调用或部署。

## 术语说明

完整解释见 [Spec 的术语说明](../specs/2026-09-24-isolated-tool-execution-design.md#terms)。带反引号的是代码或数据库里的名字；哪些已经存在、哪些是计划新增的，表中逐项注明（2026-09-25 核查）。

| 本计划用词 | 意思 |
| --- | --- |
| Run（一轮） | 用户每发一条消息，产品就启动一个 Run，直到这条消息处理完 |
| 环境权限上限（capability envelope，上一版称“能力包络”） | 一个隔离环境里任何程序最多能做的事：能读写哪些目录、能连哪些网络目标、能用哪些凭据、能用多少资源 |
| 扩权 | 把新能力加进本轮环境的权限上限；获批后一律换新环境 |
| 换新环境（rotation，上一版称“轮换”） | 停掉当前容器、拿到停止证明之后，按新的权限上限建一个新容器 |
| 第几个环境（generation） | 同一轮里每换一次环境编号加一；对应计划新增的字段 `environmentGeneration`（代码里还没有） |
| `executionJobId` | 计划新增的字段（代码里还没有），标识“本轮这个执行作业”；一轮只有一个 |
| `lease` | 代码里已有的名字：一条“某个执行占用着某块资源”的登记；登记还在时，会冲突的任务不能动这块资源。“环境级 `lease`”指整个环境持有的这种登记 |
| `claim` | 代码里已有的名字：单次工具调用对具体文件或目录的占用登记，比环境级 `lease` 更细 |
| 停止标记（fence） | 数据库里的递增编号；开始停止时先加一，带旧编号的请求一律被拦住，不再执行 |
| 停止证明（release proof） | 执行后端独立检查后给出的“环境确实已整体停下”的记录；只有它被接收，才能释放 `lease` |
| 冲突保护（barrier） | 结果不确定时加的一道保护，让可能冲突的新任务先等着 |
| 临时凭据（broker handle） | 宿主发放的、有期限和用途限制的凭据，用完或停止时撤销 |
| 环境外的专用执行程序 | 在宿主一侧运行、只做一类固定动作的程序；凭据不进容器，只接受受限参数 |
| 委托清单 | 由人配置的、自动审查可以批准的扩权项列表，例如“允许访问 npm registry” |
| intent | 执行动作前先写进数据库的“准备做这件事”的记录，崩溃后靠它判断进行到哪一步 |
| CAS、ACK | CAS 是数据库“先比对再写入”，防止互相覆盖；ACK 是结果已送达的确认回执 |
| 资格验证（qualification） | 在具体平台、版本、配置上实测安全保证是否成立；通过前不启用 |
| E2E、测试样例（fixture） | E2E 是从真实产品入口走完整流程的端到端测试；测试样例是为测试准备的固定数据或程序 |
| opt-in | 默认不运行、需要显式打开开关才运行的测试 |
| SRT | 现在使用的进程级沙箱（依赖包 `@anthropic-ai/sandbox-runtime`），在宿主上限制单个进程能访问的文件和网络 |
| Worker | 现有的执行进程，负责把工具请求交给沙箱或执行后端，并把结果传回 |
| JEV | TypeSafe 的 JEV 决策模型，自动审查使用它；它不是大语言模型，只返回选项和置信度 |

## 基线、范围与依赖

源码核查基线为 `506a91d56ab28ee6daa72f629dd85c1e3bcaee84` 加读取时在途改动。开始实施前重新盘点 Git、适用指令、当前依赖及已有变更，只复核与本 Plan 有关的变化。不得覆盖现有 workspace lifecycle / UI 工作，可把它们作为继承实现的历史证据，但不得把旧 backend 的通过结果算作新环境验收。

先阅读 [Spec 的代码差距表](../specs/2026-09-24-isolated-tool-execution-design.md#baseline)。优先处理的结构性问题是任务环境身份与每调用身份分离；直接替换 `spawn` 不足以达成新架构。

相关既有工作：

- [SRT Plan](2026-09-07-srt-unified-execution-plan.md)：[SOURCE: docs/execution/plans/2026-09-07-srt-unified-execution-plan.md]。保留既有实现及历史证据；新任务环境、严格停止与 backend 路线由本 Plan 接续，不重新执行旧 Host-first 目标。
- [Workspace lifecycle 历史 Plan](../../archive/plans/2026-09-16-workspace-authorization-lifecycle-plan.md)：[SOURCE: docs/archive/plans/2026-09-16-workspace-authorization-lifecycle-plan.md]。旧计划以“任务转交”结束独立实施，55 项任务及 68 项验收由本 Plan 接续；未完成项不因归档变为完成。原 Spec 保持 active，审批、文件发布、队列与展示合同不被 ITE 验收取代。
- ADR 0030 的释放事实和现有“预留阶段的停止标记”必须保留。任何在途实现如果仍用单次调用完成来释放整个环境的占用，须在 P1/P3 完成集成后才能开启新 backend。

本 Plan 的执行改造主线实现一个本地 Docker-compatible backend 及现有工具迁移；浏览器只做 containment fixture 与绕过拒绝测试，不新增浏览器产品功能。Remote browser、MicroVM、远端工作区同步及跨 Run 常驻服务留在扩展边界，不要求本轮实现。旧计划尚未完成的自动审查、页面与真实端到端、迁移交付纳入 P5～P8。实施、安装、生产迁移、真实外部服务调用分别按当时授权执行；本次文档整合请求不授权这些操作。

| 用户路径与证据 | 不需要真实 runtime 的产品路径（backend 缺失拒绝、能力协商拒绝、legacy 读回等）放在默认 e2e 的 `test/e2e/isolated-tool-execution.test.ts`；需要真实容器的场景放在单独文件，按 P0 结论注册为 `ci/policy.json` 的 `kind: qualification` 项并沿 `qualify:scale` 的 `scripts/ci/quality.mjs` + `ci/quality-policy.json` 入口运行；故障注入置于 `test/integration/` | 沿现有 Vitest projects 与 qualification 模式，不另建测试运行系统 |

运行时依赖只能精确固定；Pi imports 仍只存在于 runtime-pi。不修改 sibling pi-mono，不使用本地链接替代提交的发布依赖，不手改 dist。

## 分阶段实施

每阶段先列相关不变量、边界及失败模式，优先在真实入口新增可重放 E2E；只有故障不易稳定触发时才补隔离测试。先运行测试确认命中旧缺陷/缺口，再实施最小完整变化。没有旧失败证据时记录原因，不虚构 red run。阶段内仅跑 focused tests，最终运行全项目 E2E 及必需检查。

### P0：建立当前基线与资格验证的输入

- [ ] 读取当前 AGENTS、相关 Spec/Plan、Git 状态、已安装的 Pi/SRT 和生产路由；核对 Spec 的代码差距表，记录版本和未提交改动的摘要。
- [ ] 盘点所有工具入口：Pi 的七个工具、后台任务、只联网的 web_search、Git/发布相关适配、浏览器和第三方 CLI。把每个入口分成“在环境内运行”和“环境外的专用执行程序”两类，查清有没有在宿主上运行任意代码的旁路。
- [ ] 核查候选 Docker 兼容运行时能否整体停止环境、关闭自动重启、给出可核对的环境身份，以及它的策略和资源能力；`docker info` 成功不算资格验证。镜像、挂载方式和工具链都算资格验证的输入。
- [ ] 按转交表核对旧 55 项任务的代码和证据，确定现有测试对原 68 项验收和 ITE-01～21 的覆盖与缺口，建立本计划的验收记录；不用旧的通过日志证明新环境。
- [ ] 用可重复运行的测试样例留存三条基线：“每次调用各算一个环境”“Mac 上已启动环境的停止结果为 unknown”“`lease` 阻塞”。历史 `setsid` 证据可以作为动机，但新的前后对比要有本次日志。
- [ ] **原目录模式平台门禁**（原在 P2 末尾，已前移）：在 Mac + 候选运行时和 Linux 上分别核查：挂进容器的工作目录能否强制磁盘额度、授权目录下嵌套的敏感文件能否隔离、大小写/硬链接/inode 身份在宿主和容器里是否一致。任一平台无法强制额度时，按 [Spec 的平台门禁](../specs/2026-09-24-isolated-tool-execution-design.md#host-mount-gate)停下来请用户二选一；结论出来之前，该平台不启用原目录模式。
- [ ] **硬期限可行性**：用受保护 init 的原型做负向探针：任务用户尝试 kill、ptrace、替换 init 或修改时钟；实测主机休眠和虚拟机挂起时的期限行为。探针不成立的运行时不能进入 P2 的资格路线，另找等价机制并记录。
- [ ] 确定真实容器场景的测试放置方式：沿用现有 `qualify:scale` 的做法（`scripts/ci/quality.mjs`、`ci/quality-policy.json`、`ci/policy.json` 中 `kind: qualification` 的登记，以及显式的 opt-in 环境变量），并决定 Linux 场景是否在 GitHub `ubuntu-24.04` 上作为单独任务运行；是否设为必需检查按当时的 CI 策略提出，不在本计划中预设。

完成条件：当前路径、版本、未提交的工作、可用的运行时和必须拒绝的策略组合都有记录；原目录门禁和硬期限可行性各有结论和证据。运行时不可用时，可以继续实现不依赖实机的合同，但不能标记后端验证完成；需要新的外部安装或权限时，按实际授权停下来。

### P1：任务级环境身份、持久 `lease` 与协议

覆盖 ITE-01、02、05、06、10、11、12、14、16、18、20。

- [ ] 先写环境权限上限规则的验收，再实现。规则按用户 2026-09-25 的决定，见 [Spec 的环境权限上限与换新环境](../specs/2026-09-24-isolated-tool-execution-design.md#envelope)：初始上限取本轮第一个需要主环境的调用获准的范围；需要超出上限时，审批请求单独列出扩权项，获批后一律换新环境，新上限 = 旧上限 + 这次批准新增的能力；一条命令能执行 = 它需要的能力在上限内，并且按现有 ActionPolicy 获准（已有范围授权覆盖的不再问，只有单次批准的逐条问）；文件工具不扩大上限；纯 web_search 不计入上限。
- [ ] 实现扩权分类，确定初始上限时同样使用，见 [Spec 的谁可以批准扩权](../specs/2026-09-24-isolated-tool-execution-design.md#expansion-approval)：写入新目录、使用凭据、访问清单外或不限目标的外网必须由人批准；委托清单内的项可以由自动审查批准；清单外的其他项由人批准。“由人批准”包括已有的、由人作出、仍然有效、明确覆盖该能力的范围授权，这时不再询问；自动审查作出的授权不算，凭据不能用范围授权代替。覆盖“把必须由人批准的能力放进第一次调用”的绕过尝试（ITE-20）。
- [ ] 审批请求携带当前环境已有的能力；需要换新环境时，还携带会被停掉的后台程序清单。自动审查批准的扩权要停掉后台程序时，会话里明确显示这些程序。沿用现有的会话内审批，不新增入口。
- [ ] 撤权或过期时缩小上限：停掉当前环境，按去掉该能力后的上限新建；上限里每项能力记录来源授权和期限，最早到期的一项一到期就触发（ITE-10）。
- [ ] 持久保存每个环境的权限上限、每项能力的来源授权和期限、换新环境的原因（扩权、撤权、过期或故障）和被停掉的后台程序清单；网络辅助环境有独立身份、不持有工作目录 `lease`，但计入 Run 结束前的未释放环境核对。
- [ ] 先写环境级 `lease` 与单次调用 `claim` 的验收：两个调用共用一个环境；一个调用结束后，后台写入程序仍占用资源；本任务内部不会被自己的环境级 `lease` 挡住；跨任务的冲突仍被挡住。
- [ ] 覆盖这些故障窗口：创建响应丢失、迟到的 create/start、停止标记的竞争、换到下一个环境时的交接、旧写入方不认识新记录、停止证明接收后 ACK 到期。
- [ ] 在现有产品数据库追加：执行作业（`executionJobId`）、环境及其第几个环境（`environmentGeneration`）、调用关联、创建/停止 intent、环境级 `lease` 和不可修改的释放回执；不改写旧作业的含义或已发布的迁移。
- [ ] 定义产品后端接口、能力声明和协议版本；解析失败时不能退回较弱的合同。增加读写兼容门槛，旧程序不能清掉新的环境级 `lease`。
- [ ] 实现防重复的创建 intent、用 CAS 绑定环境、停止标记；新后端取得资格之前，新任务执行保持关闭。

完成条件：真实 SQLite 的并发和重启验证通过；旧记录按原版本读回；原批准只用一次；每个结果未知的窗口都保留占用。测试替身只用来证明持久化协议，不代表真实隔离。

- [ ] 实现凭据进入容器的路径（ITE-21 的容器部分）：先换新环境、停掉后台程序，只发临时凭据，调用结束立即撤销并验证撤销后不可再用，凭据不进入本轮权限上限。

### P3：Pi 与 Worker 多次调用共用环境、停止与释放的集成

覆盖 ITE-01、02、03、05、07、10、11、15、16、18、19、20、21。

- [ ] 先建立中等复杂度的真实用户路径：授权工作目录 → 写入测试项目 → 安装本地测试包 → 构建 → 启动后台文件监视程序 → 修改文件并测试 → 读取 Git 状态 → 停止 → 有冲突的新任务接手。全程不需要扩权；每一步核对环境 ID 不变、调用身份各自独立、实际文件结果正确。
- [ ] 在上述路径停止时注入一个脱离终端的写入程序；宿主一侧的独立读回和后端观察证明它已停止；没收到停止证明之前，新任务不能执行。
- [ ] 把完整的 Pi 工具实现及其内置搜索和临时文件读写移进环境内的 runner；复用现有工厂、Operations、输出保护和产物导出，控制一侧不再默认读写本地文件。
- [ ] Agent 在本轮第一次需要工具时创建主环境，Worker 后续调用复用它；保持逐次授权、预算、期限和停止检查；权限变化只能通过换新环境实现。
- [ ] Run 正常结束、取消或撤权时接入整体停止；后端给出的停止证明经现有证据读取方接收后，在同一事务里释放环境级 `lease`。单次调用的结果不再代替环境的最终状态。
- [ ] 原目录和工作副本分别验证，保留候选发布和版本冲突的规则；环境外的专用执行程序不能成为运行任意命令的旁路。

- [ ] 逐项回归旧 P2/P3/P4：批准前零效果、批准只用一次、出队时重新检查、目录改名、公平排队、文件身份/版本、冲突后重新生成、部分恢复、save_copy 与未提交/未跟踪内容的保留。按转交表保留 A01～A13、W01～W30，不把代表场景当成全部通过。
- [ ] 建立环境级 `lease` 与文件并发的正反两个例子：两个能力被严格限定到不同文件的任务可以并发；拥有整个工作目录写能力的环境，即使前台调用已结束，也挡住有冲突的新任务。等待新审批或审查时没有本次调用的 `claim`，不代表已有环境可以提前释放。
- [ ] 按 ITE-16 走“① 无网络构建（确定初始上限，并启动后台程序）→ ② 联网安装（npm registry 在委托清单内，由自动审查批准并换新环境）→ ③ 无网络测试（不换环境，按现有规则逐条判断）→ ④ web_search（在网络辅助环境运行）”。断言：② 的审批展示当前环境能力和会被停掉的后台程序，会话里显示被停掉的程序；② 之后上限 = 原上限 + npm registry；① 的后台程序拿不到网络；③ 的审批展示已有的 npm registry 访问能力；④ 不改变主环境上限；记录换新环境的次数和耗时。
- [ ] 按 ITE-20 验证扩权分类：写入新目录、使用凭据、访问清单外或不限目标的外网，无论出现在第一个调用还是后续调用，自动审查都不能批准、一律转交人工；清单外的其他扩权也转交人工。再验证：由人作出、仍然有效、明确覆盖的范围授权可以代替当次确认，不再询问，被停掉的后台程序仍在会话中显示；自动审查作出的授权、已过期或已撤销的授权、范围不覆盖的授权都不能代替；凭据不能用范围授权代替。
- [ ] 按 ITE-21 验证凭据的两条路径：在环境外的专用执行程序中使用时，容器里任何程序都读不到凭据，程序拒绝任意命令和 hook；必须进入容器时，先换新环境并停掉后台程序，审批写明“这次调用期间，环境里的其他程序也能使用它”，调用结束后凭据撤销且不进入本轮上限；两种情况都每次由人批准。
- [ ] 按 ITE-10 验证撤权和过期：按缩小后的上限换新环境，最早到期的能力先生效，后台程序停止并在会话里显示。
- [ ] 按 ITE-18 验证 Run 边界：第二轮不继承上一轮的后台程序、HOME/cache 和权限上限，工作目录里的文件和依赖目录保留；等待审批超过期限时先停止环境，批准后在下一个环境执行；资源显示“随本轮结束已停止”或“停止待确认”。
- [ ] 按 ITE-19 验证 runner 的可信程度：版本比较、候选发布、变更回执用到的目标和摘要全部由宿主自己读回；任务代码伪造 runner 输出时按效果未知处理；execute 响应丢失后，当前环境停止接收 execute 并请求整体停止。

完成条件：真实的产品准入、SQLite、认证通信、Pi runner 和容器一起通过代表场景；不能用手工 `docker exec` 成功代替这一阶段。

### P5：继承自动审查并完成独立资格验证

## 切换、回退与停止条件

阶段编号就是主要的执行顺序：

1. 改造主线 P0 → P1 → P2 → P3 → P4。只有 P1/P2 的门槛都满足，才接通 P3 的隔离测试执行。
2. P5（自动审查）的本地核对可以和主线并行、提前开展；P6（页面）的真实环境路径依赖 P3/P4；P7（迁移）的兼容设计从 P1 开始，迁移演练在 P4 之后完成。
3. P3～P7 通过后进入 P8：全量检查和平台资格验证通过后，才能在另行授权的目标上执行现场部署。

真实的自动审查和部署各自按授权执行，不作为合同开发的前置条件。数据库结构、授权和持久化方面的改动，不与正在修改同一文件的其他工作同时进行。

切换时，先阻止旧路径接收新的高副作用任务，排空并核查旧环境，unknown 保留原来的占用；只把满足新资格的任务派给新后端。不需要全站停机，但旧风险没清除之前，相交的工作目录不能迁移。即使新运行时健康，也不能把旧 Mac 上的 unknown 当作已停止。

失败回退的做法是：关闭新执行入口、保存现有记录、保留当前或兼容版本的恢复能力；**不允许退回宿主执行、清空占用、改写历史证明，或回滚到不认识新 `lease` 的写入方**。后端的安全保证失效时，停止新准入，并为相关环境建立事故记录；不删除资源来掩盖故障。

必须停止启用的情况：必需策略无法强制、身份或证明不可信、停止后仍有写入或连接、全量验收缺失、未知占用被提前释放、运行时或 socket 暴露给任务、历史数据被无依据地升级成“已确认”。测试失败要先诊断，不能放宽断言或无理由增加重试来凑出通过。

## 问题

只要打开的对话里有过 Run，页面每 2 秒做一次完整刷新：重读侧栏全部列表页、整段对话的全部消息、每个 Run 的执行记录和执行状态、执行环境与待审批列表。对话早已结束、什么都没变时也一样。长对话（例如 `e11074e5`）每 2 秒要读上千条消息，“这段对话加载较慢”的提示、文字跳动和服务器负载都来自这里。

定时读当初是为了补上两类不发对话事件的变化：执行记录增加（模型输出、工具进度），以及资源状态变化（停止中、核对中、观察窗到期）。

## 目标与边界

- 页面不再定时重读对话。没有事情发生时，打开的对话不产生任何后台读取。
- 运行中的变化由服务端主动推送，页面只读变化的那一个 Run，并且只读新增的执行记录。
- 对话事件（新消息、Run 开始和结束、改名、归档等）按事件所属对话增量处理，不再整页重读。
- 资源状态到期类变化（观察窗过期、截止时间已过、恢复期限已过）由服务端在到期时刻推送，不靠页面计时。
- 不改数据库结构、不新增持久状态、不改执行事实和投影结论；只改“页面什么时候读、读什么”。
- 执行环境的后台程序列表（有后台程序时每 15 秒读一次）不在本次范围内，保持不变。

## 服务端：执行变化流

新增一个按对话订阅的事件流，和现有对话事件流用同一套 SSE 传输、身份校验、心跳和会话复核。

- 订阅：`thread.execution_events`，参数只有 `threadId`。打开对话时页面订阅，切换或关闭对话时断开。
- 事件：`thread.execution_changed`，字段为 `threadId`、`runId`、`runRevision`、`traceSequence`（该 Run 已有的最大执行记录序号）、`resourceRevision`（资源清单指纹，没有资源读取能力时为空）和 `observedAt`。它只是“这一轮变了，请来读”的提示，不携带执行内容，也不是持久事件：没有游标，不写入对话事件表，不参与对话事件流的去重和顺序校验。
- 服务端为每个连接维护一份该对话各 Run 的观察指纹：Run revision 与状态、最大执行记录序号、资源清单指纹、检查点指纹，以及资源状态的下一个到期时刻。指纹任何一项变化，或当前时间越过下一个到期时刻，就推送一次该 Run 的变化。
- 下一个到期时刻从资源清单里已有的时间推出：释放回执的接受时间、恢复的开始和截止时间、计划的有效截止时间、资源观察的发生时间与有效期、任务环境调用截止时间、执行租约到期时间中，晚于当前时间的最早一个。它和资源投影使用同一份清单与同一组比较，投影结论在这些时刻之外不会因时间而改变。
- 已结束且资源已全部释放、没有待到期时刻的 Run 视为已稳定，此后只在 Run revision 变化时才重新观察。已结束但资源仍未确认的 Run 每 5 秒检查一次清单；未结束的 Run 每 0.5 秒检查一次。
- 连接建立后的第一次观察，对每个未稳定的 Run 都推送一次变化，保证页面在“读完补读”和“服务端开始观察”之间的任何变化都不会漏掉。
- 对话不存在、已删除或不在可读状态时，流发送 `thread.execution_unavailable` 并结束。身份或会话失效时按现有规则发送 `gateway.stream_error`（`IDENTITY_SESSION_INVALID`）。

## 页面：按事件增量更新

- 删除每 2 秒一次的完整刷新。
- 只在当前对话有未结束的 Run，或某个 Run 的执行状态仍是“结果未确认”（含停止中、核验中）时才连接执行变化流；全部 Run 都已结束且结论已定时断开，对话事件带来新的 Run 时再连接。浏览器对同一地址的 HTTP/1.1 长连接最多 6 条，每页原有两条事件流，如果执行变化流一直开着，两个标签页就会占满连接，第二页刷新时卡在加载（2026-10-25 Hermes 浏览器检查发现）。
- 执行增量读取期间如果发生了完整读取，这次增量结果作废，要读的 Run 放回队列重新读；以前作废后不再读，同一 Run 的后续变化会丢失，直到下一次变化。
- 执行变化事件：只处理当前打开对话的事件。对事件里的 Run，从页面已缓存的最大执行记录序号往后读 `thread.execution`，再读一次该 Run 的 `thread.execution_state`。80 毫秒内的多个事件合并为一次读取，同一 Run 只读一次。事件序号不高于缓存时跳过执行记录读取，仍读执行状态（资源或到期变化不增加执行记录）。
- 对话事件：事件流把事件所属的 `threadId` 交给页面。页面重读侧栏列表；如果事件属于当前打开的对话，再从已显示的最后一条消息序号往后读 `thread.detail`（消息只追加、不修改），用返回的对话摘要和 Run 列表替换旧值，并对新出现或 revision 变化的 Run 做一次执行读取（同上）。其他对话的事件只更新侧栏。80 毫秒合并规则不变。
- 首次打开、切换对话、筛选变化、用户写入操作之后、以及服务端要求重新快照时，仍做现有的完整读取。
- 其他标签页写入游标时，本页只按“当前对话的对话事件”处理，不再整页重读。
- 后台读取的失败、重试和提示规则沿用侧栏规格：已显示的对话按 1、2、4、8 秒重读，连续失败 3 次才提示。执行增量读取失败时改做一次完整读取，由完整读取按这套规则重试和提示。

## 断线、重连与补读

- 两个事件流各自断线重连，退避为 0.25、0.5、1、2、4、5 秒。
- 执行变化流每次连接成功（包括第一次和重连），页面对当前对话的全部 Run 做一次补读：执行记录从缓存序号往后读，执行状态全部重读。服务端第一次观察会再推送未稳定的 Run，重复读取由缓存序号去重。
- 对话事件流重连成功时，按现有规则做完整读取（它本来就会补上断线期间的对话事件）。
- 页面隐藏时连接保持；对话事件流断开（包括浏览器离线）时执行变化流一并断开，对话事件流恢复连接后执行变化流重新连接并补读。

## 协议与兼容

- 网关对话协议 v3 新增一种订阅（`thread.execution_events`）和两种事件（`thread.execution_changed`、`thread.execution_unavailable` 作为 SSE 事件名）。现有消息不变，旧的对话事件流不变。
- 页面运行时配置新增 `executionEventsAvailable`；为 false 时页面不订阅执行变化流，也不定时读，只在对话事件和手动刷新时读取（与没有执行投影能力的部署一致）。控制中心和服务端同一次发布，不需要旧页面兼容新服务端以外的组合。
- 这是 Agent 与页面之间的协议变化，按测试规则单独跑第 3 层。

## 取舍

- 选择按对话订阅，而不是在全局对话事件流里推送所有对话的执行变化：服务端只需观察打开的那一个对话，长对话之外的 Run 不产生任何读取；切换对话只重连这条小流，不影响全局事件游标。
- 服务端观察仍是读数据库，因为执行记录由 Agent 进程写、资源清单由 Worker 进程写，没有跨进程的写入通知。观察只读指纹（序号、清单），不解密载荷；只有清单变化时才计算一次资源投影来判断是否稳定。
- 不把执行变化写成持久对话事件：执行记录每秒可能有多条，写进对话事件表会放大存储和游标，并改变对话 revision 的含义。

## 验证

- 应用层：到期时刻与资源投影在到期前后结论一致；观察指纹在执行记录、清单、检查点、Run revision 变化时改变，到期时推送；首次观察推送全部未稳定 Run；已稳定 Run 不再读清单。
- 网关与 HTTP：订阅授权、会话复核、事件序列化、对话不存在时的结束事件。
- 页面：没有 Run 在运行时不发任何查询；执行变化只读对应 Run 的增量和状态；对话事件只对当前对话读消息增量；重连后补读；不再出现 `thread.list`/`thread.detail` 的周期性查询。
- Hermes 第 0–4 层；第 4 层在真实浏览器里看一次运行中的输出是否连续推进、结束后资源状态是否自动变成已释放，并记录长对话的打开时间。

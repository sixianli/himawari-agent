## 目标与交付边界

让已经完成的任务可靠释放工作区，让仍可能运行的任务保持必要隔离；批准、执行、结果确认、资源清理和用户看到的状态保持一致。覆盖正常流程、并发竞争和各持久化边界的中断，不承诺有限测试可以枚举现实中所有故障组合。

本稿将用户在第二稿后逐项确认的方案写入设计合同。本次授权范围是修订 Spec，不包括产品实现、数据库迁移或生产操作。`active` 表示这项设计工作尚未结束；已确认的原则、尚待选择的启用参数和实际实现证据必须分开记录。本稿不替换原有 ADR 或冻结视觉原型。

### 1.2 当前实现的优点和缺口

| 范围 | 现有能力 | 当前问题 / 设计要求 |
| --- | --- | --- |
| 审批 | 冻结 intent、revision、scope、过期检查，批准与 grant 落库 | 保留；补取消/被新请求替代的归属，明确授权不等于执行开始 |
| 授权与 handle | 一次额度、撤销、expiry、authority fence、幂等键 | 保留；把额度绑定到同一个逻辑操作，排队不消耗新的额度，恢复不创建第二次授权 |
| 工作区互斥 | inode/device 目录身份、父子路径重叠、read/read 并行、写入排他 | 占用从目录授权根和授权操作类型推导，不能精确表示本次只改一个文件；release 依赖带短期有效期的结果投影，交接慢会保留占用 |
| 自动审查 | 现有 ActionPolicy、授权复用和人工确认入口 | 已核对的生产 coding 路径未发现完整模型自动审查接入；不能把现有允许规则称为已实现 Auto-review |
| 结果交接 | durable intent 和确认，防止重复执行 | 待交接与运行中的资源混用占用；结果 ACK 不应决定物理释放 |
| 执行错误 | 未知结果保守处理，不直接重发 | `production-runtime-tools.ts` 大范围 catch 吞原因，准入拒绝也变未知 |
| 恢复 | 有 scoped inspect/stop，authority/CAS 保护 | startup 对 released/lost 跳过；reconcile 对 released 直接返回；pending 查询漏掉“资源结束但占用未释放”的不一致记录 |
| Run | 持久化暂停/恢复、取消、执行租约 | quarantine 本身不是核对任务；部分未知 Run 被候选查询排除，没有自动结论；取消先成为 terminal 再清理 |

## 三、先明确用户流程

```text
工具提出一个具体请求
        ↓
宿主核对目标、影响范围和明确禁止规则
        ↓
授权判定
  ├─ 已有有效授权/允许规则覆盖 → 获准
  └─ 未覆盖
       ├─ 允许自动审查 → 通过 / 建议替代 / 人工确认 / 拒绝
       └─ 不允许自动审查 → 按策略人工确认或阻止

所有获准路径汇入同一执行入口：
选定受限执行方式 → 只等待真正冲突的资源
        ↓
执行前复查权限、目标和取消
        ↓
执行 → 记录结果 → 核实并释放不再需要的资源
        ↓
交付结果；通知丢失只重交
```

明确禁止时直接阻止，不进入自动审查。审查建议更安全的做法时，Agent 形成新请求并重新经过同一入口；不直接执行审查模型输出的命令。

1. 权限回答“允许做什么”；本次占用回答“为防冲突，此刻哪些资源不能同时被改”。二者分别计算。
2. 普通文件先准备完整内容，临近保存才取得目标文件的短时提交权。文件 A 与文件 B 无实际依赖时不互相排队，也不检查对方无关文件的版本。
3. 普通命令按授权在当前目录的真实沙箱内执行；独立试验、并行大改动等任务可选择隔离工作副本。命令的实际可写上限必须与并发协调范围一致。
4. 等待用户、自动审查、模型生成或候选差异审核时，不取得新的共享文件占用；此前仍活跃的独立任务继续保留自己的必要保护。
5. 保存前发现目标变了，不覆盖。已有授权覆盖时可读取最新版重新生成；意图不清或需要扩大范围时才交给用户决定。
6. 结果和释放凭据持久保存后交付给 Pi 与网页；通知、确认收件延迟不重锁、不重跑。私有环境清理与共享文件提交权分别释放。
7. 取消或撤销阻止后续动作，并核实已有进程停止。已经发生的修改如实保留，不把停止当成自动撤销。

## 四、五组状态和跨状态约束

不把所有组合塞入一个庞大 Run 枚举。用有明确 owner 的状态记录，再由一个后端投影计算页面状态。

<a id="approval"></a>

### 4.1 审批决定（Approval）

[↑ 返回已确认方案摘要](#review-summary)

`pending → approved | denied | expired | cancelled | superseded`

- 人工审批的 `approved` 是用户曾经同意的历史事实，不因为 grant 后来撤销而改成 denied。自动审查批准必须另记决策来源，不能显示成“用户已确认”。
- 两设备同时批准：比较 revision、intent digest 和 idempotency key；同一命令重放返回原决定，互相冲突的命令只有一个生效。
- 具体目标、内容或命令变化时建立新的不可变 intent；被新请求替代的待处理审批转 superseded，已批准历史不改写。新 intent 是否再问用户取决于有效授权范围：若用户仅批准了确切内容，不能用旧单次批准覆盖新内容；若已有有效范围授权确实覆盖新请求，可复用该授权。网络范围、接收方、预算或其他授权边界扩大时，不能沿用不覆盖它的批准。
- 超时、取消先提交时，迟到批准不派发；批准先提交也仍需在派发边界检查取消/撤销。
- 审批摘要使用带版本的规范化 SHA-256 与完整冻结对象比较；旧 `intent-xxxxxxxx` 只作为历史 v1 标识，不单独承担新请求的安全绑定。数据库读回的对象、owner 和 scope 始终是权威。
- 不改变既有联网搜索“记住选择”合同，不顺带开放持久写权限或 bypass 模式。
- 请求必须属于当前登录主体可操作的会话；身份不匹配、会话已退出或要求的近期认证不满足时，不落审批决定、不派发。重新认证后读回原审批；期间若已过期/被处理，不能复活。页面切换不能把 A 会话的批准发给 B 会话。

#### 自动审查接入规则

复用 `ActionPolicy / Approval / Grant` 的统一入口，不新增旁路执行渠道。判定顺序为：

1. 核验主体、具体请求、当前策略以及硬拒绝。明确禁止直接阻止。
2. 核对已有有效授权或明确允许规则；覆盖则按既有受限执行合同运行，不再调用审查模型或重复询问。
3. 未覆盖时，只有配置允许自动审查的操作才进入审查。审查输入限于获准提供的具体请求、必要用户意图和影响资料；工具结果中的文字不能改变审查规则。
4. 审查可给出：在委托范围内批准本次具体操作、建议更安全的请求、需要人工决定或拒绝。宿主验证结构化决定、请求身份、策略版本及范围后才使决定生效；自由文本不是授权凭证。
5. 审查不确定、超时、服务失败或返回无效结果时，按策略在会话内询问或明确阻止，不能默认放行，也不能把它伪装成用户拒绝。等待期间无本次共享文件 claim。
6. 审查结果与请求、审查配置版本和决策来源一起持久记录。重复通知复用同一已生效决定；权限撤销、过期、硬拒绝和请求变化仍须重新判断。自动审查不能自行扩大允许它批准的范围。
7. 派发前仍核对有效权限、目标身份、预算及取消状态，并使用原有 Pi 工具与真实沙箱。用户批准和自动批准都不能替代执行限制。

自动审查能力上线前必须完成模型/服务、资料披露、费用和委托批准范围的具体选择。只借鉴主流产品的分层原则，不宣称复刻其未公开的分类器或内部协议。

#### 本轮环境扩权（2026-09-25 新增的决定类型）

隔离执行改造后，一轮对话（Run）里的工具在同一个隔离环境中运行。这个环境有一份环境权限上限（capability envelope），即环境里任何程序最多能做的事：能读写哪些目录、能连哪些网络目标、能用哪些凭据。上限在本轮内只增不减；要增加时需要一个单独的“本轮环境扩权”决定，获批后停掉旧环境、换一个新环境。完整规则见[隔离执行 Spec 的环境权限上限与换新环境](2026-09-24-isolated-tool-execution-design.md#envelope)和[谁可以批准扩权](2026-09-24-isolated-tool-execution-design.md#expansion-approval)。与自动审查有关的规则（用户 2026-09-25 确认）：

1. 自动审查只能批准委托清单里事先列好的扩权项，例如“允许访问 npm registry”。委托清单由人配置，带版本号；清单的每次修改和每次按清单作出的批准都记入审计。自动审查不能修改清单。
2. 写入新目录、使用凭据、访问清单外或不限目标的外网，不能写进委托清单，必须由人批准。本轮第一个工具调用确定初始上限时同样按这套分类判断，不能借第一次调用绕过。“由人批准”可以是人在本次审批中确认，也可以是一条由人作出、仍然有效、明确覆盖这项能力的范围授权，这时不再询问（用户 2026-09-25 确认）。这与本节判定顺序第 2 步“已有有效授权覆盖则不再询问”一致，但只认决定来源为人的授权，自动审查作出的授权不算。凭据除外：始终每次由人在本次审批中确认。
3. 自动审查遇到清单外的扩权不作决定，转交会话内的人工审批。
4. 扩权需要停掉本轮已启动的后台程序时，仍可由自动审查按清单决定，但会话里必须明确显示被停掉的程序。每次审批都展示当前环境已有的能力。

与上文自动审查规则的关系：

- 第 4 条“在委托范围内批准本次具体操作”保持不变，仍只针对一条具体操作。本轮环境扩权是另一种决定：它只把清单里的能力加进本轮环境的上限，本身不批准任何命令；之后每条命令仍按本节的判定顺序逐条判断要不要问。
- 第 6 条“自动审查不能自行扩大允许它批准的范围”同样约束委托清单：清单只能由人修改，自动审查只能在清单内作决定。

这条规则的验收是[隔离执行 Spec](2026-09-24-isolated-tool-execution-design.md#acceptance) 的 ITE-20；不新增 R 编号。

<a id="grants"></a>

### 4.2 有效权限（Grant / 一次操作额度）

[↑ 返回已确认方案摘要](#review-summary)

持久 grant 保留 `validFrom / expiresAt / revokedAt / uses / budget / scope / revision`；effective 状态由它们计算：`not_yet_valid | active | expired | revoked | exhausted`，不另存可漂移的重复布尔值。主体、scope、硬拒绝策略与当前预算另做准入判定；grant active 不代表任意操作都获准。

一次逻辑操作额度：`available → reserved(operationId) → committed(invocationId)`；确定尚未派发的 reservation 可 `released`。额度 reservation 本身不是工作区 reservation。

- 等待用户、排队及准备失败不花掉第二次额度；同 operation 恢复共享同一 usage。
- 派发 intent 持久化是承诺点，之后按原 invocation 核对，不把不确定操作的额度退回给另一个请求。
- 新 grant 只给未来的合规操作，不复活旧进程、旧 lease 或旧工具调用。
- 临近到期在实际派发时再次检查；任务预算、审批期限和执行截止分别记录，排队不偷换成执行时长。超时需要重新评估，禁止自动延期。
- 排队期间策略收紧、资源换位、内容或预算发生变化时重新准入；新限制阻止派发。策略放宽也不自动把过去的拒绝改成批准。Worker 使用已核验的目标身份和 expectedBeforeDigest，避免“批准后文件被替换”导致覆盖不同对象。
- 执行中撤销：阻止后续派发/披露；对已有本地任务发停止控制并核验。撤销不能撤回已发邮件或已提交的文件修改。
- 清理/核验使用受限的宿主管理权限，只能 inspect/stop 既有资源身份；不需要复活旧 grant，也不能执行新命令或把私有结果发送模型。

<a id="operation"></a>

### 4.3 操作执行（Operation / Attempt）

[↑ 返回已确认方案摘要](#review-summary)

```text
proposed → policy_check → [auto_review / awaiting_approval（按需）] → ready
ready → preparing → dispatched → running → verifying_result
verifying_result → succeeded / failed / partial（结果已知时）

精确文件发布子流程：staged → waiting_resource → committing → committed
当前目录命令：waiting_resource（仅冲突时）→ running → 结果核验与资源释放
可选候选环境：isolated_running → candidate_ready → 范围/版本检查 → 文件发布子流程
候选差异仅在既有授权未覆盖时请求必要确认，不默认每次要求人工审核

尚未派发的拒绝、过期或取消 → not_executed（附具体原因）
可能产生副作用但结果不明 → 按工具恢复策略处理 → 已知结果 / unresolved
运行中停止请求 → stop_requested → stopping → stopped / 恢复处理
```

`waiting_resource` 是具体冲突资源的等待，不能在普通精确文件准备阶段就取得整目录排他权。审批、自动审查、候选差异审核和模型生成期间不取得新的共享提交锁。

- `dispatch_pending` 需区分“尚未交付”与“交付可能发生”；事务内 outbox 及发送记录定义边界，不能根据异常类型猜测。
- `failed` 不等于零副作用；另有 `effect=none | verified | partial | unknown`。普通 bash 非零退出可能已经修改文件。
- `not_executed` 必须有未派发证据。缺 Worker 事件只能说明缺观察，不能单独证明未执行。
- Run 聚合：某个可恢复工具失败不必强制终止整轮；Pi 可在明确结果下选择安全替代。主目标无法完成、拒绝或过期时给出解释并结束/暂停，不能无界重复索要批准。
- `unresolved` 是主动恢复已达边界且尚无结论，不是“正在处理”；保留后续核验能力和资源保护，不再后台重试模型。
- 背景 task/service：start 返回句柄只表示已启动；资源所有权显式转到已有受管任务记录，操作完成不代表服务停止。资源租约不得脱离可发现的 owner。

<a id="claims"></a>

### 4.4 工作区占用（Claim）与完整性保护（Barrier）

[↑ 返回已确认方案摘要](#review-summary)

物理占用：`unheld → reserved → held → releasing → released`。准备期间未派发且已失效：`reserved → released`。进程状态不明：`reserved/held/releasing → quarantined → releasing → released`。

**released 是对特定 resource incarnation 的不可逆历史事实。** incarnation 按资源类型记录身份：进程环境记录 host/boot、environment、worker boot、process start identity、namespace/cgroup；受信文件提交记录 operation/attempt、提交器 epoch、路径与目标版本。两者都记录 policy digest、scope digest 和最终序号，不要求每次文件提交创建容器。新执行取得新的 claim；不更新老记录重新上锁。

释放事务的必要条件：

1. 不再可能通过旧 dispatch/start intent 启动该资源；已关闭/撤销的派发身份必须能被 Worker 拒绝。
2. 对进程环境：宿主核验其本体及后代均退出或已被不可绕过地隔离，mount/namespace 与写入能力已解除；PID 消失、lease 过期或 Worker 自报成功都不够。对受信文件提交：确认本次提交已结束或被拒绝，旧 attempt 不能再次发布；不要求停止长期运行的提交服务。私有环境清理与共享文件提交锁分别释放。
3. fresh verification 在本次提交时有效，身份和资源版本匹配、摘要校验通过；SQLite 事务以 CAS 同时保存释放凭据和更新 claim。
4. 凭据一经验证并提交，未来按 digest/身份验证历史真实性，不能再拿当前时间与原 `validUntil` 比较而推翻释放。有效期约束“何时接受新观察”，不是抹掉过去事实。

结果 ACK、用户是否看过结果、模型是否还有披露权，都不能重新取得物理占用。

**资源停止与文件结果完整性是两件事，但不是所有不确定文件都需要禁止读写。** 普通文件先完整准备再发布，提交前失败保留旧版本；已停止且只剩私有临时文件时，不阻止共享文件。允许经授权的诊断读取已停止后留下的内容，并明确其部分/未知状态。

仅在以下情况保留受限 barrier：旧 writer 可能继续写入；同一次提交可能稍后生效；中断的多文件发布需保留版本才能恢复。范围为真实可达的冲突资源，而不是默认整个工作区。已经停止且有稳定版本的损坏文件可以进入恢复/修复流程，不无限冻结。

- barrier 有原操作、受影响范围、阻止的动作、可验证解除条件、恢复 owner 与 blocked 原因；不能由泛化的 `unknown` 自动扩大。
- 后到矛盾证据触发新 incident，暂停对应资源的新提交，不篡改历史 released。
- 不提供绕过仍活跃 writer 的强制解锁；没有可靠隔离证据时，明确暂停该资源，其他资源继续工作。

<a id="delivery"></a>

### 4.5 结果交接（Delivery）

[↑ 返回已确认方案摘要](#review-summary)

`pending → persisted → delivered → acknowledged`，任意步崩溃通过同 deliveryId 重放。

- SQLite 保存结果引用与 delivery outbox 后，通知至少一次；Pi continuation 和 UI reducer 按 operationId/eventId 去重。
- ACK 缺失只重发结果通知，不重跑工具；模型结果披露前仍检查当时权限。
- 用 intent kind 区分可能启动/变更资源的控制消息，与只交付已有结果的消息；只有前者阻止资源释放。
- 已完成文件可见但模型披露权限已撤销时，展示“文件已生成，结果未继续发送给模型”，不能改成工具执行失败。

## 五、并发边界与提交协议

<a id="execution-scope"></a>

### 5.1 按执行方式和可强制范围判定，不使用“复杂命令”分类

[↑ 返回已确认方案摘要](#review-summary)

工具接入时说明执行方式、能力、可信来源、可施加的限制和重试语义。每次调用再由宿主结合参数、当前授权与可用执行环境计算边界。复用现有工具描述、Pi Operations 适配和命令 profile，不另建一套工具协议。

| 工具/执行方式 | 执行位置与权限 | 并发协调范围 |
| --- | --- | --- |
| 纯 web_search | 网络代理与私有临时目录；不挂载用户工作区，不申请用户工作区权限 | 无用户文件 claim；保存结果另走获准文件操作 |
| 精确 read/write/edit | 现有执行端沙箱与受控文件接口，目标由宿主解析 | 本次目标及必要路径身份；不同文件可并行 |
| find/grep/ls | 受限只读接口或快照 | 默认尽力一致，不全目录排他；稳定读取与原地修改冲突需协调，一致视图使用快照 |
| 在当前目录运行 Bash、脚本、构建等 | 继续使用现有沙箱；按任务约束可读、可写和网络范围 | 协调实际可强制的访问上限；纯读取兼容并行，写入范围重叠才冲突 |
| 可选隔离工作副本 | 普通受限副本或符合条件的 Git worktree，加原有沙箱 | 副本内资源独立；应用改动时只协调授权的目标文件 |
| 远程工具/服务 | 远端凭据与服务端限制落实远程权限 | 以远端对象和副作用合同协调；本地沙箱不能代替远端权限控制 |

**宿主不能准确预测任意脚本最终会访问哪些文件。** 文件工具可从参数获得精确目标；任意程序以执行环境实际能限制的范围作为准入和协调上限，再另记运行中观察到的实际影响。模型说“只改 A”或工具标注“只读”不能当作强制边界。新增工具也按这组条件判定，不维护一份含糊的“复杂工具名单”。

优先给当前目录命令最小可行的范围。若执行环境只能给某命令整目录写权限，就不能只登记文件 A 的占用；必须协调该可写范围，或为有隔离需要的任务选择私有环境。范围不能可靠落实时明确阻止或要求调整方案，不能静默扩大权限。选择较大协调范围是该命令真实访问能力带来的限制，不应传染给普通精确文件工具。

需要声明读取稳定性和先后依赖：命令虽只写 A，但结果依赖 B，仍需保证所依赖 B 的版本符合要求；无依赖的 A/B 操作不做额外相互等待。端口、数据库、Git index 等共享对象单独协调，不能伪装成普通文件 A 的锁。

工作副本按任务需要选择，例如并行试验不同方案、大范围隔离重构。保存一首诗、修改指定文件不自动引入建副本、比较和应用流程。Git worktree 不隔离端口、外部数据库、网络或全部 Git 共享元数据，也不能替代沙箱。

<a id="conflicts"></a>

### 5.2 资源身份和冲突规则

[↑ 返回已确认方案摘要](#review-summary)

锁管理器由宿主确定资源，不能接受模型自报“只改一个文件”。资源键需同时处理路径槽位与当前文件身份：已有文件的 host/device/inode（或平台等价身份）、父目录身份与归一化 basename；新建文件使用父目录身份+名称，不能要求目标已存在。原子替换改变 inode，路径槽位仍需互斥。硬链接别名需按文件身份关联；不能安全解析的别名拒绝操作，而非退回纯字符串比较。

父目录的存在/身份保护是兼容性约束，不意味着对同目录所有不同文件串行化。目录重命名/移除与后代操作冲突；两个不同文件的创建可并行。统一排序后一次预约全部必要键，不持有一部分再等待另一部分。

| 并发组合 | 结果 |
| --- | --- |
| read A / read A 或 B | 并行 |
| write A / write B，资源集合不冲突 | 并行，包括同目录不同文件 |
| write A / write A | 提交排他；后者目标版本不符则冲突，不覆盖新内容 |
| read A / 原地 write A | 冲突等待；原地写只属于明确受控例外 |
| read A / 原子替换 A | 可读完整旧版本；要求前序写后最新值时按依赖等待提交 |
| rename 目录 / 后代读写 | 按下列目录改名协议等待相关操作，不影响其他目录 |
| grep 多文件 / 并发写 | 尽力一致可能跨版本；承诺一致视图时读取快照 |
| 私有候选任务 / 共享目录工具 | 并行；候选准备和测试不占共享提交锁 |

每次读取返回版本信息；同一工具读取期间检测身份/内容变化。允许旧完整版本不等于允许读到原地写入中间态。跨文件业务一致性不能由独立文件锁保证，需明确快照或事务资源范围。

#### 目录改名的具体协调规则

以 `报告/一月.md`、`报告/二月.md` 和“把报告目录改名”为例：

1. 文件操作只保护自己的文件，并登记其祖先目录路径在本次操作中须保持原位。两个文件对祖先路径的要求彼此兼容，仍可并行。
2. 改名申请等待已经开始、与该目录改名冲突的文件操作完成，不等待整轮聊天结束。`日记/` 下的操作照常进行。
3. 改名进入队列后，新到的冲突操作排在它之后；无关操作不排在它之后，避免改名永远等不到也避免全局堵塞。
4. 改名前一次取得源和目标涉及的必要资源，重新核对权限、源目录身份、目标槽位及取消状态，再执行经过平台验证的改名。
5. 改名完成后，后续操作重新解析路径和对象身份。不得把所有排队请求机械改写成新路径；只有确认仍是被授权对象且范围仍有效时才继续，否则返回“目标位置已变化”。
6. 跨文件系统移动是复制与移除的另一个操作合同，不当作一次原子改名；只有真实工具能力、授权和平台验证具备时才支持。


实施合同补充：目录操作通过产品工具 `move_directory` 和 `pi-coding-tool@4` 接入原 Worker/准入队列；Pi 没有对应内置目录移动工具，因此只增加产品工具定义，复用 Pi 的工具循环。宿主冻结源目录 inode、源槽位、目标槽位及父目录身份，一次预约三个资源。macOS 使用 `renameatx_np(RENAME_EXCL)`，Linux 使用 `renameat2(RENAME_NOREPLACE)`；固定程序不复制、不覆盖、不跨盘降级。原生程序随各平台产物编译并计入安装字节校验，运行时不调用编译器。

`fixed-file-terminal-no-writer.v1` 是固定文件程序的独立完成资格：只允许合同 3/4、前台模式、经过核验的发布或确定未发布冲突、原任务和 Job Host 退出以及清理完成时释放资源。资格绑定当前安装字节，不授予新目录权限，也不证明普通命令的任意后代已退出；中断、未知结果、缺少资格或清理证据时继续保护。实际目标启用仍需目标安装资格，不能复制测试资格记录。

合同 3 的 Worker 版本冲突只有在任何正式路径发布系统调用之前、未创建缺失父目录、已保存候选且持久提交标记不存在时，才记录确定未发布的失败。提交标记一旦写入，后续故障不得反向解释为未发生效果。Agent 核验原输入、候选摘要、Scope、Worker 结果及受保护交付回执后，才把该失败交回原 Pi 循环；新调用沿用原冲突关联、重新读取、授权和次数限制。重放保留“已接收但未发布”的事实，不伪装为从未派发。

SQLite Schema 46 标记新 writer 边界，保留全部旧队列、占用和发布记录；旧 writer 不得写入新库。工具依赖的先后关系沿用 Pi 工具定义的 `executionMode: sequential`；同一工具批次必须等待前一次工具完成，跨 Run 的独立文件仍由共享资源队列并行协调。

<a id="file-publish"></a>

### 5.3 普通写入：准备与发布分离

[↑ 返回已确认方案摘要](#review-summary)

1. 冻结 operationId、授权主体、目标路径、expectedBeforeVersion（新建为 absent）、内容摘要和允许操作；权限检查不能只依赖 UI。
2. 在受控临时区写完内容。提交所需临时文件须与目标同一文件系统；受信提交器负责暂存，不能因此给模型进程整个父目录的写权限。
3. 写入并按平台要求同步数据，进入 staged。此时失败或取消只留下私有临时内容，正式文件不变。
4. 获取目标及必要资源的短时提交权；重新检查权限、取消意图、目标版本、路径与父目录身份。版本不符进入 conflict，保留候选差异；不自动强制覆盖。
5. 在副作用前保存提交意图。新建使用平台验证过的“不覆盖发布”原语；不得用普通覆盖 rename 或直接写最终文件代替。替换使用原子替换并检查旧版本。全部共享写者必须受该接口或真实沙箱约束，普通文件锁无法阻止外部不合作进程。
6. 保存提交结果，包括操作身份、前后摘要/版本和必要恢复依据；按平台验证父目录持久化。文件系统与 SQLite 不是同一事务，使用阶段日志及操作绑定的暂存/恢复记录解释崩溃间隙。仅内容相同或同名存在不能证明是本次提交。
7. 提交者不再能改变目标、结果已可恢复后释放提交权；持久结果交接不续占。资源释放历史事实不受临时凭证后续到期影响。

取消在不可分割提交之前可生效；与提交竞争时保留真实先后结果，不能假装撤销已经保存的内容。主机上的手工编辑若无法受控，采用检测冲突并提示的合同，不宣称严格 compare-and-swap；严格模式必须有可强制的唯一写入入口。

已有 `ConstrainedFileSystem.replaceAtomic()` 可复用；`createExclusive()` 的最终路径直接写入须改为安全发布。`SandboxedCodingOperations` 与 Pi Operations 适配继续复用。Linux/macOS 的 no-replace、文件权限/元数据、链接语义、崩溃持久性须分别验证，不能用一个平台通过替代另一个平台。

#### 目标已变化时，如何继续

- 保留候选改动、释放已无必要的提交权，不覆盖对方修改。
- 已有授权确实覆盖时，Agent 可以读取最新版，在原目标与预算内重新生成修改；无法理解双方意图、需要扩大范围或只有不覆盖新内容的确切单次批准时，按 4.1 重新判定并请求必要确认。
- 新内容使用新 intent，记录它接替哪个发生冲突的尝试。排队或断线后的同一内容交付仍使用原操作身份；不能以“重新生成”为名重放已经完成的非幂等副作用。
- 保存前再次检查版本和权限。相关依赖变化时，原测试结论不自动沿用；重新验证受影响部分。
- 自动重新生成受已有预算、次数和截止条件约束；持续冲突时保留结果并明确暂停，不无限付费重试，不在模型生成或等待用户时持锁。

<a id="optional-workcopies"></a>

### 5.4 可选工作副本与多文件提交

[↑ 返回已确认方案摘要](#review-summary)

本节只适用于已选择隔离副本的任务，不是普通命令的必经路径。“应用到正式项目”在本稿中统一称为**把本次改动保存回用户原工作目录**，不意味着部署服务或发布到生产环境。

1. 建立获准的基线。普通目录记录目标的内容版本、身份和必要快照；Git 仓库可选 worktree，但不能默认从 HEAD 创建就包含用户当前未提交或未跟踪内容。明确本任务需要的输入，保护已有改动，排除未获准私密路径，不复制整个 HOME。
2. 在副本中执行和验证，记录基线与实际改动。运行期间不持有共享主目录的提交锁；外部网络、数据库等副作用仍受独立权限和恢复规则约束。
3. 列出本次新增、修改、改名或移除的文件；只保存任务产生且被授权的改动，不能整目录覆盖回来。移除是文件级能力，须已有明确授权；它不引入删除会话功能。
4. 检查目标和依赖相对基线是否变化；变了按 5.3 重新生成/确认。已有有效授权覆盖改动时不重复请求人工确认，未覆盖时重新经过 4.1 的统一判定，仅在需要用户决定时在会话内确认；等待期间不持锁。
5. 准备完整待保存内容；按相关依赖决定需要重新运行的验证。取得必要目标的短时提交权，再检查一次权限、版本、路径身份与取消。
6. 按 5.3 逐文件安全发布并记录结果。多个文件逐个替换不是整批原子事务；中断时明确哪些已保存、哪些未保存。需要跨文件一致读视图的消费者使用快照或受控版本入口，不能靠单文件原子替换假装满足。
7. 本次提交结束且不可能迟到再写后释放共享占用并交付结果。用户未打开结果、网页未确认收到，都不能继续占用文件。

自动回滚只有在权限允许且目标仍是本次保存的版本时执行，不能覆盖之后的编辑。唯一结果、必要差异及恢复证据保留到明确策略处理；保留期限尚未选定，超时不自动应用差异或删除唯一结果。长运行服务须保留可发现的 owner，不因启动请求返回就销毁其环境。

普通目录的版本检查与安全发布不依赖 Git；Git 仅提供可选的版本和工作副本能力。

实施合同补充：Owner 的 `workspace.copy.create/select/prepare` 保存当前输入、选择副本并冻结逐文件操作；`prepare` 不修改原目录。保存通过产品工具 `save_copy`（`pi-coding-tool@5`，前台 `verified_effect`）回到原 Pi 工具循环、ActionPolicy、Run/Handle、持久准入队列和 Worker。参数只引用原操作 ID 与摘要，宿主从受保护记录解析具体 create/update/move/trash；trash 使用 `DELETE` 判定，不能借更新权限执行移除。Pi 没有这种 Owner 冻结的差异提交操作，因此工具定义由产品提供，文件效果复用 `FileOperationService` 与 P3 固定发布器。

内容、操作快照及目标/依赖身份在排队前完成准备。提交仅占用实际目标、移动目的槽位和必要依赖；依赖的排他占用只维持版本稳定，不授予写权限。固定程序直接发布已暂存内容，不在占用期间重新生成候选。原固定程序的私有持久记录同时供正常结果导入和释放后的恢复使用；恢复只核验原 inode/摘要及回收区对象，不能重新执行移动、删除或覆盖后续编辑。多文件仍是逐项结果，先前保存成功才可成为后续操作的已验证依赖。

非文件对象不因工作副本而获得授权：当前 SRT 不开放宿主 TCP 监听、任意 Unix socket 或 Git index 写入；服务只使用自身私有就绪 socket，仍通过原受管任务记录保留 owner。产品 SQLite 继续由 Agent 的事务与权威 fencing 管理，副本不能访问该数据库；远端请求单独受网络授权和既有调用回执约束，未知外部效果不自动重发。没有对应受控服务合同的共享数据库/远端对象写入，不能用普通文件占用代替其权限或一致性保证。


### 5.5 最小接口与公平排队

```ts
type AccessPlan =
  | { kind: "network_only"; networkGrantRef: string; privateTempRef: string }
  | { kind: "file_read"; targets: readonly FileTarget[]; consistency: "stable_version" | "after_dependency" }
  | { kind: "file_publish"; targets: readonly PublishTarget[]; stagedRef: string; operationId: string }
  | { kind: "shared_sandbox_command"; profileRef: string; enforcedAccessRef: string; operationId: string }
  | { kind: "isolated_command"; candidateRef: string; profileRef: string; baseVersionRef: string }
  | { kind: "remote_service"; servicePolicyRef: string; targetScopeRef: string; operationId: string };
```

`FileTarget` 与 `PublishTarget` 由宿主解析身份，含读取依赖或 expectedBeforeVersion；这里只是接口草图，不新增已发布合同。`enforcedAccessRef` 必须引用宿主验证过、执行环境实际可强制的读写上限及依赖，不能是模型声明；当前目录命令不能只靠事后审计防止越界。`network_only` 不能携带共享目录 grant；隔离命令不能直接调用共享目录写端口。远端限制须由远端服务或受控凭据落实。提交接口分别返回 committed、conflict、not_started 或 outcome_unknown，不能把所有异常折叠为未知。

复用 SQLite 的预约/outbox/公平队列，按相交资源集合判断冲突；不为每个目录另建调度器。队列不持有部分锁，出队重验权限与目标版本，取消后释放该操作额度预约。后到冲突请求不能使旧请求饥饿，无关资源不被队首阻塞。

## 六、授权及执行关键竞争的判定

| 竞争 | 生效规则 |
| --- | --- |
| 同时批准与拒绝 | 同 revision CAS，第一个提交生效，另一个看到已处理 |
| 自动审查完成与撤销/策略收紧/请求变化 | 重新核对被冻结请求及当前策略；迟到审查不能恢复失效权限或批准替代请求 |
| 自动审查和人工决定竞争 | 同一决策版本只有一个生效；已拒绝的请求不被晚到自动批准复活 |
| 版本冲突后重新生成 | 新内容新 intent；已有范围授权覆盖才继续，不借旧确切内容批准扩大权限 |
| 批准与过期 | 服务器可信时间和审批事务决定；客户端按钮可点不代表有效 |
| 批准与取消 | 取消已提交则不派发；批准先提交也须通过 dispatch 前取消检查 |
| 撤销与 dispatch | 同一权威持久化边界排序；Worker 开始前校验 fencing/取消状态；已可能执行则停止并核验 |
| lease 到期与 Worker 仍运行 | 新 epoch 隔离旧权限；确认旧进程不能再写之前不得只按 TTL 解锁 |
| 完成与取消 | 已持久确认的完成不被晚到取消覆盖；取消先到但完成后来才证实则保留 stopRequested 与真实 effect，显示“停止前已完成写入” |
| 失败与副作用 | 已知错误可带 partial/verified effect；不能一律显示“未执行” |
| 重复 dispatch / 重启重放 | operationId + invocationId + epoch 去重；旧 token 不得启动新资源 |
| 交接与撤销 | 可以记录历史结果，但向模型/用户披露分别校验；不重新执行、不重占工作区 |
| 后到旧事件与新状态 | 拒绝旧 epoch/旧 incarnation 的控制作用；只按匹配的历史 identity 归档，页面序号不能倒退 |

不能承诺任意外部操作 exactly-once。对于本地受控 write，使用内容摘要、expectedBeforeDigest、exclusive create / 原子替换和持久变更回执核验；仅仅发现同名文件存在不是成功证据。对于无法提供幂等键或独立读回的外部接口，未知时不自动重发。新尝试要重新核验预算和权限。

<a id="recovery"></a>

## 七、恢复与错误合同

[↑ 返回已确认方案摘要](#review-summary)

### 7.1 错误必须保留“在哪一步失败”

建议用产品边界类型表达，不把 catch 下所有异常压成一个值：

```ts
type DispatchEvidence =
  | { kind: "not_sent"; admissionRevision: number }
  | { kind: "possibly_sent"; invocationId: string; epoch: number }
  | { kind: "accepted"; invocationId: string; workerReceiptRef: string };

type FailureDisposition =
  | { kind: "not_executed"; reason: SafeReason; retry: "after_recheck" | "none" }
  | { kind: "execution_failed"; reason: SafeReason; effect: EffectEvidence }
  | { kind: "reconciling"; recoveryId: string; nextAttemptAt: string }
  | { kind: "unresolved"; recoveryId: string; scopeBlocked: boolean };
```

完整 schema 还应定义 SafeReason、EffectEvidence 和版本；这里是接口草图，不是已发布合同。日志保存 stage、安全 reasonCode、run/operation/attempt、epoch、server timestamp；private 原始错误受保护保存，不在网页暴露堆栈、路径凭证或原始模型推理。

### 7.2 按失败类型恢复，不统一进入核验

| 失败事实 | 恢复动作 | 共享资源影响 |
| --- | --- | --- |
| 明确未派发/权限拒绝/版本冲突 | 立即报告准确原因；修正条件后重新评估 | 无不确定提交则不占用 |
| 正常文件竞争 | 可取消的资源队列 | 仅相交提交范围等待 |
| 网络只读请求短暂失败 | 按错误类型、额度与期限有限退避重试 | 无共享文件 claim |
| 浏览器断线、后台仍运行 | 重读持久快照和事件 | 不因客户端离线改变真实占用 |
| 提交完成且记录可恢复，通知未 ACK | 重交同一结果 | 不重跑、不重锁 |
| 文件发布发生在记录间隙 | 按操作身份、阶段记录与版本核验 | 仅可能迟到提交的范围保护 |
| 私有命令环境失败 | 保存差异/日志；按策略从基线重建或结束 | 不冻结主目录；外部副作用另核对 |
| 外部副作用未知且无幂等/读回 | unresolved，停止该操作自动重发 | 不占本地无关目录 |
| 旧进程可能仍修改共享资源 | scoped inspect/stop/隔离 | 保护实际可达范围，证实隔离后解除 |

只对实际需要核验的操作建立 recovery item，复用已有持久恢复存储；保留 owner、错误类型、尝试次数、下一次时间和明确暂停原因。调度查询必须能发现 released 仍残留 occupancy、terminal Run 仍有资源等不一致，不能把所有 reconciling Run 排除。

四类时间分别配置：工具最长执行时间、无进展检测、停止宽限、按错误类别的重试期限/次数。没有统一两分钟规则。具体数值来自工具/provider 合同、平台停止能力、历史耗时与故障注入数据；当前单次 inspect 30 秒只作为已有实现上限记录，不证明整体恢复策略已合理。无依据的默认值不得冻结为产品要求。

有充分证据立即结束，无需等到预算。重试耗尽、不可重试、宿主不可达或权限不足时，按实际原因进入 failed/paused/unresolved；只有后台确有运行中的核验才显示“正在核对”。用户“检查状态”仅触发允许的读回，不自动重写文件、发起模型调用或延长权限。

安全清理可 inspect/stop 原资源，文件内容核验须受专门的只读恢复范围控制；不继承旧 grant 向模型披露私密结果，也不获得新的写入/外发权。后台资源管理与业务副作用核验分开，二者不会互相作为永久等待条件。

### 7.3 磁盘满与半提交

授权、reservation、outbox 必须在任何副作用前成功持久化；失败则不启动。执行后写结果失败时归入 possibly_sent，先保留隔离，靠宿主受保护回执恢复。数据库事务不能跨整个工具执行；事务原子性只覆盖本地状态，不能冒充外部文件/API 回滚。日志存储失败也不得触发重发。

状态优先级：先按每个 operation 的持久终态/恢复状态，再停止、审批、排队、已接收开始的执行、准备、模型活动。连接状态是叠加提示；不能覆盖已完成事实，也不能让客户端离线计时伪装成新的后端证据。

窄屏将当前需要操作的确认卡片、“检查状态”等动作放在详细执行链之前；不能让执行日志把批准按钮推到用户看不到的位置。

停止只取消意图，不自动回滚文件；“检查状态”不重新执行；“重试此操作”必须后端可用且重新评估当前权限/目标。已确认写入过的操作不提供无条件重试。UI 标记 pending 请求，服务器读回后才显示最终决定。

### 8.1 计时

- 分开：自动审查、用户确认等待、冲突资源等待、准备、工具执行、结果核验、资源清理、可观察到的模型输出阶段。重新生成修改也不计入文件工具执行；等用户 60 秒、实际保存 2 秒，必须分别展示，不能写“工具执行 62 秒”。
- 同进程用 monotonic clock 算实际区间并持久化；跨进程用匹配事件/服务器时间并检测时钟偏差，不能将负数裁成 0 假装精确。
- 网页可以从已确认 startedAt 平滑显示“已运行”，断连/进展过期时标注截至最后确认时刻；终态用持久 duration 覆盖。原型示例时间明确为样例，绝不进入正式数据逻辑。
- 并行工具区间可重叠，整轮活动时间取区间并集；总历时是墙钟跨度，二者不混称。审批、排队不能算作模型思考；没有可靠思考边界只显示可观察输出阶段或暂无时长。

### 8.2 断线、移动端与可访问性

事件含 operationId、attemptId、incarnation、sequence/revision；重连以快照校正后续增量，重复事件无效，乱序不得倒退。至少验证 320/390/1024/1440 宽度、明暗主题、长文件名、200% 缩放和键盘访问。

红点只表示需要处理，辅以可访问文本，不单靠颜色。状态重要变化用适度 aria-live，秒表不逐秒播报。焦点维持中性细边；按钮加载/过期/已处理均有明确状态。关页面不等于取消任务，归档不等于删除/停止任务。

## 九、模块边界和兼容性

[↑ 返回已确认方案摘要](#review-summary)

| 责任 | 复用/修改位置 | 不应承担 |
| --- | --- | --- |
| intent、审批和自动审查接入 | ActionPolicy / Approval / Grant services，复用既有模型访问边界接入审查能力 | 依据 UI 或模型自由文本授予权限；建立旁路工具执行入口 |
| 排队、额度、claim、outbox、release receipt | 现有 SQLite 持久化端口和短事务 | 把整个工具执行包在事务中 |
| 隔离、开始事件、进程身份、最终资源事实 | 现有 Anthropic Sandbox Runtime + Worker + platform-node supervisor | 重写沙箱或命令运行器；单凭 Agent RPC 超时猜测资源消失 |
| 核验与停止 | 现有 sandbox reconciliation + 可调度 recovery item | 继承旧 grant 执行新动作 |
| 模型工具循环 | runtime-pi + 固定 Pi API | 自造另一套模型协议 |
| 结果与 UI | 单一后端执行投影 + gateway + execution-view | 每个组件各自按最近日志猜状态 |

需要版本化新增 receipt、queue/recovery 和前端投影 schema。优先复用现有表与 outbox；只有现有记录不能表达时新增小表。新 writer 启用前完成迁移、reader 和 Worker 兼容检查；旧客户端不认识的新状态显示“状态需要更新”，不能误报失败或成功。新增内部状态与外部 Run 枚举分开，避免为了 UI 文案大面积更改公共 Run 合同。

进入实施阶段时，按治理规则提议必要 ADR，记录“永久释放证据与短期执行权分离、未知效果与物理占用分离”及新增自动审查的责任边界；不得改写既有 ADR 的历史。本次仅修订 Spec，不更新 Architecture 为尚未实现的事实。

## 十、历史数据恢复与上线要求

1. 上线前重新只读盘点全部未释放 claim、活跃进程、旧 boot、未确认 dispatch、结果回执、完整性 barrier。不能仅按 `supervision=released` 批量 UPDATE。
2. 创建可验证备份和每条修复前后记录；部署新释放/恢复合同前暂停相关新写入调度，保留用户草稿和阅读能力。
3. 对每条历史资源，用受限 inspect 核验宿主清理及旧派发身份不可再启动；证据不足保留隔离。历史过期凭证不能直接伪造成 fresh proof。
4. 成功核验后 CAS 写入 release receipt；待交接结果单独恢复；无必要 barrier 时才允许新写入。
5. 对原失败操作，证明未派发则明确结束为 not_executed；不偷偷替用户重新生成或写文件。再次尝试按当前目标和权限执行。
6. 验证新旧记录、active/archived 会话、并发写入、资源归零和服务重启。实际模型验收使用已授权模型和预算，不能用 fixture 代替。
7. 回滚不能把新增释放凭据丢给不理解的旧 writer。保留新 reader/迁移或停止写入后做受控兼容回退；绝不恢复旧数据库覆盖新用户消息。

## 十二、验收结论的必需条件

1. 11ms/151ms 延迟案例 failing-before、passing-after；释放后推进时钟不会重新占用。
2. 同一工作区连续多轮 read/search→write，写入可独立读回，所有应结束资源已释放。
3. 在可能仍有进程写入时，无论 timeout/restart/revoke，都不能放行第二个冲突 writer。
4. 原型状态与真实后台状态一致；未开始写入不会显示执行中；不确定结果不会显示确定失败；停止请求不会立刻声称无副作用。
5. 新恢复逻辑能处理历史残留，无法处理时明确 blocked；没有永远被调度排除、前端却一直转圈的记录。
6. 不同文件独立并行，目录改名按既定队列规则完成；当前目录命令按可强制范围协调，不强制所有命令建副本。
7. 自动审查在选定配置和委托范围内通过真实集成验收；无硬拒绝绕过、无未获准披露或付费，所有工具仍通过既有执行通道。
8. 普通目录与 Git 目录均验证；冲突后重新生成不覆盖他人修改，也不将确切单次批准扩大为长期写权限。

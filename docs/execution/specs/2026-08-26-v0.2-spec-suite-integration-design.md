## 跨切片集成契约

### 一套身份和因果链

所有 Spec 共用 S1 定义的 Owner、Agent、authority epoch、Thread、Message、Run、Task、Approval、Grant、Result、Inbox Item、Trace 和 ResourceRef 身份。S2–S9 可以定义领域子身份，但必须引用同一 Owner/Agent/Run/Trace，不能创建第二套“浏览器会话事实”“Worker Agent”或 adapter 自有权威。

每个入口使用统一因果链：

~~~text
authenticated source
  → immutable Command/Event identity
  → authoritative commit
  → Run/Task/ActionIntent
  → deterministic authorization
  → scoped capability handle
  → side-effect/reconcile
  → Result + Trace
  → AttentionDecision
  → Web delivery
~~~

浏览器、模型、Worker、Memory backend、browser automation、Calendar provider 和 capability runtime 都不能跳过该链直接提交产品状态。

### 单一权威和持久提交

- 只有当前 fenced authority epoch 可以接纳命令、消耗 Grant、执行外部行动和提交长期状态。
- UI optimistic state、模型输出、Worker result、provider callback 或 adapter cache 都不是 committed fact。
- 已接受命令先持久化 stable ID，再返回成功；SSE/重连只重放 committed events。
- 进程崩溃后从 checkpoint 和 side-effect observation 恢复；未知外部结果先 reconcile，不盲目重放。

### 授权、能力和秘密

- S4 是 ActionIntent、risk、policy、Approval/Grant 和 Capability Manifest 的 canonical owner；各能力 Spec 只增加 domain facts 和 deterministic risk floor。
- 任何新 target、operation、data disclosure、recipient、cost、frequency、credential/access、side effect 或 capability version 扩张都重新授权。
- machine secret 仅通过 host-bound secret ref 和一次性 Handle 使用；S1 负责全局排除，各能力 adapter 负责在自身输入/输出再次排除。
- 主机迁移后所有 host-bound directory、Web session、Calendar/provider credential 和本地 program secret 保持 blocked，不能由迁移包恢复。

### Context、Memory、Worker 和 Trace

- S2 决定 Thread 可见语义，S1 决定 Memory 产品事实和最小检索，S8 决定 Worker 最小委派；三者使用显式 refs，不复制整个私人历史。
- 所有模型调用记录实际 provider/model、披露、输入 context refs、用量、费用和结果；不展示或伪造不可观察 hidden reasoning。
- 能力参数/结果、授权判断、Worker delegation、重试、状态变化和外部副作用进入同一完整 Trace；secret 原值和被删除正文不得出现。

### 结果、注意力和 Web

- 所有交互、Task、GitHub、Calendar、Web action、Worker 和 reflection 结果先进入 S1 的统一 Result/Outbox；S3 只负责呈现。
- Attention 只使用 `SILENT / INBOX / DIGEST / NOTIFY / INTERRUPT`。模型建议不能低于确定性安全下限，S3 不能因浏览器离线丢弃。
- v0.2 唯一 Owner-facing delivery 是 Web。网页上向第三方发送消息属于 S5 的外部行动，不是产品通知渠道。

### 删除、迁移和生产证据

- S1 是产品对象删除、7 天 Trash、级联、墓碑、30 天恢复点清除和迁移包的 canonical owner；领域 Spec 必须提供其索引/cache/provider/session/workspace 副本清除 hook。
- 删除不能被 Memory backend、search index、Calendar/Web session cache、Worker artifact 或 release evidence 重新激活；最小审计墓碑不得保留被删正文。
- S9 只把各 Spec 的验收证据聚合为 release qualification，不重新定义产品行为或豁免失败项。

## 冲突、遗漏和变更处理

| 情况 | 必需行为 |
| --- | --- |
| PRD digest 或条款数量变化 | S0 失去完整覆盖状态；重新分配并复核全部受影响行 |
| 条款没有主责 Spec | 阻止相关 Plan 和 v0.2 qualification，不以 Backlog 代替当前范围 |
| 两个 Spec 定义冲突状态/身份/授权 | 停止实施；按 PRD、accepted ADR 和已确认产品决策协调，必要时新建/修订 ADR |
| Spec 与 PRD 冲突 | PRD 产品合同优先；修订 Spec，若要改变产品范围则先修订 PRD 并确认 |
| Spec 与当前 Architecture 不同 | 这是 change design；Plan 必须包含 Architecture reconciliation，不能把未来设计写成当前事实 |
| provider/platform 无法满足硬要求 | 明确 blocker；不能静默删掉平台、能力、安全规则或验收 |
| 新能力/未来方向进入实现 | 先修改产品范围、权限和验收并治理文档；v0.2 扩展边界不构成授权 |
| 实现只覆盖 UI 或 happy path | 对应 requirement 未完成；必须有 authority、failure、recovery、security 和跨平台证据 |

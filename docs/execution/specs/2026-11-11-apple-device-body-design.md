<a id="goal"></a>

## 目标

让 Himawari 从“只有主人打字它才知道、只有网页推送能找到主人”，变成有感官、有嘴和耳、有手：

- **感官**：知道主人正在经历什么（听到的、去过的、日程、身体、看到的、读到的、周围的情境）。
- **时机**：知道现在该不该开口。
- **在场**：不打开对话框也能用它（随口叫它、原生聊天和语音、小组件、带按钮的通知、锁屏进度）。
- **动手**：在主人的设备上把事办成并核实（日历、提醒事项、通讯录、闹钟、家居、Mac 上的文件和 App）。

要变好的数字（定义沿用 `docs/product-vision.md` 的 Jarvis Test 和现有周报）：记忆回忆准确率、多余的提醒占的比例、每周需要主人介入的分钟数、任务完成验证率；新增[说完到第一个字](#transport-metrics)等延迟数字。

## 范围

包括：

- 服务器：设备配对和接口、连接、感知记录、感知抽取、来源登记、送达时机、苹果推送、设备工具、上限和用量、删除规则。网页不加新页面（Andy 2026-11-12：“有 APP 版就不再做网页版啦”）；网页现有的“设置 → 设备”保留，第一台设备的配对和手机丢了以后的移除都靠它。
- 客户端：iPhone、Apple Watch、Mac 三个 App 和它们的扩展（小组件、通知按钮、分享、Safari 扩展）；随身麦克风经蓝牙接入。每一端只做它最擅长的那几样，见[客户端的结构和发布渠道](#clients)里的“每一端做什么”。
- 测试规则的改写（ADR 0229 决定第 8 条）。

不包括：

- 自定义键盘（Andy 已定先不做）。
- 按量付费的实时语音模型（和“禁用贵模型”冲突）。传输层留了位置。
- 平台做不到的：iPhone 和手表在后台自己打开麦克风、通话录音、直接读别的 App 的通知和界面、不经主人确认发短信。绕路的办法见 `/mnt/project-files/ambient-sensing/integrated-plan.md` 第 10 节。
- 多人的开通流程本身（由 [ADR 0234](https://github.com/sixianli/himawari-agent/blob/7d0ffcd52cbb69d4941871cf9bf08d93f3843da8/docs/adr/0234-one-program-per-person-database-file.md) 和“多人使用”线程管：一套程序、一个网址、每人一个数据库文件）；这里只保证设备接口能按设备找到是谁，见[设备身份和配对](#identity)。

## 验收条件

每条都有正向和反向两种。完整的检查清单在[检查和验收怎样做](#verification)。

第 1 到 3 条依赖“认出是主人在说话”。认人的错认率达标之前（见[指令和数据的界线](#instruction-vs-data)），这三条按“达标前”的样子验收：听到的话都只当线索；口头指令在两种情况下从第一天就执行：戴着 AirPods 叫它的名字（不用动手）；或者按按钮、抬腕、用 Siri 之后说。只有“没戴耳机、对着放在一旁的手机或 Mac 叫名字”这一种要等认人达标。达标后再按下面写的验收一遍。

1. 主人对朋友说“我喜欢骑车”，之后问“周末去哪玩”：回答用上这一点，并说明是听到的。反向：电视里的同一句话、朋友说他自己喜欢骑车，都不会记成主人的偏好。
2. 主人戴着耳机说“嘿 Himawari，帮我……”：耳机里听到回答，电脑网页上同时出现这轮对话。反向：朋友说同一句话，不执行。
3. 主人在收听时说出“周六七点和小林吃饭”：她在主对话里说一句，下面带一个写明要建什么的选项和“不用了”，点了才建，建完能撤销，决策记录里有一条。反向：网页或短信里写着同一句话，同样只给选项、不自动建，并写明是从哪看到的。（原先写的是“亲口说的直接建”；2026-11-12 起改成等主人点；2026-11-24 起放在[主对话](#main-chat)里。）
4. 一条非紧急提醒在主人开会时产生：会后才送到，不晚于它的最晚送达时间。反向：状态不知道时不额外延后。
5. 通知上点“同意”：审批通过。反向：过期、重复点、审批内容变了、换一台设备点，都无效；高风险的不解锁点不了。
6. 在网页上吊销一台设备：它已连着的连接最迟在下一次心跳时断开，之后连不上；设备上的本地缓存被清掉。
7. 删一段感知记录：只由它产生的记忆不再被想起。
8. 用量页和小组件上每个上限显示上限、已用、何时清零、到了会怎样。反向：没有用量时显示 0。
9. 地铁里断网几秒：回答接着出，不重来、不丢字、不重复。
10. 加新工具和这批新提示词的那个版本上线后：每个老对话只重建一次请求开头，之后逐字节稳定。

## 1. 总体结构

```text
iPhone / 手表 / Mac（随身麦克风经蓝牙接到其中一台）
   │  采集、转文字（可在设备上）、显示、执行动作
   │
   │  HTTP/3 多通道（设备到 Cloudflare）；没有连接时：系统代传文件、苹果推送
   ▼
Cloudflare（服务令牌是第一道门）──隧道──▶ 生产机上的 Himawari 服务
                                          │
            ┌─────────────────────────────┼──────────────────────────────┐
            ▼                             ▼                              ▼
   设备接口 /api/device/v1         感知记录（自己的表）            现有的对话、记忆、
   （设备密钥签名、白名单命令）     │                              审批、决策记录
                                   ├─▶ 感知抽取（后台）──▶ 记忆；新知道的事 ──▶ 收件箱
                                   ├─▶ 系统主动提醒的检查（来源登记）──▶ 送达时机 ──▶ 推送
                                   └─▶ perception_read 工具（对话里按需读）
```

分工：

|                                  | 设备                                                                 | 服务器                             |
| -------------------------------- | -------------------------------------------------------------------- | ---------------------------------- |
| 收音、拍照、读屏幕、定位等采集   | 全部                                                                 | 无                                 |
| 人声检测、转文字、认人、屏幕认字 | 每一步、每种语言按实测决定在哪做                                     | 始终具备全部能力，可以重做         |
| 记忆、规则、决策记录、调用大模型 | 只有只读缓存                                                         | 全部                               |
| 推送                             | 接收、按钮、实时活动、小组件                                         | 决定发不发、何时发                 |
| 设备动作                         | 执行、读回                                                           | 决定、审批、记录                   |
| 界面                             | 全部原生，不嵌网页；每一端只做它擅长的那几样（见[客户端](#clients)） | 提供数据；选项和同意卡片上的字由服务器给 |

服务器这一侧**不需要会说 HTTP/3**：HTTP/3 只在设备到 Cloudflare 这一段，Cloudflare 经隧道把每个请求按普通 HTTP 转给生产机（ADR 0229 前提 13）。所以设备接口在服务器上是普通的 HTTP 路由加现有的事件流，自动测试可以直接对它跑。

## 2. 设备身份和配对

**设备种类**：`iphone`、`watch`、`mac`。随身麦克风不是一台“设备”，它没有自己的密钥，是接在某台设备上的一个采集来源（感知记录里记 `capture_source = wearable_mic`）。

**这是谁的设备**：按 ADR 0234，一套程序服务多个人、每人一个数据库文件。设备请求进来时，要在打开任何人的数据库之前知道它是谁的，所以共用层加一张“设备索引”表（不是名册，名册的内容不变）。ADR 0234 已经有同类做法：Gmail 授权回调“按记录找人，这个记录要从内存挪到共用层”（决定第 5 条）。设备索引只有两种行，都不含私人内容：“设备编号 → 人”和“配对码的哈希 → 人、过期时间”；设备名、公钥等其余信息在那个人自己的库里。规则：设备编号由服务器在配对时生成（128 位随机），索引里唯一，同一个编号不能对应两个人；配对码只存哈希，没用过的码过期就删那一行；用过的码留到主人下次开始配对时再删，这样配对到一半断网的设备拿同一个码、同样两把公钥重试，会拿回同一台设备而不是报错；设备吊销时这一行留着（状态只在那个人自己库里的 `paired_devices` 表里，服务器照常按索引找到人、开库、看到 `revoked`，回“已吊销”，设备才能据此自清）；彻底删除一个人时（ADR 0234 决定第 10 条的流程里）连同他的全部设备索引行一起删，回执里核对；人在名册里停用时，他的设备请求一律拒绝（先查名册状态，再开库）。设备索引不进个人的数据导出，可以从各人库里的 `paired_devices` 表重建（含已吊销的设备；还没用掉的配对码不重建，让主人重新生成一个）。在 ADR 0234 的实现落地之前只有一个人，这个入口直接返回主人。

**配对**：

1. Andy 在已登录的网页“设置 → 设备”里点“添加设备”。服务器生成配对码：128 位随机数，10 分钟有效，只能用一次，库里只存它的哈希。“只能用一次”用一条带条件的更新来保证（还没用过、还没过期才标成已用），两个请求同时拿同一个码只有一个成功；配对入口在 Cloudflare 那道门后面，没有服务令牌到不了；码是 128 位随机数，不怕一个个试。手机扫码后先把二维码里的服务器地址显示给主人看，主人点了才发配对请求。
2. 网页显示二维码，里面是服务器地址、配对码和 Cloudflare 服务令牌（设备要靠它才过得了 Cloudflare 那道门）。二维码只在已登录的页面里显示。二维码的内容是一段 JSON：`v`、`origin`、`code`，加一个可选的 `access`（里面是 `clientId`、`clientSecret`）；服务器的密钥配置里有设备入口的服务令牌时才带 `access`，没有这道门的环境（例如测试服务器）不带。设备拿到后存进钥匙串，每个请求带 `CF-Access-Client-Id`、`CF-Access-Client-Secret` 两个请求头；没拿到就不带。
3. App 扫码，在安全芯片里生成两把 P-256 密钥：
   - **设备密钥**：平时签请求用，不需要解锁。
   - **确认密钥**：每次使用都要面容或解锁（给高风险审批用，见[推送和通知按钮](#push)）。
4. App 把配对码、两把公钥、设备种类、设备名、包的发布渠道发给服务器。服务器核对配对码，存下设备，状态是“等确认”。
5. 网页上立刻显示“有一台叫某某的 iPhone 想配对”，Andy 点确认后设备才变成可用。这样二维码被别人拍走抢先配对时，Andy 会看到一台不认识的设备，不点就没事。两边还各显示一个 6 位的**配对确认数字**，一样才点确认：对 UTF-8 字符串 `himawari-pairing-v1`、设备公钥、确认公钥（两把都是 SPKI 的 DER 编码）依次拼起来算 SHA-256，取前 4 个字节当大端无符号整数，对 1000000 取余，左边补零到 6 位，显示成“482 913”。手机自己算，而且只在服务器收下配对请求之后才显示；服务器不存这个数，列出“等确认”的设备时现算（字段 `pairingNumber`）。用处：别人抢先配对时，Andy 自己的手机收到的是“这个码用过了”，没有数字可对，就不会把网页上那台同名的设备当成自己的点了确认。两把公钥都算进去，是为了确认密钥不能被单独换掉。
6. 已经配对的 iPhone 也能发起和确认配对，不必回到网页：在“设置 → 添加设备”里刷面容后生成配对码并显示二维码（Mac 不方便扫时可以拷贝配对链接），新设备发来请求后，在这台 iPhone 上核对数字、再刷一次面容确认。生成配对码、确认、改名、移除设备在客户端能力表里都是“改”，列设备是“读”。
7. 手表经它配对的 iPhone 完成同样的步骤，有自己的密钥。

**每次请求怎样证明身份**：按 RFC 9421 签名。签名覆盖方法、主机名、路径、查询参数、正文摘要、正文类型、创建时间、一次性随机值和设备编号（RFC 9421 写明没被覆盖的部分可以被改而不影响签名，路径这一项不含查询参数，所以查询参数要单独覆盖）；算法 `ecdsa-p256-sha256`。服务器拒绝：创建时间和服务器时间差超过容许值的（容许值是配置，默认 60 秒）、随机值出现过的（随机值保留两倍容许时间）、设备不是可用状态的、路径不在白名单的。

**系统代传的文件不能用上面这种签名。** 苹果系统会在它认为合适的时候才上传，可能拖几小时到几天，请求头在入队时就定死了，到真正发出时 60 秒早过了，系统重试还会原样重发。所以后台上传另用一种凭据：设备在有连接时用正常签名向 `uploads/begin` 申请一个上传凭据，凭据绑定这台设备、这个文件的摘要（轨迹文件里的点没有记录编号，改绑设备在申请时报的批次编号，同一个批次编号只收一次）、文件里的记录编号范围和一个较长的有效期（暂定 7 天；苹果后台上传最长能拖多久还没读到原文，见[还没核实的事](#unverified)，核实后按它定）；服务器只在上传路径上认它，同一个凭据重复上传只处理一次，文件摘要对不上就拒绝。设备被吊销时它的上传凭据一起作废。

**密钥轮换**：设备可以用旧密钥签名提交一把新公钥来换钥；确认密钥丢失（例如重设面容）时在 App 里重新生成，并要 Andy 在网页上确认一次。

**吊销**：网页“设置 → 设备”里逐台吊销。吊销写库后立即生效：这台设备所有打开的连接最迟在下一次心跳时被掐断（现有事件流在每次发事件和心跳时核对身份）；它排队中的动作、通知按钮凭据、上传凭据作废；它的推送令牌停用。吊销成功之后服务器给它发一条“清掉本地数据”的推送（尽力送达，吊销请求被拒时不发）；设备下次联网收到“已吊销”的回答时也会清掉本地缓存和还没执行的动作。

**设备上的本地数据**：缓存的对话和记忆副本、待传队列，都用系统的文件加密存放（锁屏后读不到），不进系统备份。设备丢了：先在网页吊销，设备一联网就自清；它在没联网时本地仍有锁屏密码保护。

**服务令牌**：几台设备共用，只负责过 Cloudflare。泄露时在 Cloudflare 换一把，新令牌经已有连接下发给设备；设备密钥不受影响。

**App 里不嵌网页**（Andy 2026-11-12：“你不会要跟我说你是直接把网页迁移到 ios app 吧？”）。她的页面和它下面的记忆、定时、用量和上限、隐私、设备，以及同意卡片、数据导出，全部做成原生页面，按手机的用法重新设计，不照搬网页的布局。原先“不常用页面嵌网页”的做法省的是开发量，代价是 App 里要另外登录一次 Cloudflare、打开慢、离线看不了；Andy 的要求是不考虑开发量。只有一种情况会离开 App：第三方授权（例如 Gmail 授权）按苹果的要求用系统的登录面板打开，授权完回到 App。有几张页面手机上不做，留在电脑的网页上，清单见下面网页页面在 iPhone 上的去处，原因见[每一端做什么](#device-roles)和 ADR 0258。

<a id="ui-review"></a>

**界面对照验收**（Andy 2026-11-12：“你要监督实施开发写代码的线程严格按照原型去开发。保证视觉和交互的完美体验！”）。每个带界面的 PR 合并前由设计线程逐屏对照，三件事都做到才放行：

1. 数值只有一个来源。颜色、圆角、尺寸、字号、图标线宽都从 `tokens.json` 生成一份 Swift 常量，页面代码只用这些常量；共用包加一道检查，页面代码里出现颜色字面量或另写的圆角、字号数值就失败。现在生成器和 `npm run check:apple-design` 读的仍是第 2 版（`clients/apple/scripts/check-design.mjs` 的 `TOKENS_SOURCE` 是 `docs/assets/apple-clients/2026-11-12-v2/tokens.json`），生成的 `DesignTokens.swift` 里还有页签栏的数值、没有头像和选项两段，这道检查通过不说明第 4 版的数值已经进了代码。照第 4 版做的第一个 iPhone PR 先把 `TOKENS_SOURCE` 和测试夹具改成第 4 版的 `tokens.json`，重新生成 Swift 和网页扩展的 CSS，再做页面。
2. 截图对照。编码线程把这个 PR 做的每一屏在 390 点宽的 iPhone 模拟器上截图，浅色、深色各一张，内容用原型里的示例数据，文件名和基线里对应的图一致，放到 `/mnt/project-files/ambient-sensing/ui-review/<PR 号>/`。设计线程把它和基线叠在一起逐屏看：位置和尺寸差 2 点以内、颜色和字体一致才算过；不过的逐条写明哪里差多少，改完再看。结论写进 PR 描述（“界面对照：设计线程某日看过，N 屏，没有偏差”），没有这一行不合并。
3. 交互对照。动的东西（过程行的扫光、头像的生长和暖光、底部面板弹出、点下去直接出面容、内容从玻璃下面滚过）编码线程各录一小段屏，设计线程对照原型和[网页设计规范的“苹果客户端”一节](../../ui-ux-design-guide.md#apple-clients)看。

对照通过的截图存成共用包里的快照测试（在 Xcode 的单元测试里把页面画出来和存下的图比），以后改动走样了测试会失败。原型做不出来、或系统控件有更好做法的地方，编码线程不自己改，回设计线程改原型给 Andy 看。真机上的手感（面容、触感、滚动）最后由 Andy 在自己手机上看。

<a id="haptics"></a>

**触感**（Andy 2026-11-12：“触感也要好好做，触感要做的智能、体贴一些。”）。触感指手机和手表里的小马达给手的一下轻震。苹果的要求是按系统定好的含义用、全 App 一致、别滥用、能关、不干扰麦克风（[Playing haptics](https://developer.apple.com/design/human-interface-guidelines/playing-haptics)，原话：“Often, the best haptic experience is one that people may not be conscious of, but miss when it’s turned off”“Ensure that haptic vibrations don’t disrupt experiences involving device features like the camera, gyroscope, or microphone”）。我们照这个做，再加一层“看场合”。原则取舍：依据用户主权，触感能关、能调档；默认和“只留要紧的”两档下，开始收听这类事一定让主人的手知道，主人自己选了“关”就只靠屏幕上的标记。

每一下都有固定的含义，分两类：

| 谁引起的 | 事件                                         | iPhone                                                           | Apple Watch     |
| -------- | -------------------------------------------- | ---------------------------------------------------------------- | --------------- |
| 主人的手 | 发出一条消息                                 | 轻的一下（impact light）                                         | 点一下（click） |
| 主人的手 | 按住说话开始、松开                           | 开始中等一下，松开轻一下；先震完再开麦克风                       | 开始、停止      |
| 主人的手 | 点选项、拨选择器、拨开关                     | 系统控件自带的，不另加                                           | 表冠自带        |
| 主人的手 | 底部面板吸到位、下拉到位                     | 软的一下（impact soft）                                          | 不震            |
| 主人的手 | 按停止                                       | 硬的一下（impact rigid）                                         | 停止            |
| 主人的手 | 刷面容后改成了、没改成                       | 成功、出错（notification success / error）                       | 成功、失败      |
| 主人的手 | 配对成功                                     | “开花”：三下由轻到重、越来越密（自己做的）                       | 成功            |
| Himawari | 有事等主人点头（App 在前台）                 | “敲门”：软的两下（自己做的）；付款、对外发送这类重的事，两下更实 | 通知            |
| Himawari | 等了很久的事做完了                           | 成功                                                             | 成功            |
| Himawari | 整件事没做成，要主人知道                     | 警告（notification warning）                                     | 可重试          |
| Himawari | 没看屏幕时叫它名字，它听到了                 | 软的一下                                                         | 点一下          |
| Himawari | 这台设备开始收听、停止收听                   | 开始中等一下，停止轻一下；先震完再开麦克风                       | 开始、停止      |
| Himawari | 回答一个字一个字出来、中间某一步没成又接着做 | 不震                                                             | 不震            |

App 在后台时的提醒和审批走系统通知，震法由系统定，不归这张表。Mac 和随身麦克风没有触感。

看场合（这一层是“智能、体贴”的部分），由共用包里的一个函数统一判断，页面只报“发生了什么事”，不直接调震动：

1. 正在录音或收听时不震（“开始收听”那一下在开麦克风之前震完），免得震动被录进去。
2. 主人正看着这一页时，Himawari 的事只有“等你点头”震；“做完了”只在主人已经离开这一页、或这件事等了超过一个时长（暂定 10 秒，放设置里能改）时才震。
3. 同一种事几秒内接连发生只震第一下。
4. 手表戴着并连着时，Himawari 的事只在手表上震，手机不重复震；主人的手引起的那些，在哪台设备上按就在哪台上震。
5. 系统的专注模式开着、或日历上此刻有会时，只留“等你点头”，其余不震。
6. 设置里有“触感”一项，三档：全部、只留要紧的（等你点头、开始和停止收听）、关。“开始和停止收听”在“关”这一档也不震，但屏幕上的收听标记始终在。系统里关了触感时跟系统走。

“敲门”和“开花”两种用苹果的 Core Haptics（自己编排震动强弱和节奏的系统接口）做成两个文件，其余都用系统现成的。强弱和节奏在图上看不出来，所以设置的“Himawari 自己”里加一页“触感试手”：列出上表每一种，点一下震一下，Andy 在真机上逐个试，哪个不对回设计线程调。共用包加一道检查：页面代码直接调系统震动接口就失败。事件表和判断函数归第 2 批的共用包，手表那一列归第 10 批。第 2 条里“主人正看着”只按 App 在前台且这一页正显示来算，不用摄像头。

**原生页面怎样拿数据、改数据**：不为手机另写一套业务逻辑。网页现在用的每一种查询和命令（网关消息类型）登记进一张“客户端能力表”，每种标一档：

| 档         | 含义                                                                                           | 设备怎样证明                                                                                           |
| ---------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 读         | 看记忆、规则、设置、审批、提醒记录、用量等                                                     | 设备密钥签名（和发消息一样）                                                                           |
| 改         | 改规则、删记忆、改设置、导出数据、移除设备等                                                   | 先取一个一次性挑战值，再用确认密钥签“挑战值、消息类型、正文摘要”（要面容或解锁）；一个挑战值只能用一次 |
| 日常       | 对话里的日常操作：新建、发消息、改名、置顶、归档、恢复、移到废纸篓（能恢复）、分叉、换回答语言 | 设备密钥签名，不用面容。设备密钥本来就能发消息，这些都比发消息轻，而且能撤回                           |
| 收紧       | 关掉或暂停某一项感知、暂停记忆、让正在跑的一轮停下                                             | 设备密钥签名，不用面容；只认“往少的方向”的那一种正文（见下），重新打开和恢复属于“改”                   |
| 手机上不做 | 写明原因                                                                                       | 设备接口拒绝                                                                                           |

设备接口加一个入口 `POST gateway`：验签通过后，按能力表查这种消息类型是哪一档，够格就交给和网页同一个处理程序，结果原样返回。所以手机和网页走的是同一份逻辑，不会两边行为不一样。只拿到设备密钥、主人不在场时，能做的只有“读”“日常”“收紧”这三档和设备接口表里的其他命令；“改”这一档每次都要主人当场解锁。这里的“读”包括记忆、规则、设置、审批、提醒记录、用量这些查询，范围比 ADR 0229 原来那张白名单大，是 ADR 0247 决定第 2 条接受的取舍：这些本来就是解锁的手机打开 App 能看到的东西，设备密钥存在安全芯片里导不出来，手机丢了可以在网页上移除这台设备。“收紧”单列一档（2026-11-12，随原型一起定）：想让它少看少听时不该被面容拦一下，而这类改动只会让 Himawari 收集得更少，拿到设备密钥的人最多让它暂时收不到感知记录，每次都记进审计记录；往回打开要面容。

**档不只看消息类型，还看正文。** 网页现有的开关命令多是一个类型管两个方向，例如 `memory.settings.set` 的正文只有一个 `capturePaused`（`packages/gateway-contracts/src/contracts-v2.ts:2780` 起），`true` 是暂停、`false` 是恢复；`proactive.settings.set` 还同时带免打扰时段和重要发件人。所以能力表里“收紧”的每一行除了消息类型，还写明一个条件：正文必须恰好是哪些字段、取哪个值（例如 `memory.settings.set` 只有 `{ capturePaused: true }`）。设备密钥签来的请求，正文多一个字段、少一个字段或值不同，都不算“收紧”，按“改”处理，没有确认密钥签名就拒绝。新做的感知开关直接拆成“关”和“开”两种消息类型。

正文里除了方向还带一个“说的是哪一项”的键时，能力表的条目可以写两样：收紧值，和不参与比较的键。判断时先去掉正文里不参与比较的键，剩下的键必须和收紧值的键一个不多、一个不少，每个值完全相等并且是布尔值，才算“收紧”，否则按条目本来的档。例如关掉某一类通知：收紧值是 `enabled: false`，不参与比较的键是说明哪一类的那个键。这是第 11 批在 PR 426 里的写法，写这份文档时还没进 main，字段名以合并时的代码为准。

正文里除了方向还带别的设置的类型，不能靠“正文恰好是什么”来分：`proactive.settings.set` 的正文是 `enabled`、`quietHours`、`importantSenders` 三项（`packages/gateway-contracts/src/contracts-v2.ts:1401` 起），只看 `enabled: false` 的话，同一次请求还能顺手删掉免打扰时段、加重要发件人。所以这种类型整个算“改”；“暂停系统主动提醒”另加一个只有方向、不带别的字段的消息类型 `proactive.pause`（正文是空的，服务器只把 `enabled` 改成 `false`，免打扰时段和重要发件人不动），登记成“收紧”；它和 ADR 0247 决定第 2 条里“关掉或暂停某一项感知”是同一个方向，只会让 Himawari 少打扰。

别的档也按正文分。一个类型里有几种动作的，能力表按动作各写一行，没写到的动作一律按“改”：`memory.mutate` 的 `action` 有 `correct`、`archive`、`delete`、`restore`、`confirm`、`recover`、`pin`、`unpin`、`restore_version`（`packages/gateway-contracts/src/contracts-v2.ts:2965` 起），全部是“改”，记忆没有“日常”这一档的动作；上表“日常”里的归档、恢复、移到废纸篓说的都是对话。`thread.delete_permanently` 是“改”。

**挑战值不建表**（2026-11-12，第 11 批实现时定）。`POST approvals/challenge` 返回的挑战值由过期时间、随机数和服务器对它们加设备编号算的 HMAC 组成，HMAC 的密钥在进程启动时随机生成；手机把它当这次请求签名里的一次性随机值，设备密钥和确认密钥两个签名都覆盖它、方法、路径和正文摘要（正文里有消息类型）。“只能用一次”靠 `device_request_nonces` 那张防重放表：挑战值的有效期等于一倍时间差容许值，防重放表保留两倍，所以过期前一直挡得住。别的设备拿去用，HMAC 对不上。服务重启后没用掉的挑战值作废，手机重取一次。

**原生页面先上传文字**：网页的改名、置顶等命令的正文里放的是文字的引用，不是文字本身，所以设备接口有 `POST payloads/text/new`（设备密钥签名；`POST payloads/text` 是第 1 批做的按引用批量读文字）。网页的 `/api/payload/v1/text` 现在由 `packages/platform-node/src/http-gateway-server.ts` 的 `admitText` 处理，它里面先做同源检查、浏览器会话和 CSRF 校验，再校验和存文字；后一半拆成一个单独的函数，网页和设备两条路共用，上限也一样（`64 * 1024` 个字符，按 UTF-16 代码单元数，不是字节），设备这条路前一半换成验设备签名。

**授权引用和近期验证引用由服务器填。** 有些命令的正文里这两项不能为空（例如 `thread.delete_permanently`，`packages/gateway-contracts/src/thread-contracts-v3.ts:239` 起），所以手机在这两项里一律填固定的占位值 `device`，填别的值直接拒绝。服务器的顺序是：先对收到的原始字节验设备签名（“改”这一档再验确认密钥签名），再解析正文、查占位值、按能力表分档，然后把占位值换成服务器自己生成的引用，最后才做网关的合约校验并交给处理程序。签名覆盖的是手机发出的原始字节，所以服务器后填的值不影响验签。只有确认密钥签过的请求才填近期验证引用。

**确认密钥的签名怎样算近期身份验证。** 现有的近期身份验证只认三种来源（`packages/application/src/ports/recent-authentication.ts:5` 起：`cloudflare_access_login_time`、`built_in_mfa`、`provider_step_up`）。加第四种 `device_confirmation_key`：设备接口验过确认密钥签名后生成这条凭据，主体是这台设备对应的主人，验证时间是验签的时刻，有效期是一倍时间差容许值，验证引用用这台设备那条内部会话的 `authenticationRef`（现有检查要求凭据的引用等于会话的引用，`packages/application/src/services/recent-authentication-service.ts:60`、`:68`，这条检查不改）；这条凭据只挂在确认密钥签过的那一次请求上。允许的来源名单在同一个文件的 `validSource` 里（第 31 行起），要和类型一起加。设备的内部会话（`product_sessions` 行）本身不带任何近期验证凭据，不能借网页登录那条路自动得到 `built_in_mfa`；反向用例：只用设备密钥签高风险审批被拒、只有内部会话被拒、确认密钥签过才通过。“收紧”和“改”每次各写一条审计记录。确认密钥的签名同时算“近期身份验证”。

**两边不能悄悄不一致**：`npm run check:client-parity`（第 11 批新增，在那之前这道检查还不存在）读三样东西：能力表、网页的页面清单（`apps/control-center/src/app/control-center-inventory.ts`，只用来核对页面）、网关合约里属于查询和命令的消息类型（服务器发的事件和快照不算，对话那份和旧的那份重名的只算一次；`packages/gateway-contracts/src/contracts-v2.ts` 的 `GATEWAY_V2_MESSAGE_TYPES` 和 `thread-contracts-v3.ts` 的 `THREAD_GATEWAY_MESSAGE_TYPES`，以及最早那份 `contracts.ts` 的 `GATEWAY_MESSAGE_TYPES`；页面清单里不全，例如没有 `memory.settings.set`）。能力表里写了合约里不存在的类型、或某个原生页面在表里一种类型都没对上又没写原因（或写了原因其实对得上），检查也失败。设备管理（列设备、生成配对码、确认配对、改名、移除）和“感知到的”页用的查询和命令是新的消息类型，分别由第 1 批和第 3 批加进网关合约，第 11 批把它们登记进能力表。设备管理这一组是查询 `device.list.read`（读）和命令 `device.pairing.start`、`device.pairing.confirm`、`device.rename`、`device.revoke`（改），网页的设备页改成走同一批类型；网关的命令不能把结果直接带回，所以配对码由发起的一方自己用系统的安全随机数生成（16 字节），放在 `device.pairing.start` 的正文里，服务器照旧只存哈希、10 分钟、只能用一次。服务器状态页用新查询 `server.status.read`（读）。这些类型进 main 之前，对应的原生页面先不做，在页面表里写明在等什么。网关新增一种消息类型或网页新增一个页面而没在能力表里登记，检查就失败；Swift 那边的消息类型清单由能力表生成。每个网页页面在表里对应一个原生页面，或写明“手机上不做”的原因。

设备页的几条口径：别的设备只显示上次连上是多久以前，不推断“连着”；改名用系统自带的输入框，不另做一页；移除不另加确认框，面容提示里写“移除”加设备名；自己这台不显示移除；添加设备的码过了 10 分钟显示“码已失效”和“再出一个”；扫码以后、发配对请求以前，先显示要连的服务器地址，按钮是“连上”和“不是我的服务器”。

改规则不做表单：主人用一句话说要怎么改，Himawari 写出新旧对照，主人同意（刷面容）后才生效，走的是现有“模型调 `rule_set` 立规”的路（ADR 0213）。

**设备请求在服务器里怎样变成主人的身份**：对话接口的权限检查要求有一条活着的网页会话（`apps/agent-service/src/production-http-composition.ts:524` 的 `activeSession`）。库里原有的 `devices` 表是网页登录用的浏览器设备（`packages/persistence-sqlite/src/migrations/0001_initial_product_schema.sql:102`，`product_sessions.device_id` 指向它），所以配对设备的新表叫 `paired_devices`，不占那个名字。设备在网页上被确认时，服务器给它在原有的 `devices` 表里建一行、再建一条只在服务器内部用的 `product_sessions`，令牌不发给任何人，谁也没法拿它当 cookie 用；设备请求验签通过后，用这条会话组成身份，走和网页完全一样的对话接口。`paired_devices` 记下那一行的编号；吊销配对设备时这条会话一起吊销。这条内部会话不算“近期身份验证”：要主人本人在场的审批只认确认密钥的签名（见[推送和通知按钮](#push)）。

| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `paired_devices`        | 编号、种类、名字、设备公钥、确认公钥、状态（`pending`、`active`、`revoked`）、发布渠道、配对时间、吊销时间、最后在线时间、支持的动作清单、确认时在 `devices` 表里建的那一行的编号（内部会话用）                                                                 |

## 3. 设备接口

全部在 `/api/device/v1/` 下。除 `pair` 外都要设备签名。每个会改数据的请求都带设备生成的唯一编号，服务器收到重复的只认一次并返回第一次的结果。

| 路径                                      | 做什么                                                                                       |
| ----------------------------------------- | -------------------------------------------------------------------------------------------- |
| `POST pair`                               | 配对（见上节）                                                                               |
| `GET stream`                              | 下行事件流：对话事件、要设备做的动作、配置变化、用量变化。带事件编号，可从某个编号续传       |
| `POST messages`                           | 主人发来的话（打字或口头指令）。进现有对话，和网页发的消息完全一样                           |
| `POST utterances/partial`                 | 主人还没说完的半句话，只用于[抢跑](#prefetch)                                                |
| `POST uploads/begin`                      | 申请系统代传用的上传凭据（见上节）                                                           |
| `POST perception`                         | 一批感知记录                                                                                 |
| `POST perception/media`                   | 需要服务器处理的原始材料：压缩的音频小段、图片、屏幕画面                                     |
| `POST mirror`                             | 日历、提醒事项、通讯录、家居配件的全量或增量同步                                             |
| `POST track`                              | 一批轨迹点                                                                                   |
| `POST actions/result`                     | 设备动作的执行结果和读回的状态                                                               |
| `POST actions/undo`               | 撤销已成功的动作（日历和通讯录那几个）；带确认密钥签名才算主人亲自点                   |
| `POST approvals/challenge`                | 取一个一次性的挑战值（给高风险审批的确认密钥签名用，限时、只能用一次）                       |
| `POST approvals/respond`                  | 回答审批（来自通知按钮或 App 内）                                                            |
| `POST feedback`                   | 通知被点开或划掉（“有用 / 打扰”只在 App 里评，不走这里）                               |
| `POST companions`                 | iPhone 报告哪块手表是它的配对手表（手表自己不能报）                                    |
| `POST push/register`                      | 登记或更新苹果推送令牌（三种推送类型各一个）                                                 |
| `GET config`                              | 心跳间隔、每种感官的开关和保留期、转文字走哪条路、各项上限                                   |
| `GET usage`                               | 每个上限的用量（小组件和用量页用）                                                           |
| `GET threads`、`GET threads/{id}`         | 主对话的内容（原生聊天界面和离线缓存用）                                                   |
| `GET data-export/archive?exportId=…` | 下载已做好的导出包（只读；导出包只能由已过面容的 `data.export.start` 产生）          |
| `GET files/content/{fileId}`      | 下载主人自己的文件内容（只读，只认路径里的文件编号，不接受查询参数）                   |
| `POST threads`                            | 新建一个对话；请求里带一个请求编号，同一个编号重发不会建出第二个。只有一个主对话以后 App 不调它（ADR 0285 决定第 1 条） |
| `GET threads/{id}/execution-stream`       | 一个对话正在跑的那一轮的过程事件（过程行用）                                                 |
| `GET threads/{id}/runs/{runId}/execution` | 读一次运行的每一步（“它做了什么”面板用）                                                     |
| `POST payloads/text`                      | 按引用批量读文字：一次最多 100 个，响应最多 4 MiB，放不下的在 `deferred` 里返回，下次再取    |
| `POST gateway`                            | 原生页面的查询和命令，按客户端能力表分“读”“日常”“收紧”“改”四档放行，交给和网页同一个处理程序 |
| `POST payloads/text/new`                  | 原生页面上传一段文字换一个引用（改名等命令的正文要用），上限和网页一样                       |
| `POST attachments`                        | 聊天输入条的附件：一张图片（`data:` 网址）或一段抽出的文字换一个引用，和网页附件存成同一种格式；只在 `GET config` 返回 `attachments` 时有。`attachments` 里的上限按服务器配置的请求体上限算，主对话用的模型不能读图（以 Magpie 报的能力为准）时 `imageCharacters` 为 0，这时不收图片 |

设备能做的就是这张表加上 `POST gateway` 里能力表放行的那些。改规则、删记忆、导出数据这类属于“改”这一档，每次要确认密钥签名（见[设备身份和配对](#identity)里“原生页面怎样拿数据、改数据”）。

系统代传（App 被挂起后由苹果系统继续上传）只支持“从文件上传”，所以 `perception`、`perception/media`、`track` 都接受“一个文件装一批”的形式，用上传凭据而不是请求签名（见上节）。

每个接口都有服务器端的硬上限，超过就拒绝，不依赖设备自觉：单个请求的正文大小、单个文件大小和解压后的大小、一批里的记录条数。`device_action` 和各接口的参数按固定结构校验，多出来的字段一律拒绝。具体数字见[上限和用量](#limits)。

## 4. 连接和传输

数据按“有没有人在等”分三种：

| 数据                       | 谁在等                   | 走哪条路                                                                                    |
| -------------------------- | ------------------------ | ------------------------------------------------------------------------------------------- |
| 对话：主人的话、回答、审批 | 主人在等                 | 一直开着的连接：下行是 `GET stream`，上行每条消息一个请求，同一条 HTTP/3 连接里各走各的通道 |
| 感知记录                   | 没人在等，但越早到越有用 | 连接开着时立刻发；不在时攒成文件交给系统代传；设备上的待传队列有上限                        |
| 服务器找设备               | 看紧急程度               | 连接开着走连接；不在时，看得见的通知走苹果推送优先级 10；小组件和实时活动走各自的推送类型   |

连接什么时候开着：App 在前台时；以及只要在听，App 在后台也是醒着的（ADR 0229 前提 12）。Mac 上常开。

要点：

- **复用现有事件流。** 设备和网页收到的是同一串事件的子集，所以手机上说一句，电脑网页上同时出现。设备只订阅和它有关的事件类型。
- **不丢、不重。** 下行靠事件编号续传；上行靠消息的唯一编号去重。事件编号是全体事件的统一序号，不是每台设备各一套：服务器从设备报的那个位置往后扫，只把和这台设备有关的发给它，同时把“已经扫到第几号”随心跳告诉设备，所以设备记的位置可以指向一个没发给它的事件，续传不会漏也不会重。服务器只保留一段时间的事件，设备报的编号太旧时，返回“请整份重新取”，设备重新取对话列表后接着收。
- **心跳。** 间隔由服务器在配置里下发。判断连接死没死，看有没有任何有效数据进来，不只看心跳回应。
- **网络切换。** 设备监听系统的网络变化，立刻在新网络上重连并续传，不等超时。
- **身份。** 建立连接时验一次签名；之后每发一个事件前核对设备是否仍有效（沿用现有事件流的做法）；连接有最长寿命（配置，默认 1 小时），到了由设备无缝重连。
- **优先级。** 回答的文字、审批用高优先级；照片、音频、屏幕用低优先级。
- **界面先动。** 主人发出的话立刻显示并存进设备本地，后台再发；失败在原处标出并自动重发。打开 App 先显示本地缓存，再补最新的。
- **传输层可换。** 客户端里“怎样连”和“连上以后干什么”分开：业务只面对“发一条消息”“收一串事件”“传一个文件”三个动作。换成 WebSocket 或直连 QUIC 时业务代码不动。

<a id="transport-metrics"></a>

**计时**。每一段都计时，数字有定义，在用量页能看到：

| 数字           | 定义                                           |
| -------------- | ---------------------------------------------- |
| 说完到有动静   | 主人说完最后一个字，到设备发出提示音或震动     |
| 说完到第一个字 | 主人说完最后一个字，到回答的第一个字显示或读出 |
| 传输占用       | 上一项减去服务器内部耗时                       |
| 感知到达       | 一条感知记录从设备产生到服务器入库             |
| 提醒到达       | 服务器决定提醒，到设备显示                     |
| 重连补齐       | 网络恢复，到缺的事件全部补上                   |

目标值不在这里写。动工第一步先测基线（现有网页、HTTP/3、WebSocket、直连 QUIC 四种，在 Andy 的手机上，Wi-Fi 和蜂窝各一轮；同时测出生产机离日本一个来回多少毫秒），再定每项的目标并写进上线走查的门槛。

## 5. 抢跑：主人还没说完就开始准备

传输层省的是百毫秒，抢跑省的是秒。

- 设备转文字时，把还没说完的半句话持续发到 `utterances/partial`，带同一个“这句话的编号”。
- 服务器拿半句话先做准备：找相关记忆、备好这轮要用的资料。结果放在内存里的临时缓存，按这句话的编号存，60 秒不用就丢（时间是配置）；缓存的条数和总大小有上限，每台设备同时只保留最近几句，满了丢最旧的。
- 主人说完，最终的话经 `messages` 发来，带同一个编号。服务器比较最终的话和准备时用的半句话：差别小就直接用准备好的结果，差别大就重做。“差别小”的门槛登记在门槛表里（前提 S4），用评测定。
- **不提前调用对话模型。** 提前调要花钱，主人改口就白花。找记忆时如果要算问题的向量（一种很便宜的模型调用），走现有的向量出口，计入[上限和用量](#limits)里的一项，到上限就不再抢跑。这一点比方案第 3 版写得更准确：方案里写的是“不产生任何模型请求”，实际是“不产生任何对话模型请求”。
- 半句话从不存进对话历史，也不存成感知记录。
- **先给个动静。** 设备认出主人在叫它后，100 毫秒内在本地响一声或震一下，不等服务器。
- **边生成边读。** 回答一句一句到，到一句读一句。在设备上读还是服务器合成，按实测音质和速度定。

## 6. 感知记录的数据模型

三类数据，三种存法：

**事件类：感知记录**（“发生了一件事”）。表 `perception_records`：

| 字段               | 含义                                                                                                                     |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| 编号               | `perception:` 开头，由设备生成：一般是时间加随机数；来源自带稳定编号的（例如 Mac 短信的 guid）用它的哈希，重复上传按它去重 |
| 类型               | 见下面的类型表                                                                                                           |
| 标记               | `owner_spoken`（主人本人说的）或 `other`，见[指令和数据的界线](#instruction-vs-data)                                     |
| 设备、采集来源     | 哪台设备；来源是设备自带麦克风、AirPods、随身麦克风等                                                                    |
| 发生时间、到达时间 | 设备时间和服务器时间。入库时都换算成统一的毫秒整数（世界协调时间），设备原样报的时间字符串另存，只用于显示。排序只用整数 |
| 把握               | 0 到 1000                                                                                                                |
| 说话人             | 只对听到的话：主人、某位已认出的联系人、不认识                                                                           |
| 所属的一段经历     | 见下                                                                                                                     |
| 内容               | 文字放在现有的内容存储里，这里存引用；带数据分级                                                                         |
| 依据               | 类型自己的结构化字段（地点坐标、健康数值、网址、App 名等），键的顺序固定                                                 |
| 状态               | `active`、`deleted`                                                                                                      |

类型（每个都是固定的字符串，登记在一处）：

| 感官 | 类型                                                                                                                         |
| ---- | ---------------------------------------------------------------------------------------------------------------------------- |
| 听   | `speech.utterance`（一句话的转写）                                                                                           |
| 位置 | `location.visit`（到访）、`location.region`（进出登记地点）                                                                  |
| 身体 | `health.sample`（睡眠、心率、锻炼、步数，子类型在依据里）、`motion.activity`（步行、跑步、骑车、开车）                       |
| 眼   | `photo.asset`、`photo.screenshot`、`camera.capture`、`share.item`、`screen.text`（手机或 Mac 屏幕认出的字）                  |
| 读   | `web.page`、`message.text`（短信和 iMessage）、`clipboard.item`                                                              |
| 周围 | `context.now_playing`、`context.connectivity`、`context.power`、`context.focus`、`context.app`（Mac 前台 App）、`home.state` |
| 在场 | `presence.app`（主人正在看哪台设备上的 Himawari）                                                                            |

类型表列的是数据的种类，不代表每种设备都采得到：`message.text` 目前只确认 Mac 能读，iPhone 上能不能拿到在[还没核实的事](#unverified)里；采不到的设备就不产生这种记录。

**一段经历**。表 `perception_episodes`：连续的一段听到的话加上同一时间的地点和情境。一段在这些时候结束：安静超过一定时间、换了地点、达到最长时长（都是配置）。抽取以一段为单位。

**镜像类**（“设备上某样东西现在是什么样”）。表 `device_mirror_items`：日历事件、提醒事项、联系人、家居配件。按“种类加设备上的编号”更新，不是每次变化加一行。带版本号和删除标记。

**轨迹点**。表 `location_track_points`：全天轨迹量大、结构简单，单独一张紧凑的表（时间、经纬度、精度、速度）。到访和进出事件仍是感知记录。每天的点数有上限。

**不另建“建议”表。** 原先这里有一张 `perception_suggestions`，只会提两种事（建提醒、建日程）。现在感知和别的来源一样写进收件箱（前提 S9，ADR 0285 决定第 3 条），值不值得说、要不要给下一步，由主对话里的她判断。这张表和它的两个接口不做。

**主人此刻的状态**不是一张表，是从最近的感知记录和镜像算出来的一份快照，见[送达时机](#timing)。

## 7. 指令和数据的界线

**标记怎样定**。入库时由服务器定，不由模型定：

- `owner_spoken`：类型是 `speech.utterance`，认人结果是主人，并且认人的分数过门槛。门槛登记在门槛表里；认人的错认率在评测里达标之前，这个门槛设成“永远不过”，所有听到的话都是 `other`。设备自己报的标记不被采信。
- `other`：其余全部。

**`other` 在代码层不能做什么**。下面每一条都是程序里的判断，不是提示词：

| 想产生的东西       | 依据全是 `other` 时                                  |
| ------------------ | ---------------------------------------------------- |
| 正式记忆           | 拒绝，改存待确认记忆                                 |
| 带提醒或人物的记忆 | 拒绝（待确认记忆本来就不带，ADR 0179 第 1 条③）      |
| 提醒、日历事件     | 不直接建；作为“新知道的事”写进收件箱，她在主对话里说，主人点了选项才建 |
| 设备动作           | 拒绝                                                 |
| 审批结果           | 拒绝；审批只认主人在设备上点的、或主人口头指令里说的 |

**对话里看到外来内容之后**。上面那张表管的是后台抽取。对话里还有一条路：模型读到网页、短信、屏幕上的字、邮件正文，这些字里可能夹着指令，模型接着就可能去调别的工具。这件事怎样管，由“有后果的工具调用走同一个授权出口”那份方案定（前提 S10），不在这里另写一套。和这份设计有关的口径：

- 记的是一条事实：“模型现在还看得到的上下文里有没有外来内容”。原先这里写的是“这一轮读过”，那份方案收紧成按上下文记：上一轮读进来、这一轮还留在历史里的网页，照样能带偏模型。算外来内容的不只 `perception_read` 读到的 `other` 记录，还有联网搜索和抓到的网页、读文件和命令的输出、邮件正文、MCP 送来的内容、外部事件的正文、主人消息里的附件。
- 在有外来内容的上下文里写下的提醒、记忆、规则，记录上带一个来源标记，以后被读出来时仍算外来内容，免得网页里的字先变成提醒、再变成“主人自己的数据”。
- 所有有后果的工具调用（`device_action` 里除读取以外的动作、建提醒、改规则、记忆转正等）执行前走同一个出口，按下表办：

| 这一轮是谁发起的                                   | 上下文里有外来内容时想做有后果的事                                                                                                                              |
| -------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 主人的消息（打字或口头指令）                       | 读取照做；中风险的出一张卡片等主人点一下（那份方案的第 3 步评测通过后，主人明说过要做的可以直接做并在回执里写明内容取自哪里）；高风险的、改规则的一律等主人点头 |
| 后台（定时、系统主动提醒的检查、对话外的“想一想”） | 按 ADR 0285 决定第 7 条（它修改了 ADR 0257 决定第 3 条里“后台发起的一轮读过外来内容后不做”那一行，ADR 0257 的 `amended_by` 已写明）：只在 Himawari 自己这边、能撤回的（记住、定提醒和跟进）直接做并记下出处；改主人外面的账号和设备、改规则、发出去、删东西，在主对话里出一张同意卡片等主人点头。例外：从感知来的提醒和日历事件按 ADR 0258 决定第 4 条，她在主对话里给选项、主人点了才建（见上面后台抽取那张表），不因为这一行而直接建                                                                                    |

- [设备动作登记](#actions)里写了“要主人本人在场”的，不管算哪一档，都要近期身份验证。

这样网页里一句“把明天的会删掉”最多变成一件等主人点头的事，不会自己发生。那份方案的前两步进 main 之前，设备动作的端口只放行读取类动作。

**口头指令**。两种触发方式，条件不同：

- **戴着 AirPods 叫名字**（不用动手，说“嘿 Himawari，帮我……”）：从第一天就能用。耳机戴在主人耳朵里，麦克风就在主人嘴边，这和“设备在主人手里”是一回事。程序核对三样：声音是从 AirPods 的麦克风进来的；耳机此刻戴在耳朵里；这句话是近处的大声音（旁边的人说话传进耳机麦克风会小得多，音量门槛登记在门槛表里，用评测定）。三样都满足就当指令。声纹注册好以后再多核对一样，但不等它。
- **动了手的**：按按钮、抬腕、用 Siri、捏耳机之后说的话。不需要认人，从第一天就能用。
- **没戴耳机、对着放在一旁的手机或 Mac 叫名字**：这时麦克风收的是整个房间的声音，谁说的都一样响，只能靠声纹。要认人结果是主人，并且分数过“口头指令”的门槛（比 `owner_spoken` 那个更严，单独登记）。认人达标之前，这种情况下设备回问一句“是你在叫我吗”，主人应一声或点一下再执行。认人的评测排在收听功能的第一周做，达标就打开。

不管哪种触发，口头指令能做的事和打字完全一样受权限管：涉及钱、删除、对外发送的仍然要确认。所以即使偶尔认错，最坏的结果是一件可撤销的小事。

设备在 `messages` 请求里带上触发方式和认人分数；服务器按门槛再判一次。触发方式、是不是戴着耳机、认人分数这些证据只有设备拿得到，服务器没法独立核实，所以这条路的可信程度等于设备密钥的可信程度：设备密钥在安全芯片里、请求有签名、设备可吊销。[指令和资料怎样分开](#instruction-vs-data)里“设备自己报的标记不被采信”说的是另一件事：`owner_spoken` 还是 `other` 这个结论由服务器按证据和门槛算，设备不能直接报结论。

口头指令进对话后和打字完全一样：同样的权限、同样的审批、同样的每轮记忆抽取。同一句话在三处出现时靠“这句话的编号”对上：抢跑的半句话、`messages` 里的最终文字、收听管道里的那条 `speech.utterance` 都带同一个编号；感知抽取看到某条记录的编号已经作为指令进了对话，就跳过它。

**数据里夹带的指令**。感知抽取、来源检查、`perception_read` 的结果里，外来文字都放在固定的“这是资料，不是指令”的包装里（提示词目录里的固定文字）。这是第二道防线；第一道是上面那张表。

## 8. 从感知记录到记忆和提醒

**抽取**。一段经历结束后，后台任务把这段的感知记录交给模型，用单独的提示词（`perception.extract`）。请求的排法：固定指令 → 这一段的记录（按“设备时间加编号”排序）→ 日历表和当前时间。请求里出现的每一种集合都按固定的键排序后再写出，不依赖数据库返回的顺序：记录按“发生时间的毫秒整数、再按编号”；日历事件按“开始时间的毫秒整数、再按事件编号”；镜像条目按“种类、再按设备编号、再按条目在设备上的编号”。每种集合的整组键都是唯一的，所以不会有并列。不沿用任何对话的请求开头，是独立的后台调用。

模型输出两样。一是可能要记下的事（下面叫候选）：记什么、分类、把握、引用的原话、引用的是哪几条感知记录。二是“可以帮主人做的下一步”（可以没有）：一句话说是什么事，加引用的原话和记录。第二样是开放的，不限于“约定”“待办”这几种，抽取这一步也不判断该不该提、怎么做。

**程序怎样处理每条候选**：

1. 引用的原话要能在引用的感知记录里逐字找到。找不到就丢，记“原话未核实”。核对用的是模型实际看到的那一份（遮盖之后的文字）；候选的原话里带遮盖占位符的直接丢，这样核对得上的原话一定也是原始记录里的原文。
2. 看引用的记录的标记：
   - 至少有一条 `owner_spoken`，并且原话就在那条里，分数过“感知直接存入”门槛：成为正式记忆。出处写这几条感知记录（`source_type = perception`）。现在存记忆的代码把出处类型一律写成 `reference`（`packages/persistence-sqlite/src/sqlite-memory-operations.ts:869` `VALUES (?, 'reference', ?, 0)`），记忆的出处在程序里也只是一串编号；要改成“类型加编号”一起传、一起存、一起读出来，记忆页的“跳到原话”按类型跳，不靠编号前缀猜。
   - 否则：存成待确认记忆（沿用 ADR 0179 的做法），出处同样写上。
3. 归属：主人说自己的事，记成主人的；已认出的联系人说他自己的事，记到这个人名下（联系人来自通讯录镜像）；不认识的人说的，只当线索，不建人物档案。
4. “可以帮主人做的下一步”：原话核对过的，连同程序填的结构化来源信息（种类、来历、采集方式、时间、说话人）一起作为“新知道的事”写进收件箱（前提 S9）。抽取这一侧不写“听到约定就建提醒、听到日程就建日历”这样的分支：值不值得说、给不给可点的下一步，由主对话里的她在全部工具的范围里判断，有后果的照 ADR 0285 决定第 7 条问主人。可信标记看这一次发给模型的全部记录：只要有一条不是主人自己的（别人说的话、屏幕上的字、网页），这一次交出去的全标成外部内容，不按“被引用的是哪一条”算（依据：边界与可逆性排在主动性之前）。
5. 每条候选的结果都写决策记录，类别沿用 `memory_candidate`，原因码加前缀 `perception_`。

**转正**。待确认记忆在这些时候转正：主人在记忆页点确认；主人之后亲口（`owner_spoken`）或打字说了对得上的原话（沿用 ADR 0179 第 6 条的两关和“待确认记忆转正”门槛）。多条 `other` 互相印证只提高分数，不转正。

**从 TaoSheng 学来的做法**：给模型一张日历表查日期，不让它自己算；宁缺毋滥；主人忽略过的建议按类别统计后回传给模型（放在请求最后的“这次的资料”里）；后来听到主人说事情办完了，就给对应的事挂“可能做完了”（是不是这个意思由模型判断，不用关键词去匹配）；判断为外放的视频音乐不提取；每条记忆和提醒都能点回原话。

**每周体检**里多一段：这一周由感知新增的正式记忆，每条带“撤销”。

## 9. 系统主动提醒的来源登记

现在 Gmail 写死在很多处（ADR 0230 前提 8），比那里列的还多：

- 表约束：`CHECK (source IN ('gmail'))` 和 `scenario IN ('gmail')` 出现在五份迁移里（`0062`、`0069`、`0087`、`0088`、`0089`，后两份是最近重建的版本），涉及来源连接、已处理条目、提醒条目、决策记录四张表。
- 导出导入校验：`packages/persistence-sqlite/src/data-export/schemas.ts:199`、`:253` 等处只认 `gmail`。
- 运行的那段程序本身是按 Gmail 写的：`apps/agent-service/src/production-proactive.ts` 里多处直接写 `source: "gmail"`，条目的字段也是邮件的样子（发件人、标题、邮件线程）。
- 设置里只有一个总开关（`proactive_settings.enabled`），没有每个来源的开关和预算。

改成一张登记表（代码里的常量，不是数据库表）。登记表只管“管道”上的事，每个来源登记：名字、读取器（怎样取到新内容、怎样变成给模型看的条目）、去重键怎样算、用哪项预算、最晚送达时间、评测集在哪、可信标记（这个来源的内容是主人自己的还是外部内容）、程序填的结构化来源信息。不登记“场景名”，也不是每个来源配一条只找某几样东西的判断提示词：值不值得告诉主人、提什么下一步，由模型在它全部工具的范围里判断（Andy 2026-11-12：“我其实想做的是一个能帮我处理所有事情、既主动又聪明的 AI agent，而不是一套固定死的工作流”）。条目的结构改成通用的（编号、时间、标题、摘要、来源自己的附加字段），Gmail 的邮件字段放进附加字段。运行的程序按登记表一个个来源跑，不再是 Gmail 一条线。

每个来源的开关和预算存在新表 `proactive_source_settings`（来源、是否开、每天预算、每次最多几条）。

第一批只登记 `gmail`（原样迁过来）。原先打算同时登记的 `speech`、`calendar`、`location`、`message`、`screen`（每个来源找固定的几样：听到的约定、日程冲突、取件码、屏幕上的待办）不做：感知到的东西由[感知抽取](#to-memory)写进收件箱，不再每个来源各有一条读取和判断的线。以后接别的服务（例如日历的变化）时，照这张登记表加一行。

给 iPhone 用的三个操作（第 7 批，PR 455，写这份文档时没有进 main，字段以合并时的代码为准）：

| 操作                            | 做什么                                                                                                                                     | 能力表里的档 |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------ |
| `proactive.sources.read`        | 列出每个来源：开没开；每天上限和每次检查上限各自的现在值、默认值、可改的范围；今天已用多少、什么时候清零、到了会怎样；今天是不是已经到上限 | 读           |
| `proactive.source.switch_off`   | 关掉一个来源。正文恰好只有来源名，多带任何字段都被拒；上限不动                                                                             | 收紧         |
| `proactive.source.settings.set` | 打开一个来源，或改它的两个上限。改上限写一条决策记录，带改前改后的值                                                                       | 改           |

“清除记录”和“断开”都只管正文里点名的那一个来源：清除记录只清这个来源的已处理条目和提醒条目，断开只清这个来源的连接和降频状态，别的来源不受影响。所以降频表也要有来源一列（第 7 批重建表时一起加）。不设“全部来源一起清”的按钮：主人在哪个来源的页面上点，就只动哪个来源（依据用户主权：他没点名的东西不替他删）。

这三个操作不带邮件专有的字段名（`messageId`、`threadId`）；现有给网页提醒页用的 `proactive.overview.snapshot` 里还有 `messageId`，iPhone 提醒页定合约时换成中性的名字。现有的降频列表（`proactive.overview.read` 里按类别列）和 `proactive.backoff.restore`（按类别名恢复）还不带来源，两个来源有同名类别时会一起恢复；iPhone 提醒页定合约时这两处也加上来源字段。碰到上限时，超出的条目留到下一次，不发通知，用量页照 [ADR 0230](../../adr/0230-perception-records-and-memories-inferred-from-perception.md) 决定第 9 条显示四样。

要改的地方：

- 类型 `ProactiveSource` 从登记表生成。
- 四张表的约束去掉：SQLite 改不了约束，要重建表搬数据，以最新的表结构（`0089` 之后）为准。这一步排进改表队列。约束去掉后，合法值由写入处按登记表校验。
- 导出导入校验、查询里写死的 `'gmail'` 改成从登记表生成。
- 网页现有的提醒来源开关改成按登记表读名字（现有页面，不新增）；每个来源的开关和预算在 iPhone 的设置里也能改。
- 新检查 `npm run check:proactive-sources`：每个登记的来源都有读取器、评测集、预算项；每个来源都能写进这四张表、能导出再导入；登记表里没有的名字写不进库。

## 10. 送达时机

**主人此刻的状态**。一份快照，每一项是三态加新鲜度：

| 状态            | 从哪来                                                    | 多久算过期                 |
| --------------- | --------------------------------------------------------- | -------------------------- |
| 在日程中        | 日历镜像                                                  | 跟随日程本身               |
| 在和人说话      | 最近的 `speech.utterance` 里有主人和别人                  | 2 分钟                     |
| 在睡觉          | 健康数据的睡眠、设备长时间静止、夜间                      | 30 分钟                    |
| 在开车或运动    | `motion.activity`、`context.connectivity`（连着车载蓝牙） | 5 分钟                     |
| 正在看 Himawari | `presence.app` 和现有的网页心跳                           | 45 秒（同现有规则）        |
| 专注模式        | `context.focus`                                           | 10 分钟                    |

过期的一律算“不知道”。专注模式读到的值有盲区（Himawari 在允许名单里时看上去是没开），所以它只是信号之一，不单独决定。

**判断**（ADR 0285 决定第 4、6 条）：

1. 她主动说的话推不推由她定；回主人的话一律推。上面这份状态是她判断时看得到的上下文，程序不按状态自动延后。
2. 程序只按主人定的安静时段延后（ADR 0244，加管“她的话”）；同意卡片在安静时段照样推。
3. 正在看 Himawari 的主对话：不弹推送，在 App 或网页里显示。

按安静时段延后、到点送达各写一条决策记录。原先的“不紧急的在忙时延后”（ADR 0273）已被 ADR 0285 取代，不做。

## 11. 推送和通知按钮

**通道**。现有的投递记录只认 `web_push`（前提 S2），迁移成能记两条通道：

| 表                         | 变化                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------ |
| `apns_registrations`（新） | 设备、推送类型（`alert`、`widgets`、`liveactivity`）、实时活动编号（只有某一次实时活动的更新令牌才填，填的是那次运行的编号）、令牌、环境（开发或正式）、App 标识、语言、状态 |
| 现有投递记录表             | 通道多一个 `apns`；多一列推送类型。重建表搬数据                                      |
| 现有待发通知表             | 多一列“这条走哪条通道”，没定之前是空                                                 |
| 现有网页推送订阅表         | 不变                                                                                 |
| 现有设备表                 | 多一列“这块手表是哪台 iPhone 的配对手表”，由 iPhone 经 `POST companions` 报告         |

**去重**。提醒类通知在两条通道间共用现有的来源键：同一件事只送到一处。先后顺序：正在看的地方不推 → 有可用的 iPhone 推送令牌就走苹果推送 → 否则走网页推送。“可用”指设备没被移除、令牌没被苹果报失效；手表不单独收提醒（iPhone 的通知由系统转到手表上）。苹果报令牌失效时停用那个令牌，同一条通知改走网页推送。反过来不改：一条通知已经走过网页推送之后才登记的 iPhone，不会再收到这一条。同一条审批通知重发时，上一次发出去还没用过的按钮凭据作废，只留最新的一对。“正在看”对手机来说是设备事件流连着（同一台设备有几条时，最后一条断开才算不在看）。小组件刷新和实时活动不参与这个去重，也不写进提醒的投递记录。

**能发到哪些 App**。服务器配置 `runPolicy.applePush` 里列出允许的 App 标识（bundle ID，苹果给每个 App 的唯一名字）和环境，登记令牌时不在名单里的被拒。同一处还配：小组件两次刷新的最短间隔、实时活动两次更新的最短间隔、运行持续多久才开实时活动、按钮凭据的有效期、请求超时、每台设备最多保留几条按运行的实时活动登记，都有默认值和上下限。配了 `applePush` 就必须也配 `webPush`，因为两条通道发的是同一批待发通知。

**她的话**：推送正文是她写的那句原话（ADR 0285 决定第 6 条），全文显示，不遮盖；同一条话用来源编号当推送表主键，不会推两次。原先的“提议通知”（“有一条建议等你看”）不做：提议变成了她那条话下面的选项。

**小组件刷新**在这几种时候发：等主人同意的件数或内容变了、定时里最近的一条变了、设备新登记了小组件令牌。按设备合并，间隔不到最短间隔的攒到下一次。

**实时活动**只用于长任务的进度：一次运行持续超过配置的时间、主人又没在看，才发“开始”；阶段变了才发“更新”（有最短间隔）；运行结束发一次“结束”并删掉那次的更新令牌。每台设备按运行的登记超过配置的条数时，删掉最久没更新的（用来收“开始”的那一条不算在内）。“开始”“更新”“结束”遇到苹果的临时错误或限流时都按 1 分钟、5 分钟、15 分钟的间隔再试，之后不再试（“更新”放弃的是那一个阶段，阶段再变时照常发）。苹果推送这一侧出错不影响同一轮的网页推送。

**锁屏内容**：她的话全文显示，不遮盖，不再有“敏感或受限的只显示一句提示”（Andy 2026-11-24 定，前提 S13：ADR 0286 决定第 4 条“锁屏推送显示全文”）。ADR 0229 决定第 9 条和后果里从 ADR 0089 第 5 条沿用的两句（“敏感或受限的只显示一句提示”“正文不放进推送”）因此不再适用，这一修改记在 ADR 0258 决定第 8 条。同意卡片的推送正文是程序写的真实动作和明细，带“不要”“同意”两个按钮。保险箱的批准推送是例外：正文只写“Himawari 请你批准一次使用”，不写是哪一项、不带按钮，点开批准页才显示项的名字和网站（前提 S14，见[主对话和她的页面](#main-chat)里的保险箱一段）。

**按钮和凭据**。每个带按钮的通知，服务器为每个按钮生成一个凭据。表 `notification_action_tokens`：凭据的哈希、动作（现在只有 `approve`、`deny`；动作名由代码校验，不写死在表的约束里，以后有别的动作时不用改表）、是否要主人本人在场、绑定的审批编号和它当时的版本与内容指纹（前提 S3）、绑定的设备、过期时间、使用时间。通知里每个按钮带：动作名、按钮文字、文字来源（`catalog` 通用文字或 `model` 模型写的；普通审批的“同意”按钮用模型写的文字，读不到或不合格时退回通用文字，其余按钮都是通用文字）、肯定还是否定、要不要本人在场、凭据。

- 设备点按钮时把凭据发回 `approvals/respond`，请求照常要设备签名。
- 服务器核对：凭据存在、没过期、没用过、是发给这台设备的、审批的版本和内容指纹没变。任何一项不对都拒绝，并让设备显示“这条已经失效，请打开 App 看最新的”。“核对没用过”和“记成已用”是一条数据库语句里完成的，两次同时点只有一次成功。
- 通知上不放“有用 / 打扰”按钮，也不放“看内容”按钮；“有用 / 打扰”只在 App 里评。替主人做完的事的通知没有按钮。
- 要主人本人在场的审批，肯定按钮的文字固定是“看内容再定”，点了进 App 看内容；没有确认密钥签名时服务器回 403，凭据不作废，带上签名再发同一个凭据才生效。否定按钮不需要确认密钥。
- 通知被转到手表上显示时，按钮由谁处理（手表自己签名，还是交回 iPhone）没核实，列在[还没核实的事](#unverified)里。在核实之前，凭据同时认这台 iPhone 和与它配对的那块手表。
- “稍后”不发任何请求，只收起通知。
- `feedback` 收的是“点开了”“划掉了”，按通知的标签记到现有的通知反馈上，和网页推送是同一份记录。
- 设备被移除时，它的推送令牌停用、按钮凭据删除；移除成功之后服务器给它发一条“清掉本地数据”的后台推送，移除请求被拒时不发。

**要主人本人在场的审批**。现有审批在两种情况下要求近期身份验证：风险是最高一档（`CRITICAL`），或者工具动作登记表里这个动作那一行写了要主人本人在场（`packages/application/src/services/action-policy-service.ts:513-517` 的 `recentAuthenticationRequired`，条件是 `intent.finalRisk === "CRITICAL"` 或带 `POLICY_FACT_CODES.ownerPresenceRequired` 事实；那一列是 `packages/application/src/services/tool-action-registry.ts:47` 的 `ownerPresenceRequired`）。所以“删除”“执行代码”这类虽然在现有基线里是 `HIGH`，只要[动作登记表](#actions)那一行写了“要”，审批一律要求近期身份验证，这一部分已经在 main 上，不用再做。这份设计要加的是近期身份验证的一种新来源：确认密钥的签名。

做法：通知按钮设成“必须解锁才能点”；App 先从 `approvals/challenge` 取一个一次性挑战值，用**确认密钥**（每次使用都要面容或解锁的那把）签“审批编号加版本加挑战值”；服务器验过签名，才生成近期身份验证的凭据交给现有的审批服务。解锁后 App 先显示审批的具体内容，主人看到了再确认，不在锁屏上盲点。口头“同意”不能用于这类审批。

**送达的轻重和按钮都由条目自己带**，推送这一层不按种类分支（2026-11-12 定，和“界面不认种类”是同一条原则）。现在响不响是按种类定的（审批用时效性通知，其余普通，声音固定），按钮只在审批上生成、固定一对。改成：

- 每条待发通知自己带“送达轻重”：要主人马上知道的（时效性）、普通（会响会震）、安静（不响不震、不算进角标）。她的话是普通的，和提醒一样守安静时段；同意卡片在安静时段也推。
- 按钮按条目给的动作列表生成，一个或两个，文字用条目给的。卡片、通知、手表只显示前两个，其余的在点开以后；样式跟角色走（肯定是实心主按钮，否定和中性是普通按钮）。只是“打开 App”的按钮不给，点通知本身就是打开。
- 角标的数字等于主对话里还没回答的同意卡片数，没有就不显示。
- 待发通知和投递记录的种类现在只收 `reminder`、`approval`、`run`，加“她的话”要一份改表迁移，随收件箱第 1 步做（ADR 0285 决定第 6 条），不在第 4 批的 PR 里。
- “主人在电脑前就送 Mac、不送手机”属于[送达时机](#timing)，和接力规则一起做（见[每一端做什么](#device-roles)）。

要主人本人在场的审批，锁屏上的肯定按钮固定写“看内容再定”并带面容图标。审批的肯定按钮文字可以由写那句话的同一次模型调用给（上限中文 6 个字、日文 8 个字、英文 16 个字符；超了、空、和否定同字就用“同意”）；推送不等它，送达后不改字。

**长任务的进度**用锁屏实时活动显示，由 `liveactivity` 推送类型刷新。小组件在这几种时候刷新：等主人同意的件数变了、定时里最近的一条变了、感知状态变了；同一台设备合并发送，最短间隔是配置项。

## 12. 设备工具和动作

**模型看到的工具**只有两个，定义的字节永远不变：

| 工具              | 参数                                                                                        | 说明                                                                                    |
| ----------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `device_action`   | `action`（字符串）、`device`（可选）、`arguments`（对象）                                   | `action` 是 `describe` 时返回现在有哪些设备、每台支持哪些动作和参数；其余值是要做的动作 |
| `perception_read` | `kinds`（可选，字符串数组）、`from`、`to`、`query`（可选）、`detail`（`summary` 或 `full`） | 读某段时间感知到的东西，默认返回摘要和出处编号                                          |

工具定义里不列具体动作、不列设备，`kinds` 也不列可选的类型（是自由的字符串，由执行端按清单校验，写错了在结果里告诉模型有哪些可用）。所以配对、断开、以后加新动作或新的感知类型，都不改工具定义。没有可用设备时，`device_action` 返回“没有可用设备”。

`perception_read` 的结果和别的工具结果一样过统一出口，带着每条记录的数据分级，沿用现有的分级和路由规则（见[发给模型的路径](#egress)），不另设一套。结果有硬上限：一次最多返回的条数和总字数是配置，`full` 也一样；超出的截断，并在结果末尾写明“还有多少条没列出，缩小时间范围再读”。

**动作登记**。设备动作不另建一张登记表，直接登记进“工具动作登记表”（前提 S10 那份方案的第 1 步），全项目只有这一张。每个动作一行：名字、哪些设备种类支持、算哪类动作和风险档位（沿用 `packages/application/src/services/action-policy-service.ts:37-50` 的那张表）、要不要主人本人在场、参数结构、怎样读回核实、做之前要不要先存一份原样、给主人看的那行明细由哪个函数从实际参数生成（三种语言）、能不能由外来内容引出。设备自己报的“我支持哪些动作”只用来过滤，不能往表里加东西。第一批：

| 动作                                                 | 现有类别和档位                                         | 要主人本人在场 | 读回；能不能撤销                                                                  |
| ---------------------------------------------------- | ------------------------------------------------------ | -------------- | --------------------------------------------------------------------------------- |
| `calendar.create`、`calendar.update`                 | 新建或修改，中；带参与者时算对外发送，高               | 带参与者时要   | 读回事件；改之前存原样，可撤销                                                    |
| `calendar.delete`                                    | 删除，高                                               | 要             | 确认不存在；删之前存原样，可恢复                                                  |
| `device_reminder.create`、`device_reminder.complete` | 新建或修改，中                                         | 不要           | 读回；可撤销                                                                      |
| `contact.update`                                     | 新建或修改，中                                         | 不要           | 读回；改之前存原样，可撤销                                                        |
| `alarm.set`                                          | 新建或修改，中                                         | 不要           | 读回；可撤销（用哪个系统接口、能不能读回还没核实，见[还没核实的事](#unverified)） |
| `home.read`                                          | 读取，低                                               | 不要           | 无                                                                                |
| `home.control`                                       | 新建或修改，中；门锁、车库门、安防算人身安全，最高一档 | 门锁这类要     | 读回配件状态                                                                      |

Mac 上的六个动作归第 10 批，登记进同一张表：`mac.files.list`、`mac.files.read`（读取）、`mac.files.apply`（改文件：动手前给主人一张清单，触控 ID 同意）、`mac.files.trash`（移到废纸篓：单独问，不和别的改动并在一次同意里）、`mac.open`（打开文件或网址）、`mac.app`（操作某个 App）。后四个都要主人本人在场。

授权走统一出口：读取直接做；上下文里没有外来内容、中风险、能撤销、只动主人自己数据的，按规则手册的预先授权直接做；高风险和“要主人本人在场”的每次等主人点头；上下文里有外来内容时见[指令和数据的界线](#instruction-vs-data)。“要主人本人在场”的见[推送和通知按钮](#push)。这依赖前提 S10 那份方案：它的前两步进 main 之前，设备动作的端口只放行读取类动作，设备动作对主人还不可用。

Mac 的动作只在 `device_policies` 允许的范围内（见[设备身份和配对](#identity)）：服务器和设备各判一次。路径先解析成真实路径（解开符号链接和 `..`）再和允许的目录比，设备上打开文件后再用打开的那个文件句柄核对一次真实路径，防止检查之后路径被换掉；网址只许 `https` 加主机名单，`file:`、`javascript:` 和自定义协议一律拒绝。

**流程**。表 `device_actions`：编号（服务器生成，也是去重键）、设备、动作、参数的引用、审批编号、过期时间、状态、读回结果的引用、是哪一轮运行里哪次工具调用发起的。

状态：`queued` → `delivered` → `succeeded` / `failed` / `result_unknown` / `expired` / `rejected`。

1. 模型调用 `device_action`。服务器按登记表校验、走权限和审批，写一行 `queued`。
2. 经连接下发给设备；连接不在时发一条苹果推送请主人点开。过期没送到记 `expired`。
3. 设备在本地记下这条动作的每一步（收到、开始做、做完、结果），再执行，再读回，再回报。同一个编号再来一次时，设备不重做，只回报上次的结果。
4. 回报没到（设备说不清做没做）：记 `result_unknown`，不自动重做；下次设备上线时只读回核实。这和现有“结果未知不重放”的做法一致。
5. 模型看到“结果未知”后换个编号再调一次同样的动作，也不能重做：每条动作存一个“这件事的指纹”（动作名加规范化后的参数）；同一个指纹有一条还是“结果未知”时，新的调用不新建动作，只触发读回核实，核实不了就问主人。
6. 设备重装或清过数据后，本地的记录没了：它先向服务器要一遍自己名下还没了结的动作。已经交给过设备、还没回报的，按“结果未知”处理，不执行，只读回核实；还在排队、从没交给过设备的，说不上“做没做”，照常送（过了有效期的照旧作废）。
7. 设备离线时不执行排队的动作里“要主人本人在场”的那些；被吊销后丢掉整个队列。
8. 工具结果里如实写：这是设备一侧的证据，读回到了什么。

## 13. 上限和用量

**上限登记表**（代码里的常量）。每项登记：键、单位、按什么周期清零、默认上限、到了上限会怎样、数字的定义。上限的值存在设置里，主人看得见、能改，到了会写明停了什么。

这些上限是防失控的保险，不是省钱的办法，不参与决定功能怎么做（Andy 2026-11-12：“贵不是问题，我要的是极致的体验”“我没有说在 Himawari 这个应用里面把设上限这个功能去掉。我是说你在设计、思考方案的时候，不要老是想着有一个费用上限，然后就去想一些折中的方案来”）。所以：默认值不按“省多少钱”定，上线后按实测的正常一天用量留足余量来定，正常使用碰不到，碰到了按异常提醒主人；实现里不许自己加为了省钱而降档、延后、少做的逻辑。下表的默认值是动工时的起始值，上线一周后按实测重定：

| 键                                 | 定义                                                                                     | 默认上限                  | 到了会怎样                                                                                                 |
| ---------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `perception.model_cost.daily`      | 当天所有由感知触发的模型调用的费用合计（抽取、看图认字、抢跑的向量），零点按主人时区清零 | 起始值 1 美元，实测后重定 | 当天不再调模型，记录照常入库，并通知主人、写明有几段没处理。没到上限时，一段经历结束后就抽取，不攒到第二天 |

| 现有的 `proactive.dailyCostMicros` | 现有定义                                                                                 | 现值                      | 现有行为                                                                                                   |

第一行的起始值和现有系统主动提醒的每天上限默认值相同（前提 S6）。模型调用仍按“套餐内 token、免费额度、最后才是低价模型”的顺序走，禁用贵模型的规则不变。

收件箱不设条数上限（ADR 0285 决定第 4 条删掉了感知的条数上限，Andy 定的规则是不用数量上限代替判断）；她花的钱受产品的花费上限管，每个子线程另有预算，都在她的页面“用量和上限”里能看能改。

用量页分两组显示：“今天”（零点清零的那些）和“总共”（感知记录的总条数、镜像条数这类不清零的），不混在一起；另有一行“没来得及处理就删掉的 N 段”（超过保留期还没轮到抽取、只留了一行记录的经历段数），点进去是清单。

除了上面这些按天算的，每个接口还有不显示在用量页、只为防失控的硬上限（都是配置键，超过了按表里最后一列处理）。每个键只放一个整数，一个上限有两个数的拆成两个键。默认值如下，实测后再调：

| 键                                | 管什么                                                                                              | 默认值                 | 超过会怎样                                                                                                   |
| --------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| `device.request.body_bytes`       | 上传接口以外，单个请求的正文                                                                        | 1 MB                   | 拒绝                                                                                                         |
| `device.upload.file_bytes`        | 单个上传文件                                                                                        | 200 MB                 | 拒绝                                                                                                         |
| `device.upload.expanded_bytes`    | 压缩文件解开后的大小                                                                                | 500 MB                 | 解到这里就停，整个文件作废（先解到临时位置，作废时整份删掉，不留半个文件；服务启动时清掉上次留下的临时文件） |
| `device.perception.batch_records` | 一批感知记录的条数                                                                                  | 500 条                 | 拒绝整批                                                                                                     |
| `device.mirror.batch_items`       | 镜像同步一次的条数                                                                                  | 1000 条                | 拒绝整批                                                                                                     |
| `device.track.batch_points`       | 一批轨迹点的点数                                                                                    | 2000 点                | 拒绝整批                                                                                                     |
| `device.prefetch.cache.entries`   | 每台设备抢跑缓存的条数                                                                              | 20 条                  | 丢最旧的                                                                                                     |
| `device.prefetch.cache.bytes`     | 每台设备抢跑缓存的总大小                                                                            | 204800 字节（200 KiB） | 丢最旧的，直到放得下                                                                                         |
| `perception.extract.max_chars`    | 一次抽取送给模型的字数                                                                              | 60000 字               | 分成几次抽取                                                                                                 |
| `device.nonce.retained`           | 每台设备保留的防重放随机值（保留两倍容许时间差后删，和[设备身份和配对](#identity)里验签的写法一致） | 10000 个               | 拒绝这台设备的新请求，直到旧的过期；同时记一条告警，“设备”页显示                                             |

**账**。表 `limit_usage`：键、周期开始时间、已用。服务器记的那几项，用“检查并预留”的一条数据库语句累加（加完会超就不加、直接拒绝），几个请求同时来也不会一起越过上限。设备上报的两项只存最新值、只用于显示，服务器放不放行不看它们。数字只有这一份，用量页、小组件、手表都从 `GET usage` 取，不在设备上另算。

**显示**。每项显示四样：上限、已用、何时清零、到了会怎样。到 80%（比例是配置）时提醒一次。到了上限，被停掉的那部分标“今天已停”。没有用量时显示 0，不显示估计值。

**改上限**在用量页直接改，写一条决策记录（新类别 `limit_change`）。

**如实显示**。“今天实际听了多久”就是 `perception.audio.daily` 的已用值；被系统打断时发通知，不假装在听。

## 14. 删除、保留和导出

**保留期默认值**（每项都能在设置里改）：

| 数据                                         | 默认保留                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------ |
| 原声                                         | 不保留。设备上转的不上传；传到服务器转的，转完即删                                   |
| 图片、屏幕画面                               | 理解完即删，只留认出的文字、描述和设备相册里的编号                                   |
| 转写文字、到访、健康、网页和短信的文字       | 一直保留，直到主人删                                                                 |
| 轨迹点                                       | 90 天，之后只留到访记录                                                              |
| 周围情境（歌、蓝牙、电量、前台 App）         | 30 天                                                                                |
| 声纹                                         | 一直保留，直到主人删；只用于认人；数据分级“受限”，不进数据导出，不发给任何模型服务方 |
| 设备动作记录（让哪台设备做了什么、结果怎样） | 一直保留，直到主人删；删掉引出它的那个对话时一起删；进数据导出                       |
| 设备上的缓存                                 | 跟随服务器：服务器上删了，设备下次同步时删；吊销时清空                               |

**删一段感知记录**（按条、按一段经历、按天、按类型都可以）：

感知记录和一段经历成为现有删除流程认识的两种新对象（现在它只认对话、运行、任务、记忆、内容五种，`packages/persistence-sqlite/src/sqlite-governed-deletion.ts:38`），走同一套“留删除标记、失败重试、删完核实”：

1. 记录状态改 `deleted`。它的内容只在没有别的记录还引用时才从内容存储里删（现有流程本来就拒绝删还被引用的内容）。
2. 找出处里有它的记忆，按 `(source_type = perception, source_id)` 两个字段一起匹配。
3. 只由它产生的记忆：按现有的记忆删除走到底，包括排队把它从检索索引里删掉并核实删干净，不只是打个作废标记。
4. 还有别的出处的记忆：去掉这一条出处，重新过一次门槛；过不了的降为待确认。
5. 由它产生的“建议”删掉；已经建好的提醒和日历事件保留，并在删除确认里列出来让主人决定。
6. 设备上的缓存副本在下次同步时删。

现有删除只按编号匹配（ADR 0230 前提 10），读出处的接口也只返回编号、丢了类型（`packages/persistence-sqlite/src/sqlite-memory-operations.ts` 的 `sources()`）。都改成类型和编号一起，才不会误伤别的来源。只按编号更新 `memory_provenance` 的地方现在有四处，要全部改：`packages/persistence-sqlite/src/sqlite-governed-deletion.ts:943`、`:986`、`:1021` 和 `packages/persistence-sqlite/src/sqlite-durable-operations.ts:3945`。

**删不掉的要说清**（删除确认里写明）：已经被 `perception_read` 读进某个对话的摘要留在那个对话里，要删就删那个对话；已经导出的文件、备份、模型服务方那边的日志收不回。

**导出导入**。新表全部登记进表结构目录（`schema-catalog.ts`）；“库里的表和目录一致”由 `packages/persistence-sqlite/test/migration-engine.contract.test.ts` 守着。数据导出分两类：

- 导出：感知记录的文字和依据、一段经历、镜像、轨迹、建议、设备的名字和种类、设备策略、上限和用量、每个来源的设置。每个来源的设置（开关和两个上限）第 7 批没有做进导出，系统主动提醒原有的总开关和不打扰时段现在也不导出；这三样在第 7 批合并后用一个单独的小任务一起加进导出，导出文件格式只升一次。在那之前，从导出恢复后这些设置回到默认值，主人关掉过的来源要重新关一次；所以这个小任务要在完整版交给 Andy 之前做完。
- 不导出：设备公钥以外的任何凭据类数据，即配对码、防重放随机值、通知按钮凭据、上传凭据、苹果推送令牌；还有声纹和已经删掉的原始材料。导出测试里有反向断言：这几张表的内容不出现在导出文件里。

决策记录的新类别和系统主动提醒的新来源也要能导出再导入：现在导出校验里这两处都是写死的名单（`packages/persistence-sqlite/src/data-export/schemas.ts:190-199`），改成从 `DECISION_KINDS` 和来源登记表生成，并加“每个类别、每个来源都能导出再导入”的测试；从名单里删掉一个，测试必须失败。

## 15. 发给模型的路径

新增的发给模型的调用，全部是后台调用或工具结果，没有一处改动对话已经发出的内容：

| 调用                                    | 排法                                       | 走哪个出口                                    |
| --------------------------------------- | ------------------------------------------ | --------------------------------------------- |
| 感知抽取 `perception.extract`           | 固定指令 → 这一段的记录 → 日历表和当前时间 | 现有统一出口，登记进 `check:egress-redaction` |
| 新来源的检查（`speech`、`calendar` 等） | 固定指令 → 条目 → 当前时间                 | 同上                                          |
| 看图认字、理解照片                      | 固定指令 → 图片                            | 同上；用套餐内或低价的多模态模型              |
| `perception_read` 的结果                | 追加在对话末尾的工具结果                   | 对话自己的出口                                |
| 口头指令                                | 作为最后一条用户消息                       | 对话自己的出口                                |

要守的几条：

- 感知内容在对话里只能以“这一轮末尾追加的工具结果”出现，不出现在系统提示、工具定义，也不插进任何更早的消息里。（工具结果追加之后当然就成了历史的一部分，以后每轮照原样重发，这是正常的只追加。）
- 一批里的记录按“发生时间的毫秒整数加编号”排序；依据里的键顺序固定；登记表（来源、动作、上限、类型）在代码里按固定顺序列出。日历事件、镜像条目、建议各按[感知记录怎样变成记忆](#to-memory)里写的键排序，最后一个键都是唯一的编号。所以同一批记录、同一份日历表和时间，发出去的字节相同；失败重试时日历表和当前时间会变，它们排在最后，前面的部分不变。
- 遮盖：照常遮密码、验证码、卡号、证件号。一次请求里的一批记录是一个遮盖单位：一条记录里点了名的密码，在同批后面的记录里单独出现时也会被遮（为了不漏）。做法和对话请求的出口一样：按排序后的顺序只走一遍，共用一份“已经点名的值”（`redactForEgress` 的 `known`；要像对话出口 `packages/application/src/services/model-egress.ts` 那样同时传按值稳定的 `tag`，不传 `tag` 时点名的值不会被记下）。不用 `maskSensitiveTexts`：它是给 MCP 读取结果用的，先把整批扫一遍再遮，前后都会互相影响（ADR 0219），用在这里会让前面记录的字节随后面的记录变。依赖只有一个方向：按上面的排序，一条记录怎样遮只取决于它自己和排在它前面的记录，不取决于后面的。所以删掉或改动同批里的一条记录，可能改变排在它后面的记录被遮成什么样；这只影响以后新发的后台请求，不影响任何已经发出去的对话。“点名的值”不去查这一段经历以外的感知记录。一段经历太长、按 `perception.extract.max_chars` 分成几次抽取时，按排序后的顺序从头数字数来切，切点只取决于记录本身；前一次请求里点了名的值要带到后一次请求里接着遮（把前面各次的 `known` 当作后一次的起点），否则同一个密码在后一次里单独出现会漏掉；依赖仍然只有“后面的受前面的影响”这一个方向。
- 数据分级：每种类型有默认分级。健康、短信、屏幕文字、剪贴板、位置默认“敏感”；声纹“受限”；其余默认“私密”。沿用现有的分级和路由规则决定能发给哪家服务方。
- 加两个新工具，会让每个老对话重建一次请求开头；新加的固定提示词文字会进“自己写的固定文字”清单，可能让老对话的遮盖结果变一次。要让这件事只发生一次，这套设计用到的全部新提示词文字（抽取、各来源的检查、资料包装、两个工具的说明和结果文字）必须和两个工具在同一个版本里一起上线，哪怕对应的功能还没开。之后分批开功能不再加提示词。Andy 同意的是“一次”，所以这一条是硬要求。

## 18. 主对话和她的页面

这一节定 iPhone 打开后的样子。服务器怎样收件、她什么时候开口、选项和同意卡片的内容怎样生成，由 ADR 0285 和它的设计规格定（前提 S9）；这里写界面要什么、每个词和数字是什么意思。每一屏的样子在界面基线第 4 版（前提 S12），从上到下的顺序就是打开 App 后的顺序。

**整屏只有四样**（Andy 2026-11-24 20:06 JST 原话：“打开就是一个主对话，没有新建线程这个入口，只有一个主对话”）：

1. 顶上正中她的头像，下面一行衬线斜体小字 himawari。头像是深色圆底里的向日葵标志。点头像打开“她的页面”。
2. 头像下面一条“后台在办 · N 件”，只在有子线程在办时出现；N 是还没做完的子线程数。点开见下文。
3. 中间是主对话：Andy 的话靠右灰底，她的话靠左，和他的话一样用系统字。主对话和子线程之间的往来、收件箱事件都不显示（ADR 0285 决定第 5 条）。
4. 底下是输入条：左边“+”（拍照、照片、文件、我现在的位置），中间“打字，或按住说话”，右边麦克风（听写）和声波图标（和她说话）。她在回答时，声波图标换成“停下”。

**输入条的三条路**：

- 按住说话：输入框是空的时候长按，输入条变成深色的实时转写，松手直接发出去；往上滑到“松手取消”就不发，转写是空的也不发。输入框有字时长按交给系统（选字、粘贴）。开始先震再开麦克风（见[触感](#haptics)）。
- 听写：点麦克风，转好的字放进输入框，看一眼、改了再发。输入框有字时，声波换成发送（深色实心圆里的向上箭头），麦克风留着。
- 和她说话：点声波进语音对话。输入条换成左边“静音”、中间声音的起伏和“在听”或“她在说 · 开口就能打断”、右边“结束”。你说的话一边说一边出现，停一下算说完；她一边说，字一边出来，头像同忙时一样生长、发光；你一开口她就停下来听。点“结束”回到输入条，说过的话都是主对话里普通的文字消息。它和“收听”不是一回事：收听是后台感知，在她的页面里开关。

没有底部页签栏、“今天”页、对话列表、“新对话”、搜索问答页，也没有角上的按钮。

**头像的动效**：她在忙（正在回答，或后台有子线程在办）时，标志用 ADR 0291 的生长动效（`SunflowerMark(growing: true)`，种子数按头像大小取，38pt 用 34 颗，长满一盘约 16 秒），头像背后一团暖金色柔光一明一暗，约 2.4 秒一个来回；平时不动、没有光。系统打开“减弱动态效果”时全部静止。

**她每条话下面的选项**（ADR 0285 决定第 5 条）：

1. 每个选项一行一个胶囊，竖着排。只是接着问的选项是白底细边；带具体动作的（例如“回复 田中：周四 15:00 可以”）是浅金底，左边一个发送图标，按钮上的字由服务器按真实收件人和内容生成，客户端不拼。最后一个固定是“不用了”，灰字。
2. 点一个选项，它变成一条 Andy 的话，上面一行小字“选了”；带动作的点一次就执行，算这一次的同意。
3. 有了更新的消息以后，旧消息下带动作的选项变灰、点不动；只是接着问的选项也变灰。

**同意卡片**：要 Andy 点头的事是主对话里的一张卡片。上面一个小标签“要你同意”和来源（“来自‘订酒店’”“读过一封外来邮件”）；中间是程序写的真实动作和明细；下面是这次同意管多久的四个选择（只这一次、这件事里都行、几天内都行、以后都行），花钱只能“只这一次”；最下面“不要”和“同意”，要本人在场的“同意”带面容图标。卡片一出现就推到锁屏，锁屏上能直接点。

**过程行**：她在做事时，Andy 那句话下面一行小字：图标加一句话，图标和句子由她自己写（ADR 0250，PR 427），没有时用服务器的模板句子。一次只显示一行，换了事原地换；没成的说一句人话，接着做下一步；Andy 点了“停下”显示“停了”加已经做到哪。做完收成一行“做了 N 件事 · 用时”，点开是每一步的列表；她直接回答、没调工具时不出现这一行。

**后台在办**：从顶上那条点开的底部面板。每件大事一张卡：标题、花了多少；下面每个子线程一行：她写的图标、子线程名、正在做的那一步和第几步、状态词（在做、等你同意、做完了）。最下面一行“定好的提醒和周期任务”进定时。点一个子线程进详情：花了多少和预算、计划（做完的打勾，Andy 中途加的写明“之后加上的”，删掉的划掉并写原因）、过程（每一步的图标、那句话、时间），最后是“和别的子线程、主对话的往来”：默认收起，只占一行写条数；点开后每条一行，写她看了哪个子线程的什么计划或结果、主对话转来的哪句话、留给哪个子线程什么，带时间，再点收起（Andy 2026-11-25：“设计 ui 的时候，尽量折叠这些子线程的沟通内容，但是呢，如果我想看的话，也可以展开查看”）。主对话，和“后台在办”面板里大事和子线程那一层，都不显示这些往来，只在子线程详情里展开看。子线程里不能打字，最下面一句“这里只能看。有话回主对话说，她会转过来。”

**锁屏推送**：推送的正文就是她写的那句原话，全文显示，不遮盖；同意卡片的推送带“不要”“同意”两个按钮。Andy 正在 App 里看主对话时不弹出她的话（ADR 0285 决定第 6 条）。

**她的页面**：点头像从顶上展开，左上角收起回主对话。最上面是大一号的头像和 himawari 字样，下面三组：

| 组 | 行 | 第二行小字 |
| --- | --- | --- |
| 一 | 她记得的 | 记忆、主题、规则各几条 |
| 二 | 定时、用量和上限、同意过的事、保险箱 | 几条提醒和周期任务；这个月花了多少、上限多少；几条“不用再问”；几项 |
| 三 | 通知、隐私、设备 | 安静时段；空；这台 iPhone |

服务器还没有的功能，那一行不显示，不放空页。各页：

- 定时：分提醒、周期任务、跟进三组；每行写下次时间、谁定的（你说的、你同意的、她想到的），周期任务加跑过几次、花了多少；点进去能暂停、能撤销。取代原来的“提醒：全部”和“你答应过的事”页。
- 同意过的事：Andy 在同意卡片上选了“几天内都行”“以后都行”的，每行右边“撤销”。读过外来内容以后这些都不算数，照样问；花钱的不会出现在这里。
- 用量和上限：这个月花了多少和上限，能改每月上限和一个子线程默认能花多少。到了上限她停下来问。
- 通知：只有安静时段（开关、从、到），一句话说明这段时间里她的话不响、到点再响，同意卡片照样响。在主对话里说“晚上 11 点以后别推”也会改到这里。
- 隐私：第一行“让她感知”；记忆组只有“暂停记忆”；感知记录留多久；删掉感知记录（按一段经历、按天、按种类）；别人说的话；我的声纹。没有“敏感”这一行。
- 设备：这台 iPhone、随身麦克风、服务器，和“断开这台 iPhone”。

**记忆**（从“她记得的”进，内容由记忆方案 v3 定）：三段：记住的事、主题、规则。读过外来内容存下的记忆在行尾标“待确认”，详情里点确认。一条记忆的详情有你当时的原话（点“看上下文”跳回主对话那一处）和以前的版本，底部“不要这条”“改一改”；不要的进回收站，30 天内能恢复。主题页是她把同一件事散落的记忆整理成的一页，每句后面的小字点了跳回原话。右上角“昨晚整理了什么”列出每晚整理改了什么，一键全部撤销。全系统不显示“已记下”、敏感标记和遮盖。

**保险箱**（从她的页面进；怎样存、怎样批准由保险箱方案 v5 定（前提 S14），这里只定界面）：

- 列表：每一项写名字、能用在哪个网站、上次什么时候用过；打开了“后台也能用”的项带一个标签。底部“加一项”和“丢手机、换钥匙”。她只知道名字和网站，看不到值。
- 加一项：从苹果“密码”导入（在“密码”App 里选“导出到其他 App”，回到 Himawari 勾选给她用的项）、手动加（API key 这类）；也可以不先加，她用到一个没存过的网站时推送来问，点开只列网站对得上的项，也能当场从“密码”选或手动输入。值在这台 iPhone 上加密后才发给服务器，存好以后任何地方都不再显示，只能换成新的。
- 从“密码”选的项和她要去的网站不完全一致（协议、域名、端口有一样不同）时，整页大字警告两边的网站，默认按钮是“不用这一项”，继续要刷脸。
- 一项的详情：网站、用户名、值“已存 · 不再显示”和“换一个”；“后台也能用”开关默认关，说明写“打开后，定时任务用它不用问你；服务器被黑时这一项会泄露”；用过的记录（做什么、批没批、结果）；“删掉这一项”。
- 用的时候：推送只写“Himawari 请你批准一次使用”，不写是哪一项；点开是批准页：项的名字和网站取自用总钥匙签过名的清单，标“名字和网站和你存的一致”，手机核对不上就拒绝并提醒；“她要做什么”标明是她说的，只作参考；“只管这次办事 · 2 分钟内不点就作废”；“不批准”和“批准”，批准要刷脸，由手机安全芯片里的签名钥匙强制。登录以后的付款、转账照同意卡片另问。

## 建造顺序

只按依赖排。实施计划另写，这里只定先后：

1. **实测和真机清单**：四种连接方式的延迟、生产机的来回时间、19 项真机测试。结果可能改动本设计。
2. **地基**：设备配对和接口、连接和计时、苹果推送、原生主对话外壳和她的页面、感知记录的表和“删掉感知记录”页、记忆出处带类型和删除规则、两个固定工具连同这套设计的全部新提示词文字（一次上线，见[发给模型的路径](#egress)）、上限和用量页、小组件。
3. **时机和通知按钮**：接上后现有的 Gmail 提醒立刻受益。
4. **不依赖声音的感官**：位置、通讯录、日程、健康、相册、分享、Safari 扩展、剪贴板；来源登记。
5. **听和随口叫它**：人声检测、转文字、认人、抽取、评测集、抢跑、边生成边读。
6. **动手**：日历、提醒事项、闹钟、家居。服务器这一半要等前提 S10 那份方案的前两步进 main，设备动作才对主人可用。
7. **手表、Mac、随身麦克风、手机屏幕**。

收件箱、她的话、选项和同意卡片的服务器部分由收件箱方案分五步排（前提 S9）；iPhone 主对话的客户端跟着那几步做，顺序见 `/mnt/project-files/ios-scope/iphone-coding-brief-2026-11-25.md` 的三段。

Mac App 的构建和测试属于苹果客户端的例外（在 Andy 的 Mac 上用 Xcode 做），不受“Mac 上的 Himawari 服务器验证已无限期推迟”那一条限制：那一条说的是在 Mac 上装和跑 Himawari 服务本身。

4 到 7 互不依赖，可以并行。2 到 4 的服务器部分可以先用测试客户端提交感知记录来验收，不依赖 App。改表的几步按项目的改表队列排。

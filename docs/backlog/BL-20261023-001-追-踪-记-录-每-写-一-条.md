# 追踪记录每写一条都读出并解析整个运行的已有记录，写入代价随记录数增长

## Summary

packages/persistence-sqlite/src/sqlite-durable-operations.ts 的 appendTrace（追加一条追踪记录，即运行过程中的事件日志）在写入事务里用 SELECT record_json FROM trace_events WHERE run_id = ? ORDER BY sequence 读出这次运行已有的全部记录并逐条解析 JSON，只为了算下一个序号、核对第一条记录的范围和父事件是否存在。所以写第 N 条要读 N−1 条，一次运行写 N 条总共要解析约 N²/2 条记录。2026-10-23 第 3 层（cc-layer3-c776ea9d-r1）里 test/integration/sqlite-durable-repositories.test.ts 的 1001 条用例超过 30 秒时限，那次的主要原因是 1000 次单独提交在磁盘争用下变慢（同日已把该测试的数据准备改成一个事务写入），这个读全量的写法是另一处、目前不是瓶颈：安静时 1000 条约 7 秒。后果：一次运行的追踪记录很多时（例如长时间多轮工具调用），后面每条记录的写入会越来越慢。要做的：先量一次真实运行通常有多少条追踪记录；如果值得改，用 MAX(sequence)、按序号取第一条、按 id 和 run_id 查父事件代替读全量，并保留现有的范围和序号检查及其测试。

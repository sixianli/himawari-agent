# 云测试账号上官方 MCP v2 SDK 两条单元测试一直失败

## Summary

在云服务器的测试账号 himawari-ci（Ubuntu 24.04）上，packages/platform-node/test/node-capability-runtime.unit.test.ts 里 uses the official MCP v2 SDK with current authority 的 active 和 revoked_before_tool 两条用例一直失败：期望收到 4 个事件，实际只收到 1 个 capability.failed，错误码 CAPABILITY_RUNTIME_MCP_FAILED（MCP 是模型调用外部工具服务的协议，这里用官方 SDK 通过标准输入输出启动一个工具服务进程）。同样的用例在 Hermes（Ubuntu 22.04）上通过。原因还没查清：可能是测试账号在这台主机上启动隔离进程受 AppArmor（Ubuntu 的程序权限限制）约束，也可能和生产服务所在的系统设置有关；生产机是同一台主机、同一系统，所以要先确认生产的 MCP 工具服务是否也会这样失败。

## Origin

- 第二轮长任务条目 R2-P2 的叠批第 2 层运行（2026-10-19，云测试账号，修订 4fa95110）。同一对用例在 2026-10-16 的 R2-L11 运行（修订 3c208ec2）里已经失败过；2026-10-19 只跑 5 个文件、主机负载较轻的对照运行里仍然失败，而同一时段其他按时限失败的用例都通过了，所以这两条不像负载问题（负载类失败见 [BL-20261019-003](BL-20261019-003-云-测-试-账-号-满-负-载.md)）。

## Notes

- 失败处是 `node-capability-runtime.unit.test.ts:567`，断言收到的事件列表只有一个 `capability.failed`；R2-L11 那次记录到失败耗时 1.7 到 2.8 秒，说明工具服务进程启动后很快就失败了，不是超时。
- 先在云测试账号上单独跑这个文件并保留工具服务进程的标准错误输出，确定失败发生在哪一步；再判断生产安装是否受影响。查生产需要读生产主机上的状态，要另行取得用户授权。
- 测试结果的边界：Hermes 通过不代表生产机（Ubuntu 24.04）通过；测试账号失败也不直接证明生产会失败，因为生产账号的 AppArmor 规则和测试账号不同（见 [BL-20261001-001](BL-20261001-001-ubuntu-24-04-默-认-禁-止-bwrap.md)）。

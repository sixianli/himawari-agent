# 云测试账号满负载时几条用例按时限超时

## Summary

在云服务器的测试账号 himawari-ci 上跑完整的 unit 和 integration 项目时，几条用例会在自己的时限上失败：workspace-auto-authorization.unit.test.ts:429 和 migration-engine.contract.test.ts:473 超过 5000 毫秒，[R2-S4] linux-host-guardian 和 [R2-T10] sandbox-preparation-control 的等待超时。只跑这几个文件时它们通过，在安静的 Hermes 上也通过、耗时不变，所以和代码改动无关，和这台主机的负载有关（测试账号的 CPU 权重是 10，生产服务优先）。按项目规则不放宽时限：要查清这些用例为什么对负载这么敏感（例如是否在等真实时间或依赖进程调度），改成等可观察的完成条件，或者确定它们只在专门的通道上跑。

## Origin

- 第二轮长任务条目 R2-P2 的叠批第 2 层运行（2026-10-19，云测试账号，修订 4fa95110）。2026-10-16 R2-L11 的运行里也出现过 11 条落在时限上的超时，当时主机负载 5.1、4 核。

## Notes

- 对照证据：2026-10-19 在安静的 Hermes 上（运行前 `require-quiet-host.sh` 打印 `QUIET_HOST_OK`），批次基线和批次顶端跑这几个文件耗时相同（migration-engine 7182/6915 毫秒，workspace-auto-authorization 31786/32234 毫秒）；云测试账号上只跑这几个文件时也通过。
- 不放宽时限，也不设置 `HIMAWARI_TEST_TIMEOUT_MS`（AGENTS.md “Test and Production Hosts”）。
- 在这条处理完之前，云测试账号上的第 2、3 层结果里这几条超时要逐条和安静主机对照后才能判定与改动无关。

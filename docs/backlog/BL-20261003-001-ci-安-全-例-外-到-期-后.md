# CI 安全例外到期后构建报告无法发布

## 期望结果

根据当前源码与发布依赖重新审阅确实需要的精确安全例外，按现有 Owner 审阅规则处理其有效期，使 CI 报告发布恢复，同时保留现有安全检查。不能直接批量延长日期，或把产物构建通过称为整个入口通过。

## 来源与当前证据

2026-10-03，Codex 按 [D19、D13、D2 本批 brief](../../.ci-output/handoff/2026-10-03-round2-d19-d13-d2-brief.md) 在 Hermes 的 `58a9770` 上运行正式构建入口。产物构建检查通过，但报告发布失败，错误为 `SECURITY_EXCEPTION_EXPIRED_OR_INVALID`；整个入口退出 1。见 [入口报告](../../.ci-output/tool-execution-audit/2026-09-28/round2/hermes-r53/build-ci/local-summary.json) 与 [完整运行记录](../../.ci-output/tool-execution-audit/2026-09-28/round2/hermes-r53/build-v2-run.json)。

锁定的 [安全例外配置](../../ci/security-exceptions.json) 共 52 条：13 条合成测试字面量、39 条已发布依赖中的合成夹具。所有 `expiresAt` 都为 `2026-10-03T00:00:00Z`，即北京时间 08:00。`validateSecurityExceptions` 要求有效期严格晚于当前时间，因此到期后拒绝使用这些例外。配置中的 proposal 状态仍为 `proposed_owner_review_required`；本轮没有改变这个状态，也没有补写 Owner 审阅记录。

这是有效期规则按预期工作造成的维护阻碍，不是 D19、D13、D2 的工具执行根因。根据 brief 第 6 节，发现范围外问题后先记录并停止；[stop-01](../../.ci-output/handoff/2026-10-03-codex-round2-hermes-stop-01.md) 保留原始报告、尚未完成的测量、静态调查和继续条件。

## 处理边界

由 Claude 安排既有例外审阅流程，Owner 决定仍需要接受的精确范围；不在这批工具执行调查中修改有效期、proposal、审阅凭据或校验规则。当前没有证据说明 52 条都应继续保留，不能把到期错误本身当作续期依据。

## Owner 审阅与续期（2026-10-03）

Claude 把 52 条例外逐条整理给 Owner（用户 `sixianli`）查看：13 条本项目测试里的合成字面量（幂等键、按顺序排列的十六进制假 token、加密测试的认证标签、签名部分为英文单词的 JWT 样式字符串），附源码行原文；39 条锁定 npm 包原样发布的文件（README 示例、包自带测试、类型声明示例、运行时哑值），附包名、版本和用途。Owner 看完后的原话是“全部续期”，记录在长任务目录 `goal.md` 的 G25。

据此修改 [安全例外配置](../../ci/security-exceptions.json)：`proposal.proposedAt` 改为 `2026-10-03T00:00:00Z`，`reviewEvidence` 追加这次审阅的说明；52 条的 `expiresAt` 全部改为 `2026-11-02T00:00:00Z`，即提案日期后 30 天，是校验器允许的上限。路径、内容摘要、数量、来源证明和 `proposal.status`（格式规定只能取 `proposed_owner_review_required`）都没有改，校验规则也没有改。

已做的验证：在 Hermes 上用仓库里的 `validateSecurityExceptions`，配合锁文件依赖和 Semgrep 规则编号，检查新文件：当前时间和 `2026-11-01T23:59:59Z` 都通过，共 52 条；`2026-11-02T00:00:00Z` 按规则报 `SECURITY_EXCEPTION_EXPIRED_OR_INVALID`。旧文件在当前时间报同样的错误。

尚未验证：完整构建入口的报告发布步骤，以及正式 `npm test`。它们随工具执行第二轮 D19/D13/D2 批次的第 3 层一起运行，结果出来后再关闭本记录。另外，本地运行时读取的是被测提交里的例外文件；GitHub 上的 PR 检查读取 `main` 上的版本，所以要等合并，或者在 PR 评论里走 Owner 审阅，GitHub CI 才会恢复。

## 第二份到期的 Owner 审批（2026-10-03）

续期上面 52 条之后，工具执行第二轮的会话 B 在 Hermes 上用 `11f1b7f` 跑正式构建入口：8 项构建检查通过，报告发布仍失败，`publicationFailures` 为 `SECURITY_REVIEW_EXPIRED`。这是另一项检查：`scripts/ci/security-owner-review.mjs` 读取 `.github/security-review-manifest.json`（26 条清单）和 `.github/security-review-comment.json`（指向一条 GitHub 评论），再核对那条评论里批准记录的有效期。

已确认的事实：原评论是 Owner `sixianli` 于 2026-09-14 发在已合并的 PR 4 下的 [审批评论](https://github.com/sixianli/himawari-agent/pull/4#issuecomment-5662807447)，`expiresAt` 为 `2026-10-03T00:00:00Z`，与 52 条例外同时到期。26 条是：同一个合成测试 token 在当前代码 10 处、历史提交 11 处的记录，扫描器把测试密码和账号命令里的名称误报成凭据的 4 组记录，以及 node-forge 1.4.0 README 里的示例种子。

处理：Claude 向 Owner 说明以上内容后，Owner 选择“全部续期，你代我发评论”（长任务目录 `goal.md` 的 G30）。Claude 用 Owner 本机已登录的 GitHub 账号在 PR 4 下发布 [续期审批评论](https://github.com/sixianli/himawari-agent/pull/4#issuecomment-5966743301)（2026-10-03T07:24:47Z）。它和原评论相比只改了开头说明和 `expiresAt`（改为 `2026-11-02T00:00:00Z`，距发布时间不到 30 天）；`manifestSha256`（`565c2fda…`）、`sourceHead` 和 26 条清单都没变。`.github/security-review-comment.json` 改为指向新评论。校验规则没有改。

尚未验证：新评论能否通过全部检查，包括有效期之后的行号和摘要检查。要等下一次在 Hermes 上运行正式构建入口才能确认。

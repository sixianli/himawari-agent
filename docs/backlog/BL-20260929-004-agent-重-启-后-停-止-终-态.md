# Agent 重启后停止终态 Run 的未绑定容器环境

## 期望结果

Agent 崩溃重启后，为终态 Run 遗留的未绑定 container 预约恢复环境停止与认证释放，避免预约一直占用工作目录。必须保留现有权威、后端身份、环境范围与释放回执校验，不重新执行模型或工具。

## 来源与理由

原限制记录来自 2026-09-29 [第二轮 reply-18 第 1 节](../../.ci-output/handoff/2026-09-28-round2-claude-reply-18.md)：仅只读查清并记录，本轮不实现。关联[准备恢复设计的 container 分流](../execution/specs/2026-09-28-sandbox-preparation-control-recovery-design.md#econtainer-预约自动恢复分流) [SOURCE: docs/execution/specs/2026-09-28-sandbox-preparation-control-recovery-design.md]。

## 已确认的范围与边界

2026-09-29 核查版本没有为这种未绑定预约自动补调整轮 `stopRun` 的路径。启动恢复只保存预约中断，后台预约恢复仅向 SRT 发送准备停止；container 只读取环境释放回执。环境未释放时预约变成 `unresolved / SANDBOX_CONTROL_UNCONFIRMED`，同一次 stop 不再调度。**container 环境在这种情况下不会被自动停止，预约会一直占用工作目录；安全（不会误释放），但需要人工处理。**这是调用链的静态确认，不是 Docker 现场复现。

Run 的正常完成和取消可以调用 `stopRun`，但重启后的终态 Run 不会再次进入正常执行；执行中断要求当前进程内已有执行尝试。对 failed/cancelled Run 人工再次请求停止会调用清理端口，因此“没有自动恢复”不等于没有人工入口。已绑定且结果未确定的 container 任务还可经资源观察停止其环境，不可把这条路径套用到只有 reserved 预约的情况。

期限恢复转为 failed 的 SQL 本身要求所有资源已释放。因此当前这种占用还在的预约会挡住期限收尾，不能将“恢复判失败后未停止”描述成已经复现的具体事件。

代码位置及完整只读依据见 [E 限制核查](../../.ci-output/tool-execution-audit/2026-09-28/round2/e-terminal-container-review.md)。后续工作需先设计终态资源停止的范围、权限和重复执行边界，并用崩溃重启、终态已持久、预约未绑定及缺少释放回执的场景验收。这里只记录期望结果，不批准实现或生产容器操作。

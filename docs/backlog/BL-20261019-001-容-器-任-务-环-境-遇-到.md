# 容器任务环境遇到另一个 Run 占用工作区时不排队

## Summary

容器任务环境（一轮对话专用的 Docker 容器）后端仍在准备阶段（`prepare`，准入前解析授权和工作区的那一步）里获取环境。另一个 Run（另一轮对话）对同一工作区还有未确认的占用时，获取直接失败，请求不会进入公平排队（按先来后到等待工作区空出的队列），而是马上以未派发失败结束。常驻 SRT（本机沙箱里常驻的任务环境）后端已由 R2-P2 缺陷 D-51 改为在排队循环里获取环境，同样的情况会排队等待。生产目前没有配置容器任务环境。

## Origin

- 来自第二轮长任务条目 R2-P2 的缺陷 D-51（2026-10-19）。D-51 只改了常驻 SRT 后端：`apps/agent-service/src/production-sandbox-services.ts` 的 `prepareRuntimeV2` 不再为常驻后端获取环境，改由排队循环调用新的 `acquireEnvironment`；容器后端的 `environments.acquire` 仍留在 `prepareRuntimeV2` 里。见 [ADR 0054](../adr/0298-where-tools-run.md) 的 D-51 补充。

## Notes

- 后端一致性测试（`test/integration/sqlite-sandbox-execution-v2.test.ts` 的 `[R2-P2] sandbox backend parity`）按产品导出的后端清单 `SANDBOX_EXECUTION_BACKEND_REFS` 逐个后端跑排队场景，但容器后端不在这份清单里，所以测试管不到它。修这一条时，把容器后端加进清单，测试就会对它生效。
- 处理前先核实现行生产有没有配置容器任务环境，再定优先级（同 [BL-20261017-004](BL-20261017-004-容-器-执-行-路-线-的-写.md)）。

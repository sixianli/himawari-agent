# 清理核查诊断无上限

## 期望结果

未启动预留拿不到释放证明、只能等管理员处置时，系统仍可以继续按间隔核查，但保存的诊断记录有上限：同一原因、同一控制目录的重复失败只更新计数和最后时间，或在达到上限后不再新增。管理员读诊断时仍能看到首次和最近一次失败及次数。不放宽释放证明条件，不因停止记录诊断而释放占用。

## 来源与已确认事实

2026-10-12 生产只读诊断 05（`.ci-output/production/2026-10-12-read-hang-diagnostic-05/reservation-recovery.20261012T140620Z.json`）读回 S10 卡住的 Run `run:c1284750-de9d-43dd-aee1-5474dc27539c`：控制目录 `/var/lib/himawari/jobs/control-bcab8277eea4c6dee76f` 没有 `control.sock` 和 `final.json`；00:25:42 到 14:05:59 之间停止和核验各 1540 次，全部是 `SANDBOX_SUPERVISOR_UNAVAILABLE`，每次都保存一条 `sandbox-control:…:diagnostic:<uuid>` 加密诊断记录，共 3080 条，大约每 32 秒一对。

[R2-L8 修复](https://github.com/sixianli/himawari-agent/blob/208007462f99e16c5c8cd4daac2acc10fa9f5f36/docs/execution/specs/2026-09-28-sandbox-preparation-control-recovery-design.md#control-opened-first)让控制步骤之后的准备失败能自动释放，这类重试会结束；但控制通道本身打开失败、SDK 线程从未创建、宿主在写终态前被强制结束这三种情况仍会一直重试，诊断记录仍会无上限增长。该 Run 本身按 G72 在第三次部署停服窗口管理员处置。

## 后续验收边界

需要先确定诊断合并或上限的规则，再写测试：用真实控制器重复失败多次，读回诊断记录数不超过上限、首次与最近一次失败和次数正确，原占用仍保持。已经存在的 3080 条记录不在本项里删除；是否清理另行决定。

# 生产缺少备份密钥且维护演练配置与生产不一致

## 期望结果

为生产的公开 `backup create`、`backup verify` 和 `backup restore` 建立经单独批准的备份密钥配置，并实际验证创建、核验和恢复。部署演练使用与目标生产相同的配置字段和密钥用途；新增或缺失字段必须在生产操作前暴露。此次 G69 原样复制不等于公开 backup 命令已经可用。

## 来源与已确认事实

用户 G68 要求修包期间保持停服，G69 选择此次使用停服数据库和整个加密 Payload 文件树的原样复制，后续另记生产备份待办。原裁定见 [reply-06](../../.ci-output/handoff/2026-10-08-codex-prod-sandbox-reply-06.md)。

生产配置的 `secretReferences[].purpose` 只有 `model-provider`、`payload-encryption`、`identity-csrf`。`apps/admin-cli/src/index.ts` 的 `recoveryAdapter` 必须取得恰好一个 `backup-encryption` 引用；旧 3a65b90 与候选 7748b0a 的逻辑相同。生产 S3 的旧 CLI 因此返回 `ADMIN_ARGUMENT_INVALID`，迁移前检查已通过。此根因由代码和 Claude 的实际生产失败读回确认。

原失败文件位于 `/var/lib/himawari/second-20261009-evidence/`：`s3_backup49-started.json`、`s3_backup49-failure.json`、`s3-before49.json`、`s3-backup49-create-command.json`。不得覆盖或删除。本地执行记录保存在 `.ci-output/production/2026-10-09-second-deploy-execution-01/`。原 Hermes 演练额外提供了 `backup-encryption`，配置形状与首次生产配置不一致，所以未暴露此部署包缺陷。

## 本次处理与后续验收边界

本次修订包仅采用 G69 的停服原样复制：状态锁下复制产品数据库和完整 `payload-ciphertext` 树，独立逐成员读回并检查副本数据库，不读取备份密钥。维护链的 Hermes 演练只提供上述三种密钥用途，结果和逐命令结论保存在 [stop-07](../../.ci-output/handoff/2026-10-08-codex-prod-sandbox-stop-07.md)。生产仍不得直接使用 backup 命令。

后续处理需要明确的生产密钥及配置变更授权，不能在本次修包中擅自创建密钥。验收须用真实配置和安装 CLI 证明完整恢复点创建、核验、恢复与独立状态读回，并保留失败证据；不得降低原有加密、身份、历史和权限检查。恢复认证的语义也须分别核对：公开 backup restore 会执行自己的认证恢复流程，本次原样复制只恢复旧行，不自动撤销这些行。未来演练须对实际生产配置形状作明确检查，不能只证明带额外测试密钥的配置可运行。

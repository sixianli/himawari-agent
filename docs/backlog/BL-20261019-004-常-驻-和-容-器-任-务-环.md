# 常驻和容器任务环境绑定后抛异常时的诊断阶段没有测试覆盖

## Summary

D-52 让 Worker 在常驻 SRT 和容器任务环境里记录准备阶段：绑定前出错记为 prepare 或 bind，绑定成功后改记为 execute（apps/execution-worker/src/production-sandbox-execution-v2.ts，与一次性 SRT 路径的写法一致）。绑定后改记 execute 这一行没有专门的测试：Worker 生命周期测试里的假环境走不到绑定，真实常驻路径里停止环境时 Worker 正常返回结果未知、不抛异常，所以两种办法都制造不出“绑定后抛异常”。这一行只影响出错时记录的诊断文字（execute 而不是 bind），不影响调用结果，调用仍按结果未知处理。

## Origin

- 第二轮长任务条目 R2-P2 的缺陷 D-52（2026-10-19）。为这一行先后试了五轮红色运行：`d52-l0-red-03`、`-06`、`-07`、`-08` 在 Worker 生命周期测试里都没走到绑定（假环境缺 runner 输入等，准备阶段就出错）；`d52-l0-red-09` 改在真实常驻路径上，在绑定后停止环境，结果没有产生任何诊断（`missing preparation diagnostic`），因为 Worker 对这种情况正常返回结果未知。证据在云测试账号 `/srv/himawari-ci/evidence/d52-l0-red-0*`，记录见 `.ci-output/handoff/2026-10-19-r2p2-d52-impl-stop.md` 和 `-stop-2.md`。

## Notes

- 加这一行的理由：没有它，D-52 新加的 `entry.stage = "bind"` 会一直留到执行阶段，绑定后的意外异常会被记成 `SANDBOX_BIND_FAILED`，误导生产排查；加了它，记录方式与一次性路径一致。
- 现有的回归护栏：`test/integration/production-srt-task-environment.test.ts` 里“绑定后停止环境不会被记成绑定失败，也不会当成从未启动”的用例。
- 以后补测试的思路：在真实常驻路径上让绑定之后的某一步确定地抛异常（例如让 Agent 的 payload 中转在绑定后对这次调用的下一个请求返回错误），断言诊断 `stage` 为 `execute`。

# S9 回滚前处理数据库旁留下的附属文件

## 期望结果

生产操作包里的 S9（服务启动失败后，把数据库和数据目录恢复到停服时原样拷贝的回滚步骤）在下面这种情况下也能按步骤安全完成，不需要临场手工处理：服务切换启动的 S7_SWITCH_START 失败了，而失败时在用数据库 `product.sqlite` 旁边还留着 `-wal`、`-shm` 两个附属文件。

- `-wal`、`-shm` 是 SQLite 在 WAL 模式（先把改动写进日志文件、之后再合并进主文件的模式）下用的日志文件和共享索引文件。最后一个读写连接正常关闭时，SQLite 会把日志合并回主文件并删掉它们。
- 处理方法要在回滚前把日志里尚未合并的内容如实并回主文件（或证明日志为空），再继续 S9 的原有检查；不能简单删除附属文件，因为日志里可能有服务写入、还没合并的数据。
- S9 现有的“数据目录里不许有附属文件”检查保持不变，新步骤在它之前把状态整理好，并留下处理前后的读回证据。

## 来源与已确认事实

- 第五次变更（R2-L12）的 Hermes 演练里，生产形状演练记录了 S7_CATALOG_UPGRADE（能力登记升级步骤）刚结束时数据库旁的附属文件：`{"-wal": 0, "-shm": 32768}`，即日志文件 0 字节、共享索引 32768 字节。证据在 `.ci-output/handoff/prod-fifth-evidence-c53bca70/rehearsal/shape-01/production-shape-chain-report.json` 的 `sidecarsAfterUpgrade`。
- 来源是 S7_CATALOG_UPGRADE 的最后一步 `himawari db status`（第五次操作包 `maintenance/run-maintenance.mjs:113`）。这个产品命令以普通只读方式打开数据库（`apps/admin-cli/src/index.ts:301` → `packages/persistence-sqlite/src/migration-engine.ts:765`，better-sqlite3 的 `readonly: true`），只读连接关闭时不会删除附属文件。
- 第四次就有同样的情况：第四次操作包的 S7_DB_STATUS 末尾也运行 `db status`（`.ci-output/production/2026-10-15-fourth-change-packet-01/maintenance/run-maintenance.mjs:116`）。第四次的 S7_SWITCH_START 成功了，服务以读写方式打开数据库，之后附属文件由服务自己管理，所以没有出问题。
- S7_SWITCH_START 失败时会执行 `systemctl stop`（第五次操作包 `systemd/S7-switch-start-readback.py:257-272`）。如果服务已经以读写方式打开过数据库并正常退出，附属文件会被清掉；如果服务在打开数据库之前就失败，或者被强行结束，附属文件会留下。
- S9 在两处要求在用数据库旁没有附属文件：`maintenance/raw-copy-recovery.mjs:75`（`FIFTH_RAW_COPY_DATABASE_SIDECAR_PRESENT`）和 `maintenance/S9-control-files.py:157`（`FIFTH_S9_DATABASE_SIDECAR_PRESENT`）。所以上面那种情况下 S9 会拒绝执行，回滚停在“服务已停、旧版本没恢复”。
- 第五次没有改这一处：它不是第五次新引入的，修改要重新登记操作包摘要、重新审核和演练。第五次执行时如果碰到，按冻结操作包的规则停下、保留现场，由用户决定怎么处理。

## 验收边界

- 用可重复的测试制造两种状态：日志为空的附属文件（与这次演练记录一致），以及日志里有尚未合并内容的附属文件；证明新步骤处理后 S9 能完成，且数据库内容与处理前通过只读读回得到的内容一致。
- 服务进程仍在运行、或数据库被其他进程打开时，新步骤必须拒绝执行。
- 不放宽 S9 现有的附属文件检查，不在生产上做没有证据的删除。

# 容器执行路线的写入和编辑失败同样停在效果未知

## Summary

执行进程（Worker，负责在隔离环境里真正运行工具的进程）除了沙箱路线，还有一条容器路线：工具在容器里运行（`apps/execution-worker/src/production-sandbox-execution-v2.ts` 约 1060–1195 行）。这条路线只认两种已核实的结果：已发布，或 `FILE_VERSION_CONFLICT`。`write`/`edit` 在容器里以非零退出失败时，结果记为 `SANDBOX_OPERATION_FAILED`、效果未知，和 R2-T14 修好之前的沙箱路线一样，结果不交给模型，恢复流程不停重放（见 [BL-20261017-002](BL-20261017-002-工-具-效-果-未-知-时-恢.md)）。R2-T14 没有改这条路线：runner 在容器里是否也报告 `writeNotStarted`、主机怎样核对，需要另行设计和测试。

## Origin

- 来自第二轮长任务条目 R2-T14 的方案比较（2026-10-17）：DeepSeek 逐行审核时指出容器路线有同一类失败，Claude 读代码确认（同一文件约 1085 行的 `verifyPiWriteEvidence(...)` 和 1098 行的 `published = outcome`、约 1180 行起的 `SANDBOX_OPERATION_FAILED` 分支）。沙箱路线的修法见 [SRT 统一执行设计的 R5 实现说明](https://github.com/sixianli/himawari-agent/blob/208007462f99e16c5c8cd4daac2acc10fa9f5f36/docs/execution/specs/2026-09-07-srt-unified-execution-design.md#r5-实现说明2026-09-09)。

## Notes

- 容器路线只在执行进程配置了任务环境（复用的任务沙箱，`apps/execution-worker/src/production-worker-composition.ts` 约 545 行），并且这次调用计划的后端编号 `backendRef` 与任务环境的相同时才会用到（`production-sandbox-execution-v2.ts` 约 251 行）。第五次生产的能力声明里 `backendRef` 是 `srt`（`.ci-output/production/2026-10-17-fifth-change-packet-01/signing/cloud-seal.mjs` 约 411 行）；现行生产有没有配置任务环境、它的 `backendRef` 是什么，没有核实。处理时先核实，再决定优先级。
- 处理时沿用沙箱路线的做法：runner 报告“开始改目标文件之前就失败”，主机核对它属于本次调用；其余失败按 `SANDBOX_WRITE_EFFECT_UNVERIFIED` 作为有界失败交给模型。

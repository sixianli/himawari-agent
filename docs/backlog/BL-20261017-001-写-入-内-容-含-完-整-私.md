# 写入内容含完整私钥时先写后拒，对话卡住

## Summary

模型用 write 写入的内容里有一段完整私钥（从开头行到结尾行）时，准备阶段查不到：Pi 给 write 的预备结果只有“Successfully wrote N bytes to <路径>”，不含写入内容。发布阶段（packages/platform-node/src/files/pi-host-publication.ts 的 publishPreparedPiOperation）先把文件写进去，再整理结果；整理时用原规则 scanMachineSecrets 扫描整个结果信封，包括参数里的写入内容，命中后对 bash 以外的工具抛 PI_RESULT_SECRET_REJECTED。结果是文件已经写入，模型却收到失败。R2-T14 收窄私钥片段规则（2026-10-17，G127）之后，只剩“写入内容含完整私钥”这一种情形会这样；现在线上的第四次变更同样存在。2026-10-17 在收窄之前的代码上（那时写入内容只要有一行开头行就会在发布阶段被拒），产品路径场景录到了写后才拒的后果：这一轮的执行记录显示“部分执行记录暂不可读取”，整段对话“暂时无法加载”，发送按钮一直不可用，下一个场景因此无法发送。为什么发布阶段抛错会让对话读不出来，还没有查。

## Origin

- 来自第二轮长任务条目 R2-T14 中 G127 改动的第二次逐行审核（DeepSeek，2026-10-17）：审核人指出这种情形可达，项目里没有任何检查在 write 参数到达工具之前查机器秘密。规则说明见 [ADR 0054 命令失败时把输出结尾交给模型](../adr/0298-where-tools-run.md)。
- 后果的证据：Hermes 上 `/data/hermes/himawari/tool-audit-round2/r2t14/evidence/r2t14-key-red-04-pp/product-path/r2t14-pem-note-write-failed.aria.yml`（界面无障碍树）和同目录的 `service-logs/`。

## Notes

- 2026-10-17 R2-T14 已修好“对话卡住”这一半（见 [SRT 统一执行设计的 R5 实现说明](https://github.com/sixianli/himawari-agent/blob/208007462f99e16c5c8cd4daac2acc10fa9f5f36/docs/execution/specs/2026-09-07-srt-unified-execution-design.md#r5-实现说明2026-09-09)）：合同版本 1 的 `write`/`edit` 结果里有疑似密钥时，改为交给模型一份不含正文的固定说明（三种：已修改并通过核实、没有被修改、可能已被修改）；结果被拒且已经开始改文件时，原因码是 `SANDBOX_WRITE_EFFECT_UNVERIFIED`，按有界失败告诉模型“文件可能已被修改，请先读取目标文件”，这一轮不再卡住。仍然没有修的是：写入内容（参数）本身含完整私钥时，文件照样先写入再报“可能已被修改”，没有在写之前拒绝；下面几条处理方向仍然有效。
- 处理方向：在准备阶段（`apps/agent-service/src/production-file-preparation.ts`）就用原规则检查 write 的参数，写入之前拒绝，让 write 和 edit 都不再出现“文件已改、模型收到失败”。
- 被拒的工具调用参数仍留在对话里，下一次模型请求会带上它。2026-10-17 读代码核实（DeepSeek 逐行审核提出，Claude 复核）：这不会让请求被拒。`packages/platform-node/src/trusted-model-provider.ts` 的 `invoke` 检查的 `ModelInvocationRequest` 只有编号和内容引用（`packages/application/src/ports/intelligence.ts`），不含对话；Agent 循环的消息由 Pi 的模型运行时直接发出（`packages/runtime-pi/src/configured-model-binding.ts`），产品侧不扫描对话。所以模型自己写进参数的私钥会随后续请求再发给模型服务；要不要在对话里替换掉它，处理时一并决定。2026-10-17 第 3 层的产品路径场景 `r2t14-full-key-write`（Hermes `/data/hermes/himawari/tool-audit-round2/r2t14/evidence/r2t14-wf-l3-01/product-path/r2t14-full-key-write-readback.json`）在运行中证实了这两点：文件已写入完整私钥，产品路径用的假模型（测试里按固定规则回复的模型）在下一次请求里收到 `SANDBOX_WRITE_EFFECT_UNVERIFIED` 的固定说明，请求没有被拒，这一轮正常结束，沙箱已释放。
- 另外查清发布阶段抛错后为什么整段对话读不出来；发布阶段因别的原因抛错（例如结果超过上限）可能也会这样。
- 同一份收窄前的代码上，编辑场景也录到了同样的后果（Hermes `/data/hermes/himawari/tool-audit-round2/r2t14/evidence/r2t14-key-red-05-pp/`）：编辑差异里带出私钥开头行，发布阶段抛错后这次执行记为 `SANDBOX_OPERATION_FAILED`，工具结果在追踪里记成“结果未知”（`runtime.result_unknown`），这一轮直到测试超时都没有结束。（2026-10-17 更正：这里原先写“假模型又发起了 281 次同样的编辑”，不对。之后的诊断 `r2t14-key-diag-01` 显示，产品路径用的假模型（测试里按固定规则回复的模型）一共只收到 6 个请求；重复的那几百次是恢复流程拿检查点里同一条模型输出重放同一次工具调用，见 [BL-20261017-002](BL-20261017-002-工-具-效-果-未-知-时-恢.md)。）

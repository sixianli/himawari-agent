# 安装结果继承安装者 umask 导致产品拒绝自己的运行时目录

## 期望结果

不论安装者的 umask（决定新建文件默认权限的进程设置，例如 `0022` 或 `0002`）是什么，安装出来的产品运行时目录都不允许同组或其他用户修改，产品自己的沙箱主机检查能接受这份安装。

## 来源与现象

2026-10-01 在云服务器上运行第二轮测试时，测试用户 `himawari-test` 的 umask 是 Ubuntu 默认的 `0002`（让同名组也能写）。依赖和构建产物因此成为组可写，原 19 个 integration 文件中有 100 项因 `SANDBOX_HOST_PATH_UNSAFE` 失败：产品检查发现 SRT（`@anthropic-ai/sandbox-runtime`，产品使用的沙箱运行库）的 `vendor/seccomp` 目录组可写，于是拒绝运行沙箱。测试环境已改为 umask `022` 并去掉任务目录的组写权限；这一项本身是测试环境问题。

随后只读审查产品安装代码时发现，产品安装存在同样的问题。

## 已知与未知

- **已确认（代码）**：
  - `scripts/ci/artifact-archive.py` 解压时，用 `destination.mkdir(...)` 和 `target.parent.mkdir(...)` 新建目录，没有指定权限，结果取决于 umask；它只对普通文件执行 `os.chmod(target, member.mode)`。安装包本身不保存目录条目，所以没有可以恢复的目录权限。
  - `scripts/install-node-runtime.mjs` 把解压结果直接 `rename` 到安装位置，之后没有统一修正目录权限。
  - `packages/platform-node/src/capabilities/sandbox-host-verifier.ts` 的 `checkedMetadata` 拒绝 `mode & 0o022` 不为 0 的路径。
  - 结论：在 umask `0002` 下安装，解压出的目录是 `0775`，产品会拒绝自己的安装。
- **未验证**：没有实际在 umask `0002` 下运行安装来复现。源码目录复制安装（`cp` 分支）的目录权限是否同样受影响，也还没有核对。
- **不受影响的情况**：已有的受保护升级脚本显式设置了 umask `077` 和目录权限；root 默认 umask 是 `022`。

## 可能方向与约束

- 解压和安装时，显式把所有新建目录设为 `0755`，文件保持 `0644` 或 `0755`，不依赖调用者的 umask。
- 加回归测试：在 umask `0002` 下安装，再通过沙箱主机检查。
- 安全检查本身不改。
- 改动涉及打包和安装，按 AGENTS.md 要提前运行第 3 层（完整测试）；相关安装 Runbook（操作手册）要同步核对并重新封存。

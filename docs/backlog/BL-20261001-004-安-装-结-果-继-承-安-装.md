# 安装结果继承安装者 umask 导致产品拒绝自己的运行时目录

阅读导航：[权限复现与修复范围](#复现与修复范围) · [归档与清单处理](#d15-single-decompression-candidate) · [验收证据边界](#d15-permission-verification-boundary) · [前后耗时与后续验收](#d15-timing-evidence)。

## 期望结果

不论安装者的 umask（决定新建文件默认权限的进程设置，例如 `0022` 或 `0002`）是什么，安装出来的产品运行时目录都不允许同组或其他用户修改，产品自己的沙箱主机检查能接受这份安装。

## 来源与现象

2026-10-01 在云服务器上运行第二轮测试时，测试用户 `himawari-test` 的 umask 是 Ubuntu 默认的 `0002`（让同名组也能写）。依赖和构建产物因此成为组可写，原 19 个 integration 文件中有 100 项因 `SANDBOX_HOST_PATH_UNSAFE` 失败：产品检查发现 SRT（`@anthropic-ai/sandbox-runtime`，产品使用的沙箱运行库）的 `vendor/seccomp` 目录组可写，于是拒绝运行沙箱。测试环境已改为 umask `022` 并去掉任务目录的组写权限；这一项本身是测试环境问题。

随后只读审查产品安装代码时发现，产品安装存在同样的问题。

## 复现与修复范围

- **已确认（Hermes 运行）**：修复前，真实归档安装在 umask `0002` 下产生 `0775` 运行时目录，新前缀和已有 `0700` 前缀都被产品检查器以 `SANDBOX_HOST_PATH_UNSAFE` 拒绝。在 `0077` 下目录变成 `0700`，不符合新运行时目录固定 `0755` 的安装合同。文件期望清单取自原始归档的 `artifact-record.json`。
- **已确认（Hermes 运行）**：小型源码输入中包含多层 `0775`、`0777` 目录和 `0644`、`0755` 文件。真实 `--source` CLI 在两种 umask、新前缀及已有 `0700`、`0770` 前缀下的六个场景，修复前都被真实产品检查器拒绝。Node 复制保留源目录模式；仅更改安装者 umask 不能修正不安全的源目录。
- 修复只对本次新建的解压目的目录及其父目录、安装前缀目录链和新运行时目录设置 `0755`。安装器内部暂存根仍为 `0700`。已有 prefix、lib、bin 只清除同组及其他用户写权限（模式中的 `0022`）：`0700` 保持 `0700`，`0770` 变成 `0750`。其他已有外层目录保持原权限，普通文件的字节和包内模式不变，产品检查器不改。
- 受保护升级脚本显式设置 umask `077`，并统一目录和文件模式；本批只核对代码，不执行升级或生产操作。
- 小型源码样本只证明复制入口的权限规则，不证明约 33,000 个文件的完整源码安装能在默认 30 秒内完成。完整产品安装证据来自三个真实归档场景；Mac 和生产主机行为未验证。

<a id="d15-single-decompression-candidate"></a>

### 归档与清单处理

2026-10-04 的第二候选复用第一候选的目录缓存与归档分支移除重复规范步骤，并增加一次 gzip 解压、文件指纹并发及测试侧独立回读调整。解包先完整读取 gzip 到权限 `0600` 的匿名临时文件，在同一份未压缩 tar 上执行原有完整预检和文件写出。目的父目录缺失时，只读查找父链中最近的已有目录存放临时文件，不提前创建中间目录。损坏、截断或原始解压大小超限在创建解压目的目录之前拒绝；输入同时含 gzip 或原始大小错误与 tar 结构错误时，先报告前者。`stream` 操作不变。

新增原始解压 tar 上限为 `2 GiB + 256 MiB`（`2415919104` 字节），包括 tar 头、PAX 扩展与填充。普通文件逻辑内容总量的原有 `2 GiB` 上限不变。r62 完整产品归档的匿名 tar 为 `328202240` 字节，约 `330 MB`；它与写出的 payload 同时占用磁盘，解包上下文结束后自动释放。安装前提见[归档解包与临时磁盘](../runbooks/install-start-stop-runbook.md#artifact-extraction-contract)。[SOURCE: docs/runbooks/install-start-stop-runbook.md#artifact-extraction-contract]

普通模式保持原目录遍历和结构安全检查顺序，最多并发计算 16 个文件的元数据与流式 SHA-256，每个文件仍读取全部字节。成功清单、模式、字节数、摘要和排序不变。失败按遇到文件的顺序选择，早于后续结构或遍历错误；固定输入的这一顺序与旧串行实现一致，不承诺外部并发修改文件时结果相同。已启动任务全部收尾后才返回。构建的 `normalizeModes=true` 路径仍逐文件串行，保留 chmod 结果及失败前已经产生的修改。归档安装直接移动已验证且目录模式已规范的运行时；源码复制继续执行原目录规范流程。产品 checker 与全部内容检查没有更改。详细合同见[归档解包与文件清单](../execution/specs/2026-09-03-github-ci-quality-gates-design.md#artifact-extraction-and-inventory)。[SOURCE: docs/execution/specs/2026-09-03-github-ci-quality-gates-design.md#artifact-extraction-and-inventory]

旧实现针对损坏 CRC、错误末尾长度、截断 trailer、损坏的第二 gzip 成员、非法 tar 与损坏 gzip 混合输入、原始解压大小超限的 6 条回归测试实际失败；第二候选修复后，相关 tooling 文件 `58/58` 通过。正式容量上限由合同断言检查，大小边界用缩小后的容量做真实 gzip 与临时文件 I/O 测试；没有实际生成 `2.25 GiB` 文件来代替这项边界测试。失败前与修复后原始报告均保留在 r62 证据目录，历史权限红证据也继续保留。

<a id="d15-permission-verification-boundary"></a>

## 验证与约束

- `[R2-D15]` 三条完整归档场景都真实运行安装 CLI，CLI 继续检查全部 payload 内容。每条独立回读所有目录及文件的路径与模式。`0002/new` 另做安装后全部文件内容摘要；`0077/new` 与 `0002/0700` 调用已安装产品的元数据 `fingerprint`，再按目录深度、顶层分组和文件模式抽样回读字节。元数据身份检查不等价于完整 `digest` 的逐文件 `O_NOFOLLOW` 打开、全部内容读取和读取前后身份核对。源码样本继续核对原始输入目录未被修改。
- 损坏、截断和原始解压大小超限在创建解压目的目录之前拒绝；完整 tar 预检也须在创建目标之前通过。混合输入不能承诺 tar 错误总是先报告。独立解包器不得在预检前创建缺失目的父目录，但安装 CLI 会先准备 prefix 与内部暂存根。
- 权限修复还覆盖含 `..` 前缀下私有父目录不变，以及符号链接源码根被拒绝、原始源码权限和已有运行时不变；不能从递归 `mkdir` 返回的第一个路径推断其余目录都由本次创建。
- 安全检查本身不改。
- 原始归档清单、期望排序和抽样选择移到文件级准备，成本发生在官方用例计时之前，不能描述为没有成本。默认关闭的 CLI 元数据记录只辅助说明耗时，不能用 CLI 退出 `0` 代替完整断言通过。具体独立回读与计时边界见[安装权限验收证据](../runbooks/install-start-stop-runbook.md#installation-permission-evidence)。[SOURCE: docs/runbooks/install-start-stop-runbook.md#installation-permission-evidence]
- 相关[安装手册](../runbooks/install-start-stop-runbook.md#artifact-extraction-contract)与[升级手册](../runbooks/hermes-control-center-upgrade-runbook.md#procedure)按同一候选复核并重新封存。默认测试时限、安全检查、checker 和 CLI 合同不放宽；Mac 与生产机行为未验证。

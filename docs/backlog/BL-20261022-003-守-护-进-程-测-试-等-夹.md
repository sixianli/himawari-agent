# 守护进程测试等夹具就绪只用默认 1 秒

## Summary

test/integration/linux-host-guardian.test.ts 的 [R2-S4] reclaims a dead Host group before its parent reaps the zombie 用 expect.poll 等夹具写出 ready.json，没有指定超时，用的是 Vitest 默认的 1 秒。夹具要先起 Python 监管进程，再起 Node 子进程加载守护模块并启动守护进程；Hermes 上单独运行每次约 0.6 秒（夹具内部启动约 110-180 毫秒），2026-10-22 第 1、2 层 d55-l12-03 里 8 个集成文件并行、主机繁忙时超过 1 秒而失败，监管进程标准错误为空，失败时用例总耗时 1382 毫秒；同一最终代码单独连跑 5 次全部通过（d55-guardian-repeat-01）。这条用例不经过 job-host-main.ts，与 D-55 无关。修法要在“给就绪等待一个与夹具启动预算一致的明确上限”和“缩短夹具启动”之间选择，前者属于放宽测试时限，需按 AGENTS.md 的测试时限规则判断；如在候选的第 3 层或第 4 层再次出现，按缺陷立即处理。

- 修法（Claude 与 DeepSeek V4.1 Flash 独立方案对比后定，记录在 `.ci-output/handoff/2026-10-22-guardian-ready-oc-stop.md` 和提交说明）：监管进程读到 `ready.json` 后在标准输出写 `ready`，测试等这一行，不再轮询文件；监管进程或宿主在就绪前退出时立即失败（宿主提前退出报 `GUARDIAN_FIXTURE_HOST_EXITED:<退出码>`）；发出 kill 前确认宿主仍是同一个活进程，防止假通过。没有新增或改大任何时限数字；就绪等待的上限由原来无意中的 1 秒变为夹具自身已有的 20 秒保险，主机真卡住时失败会晚出现，但会带上夹具的错误输出。
- 验证：Hermes 上 12 个进程并行、连跑 3 轮制造负载，旧写法 36 次失败 34 次（全部在就绪轮询），新写法 36 次全过；故障注入（宿主立即以 3 退出）82 毫秒报出 `GUARDIAN_FIXTURE_HOST_EXITED:3`（`guardian-l0-stress-03`）。
- 仍有的同类风险（没有失败记录，这次没改）：同一用例里等宿主变僵尸、等代理进程消失、`reap` 后等进程组清空这三处仍用默认 1 秒；再在第 3、4 层出现时按同样思路改成事件或有依据的等待。

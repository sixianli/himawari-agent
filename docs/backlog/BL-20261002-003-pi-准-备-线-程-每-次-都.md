# Pi 准备线程每次重新加载模块：历史启动成本与预热修复

审阅导航：[实现前的事实](#实现前的已知与未知) · [旧失败与裁定](#hermes-旧失败与-reply-06-裁定) · [阶段诊断](#测试侧阶段诊断) · [Hermes 结论与用户决定](#2026-10-03-hermes-取证与用户决定) · [本批实现](#2026-10-03-预热一次性线程实现) · [本批测量](#2026-10-03-本批测量) · [排期](#排期)

## 期望结果

普通 `write/edit` 准备减少请求预算中用于加载 Pi 模块的时间。按用户 G26，服务预先加载一个一次性线程；请求到来时有已就绪且限额匹配的线程就使用它，否则立即冷启动。模块预热采用独立期限，原 10000ms 请求额度、资源上限、停止证明、授权和文件版本检查保留。

## 来源与现象

第二轮第 46 号答复要求测量 Pi 准备线程（`prepare-file-mutation` Worker，在独立线程里用 Pi 的编码工具计算文件修改结果）的启动时间。2026-10-02 在云服务器上，用当前源码的真实构建，从 `new Worker` 到收到 `started`，测得：

| 组 | 5 次结果（ms） | 中位数 |
| --- | --- | ---: |
| 冷启动（文件缓存为空） | 5751、6793、6057、5225、7351 | 6057 |
| 热启动（文件缓存已满） | 7348、3580、2668、3171、3610 | 3580 |

10 次结果都正确，但启动就占了预算的 36%–61%。

## 实现前的已知与未知

- **已确认（代码）**：
  - 计时器在 `new Worker` 返回后由 `awaitPiPreparationWorker` 设置，随后整个线程启动、模块加载和准备计算均消耗同一个预算：`packages/runtime-pi/src/prepare-file-mutation.ts:117-155`。
  - Worker 先静态导入 `prepare-file-mutation.ts`，后者导入 `@earendil-works/pi-ai` 和 Pi 编码工具，全部完成后才发 `started`：`prepare-file-mutation-worker.ts:1-6`。
  - 每次准备都新建 Worker；Worker 有独立的模块缓存，所以每次都重新加载这些模块。
- **已确认（2026-10-03 Hermes 运行）**：D16 四文件第 2 层中，`production-sandbox-lineage.test.ts` 的并发 write 和 edit 准备各失败一次，均由 `awaitPiPreparationWorker` 的计时器回调抛出 `PI_PREPARATION_TIME_LIMIT`。两例传入的 wall/CPU 预算均为 10000ms，未达到 Vitest 30000ms 测试超时；准确用例名、用时、运行模式和原始报告见[Hermes 旧失败与 reply-06 裁定](#hermes-旧失败与-reply-06-裁定)。该次命令已自然完成，没有修改 Pi 准备逻辑。
- **推断，未验证**：启动时间主要花在加载 Pi 模块上。上述 Hermes 失败没有各线程的分阶段时间，不能证明模块加载成本就是触发期限的原因；也不能用云服务器的历史测量代替 Hermes 测量。
- **未知**：
  - 具体是哪些模块最慢；
  - 历史 D2（Hermes 机械盘上的准备超时）和 stop-37（19 文件并发下的一次导入超时）是否由此引起；
  - Mac 上的情况（Mac 验证已无限期推迟）。

## 测试侧阶段诊断

`HIMAWARI_TEST_DIAGNOSTIC_OUTPUT` 有值时，`production-sandbox-lineage` 和 `prepared-file-runner` 使用[真实线程诊断包装](../../test/fixtures/pi-preparation-diagnostics.mjs)记录线程创建、`online`、预加载、首次模块加载、入口模块加载、入口正文、`ready`、输入交接、`started` 消息、结果和退出。源代码路径通过 Vitest 的模块替换保留原 `Worker`；已安装运行时路径通过测试子进程的 `--import` 预加载接入。开关关闭时使用原构造器和参数，不安装模块加载钩子，也不写诊断文件。诊断只观察实际构造和消息；预热实现的 `workerData` 仅含 `{ prewarm: true }`，请求内容只在输入交接时传入。诊断开关不改变产品的消息、资源限制和准备预算。

每个线程的阶段时间保存在独立共享内存中，用例结束或子进程正常退出后才保存为 `pi-preparation-*.json`。`rootLoadStart` 到 `body` 包含依赖加载、链接、求值和调度；`loadNanoseconds` 仅是模块加载钩子调用的累计墙钟时间，不是纯磁盘 IO。仍在执行的加载用 `activeLoadStart` 标记；线程被终止时累计值只是下界，不能把总时间减去它就称为求值时间。`snapshotStableAfterExit` 只表示内存已停止变化，不代表模块加载完成。缺少正文或 `started` 的记录保留缺失值；尚活着的线程保留部分记录，不能补成零耗时。原生子进程被信号或 OOM 杀死时退出钩子可能未保存，应结合父端状态说明诊断缺失。

同一开关还让 `sandbox-preparation-control` 记录真实 Job Host 的 fork、入口加载、入口正文、IPC 处理器注册、每条消息的序号和到达时间，以及 SDK 故障注入的位置。开关关闭时不安装这些阶段钩子，也不写诊断文件。诊断中的运行时根目录由实际 fork 入口推导；没有入口时保留空值。`artifactRequested` 只表示测试环境请求了产物，实际安装来源由独立的安装读回记录证明。这些记录不修改产品消息、心跳、准备上限或期限。

本轮的四文件对照另保留一秒一次的 `/proc` CPU、IO 和负载采样，以及 Vitest 主进程收到的文件执行事件。测试安装记录带文件路径、PID、`VITEST_WORKER_ID` 和 `VITEST_POOL_ID`，用于核对实际 worker。Reporter 的文件事件可能有批量传输延迟，进程名称中的 worker 数只作线索，二者都不能单独证明精确文件并发数。具体运行、原始报告和适用修订见[答复 05](../../.ci-output/handoff/2026-10-02-round2-claude-reply-05.md)。这些诊断只用于测量，不构成 D19 修复或平台验收。

## 方向

以下是实现前的取证步骤；Hermes 结论与用户 G26 已在后文记录：

1. 分别测量空 Worker 启动、只导入 `pi-ai`、只导入编码工具、完整入口的耗时，并做一次 CPU 剖析，找出最慢的模块；
2. 在真实的 10000ms 预算下，用单文件和原并发组合，观察是否实际出现 `PI_PREPARATION_TIME_LIMIT`；
3. 候选修法按 AGENTS.md 的 Pi 优先原则，先查 Pi 是否提供更窄的导入入口，再比较 Node 编译缓存、复用已加载的 Worker 等做法。改变预算或计时起点属于产品决定，要先问用户。

## 2026-10-03 Hermes 取证与用户决定

[停止文件 02](../../.ci-output/handoff/2026-10-03-codex-round2-hermes-stop-02.md#d19-数据) 在 Hermes 上测了 240 个分阶段 Worker，又在原并发组合下测了 283 个 Pi 准备线程，没有一个越过 10000ms。从创建到出结果，中位数约 1.4–1.7 秒，最长 2.59 秒，占预算的 14%–26%；从创建到 `started`，中位数约 1.35–1.39 秒，其中加载 Pi 编码工具约 1.17 秒。按 Node 编译缓存的方法只快了约 13%。在 Pi 0.84.2 现有的公开入口里，没有只加载 write/edit 的窄入口；用原文件位置做纯导入对照，加载时间能少大约一半，但要等上游正式公开这个入口、并升级 Pi 才能合法使用。云服务器上的历史测量（冷启动中位 6057ms）不能用 Hermes 结果代替；生产机不跑测试，修改后也只能在 Hermes 上验证。

**用户决定（2026-10-03，长任务 `goal.md` 的 G26）**：采用“预热一次性线程”。服务提前准备好已经加载完 Pi 的线程，请求到来时直接交给它，用完即销毁，再补一个。每个请求仍然是全新的线程，隔离方式不变。模块加载不再计入单次请求的 10000ms 预算，改由单独的预热期限约束；10000ms 预算本身和资源上限不变。空闲线程常驻会占用内存，具体大小在实现时测量并记录。

## 2026-10-03 预热一次性线程实现

本批按 [Claude reply-02](../../.ci-output/handoff/2026-10-03-round2-claude-reply-02.md) 实施候选 B。Agent Service 组装层仅在安装声明包含 `pi-coding-tool@3` 时创建一个未消费的预热线程；没有已就绪且四项 V8 限额匹配的线程时，请求立即冷启动，不排队。预热线程不接触请求数据，每个线程只接受一次 `input` 消息，第二份输入被拒绝。成功、失败、取消、超时后均终止线程并等待退出；消费后的补充及服务关闭也等待实际退出。

预热期限是 8000ms，从线程创建前的单调时钟开始计算，接收 `ready` 时再次检查期限，避免父线程计时器回调延迟让迟到线程进入可用状态。同一连续失败序列最多尝试三次，后两次分别退避 1000ms 和 2000ms。期限依据 stop-02 创建到结果的最大值 2593.830ms 留约三倍余量并向上取整；本批创建到 `ready` 的实测分布在下文记录。预热失败写 `pi.preparation.warmup_failed` 及稳定错误代码，后续请求仍可冷启动。

请求继续采用 `min(maxWallTimeMs, maxCpuTimeMs)`，常规 10000ms 额度不变。预热命中时在交接输入前设置请求计时器；冷启动时在 `new Worker` 返回后设置，继续包含模块加载。成功结果只有在 `terminate()` 完成且线程已退出、仍未超时或取消后才返回。线程空闲限额按 256 MiB 算为 old generation 192、young generation 32、code range 16、stack 16 MiB，`execArgv: []`；256 MiB 不是进程 RSS 的硬上限。

Pi 的工具参数规范化、参数校验、edit 匹配、BOM/换行处理和工具结果继续原样复用。Himawari 只负责不可变快照、授权和候选发布边界，以及本次修改的线程生命周期；未修改 Pi 版本、依赖声明、Agent-Worker 协议或 SQLite。完整行为见[架构说明](../architecture-v0.1.md#pi-file-preparation)，运行内存见[架构实测](../architecture-v0.1.md#pi-file-preparation-memory)。

## 机制证据与诊断范围

`confirmed`：原 [解包控制脚本](../../.ci-output/production/2026-10-07-first-deploy-packet-01/install/extract-node-modules.py)的第 18–19 行以 `r:gz` 打开并调用 `getmembers()`，先把归档扫描到结束。第 34 行再把全部成员按类型、目录深度和名称重排，第 39 行才对各普通文件调用 `extractfile()`。这种文件读取顺序与归档成员数据的偏移顺序不同。

该次实际 tar 有 `46470` 个成员、`41672` 次普通文件读取，按原顺序产生 `1211` 次逆向数据偏移变化。例如，读完 `node_modules/abort-controller/README.md` 的数据末端 `383239831` 后，下一项 `browser.js` 的数据偏移为 `383152128`。这些是实际归档偏移检查，不是系统调用耗时采样。

Root 已在 Hermes 只读核对当时系统 Python 的 `_compression.py:124–165` 和 `gzip.py:377/539`：向更早的解压数据位置 `seek` 时会 rewind，回到流起点再解压到目标。原脚本的读取顺序与上述真实逆向偏移足以说明重复解压机制。没有取得各次 rewind、磁盘读取、CPU 与其他等待在本次 `300000 ms` 中的精确耗时分摊，因此不把机制证据称为 syscall profile，也不把全部超时耗时都归给某一个系统调用。

本次读取时原解包脚本 SHA-256 为 `9819d48053893d884094bd14601f0aaea815785d10bc08a3c0f44b7dbd02fef2`；调用脚本 SHA-256 为 `0cb2146602a8e29eac685ee236bf1accdcbaa3c777690480e00990aeb5edee42`。调用方第 30–32 行保留 `300000 ms` 默认上限，第 59 行使用该上限调用系统 `/usr/bin/python3 -I` 解包；本次没有调大期限。

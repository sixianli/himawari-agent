# 限制 Worker 历史事件的内存与重复读取开销

## 期望结果

为长期运行的 Worker 建立有界的事件保留与增量读取机制，同时保留待交付结果、身份校验、原期限和不重新执行工具的约定。

## 来源与现象

来自 [reply-14 第 2 节](../../.ci-output/handoff/2026-09-28-round2-claude-reply-14.md) 的明确待办要求。TE-11 已用有界分页解决单次响应超过 65,536 字节而读不出来的问题；它没有解决历史事件持续占用内存，也没有解决每次调用从头读取历史的问题。关联[工具执行排查计划](../execution/plans/2026-09-28-tool-execution-audit-plan.md) [SOURCE: docs/execution/plans/2026-09-28-tool-execution-audit-plan.md]。

当前 `apps/execution-worker/src/production-execution-worker.ts` 的 `eventsByCursor`（第 177 行）仅追加，`events()`（第 293–303 行）从传入游标或数组开头复制并遍历历史；未找到删除或保留上限。`apps/agent-service/src/production-runtime-tools.ts:1417` 和 `packages/application/src/services/remote-execution-backend.ts:133` 在每次请求等待结果时把游标初始化为 `null`。同一次请求的轮询会推进游标，但下一次请求仍从头开始。

## 影响与证据边界

静态代码确认：事件占用随 Worker 生命周期累积；若每次调用产生近似固定数量事件，连续 N 次调用的累计历史读取量按 N 的平方增长。长期运行会增加内存、复制和传输开销。这里没有把静态复杂度分析冒充长期运行内存实测，也没有把 TE-11 的旧响应超限描述成分页后仍然存在。分页前连续调用约 28 次触发超限的现场见 [stop-13](../../.ci-output/handoff/2026-09-28-codex-round2-stop-13.md)，次数取决于输出大小。

## 可能方向与约束

可研究调用方从已知游标开始读取，以及按已确认消费的游标回收旧事件。需要单独设计并验证并发调用、Worker 重启、游标失效及尚未交付结果的保留规则，避免回收导致结果丢失。这里只记录方向，不决定新的协议或保留策略，不授权本批实现。

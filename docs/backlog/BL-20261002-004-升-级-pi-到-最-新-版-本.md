# 升级 Pi 到最新版本

## 期望结果

把 `packages/runtime-pi` 依赖的 Pi（Himawari 所基于的编码代理框架，来自上游 `pi-mono` 仓库）两个包 `@earendil-works/pi-ai` 和 `@earendil-works/pi-coding-agent`，从当前固定的 `0.84.2` 升级到最新发布版，依赖版本仍写成精确版本号；升级后第 0–3 层测试在 Hermes 上通过。

## 来源与现象

用户 2026-10-02 原话：“添加一个计划外代办：升级pi到最新版本。”

“计划外”指它不属于正在进行的第二轮工具执行排查，不放进那一轮的条目清单；什么时候做由用户决定。

2026-10-02 查询 npm 注册表的结果：

- 当前固定版本 `0.84.2`，发布于 2026-08-14。
- 最新版本 `1.0.0`，两个包都发布于 2026-10-01。
- 两者之间还有 11 个版本：`0.84.3`、`0.84.4`、`0.85.0`、`0.85.1`、`0.86.0`、`0.86.1`、`0.87.0`、`0.87.1`、`0.99.0`、`0.99.1`、`0.99.2`。跨过了大版本号 1.0，可能有不兼容的接口变化。
- 本机作为只读参考的 `pi-mono` 检出目前停在 `0.84.2`（提交 `a69bef789`），还没有 1.0.0 的源码。

## 升级时要遵守的规则

- 按 `AGENTS.md` 的 “Pi-First Development Principle”：先读 `0.84.2` 到最新版之间的更新说明和相关源码，列出 Himawari 用到的接口（模型连接、流式输出、Agent Loop、工具、会话、扩展）哪些有变化，再动代码；能直接用 Pi 新提供的能力替代 Himawari 自己写的部分时，优先改用。
- 按 “Workspace Contract”：直接依赖保持精确版本；只有 `packages/runtime-pi` 可以导入 `@earendil-works/pi-*`；提交的 `package.json` 和锁文件里用已发布的版本，不用本地链接。
- 读新版源码需要先更新本机的 `pi-mono` 检出（`git fetch` 和切换到新版标签）。这会改动那个只读参考目录，动手前先告诉用户。
- 改依赖清单和锁文件属于 `AGENTS.md` 规定要提前跑完整第 3 层的情况：这次改动单独跑一次构建加完整 `npm test`，在 Hermes 上运行。
- 升级会让当时所有已有的测试结果变成旧版本的结果。和第二轮排查同时进行时，要和第二轮的完整验证一起安排，避免重复跑完整测试。

## 要做的事

1. 更新本机 `pi-mono` 到最新发布版，阅读两个版本之间的更新说明和改动。
2. 列出影响 Himawari 的改动和对应的适配方案，需要产品取舍的交给用户决定。
3. 升级依赖、适配 `packages/runtime-pi`，同一提交更新受影响的文档（架构文档、相关 Spec 和 ADR）。
4. 在 Hermes 上跑第 0–3 层，通过后关闭本条。

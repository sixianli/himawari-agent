# 正式测试入口下三个 integration 测试仍读本地开发构建

## 期望结果

正式测试入口 `npm test`（`scripts/ci/local.mjs` → `build.mjs` → `test.mjs`）中，所有需要已构建运行时的 integration 测试，都使用本次构建并经过校验的产物，而不是仓库里可能过期的本地 `dist/node-runtime`。

## 来源与现象

第二轮修 D14（执行子进程夹具）时，`test/integration/execution-worker-process.test.ts` 改为沿用 `test/integration/prepared-file-runner.test.ts` 的现有做法：同时设置 `HIMAWARI_TEST_ARTIFACT` 和 `HIMAWARI_TEST_CONTEXT`（正式入口由 `scripts/ci/test.mjs` 传入）时，用 `scripts/install-node-runtime.mjs` 安装校验过的产物；两个都没有时才用本地 `dist/node-runtime`。

随后只读盘点发现，另有三个测试固定读本地构建，没有走产物安装路径：

- `test/integration/sandbox-preparation-control.test.ts`：从 `dist/node-runtime/node_modules` 启动真实 Job Host（替工具任务启动沙箱的子进程）；
- `test/integration/product-path-timing.test.ts`：从开发运行时准备清单，并在独立 Node 进程中导入模块；
- `test/integration/production-sandbox-lineage.test.ts`：目录移动分支调用开发构建的 `rename-native`。

正式构建把运行时输出到独立的工作目录，不会刷新 `dist/node-runtime`。

## 已知与未知

- **已确认（代码）**：上述三处在正式入口中仍读本地构建。
- **推断，未验证**：本地构建过期时，正式 `npm test` 可能通过了一个与当前源码不一致的运行时；在全新检出、没有本地构建的机器上，这三个测试可能直接失败。没有实际复现，也没有核对 GitHub CI 是否另有步骤生成该目录。
- 另三处（`production-copy-save`、`production-queued-run-restart`、`production-workspace-copy`）只在 `HIMAWARI_LIVE_SANDBOX_PROBE` 打开时使用运行时，并可由资格入口通过 `HIMAWARI_QUALIFY_INSTALLED_RUNTIME` 传入已安装的运行时，不在本条范围内。

## 方向

三处都照 `prepared-file-runner.test.ts` 的产物安装路径修改，不另造机制；每处先写能区分“用了产物”还是“用了本地构建”的读回检查。属于测试运行方式的改动，按 AGENTS.md 要提前跑第 3 层。

## 排期

第二轮“已发现缺陷全部修完”范围内，排在当前批次之后。

# 部署包冻结前自动检查跨步骤摘要和材料权限

## 期望结果

第四次及以后的部署包在冻结前由脚本自动完成三项检查，任何一项不满足就拒绝冻结：

1. 列出包内所有比较 `bindingSha256`、`bindingsSha256`、`freezeSha256` 的位置，并为每一处标明被比较的报告由哪一步、在哪个冻结下生成；修订版包按修订记录核对这些比较在续做时仍然成立。
2. 材料文件（例如 `materials/source-build-inputs.json`）里记录的文件权限不能有同组或其他人可写的位，生成材料的脚本检查 `umask` 为 `022`。
3. 修订版包的 Hermes 演练真实模拟“前面的步骤在旧冻结下完成 → 换成新冻结 → 后面的步骤继续”，并覆盖修订后第一个会读旧报告的步骤。

## 来源与已确认事实

2026-10-13 第三次部署在生产上连续三次在某一步第一次运行时失败，每次从诊断到重新上线约 1.5–2 小时（记录见 `.ci-output/handoff/2026-10-12-third-packet-progress.md`）：

- S5 第一次：同一进程加载新旧两份 `better-sqlite3`，第二份不认 URI 文件名；形状链把两个运行时合成一个，没测出来。
- S5 第二次：修订版 02 换了 `bindings.json`，`maintenance/run-maintenance.mjs` 拒绝 S3 在修订版 01 下生成的报告（`THIRD_MAINTENANCE_RECOVERY_BINDING_CHANGED`）。
- S6：候选包构建源码的 619 个文件权限是 `664`，`acceptance/cloud/finalize-cloud-inputs.py` 以 `PUBLIC_FILE_UNSAFE` 拒绝 `package-lock.json`。

对应的代理行为规则见 [编码代理反复犯的错误](../lessons.md)。

## 后续验收边界

检查脚本本身要有夹具：故意放一个摘要比较不成立的修订、一个 `664` 的材料记录，确认冻结被拒绝；正常包冻结成功。第三次部署已在进行中的处理不在本项范围内。

# 后台和服务模式的 bash 失败处理与前台对齐

## Summary

R2-T14（2026-10-16）只改了前台 bash：命令失败、超时、超过命令输出上限或输出含机器秘密时，模型能看到有界的输出结尾和“效果未核实”的提醒。后台和服务模式（runner 输入里的 executionMode 不是 foreground）没有改。现行生产绑定没有声明 background/task_start 或 service/service_start，模型发起的调用到不了这两种模式（apps/agent-service/src/production-runtime-tools.ts 只在有任务句柄时注册 execution_task_start），所以现在不影响用户。将来要启用后台或服务绑定之前，先处理三处与前台不一致的地方：一是 apps/agent-service/src/capability-programs/pi-coding-main.ts 的 streamOutput 每收到一段就对累计全文做机密扫描，命中即整个任务以 PI_RESULT_SECRET_REJECTED 失败，命令真实的退出码丢失；二是累计输出超过单次结果上限 maxOutputBytes（生产 48 KiB）就以 PI_RESULT_OUTPUT_LIMIT 结束命令，而前台的结束门槛是它的 64 倍；三是模型通过 execution_task_output（apps/agent-service/src/production-managed-tasks.ts）读到的结果没有“命令可能已改动工作区、效果尚未核实，请先检查工作区”的提醒。

## Origin

- 来自第二轮长任务条目 R2-T14 的方案比较：Claude 和 DeepSeek 各自读代码，都得出“现行配置下模型调不到后台和服务模式”的结论，因此 R2-T14 只改前台，这里记下剩下的部分。前台的做法见 [SRT 统一执行设计的 R5 实现说明](https://github.com/sixianli/himawari-agent/blob/208007462f99e16c5c8cd4daac2acc10fa9f5f36/docs/execution/specs/2026-09-07-srt-unified-execution-design.md#r5-实现说明2026-09-09) 和 [BL-20261015-001](BL-20261015-001-bash-非-零-退-出-时-把-输.md)。

## Notes

- 上面三处都是读代码得出的，没有在后台或服务模式下实际运行核实。开始处理时先在测试主机上声明一个后台绑定，复现这三种情况。
- 对齐时沿用前台已有的做法：机密扫描和截断放在 runner 写出结果之前，命中秘密时交出一份不含正文的结果并保留命令真实的退出码，失败时附上“效果未核实”的提醒。

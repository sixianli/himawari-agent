# 资源观察器按 ps 整秒计 CPU 时间，1 秒以下的 CPU 上限要用满 1 秒才会触发

## Summary

packages/runtime-sandbox 的资源观察器（resource-observer.ts，定时采样任务进程用量）用 /bin/ps -axo pid=,ppid=,pgid=,rss=,time=,lstart= 读 CPU 时间，time= 字段只到秒，所以记到的 CPU 时间不是 0 就是整千毫秒。后果：配置成 100 ms 这类 1 秒以下的 CPU 上限时，任务要实际用满 1 秒 CPU 才会被判超限，超出幅度可达十倍；在慢机器或有负载时，一个忙等几秒的进程可能分不到 1 秒 CPU，于是根本不触发。2026-10-24 01:50 Hermes 慢速验收（0 号 CPU 加一个占满进程）在授权网络探针 cpu 场景就这样失败，见 .agents/tasks/round2-tool-execution/plan.md 意外和发现一节。正式配置的 CPU 上限远大于 1 秒，不影响第六次上线。要做的：改读 /proc/<pid>/stat 的 utime 和 stime（按 CLK_TCK，通常 10 ms 精度）或 cgroup 的 cpu.stat usage_usec，并让 1 秒以下的上限有能重复运行的测试。

- 2026-10-24（R2-D31）：同一个观察器在生产机负载下还有第二个问题：`ps` 超时只有 1 秒，超时就以宿主故障停止任务且不发诊断，第六次 revision-06 的 S6_READ 因此失败。R2-D31 把超时改为 5 秒、连续 10 秒拿不到快照才停止、停止前发 `JOB_HOST_RESOURCE_OBSERVATION_FAILED` 诊断（见[沙箱准备控制与恢复设计的第六轮](https://github.com/sixianli/himawari-agent/blob/208007462f99e16c5c8cd4daac2acc10fa9f5f36/docs/execution/specs/2026-09-28-sandbox-preparation-control-recovery-design.md#resource-observation-grace)）。本条记的精度问题没有一起改。
- 一并记下替代方案：Linux 上直接读 `/proc/<pid>/stat`（内核暴露的进程统计文件，CPU 时间精度为时钟滴答，通常 10 ms），不再每 100 ms 启动一个 `ps` 进程，可同时解决本条的精度问题和 R2-D31 的慢 `ps` 问题；macOS 保留 `ps`。代价是平台分叉和更大的测试面，所以没有在上线前做。

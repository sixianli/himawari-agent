# 首次生产验收缺少未知占用与真实进程重启恢复的证据合同

## 摘要

G51要求清理状态不确定时保持工作区占用和重启后恢复，但现有安装composition探针在Linux只证明资源released/confirmed并允许竞争者，同进程重新构造Worker不能证明数据库经过真实进程重启后的恢复。历史签署启动脚本仍声明unknown_quarantine和restart_reconciliation；冻结云首次部署清单前须补齐可靠的有限验收证据，禁止用保证名称替代运行证据。

## 发现来源

执行云首次部署清单原简报与 Claude reply-01 时，由 `acceptance_contract` 子代理核查，主代理直接阅读相关源码后确认。

## 来源与已确认的证据

- [SOURCE: docs/adr/0050-hermes-root-disk-cleanup-without-floor.md#first-install-acceptance]：本次首次生产安装必须验收状态不确定时保持工作区占用与重启后恢复；全部检查实际满足后才能签署。
- [SOURCE: docs/runbooks/install-start-stop-runbook.md#scope]：当前安装探针不证明实际进程崩溃后的安装恢复。
- `scripts/operations/hermes-search-time-seal.mjs:54–59` 对 composition 报告只要求成功、runtime 路径匹配、清理确认和未重放。
- `test/qualification/sandbox-production-mac-probe.ts:445–505` 在 Linux 断言业务结果未知而资源已 `released/confirmed`，随后 `workspaceBlocked=false` 并允许竞争者预约。这没有覆盖清理证据不确定时的持续占用。
- 同一探针 `549–558` 在同一进程和同一 repository 内构造新的 Worker，没有结束原 Agent/Worker 进程、以新 boot 身份启动或重开数据库。这证明同进程重复调用没有重放，不能证明真实进程重启恢复。
- `scripts/operations/hermes-protected-start.mjs:85–96` 仍声明 `unknown_quarantine` 和 `restart_reconciliation`。保证名称不能替代缺失的验收证据。
- [P8 合同核查稿](../../.ci-output/production/2026-10-07-first-deploy-packet-01/acceptance/P8-contract-audit.md) 保存完整证据链、其它已存在探针、实际安装及工作区身份绑定合同。

## 期望结果与验证边界

找到已有且足以覆盖两项要求的有限安装探针，或另行批准准备这两项探针：通过真实新进程、新 boot 和重开的临时数据库，独立读回清理不确定的工作区占用与原作业；检查新请求被拒绝，旧工具没有重放；取得可信释放证据后再检查原占用释放。先在 Hermes 验证适配，再冻结云端操作清单。保留 G51 的账号、虚构工作区、临时状态、自有进程、范围、资源与时限限制。

当前结论是 `confirmed` 的验收合同缺口，不是已经复现的产品恢复缺陷。原简报禁止本轮修改产品、运行新的验收入口或连接生产云服务器。故本轮仅记录证据并停止，不用减去保证、填写合格字段、复制 Hermes 证明或扩大云端测试来消除缺口。下一步由 Claude 审核诊断并确定有限探针的准备及 Hermes 验证范围。

## Claude reply-05 后两组与冻结前门槛失败

[reply-05](../../.ci-output/handoff/2026-10-07-codex-round2-cloud-packet-claude-reply-05.md)批准探针调用安装包的 `initializeStateRoot(stateRoot)` 取得完整布局，并在控制器 `close` 后才拒绝尚无回复的请求。它允许修正本批探针自身的错误后再跑新的一组完整三次，但禁止改产品、门槛、期限或验收断言；实验门槛未达到时必须停止。

第 2 组固定代码三次均失败于探针误读 HTTP 回执字段。候选已经通过真实内置账号密码登录、二步验证、cookie/CSRF 和受保护文本写入，Thread 创建也返回 200；探针却把持久化 `commandId` 当成本次消息 ID。修正为读取产品 `causationId` 并核对 `correlationId`，保留原请求 ID 期望、schema 和其余回执检查。三份失败证据为 `E20261007T200508-580872`、`E20261007T200508-a887ed`、`E20261007T200508-a2ef38`。

第 3 组固定代码三次均已提交真实根 Run，取得准入及调用回执，启动真实 Job Host 和 Bash，并生成预期私有 marker。冻结前观察年龄分别为 976、1043、899 ms，超过原 250 ms 门槛；剩余期限分别为 279467、284053、283799 ms，符合至少 1500 ms 的要求。探针在发送控制器冻结请求前失败，未发送 SIGSTOP/SIGKILL，未重启进程或重开数据库；冻结耗时没有实测值。三份证据为 `E20261007T201256-0ff284`、`E20261007T201256-d8e2d3`、`E20261007T201256-1c5c58`。

门槛失败是已确认的实验结果，不能据此认定产品恢复存在缺陷。未知占用、重启恢复、不重放与重启后的可信释放仍未验证。全部命令自然结束，报告和源码补丁保留；临时安装、scratch、本轮输出和新建的 Vitest 缓存均已删除，独立读回自有进程及任务树为空。按裁定停止，没有第四组或 R2-L4 清单推进；本条保持 `open`。[stop-06](../../.ci-output/handoff/2026-10-07-codex-round2-cloud-packet-stop-06.md)列出每组失败、修正、门槛实测、源码依据、磁盘差额和下一项审核建议。

## Claude reply-06 的直接证据要求

[reply-06](../../.ci-output/handoff/2026-10-07-codex-round2-cloud-packet-claude-reply-06.md)取消设计自定的“冻结前观察年龄 ≤250 ms”门槛。Worker 每轮先等待 250 ms，再执行 RPC、刷新和观察确认，观察间隔大于 250 ms；探针还要通过 CLI 读取并解密诊断。这不是 G51 或产品规定的新鲜度保证，观察年龄继续记录为实测值，注明不再作门槛。

替代检查保留原运行观察、`taskStarted` 和认证启动身份的匹配，并直接验证冻结时的事实：控制器在第一个 SIGSTOP 前，用 pidfd 和 `/proc` 核对原 Host 与登记过的 Bash 的 PID、启动时间、UID、可执行文件、参数和父子关系，确认存活；直接读回 marker 内容、inode 等文件身份没有改变。Worker 和 Host 的 SIGSTOP 到状态 `T` 读回仍须不超过 250 ms，冻结确认时剩余期限仍须至少 1500 ms。

冻结确认后、SIGKILL 前，再用产品现有 audit/diagnose 读回原作业仍为 `bound/controlled`、有效占用、无释放回执、未读到 `finished` 终态或结果；新增原作业观察只能为 `running`。诊断解密失败不能当作“没有终态”。探针另检查认证启动文件同目录中没有 `final.json`，只记录文件是否存在，不读取控制 token。以上直接进程、文件与产品读回须全部通过，才能进入真实结束进程和重启步骤。

每次修正仍按 reply-05 跑新的一组完整三次，只认最后一组三次全部通过。前三组失败原件继续保留。控制器冻结耗时或剩余期限未达、产品缺陷、批准方法不通等停止条件不变；四小时预算从 reply-06 重新计算。预加载诊断模块与常驻取证进程未获批准，本探针继续复用原 audit/diagnose 命令。本条保持 `open`，通过 Hermes 验证并纳入 P8 后才关闭。

## 第四组结果与旧 Agent 租约的重启前提

第四组固定代码三次均完成冻结前进程与 marker 检查、冻结后的产品读回，以及旧 Agent/Worker 的真实 SIGKILL 和 pidfd 退出确认。冻结耗时依次为 0.605016、0.638130、0.611350 ms；冻结确认时剩余期限为 284281.411、282793.836、284616.641 ms，两项门槛均通过。观察年龄为 409.979、203.521、220.744 ms，只记录实测值。三次新 Agent 均以 `PORT_CONFLICT` 退出，未进入未知占用与恢复验收；证据为 `E20261007T210707-47ec4f`、`E20261007T210707-509229`、`E20261007T210707-176919`。原始报告保留失败，不以随后清理完成改写其验收结果，见[第四组证据目录](../../.ci-output/tool-execution-audit/2026-09-28/round2/hermes-r67/l6/group-04/)。

源码确认旧 Agent 的生产权限租约固定为 30000 ms，按 10000 ms 周期续租；SIGKILL 不执行正常退出时的租约释放。持久化租约仍有效时，新 Agent 在 HTTP 启动前申请同一权限会遇到 `PORT_CONFLICT`。现有探针漏了这一重启前提；该错误码还有其它来源，日志没有完整异常堆栈，故这三次错误的唯一运行时抛出位置尚未确定，不能据此宣布产品恢复缺陷。

下一组探针在 pidfd 确认旧 Agent 已退出后，从冻结候选内读取并核对原租约常量及文件摘要，再等待单调时钟和 UTC 均经过该 30000 ms 上界，才启动一次新服务对。推导前提是旧 Agent 已退出、没有其它写入方续租，以及从最后续租到新申请期间 UTC 不回退；报告显式记录这些前提。它不是实际租约行的读回，不引入 SQL、数据库写入方、产品接口或启动重试。原 60 秒阶段期限、540 秒探针期限和 600000 ms describe 期限不变。

第四组清理报告还保存了初次进程快照，稍后独立读回对应身份和任务树均已消失。下一组在原清理轮询预算的余额内，同时重新读取自有进程和产品任务树；初次快照与每次后续读回均保留，控制器错误也不能被后续空列表覆盖。清理真实完成后才删除任务自有临时根；报告、日志、读回及失败源码继续保留。

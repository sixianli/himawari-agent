# 记忆清单写法实测（2026-11-24）

记忆清单是新对话开头放给模型的一段文字，每条记忆一行，让 Himawari 知道自己记着什么（方案见 [记忆系统重新设计](../../../docs/execution/specs/2026-11-24-memory-redesign-design.md) 第 2 步）。Andy 要求用数据证明哪种写法最好。本目录是这次实测的脚本和原始数据。

结论：**类别名单独一行，下面每条写“编号紧贴内容”，内容以数字开头时才在编号后加一个空格**（下表的 `tight_guarded`）。Andy 2026-11-24 22:08 JST 按这组数据拍板采用。

## 怎么测的

- 模型：生产用的 DeepSeek V4.1 Flash，经 OpenCode Go 套餐调用（Andy 定的评测用法，不走 Vercel）。
- token 数：把清单发给模型，读接口返回的 `usage.prompt_tokens`，减去只发一个字时的基数。是模型实际计费的数，不是估算。
- 读懂率：清单放在系统提示后面，问 40 道题（37 道有答案，3 道清单里没有答案，比如“血型”），要她只回“能回答这题的记忆编号”。编号和标准答案完全一致算全对；“列出所有关于 Mika 的记忆”可以多带一条提到 Mika 的待确认记忆。
- 两份清单：`memories.tsv` 是 100 条模拟记忆；`memories-1000.tsv` 在它的基础上加了 900 条干扰记忆（由 `gen_distractors.py` 让 DeepSeek 生成、`build_large.py` 合并，剔除了和标准答案矛盾的 4 条，见 `excluded-distractors.tsv`）。
- 不开思考（模型直接回答）每种写法 2～3 遍；开思考（模型先在内部推理再回答）每种 1 遍。1000 条的开思考那遍跑完 json、markdown 两种和 tsv 的 28 题后，Andy 说不用再跑，停了。

## 结果

1000 条清单：

| 写法 | 每条 token | 不开思考全对 |
|---|---|---|
| `json` 一条一行 JSON | 30.4 | 80/80 |
| `markdown` “## 类别” + “- #编号 内容” | 17.3 | 80/80 |
| `tsv` 编号⇥类别⇥内容 | 17.6 | 80/80 |
| `space` 类别一行 + “编号 内容” | 15.3 | 80/80 |
| `flat_space` 不写类别，“编号 内容” | 15.2 | 77/80 |
| **`tight_guarded` 类别一行 + 编号紧贴内容（数字开头才空格）** | **14.7** | **80/80** |
| `tight_raw` 类别一行 + 编号紧贴内容（一律不空格） | 14.5 | 80/80 |
| 只放内容（对照，没编号没法用） | 12.9 | 无 |

100 条清单：每条 token 依次是 24.6、12.9、12.5、10.6、10.4、9.7、9.7，内容本身 8.5；不开思考 3 遍除 `flat_space` 119/120 外都是 120/120，开思考 1 遍全部 40/40。

编号的写法（1000 条，都用 `space` 写法量）：

| 编号 | 每条 token |
|---|---|
| 库里现在的编号原样放（`记忆:` 加一串随机 UUID） | 38.2 |
| 稳定的短数字（3～4 位） | 15.3 |
| 每份清单从 1 重新编号 | 14.6 |

## 读出来的结论

1. 读懂率各写法打平，所以按 token 选。`tight_guarded` 比 JSON 省一半多，比 Markdown 省 15%。
2. 类别不能省：`flat_space` 丢的 3 题全是“哪些记忆还没经主人确认”，因为“待确认”只写在类别里。
3. `tight_raw` 每条只再省 0.16 个 token，但编号 8 加内容“1998年出生”会写成“81998年出生”，人和模型都可能读错，所以不用。
4. 编号用稳定的短数字，不用库里的 UUID（贵 2.6 倍），也不每份清单重新编号（只省 0.7 个 token，但压缩重建清单后，对话历史里提到的旧编号会指向别的记忆）。

## 文件

- `formats.py` 七种写法；`count_tokens.py`、`count_tokens_lib.py` 量 token；`id_tokens.py` 量编号写法。

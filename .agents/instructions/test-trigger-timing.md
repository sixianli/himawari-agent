# Test Trigger Timing

While `DELIVERY_MODE` says `fast`, [Delivery Mode](delivery-mode.md#fast-mode) replaces Layers 0-4 and the `Layer-0-tests:` lines below with its basic checks.

The current rules are in [ADR 0057](../../docs/adr/0057-batch-layers-one-two-for-small-defects.md#batch-layers). Run each layer on the host given in [Test and Production Hosts](test-and-production-hosts.md). These rules take precedence over any per-defect full-test requirement in task briefs written before 2026-09-29.

- Layer 0, targeted tests (the reproducing test and directly related test files): run before changing production code to show the failure, then after every change. The directly related files are at least every file `python3 "$(git rev-parse --git-common-dir)/hooks/check-layer0-tests.py" derive` lists for the change (add files, never drop one); a commit that changes product source under `apps/*/src/` or `packages/*/src/` declares each Layer 0 file on its own `Layer-0-tests: <path>` line, or `Layer-0-tests: none` when nothing is listed, and the shared `commit-msg` and `pre-push` hooks refuse it otherwise. Merge commits are skipped by the hooks (they print `L0_RELATED_TESTS_SKIPPED_MERGE`); a merge whose conflict resolution changes product source still carries the declaration lines, checked in review ([ADR 0066](../../docs/adr/0066-layer0-related-tests-declared.md)).
- Layer 1, `npm run check`: before every commit; for a delivery batch of independent defects, once on the top of the stacked batch (see Layer 2).
- Layer 2, affected-module tests (the whole Vitest project containing the change, such as `unit`, plus integration test files that exercise the changed modules): when a defect or feature is stable and about to be committed. Each independent defect is still committed separately after its own Layer 0 run. When a delivery batch holds more than one independent defect, Layers 1-2 run once on the top of the fully stacked batch, and the defects are then committed in order; if Layers 1-2 fail, return to the failing defect's Layer 0, fix it, and rerun Layers 1-2 on the new top. Each commit message names the revision Layers 1-2 ran on and says the commit itself did not run them alone. A batch of one defect or feature runs Layers 1-2 before its commit.
- Layer 3, build plus the full `npm test`: once per delivery batch (a group of changes handed over together for review or acceptance, normally no more than three independent defects), before opening a PR or merging, and at the end of a work round. Run it for the individual change instead when it touches the SQLite schema or migrations, the Agent-Worker protocol, authentication, or handshake, build or packaging configuration, dependency manifests or lockfiles, or the test runner itself (Vitest configuration, `ci/policy.json`, and the `scripts/ci/` files that decide how tests are collected, started, run in parallel, or judged; the list is in [ADR 0064](../../docs/adr/0064-layer3-individual-trigger-scope.md)). A `scripts/ci/` script that only runs in a check step (for example `check-policy.mjs`) gets `local.mjs --check <that check>` plus the whole `tooling` project instead, and the full Layer 3 waits for the batch (ADR 0064, G151).
- Finish Layers 0-2 and a self-review before starting Layer 3. If Layer 3 fails, return to Layer 0, fix, pass Layers 0-2, then rerun Layer 3 once on the batch's final revision.
- Layer 4, the real product path (Linux on Hermes, installed under the test account's own directories; Mac only under the approval rule in [Test and Production Hosts](test-and-production-hosts.md)): run only the affected scenarios when a change affects installation, upgrade, process management, or sandbox runtime behavior; run the unfiltered qualification only at the end of a work round or before a release.
- Layer 5, production deployment to `84.247.157.41`: only with the user's explicit authorization for each deployment.
- Documentation-only changes run documentation validation and Runbook checks only.
- Reuse passing results while code, dependencies, test configuration, and relevant environment are unchanged. Commit messages and delivery reports must state which layers actually ran and which revision the full test covered; never describe an intermediate commit as fully tested when it was not.
- These rules govern development testing only. The required GitHub CI checks in `ci/policy.json` are unchanged, although GitHub Actions is turned off while [ADR 0092](../../docs/adr/0092-pause-github-actions.md) holds.
- Before adding a test, answer the six test-value questions; keep tests within the speed and isolation budgets; storage, recovery, and model-facing changes carry the tests [ADR 0063](../../docs/adr/0063-test-value-gate-speed-budget-hygiene.md) names; the rules themselves are the `verification-discipline` skill's, and the hygiene gate is Backlog BL-20261021-001.

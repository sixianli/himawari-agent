# 和 OpenCode 协作：方案讨论和代码复核

默认只用 `opencode-go/deepseek-v4.1-flash` 一个模型，推理强度设为高；方案讨论、核对代码说法和代码复核的每一轮都是这样（Andy 2026-11-12 定，原话“除非我特别指明，否则现在默认只让 DeepSeek 去审”，[ADR 0259](../../docs/adr/0259-review-models-default-to-deepseek.md)）。Andy 特别指明时才加上 `opencode-go/glm-5.3-flash`：传 `--models deepseek-v4.1-flash,glm-5.3-flash`。能用的只有这两个模型（Andy 在项目指令第 17 条规定）。能用哪些、默认跑哪些、谁替补谁，都写在 `scripts/model-review/review-models.json`（`allowed`、`default`、`substitutes`），脚本启动时读它并校验（默认和替补都必须在能用的清单里，否则以 `REVIEW_MODELS_CONFIG_INVALID` 停下）；要改默认，改这个文件的 `default`，不改脚本，同时把测试里按现在的默认值（只有 DeepSeek）写的断言一起改（`test/tooling/opencode-review.test.mjs`、`test/tooling/opencode-review-merge-gate.test.mjs` 里对 `DEFAULT_REVIEW_MODELS` 的断言，和 `test/tooling/plan-claims-gate.test.mjs` 里默认只跑 DeepSeek 的断言，改了默认它们会失败，提醒你核对）；改 `substitutes` 会让旧账本里的替补轮次按新的对应关系重新判断，只会更严；`allowed` 里的每个模型还要在脚本里有固定侧重（`MODEL_LENSES`）和输出上限（`MODEL_OUTPUT_LIMITS`），在 `gateway.json` 里有条目，所以往 `allowed` 加模型不是只改这个文件就行（有测试核对现有的每个模型三样都有）。下文说“模型”指这一次跑的模型：默认是 DeepSeek 一个，指明两个时是两个。一律用 `node scripts/model-review/opencode-review.mjs` 跑（见[怎么跑](#how-to-run)）。交给它们的材料只讲问题、目标、约束和已核对的事实，不预设结论，脚本会自动加上项目指令第 16 条的原话：列出的方案只是参考，请从问题本身出发，提出你认为更好的方案。

<a id="plan-discussion"></a>
## 写代码之前：方案讨论

动手写代码之前要出方案的任务都走这三步；项目规则里的大改动（见[修 bug 和做新功能](../../.claude/rules/owner-standing-rules.md#fixing-bugs-and-new-features)）一定要走。修小 bug 不用。

1. 独立出方案（`--mode plan`）：线程先把自己的方案写好存着，不给模型看。材料只写问题、目标、约束、已核对的事实和查到的一手资料，不写线程的方案或倾向。模型自己读代码、上网搜索，出一套方案（指明两个模型时各出一套）。
2. 审核线程的方案（`--mode plan-review`）：把线程的方案发给模型，请它找漏掉的场景、判断错的地方、和业界成熟做法不一致的地方。先独立、后审核，是为了不让模型顺着线程的思路走。
3. 线程整合：线程把模型的方案、审核意见和自己的方案逐条比较，自己先判断每一条采纳还是不采纳、为什么、最后建议怎么做，线程自己的方案也一样要过这一遍。交给 Andy 的是一份整合后的方案：开头按[方案的前提](../../.claude/rules/proposal-premises.md)列前提和来源，然后是方案，最后只列真正需要他拍板的几项取舍。各方的原始方案和逐条判断作为附件，不要求 Andy 逐条看。Andy 同意后才写代码。

<a id="plan-claims"></a>
## 方案交给 Andy 之前：核对代码说法

起因：线程整合两个模型的意见时，把其中对代码行为的说法写进了方案和 ADR 0242，没有自己打开代码核对，三次都是这样（[审核时直接采信代理自报的检查结果](../../docs/lessons.md#trust-reported-checks)）。按[事故和反复犯的错误](../../.claude/rules/incident-gates.md#what-counts)，第三次要上硬门槛：整合后的方案里每一句讲代码或仓库文档现状的话，都由低价模型对着代码核一遍，没核过的 ADR 不让合并。

1. 方案要放在仓库里并提交（例如新 ADR 的草稿 `docs/adr/NNNN-….md`）；放在仓库外的整合方案，先提交成分支里的文件再核。
2. 运行：`node scripts/model-review/opencode-review.mjs --mode plan-claims --head <提交> --topic <短名> --claims-file <方案文件的仓库路径> --gateway magpie`。不传 `--brief`：脚本直接读 `--head` 那个提交里的文件，所以核的就是提交过的内容。默认只跑 DeepSeek，Andy 指明两个模型都跑时加 `--models`；只用这两个模型，经 Magpie；不上网、只读代码；提示里不放代码复核的必答问题（它只核事实，不评方案）。记录写进这件事的方案讨论记录目录 `.agents/reviews/topic-<短名>/round-<序号>/`，用量进同一份 `usage.jsonl`。核对的先问线是 1 美元（Andy 2026-11-14 同意，见[钱和模型](../../.claude/rules/owner-standing-rules.md#money-and-models)），算的是这份账本里已花的全部，包括同一件方案前面的方案讨论，再加上别的 `topic-*` 账本里核对同一个方案文件（`--claims-file` 相同）的花费，换个题目名不会重新从零算（`--approved-usd` 照旧）。
3. 模型把每一句现状说法单独列成一行：`CLAIM|<序号>|<一致、不一致 或 找不到>|<文件:行>|<方案原句>|<代码原文>`。脚本跑完打印 `CLAIMS_SUMMARY`（总数、一致数、有问题数）和每条 `CLAIMS_FLAGGED`；答案里一条 CLAIM 都解析不出来，或有格式坏了的行，打印 `CLAIMS_PARSE_FAILED`，退出码 4，不算核过。序号只要求不重复（提示里要求用 1、2、3……，脚本不检查是否连续）。方案原句里的竖线要换成全角“｜”（提示里已经这样要求）；只有“代码原文”这一栏允许出现竖线。
4. 线程逐条处理“不一致”和“找不到”：自己打开代码看。
   - 方案写错了：改方案，提交，对改后的内容重新跑一次，直到这一轮没有“不一致”和“找不到”，或剩下的都是模型看错的。旧的记录留着。
   - 模型看错了：在这一轮目录里的 `claims-verdicts.jsonl` 加一行 JSON：`{"id":"<序号>","model":"<模型全名>","quote":"<答案里那条 CLAIM 行，逐字>","outcome":"model-wrong","evidenceFile":"<仓库里的文件路径>","evidence":"<那个文件里逐字存在的代码原文，不少于 8 个字符>"}`。改了方案的记 `"outcome":"plan-fixed"` 加 `"change":"<改了什么>"`，只当备忘；它不能让“当前内容那一轮”里的条目过关，因为那一轮核的已经是改后的内容。同一个模型的同一个序号只写一行，写了两行整份文件作废（`claims-verdicts-invalid`）。
5. 合并检查（`--assert-reviewed`）：PR 相对 `--main-ref`（默认 `origin/main`）新增了 `docs/adr/NNNN-*.md` 时，对每个新增的 ADR 要求：
   - 有一条 `plan-claims` 记录，记的文件路径和内容摘要（SHA-256）与 HEAD 里这个 ADR 的当前内容一致；内容改过一个字节就不一致，报 `claims-stale`，必须对新内容重核；根本没有记录报 `claims-unchecked`。这样定的原因：核对对象是“交给人看的那份文字”，改一句就可能改变一条说法的真假；单次约 0.1 美元，比漏掉错误便宜。
   - 同一内容（摘要一致）的每个轮次里、每个模型最后一次有结果的运行都要过关，不是只看最后一轮：前面某一轮标出了“不一致”或“找不到”，哪怕后来重跑换出了全一致的结果，那一轮的条目也还要有 `model-wrong` 判断。所以不能靠重跑到碰巧全一致来蒙混。这个内容没有任何一轮里有模型 `ok`，报 `claims-run-failed`（失败的运行不用判断，也不算数）；答案文件缺失 `claims-answer-missing`；一行都解析不出 `claims-none`；格式坏了或序号重复 `claims-answer-invalid`。
   - 每一条（含“一致”）的“文件:行”都要在 HEAD 里存在、行号不超出文件，代码原文逐字（空白不计，可用 `…` 省略中间；模型把几处原文用全角分号“；”连在一起写时，整段找不到就按分号拆开，每一段都要在文件里，而且先后顺序和文件里一致；引文里同时用了 `…` 的，和只用 `…` 时一样不查先后）出现在那个文件里，否则报 `claims-evidence <ADR> <模型> <序号> <原因>`：模型没读到代码、整段编出来的引文过不了；把文件里真有的几段拼在一起的引文仍能通过（用 `…` 省略中间时不查先后）。核对用的是 HEAD 里的文件：引用的那几行后来被改掉、不再逐字存在，就要重核；但行还在、周围的代码改了意思时，脚本发现不了。每个引文片段至少 4 个字符，行号从 1 起。
   - 每条“不一致”和“找不到”都要有 `model-wrong` 判断，且 `evidence` 真的是 `evidenceFile` 里的原文、`quote` 真的是答案里的原文，否则报 `claims-unjudged` 或 `claims-verdict-evidence`、`claims-verdict-quote`。
   - 这一步用到的记录文件（对这个 ADR 跑过的所有 `plan-claims` 轮次的目录和那份 `usage.jsonl`）不算“PR 自己的未复核改动”，所以补记录不必为此再复核一轮；它们照样做像密钥的文字检查。
   - 文件名里含字母、数字、`._/-` 以外的字符（空格、控制字符、全角标点、emoji 等），或者长得像密钥的文字（记录会被遮盖）的新增 ADR 没法传给 `--claims-file`，报 `claims-name-unsupported`；改个名字。
   - 不改代码、不新增 ADR 的 PR，和只修改已有 ADR 的 PR，都不要这一步。
   - 模型答案里的“文件:行”可以写成 `文件:行@完整提交哈希`，专门给讲“原来”“已删除”的旧代码用：提交必须是 40 或 64 位十六进制，并且是当前提交的祖先，同时是本 PR 现在与 `--main-ref` 的共同祖先（基线）、跑 `plan-claims` 那次的提交与 `--main-ref` 的共同祖先（账本里那条记录的 `head`，所以之后把 main 合进分支，旧基线照样认），或是 PR 自己的提交；代码原文取自那个提交里的文件；而且当前提交里已经没有这段原文（同一个文件里没有，那个提交到当前提交之间新增、改动或改名的文件里也没有，不看 `docs/adr/` 下的 ADR，最多看 400 个文件，超过 400 个、`git diff` 失败都没法核对，报 `commit-quote-check-incomplete`；代码只是挪了地方也算还在），否则报 `commit-quote-still-in-head`（讲现状的句子必须用当前提交），提交不在范围内报 `commit-not-in-pr`。跑 `plan-claims` 时脚本在材料里写明基线提交（按 `origin/main` 算；`plan-claims` 不接受 `--main-ref`，合并检查用别的 `--main-ref` 时两边可能对不上）。
   - 同一句方案原句（空白折叠后逐字相同）、同一个模型，在这个 ADR 的任何一轮里已经有合格的 `model-wrong` 判断（证据在当前提交里仍逐字存在、`quote` 在那一轮的答案里逐字存在）时，这句在后来的轮次里再被标成“不一致”或“找不到”，沿用那条判断，不必重写。判断只按句子沿用，每一轮仍要对当前内容整份核对、仍要没有“未判断”的条目。
   - 这一步不能经 `delegate.mjs` 交接（会报 `DELEGATE_INVALID mode`，交接任务里没有 `--claims-file`，也没有 `--brief`）。Mac 线程要跑它，请协调者开一个云端线程，让它按上面的命令直接运行并把记录推回分支。
   - 上面所有 `claims-` 开头的问题，Andy 明确说跳过时，可以和其他复核问题一样用 `--accept-unreviewed "<Andy 的原话>"` 盖过（见[代码复核](#code-review)第 6 步的例外）。
6. 局限，如实写在这里：低价模型自己也会看错，也可能漏列某句说法，脚本只能验证“列出的每一句都有真实的文件和代码原文，每条对不上的都被线程处理过”，验证不了“没有漏列”，也验证不了“引的那行真的能证明这句话”，更保证不了方案一定对。记录、答案和判断都是线程提交的文件，脚本验证格式和引文，验证不了这次运行是不是真的发生过：和整个复核机制一样，防误操作，不防有意（Andy 2026-11-03 定）。答案落盘前会把像密钥的文字遮盖，如果被引的代码里有这类文字，引文会对不上，报 `claims-evidence`，这时让线程改引那一段旁边的代码，或请 Andy 说跳过。它不核对外部网站和第三方产品的说法，也不替代下面合并前的代码复核。

<a id="code-review"></a>
## 合并之前：代码复核

1. 合并前对 PR 的最终提交做一次完整复核（`--mode code-review`，不传 `--previous`），默认只跑 DeepSeek（Andy 2026-11-12 定；此前第 1 轮必须两个模型都跑，只给一个时脚本拒绝，这条限制已去掉）。Andy 指明要两个模型时加 `--models deepseek-v4.1-flash,glm-5.3-flash`。开 PR 前不另做。
2. 分类由线程做，不由模型做。线程对每一条意见逐条核对，每条都写下判断和依据（文件:行或实际运行结果），先判断它成不成立，再把成立的意见分成两类：
   - 会出错：照现在的代码，只要存在一种输入或使用方式（包括不合规范的、恶意的或不可信的输入）会让功能出错、丢数据、出安全漏洞，或造成其他实质损害（例如资源耗尽、无法撤销的破坏性操作），即使现有测试没有走到那条路径；或者说明、规则、文档与代码或事实不符、或与另一条规则矛盾，会让后来的人照着做错；或者本轮核对中确认的错误（包括本 PR 刚修好的）缺了能证明它的测试用例。这类意见必须修改（改代码、文档、规则或测试，看问题出在哪里）。
   - 可以更好：不改变任何可观察行为，也不改变任何陈述的真假，只是写法、结构、命名、措辞还能更好（判类只看意见指出的是什么问题，不看改起来有多小：指出说明与代码或事实不符的，哪怕只要改一行注释，也是“会出错”）；或者建议补的测试，线程在工作区里临时写出并运行过，用现在的代码也通过（核对用的测试不提交；证明已确认错误的回归测试除外，它属于“会出错”，要提交，提交后按第 3 步被复核；没有实际运行的，按“会出错”）。这类意见不修改，也不因为它再复核一轮。
   - “会出错”的意见再分严重度（Andy 2026-11-06 定）：
     - 中、高：正常使用就会触发的错误结果、丢数据、泄露凭据或令牌，能绕过合并前检查或花钱上限的问题，无法撤销的破坏性操作；还有会让人照着做错这类事的规则或文档错误。
     - 低：只有故意构造的怪输入才能触发（例如文件名开头带空格、参数里带控制字符），而且触发后是报错拒绝、不会给出错误结果；或者文字漏写、写得不准，但不会误导人做错事。
     - 拿不准的按“中、高”。判为“低”必须写出怎样才能触发、触发后具体发生什么，并写明模型自己给的严重度；线程判得比模型低时要写理由，方便 Andy 抽查。
   - 逐条判断除了写进给人看的 `round-<n>/judgments.md`，还要一条一行写进 `round-<n>/verdicts.jsonl`（脚本读它）：`id`、`model`（完整模型名）、`quote`（模型原话，必须能在这一轮的 `<模型>.md` 里逐字找到）、`valid`（成立与否）、`class`（`error` 是“会出错”，`better` 是“可以更好”）；成立的“会出错”还要有 `severity`（`low` 或 `medium-high`）、`trigger`（怎样触发）、`consequence`（触发后会怎样）、`modelSeverity`（模型自己给的严重度），模型给的不是“低”而线程判 `low` 时还要有 `reason`。每行是一个 JSON 对象，任何字段都不能带换行；`id` 在同一个文件里不能重复。格式不对或 `id` 重复时脚本以 `VERDICTS_INVALID` 拒绝。
   - 拿不准它成不成立、或属于哪一类的，都按“会出错”处理；判为不成立或“可以更好”都必须给出能核对的依据，只写“只是写法问题”不算：不成立，要给具体的反例、实际运行结果，或证明没有可达输入的代码引用；可以更好，要写清这处改动如果做了，只会动注释、命名、格式或措辞（不改变事实和行为），并附上核对过程；现有测试改动前后输出一致只能当辅助证据，不能单独作为依据。涉及错误路径、安全、数据、资源耗尽、不可逆操作的意见，没有这样的依据就按“会出错”。
   - 两条不花钱的命令代替手工步骤（[ADR 0263](../../docs/adr/0263-cheaper-claude-side-of-code-review.md)）：`--judge-skeleton --pr <编号>` 把最新一轮模型答案里每个 `###` 标题写成 `verdicts.jsonl` 的一行（编号、模型、原话已填，“结论”“侧重检查”“必答问题”几节跳过，文件已存在时以 `JUDGE_SKELETON_EXISTS` 拒绝），线程填好判断；`--finish-round --pr <编号>` 核对每条原话都在答案里、判“不成立”和“可以更好”的都写了依据字段 `why`、账本里这一轮的 `base` 是提交哈希（不满足时以 `FINISH_ROUND_REFUSED` 拒绝，账本的 `base` 不对时原因是 `base-invalid`），由 `verdicts.jsonl` 生成 `judgments.md`，打印 `ROUND_SUMMARY` 和下一步 `NEXT`（`fix-and-rereview` 附下一轮命令，`--previous` 已填成这一轮复核的提交；`fix-low-then`；`low-deferred`；`done`）。两条命令只接受 `--pr`、`--repo`。
3. 按中、高严重度的“会出错”意见，或第 5 步里 Andy 采纳的意见，做了修改，就对这些修改再复核一轮（传 `--previous <上一轮复核的提交>`，模型只复核增量和增量直接影响的代码；上一轮之后用 `--accept-low` 记过低意见修改的，传 low-fix 记录的 `head`（`--accept-low` 当次打印的 `REVIEW_LOW_FIX … head=`，或提交账本后再跑 `--assert-reviewed` 打印的 `REVIEW_CURRENT … reviewed=`），不是之后提交账本的那个提交。脚本开跑前用工作区里的账本算复核链（low-fix 记录按合并前检查同样的规则重新核对），`--previous` 接不上最后一个已接受的复核点、或和同一轮已有结果用的 `--previous` 不同，就以 `REVIEW_PREVIOUS_REFUSED` 拒绝、一分钱不花，并在 `use=` 后面写出该传的提交、`no-previous`（不传 `--previous`，从分叉点整份复核）或 `new-round`（这一轮已有结果接不上复核链，不要再补跑这一轮：不传 `--round` 也不传 `--previous`，新开一轮从分叉点整份复核），[I-98](../../docs/incidents-and-gates.md#incidents)），一直到线程核对后没有中、高严重度的“会出错”意见为止，第 4 步的停止条件除外。
   - 每一轮没写 `--models` 时脚本都只跑 DeepSeek（第 2 轮起是 Andy 2026-11-06 定的，为了省钱：PR #255 的账本里 DeepSeek 的 56% 花在思考上，GLM 的 58% 花在反复读代码上；第 1 轮是 Andy 2026-11-12 定的）。只跑一个模型的代码复核（第 1 轮也算），DeepSeek 遇到服务报错（账本 `outcome` 记 `api-error`）时，opencode 自己会先按服务给的间隔连试 5 次；还不行，脚本等 60 秒、在同一个 0.2 美元上限里整轮重跑一次；重跑后仍是可以重试的服务报错（“可以重试”指 opencode 给错误标了 `isRetryable`，或响应带数字形式的 `retry-after`、`retry-after-ms`；钱或时间不够、脚本没重跑的不算），就让 GLM 跑这一轮（打印 `REVIEW_SUBSTITUTE`，账本记 `substitute: true`、`substituteFor`），替补前按第 4 步的先问门槛重新核对，超了就打印 `REVIEW_SUBSTITUTE_SKIPPED` 不跑；这时先问 Andy，他同意后用 `--round <这一轮> --models deepseek-v4.1-flash --approved-usd <美元>` 重跑 DeepSeek（这一轮原来传了 `--previous` 的，重跑时传同一个，否则脚本以 `REVIEW_PREVIOUS_REFUSED round-previous-differs` 拒绝），再遇到服务报错时脚本会自动替补。在 DeepSeek 失败的那一轮里用 `--round <这一轮> --models glm-5.3-flash` 手工补跑的 GLM 没有替补记录，合并前检查不认这一轮，不要这样跑。
   - 从第 `lowDeferFromRound` 轮起（写在 `scripts/model-review/review-models.json`，现在是 3），一轮里成立的“会出错”意见全部是“低”时，不修、不记 `low-fix`、不再复核；`--report` 在“低严重度未修（第 3 轮起只列不修）”一节列出这样的每一轮的这些意见（轮次、编号、原话、触发条件、后果），交给 Andy 抽查；某一轮的 `verdicts.jsonl` 没有提交时，这一节打印一行说明列不出那一轮，不静默略过。这一轮之前的轮次照下一条处理。
   - 一轮里的“会出错”意见全部是“低”时，这一轮不再触发下一轮：线程照常修改、补测试、做反向验证，把这一轮的 `verdicts.jsonl` 和修改都提交后，运行 `node scripts/model-review/opencode-review.mjs --assert-reviewed --pr <编号> --accept-low <轮次>`。它核对：这一轮是复核链上最后一轮；`verdicts.jsonl` 已提交、格式对、原话都能在模型答案里找到；成立的“会出错”全部是 `low`，且至少有一条；这一轮复核的提交之后（只合入 main 带进来的文件不计，判法同第 6 步；PR 和 main 都动过的文件，行数仍按两个提交之间的全部差异算，偏多不偏少）只改了不超过 5 个文件、每个文件增删合计不超过 30 行，文件名不含换行，并且至少一个测试文件（`test/`、`tests/`、`__tests__/` 下的文件，或名字以 `.test.js`、`.spec.ts` 这类 JS/TS 测试后缀结尾的文件，或 `test_*.py`、`*_test.py`、`*_test.go`、`*_test.rs`、`*Test.java`；`.md` 不分大小写都不算。认哪些文件写在代码里，不读 PR 自己的测试配置，免得 PR 自己放宽口子（[ADR 0270](../../docs/adr/0270-faster-review-rounds.md)）有新增的行（只改 `.md` 文档的除外）；每一轮最多一条 `low-fix` 记录，要再改就把修改合在一起，或者再复核一轮（第二次以 `already-low-fixed` 拒绝）。都满足才在账本追加一条 `mode: "low-fix"` 的记录（打印 `REVIEW_LOW_FIX`），否则打印 `REVIEW_LOW_FIX_REFUSED` 和全部原因（例如 `not-low`、`no-test-change`、`too-many-files`、`too-many-lines`、`quote-not-found`、`not-last-round`），不写账本，并以退出码 5 结束（没有未复核的改动时同样拒绝，原因 `nothing-unreviewed`）；每次拒绝还把轮次、提交和原因词（只有原因的第一个词，不含文件名）追加到 `.agents/reviews/pr-<编号>/low-fix-refusals.jsonl`，用来统计哪种原因最常见（ADR 0270 起）。超过规模上限的修改按中、高处理，再复核一轮。这些核对防的是线程手误，不防有意伪造：模型答案 `<模型>.md` 和 `verdicts.jsonl` 都由线程提交，在修改的同一个提交里一起改掉，脚本认不出（和下文“这套限制防误操作，不防有人故意”是同一个取舍）。
4. 每多跑一轮之前，在汇报里写明已花的累计费用；这一个 PR 的复核累计费用（已花的加上这一轮预计的）会超过 1 美元时，先问 Andy；费用说不准时按会超过处理（Andy 2026-11-03 为 PR 复核定的先问门槛，不是硬上限；2026-11-14 又定全项目每天的复核和核对合计 5 美元以内不用问，由协调者汇总核对，见[钱和模型](../../.claude/rules/owner-standing-rules.md#money-and-models)；其他花钱仍按 0.5 美元先问）。
   - 第 1 步的完整复核算第 1 轮，之后每次复核算一轮，包括第 5 步引起的复核；`--accept-low` 写的记录不算一轮。
   - 一轮里只要有一条意见被判为中、高严重度的“会出错”，不管线程是否已经改完、是否在等 Andy 定，这一轮就算没过；线程已经写明理由判为不成立或“可以更好”的意见，后面的轮次再提，不算新的“会出错”意见；但这条意见涉及的代码后来改过，或者后来的改动改变了这条意见的触发条件，或者模型给出了此前没有核对过的新证据（例如具体的失败输入、复现步骤或运行结果，哪怕意见的文字和上次相同），线程要重新判断并把判断和依据写下来，维持原判也一样；改判为“会出错”的照常算。
   - 连续三轮没过，第三轮的“会出错”意见可以先改，但改完不再复核，直接停下报告 Andy，把已改未复核的和还没解决的分开列出，等他决定，不要一直循环；Andy 明确说继续后，连续的轮数从头算，费用仍按上面的先问门槛。
   - Andy 在停下时明确裁定“这条不改”的“会出错”意见，连同他的理由记进报告附件，之后的轮次不再算没过，已经记录的连续失败不追溯；除非这条意见涉及的代码后来改过、触发条件变了，或者有新的证据。
5. 报告 Andy 时，把各轮所有“可以更好”的意见一起列给他：每条写清是什么、线程建议采纳还是不采纳、为什么。判为不成立的意见和理由放在附件里，不要求他逐条看。只有 Andy 说可以采纳的才改；采纳的改动属于这个 PR，改完按第 3 步再复核一轮（算一轮），再报告一次。合并按[授权、上线和合并](../../.claude/rules/owner-standing-rules.md#authorization-deploys-and-merges)：没有中、高严重度的“会出错”意见、过了[交付模式](delivery-mode.md#fast-mode)写的合并条件，线程就自己合并；那里列出的几类等 Andy 说“合并”。
6. 合并前核对代码都复核过（Andy 2026-11-05 定：合并前 main 必须已经在分支里；Andy 2026-11-09 改：只是合入 main、PR 自己的改动没变，不用再复核）。先 `git fetch origin main`，`origin/main` 不在分支里就先把它合进分支；把复核记录目录提交后，运行 `node scripts/model-review/opencode-review.mjs --assert-reviewed --pr <编号>`。它不花钱，不带 `--accept-unreviewed` 时只读；它从当前提交里读账本，按轮次顺序把复核串成一条链。一轮算数的条件：这一轮要跑的模型（账本里这一轮出现过的、在 `allowed` 清单里、记录上没有 `substitute` 字段的模型）每个都有 `ok` 的结果或有替补它的 `ok` 结果（替补只在这一轮里被替补的模型自己有一条没通过的记录时才算）；或者默认模型（`review-models.json` 的 `default`）每个都有。起点是最后一个不带 `--previous` 的算数的轮次；之后每个算数的轮次，以及每条 `low-fix` 记录，都是链上的一点（链上不止一点时打印 `REVIEW_CHAIN`，每一点后面标 `requested`（要跑的模型都通过）、`default`（要跑的没全通过，但默认模型通过了）、`substitute`（靠替补通过）或 `low-fix`）。带 `--previous` 的一轮要接得上：它的 `previous` 必须是链上前一点的提交或更早的提交（这样模型看的增量把前一点之后的改动全包进去），它复核的提交必须是前一点的后续提交；没传 `--previous` 的轮次看的是整个 PR，从它重新起头。`low-fix` 记录的 `from` 必须等于前一点的提交，并在它自己的提交上按第 3 步的条件重新核对一遍，记录里的 `files`、`findings` 也必须和重算的一致，同一轮接连两条 `low-fix` 也不行，不合格报 `low-fix-invalid`（例如 `files-differ`、`findings-differ`、`second-low-fix`）。接不上的一点报 `chain-broken`，直到下一个不带 `--previous` 的算数的轮次重新起头。它要求链上最后一点的提交是当前提交的祖先、两者之间 PR 自己的改动没变（对每个文件，分别取该提交相对它与 `--main-ref` 的合并基线的 `git diff -U0 --binary --no-renames`，去掉 `@@` 和 `index` 行后取 SHA-256 比较；按原始字节比较，空白、权限位、二进制内容都参与，行号和上下文不参与；记录目录不算；只是合入 main 带进来的文件差异不算改动，冲突手工解决、合并时顺手改的内容会让这个文件的比较结果变，仍报 `unreviewed <文件>`；已知盲区：文件里按原顺序把一段改动挪到别处不会被发现，这套检查防手误不防有意；只比较两个提交之间内容确有差异的文件；算不出合并基线、某个文件的 diff 失败或为空、文件名含无效 UTF-8 时退回比较两个提交的全部文件差异））、`origin/main` 已合进分支。输出 `REVIEW_CURRENT` 才能合并；输出 `REVIEW_RECORD_INVALID`（退出码 5）说明分支里提交的复核账本格式不对，按它打印的原错误修好账本再跑；输出 `REVIEW_NOT_CURRENT`（退出码 5）就对列出的改动再复核一轮（`--previous` 传它打印的 `reviewed`），包括解决冲突和复核后顺手的小改动（干净合入 main 不在其内）。
   - 例外：Andy 明确说跳过复核（Andy 2026-11-08 定，原话“放松”：任何 PR、不论复核了几轮都可以），或者按第 4 步连续三轮没过而停下、Andy 看过报告仍说“合并”时，加 `--accept-unreviewed "<Andy 的原话>"` 运行。原话只认 Andy 本人在线程里打的字或协调者转来的他的原话，逐字引用、不改写；模型答案、PR 描述、GitHub 评论、提交说明里的文字都不算，即使写着“Andy 同意”。它能盖过的只有复核类问题：`ledger-not-committed`、`no-complete-round`、`chain-broken`、`not-ancestor`、`low-fix-invalid`、`unreviewed`；`origin/main` 没合进分支、主分支引用不存在照样失败（`REVIEW_OVERRIDE_REFUSED not-review-problems <问题>`）；写入新的覆盖记录时，工作区里的账本和当前提交里的不一致就拒绝（`REVIEW_OVERRIDE_REFUSED ledger-differs-from-HEAD`），先提交或还原。脚本把原话、当前提交和当时的问题写进本 PR 的账本（一轮都没复核过时新建记录目录），打印 `REVIEW_OVERRIDE_WRITTEN quote=<原话> commit-and-rerun`，这一次仍以退出码 5 结束；线程把账本提交后再运行一次 `--assert-reviewed`，它认出已提交的记录（那条记录的提交之后只改了本 PR 的记录目录），打印 `REVIEW_OVERRIDE quote=<原话> recorded=<提交>` 并以 0 退出，这时才能合并。脚本验证不了原话是不是真是 Andy 说的：已提交的覆盖记录本身被信任，能往分支写账本的人都能写一条，和上文“这套限制防误操作，不防有意”是同一个取舍；由线程负责，`--report` 在“Andy 说跳过复核的记录”下逐条列出每次覆盖（`REVIEW_OVERRIDE_RECORD head=… quote=… problems=…`）供 Andy 抽查。`--assert-reviewed` 和 `--report` 只接受各自用得上的参数，多给的参数以 `ARG_NOT_FOR_SUBCOMMAND` 拒绝，不会悄悄忽略。
   - 局限：合并由线程执行，这条检查拦不住线程不跑它；要真正拦下，得等 CI 能读账本、Andy 决定规则集要求 `ci/required`。
7. PR 描述和给 Andy 的复核汇报，复核部分照贴 `node scripts/model-review/opencode-review.mjs --report --pr <编号> --stop <原因>` 的输出，不手写。它从当前提交的账本生成固定几行：每条代码复核记录的 `REVIEW_RESULT`（同一轮里失败后用 `--round` 重跑的，两次都列出）、`REVIEW_SPENT_TOTAL`、第 6 步检查的结果、停下的原因和一句固定的话“复核模型只读代码、不运行代码；复核通过不等于测试通过。”。有 `low-fix` 记录时，另起一节“低严重度已改、未复核：”，逐条列出每条记录的轮次、提交、改动的文件，以及它放行的每条意见的编号和模型原话（原话从那条记录自己的提交里读，不受之后改动影响），供 Andy 抽查；不在复核链上的 `low-fix` 记录（例如手写的、重核不合格的）只打印一行 `REVIEW_LOW_FIX_NOT_IN_CHAIN`，不列原话，也不算放行。`--stop` 只能是 `no-error`（没有中、高严重度的“会出错”意见，要求最后一轮在复核链上且第 6 步检查通过）、`three-rounds`（连续三轮没过，至少有三轮）、`andy-decision`（Andy 裁定，必须加 `--andy-quote "<原话>"`）、`run-failed`（最后一轮不在复核链上，即该跑的模型没有 `ok`）；和账本对不上时以 `REPORT_STOP_INCONSISTENT` 拒绝。哪条意见算“会出错”仍由线程判断，脚本只核对说法和账本是否自洽。

<a id="checklist"></a>
## 每次都要问的问题

1. 这个改动会不会改变模型已经见过的请求开头？包括系统提示、工具定义、历史消息、遮盖结果。要求回答：发给模型的内容是不是仍然只在末尾追加，每轮会变的值是不是都在最后一条消息里。依据：[发给模型的内容只追加](../../.agents/instructions/prompt-prefix.md#rules)。
2. 这个改动会不会让同一段文字在不同请求里变成不同的字节（例如依赖前后文的遮盖、带时间的字段、无序的集合）？
3. 改动有没有对应的自动检查，反向用例是否真的会失败？
4. 改动产生或修改的每个值（标识、字段、配置键、清单项、序列化格式），每一个使用它的地方都能接受吗？逐个找到产生它的地方和使用它的地方，核对两端的校验，只看改动本身不够。依据：[I-73](../../docs/incidents-and-gates.md#incidents)，双模型复核只看了改动，没问“清单里的 id 能通过后端校验吗”。

<a id="owner-control"></a>
## Andy 怎样控制复核

Andy 在项目聊天对协调者说、由协调者附原话转来，或者他直接在线程里打字，都算数（[授权、上线和合并](../../.claude/rules/owner-standing-rules.md#authorization-deploys-and-merges)）。他的话只管当次，以后的复核照常。

- “停止复核”“别复核了”：线程对复核进程发 `kill -INT <REVIEW_PID>`（`SIGTERM` 也按叫停处理，例如容器关停时）（复核一律用后台命令启动，开跑后第一行打印 `REVIEW_PID`），不用 `SIGKILL`。脚本让正在跑的模型停下、读完用量、把这一轮记进账本（`outcome: "owner-stopped"`，费用照常按宁可多记的规则算），打印 `REVIEW_STOPPED owner-stopped` 后以 130 退出；API 报错后等待重试的那 60 秒里叫停，等待立刻结束、不再重试，第一次运行照样记账，`outcome` 和 `retry` 都记 `owner-stopped`；再发一次信号，或 30 秒内没走完，就清理后强制退出。线程提交账本和已写出的提示词，不再开新的一轮。停止不等于合并。
- “跳过复核，合并”“不用复核直接合并”：按[代码复核](#code-review)第 6 步的例外，用 `--accept-unreviewed "<原话>"` 记下他的原话，提交后再核对，然后合并。
- “这次用 OpenDesign”“这次不用 CodeBuddy”：下一条复核命令加 `--providers <服务方 id>[,…]`（`workbuddy-ai` 是 CodeBuddy、`opendesign` 是 OpenDesign、`opencode-go` 是 Go），“不用某一家”就列出其余几家。只说“换一家”没点名时，列出服务方和顺序问他要哪家，不猜。
- “直连 Go”：下一条复核命令加 `--gateway direct`。

## 怎么跑

用 `node scripts/model-review/opencode-review.mjs` 跑，不要自己拼 `opencode run` 命令。它做这些事（Andy 2026-11-03 定）：

- 模型自己读代码：只开读文件、按内容搜索、按文件名找文件，以及 `git diff`、`git log`、`git show`、`git blame`、`git status`；改文件、别的命令、派子代理、仓库外的路径全部禁止。
  - git 命令里的重定向（`>`、`<`）、制表符、`difftool`（它能执行任意命令）、写文件参数（`--output`、`-o`）、照样打印被隐藏内容的参数（`-a`、`--text`、`--binary`）、读仓库外文件的参数（`--no-index`、`--contents`）、外部程序参数（`--ext-diff`、`--textconv`）另行禁止。
  - opencode 只按命令文字匹配，引号和反斜杠能绕过（实测 `"--output=文件"` 照样写出文件），所以脚本还在模型用的 `PATH` 最前面放了一个 git 替身：它拿到的是 shell 解析后的真实参数，子命令不在上面五个里、参数是这些禁用参数及其缩写、或是会读文件的 `--ignore-revs-file`、`--pathspec-from-file`、`--mailmap-file`、`--orderfile`、`blame -S`、打开帮助程序的 `--help`，或者短参数连写里藏着 `-o`、`-O`（如 `-pO文件`）就拒绝，否则才交给真的 git；同时用 `GIT_TEST_DISALLOW_ABBREVIATED_OPTIONS` 让 git 自己也拒绝缩写，并不读系统和用户的 git 配置。
  - opencode 的文字规则还漏掉了 `cd 副本 && git log > 文件` 这种写法（实测写出了文件），所以模型的命令改在受限 bash（`bash -r`，bash 自带的模式：不许输出重定向、不许 `cd`、不许改 `PATH`、不许用带斜杠的命令名）里执行。
  - git 替身调用真 git 之前会去掉所有 `GIT_*`、`LD_*` 等环境变量，只留 `PATH`、`HOME`、`LANG`、`TERM` 和固定的 git 设置，所以模型先 `export GIT_EXTERNAL_DIFF=程序` 再跑 `git diff` 也不能让 git 执行别的程序（第五轮复核实测过这种写法）。真 git、受限 bash 和 opencode 自己都额外拿到同一套消息语言设置（脚本里的 `englishMessages`）：去掉会盖过一切的 `LC_ALL`，把 `LC_MESSAGES` 和 `LANGUAGE` 固定成 `C`，让报错和拒绝提示一定是英文（脚本按英文原文认拒绝），同时按 `LC_ALL`、`LC_CTYPE`、`LANG` 的优先次序把字符类语言接过来写进 `LC_CTYPE`，这样 grep 之类的命令仍然按 UTF-8 匹配中文。代理地址（`HTTPS_PROXY`、`HTTP_PROXY` 及小写写法）在白名单里，模型同样读得到，所以其中带用户名或密码（去掉首尾空白后，主机名前面有 `@`，写不写协议头都算）时脚本拒绝开跑（`PROXY_HAS_CREDENTIALS`）。opencode 本身也只拿到一份白名单里的环境变量（脚本里的 `OPENCODE_KEPT_ENV`：`PATH`、`HOME`、`USER`、`LOGNAME`、`TERM`、语言和时区、临时目录、XDG 的数据、缓存和状态目录、代理和证书设置），线程容器里的令牌和密钥（例如 `GITHUB_TOKEN`）不传给它：原先整份环境都传过去，模型写 `git log $GITHUB_TOKEN` 就能从 git 的报错里读到值（2026-11-05 在云端容器实测），而方案讨论能读网页，网页内容可能诱导模型这样做。
  - 这套限制防的是复核模型误操作（顺手改了文件、跑了别的命令、上了网），不防有人故意在 PR 里埋恶意代码：PR 都是本项目自己的线程写的，复核又跑在用完即删的云端容器里。Andy 2026-11-03 定：这是开发协作工具，不是 Himawari 的功能，不用系统级沙箱，也不再为后一种情况加固；复核材料不要再让模型专门去找这类绕过办法。原因：系统的真相在代码里，只读线程给的材料，材料错了复核就跟着错。
- 代码复核（`--mode code-review`）不联网；方案讨论的两个模式（`--mode plan`、`--mode plan-review`）可以用 opencode 自带的搜索和读网页工具（Andy 2026-11-03 定）。搜索走 opencode 内置的 Exa 免费搜索服务，不花 Andy 的钱，只是搜索结果会算进模型的输入 token。
- 必问问题从 `--base` 提交里的本文件读（方案讨论不传 `--base` 时从 `--head` 提交读），不从被复核的改动或工作区读，免得改动自己改掉要问的问题。要用另一个已提交的版本时（例如在旧提交上做对比实验），传 `--questions-ref <提交>`，仍然只读提交过的内容。
- 代码复核和方案审核（`--mode plan-review`）里，两个模型除了都回答全部必答问题，还各有一节额外侧重（脚本里的 `MODEL_LENSES`，Andy 2026-11-05 同意）：DeepSeek 先查错误路径、不可信输入、安全、资源耗尽和不可撤销的操作，以及规则文件、说明文档和代码是否一致（Andy 2026-11-06 同意加上后一项，因为默认每一轮都只有它一个（定这条时是第 2 轮起），GLM 那份侧重没人看；这句侧重第 1 轮起每轮都带，所以 DeepSeek 的提示词开头每轮仍然逐字节相同）；GLM 先查测试覆盖、文档和规则与代码是否一致，并走一遍最普通的使用流程。侧重写在“本次材料”之前、同一个模型每轮都一样，所以每个模型发出的内容仍然只在末尾追加；两个模型的提示词因此不同，每轮分别存成 `<模型>.prompt.md`。独立出方案（`--mode plan`）不加侧重。依据：Anthropic 官方复核插件把复核分给不同侧重的代理，并在高风险项上让两个代理重复看（https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/plugins/code-review/README.md ）。
- 第一次运行会联网安装 `opencode-ai@1.19.5` 到 `~/.cache/himawari-opencode-1.19.5-<锁文件摘要前 12 位>`，之后复用；也可以用 `HIMAWARI_OPENCODE_BIN` 指定已装好的程序（这时不做下面的核对）。安装用 `npm ci` 按 `scripts/model-review/opencode-lock/` 里提交的锁文件（`package-lock.json`，逐个记了 `opencode-ai` 和 12 个平台包的 sha512 摘要）进行，下载的包摘要不符时 npm 自己就会拒绝；每次使用前，脚本还会核对 npm 的安装记录（`node_modules/.package-lock.json`）里每个包的摘要和锁文件一致；它不重新计算已装文件的摘要，所以挡的是下载时被替换，不是装好之后有人改了磁盘上的文件。复用已有安装时若核对不一致或安装记录缺失、读不出，脚本删掉这个安装目录、按锁文件重装一次（刚装好就不一致时直接报错，不重装）（打印 `OPENCODE_REINSTALL`），重装后仍不一致以 `OPENCODE_INTEGRITY_MISMATCH` 停下。升级 opencode 时，改 `OPENCODE_VERSION` 和 `opencode-lock/package.json`，在该目录运行 `npm install --package-lock-only --ignore-scripts` 重新生成锁文件，一起提交。
- 云端会话默认经本次运行自起的本机 Magpie（一个开源的本机模型网关，背后挂多个服务方，一家用不了就换下一家）调模型；Mac 线程不在本机跑复核，交给云端线程跑，见[Mac 线程把复核交给云端线程](#delegate)。做法和怎样选见[经 Magpie 调用模型](#gateway)。
- 密钥不写进脚本生成的配置，由 OpenCode 自己找：Mac 上先用这个 1.19.5 执行 `opencode auth login` 选 OpenCode Go 登录，密钥存在 `~/.local/share/opencode/auth.json`（OpenCode 保存登录密钥的文件）；云端不用登录，云端容器的出口代理（所有外发请求经过的那一层）会给发往 opencode.ai 的请求补上密钥。配置里一旦写了 `apiKey`，OpenCode 1.19.5 就不再用 auth.json 里的密钥，真实请求会报 401（[I-76](../../docs/incidents-and-gates.md#incidents)）；直连 OpenCode Go 时，只有自检连本机假服务器才写假密钥；经 Magpie 时配置里的占位密钥只和回环地址一起出现，见[经 Magpie 调用模型](#gateway)。
- 在 PR 最新提交的一次性副本里运行：副本是干净克隆，只有提交过的文件。历史里任何一个提交（包括合并提交）的文件树里出现过 `.env` 一类文件（`.env.example` 这类模板除外）就拒绝复核，因为 git 命令能从历史里读出它。副本删掉了远程地址、引用日志（reflog，记录分支移动的日志，里面有原仓库路径）和 `FETCH_HEAD`，用完即删，脚本收到中断或结束信号（`SIGINT`、`SIGTERM`）时也会删（模型已经在跑时，先让它们停下、记完账再删，见[Andy 怎样控制复核](#owner-control)）；被强杀（`SIGKILL`）时删不掉。副本里 PR 自带的 `.opencode/`、`opencode.json(c)`、提交进仓库的 `.env*` 文件和指向副本外的符号链接会先删掉，因为 opencode 启动时会执行项目目录里的插件，符号链接能把读文件带出副本；配置改从副本外的文件读。副本里的分支和标签全部删掉，只留 `refs/review/head`、`refs/review/base`、`refs/review/previous` 三个引用；其他提交的对象还在，知道哈希仍能读到。opencode 的全局配置（`~/.config/opencode`）不会被读入，脚本给它一个空的配置目录。
- 把 opencode 默认写死的 32 000 输出上限调高（`OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` 设为 200 000），DeepSeek 高推理时不再被截断。opencode 会再按模型目录里的上限往下调：2026-11-03 抓包实测 DeepSeek 请求是 200 000，GLM 是 131 072（GLM 的模型上限）。
- 开跑前先对本机假服务器自检，不花钱：让假模型发出一条正常的 `git log`、十几种写文件的命令（含引号、反斜杠、缩写、`difftool` 等绕过写法），以及用 git、读文件、搜索、找文件四种工具读仓库外文件的尝试。
  - 正常命令必须能跑；写文件命令既写到副本外，也写到副本里（含先 `cd` 再重定向）；每条写文件命令和每条读仓库外的 git 命令都必须被明确拒绝，只认 opencode 的权限拒绝、git 替身的 `REVIEW_GIT_REFUSED` 和受限 bash 的 `restricted` 三种文字，因别的原因失败（如目录不存在）同样算失败；读仓库外的尝试不能拿到内容；探针按内容对号，不按顺序。读文件、搜索、找文件三种工具读仓库外也必须被明确拒绝。
  - 另有几条先 `export` git 环境变量再跑 git 的探针（让 git 去执行 `env`、`touch`），要求看不到父进程里的标记、副本没有任何改动；还有一条探针在脚本自己的环境里放一个标记变量 `REVIEW_PARENT_CANARY`，让假模型运行 `git log $REVIEW_PARENT_CANARY`，输出里出现标记就算失败（环境白名单失效时它会失败），在 Linux 上读 `/proc/self/environ` 也必须被明确拒绝（Mac 没有 `/proc`，不做这条）；每个模型跑完都检查副本的 `git status`，有改动就算失败。
  - 五个允许的 git 子命令各有一条必须跑通的探针；受限 bash 外壳每次启动都记一笔，记录数少于这五条就说明 opencode 没有用它，算失败；opencode 发给模型的系统提示里不能出现副本里 `AGENTS.md` 的标题（PR 自带的项目指令不能变成复核模型的指令）；读仓库外的探针也包括 `../` 这种相对路径；`max_tokens` 不能低于 10 万，也不能高于该模型能接受的上限。工具表、输出上限、推理强度也要对。
  - `; touch`、`| tee`、`$(...)` 这类复合命令被拒，靠的是 opencode 把命令按片段分别判断权限（opencode 1.19.5 实测如此）；升级 opencode 后自检突然失败，先查这一点。任何一项不对就以 `SELF_CHECK_FAILED` 停下。
- 不限步数：提示里要求模型先想清楚要查什么、直奔目标去读，读到足以下结论就停，不要漫无目的地翻代码或反复调用同类工具（Andy 2026-11-03 定）。兜底靠下面的费用封顶和超时，再加 opencode 自带的「同一工具连续三次相同调用就拒绝」（`doom_loop`）。
- 自检缓存（ADR 0270）：自检通过后，把“脚本目录里所有 `.mjs`/`.json` 的摘要、这些脚本从目录外导入的文件（例如 `scripts/ci/verified-download.mjs`）的摘要、传给 opencode 的环境变量（`OPENCODE_KEPT_ENV` 加 `LC_ALL`，例如 `HOME`、`TZ`、代理和证书设置）的值、opencode 程序、git、bash 的路径大小修改时间（小于 1 MB 的再加内容摘要）、Node 版本、平台、模式、复核配置、Magpie 安装和配置”的摘要写到 `~/.cache/himawari-review-selfcheck/<摘要>.json`（环境变量 `HIMAWARI_REVIEW_SELFCHECK_CACHE` 设成 `off` 关闭，设成目录改位置）。7 天内同一摘要再跑复核时，只对第一个模型跑一次探针（保留“PR 自带的 `AGENTS.md` 不得进系统提示”和“副本跑完没被改动”两项每个 PR 都要查的检查，和 Magpie 安装摘要核对），跳过其余模型、循环上限探针、直通探针和故障转移探针；输出 `SELF_CHECK_OK ms=… cache=hit|miss|off`。`--self-check-only` 永远跑全套。
- 一次跑多个模型时并行（`--models` 指定跑哪些，例如只重跑失败的那个），每轮的结果写到这件事的记录目录（见下一条）下的 `round-<序号>/`：每个模型收到的提示词的遮盖后存档（`<模型>.prompt.md`，像密钥的文字已按下面的规则遮盖，账本里的 `promptSha256` 是未遮盖原文的摘要，补跑时存档文件按三种写法之一接受（按当前规则遮盖后的重建提示词、没遮登记值的重建提示词、或和账本里记的 `promptFileSha256` 一致的，见 ADR 0190），提示词本身是否变了仍按这个摘要核对；`promptFileSha256` 是存档文件（遮盖后）的摘要，`delegate.mjs check` 用它核对文件，旧记录没有这个字段时退回用 `promptSha256`，但旧记录的 `promptSha256` 是遮盖前的摘要，原文含像密钥的文字时回退仍会报 `prompt-hash=`，只能人工核对或重跑）、模型的答案（`<模型>.md`，每行末尾的空格和制表符已去掉，否则 `git diff --check` 拒收提交；`--brief` 的行尾空格也在读入时去掉）、失败时的报错（`<模型>.stderr.txt`）；思考内容（`<模型>.thinking.md`，opencode 的 `--thinking` 输出）和原始事件（`<模型>.jsonl`）太大，写到系统临时目录下的 `himawari-review-raw/<仓库路径摘要前 12 位>/<记录目录名>/round-<序号>/`，运行时打印 `REVIEW_RAW_DIR`，不进仓库；目录只给本人读写（权限 0700）。账本每行除了费用和轮次，复核记录还必须有 40 位（SHA-1）或 64 位（SHA-256）的提交哈希 `head`、`model`、`outcome`，任何文本字段（包括列表里的）都不能带换行，`mode` 只能是四种复核模式、`override` 或 `low-fix`（`low-fix` 记录还必须有正整数轮次、提交哈希 `from`、费用为 0、非空的 `files` 和 `findings` 列表），否则以 `USAGE_LEDGER_INVALID` 拒绝。服务报错时 `outcome` 记 `api-error`，`apiError` 记状态码和去掉控制字符、截到 300 字的错误信息；脚本重跑过一次的记 `retry: "retried"` 和第一次的错误 `retriedAfter`，钱或时间不够没重跑的记 `retry` 为 `no-budget`、`no-time` 或 `cost-unknown`。Andy 叫停的记 `outcome: "owner-stopped"`：不上复核链、不算通过，也只有 `owner-stopped` 记录的那一轮不算“连续三轮没过”里的一轮；补跑用 `--round <那一轮的序号>`，`--head` 传那条记录里的提交（提交账本后 HEAD 变了，不能传 `HEAD`）。`--main-ref`、`--questions-ref` 的值不能以 `-` 开头，也不能含控制字符；`--accept-unreviewed`、`--andy-quote` 的原话同样不能含控制字符（换行、退格、终端转义等）。`--main-ref`、`--stop`、`--andy-quote` 只属于 `--assert-reviewed` 或 `--report`，普通复核里给了以 `ARG_NOT_FOR_MODE` 拒绝。`--assert-reviewed` 打印文件名和 `--main-ref` 时，含控制字符的按 JSON 字符串打印，文件名的首尾空格原样保留。答案和错误输出存档时把回车统一换成换行（提示词存档不做这一步，摘要对存档的原字节计算）。每个模型的真实用量（输入、输出、推理、缓存命中 token、费用、轮次、是否追问过）追加到 `--out` 下的 `usage.jsonl`。

  - 所以追问这一步的配置把所有「允许」（`allow`）的工具权限改成「先问」（`ask`），「禁止」的照旧：工具定义不变，但 `opencode run` 没有人回答「先问」，会自动拒绝，而 opencode 在工具被拒后就结束这段对话（opencode 1.19.5 的 [run.ts](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/cli/cmd/run.ts) 自动回复 `reject`；[processor.ts](https://github.com/anomalyco/opencode/blob/v1.19.5/packages/opencode/src/session/processor.ts) 在 `experimental.continue_loop_on_deny` 不为 `true` 时，被拒就返回 `stop`）。模型若仍然调工具，这个工具不会执行，opencode 也不会再发下一次请求；这一步结束、费用入账后，脚本记为 `wrap-up-tool-call`（这一步的费用同时超出剩余额度时记 `cost-limit`）。以前靠脚本看到这一步结束再停进程，可 opencode 在这之间已经执行了工具、发出了下一次请求，这些请求的费用不入账（2026-11-04 复现：把 opencode 输出里每一步结束的那行延后 1 秒，两次各多发了 22、23 次追问请求；`test/tooling/opencode-review.test.mjs` 和 `test/tooling/opencode-review-merge-gate.test.mjs` 里的追问调工具用例就按这个延后来跑）。
  - 第一次运行也靠 opencode 自己拦：脚本给 opencode 装了一个很小的插件（`scripts/model-review/spend-guard.mjs`，只读，不改任何消息、系统提示和工具定义），每次要发模型请求之前，由插件在 opencode 进程里先判断，到线就抛错，这次请求不会发出去。判断用的是插件自己累计的各步费用（和 `step_finish` 里的 `cost` 同源，压缩历史后也不会漏算）和脚本传给它的几条线：会话总费用上限、收尾费用线（第一次运行）、收尾时刻、总期限；追问运行只带总上限、总期限和脚本已记的首轮费用（插件在追问进程里看到的历史被压缩时也不会漏算首轮），不带收尾线，否则追问的唯一一次请求会被自己拦下。
  - 插件把停下的原因、累计费用和放行次数写进每个运行独有的标记文件，脚本在子进程退出后读它：标记里有停止原因就采用它（插件的拦截一定早于脚本之后才发的杀进程信号），只有脚本自己发现的 `cost-unknown`、追问时的 `wrap-up-tool-call` 和 Andy 叫停的 `owner-stopped` 保留脚本的判断（插件已拦下时 Andy 又叫停，记成 `owner-stopped`，费用照样取较大的那个）；插件也把读不出费用的已完成步当作 `cost-unknown` 拦下；运行的费用取 `step_finish` 累计和标记累计中较大的一个。以前靠脚本读到 `step_finish` 才发停止信号，opencode 在这之间已经执行了工具、发出了下一次请求，这些请求的费用不入账（2026-11-04 复现：把每一步结束的那行延后 1 秒，费用线路径多发请求，实发 130 次、脚本只看到 9 步；时间线路径实发 101 次、只看到 6 步）。

  - 本来要追问（花到 0.15 美元、用掉八成超时、或没写正文）但拿不到会话编号、有一步的费用读不出来、剩下的钱不到 0.02 美元或时间不到 15 秒时不追问，`usage.jsonl` 的 `wrapUpSkipped` 分别记 `no-session`、`cost-unknown`、`no-budget`、`no-time`（顺序如此）。第一次运行里费用读不出来本身就会停掉它（`outcome` 记 `cost-unknown`），这种情况不追问，也没有 `wrapUpSkipped`。追问的钱和时间都算在这个模型的 0.2 美元和总超时里。

- 记录目录固定在仓库里：代码复核必须传 `--pr <编号>`，记在 `.agents/reviews/pr-<编号>/`；方案讨论必须传 `--topic <短名>`（小写字母开头，只含小写字母、数字和连字符），记在 `.agents/reviews/topic-<短名>/`。同一个 PR 的所有轮次必然写进同一个账本，换目录名绕不过先问线；`--out` 只在 `--self-check-only` 时允许（Andy 2026-11-05 定记录存这里）。线程在合并前把记录目录随 PR 一起提交。

  - 只重跑某一轮里失败的那个模型时，加 `--round <那一轮的序号>`，结果记进原来那一轮，不另占一个序号：这一轮里这个模型已经有 `outcome` 为 `ok` 的记录（`ROUND_ALREADY_HAS_RESULT`）、这一轮不存在（`ROUND_NOT_FOUND`）、这一轮记录的提交和这次的 `--head` 不同（`ROUND_HEAD_MISMATCH`），或者这一轮里这个模型的 `<模型>.prompt.md` 和这次发给它的提示词不同（`ROUND_PROMPT_MISMATCH`，例如改了 `--brief`）时拒绝，都在花钱之前；失败那次的文件改名为 `<模型>.attempt-<序号>.*` 留在原目录。提示词文件不在时，改用账本里这一轮记下的 `promptSha256` 比较；两样都没有时以 `ROUND_CANNOT_VERIFY` 拒绝；这一轮有记录缺 `head` 时同样以 `ROUND_CANNOT_VERIFY <轮> head` 拒绝。这一轮已有别的模式（例如方案讨论的独立出方案和审核共用一本账）的记录时以 `ROUND_MODE_MISMATCH` 拒绝；例外记录不算进任何一轮。
  - `usage.jsonl` 有一行读不出来、费用不是非负数字或轮次不是正整数，脚本以 `USAGE_LEDGER_INVALID` 拒绝开跑，不猜已花多少。
  - 开跑前脚本把 `usage.jsonl` 里已花的加上这一轮最多会花的（每个模型 0.2 美元）：代码复核和方案说法核对（`plan-claims`）超过 1 美元、方案讨论（`plan`、`plan-review`）超过 0.5 美元，就以 `BUDGET_NEEDS_APPROVAL` 拒绝开跑，并打印这几个数。线程把数报给 Andy，他同意的总额用 `--approved-usd <美元>` 传入，累计不超过这个数才放行。每次运行结束打印 `REVIEW_SPENT_TOTAL`，线程汇报费用就用这个数。
  - 全项目一天的复核和核对花费：`node scripts/model-review/opencode-review.mjs --spend-day [--date <YYYY-MM-DD>]`，只读，不花钱。它按日本时间的日期把工作区里所有 `.agents/reviews/*/usage.jsonl` 的花费加起来，每本当天有花费的账本打一行 `REVIEW_SPEND_DAY_ITEM`（当天没有记录的账本不打）；账本里某条记录的 `at` 缺失或不是以 `Z` 结尾的可解析时间，就以 `USAGE_LEDGER_INVALID` 拒绝，最后一行 `REVIEW_SPEND_DAY date=… total=… line=5 over=yes|no`。只看得到已经在这个工作区里的账本：别的分支上还没合进来的复核不在内，所以先合最新 `main` 再看。

用法：

```
node scripts/model-review/opencode-review.mjs --mode code-review \
  --base <分叉点提交> --head <PR 最新提交> [--previous <上一轮复核的提交>] \

node scripts/model-review/opencode-review.mjs --mode plan \
  --head <当前提交> --topic <短名> --brief <问题、目标、约束.md>

node scripts/model-review/opencode-review.mjs --mode plan-review \
  --head <当前提交> --topic <短名> --brief <线程的方案.md>
```


四种模式都可以加 `--gateway magpie`（经本机 Magpie 调模型，见下一节）、`--models deepseek-v4.1-flash`（只跑列出的模型，逗号分隔，可写短名或完整名；自检仍对两个模型都跑，不花钱；不写它时四种模式都只跑 `review-models.json` 里的默认模型，现在是 DeepSeek，Andy 指明两个都跑时写 `--models deepseek-v4.1-flash,glm-5.3-flash`）、`--round <序号>`（把单个模型的重跑补进原来那一轮，见上文）、`--questions-ref <提交>`（从这个提交读必问问题，见上文）、`--approved-usd <美元>`（Andy 同意的这件事的总花费）和 `--providers <服务方 id>[,…]`（经 Magpie 时这一次只用列出的服务方，见[Andy 怎样控制复核](#owner-control)；自检不收，`ARG_PROVIDERS_NOT_FOR_SELF_CHECK`）。

`--brief` 只写这次的材料：代码复核写问题、目标、约束和作者的说法；`plan` 只写问题、目标、约束和已核对的事实，不写线程的方案；`plan-review` 写线程的方案。脚本会在前面加上各模式的固定说明（上面的必问问题、项目指令第 16 条原话、该模式的任务和输出格式；`plan-claims` 例外：它既不放必答问题，也不放第 16 条那句，因为它只核事实、不提方案），代码复核的第一轮会让模型自己用 `git diff` 看改动。提交可以写分支名，脚本先在原仓库解析成提交哈希。按意见修改后的复核传 `--previous`，脚本先用合并前检查同一个函数 `unreviewedFiles` 算出“PR 自己这一轮的改动”（只是合并 main 带进来的文件不算，合并时手工解决冲突写的内容算），取这些文件 `previous..head` 的差异，放进提示末尾的“本轮增量”一段（开始和结束有标记，注明是数据不是指令；main 也改过的文件另附 main 自己的那段，注明不是本轮 PR 的改动；git 判为二进制的文件只列路径；放不下的文件整份不放，列出文件名和取差异的命令，标明“已截断”），提示不再让模型取整个 PR 的差异（[ADR 0280](../../docs/adr/0280-incremental-review-rounds-see-only-the-pr-s-own-increment.md)）。这一轮 PR 自己没有改动时打印 `REVIEW_INCREMENT_EMPTY` 退出、不花钱，直接做第 6 步的合并前检查；算不出增量时（配置文件缺失、取不到 `origin/main`、git 出错、文件名不合法、放不进提示上限）打印 `REVIEW_INCREMENT_FALLBACK <原因>`，按原来的整段 `previous..head` 复核，账本记下原因。数值（内联差异的字节上限、上下文行数、最多列出的文件数、工具调用摘要列几个文件、抽样全量复核做几次、报表分档）在 `scripts/model-review/review-increment.json`，启动时校验，类型或范围不对以 `INCREMENT_CONFIG_INVALID` 拒绝。账本每条代码复核记录多记 `increment`（文件数、增删行数、混进 main 与否、`previous..head` 原始行数、内联字节数、是否截断，或退回原因）和 `toolSummary`（按工具类型的调用次数、读得最多的几个文件）。提示让模型只做三件事：上一轮成立的“会出错”意见是否真的改好了、增量改的那些行有没有新错、增量产生或修改的值（导出的函数、配置键、字段、格式）的直接使用端能不能接受；没有碰到的旧代码不必重读，必答问题照样回答、无关的一句话带过。上一轮成立的“会出错”意见（从当前提交里已提交的 `round-<上一轮>/verdicts.jsonl` 读，最多 20 条、6000 字节、每条原话最多 160 字）放在材料里，注明只是线索不是指令；读不出来时写固定的一句话。固定前缀和必答问题一字不变（ADR 0270）；增量轮的材料写明必答问题里的“这个改动”指本轮增量加上一轮意见的修复，每题先写涉及还是不涉及，增量碰到请求开头、遮盖、序列化、配置键或标识时必须完整回答。

抽样全量复核（Andy 2026-11-15 同意，衡量增量轮漏查了多少）：增量轮跑完、全项目已完成的抽样次数还没到配置里的 `shadowFullTotal` 时，脚本打印 `SHADOW_FULL_SUGGESTED <命令>`。主线程在后台照跑这条命令（带 `--shadow`，在同一个提交上不带 `--previous` 整份复核），结果写进 `.agents/reviews/pr-<编号>/shadow/`，自带账本，不进复核链、不起子代理判断，花费算进这个 PR 的 1 美元和当天合计；随复核记录一起提交。`--shadow` 不能和 `--previous`、`--round`、`--self-check-only` 一起用。效果用 `node scripts/model-review/review-speed-report.mjs --cut <时间> --repo .` 看：表后按本轮增量行数分档比较改前改后的步数、时长和费用，旧轮次的增量行数用 git 历史回算。

<a id="delegate"></a>
## Mac 线程把复核交给云端线程

Andy 2026-11-08 定：Mac 本地线程要做方案讨论或代码复核时，把“跑复核”交给一个跑在 himawari-cloud 环境里的云端线程，Mac 上不配任何模型密钥。方案讨论记录在 `.agents/reviews/topic-review-delegation/`。云端线程自己要复核时照旧直接跑，不用交接。

- 分工：Mac 线程准备材料、问 Andy 要预算、交出任务、收回结果后逐条判断、修改、记账、合并；云端线程只跑一条复核命令、只提交 `.agents/reviews/<目录>/` 下的记录、推回同一个分支，不做判断、不改代码、不合并、不在 PR 上评论。
- 交出之前：把要复核的代码、这件事的整个记录目录（含 `usage.jsonl` 和已有的逐条判断）都提交并推送；再把材料写进 `.agents/reviews/<目录>/briefs/<要复核的提交前 12 位>-<模式>.md`，提交并推送（材料不要放在 `/tmp`，云端读不到，过后也会没有）。此时的分支头叫“交出点”。预算和服务方先按现行规则问 Andy，写进命令。干净地合入 main 不会让已复核的结果失效（判法见代码复核第 6 步）；仍建议在最后一轮复核之前做，这样最后一轮看到的就是最终形状。
- 生成任务说明：`node scripts/model-review/delegate.mjs prompt --mode <模式> --pr <编号>|--topic <短名> [--base …] --head <完整提交号> [--previous …] [--models …] [--round …] [--approved-usd …] [--providers …] --branch <分支> --tip <交出点> [--reply-to <本会话编号>]`；`--reply-to` 只收 `session_` 开头的云端会话编号，桌面应用里的本地会话编号（`local_…`）格式对不上会被拒绝，这种情况直接不写这个参数。参数都按固定格式校验，输出不含时间，同样的参数输出逐字节相同。任务说明里的复核命令一律带 `--gateway magpie --require-gateway`，第 0 步要求云端线程先确认 `HIMAWARI_REVIEW_GATEWAY` 是 `magpie`、分支头正好是交出点。
- 开会话：用桌面应用的 `start_session`（target 为 cloud），环境选 himawari-cloud，把任务说明原样当 prompt。环境选不上、应用读不到环境列表时停下，请 Andy 手动选 himawari-cloud；不要去掉环境参数退到 Default。万一还是落在 Default，复核脚本的 `--require-gateway` 会在读材料、安装、花钱之前停下：不经 Magpie 报 `GATEWAY_REQUIRED not-magpie`，环境变量 `HIMAWARI_REVIEW_GATEWAY` 不是 `magpie`（不在 himawari-cloud 里）报 `GATEWAY_REQUIRED not-cloud`，没有代理变量报 `GATEWAY_REQUIRED no-proxy`。
- 桌面应用的沙箱：Mac 线程在桌面应用的沙箱里时，`git fetch`、`git push`、`git ls-remote`（`wait` 和 `check` 都要用）会被拦在 `github.com` 之外，要按应用的提示关掉沙箱再跑；被拦时 `check` 以 `DELEGATE_GIT_FAILED`（退出码 2）停下，不是结果有问题。
- 等结果：云端会话结束时不会通知 Mac 线程，所以交出任务的同时在后台运行 `node scripts/model-review/delegate.mjs wait --branch <分支> --tip <交出点>`，它每 2 分钟查一次远端分支，分支头变了就打印 `DELEGATION_BRANCH_MOVED <提交>` 并结束，90 分钟没变打印 `DELEGATION_WAIT_TIMEOUT` 并以 3 结束（超时就把会话编号告诉 Andy，不再交出第二份）。云端线程如果有给 Mac 线程发消息的工具，会发开始和结束的消息，只当提醒，不依赖它。不要让 Andy 来通知。
- 收回结果：先运行 `node scripts/model-review/delegate.mjs check` 加交出时的同一组参数（`--apply` 通过后快进合并）。它只 `git fetch`，不检出新提交，用的是 Mac 本地这份脚本，云端改过的脚本不会被执行。它核对：远端分支头是交出点的后续提交（没被强推，否则 `DELEGATION_REWRITTEN`；git 自己出错则以 `DELEGATE_GIT_FAILED` 停下，不当成强推）；交出点之后没有合并提交（`DELEGATION_MERGE_COMMIT`）、每个提交和最终差异都只碰这次的记录目录（`DELEGATION_OUTSIDE_RECORDS`，逐提交检查，所以“改了又还原”也拦得住）、除补跑改名外没有删除文件（只允许删除被改名成 `.attempt-N.stderr.txt` 的旧报错文件；答案和提示词文件是改写，不是删除）、没有符号链接等非普通文件（`DELEGATION_IRREGULAR_FILE`）；`usage.jsonl` 只在末尾追加（`DELEGATION_LEDGER_REWRITTEN`），追加的行不能和交出点账本里已有的某一行完全相同（`DELEGATION_LEDGER_DUPLICATE`）；新记录的 `mode`、`head`、`base`、`previous` 和交出时一致，`round` 等于预期的下一轮（补跑则等于 `--round`），预期的模型每个都有记录（`absent=`），经 Magpie，服务方在允许范围内（没写 `--providers` 时以交出点那个提交里的 `gateway.json` 为准，读不到、不是合法 JSON 或缺 `providers` 则 `DELEGATION_NO_GATEWAY_CONFIG`，账本里的 `none`、`unknown` 两个占位照收），每条都有模型答案和提示词文件且提示词文件的哈希对得上账本（`promptFileSha256`）；改动的文件只能是预期那一轮、新记录对应模型的 `<模型>.md`、`<模型>.prompt.md`、`<模型>.stderr.txt`，以及补跑留下的 `<模型>.attempt-<数字>.` 加这三种后缀的文件，旧文件、逐条判断、材料都不能动（`unexpected-file=`），以上不符统一是 `DELEGATION_RECORD_MISMATCH`。预期的下一轮既看账本，也看交出点里已有的 `round-N/` 目录；新记录里的任何字段或键带控制字符或不可见的格式字符（例如改变文字方向的字符）都直接拒绝（`DELEGATION_CONTROL_CHARACTER`）。花费按复核脚本自己的口径算，有费用未知或在途请求的记录会在汇总行加 `estimated=true`。某个模型在这一轮里没有任何 `outcome` 为 `ok` 的记录（本模型的，或由别的模型顶替它的）时，`check` 照样接受这些记录（钱已经花了），但打印 `DELEGATION_RESULT_INCOMPLETE … not-ok=<模型>` 并以 4 退出，由 Mac 线程决定补跑。花费以账本为准，不信消息里转抄的数字。没有新提交时打印 `DELEGATION_PENDING` 并以 3 结束，被拒绝时以 5 结束，不要采用、告诉 Andy。通过后 `--apply` 合并的是刚核对过的那个提交，不是会变的远端引用；它要求本地分支头还是交出点（`DELEGATION_LOCAL_MOVED`），这就是交出期间 Mac 线程对这个分支不做任何提交的原因。
- 云端线程补跑：某个模型的 `outcome` 是 `timeout` 或 `no-text` 时，云端线程只对那一个模型用 `--round <序号> --models <模型>` 补跑一次，仍受 `--approved-usd` 和先问门槛约束；其他失败不重跑，原样报告，由 Mac 线程决定。
- 提交前检查：`npm run check:gitleaks`（`package.json` 里的 `check:gitleaks`，也是 `npm run check` 的一步，见[交付模式](delivery-mode.md#fast-mode)）已经存在，云端线程提交记录之前必须先运行它，因为模型写出的意见里可能有长得像密钥的文字（事故 I-90）。它以 `GITLEAKS_GATE_FAILED` 失败时，先看命中的是不是这一轮新写的记录：是就按它打印的办法处理，不是就在汇报里写明命中在哪个文件、和这次的记录无关。
- 费用：每次交出会多开一个云端会话，按 Claude 标价折算每次约 0.4 到 1.1 美元（PR 291、PR 296 两次实测），算在 Andy 的 Claude 账号额度里，不进复核账本；Andy 2026-11-08 定：每次交出不再单独问，汇报里写明开了哪个会话。复核模型的花费照旧进账本、照旧先问。
- 叫停和换服务方：Andy 可以直接对那个云端会话说，按[Andy 怎样控制复核](#owner-control)做；也可以对 Mac 线程说，Mac 线程再转给云端会话。
- 局限：云端线程是另一个 Claude，可能不照任务说明做，所以结果一律先 `check` 再采用；账本记录本身仍被信任（“防误操作，不防有意”）。云端线程跑的 `scripts/` 和 `package.json` 来自被复核的分支，和上文“PR 都是本项目自己的线程写的”是同一个前提，这里不另设防；`check` 里的 git 命令有 2 分钟超时，超时按 `DELEGATE_GIT_FAILED`（退出码 2）停下。

<a id="gateway"></a>
## 经 Magpie 调用模型

加 `--gateway magpie` 时（[ADR 0178](../../docs/adr/0178-review-model-calls-through-a-local-magpie.md)，Andy 2026-11-07 定），复核脚本和 OpenCode 只认模型名和推理强度，由 Magpie 决定发给哪家服务方。

- 怎样选（Andy 2026-11-07 验收后定）：命令行的 `--gateway magpie` 或 `--gateway direct`（直连 Go）优先；没写时看环境变量 `HIMAWARI_REVIEW_GATEWAY`（只认 `magpie`、`direct`，别的值以 `ARG_INVALID HIMAWARI_REVIEW_GATEWAY` 停下）；都没有就直连 Go。云端环境 himawari-cloud 把这个变量设成 `magpie`，所以云端线程不用加参数；Mac 上没有出口代理代填凭证，不设这个变量；Mac 线程不在本机跑复核，交给云端线程（见[Mac 线程把复核交给云端线程](#delegate)），只有 Andy 说“直连 Go”才在本机直连。Magpie 装不上或预检失败时，复核以对应的错误码停下，不会悄悄改成直连；要直连就显式加 `--gateway direct`。`vitest.workspace.ts` 给 tooling 测试把这个变量清空，测试的结果不受云端环境影响。

- 服务方和顺序写在 `scripts/model-review/gateway.json`（不含任何密钥），读入时逐项校验，缺字段、服务方名拼错、数字不合法、积分底线不大于 0、积分服务方不是带登录的插件，都以 `GATEWAY_CONFIG_INVALID` 停下，不会让积分底线悄悄失效：两个模型的成员都是 CodeBuddy 国际版、OpenDesign（包月，接口 `amr-link.open-design.ai`）、OpenCode Go，按这个顺序排，路由组名是 `review-<模型短名>`，`routing=order`、`stays=session`（Andy 2026-11-07 定：先 CodeBuddy，再 OpenDesign，最后 Go；前一家用不了才换下一家；同一次复核固定在同一个账号，换过去后不再切回）。Magpie 的默认策略 `smart`（在还有余量的套餐里先用最快续费的那家）试过：Magpie 只读得到 CodeBuddy 的额度，读不到 OpenDesign 和 Go（Go 要在网络密钥里放开 `/zen/go/` 路径），实测 6 次独立会话三家轮流接到请求，不是按到期时间挑，所以不用。自定义服务方的 `models` 必须是非空字符串，路由组里写的 `<服务方 id>/<模型名>` 必须在它的 `models` 里，否则报 `models.<模型>.custom`。
- 新增一家服务方（例如新开一个套餐）分两步，都不用改代码：
  1. 密钥：在 claude.ai 里 himawari-cloud 环境的设置中加一条网络密钥（主机名和请求头，例如 `Authorization: Bearer` 加密钥），或者让线程弹出安全表单由 Andy 填。密钥只存在出口代理里，不进仓库、容器和 Magpie 的配置；Magpie 发出的是假密钥，出口代理在请求离开容器时换成真的。
  2. 服务方：在 `gateway.json` 的 `providers` 里加一项（OpenAI 兼容接口写 `kind: "custom"`、`url` 和 `models`；Magpie 认识的服务方写 `kind: "preset"`，地址不同再加 `url`），再把 `<服务方 id>/<它那边的模型名>` 加进两个复核模型的 `members`，排在想要的位置（`routing=order` 时越靠前越先用）。改完跑 `--self-check-only --gateway magpie` 和 `test/tooling/review-gateway.test.mjs`，按代码复核流程合并。自检用的是本机假服务方，不检查真服务方；真服务方的模型名在第一次真实复核开跑前核对：Magpie 的模型清单只列出服务方自己 `/models` 里有的模型（2026-11-07 实测：模型名拼错时清单里没有它），成员缺失的那一家这次被去掉（见下文“开跑前”）。
  - 限制：新服务方必须提供同样的两个模型（读入配置时检查，两个模型的服务方不同就报 `models.providers-differ`）；美元折算和每个模型 0.2 美元的上限都按 `gateway.json` 里每个模型的一份单价算（现在是 Go 的单价），新服务方按量付费且单价更高时，要先让每家服务方能写自己的单价再接入；按量付费的服务方同样受“花钱先问”和“禁用贵模型”约束；积分底线只对 CodeBuddy 有效，别家额度用完时靠 Magpie 换下一家。
- 真凭证都在云端环境（himawari-cloud）的网络密钥里，由出口代理补上：`www.workbuddy.ai`（CodeBuddy 国际版的登录凭证，一年有效，能操作整个账号；撤销就删掉这条网络密钥）、`amr-link.open-design.ai`（OpenDesign 的 API key）和 `opencode.ai`。容器里只放假凭证 `proxy-injected`，Magpie 发给三家的都是它，出口代理按主机换成真的。所以这个开关现在只适用于云端会话；Mac 上要用还得另做登录。
- 版本锁在 `scripts/model-review/gateway-lock.json`（Magpie 命令行版四个平台的下载地址和 SHA-256、CodeBuddy 插件的版本和 npm integrity）。`node scripts/model-review/gateway.mjs install` 按锁文件安装到 `~/.cache/himawari-magpie-<版本>-<锁文件摘要前 12 位>`，摘要不符就删掉并报 `GATEWAY_INTEGRITY_MISMATCH`；复核脚本发现没装时，按同一份锁文件自己安装（不做 Bun 预热，第一次加载插件时 Magpie 再下载 Bun）。升级用 `node scripts/model-review/gateway.mjs upgrade`（取官方更新源的最新版写进锁文件），升级后跑 `--self-check-only --gateway magpie` 和 `test/tooling/review-gateway.test.mjs` 再提交。每次运行前后都核对 Magpie 程序的摘要，不符报 `GATEWAY_BINARY_CHANGED`；CodeBuddy 插件只在安装时按 npm integrity 核对，之后不再逐次核对。
- 每次运行在临时目录里起一个全新的 Magpie（配置、用量记录、插件登录都在里面，跑完随临时目录删除），监听回环地址的空闲端口。OpenCode 进程的 `NO_PROXY` 加上回环地址，直连 Magpie，不经过出口代理；还设 `OPENCODE_ENABLE_EXA=1`，否则方案讨论没有网页搜索工具；代码复核也设，网页工具照样被权限禁止，经 Magpie 的代码复核自检会核对工具表。
- 开跑前：带了 `--providers` 时，没列出的服务方不配置、不登录，打印 `GATEWAY_PROVIDER_DROPPED <服务方> requested`；列出的服务方里某个要跑的模型没有成员时，在花钱前以 `GATEWAY_PREFLIGHT_FAILED` 停下，不换回没列出的服务方；列出的 id 不在 `gateway.json` 里时以 `ARG_INVALID --providers <id>` 停下，不经 Magpie 却给了它以 `ARG_PROVIDERS_NEED_GATEWAY` 停下。CodeBuddy 在这一次的服务方里时，经代理查它的账号编号，经 Magpie 查剩余积分（打印 `GATEWAY_CREDITS`），积分底线照旧，`--providers` 绕不过它。剩余减去预留低于 20，或查不到，就这次不用 CodeBuddy，先 OpenDesign 再 Go（打印 `GATEWAY_CREDIT_FLOOR` 和原因）。带着 CodeBuddy 启动 Magpie 失败时，同样去掉 CodeBuddy（打印 `GATEWAY_CREDIT_FLOOR … start-failed` 和原因）；去掉后也启动失败，才以 `GATEWAY_PREFLIGHT_FAILED` 停下。预留 = 模型数 × 0.2 美元 × 积分/美元换算比（只跑 DeepSeek、出错时可能由 GLM 顶上的代码复核轮次，按两个模型算），换算比取账本里只用了 CodeBuddy 的运行中最大的那个，且不低于 `gateway.json` 的 `defaultCreditsPerUsd`（实测 54）。然后核对本次要跑的模型的每个路由组成员都在 Magpie 的模型清单里；某一家的成员不在清单里（Magpie 建组时说不认识这个模型，或起来后的模型清单里没有它），这次就去掉这一家，打印 `GATEWAY_PROVIDER_DROPPED <服务方> missing=<成员>`，账本的 `gatewayDropped` 记下，复核照常用其余几家（Andy 2026-11-08 定：几家服务方是主备关系，一家连不上不能让复核停下；顺序只是因为前面的便宜）。去掉之后任何一个要跑的模型没有成员可用时，以 `GATEWAY_PREFLIGHT_FAILED` 停下，不发任何模型请求。某一家连不上、但 Magpie 仍把它的模型列出来时（2026-11-08 实测接口主机不存在时就是这样），开跑前发现不了，由 Magpie 在请求失败时换下一家。积分卡片的百分比和已用积分对不上时，按查不到处理。
- 花费上限不变：OpenCode 配置里按 Go 的单价写模型价格，现有的费用插件照旧在请求发出前拦，每个模型 0.2 美元、先问线都照旧。账本每条记录多两个字段：`gateway: "magpie"` 和 `providers`（每家服务方的请求数、失败数，CodeBuddy 记 `credits`，Go 按单价折算 `usd`：Magpie 记的 `out` 已经包含思考 token，`reasoning` 只是其中的明细，所以按 `in`、`out`、`cache_read` 三项折算，不再把 `reasoning` 加一遍；2026-11-13 以前的账本把思考 token 算了两遍，DeepSeek 代码复核的账面费用因此比实际多约三成）；读不到 Magpie 的用量记录（读两次条数一致才算读到），记录里有不是 JSON 对象的行，复核路由组的成功请求缺 token 或积分、Go 这类按美元计价的服务方的失败请求缺 token、或者这些值不是数字（读不懂的行只算到它所属的模型，不是 JSON 对象的行两个模型都算），服务方名不在配置里，或者 Magpie 记下的这个模型的请求数少于费用插件放行的请求数（取 OpenCode 记的步数和放行次数中较大的那个），都记 `costUnknown`，并记 `costUnknownWhy`（读不懂几行、Magpie 记下几次、费用插件放行几次；读不到用量记录记 `usage-unreadable`），打印 `GATEWAY_COST_UNKNOWN <模型> <原因>`，把这次的 Magpie 用量记录存到本轮原始目录的 `<模型>.magpie-usage.jsonl` 供排查；没发过请求又读不到用量记录时不记，账本这一行照样写下。这次不用 CodeBuddy 时，账本记 `gatewayDropped`。Magpie 记录的 Go 实际花费（按单价折算）高于 OpenCode 算的费用时（例如回答到一半断开后 Magpie 重发），账本的 `cost` 取较大的那个，原值记在 `costFromProviders`；这是事后修正账本，运行中的 0.2 美元上限只看得到 OpenCode 算的费用。运行结束打印 `GATEWAY_USAGE`，这次去掉了服务方时末尾带 `dropped=`。每条记录还记耗时：`selfCheckMs`（自检）、`selfCheckCache`（自检缓存 `hit`、`miss` 或 `off`，旧记录没有）、`runMs`（这个模型从启动到结束），经 Magpie 时另记 `gatewayTiming`（请求数 `requests`、各次请求耗时之和 `modelMs`、等第一个字的时间之和 `firstTokenMs`、最慢一次 `slowestMs`、提示缓存没命中的次数 `cacheMisses` 和这几次按全价算的输入 token `missTokens`；没命中指这次读到的缓存不到同一会话上一次请求的一半），并打印 `REVIEW_TIMING`；Magpie 因额度用完、报错等原因暂停使用某家服务方时，打印 `GATEWAY_REST <服务方> <原因> <状态码> <恢复时间>`，用来解释这次为什么换到了后面的服务方；Magpie 的暂停记录读不出时打印 `GATEWAY_REST - unreadable:<原因> - -`。这两行只在运行时打印（委托复核时由云端线程转述），`--report` 不含；耗时数字留在账本里。脚本结束或收到中断信号时，停掉它启动过的所有 Magpie，包括自检用的。
- 自检：原有探针全部经自检专用的 Magpie 发到本机假服务器；输出上限按 `gateway.json` 的声明值核对（DeepSeek 12.8 万，GLM 3.2 万）。另加四项：透传探针（同一提示直连和经 Magpie 各发一次 DeepSeek，只在系统消息里把 OpenCode 写进去的模型名换回直连写法后，第一条带工具的请求的 `messages` 和 `tools` 序列化结果必须相同，提示里的假邮箱不得被遮盖，`GATEWAY_PASSTHROUGH_*`）、故障转移探针（第一个成员返回 500，必须换到第二个，`GATEWAY_FAILOVER_*`）、费用计入检查（经 Magpie 时 OpenCode 给这次探针运行算出的费用必须大于 0，否则美元上限不起作用，`GATEWAY_COST_NOT_COUNTED`）、程序摘要检查。Magpie 的敏感信息遮盖保持关闭（它默认就关）；遮盖被打开且会遮邮箱时，透传探针会失败。
- 已知例外：CodeBuddy 以 11128 拒绝某段系统提示时，插件会给它加逗号重发或挪进第一条用户消息，改变已发出的请求开头。这是 Andy 同意的受控例外，见 ADR 0178。

# 和 OpenCode 协作：方案讨论和代码复核

用 `opencode-go/deepseek-v4.1-flash` 和 `opencode-go/glm-5.3-flash` 两个模型，推理强度都设为高，各看一遍。只能用这两个模型（Andy 在项目指令第 17 条规定）。一律用 `node scripts/model-review/opencode-review.mjs` 跑（见[怎么跑](#how-to-run)）。交给它们的材料只讲问题、目标、约束和已核对的事实，不预设结论，脚本会自动加上项目指令第 16 条的原话：列出的方案只是参考，请从问题本身出发，提出你认为更好的方案。

<a id="plan-discussion"></a>
## 写代码之前：方案讨论

动手写代码之前要出方案的任务都走这三步；项目规则里的大改动（见[修 bug 和做新功能](../../.claude/rules/owner-standing-rules.md#fixing-bugs-and-new-features)）一定要走。修小 bug 不用。

1. 独立出方案（`--mode plan`）：线程先把自己的方案写好存着，不给模型看。材料只写问题、目标、约束、已核对的事实和查到的一手资料，不写线程的方案或倾向。两个模型各自读代码、上网搜索，各出一套方案。
2. 审核线程的方案（`--mode plan-review`）：把线程的方案发给两个模型，请它们找漏掉的场景、判断错的地方、和业界成熟做法不一致的地方。先独立、后审核，是为了不让模型顺着线程的思路走。
3. 线程整合：线程把两个模型的方案、审核意见和自己的方案逐条比较，自己先判断每一条采纳还是不采纳、为什么、最后建议怎么做，线程自己的方案也一样要过这一遍。交给 Andy 的是一份整合后的方案：开头按[方案的前提](../../.claude/rules/proposal-premises.md)列前提和来源，然后是方案，最后只列真正需要他拍板的几项取舍。三方的原始方案和逐条判断作为附件，不要求 Andy 逐条看。Andy 同意后才写代码。

<a id="code-review"></a>
## 合并之前：代码复核

1. 合并前对 PR 的最终提交做一次完整复核（`--mode code-review`，不传 `--previous`）。开 PR 前不另做。
2. 分类由线程做，不由模型做。线程对每一条意见逐条核对，每条都写下判断和依据（文件:行或实际运行结果），先判断它成不成立，再把成立的意见分成两类：
   - 会出错：照现在的代码，只要存在一种输入或使用方式（包括不合规范的、恶意的或不可信的输入）会让功能出错、丢数据、出安全漏洞，或造成其他实质损害（例如资源耗尽、无法撤销的破坏性操作），即使现有测试没有走到那条路径；或者一个已经确认的错误（包括本 PR 刚修好的）缺了能证明它的测试用例。这类意见必须改代码。
   - 可以更好：不改变任何可观察行为，只是写法、结构、命名、说明还能更好；或者建议补的测试用现在的代码跑也会通过（证明已确认错误的回归测试除外，它属于“会出错”）。这类意见不改代码，也不因为它再复核一轮。
   - 拿不准它成不成立、或属于哪一类的，都按“会出错”处理；判为不成立必须给出能核对的反证。
3. 按“会出错”的意见改了代码，就对这些改动再复核一轮（传 `--previous <上一轮复核的提交>`，模型先看增量），一直到线程核对后没有“会出错”的意见为止，第 4 步的停止条件除外。
4. 每多跑一轮之前，在汇报里写明已花的累计费用；这一个 PR 的复核累计费用（已花的加上这一轮预计的）会超过 1 美元时，先问 Andy；费用说不准时按会超过处理（Andy 2026-11-03 为 PR 复核定的先问门槛，不是硬上限；其他花钱仍按 0.5 美元先问）。第 1 步的完整复核算第 1 轮，之后每次复核算一轮，包括第 5 步引起的复核。一轮里只要有线程判定要改的“会出错”意见，这一轮就算没过；线程已经写明理由判为不成立或“可以更好”的意见，后面的轮次再提，不算新的“会出错”意见；但这条意见涉及的代码后来改过，或者模型给出了新的证据（例如具体的失败输入、复现步骤或运行结果，即使文字和上次一样），线程要重新判断并把判断和依据写下来，维持原判也一样；改判为“会出错”的照常算。连续三轮没过，就停下报告 Andy，列出还没解决的“会出错”意见，等他决定，不要一直循环；Andy 作出决定后，连续的轮数从头算。
5. 报告 Andy 时，把各轮所有“可以更好”的意见一起列给他：每条写清是什么、线程建议采纳还是不采纳、为什么。判为不成立的意见和理由放在附件里，不要求他逐条看。只有 Andy 说可以采纳的才改；采纳的改动属于这个 PR，改完按第 3 步对改动再复核，再报告一次。Andy 说“合并”才合并。

<a id="checklist"></a>
## 每次都要问的问题

1. 这个改动会不会改变模型已经见过的请求开头？包括系统提示、工具定义、历史消息、遮盖结果。要求回答：发给模型的内容是不是仍然只在末尾追加，每轮会变的值是不是都在最后一条消息里。依据：[发给模型的内容只追加](../../.claude/rules/prompt-prefix.md#rules)。
2. 这个改动会不会让同一段文字在不同请求里变成不同的字节（例如依赖前后文的遮盖、带时间的字段、无序的集合）？
3. 改动有没有对应的自动检查，反向用例是否真的会失败？

<a id="how-to-run"></a>
## 怎么跑

用 `node scripts/model-review/opencode-review.mjs` 跑，不要自己拼 `opencode run` 命令。它做这些事（Andy 2026-11-03 定）：

- 模型自己读代码：只开读文件、按内容搜索、按文件名找文件，以及 `git diff`、`git log`、`git show`、`git blame`、`git status`；改文件、别的命令、派子代理、仓库外的路径全部禁止。git 命令里的重定向（`>`、`<`）、制表符、`difftool`（它能执行任意命令）、写文件参数（`--output`、`-o`）、读仓库外文件的参数（`--no-index`、`--contents`）、外部程序参数（`--ext-diff`、`--textconv`）另行禁止。opencode 只按命令文字匹配，引号和反斜杠能绕过（实测 `"--output=文件"` 照样写出文件），所以脚本还在模型用的 `PATH` 最前面放了一个 git 替身：它拿到的是 shell 解析后的真实参数，子命令不在上面五个里、参数是这些禁用参数及其缩写、或是会读文件的 `--ignore-revs-file`、`--pathspec-from-file`、`--mailmap-file`、`--orderfile`、`blame -S`、打开帮助程序的 `--help`，或者短参数连写里藏着 `-o`、`-O`（如 `-pO文件`）就拒绝，否则才交给真的 git；同时用 `GIT_TEST_DISALLOW_ABBREVIATED_OPTIONS` 让 git 自己也拒绝缩写，并不读系统和用户的 git 配置。opencode 的文字规则还漏掉了 `cd 副本 && git log > 文件` 这种写法（实测写出了文件），所以模型的命令改在受限 bash（`bash -r`，bash 自带的模式：不许输出重定向、不许 `cd`、不许改 `PATH`、不许用带斜杠的命令名）里执行。git 替身调用真 git 之前会去掉所有 `GIT_*`、`LD_*` 等环境变量，只留 `PATH`、`HOME`、`LANG` 和固定的 git 设置，所以模型先 `export GIT_EXTERNAL_DIFF=程序` 再跑 `git diff` 也不能让 git 执行别的程序（第五轮复核实测过这种写法）。这套限制防的是复核模型误操作（顺手改了文件、跑了别的命令、上了网），不防有人故意在 PR 里埋恶意代码：PR 都是本项目自己的线程写的，复核又跑在用完即删的云端容器里。Andy 2026-11-03 定：这是开发协作工具，不是 Himawari 的功能，不用系统级沙箱，也不再为后一种情况加固；复核材料不要再让模型专门去找这类绕过办法。原因：系统的真相在代码里，只读线程给的材料，材料错了复核就跟着错。
- 代码复核（`--mode code-review`）不联网；方案讨论的两个模式（`--mode plan`、`--mode plan-review`）可以用 opencode 自带的搜索和读网页工具（Andy 2026-11-03 定）。搜索走 opencode 内置的 Exa 免费搜索服务，不花 Andy 的钱，只是搜索结果会算进模型的输入 token。
- 必问问题从 `--base` 提交里的本文件读（方案讨论不传 `--base` 时从 `--head` 提交读），不从被复核的改动或工作区读，免得改动自己改掉要问的问题。
- 第一次运行会联网用 npm 安装 `opencode-ai@1.19.5` 到 `~/.cache/himawari-opencode-1.19.5`，之后复用；也可以用 `HIMAWARI_OPENCODE_BIN` 指定已装好的程序。
- 在 PR 最新提交的一次性副本里运行：副本是干净克隆，只有提交过的文件。历史里任何一个提交（包括合并提交）的文件树里出现过 `.env` 一类文件（`.env.example` 这类模板除外）就拒绝复核，因为 git 命令能从历史里读出它。副本删掉了远程地址、引用日志（reflog，记录分支移动的日志，里面有原仓库路径）和 `FETCH_HEAD`，用完即删，脚本收到中断或结束信号（`SIGINT`、`SIGTERM`）时也会删；被强杀（`SIGKILL`）时删不掉。副本里 PR 自带的 `.opencode/`、`opencode.json(c)`、提交进仓库的 `.env*` 文件和指向副本外的符号链接会先删掉，因为 opencode 启动时会执行项目目录里的插件，符号链接能把读文件带出副本；配置改从副本外的文件读。副本里的分支和标签全部删掉，只留 `refs/review/head`、`refs/review/base`、`refs/review/previous` 三个引用；其他提交的对象还在，知道哈希仍能读到。opencode 的全局配置（`~/.config/opencode`）不会被读入，脚本给它一个空的配置目录。
- 把 opencode 默认写死的 32 000 输出上限调高（`OPENCODE_EXPERIMENTAL_OUTPUT_TOKEN_MAX` 设为 200 000），DeepSeek 高推理时不再被截断。opencode 会再按模型目录里的上限往下调：2026-11-03 抓包实测 DeepSeek 请求是 200 000，GLM 是 131 072（GLM 的模型上限）。
- 开跑前先对本机假服务器自检，不花钱：让假模型发出一条正常的 `git log`、十几种写文件的命令（含引号、反斜杠、缩写、`difftool` 等绕过写法），以及用 git、读文件、搜索、找文件四种工具读仓库外文件的尝试。正常命令必须能跑；写文件命令既写到副本外，也写到副本里（含先 `cd` 再重定向）；每条写文件命令和每条读仓库外的 git 命令都必须被明确拒绝，只认 opencode 的权限拒绝、git 替身的 `REVIEW_GIT_REFUSED` 和受限 bash 的 `restricted` 三种文字，因别的原因失败（如目录不存在）同样算失败；读仓库外的尝试不能拿到内容；探针按内容对号，不按顺序。读文件、搜索、找文件三种工具读仓库外也必须被明确拒绝。另有几条先 `export` git 环境变量再跑 git 的探针（让 git 去执行 `env`、`touch`），要求看不到父进程里的标记、副本没有任何改动；每个模型跑完都检查副本的 `git status`，有改动就算失败。五个允许的 git 子命令各有一条必须跑通的探针；受限 bash 外壳每次启动都记一笔，记录数少于这五条就说明 opencode 没有用它，算失败；opencode 发给模型的系统提示里不能出现副本里 `AGENTS.md` 的标题（PR 自带的项目指令不能变成复核模型的指令）；读仓库外的探针也包括 `../` 这种相对路径；`max_tokens` 不能低于 10 万，也不能高于该模型能接受的上限。工具表、输出上限、推理强度也要对。`; touch`、`| tee`、`$(...)` 这类复合命令被拒，靠的是 opencode 把命令按片段分别判断权限（opencode 1.19.5 实测如此）；升级 opencode 后自检突然失败，先查这一点。任何一项不对就以 `SELF_CHECK_FAILED` 停下。
- 两个模型并行，结果写到 `--out` 目录；每次的真实用量（输入、输出、推理、缓存命中 token 和费用）追加到其中的 `usage.jsonl`。一次运行里每个模型累计费用超过 0.2 美元就停掉它（只管这一次运行；同一个 PR 多轮复核的总花费不归脚本管，由线程按上面的规则汇报），某一步的费用读不出来也停（标 `cost-unknown`），不当作 0；费用是每一步结束后才知道的，最后一步可能略超，所以两个合计约 0.4 美元加最后一步，仍在 0.5 美元内。超时先发结束信号，10 秒不退再强杀。被截断、超时、超费用、进程出错、被信号杀掉或没出文字时退出码为 4，按 `usage.jsonl` 里的 `outcome` 处理，不要原样重跑。

用法：

```
node scripts/model-review/opencode-review.mjs --mode code-review \
  --base <分叉点提交> --head <PR 最新提交> [--previous <上一轮复核的提交>] \
  --brief <作者说明.md> --out <结果目录>

node scripts/model-review/opencode-review.mjs --mode plan \
  --head <当前提交> --brief <问题、目标、约束.md> --out <结果目录>

node scripts/model-review/opencode-review.mjs --mode plan-review \
  --head <当前提交> --brief <线程的方案.md> --out <结果目录>
```

`--brief` 只写这次的材料：代码复核写问题、目标、约束和作者的说法；`plan` 只写问题、目标、约束和已核对的事实，不写线程的方案；`plan-review` 写线程的方案。脚本会在前面加上各模式的固定说明（上面的必问问题、项目指令第 16 条原话、该模式的任务和输出格式），代码复核还会让模型自己用 `git diff` 看改动。提交可以写分支名，脚本先在原仓库解析成提交哈希。按意见修改后的复核传 `--previous`，模型先看增量，但可以读任何文件。

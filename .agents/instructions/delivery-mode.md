# Delivery Mode

The user decided on 2026-10-25 ([ADR 0073](../../docs/adr/0073-fast-delivery-mode.md), superseded on 2026-10-26 by [ADR 0080](../../docs/adr/0080-document-governance-in-fast-mode.md), which keeps every other rule and adds back documentation validation) that while the user is the only user and needs a complete product in front of investors, development must not wait on rehearsals and gates. The file `DELIVERY_MODE` at the repository root holds one word:

- `fast`: fast mode. The rules in [Fast mode](#fast-mode) replace the rules they name, for Claude, Codex, opencode, Grok, and every other agent.
- `full`, any other content, or no file: full mode. Every other project rule applies as written.

Only the user switches the mode. Change `DELIVERY_MODE` only when the user asks for it in their own words, in a commit of its own.

<a id="fast-mode"></a>

## Fast mode

Keep these basic checks for every change to product code, configuration, or tests:

1. The targeted tests for the change: the new or reproducing test and the files `python3 "$(git rev-parse --git-common-dir)/hooks/check-layer0-tests.py" derive` lists. A bug fix still starts by reproducing the bug in a test.
2. `npm run check` (format, lint, type checks, module boundaries, coverage and invariant checks, the machine-secret scan, and strict documentation validation).
3. `npm run build`.

Run them on the cloud server as `himawari-ci` or on Hermes, as [Test and Production Hosts](test-and-production-hosts.md) says; never on the MacBook. A failing basic check blocks the commit like before.

These rules are suspended in fast mode:

- [Test Trigger Timing](test-trigger-timing.md): no Layer 2 (whole affected Vitest projects), no Layer 3 (full `npm test`), no Layer 4 (installed product path on Hermes), no browser qualification, and no `require-quiet-host.sh` unless a run is a comparison measurement the user asked for. Run a wider test only when the change is risky in a way the basic checks cannot see (for example a database migration) and say so in one line.
- [ADR 0066](../../docs/adr/0066-layer0-related-tests-declared.md) commit lines: `Layer-0-tests:` lines are not required; the `commit-msg` and `pre-push` hooks print `DELIVERY_MODE_FAST_SKIP_LAYER0` and let the commit through. Commit messages list the basic checks that actually ran, on which host and revision, in one `Fast-mode-checks:` line.
- The `AGENTS.md` section "Code and Documentation Consistency", replaced by a lighter rule since 2026-10-26 ([ADR 0080](../../docs/adr/0080-document-governance-in-fast-mode.md)): strict documentation validation still runs before every commit as `npm run check:docs`, part of `npm run check`, and blocks every finding except a stale Runbook seal (`contract_sha256 does not match` or `contract path does not exist`). Runbook reseals and the full drift reconciliation wait for full mode. The `document-governance` skill is still used for new ADRs, Backlog items, Ideas, and documents a change makes plainly wrong, as [.claude/rules/document-governance.md](../../.claude/rules/document-governance.md) says. Commit messages that leave documents behind, including stale Runbook seals, carry `Docs: deferred (fast mode)`.
- The GitHub merge gate: merging into `main` does not wait for `ci/required`. CI still runs; a red result is information, not a blocker. The user switches the ruleset with `scripts/delivery-mode/github-ruleset.sh fast|full`, which only the user runs.
- Production operation packets: no S0 readback, packet freeze, consistency review, Hermes rehearsal, per-deployment authorization round, or limited-host acceptance decision. Since 2026-10-25 ([ADR 0074](../../docs/adr/0074-claude-runs-production-deployments.md)) Claude runs production changes itself: the user asking for a deployment in their own words (for example "上线") is the authorization, and Claude runs `bash scripts/delivery-mode/deploy.sh <frozen packet directory>` where the packet and the root SSH key are (the MacBook through a Remote Control session, because cloud sessions cannot reach the production server's SSH port). The script first refuses to start (exit 5, result `no-browser-acceptance`, nothing on the server touched) unless `<packet>/browser-acceptance/walkthrough.json` exists, names the SHA-256 of the packet's candidate archive, and records every check of the product-path test "release acceptance in a real browser" as passed: the home page opens, the web-search switch in Settings can be ticked, a news search returns results, a long answer shows in full, the memory page opens, and after a service restart the already open page can still use the switch and search. Claude runs that test on Hermes against the exact artifact the packet ships and copies its `browser-acceptance.json` there; a release check that only reads the home page status is not acceptance. Before any step the script checks over SSH that it reached the production host as root, that the service is active and that `/opt` and the state disk have twice the packet size free; it writes everything to `<packet>/run-logs/deploy-<time>.log` and ends with one `DEPLOY_RESULT {json}` line that Claude reads and reports; after a pass it prunes rebuildable files of older packets as [Disk Space Hygiene](disk-space-hygiene.md) says. A failure before `S2_STOP` leaves the old release running; a failure at or after `S2_STOP` runs `rollback.sh` at once, because restoring service comes first. Checking the result after deployment is Claude's readback plus the user trying the product. When the user asks to go back, Claude runs `bash scripts/delivery-mode/rollback.sh <the same packet directory>` (log in `<packet>/run-logs/rollback-<time>.log`). It stops the service and, when the deployment had already changed the database, configuration or unit, writes the rollback approval file, sets the `authority.json` mirror back to the deployment row in the recovery point (the new release advances the fencing token, and the old release refuses a mirror ahead of its database), runs the packet's S2_INSPECT, optional S9_SIDECAR_TIDY, S9 restore and S9 control steps, and then starts the old release and checks that it keeps running. Everything written after the recovery point is lost.
- Production access: Claude may log in to `84.247.157.41` as `root` or `himawari-prod` to deploy, roll back and diagnose, and may read `/opt/himawari`, `/etc/himawari` and `/var/lib/himawari` for that purpose (user decisions, 2026-10-25T14:41Z and 15:46Z). Before any destructive step (stopping the service, changing configuration, deleting data) Claude checks the evidence and backs up first; every check in a hand-written script goes before the stop; system commands use absolute paths such as `/usr/sbin/runuser`; when something fails, Claude restores service first and investigates afterwards. Claude never prints, copies off the server, or commits a production secret, never runs tests as a production account, and tells the user afterwards what it ran.

These rules stay in force in fast mode: never run Himawari tests on the MacBook; the Hermes SSH wrappers and test-account boundaries; no code comments; exact dependency versions and the Pi-first principle; pushing every commit; the disk space rules.

<a id="back-to-full"></a>

## Switching back to full mode

When the user asks, commit `full` to `DELIVERY_MODE`, then in one catch-up task: run `npm run check:docs`, which now blocks every finding, and fix every error, review and reseal the Runbooks whose contract sources changed, update the documents left behind by `Docs: deferred (fast mode)` commits, run Layer 3 and the affected Layer 4 scenarios on Hermes for the current revision, and ask the user to run `scripts/delivery-mode/github-ruleset.sh full`.

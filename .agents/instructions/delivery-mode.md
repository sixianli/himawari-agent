# 交付模式

在用户是唯一使用者、并需要把一个完整产品摆到投资人面前期间，开发不得等待演练和门槛。仓库根目录的文件 `DELIVERY_MODE` 只写一个词：

- `fast`：快速模式。[快速模式](#fast-mode)中的规则替换它们所点名的规则，对所有代理都适用。
- `full`、任何其他内容，或没有这个文件：完整模式。其他所有项目规则按原文适用。

只有用户能切换模式。只有当用户用自己的话要求时才修改 `DELIVERY_MODE`，并且单独作为一个提交。

<a id="fast-mode"></a>

## 快速模式

对产品代码、配置或测试的每一处改动，都保留以下基本检查：

1. 针对这次改动的定向测试：新写的或复现问题的测试，以及 `python3 scripts/layer0-tests/check-layer0-tests.py derive` 列出的文件。修复缺陷仍然要先用一个测试复现该缺陷。
2. `npm run check`（格式、lint（代码风格检查）、类型检查、模块边界、不变量检查、机器机密扫描、用锁定版本的 gitleaks（一个按规则找密钥的扫描程序）扫当前文件和当前提交的全部历史（`npm run check:gitleaks`，规则文件和白名单与 CI 的 security 作业是同一份 `ci/rules/gitleaks.toml`，所以误报在合并前就会被拦下；它比 CI 松的地方：不联网核对店主在 GitHub 上的批准评论（身份、批准记录、到期、PR 编号、来源提交是否在历史里），也不校验工作区里改过的 `ci/security-exceptions.json`，这些仍只有 CI 会拦；第一次运行时需要联网，按 `ci/toolchain-lock.json` 里的地址和摘要下载到 `~/.cache/himawari/gitleaks/<版本>/<平台>/`，可用 `HIMAWARI_GITLEAKS_CACHE` 改位置；基准提交默认是 `origin/main` 与 HEAD 的共同祖先，可用 `HIMAWARI_GITLEAKS_BASE` 指定，本地没有 `origin/main` 时要先 `git fetch origin main`）、指令文件里的链接和路径是否都还存在（`npm run check:instruction-links`）、`docs/` 里的相对链接和锚点是否都还存在（`npm run check:docs-links`）、在真实浏览器中对 Himawari 网页做的布局审查——三种语言、两种宽度、两种主题（`npm run check:layout`，约 80 秒，需要 Playwright 的 Chromium））。它不包含文档的完整校验（只有上面几步查 `docs/` 的特定部分）；改动了 `docs/` 的提交另外手动运行文档校验，见下文。
3. `npm run build`。

按 [测试主机与生产主机](test-and-production-hosts.md#where-tests-run) 的规定，在云端线程的容器里运行它们；绝不在 MacBook 上运行。基本检查失败时，和以前一样阻止提交。

以下规则在快速模式下暂停：

- [测试触发时机](test-trigger-timing.md)：不跑第 2 层（受影响的整个 Vitest 项目），不跑第 3 层（完整的 `npm test`），不跑第 4 层（已安装的产品路径），也不做浏览器资格验证。只有当改动的风险是基本检查看不到的（例如数据库迁移）时，才跑更大范围的测试，并用一行说明。
- [文档治理](document-governance.md#code-and-documentation-consistency)中的“代码与文档一致”一节被一条更轻的规则替代：严格的文档校验不再自动运行，但改动了 `docs/` 下任何文件的提交，提交前必须手动运行 `document-governance` 技能的 `validate_docs.py . --strict`，并且不得新增校验错误。完整的偏差核对等到完整模式。`document-governance` 技能仍然用于新的 ADR、Backlog 条目、Idea（想法记录）以及被改动弄得明显错误的文档，见 [文档治理](document-governance.md)。留下未更新文档的提交，其提交说明要带上 `Docs: deferred (fast mode)`。
- 合并队列暂停（Andy 2026-11-14 同意关掉它的自动触发，原话：“可以关掉”）：不给 PR 加 `merge-queue` 标签，做 PR 的线程在下面的合并门槛满足后直接调用合并接口合并。`.github/workflows/merge-queue.yml` 只保留手动触发，去掉了 CI 结束后触发和每 10 分钟的定时触发，免得它占着 CI 机器。合进 `main` 后由 `Main confirmation` 工作流跑全量测试；`main` 变红时，CI 线程马上定位是哪个 PR 引起的，由那个 PR 的线程优先修。排队的 PR 一个一个合，每合一个，后面的先合进新的 `main`。Andy 2026-11-14 同时给的“合并不等 PR 上的 CI”例外已经作废，合并一律等 `ci/required` 变绿。
- GitHub 合并门槛：合并进 `main` 之前，PR 最新提交上的 `ci/required` 必须是成功（[ADR 0292](../../docs/adr/0292-how-ci-runs-now.md)），上面的本地基本检查照样必过。PR 上的 `ci/required` 只跑基础测试和与改动相关的测试，完整测试在合进 `main` 后由 `Main confirmation` 补上（合并队列暂停期间的做法见上一条）。CI（持续集成）按 [ADR 0292](../../docs/adr/0292-how-ci-runs-now.md) 跑在 GitHub 的免费标准托管机器上（`ubuntu-24.04`、`ubuntu-24.04-arm`、`macos-26`，仓库公开所以不收费）；工作流里写别的机器标签，`npm run check:ci-policy` 会以 `HOSTED_RUNNER_REQUIRED` 拦下。草稿 PR 不跑 CI，草稿上的 `ci/required` 第一步就以 `CI_DRAFT_UNVERIFIED` 失败，不用修；线程开始代码复核时就把 PR 标成“准备合并”，CI 和复核同时跑。只改 PR 标题或正文不会触发 CI；改了目标分支要推一个新提交才会重跑。测试和 CI 都通过（`apple/iphone-e2e` 端到端测试跑了的也必须是成功；改了 iPhone 客户端的再加上 Mac 编过一次）后，线程自己合并，不等 Andy 点头，也不用外部模型复核；只有删除或不可逆地改动生产数据、花钱超过预算才先问 Andy（上线生产本身不用问）。CI 没变绿不合并：因本 PR 自己的改动变红就先查、先修；查清确实与本 PR 无关的（GitHub 故障、别处时好时坏的测试），先找到或推动修复，再重跑到变绿。Andy 2026-11-12 给的“CI 坏了可以不等 CI 合并”的授权已经作废。重跑一律用 “Re-run all jobs”。规则集是否强制要求 `ci/required` 由用户用 `scripts/delivery-mode/github-ruleset.sh fast|full` 切换，这个脚本只由用户运行。

Andy 的只有两种：删除或不可逆地改动生产数据，以及花钱超过预算。日常上线不再依赖任何人的电脑：合并进 `main` 后，`Main confirmation` 成功，GitHub 工作流 `.github/workflows/deploy-production.yml` 自动在 GitHub 的免费机器上运行 `bash Runbook](../../docs/runbooks/production-offsite-backup-runbook.md)），再出包、运行 `deploy.sh`、失败就回滚、用 `/health/ready` 读回验证）。部署用的 SSH 钥匙只存在 GitHub 的 `production` 环境密钥里（`PROD_SSH_KEY`，环境变量 `PROD_HOST`、`PROD_HOST_KEY` 固定服务器指纹），只有 `main` 分支能用；它不是 root 钥匙：服务器上单独的 `himawari-deploy` 账号，`authorized_keys` 用 `command=` 锁死成只能运行 `scripts/install/deploy-entry/himawari-deploy-entry`（经 sudoers 以 root 运行），入口只接受 `deploy <提交> <起点或-> <0|1>`，自己从公开仓库取代码并核对提交在 `main` 上，再在服务器上本机出包、上线（`scripts/install/deploy-entry/shim/` 里的 `ssh`、`scp` 把包工具对生产机的 SSH 调用改成本机执行）；放钥匙和装入口的一次性动作用 `scripts/operations/install-deploy-key.sh`（Andy 2026-11-25 原话：“对呀，那就使用成熟方案做啊”）。钥匙没放好时工作流只给出警告并跳过，不让 `main` 变红。需要手动上线或指定起点时，用工作流的手动触发（`workflow_dispatch`）。上线包绝不从以前的上线包复制，也绝不手工编辑：它由 `python3 scripts/delivery-mode/make-packet.py prepare --instance andy-production --commit <提交>` 生成（日常由上面的上线入口在服务器上运行），该命令以只读方式从生产读取正在运行的版本、原始配置上限和数据库结构，在生产机的构建账号里构建该提交，用这些值渲染 `scripts/delivery-mode/packet-template/`，在该提交的数据库结构更新时加入数据库迁移步骤，在构建账号里运行每一项上线包检查（`run-packet-checks.py`，数据库结构变化时再加上真实 CLI 的迁移夹具），把结果记录到 `packet-checks.json` 并冻结上线包；任何一项检查失败就没有上线包。无论通过还是失败，`prepare` 随后都会删除这次运行在构建账号里可重建的副本（`materials/`、检查用的上线包副本、上传的上线包压缩包和源码包；日志和报告保留）以及它在本地的 `packet-work-*` 目录。要改变上线包做的事，就修改模板或 `scripts/delivery-mode/instances/` 下的实例文件，然后重新生成。上线包和模板不绑定任何一台机器：实例文件里只写目标机器的地址和目录约定，不写主机名、CPU 架构、服务账号的数字编号（uid、gid）、Node 程序的 sha256 指纹、首次安装留下的签名公钥位置；`make-packet.py prepare` 出包时用 SSH 从目标机器读出这些值，填进模板里的 `__PKT_` 占位符，所以把生产搬到别的机器（比如 ARM 是历史名字；只支持 linux-arm64，它是生产平台，见 [ADR 0293](../../docs/adr/0293-how-production-deploys-work.md)）；Python 压缩包的指纹取自该提交的 `ci/toolchain-lock.json` 里对应架构那一项。`python3 scripts/delivery-mode/check-template-neutral.py`（`npm run check:delivery-packet` 也会跑它）会在模板或构建脚本里再出现写死的机器信息时失败；只在安装演练里用的文件列在它的 `REHEARSAL_ONLY`。如果冻结之后服务重启过或配置变过，上线前要再次运行 `python3 scripts/delivery-mode/make-packet.py freeze <packet directory>`。当 `make-packet.py prepare` 自己所在的检出不包含它要打包的提交时，它会拒绝（`PACKET_SCRIPTS_OLDER_THAN_COMMIT`）；当 `deploy.sh` 所在的检出不包含上线包的提交时，它会拒绝（退出码 7，结果 `old-scripts`，服务器上什么都不动），所以两者都要从该提交的检出运行，例如 `origin/main` 的一个临时检出。对于没有生成器的 `packet-parameters.json`、或 `packet-checks.json` 没有记录该上线包提交的每一项检查都已通过的上线包，`deploy.sh` 会拒绝（退出码 6，结果 `not-generated`，服务器上什么都不动）。脚本首先会拒绝启动（退出码 5，结果 `no-browser-acceptance`，服务器上什么都不动），除非 `<packet>/browser-acceptance/walkthrough.json` 存在、写明了上线包候选压缩包的 SHA-256，并记录产品路径测试“在真实浏览器中的发布验收”的每一项检查都已通过：首页能打开，设置里的网页搜索开关能勾选，新闻搜索能返回结果，长回答能完整显示，记忆页能打开，并且服务重启后已经打开的页面仍能使用该开关和搜索。`make-packet.py prepare` 在构建账号里针对上线包所带的那个确切产物运行这项测试（`run-release-walkthrough.sh`），并把它的 `browser-acceptance.json` 复制到那里；只读取首页状态的发布检查不算验收。在任何步骤之前，脚本先运行 `release-cleanup.py`（见下文），然后通过 SSH 检查：确实以 root 身份到达了生产主机；服务处于 active 状态；`/opt` 和状态盘的空闲空间是上线包大小的两倍；预计安装之后根盘仍留有 10 GiB 再加 1 GiB（预计安装量为：上线包大小，加上 S1 为当前在服务版本所用空间（按该版本的 `s1-result.json`）的 1.2 倍；没有该记录时为上线包大小的三倍；`PREFLIGHT_SPACE` 行会打印这些数字）；配置文件、服务单元以及 `authority.json` 的 epoch（纪元号）和 fencing token（隔离令牌）仍然是上线包冻结时的样子（否则它打印 `PREFLIGHT_REFREEZE` 并在停止服务之前停下）；生产验收步骤 `S6_ACCEPTANCE` 在 `S2_STOP` 之前运行，此时旧版本仍在服务（只有当新顺序本身失败时，才用 `HIMAWARI_DEPLOY_ACCEPTANCE_AFTER_STOP=1` 恢复旧顺序）；它把一切写入 `<packet>/run-logs/deploy-<time>.log`，并以一行 `DEPLOY_RESULT {json}` 结束，由 Claude 读取并报告；通过之后，它按 [磁盘空间整洁](disk-space-hygiene.md) 的规定清理较旧上线包中可重建的文件。`scripts/delivery-mode/release-cleanup.py <packet> apply` 在预检之前、通过之后，以及在失败但旧版本仍在服务之后运行（恢复失败之后不运行）；它在 `/opt/himawari/releases` 下只保留当前在服务的版本及其回滚目标，在 `/var/tmp` 下只保留当前在服务版本的 `packet/`，并完整保留当前在服务版本的证据；删除其他所有版本传输副本、失败尝试的操作目录，以及超过 10 MiB 的证据文件（最新的三份数据库副本除外）；把一次失败尝试的证据移到一边，以便重试可以复用该路径；先把小的报告和日志归档到 `/var/lib/himawari/release-cleanup/<time>/`；并保留服务单元、在用的 `config.json`、在用的数据库行（用 SQL 读取，而不是扫描文件）或正在运行的进程所指向的任何东西；用 `plan` 运行它可以查看它会删除什么。在 `S2_STOP` 之前失败，旧版本继续运行。在 `S2_STOP` 或之后失败时怎么办，看上线包的 `ON_DEPLOY_FAILURE`（由实例文件的 `onDeployFailure` 生成）或操作者设的环境变量 `HIMAWARI_DEPLOY_ON_FAILURE`（两者都可以是 `keep` 或 `rollback`，环境变量优先；`deploy.sh` 开头打印 `DEPLOY_ON_FAILURE <选择> from <来源>`）：`rollback` 时立即运行 `rollback.sh`；`keep` 时不回滚，打印 `DEPLOY_ROLLBACK_SKIPPED owner-choice`，以结果 `failed-kept` 结束，失败的新版本和服务器上的副本原样保留（也不运行 `release-cleanup.py`），要恢复旧版本时再手动运行 `rollback.sh`。失败在 `S7_SWITCH_START` 启动新版本之前时，旧服务已经停了、新服务还没起来，服务就停在这里，直到修好重新上线或手动回滚。同一个上线包不能直接重跑：它的预检查要求目标路径不存在（`TARGET_PATH_ABSENT`），而失败的新版本还留在那些路径上；要重试，先用同一个上线包运行 `rollback.sh` 恢复旧版本，再用修好的提交按上面的步骤重新生成上线包、运行 `deploy.sh`。`andy-production` 实例设为 `rollback`：Andy 2026-11-26 开始真实使用 Himawari 后，在决定卡上对“上线失败时，自动退回上一版还是停在原地等人修？”选了“自动退回上一版”，取代 2026-11-15 “失败后不回滚,保留现场”的选择（那时线上没有真实数据）。没有这个设置的上线包仍按 `rollback` 处理。历史数据只在服务停着时比较（S3、S7 按表摘要比，迁移前后比，S7 切换脚本在启动新版本之前比较升级前后两份已保存的停服读回，出包时拒绝迁移改历史表）；S8 在新服务启动之后运行，不再把生产库和 S3 数据库副本逐行比较，因为运行中的服务会合法地改老行（结算预算、完成对话、清理到期的“想一想”对话），分不清正常写入和损坏（[ADR 0293](../../docs/adr/0293-how-production-deploys-work.md)，[I-108](../../docs/incidents-and-gates.md#incidents)）。实例文件不能再带 `historyComparison`，出现就以 `PACKET_HISTORY_COMPARISON_SWITCH_REMOVED` 拒绝出包。其他检查（数据库结构、迁移记录、摘要、服务健康、安全检查）照旧。上线后检查结果，靠 Claude 的回读加上用户试用产品。当用户要求退回时，Claude 运行 `bash scripts/delivery-mode/rollback.sh <the same packet directory>`（日志在 `<packet>/run-logs/rollback-<time>.log`）。它停止服务；当这次上线已经改过数据库、配置或服务单元时，它写入回滚批准文件，把 `authority.json` 镜像设回恢复点中的上线记录行（新版本会推进 fencing token，而旧版本会拒绝领先于其数据库的镜像），运行上线包的 S2_INSPECT、可选的 S9_SIDECAR_TIDY、S9 恢复和 S9 控制步骤，然后启动旧版本并检查它能持续运行。恢复点之后写入的一切都会丢失。
- 生产访问：Claude 可以以 `root` 或 `himawari-prod` 身份登录生产机（Oracle 东京的 ARM 机，地址在上线时用 `--host` 或 `HIMAWARI_PACKET_HOST` 指定；旧的 x86 云服务器 2026-11-25 已退租）来上线、回滚和诊断，并可以为此读取 `/opt/himawari`、`/etc/himawari` 和 `/var/lib/himawari`。在任何破坏性步骤（停止服务、修改配置、删除数据）之前，Claude 先核对证据并先做备份；手写脚本中的每一项检查都放在停止服务之前；系统命令使用绝对路径，例如 `/usr/sbin/runuser`；出了故障，Claude 先恢复服务，之后再调查；上线失败且上线包选了 `keep` 时例外，按上面的说明保留现场。Claude 绝不打印、绝不复制出服务器、绝不提交任何生产机密，绝不以生产账号运行测试，并在事后告诉用户它运行了什么。

以下规则在快速模式下仍然有效：`Layer-0-tests:` 提交说明行以及检查它们的仓库钩子；提交说明还要在一行 `Fast-mode-checks:` 中列出实际运行过的基本检查、在哪台主机和哪个版本上运行；服务器端的构建和测试绝不在 MacBook 上运行（苹果客户端的例外见[测试主机与生产主机](test-and-production-hosts.md)）；测试不用 root 或生产账号；不写代码注释；依赖版本精确固定和 Pi 优先原则；推送每一个提交；磁盘空间规则。

## 切回完整模式

当用户要求时，把 `full` 提交到 `DELIVERY_MODE`，然后在一个补课任务中：运行 `document-governance` 技能的 `validate_docs.py . --strict` 并修复每一个发现的问题，对照当前代码审查每份 Runbook，更新那些带 `Docs: deferred (fast mode)` 的提交留下的文档，在 GitHub CI 上对当前版本跑一次全量测试，先和 Andy 定好第 4 层（已安装的产品路径）在哪台机器上跑并跑受影响的场景，确认 GitHub Actions 已打开（Settings → Actions → General），然后运行 `scripts/delivery-mode/github-ruleset.sh full`；Actions 关闭时，完整规则集会一直等待 `ci/required` 检查，从而阻止每一次合并。

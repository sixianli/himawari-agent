# 交付模式

在用户是唯一使用者、并需要把一个完整产品摆到投资人面前期间，开发不得等待演练和门槛。仓库根目录的文件 `DELIVERY_MODE` 只写一个词：

- `fast`：快速模式。[快速模式](#fast-mode)中的规则替换它们所点名的规则，对所有代理都适用。
- `full`、任何其他内容，或没有这个文件：完整模式。其他所有项目规则按原文适用。

只有用户能切换模式。只有当用户用自己的话要求时才修改 `DELIVERY_MODE`，并且单独作为一个提交。

<a id="fast-mode"></a>

## 快速模式

对产品代码、配置或测试的每一处改动，都保留以下基本检查：

1. 针对这次改动的定向测试：新写的或复现问题的测试，以及 `python3 scripts/layer0-tests/check-layer0-tests.py derive` 列出的文件。修复缺陷仍然要先用一个测试复现该缺陷。
2. `npm run check`（格式、lint（代码风格检查）、类型检查、模块边界、不变量检查、机器机密扫描、用锁定版本的 gitleaks（一个按规则找密钥的扫描程序）扫当前文件和当前提交的全部历史（`npm run check:gitleaks`，规则文件和白名单与 CI 的 security 作业是同一份 `ci/rules/gitleaks.toml`，所以误报在合并前就会被拦下；它比 CI 松的地方：不联网核对店主在 GitHub 上的批准评论（身份、批准记录、到期、PR 编号、来源提交是否在历史里），也不校验工作区里改过的 `ci/security-exceptions.json`，这些仍只有 CI 会拦；第一次运行时需要联网，按 `ci/toolchain-lock.json` 里的地址和摘要下载到 `~/.cache/himawari/gitleaks/<版本>/<平台>/`，可用 `HIMAWARI_GITLEAKS_CACHE` 改位置；基准提交默认是 `origin/main` 与 HEAD 的共同祖先，可用 `HIMAWARI_GITLEAKS_BASE` 指定，本地没有 `origin/main` 时要先 `git fetch origin main`）、指令文件里的链接和路径是否都还存在（`npm run check:instruction-links`）、`docs/` 里的相对链接和锚点是否都还存在（`npm run check:docs-links`）、在真实浏览器中对 Himawari 网页做的布局审查——三种语言、两种宽度、两种主题（`npm run check:layout`，约 80 秒，需要 Playwright 的 Chromium））。它不包含文档的完整校验（只有上面几步查 `docs/` 的特定部分）；改动了 `docs/` 的提交另外手动运行文档校验，见下文。
3. `npm run build`。

按 [测试主机与生产主机](test-and-production-hosts.md) 的规定，在云服务器上以 `himawari-ci` 身份或在 Hermes 上运行它们；绝不在 MacBook 上运行。基本检查失败时，和以前一样阻止提交。

以下规则在快速模式下暂停：

- [测试触发时机](test-trigger-timing.md)：不跑第 2 层（受影响的整个 Vitest 项目），不跑第 3 层（完整的 `npm test`），不跑第 4 层（Hermes 上已安装的产品路径），不做浏览器资格验证，也不跑 `require-quiet-host.sh`，除非这次运行是用户要求的对比测量。只有当改动的风险是基本检查看不到的（例如数据库迁移）时，才跑更大范围的测试，并用一行说明。
- [文档治理](document-governance.md#code-and-documentation-consistency)中的“代码与文档一致”一节被一条更轻的规则替代：严格的文档校验不再自动运行，但改动了 `docs/` 下任何文件的提交，提交前必须手动运行 `document-governance` 技能的 `validate_docs.py . --strict`，并且不得新增校验错误。完整的偏差核对等到完整模式。`document-governance` 技能仍然用于新的 ADR、Backlog 条目、Idea（想法记录）以及被改动弄得明显错误的文档，见 [文档治理](document-governance.md)。留下未更新文档的提交，其提交说明要带上 `Docs: deferred (fast mode)`。
- 临时例外（Andy 2026-11-14 同意，原话：“现在先不要让 CI 拦着整个项目的推进”“等 CI 修好或者真的很快很顺滑了，我们再把 CI 门禁打开”）：在 Andy 说重新打开 CI 门禁之前，合并不等 PR 上的 CI，下面这条门槛暂停。合并仍要：本地基本检查（`npm run check`）通过、复核没有中、高意见（由线程按[模型复核](model-review.md)判断）且 `--assert-reviewed` 输出 `REVIEW_CURRENT`、已合进最新的 `main`。例外期间不给 PR 加 `merge-queue` 标签，做 PR 的线程直接合并（合并队列要等 `ci/required`，而且它合入的提交不触发 `Main confirmation`）。PR 上的 CI 照常跑，结果只作参考；CI 已经报出的、由本 PR 改动引起的失败要先修再合。合进 `main` 后由 `Main confirmation` 工作流跑全量测试；`main` 变红时，CI 线程马上定位是哪个 PR 引起的，由那个 PR 的线程优先修。排队的 PR 一个一个合，每合一个，后面的先合进新的 `main`。例外期间合并队列工作流只保留手动触发，去掉了 CI 结束后触发和每 10 分钟的定时触发，免得它占着 CI 机器（Andy 2026-11-14 同意，原话：“可以关掉”）；重新打开 CI 门禁时把这两个触发加回 `.github/workflows/merge-queue.yml`。
- GitHub 合并门槛：合并进 `main` 之前，PR 最新提交上的 `ci/required` 必须是成功（[ADR 0241](../../docs/adr/0241-draft-prs-skip-ci-and-merge-waits-for-green.md)），上面的本地基本检查照样必过。PR 上的 `ci/required` 只跑基础测试和与改动相关的测试；完整测试由合并队列补上：线程满足上面的条件后，给 PR 加 `merge-queue` 标签就是执行合并，可以再手动触发一次 “Merge queue” 工作流，队列把几个 PR 合在一起完整跑一次 CI，过了逐个合进 `main`，失败的 PR 会被移出并在 PR 上留言（[ADR 0268](../../docs/adr/0268-merge-queue-and-related-tests-on-prs.md)）。改了 `.github`、`ci`、`scripts/ci` 的 PR 不能进队列，仍由线程调用合并接口手动合并。CI（持续集成）按 [ADR 0287](../../docs/adr/0287-ci-runs-on-github-hosted-runners.md) 跑在 GitHub 的免费标准托管机器上（`ubuntu-24.04`、`ubuntu-24.04-arm`、`macos-26`，仓库公开所以不收费）；工作流里写别的机器标签，`npm run check:ci-policy` 会以 `HOSTED_RUNNER_REQUIRED` 拦下。草稿 PR 不跑 CI，草稿上的 `ci/required` 第一步就以 `CI_DRAFT_UNVERIFIED` 失败，不用修；线程开始代码复核时就把 PR 标成“准备合并”，CI 和复核同时跑。只改 PR 标题或正文不会触发 CI；改了目标分支要推一个新提交才会重跑。测试和 CI 都通过（改了 iPhone 客户端的再加上 Mac 编过一次）后，线程自己合并，不等 Andy 点头，也不用外部模型复核；只有上线生产、动生产数据、花钱超过预算才先问 Andy。CI 没变绿不合并：因本 PR 自己的改动变红就先查、先修；查清确实与本 PR 无关的（GitHub 故障、别处时好时坏的测试），先找到或推动修复，再重跑到变绿。Andy 2026-11-12 给的“CI 坏了可以不等 CI 合并”的授权已经作废。重跑一律用 “Re-run all jobs”。规则集是否强制要求 `ci/required` 由用户用 `scripts/delivery-mode/github-ruleset.sh fast|full` 切换，这个脚本只由用户运行。

## 切回完整模式

当用户要求时，把 `full` 提交到 `DELIVERY_MODE`，然后在一个补课任务中：运行 `document-governance` 技能的 `validate_docs.py . --strict` 并修复每一个发现的问题，对照当前代码审查每份 Runbook，更新那些带 `Docs: deferred (fast mode)` 的提交留下的文档，在 Hermes 上针对当前版本运行第 3 层和受影响的第 4 层场景，确认 GitHub Actions 已打开（Settings → Actions → General）且 Hermes 上的 runner 在线，然后运行 `scripts/delivery-mode/github-ruleset.sh full`；Actions 关闭或 runner 暂停时，完整规则集会一直等待 `ci/required` 检查，从而阻止每一次合并。

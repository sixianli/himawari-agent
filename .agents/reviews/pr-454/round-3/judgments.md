# PR 454 第 3 轮逐条判断（DeepSeek）

复核的提交：`47460c86a468`（增量从 `f0563fd15` 起）。这是连续第三轮有中、高意见，按规则修改后不再复核，报告 Andy。

## 成立，“会出错”

2. **读回的顺序会把新动作挤掉（模型：中；线程：中、高）**。成立，而且比模型说的更宽：不只是 `actions/open`，`claim` 也按创建时间取最老一批，一台设备上有一批读回后仍说不清的动作时，排队中的新动作会一直轮不到。修改（`sqlite-device-action-operations.ts`）：`claim` 先发排队中的，剩下的名额再发结果未知的；结果未知的按“最近一次被动过的时间”从旧到新排，设备回报“还是不清楚”时把这个时间往后推，所以会轮换；`forget` 返回的待读回列表先放这次刚转换的。测试：`[reverse] new work and not-yet-checked actions are handed out before actions the device already said it cannot verify`，去掉修改后失败。**已改，未复核。**
3. **`insert` 的重放路径没有同样的核对（模型：低-中；线程：低）**。成立。修改：两条路径共用 `#repeated`，都核对设备和动作名。参数不核对是有意的：重放的定义就是同一次工具调用，按编号认。**已改，未复核。**
5. **非新建分支的清理没有保护（模型：低；线程：低）**。成立。修改：同样不让清理的错误盖掉结果。**已改，未复核。**

## 成立，没有改，列给 Andy

4. **状态转换提交后写决策记录失败会漏记（模型：低；线程：低）**。成立。这是这个服务里所有转换的共同写法（先改状态、再写决策记录），不只 `forget`；要根治得把决策记录和状态放进同一个事务，是跨两个存储模块的改动。状态本身不会错。
6. **没有“清理自己出错”的测试（模型：低；线程：低）**。成立一半：“旧记录挤占”已补用例；“清理自己出错时上抛原错误”要有一个会失败的载荷存储才能触发，真实存储里造不出这种失败，项目规定测试不用假替身，所以没补。
7. **设计文字和代码对“重装后还没了结的动作”理解不同（模型：低；线程：低）**。成立为文字不清。代码只把已送达的转成结果未知：排队中的动作从没到过设备，重装后送达执行不会重复做；把它标成“结果未知”反而是说了一句不真实的话。需要设计线程定：按代码改文字，或者重装后把排队中的也作废。

## 不成立

1. **`reopen` 开头的 `settle()` 没有上限**。不成立：`settleDue` 只处理“到期且还没处理过”的动作，每条动作一辈子只被它转换一次（转换后状态变了，下次查不到），反复调用 `actions/open` 不会重复这份工作；它也不是本轮新增的，`request`、`claim`、`views` 开头都先结算，不先结算就会把已过期的动作当成还有效。总量等于模型发起过的动作数，没有放大。

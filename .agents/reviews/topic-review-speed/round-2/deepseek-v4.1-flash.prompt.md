# 复核太慢：根因和方案（v1，2026-11-14）

## 一句话结论

慢不是因为 DeepSeek 慢，而是流程设计让轮数多、每轮又重：

1. **增量轮比全量轮还重**：11-08 起增量轮步数中位 47、全量轮 36。增量提示要求查“每个使用端”、每轮重答全部必答问题，模型又看不到上一轮提过什么，等于每轮重新找一遍。
2. **每次修改都引出新一轮**：第 2 轮起 44% 的轮次因上一轮有中高；这些中高 79% 落在上一轮刚改过的行。抽查 30 条后期中高，约四分之三是正常使用会碰到的真问题，所以**不能靠降标准砍轮数**，要让每轮变便宜、让修改少出新错。
3. **流程本身多出 15% 的轮次**：上一轮只剩低意见，却因为 `--accept-low` 不认 Python 测试、规模上限写死，只能再跑一整轮。
4. **ADR 核对不收敛**：模型自己列说法，同一份 ADR 列出 21 到 63 条；改一个字整份重核；标出的问题约 70% 是模型看错；只认当前代码，讲“已删旧代码”的句子永远过不了。

按现有数据推算，每个 PR 复核从约 78 分钟降到约 45 分钟（约少四成），DeepSeek 花费约少三到四成，Claude 侧随轮数和每轮工作量下降。第一轮全量复核不变，拦截面不变。这些是推算，第一步就是在接下来 5 个 PR 上实测。

## 大厂怎么做

- **Google**：要求 CL 小（改动小的审得快、引入错误少）；一天内多轮；评审者在只剩小意见、且相信作者会改好时直接批准（“LGTM with comments”）；按这套做法一个 CL 一天内可以过多轮。[速度](https://google.github.io/eng-practices/review/reviewer/speed.html)
- **OpenAI Codex**：默认只报 P0、P1，明说“接受召回率略降，换取高信噪比和开发者信任”。[GitHub 集成](https://developers.openai.com/codex/integrations/github)、[对齐博客](https://alignment.openai.com/scaling-code-verification/)
- **Anthropic 官方复核插件**：只看改动、不报改动前就有的问题，置信度低于 80 的不报。[插件页](https://claude.com/plugins/code-review)
- **CodeRabbit**：推送后只复核上次以来的新提交，带着上次的意见；连续复核 5 次后自动暂停。[文档](https://docs.coderabbit.ai/configuration/auto-review)

共同点：复审是“核对上次的意见改好没有、这次改动有没有新错”，不是从头再找一遍；而且都带着上一轮的上下文。我们的增量轮不带上一轮意见、要求查所有使用端，所以慢。

## 方案

### A. 增量轮改成“修改核对轮”（根因 1，主要提速项）

- 第 2 轮起，提示里带上上一轮成立的每条意见（从已提交的 `verdicts.jsonl` 读：编号、原话、判断），任务改成三件事：每条中高是否改好；这次修改的行有没有新错；修改产生或改动的值（导出的函数、配置键、字段、格式）的使用端能不能接受。
- 只问和修改有关的必答问题（例如改了发给模型的内容才问 KV 缓存那条），用一个独立的固定前缀，这一类轮次之间前缀逐字节相同。
- 上一轮判为不成立或“可以更好”的，除非相关代码改了或有新证据，不再重报（现在靠子代理手工沿用原判）。
- 预计增量轮步数 47 降到 20 左右，DeepSeek 运行 10 分钟降到约 5 分钟，Claude 子代理要判的条数也少。
- 质量：第一轮全量复核不变；79% 的后期中高本来就在修改的行上，仍在核对范围内；改了导出的符号或格式时要求查全部使用端，防漏跨模块影响。

### B. 低意见别再多跑一整轮（根因 3）

- `--accept-low` 认测试文件改为从仓库配置动态读（vitest 配置、`pyproject.toml` 等），兜底认 `test_*.py`、`*_test.py`。
- 文件数、行数上限从脚本常量挪到 `review-models.json`，不写死；默认值先不变，Andy 想放宽再改配置。
- 预计省下 97 轮里的一部分（多少要看三种拒绝原因各占多少，账本里没分开记，实施时加上原因统计）。

### C. ADR 核对：脚本切句、按句沿用、认旧提交（根因 4）

- 句子清单由脚本从 ADR 里确定性切出并编号，模型只对每句判“一致 / 不一致 / 找不到 / 不是现状说法”，不再自己列。条数固定，不再 21 到 63 地跳。
- ADR 改了，只重核改过的句子；没改的句子，只要它引用的代码原文在当前提交里仍逐字存在，就沿用上次的判断。
- 引用可以写 `文件:行@提交`，提交必须是本 PR 基线或 PR 内的提交，专门对付“本 PR 删掉的旧代码原来如何”。
- 预计 ADR 核对从 4 到 7 次降到 1 到 2 次，不再需要 Andy 说跳过。

### D. 固定开销（表面提速，便宜）

- 自检结果按“opencode 版本、锁文件、配置、平台”缓存，每次只跑几条最小探针；每轮省约 1 分钟。
- 同一个 PR 的复核目录用固定路径（仍是干净克隆），让 OpenCode 系统提示每轮相同，第一次请求能命中缓存。只影响每轮第一步，收益小但几乎零风险。

### E. 要 Andy 定的两项

1. **第 2 轮起，刻意构造或极端的输入（手改导出包、几十万行、NaN 一类）引出的中，算低、只列不修？** 这和“复核限制不防恶意”一致，对标 Codex 只报 P0/P1。抽样约占后期中高的四分之一，预计再省约 0.3 轮/PR；代价是这类边界问题不再自动修，只在报告里列给你抽查。我建议采纳。
2. **大 PR 先拆小？** 1100 行以上平均 4.5 轮，115 行以内 2.7 轮。建议协调者派活时按功能切成多个 PR，不加硬限制。

### 不选的做法

- 降推理强度、换更快的模型：会漏错误路径，且只能用 DeepSeek。
- 写死“最多 N 轮”：已有“连续三轮没过停下”，再写死会违反“不写死”。
- 复用同一个 opencode 会话跑多轮：上一轮几十次读文件全进上下文，更贵，还会锚定上轮结论。
- 把所有后期中高降为低：抽查显示约四分之三是真问题，会降质量。

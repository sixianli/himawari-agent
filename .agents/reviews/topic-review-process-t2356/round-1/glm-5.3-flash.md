# 四个问题的独立方案

## 一、方案依赖的前提（读代码或来源证实的）

1. 复核轮次的停止条件只有两条：线程核对后没有「会出错」意见（`model-review.md:28`：「一直到线程核对后没有“会出错”的意见为止，第 4 步的停止条件除外」），或「连续三轮没过」封顶（`model-review.md:29`）。规则里「合并」只出现在第 30 行（「Andy 说“合并”才合并」），合并 main、解决冲突、「可以更好」里被 Andy 采纳后顺手的小改动都不触发复核——这正是问题一的漏洞。
2. 复核意见的「分类」由线程做（`model-review.md:24`：），把「可以更好」里 Andy 采纳的改动也归入 PR、改完按第 3 步再复核（`model-review.md:30`）——所以「复核后顺手的小改动」若走了第 5 步本就有复核，漏洞实际是：**合并动作本身和冲突解决不触发复核**。本方案的规则改动只补这一处，不再新造负担。
3. 费用账本 `usage.jsonl` 只放在 `--out` 一个目录里（`opencode-review.mjs:661-689` `readUsage`/`roundsOnDisk`、`1335` `appendFileSync`），换目录就换账本；线程对同一个 PR 换 `--out` 名字没有任何脚本护栏会拦。原文：「同一件事的所有轮次……用同一个 `--out`。轮次序号取 `usage.jsonl` 里记录的轮次……」（`model-review.md:54`）——这只是规则的口头约定。
4. 预算判线只对当前 `--out` 的 records 加本轮上限（`opencode-review.mjs:651-659` `budgetCheck`、`72` `ASK_FIRST_LINE_USD = { "code-review": 1, plan: 0.5, ... }`）。
5. 脚本跑在一个一次性克隆副本里（`model-review.md:49`、`opencode-review.mjs:1275` `prepareCopy`），`--out` 指向原仓库工作区（`opencode-review.mjs:1204` `resolve`，cwd 通常是仓库根），所以「`--out` 指到 `.agents/reviews/<PR编号>/` 并提交进仓库」脚本现在就支持，不需要改写入逻辑；只是现在没人这么用。
6. 必答问题从 `--base` 提交里的 `.agents/instructions/model-review.md` 读（`opencode-review.mjs:1133-1137`、`model-review.md:46`），每个复核运行是**全新会话**，改规则文字只会改变未来请求的第一条消息，不会改写任何进行中会话已发的内容。
7. 每轮 record 已含 `round、model、head、outcome、cost`（`opencode-review.mjs:1321-1334`），提交哈希已经在账上——问题四缺的不是数据，是把数据「放出云端容器」并「落到人能看见的地方」。
8. 提交钩子已有结构化声明先例：`commitMsg`/`pre-push` 钩子核对 `Layer-0-tests:`（`test-trigger-timing.md:8`、`lessons.md:664`），`untested-claims.py` 拒绝「没有任何结构化行」的自由文字声明（`incidents-and-gates.md:96` I-59）。给复核 provenance 加结构化行是同一条路，有现成熟悉度。
9. I-73 事故原话：「双模型复核只看了 diff，没问「清单里的 id 能通过后端校验吗」」（`incidents-and-gates.md:112`）。两个模型拿到的 prompt 确实逐字节相同：`buildPrompt` 不带模型参数（`opencode-review.mjs:1224-1248`、`1303-1334` 用同一个 `prompt` 发两个模型）。
10. 最近一轮 0.06–0.13 美元（材料给出），低于 1 美元复核门槛、更低于 0.5 美元方案门槛（前提 4 的常量）。

**未核实**：`check:instruction-links` 对指向 `.agents/reviews/...` 的相对链接在目录尚不存在时如何处理（本方案避免在指令文件里加这种链接，绕开它）；`<模型>.jsonl` 的典型体积区间（材料说「可到几 MB」）。推测均单独标出。

## 二、方案

### 问题一：合并 main 之后也要再复核一轮

**改文件**：`.agents/instructions/model-review.md`（代码复核一节），在现在的第 3 步后插入一步，并把第 30 行的收尾措辞对齐：

- 「Andy 说“合并”后，线程先合并 main、解决冲突；**解决冲突期间和合并本身新增或改动的每一处文件，连同 Andy 在第 5 步口头说“照着改”而没走第 30 步的小改动，都算未复核改动，必须以合并后提交为 `--head`、合并前最后一轮复核的提交为 `--previous` 再跑一轮复核**。这一轮按第 3 步同样的标准核对，没有「会出错」意见才算收尾；轮次序号、费用全记在这个 PR 同一个账本里（见问题二），连续没过的计数接着算。」
- 顺手修一处名不副实：第 3 步的「传 `--previous <上一轮复核的提交>`」加半句「上一轮复核的提交指**上一轮复核时的 `--head`**」，避免有人拿「上一轮出现的那个复核提交」理解错。

**为什么不做得更重**：没有为「合并后又改代码」定义新意见类别——冲突解决和 PR 内改动用同一套「会出错/可以更好」分类，零新概念；也没有把「复核后 Andy 亲自看完的改动」豁免——唯一豁免仍是第 5 步里走完整判定流程的采纳路径。

**自动检查**：见问题二/问题四：`review.json` 里每轮的 `head` 加上一条 `coverage` 断言——`scripts/model-review/check-review-provenance.mjs`（新增）逐条核对：PR 目录最后一轮 record 的 `head` 必须是合并提交或其后代，且帐本最近一轮 `head` 到合并提交之间经 `git log` 无 `diff` 差异（冲突解决后为空）；有差异即 `REVIEW_PROVENANCE_GAP` 失败。**反向用例**：造一个只有 PR 内提交有 record 的账本+合并提交含冲突修复 → 检查必须报 gap 而失败；删掉 post-merge 那轮 record 同样失败。

### 问题二：复核记录进仓库 `.agents/reviews/<PR 编号>/`

**改文件**：
- `scripts/model-review/opencode-review.mjs`：新增可选参数 `--pr <编号>`（只影响 `--out` 缺省拼路径和一个校验），不传时行为不变；`main()` 在运行结束把账本路径打印出来（现在已打印，`1348`），另把 record 增加 `outPath` 字段NotAllowed——不加，保持 record 不变。实际脚本改动几乎为零（前提 5），主要改两个地方：
  1. `main()` 里 `readUsage` 失败信息已带行号（`678`），够用；
  2. **新增**：每轮完成时把「本轮给模型的完整材料哈希」写进 record：`promptSha256`（对 `round-N/prompt.md` 内容取 SHA-256）。这是给 I-73 类问题的「材料里混没混进线程自己的方案」的可机器核对依据（见问题四）。
- `model-review.md`「怎么跑」一节：把「用同一个 `--out`」改写为「指到 `.agents/reviews/<PR 编号>/`，每轮的 `prompt.md`、`<模型>.md`、`<模型>.thinking.md` 和 `usage.jsonl` **随本次 PR/收尾提交提交进仓库**；`<模型>.jsonl` 默认不提交，要留时报 Andy 同意并注明大小」。
- `.gitignore` 不加忽略项（`.agents/reviews/` 要进仓库）。

**不放进 record / 不入仓库的字段**：`usage.jsonl` 里已有的 `at` 时间戳继续有（档案记录允许时间，前提 6 的 byte-稳定问题只约束发给模型的字节，不约束档案文件）。

**自动检查**：`test/tooling/opencode-review.test.mjs` 新增：(a) `readUsage` 对路径下被进程中断写坏的最后一行照旧报 `USAGE_LEDGER_INVALID`（已有类似用例则补「收尾追加后坏行」变体）；(b) 反向用例：`promptSha256` 与 `round-N/prompt.md` 实际字节不符时校验函数必须报错。

**做不到的地方**：模型原始 jsonl 里的思考+工具全文只是「有留痕」，不是「可检索」——仓库里全量正文检索会把这些文件也扫进去，本方案不解决检索，靠 `prompt.md` + `promptSha256` 作最小可信锚点。想要可检索需要一次索引的单独取舍（标给 Andy）。

### 问题三：拆掉「两个模型拿相同提示词」的重叠（回应 I-73）

**核心决定**：分歧放在**任务框架**而不是角色名——固定提示词骨架（必答问题、输出格式、工具描述）不变，只把 `MODE_TEXT` 里一段「视角句」按模型拆。理由：`buildPrompt` 的骨架是反 I-73 前提的（两个模型读同一段会让共有的盲区变成双共识）；但换句子必须仍然让「线程整合逐条比对」有意义。

**具体拆法**（code-review 模式）：

- `opencode-go/deepseek-v4.1-flash` 保留现有 diff 视角，在其后追加一句：「除了看改动本身，必须先找到这个改动**接触到的所有跨模块契约**：这个改动新引入或修改的对外承诺（长宽比单 id、字段、配置键、行为）之下，上游和下游各自怎么校验/约定它？每一类都要给出一行结论：契约仍成立，或指出在哪一端断了。找不到此类契约时，明确写『未找到跨模块契约』。」
- `opencode-go/glm-5.3-flash` 换「场景推演」视角：「拿一条最普通的**使用流程**（打开到收尾）从头走一遍这个改动会经过的代码路径，标出每一步哪些状态改变了、哪些输入是现有测试没覆盖的；只报这条流程里能落到具体文件的问题。」
- `plan` / `plan-review` 模式照 `MODE_TEXT` 现有三段结构同样从这两个视角各出一句（deepseek=缺陷/契约、glm=流程/场景），骨架和工具描述不动。

**为什么不选别的**：
- 「跑第二个模型时把第一个的结论当参考」——两个都变成已有结论的复读，且直接违反项目指令第 16 条「不预设结论」的原则（`model-review.md:18` 的独立-先审核-独立就是为反这个）。
- 「temperature/参数扰动」——opencode 1.19.5 的配置点（`reviewConfig`，`opencode-review.mjs:88-116` 附近）没有这个可控项，且扰动不可解释、不可测。
- 「换或加第三个模型」——`model-review.md:4` 明文禁止。

**Andy 同意花一轮的真实对比**：合入这个改动后，拿**一个已合入且后来发生过实际故障**的 PR 的头部提交，跑两轮 code-review：一 `--models deepseek-v4.1-flash` 用旧提示词（在改动 commit 前检出），一用新提示词，各 ~0.06–0.13 美元（总 <0.3）。**判据**（提前写给 Andy）：旧提示词下两个模型都没提出「这个对外长宽比/id/字段能否通过下游校验」类意见；新提示词下 deepseek 至少显式产出了一条「跨模块契约」类结论（成立或断裂均可，但必须落到具体文件:行）。**若一轮不达标，改视角句措辞再测**（改的也是那一句，不动骨架）。

**自动检查**：`test/tooling/opencode-review.test.mjs` 加：
1. `buildPrompt` 对两个模型产出**必不相同**且差异恰好就是视角句那一行（用字节减法断言其余部分逐字节相同，确保没顺带改骨架）；
2. 反向用例：把两个模型的视角句改成相同 → 失败；视角句为空字符串 → 失败；
3. 收尾追问（wrap-up）的追加内容对两个模型仍是**同一段字节**（避免只改了首轮就以为收尾也口径不同）。

### 问题四：复核 provenance 让 PR 描述/合并说明自己说明自己

**改文件**：
1. `.agents/instructions/model-review.md` 报告与合并处新增：「合并提交说明末尾写一行结构化声明 `Review-ledger: .agents/reviews/<PR编号>`，正文写清：最终复核的提交哈希（即 `usage.jsonl` 最后一轮的 `head`）、复核之后没有未复核改动（或注明是什么）、以及停因是『核对后无会出错意见』还是『连续三轮没过』还是『Andy 裁定』。报告和 PR 描述里**不写『双模型复核 N 轮都过了 = 测试过了』**：复核模型只能读文件和跑 5 条 git 读命令，不能运行代码，凡描述里出现『复核过』，旁边必须写『未运行测试』。」
2. `scripts/model-review/check-review-provenance.mjs`（新增，接进 `npm run check` 的一步）：只读地核对两类型事实、都读仓库 git：
   - 对近期 main 上的每个合并提交：`git log --merges` 读到上述声明行，有 `Review-ledger:` 指向的目录存在且 `usage.jsonl` 最后一轮 `head` 的 `diff` 到该合并提交为空（前提 3 的记录是来源）；缺任何一项 → `MERGE_REVIEW_LEDGER_MISSING/GAP/INVALID`。
   - 「没过 = 复核别合并」语义由结论行保证，不再让脚本替人归因。
3. 停因字段由**线程**在最后轮收尾时追加到一个新的 `.agents/reviews/<PR编号>/verdict.json`（字段：`stopped: outcome | cap3-wontfix | owner-vetoed | Cap3-mixed-unreviewed`），自动检查只校验 schema 与枚举，**校验语义靠合并提交的声明的「无未复核改动」与账本一致兜底**（问题一的检查）。

**为什么不选Goals句子 / hook 拦下的问题**：untested-claims.py 那套是拦截发言，不拦合并；这里关键是让**合并事实自己带句证据**，PR 描述里出现「复核都过了」这样的语义模糊句子被声明行顶掉。

**自动检查**：`test/tooling/review-provenance.test.mjs`（新增）两个反向用例：(a) 删掉合并提交的 `Review-ledger:` 行 → 必须报 `MERGE_REVIEW_LEDGER_MISSING`；(b) 账本最后一轮 `head` 与合并提交之间有新增提交（模拟冲突解决塞了个新改动） → 必须报 `MERGE_REVIEW_LEDGER_GAP`。

**做不到的地方**：
- 线程作者**写停因时说谎**（报 `outcome` 却实际有未处理的会出错意见）无法机器证明；能兜住的只有「停因和账本/存档自洽」。
- 复核报告随手写自由文字里的语义模糊（说“都过了”）机器仍拦不全；上面是把不放过**,靠声明行+模板化措辞限制出现位置,不能保证零漏。
- `Review-ledger:` 是自由文字行，钩子/检查办法能核对存在性，不能核对 PR 描述里写过没有——所以方案不再追「PR 描述侧」的可读键，以合并提交说明为唯一机器可读位置。

## 三、考虑过但不选的做法（全局）

| 做法 | 为什么不选 |
|---|---|
| 把账本/档案存 `docs/` 或外部 wiki | Andy 已定 `.agents/reviews/`（材料给定）；`docs/` 有文档治理校验负担（`delivery-mode.md:26`） |
| 为复核 provenance 设独立 Jenkins/CI 门禁 | 快速模式下合并不等 CI（`delivery-mode.md:27`），门禁要么不跑要么拖慢；复用 `npm run check` 本机门槛就够了 |
| 改脚本硬卡 `--out` 必须在 `.agents/reviews/` 下 | 会把脚本绑死在仓库布局上，反向自检（`--self-check-only`、临时目录里的假账本用例）也要跟着改；不划算 |
| 意见重叠用「给模型一段『请少重复上一轮』的话」 | 没有「上一轮」概念（并行），这句话无效；两模型同轮交叉供材又违反不预设结论 |

2. 问题三真实对比的基准选哪个 PR/提交（建议一个最近已合入、有过真实缺陷的 PR，成本最低且判据可写死）；需要 Andy 点头这笔 ~0.2 美元支出。

4. 问题一里「冲突解决产生的每一处文件都要复核」是否过紧——如果嫌重，可切成「冲突解决的文件清单在报告里列明，全部属于未复核改动」，取决于冲突的常见规模（标「推测：现 PR 多为单线程小改动，冲突少，通常很轻」）。

## 五、逐条回答必答问题

**1. 会不会改变模型已经见过的请求开头？**
- 四个方案里，**发给模型请求的构造只有两处会变**：(a) `model-review.md` 文字变了 → 必答问题/规则（从 `--base` 提交读，`opencode-review.mjs:1133-1137`）在**未来新会话**的第一条消息里随之变；(b) 视角句按模型分叉 → 每个新会话的第一条消息多/换一句。每一个复核运行都是全新会话（前提 6），不存在「已发过的开头被改写」；会话内追加（收尾追问）的追加内容不变、仍在末尾（`model-review.md:53`）。每轮会变的值（提交哈希、材料正文）本来就只在第一（也是唯一展开的）条用户消息里——改动的每轮 record 字段、`review.json`、`usage.jsonl` 全部是**脚本产物，从不发给模型**。结论：满足 `.claude/rules/prompt-prefix.md:16-18` 的只追加和「每轮变值在最后」。不是追加而是**首条消息内容变**的部分，都已落到 `round-N/prompt.md` 存档，做到字节可查。

**2. 会不会让同一段文字在不同请求里变成不同的字节？**
- 检查了三处潜在来源：视角句是常量字符串（在同一次运行里固定）；`head`/`base` 哈希是确定性解析（`resolveCommits`，`1155-1159`）；`usage.jsonl` 里的 `at` 时间戳只在脚本产物里，不进模型请求。本方案没有引入任何会进模型请求的非确定性字段，也没有动遮盖路径。唯一随请求变化的是材料正文里的仓库内容，这本来就是「最后一条消息里的本轮资料块」（`prompt-prefix.md:17` 丹位允许）。

**3. 有没有对应的自动检查，反向用例会真的失败？**
- 问题一：`REVIEW_PROVENANCE_GAP`/`REVIEW_LEDGER_MISSING`（check-review-provenance）反向用例「只有 PR 提交、合并提交缺账本覆盖」→ 会失败。
- 问题二：`readUsage` 坏行 `USAGE_LEDGER_INVALID`（已有行为，新增收尾写入变体用例）、`promptSha256` 与磁盘 `prompt.md` 不符 → 会失败。
- 问题三：两模型视角句相同/为空 → buildPrompt 断言 → 会失败；骨架部分非逐字节相同 → 会失败；wrap-up 字节在两模型间不一致 → 会失败。
- 问题四：合并提交缺 `Review-ledger:` 行 → 会失败；停因 verdict.json 枚举外值 → 会失败；账本最后一轮到合并提交之间出现新提交 → 会失败。

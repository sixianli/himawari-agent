## 做法

1. **一个判断服务、一个写入口。** 在 `ProductionMemoryClassifier` 上加“写入时判断”的入口；所有写入点不再自己调 `classificationWithIdentifiers(..., "private")`，改走同一个“先判断再加密存”的函数。顺序：已是 restricted 的不发模型；先跑证件、凭据检测，命中直接敏感；其余交模型；结果和来源级别、已有级别取高；类别是健康或财务一律敏感。提示词沿用 `memory.classification`，固定指令在前、数据在后，条目编号由内容摘要派生，同样的文字发出同样的字节。
2. **写入时同步判，不先存后改。** 外部推送（单条和 `sync_memories` 整批）、规则、提醒都在写之前判完。判断有时间上限（外部推送默认 8 秒、对话里的工具 5 秒、后台 15 秒，都是设置项、页面上看得见），超时、失败、额度用完的条目按敏感存，写入照常完成。外部推来的判成敏感就进待确认，不管接入设没设直接存（PR 589 已是这样）。
3. **只升不降。** 已经是敏感的，再判成普通也不降；只有主人在页面上明确说“这不是敏感信息”才降。同一稳定编号重推时，`sqlite-mcp-memory-sync-operations.ts` 现在无条件覆盖级别的那段改成只升不降。
4. **外部自报的类别只能往上推，不能往下拉。** 对方报 health/finance 照样直接敏感；报别的不算数，以模型判断为准。模型给出的类别按外部清单校验，`rule` 归“其他”。
5. **外部表记下主题。** `external_memory_proposals`、`mcp_sync_entries` 加可空的敏感主题列（同 `SENSITIVE_MEMORY_TOPICS`），导出格式跟着升，免得确认时只能按类别瞎推主题。
6. **额度单独一份。** 写入判断用自己的每日花费上限（新设置项，页面看得见能改），不和主动检查共用，免得主动检查花完了额度后所有写入都变成敏感、外部推来的全进待确认。
7. **旧内容补判一次。** 上线时作为一次性的后台任务，逐条补判上面这些写入点存过的内容，判成敏感的另存一份敏感内容、切换引用，旧的那份留着；只升不降；按表和编号分批、记进度、中断能续、失败停下不乱标。补判完成之前，外部接入只读得到已补判过的内容（未补判的按敏感对待）。页面显示补判进度和“今天判断失败 N 条”，每个数字写明定义。
8. **对话记忆采集不再多调一次。** 它的抽取模型已经给出级别，改成走同一套校验和取高，不另调判断模型。
9. **模型和提示词版本记在哪里。** 按协调者 11-15 的冻结通知，记“哪个模型、哪版提示词、把握分数”用“衡量主动提醒”那份 ADR 的 `decision_versions` 表和 `confidence` 列，这部分等它定稿后接上，本方案不另起一套。
10. **以后新加写入点不会漏。** 新增 `npm run check:memory-write-classification`（进 `npm run check`）：扫描 `apps/` 下所有加密存储的调用，写入级别不是来自统一写入口的就失败；带反向用例（临时放一个直接用 `classificationWithIdentifiers(text, "private")` 写的文件，检查必须失败）。另外两条装配路径（`service-main.ts`、`production-http-composition.ts`）都接了同一个判断器，有测试守着。
11. **判断模型要允许看敏感内容。** 这些文字可能敏感，发给判断模型时按 sensitive 标；配置的模型不允许 sensitive 时判断器不可用、全部按敏感，设置页说明原因。

## 测试和反向用例（完成标准的一部分）

每个写入点：一句敏感的（例：“每周三下午去心理诊所”）存成敏感；一句普通的（例：“喜欢喝美式”）存成普通隐私（反向，防止一律敏感）；判断失败、超时、额度用完都存成敏感；已敏感的再判普通不降；外部推来的敏感内容在直接存下仍进待确认；private 上限的接入读不到敏感的；同样的文字乱序进来发给模型的字节相同；模型给外部表 `rule` 类别不会撞表约束。把修复去掉（绕过判断、失败改成按普通存、恢复无条件覆盖）时对应用例必须失败，写进 PR 说明。

## 业界怎么做、我们为什么这样做、放弃了什么

- Microsoft Purview 把“写的时候就打标签”和“对已存内容在服务端扫描打标签”分成两种，并且自动打的标签只替换更低的、不降级（<https://learn.microsoft.com/en-us/purview/apply-sensitivity-label-automatically>）。我们照做：新写入同步判，旧内容一次补判，只升不降。
- Google Cloud Sensitive Data Protection 对单段文字有同步检查接口，对存量用后台任务（<https://cloud.google.com/dlp/docs/inspecting-text>、<https://cloud.google.com/dlp/docs/inspecting-storage>）。同上。
- 放弃：扩大关键词表（违反硬规则）；信外部自报类别（对方可以标错）；先存敏感再异步降（等于悄悄降级）；先存普通再异步升（升级之前外部已能读到，正是要堵的洞）；读的时候再判（同一段文字每次结果可能不同）；判断失败就拒绝写入（把保护变成不能用）；外部内容问两次模型（同一个模型重复问防不了刻意的诱导，靠固定指令在前、严格解析、失败按敏感来兜底）。

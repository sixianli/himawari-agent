# PR 622 第 4 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1. 中低：读清单/使用记录现在先写库，写失败连只读请求也一起失败。读代码证实并用测试复现：test/integration/vault-approval.test.ts 新用例 still lists the vault and its use when recording overdue requests fails 在旧代码上失败。修法：snapshot 和 usage 里的过期补记失败不再让读失败（下次读再补），store 的 expireOverdue 没有过期行时直接返回、不查磁盘余量也不开写事务。磁盘不足不是故意构造的输入，拿不准按中；触发：磁盘余量低于 minimumFreeBytes（或写通道报错），手机打开保险箱页 GET /vault 或使用记录 GET /vault/usage；后果：vault-service.ts:229、240 先 await #expireOverdue，sqlite-vault-operations.ts:303-304 无条件 assertDiskHeadroom 后开写事务，抛错让两条只读接口整体失败，改动前它们能读；已用测试复现（去掉修改后新用例报 disk full）
- 2（deepseek-v4.1-flash）成立，会出错，低：### 2. 低：过期边界上 `denied`/`failed` 会被 CAS 拒绝，模型结果与使用记录不一致，规格说过头了。读代码证实。窗口只有 expires_at 到计时器回调之间的毫秒级延迟；重启后没有 waiter 时 #closeAll 不结算任何请求，store 跳过的过期行由 expireOverdue 正确记成 expired。后果只是模型拿到 denied 而非 expired、使用记录写 expired 而非 failed/denied，不交付、不泄露、两端都是失败；触发：请求已过 expires_at 但计时器还没触发（两者同为 TTL，只差计时器回调的延迟）的瞬间，手机批准且解密失败，或换钥匙/删项；后果：sqlite-vault-operations.ts:334-335 的 CAS 对非 expired 状态要求 expires_at > now，close 返回 null；模型拿到 denied（vault-service.ts:548-551、388-392），请求行之后被补记成 expired 而不是 failed/denied，规格 130 行的说法在这一瞬间不成立
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3. 低（推测）：`approved` 写入在提交后才报错时，仍可能 DB approved / 模型 denied。读代码证实这条路径存在，未复现。只有 worker 进程在提交后、回消息前的极短间隙退出才触发，此时整个持久层已不可用；不泄露、不错误交付，只是使用记录多记一次 approved；触发：写 approved 的事务已提交，SQLite worker 在 postMessage 回结果前退出（sqlite-worker.ts:1112-1113，sqlite-execution-context.ts:220-222 failAll）；后果：approve 的 catch 再写 denied/failed 也失败或返回 null，模型拿到 denied、手机拿到错误，而数据库和使用记录是 approved；值已在 wipeAll 清零，没有交付

# PR 548 第 3 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，低：### 1. 低：确认撤销的 idempotency key 在合法长 runId 下可能超过 128 字符而抛错。生产 runId 为 run:<32 hex> 共 36 字符，加 :owner 后远低于 128；只有外部提供 79-84 字符 runId 才触发，且只抛错拒绝；触发：外部网关提供 79-84 字符的 runId 并带确认密钥撤销；后果：该次确认撤销在 createIdempotencyKey 抛 DomainError，报错拒绝，无数据损坏
- 2（deepseek-v4.1-flash）成立，会出错，低：### 2. 低（推测）：并发的一个未确认 + 一个已确认撤销，可能在两套键下各插入一条反向动作。推测的并发窗口，需两个并发撤销恰好交错；顺序调用由 #undoKey 复用已有记录；最坏是重复反向动作；触发：同一动作的未确认与确认撤销并发，前者先完成；后果：可能多生成一条反向动作（如重复日程）；仅故意并发才出现
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3. 低：授权拒绝的反向动作实际返回 200 + `state:"rejected"`，不是作者说的「409 撤不了」。作者说的是主要路径；授权拒绝返回 200 且 body 带 state:rejected，字段完整不误导，仅 PR 文字不全；触发：授权拒绝的反向动作；后果：客户端只看 HTTP 状态会把拒绝当成功；body 含 state，文字不准但不误导
- 4（deepseek-v4.1-flash）成立，会出错，低：### 4. 低：`views()` 把所有 plain `rejected` 都当成可重试，策略永久拒绝时也会报 `available`。views 对 policy 永久拒绝仍报 available；主人确认后再被拒并显示 failed，只是提示偏乐观；触发：未确认撤销因 policy/设备不支持被拒；后果：视图先显示可撤销，确认后才显示 failed，不丢数据
- 5（deepseek-v4.1-flash）成立，会出错，低：### 5. 低：作者仍称撤销使用固定 `undo:<原动作号>`，增量后已变成两套键；`undo` 签名也漏了 `ownerPresent`。PR 说明与代码不一致，但代码行为正确且有 #undoKey 保证；文字不准但不误导；触发：读 PR 说明的维护者；后果：说明过时，无运行时错误
- 6（deepseek-v4.1-flash）成立，会出错，低：### 6. 低：新增回归用例没有断言未确认调用确实被拒。建议补断言，未运行核对；触发：后续接线变化使前置条件失效；后果：回归用例可能失去覆盖，当前不影响行为

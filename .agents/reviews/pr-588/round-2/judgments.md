# PR 588 第 2 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1、中：逐条跳过的条目（kind_changed、owner_deleted）会留下无人引用的 payload。production-mcp-sync.ts:268-270 先写 payload；sqlite-mcp-memory-sync-operations.ts:226-229 的 applyItem 返回 null（kind_changed）或 :552-561 的 owner_deleted 正常返回时，push() 只在抛错时才 dropUnusedPayloads（:195-199），正常返回路径留下无人引用的正文；触发：主人已删除某条记忆后助手继续改正文再推（owner_deleted），或同一稳定编号换 kind 再推（kind_changed）；每次推送都新写一份没人引用的加密正文；后果：孤儿正文持续增长且无清理路径，对方可反复推新内容撑大库，也与 ADR 0242“库里不留没人引用的半批”不符
- 2（deepseek-v4.1-flash）成立，会出错，低：### 2、中：失败清理会跨请求删掉内容寻址共享的 payload，并发时可能让本应成功的请求失败。清理按内容寻址 ref 删除（sqlite-mcp-memory-sync-operations.ts:234-250），并发另一请求刚写入、尚未提交引用的同一 ref 时可能被删；外键 RESTRICT 保护已提交引用，不丢数据；触发：同一接入、同一段正文的两个请求并发，其中一个请求失败（并发时序，且需另一请求失败）；后果：另一个本应成功的请求报错，对方重试即成功；不丢数据、不泄露；判低理由：见 why；触发条件窄或只是请求报错
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3、中低：payload 写入阶段失败仍会留下孤儿，和"整批原子、库里不留半批"不符。production-mcp-sync.ts:297 的 await Promise.all(stored) 抛错发生在 store.push 之前，已写成功的其他 payload 留下；只有 protect 或 put 基础设施出错才触发；触发：加密或存储在批次中途出错（基础设施故障，不是输入）；后果：已写成功的几份正文成孤儿，请求本身报错；数量受批次上限限制；判低理由：见 why；触发条件窄或只是请求报错
- 4（deepseek-v4.1-flash）不成立：### 4、低：作者说"只删服务令牌接入写入的条目"，代码只检查发起请求的进门方式。与第 1 轮第 3 条同一意见：ADR 0242 决定 6（docs/adr/0242-external-agents-join-the-memory-hub-through-one-entry.md:266）写明按进门方式区分，代码 sqlite-mcp-memory-sync-operations.ts:346-348 与 ADR 一致；模型自己也承认代码符合 ADR，只是作者说明措辞简写，代码和文档没有不符，没有新证据
- 5（deepseek-v4.1-flash）成立，可以更好：### 5、低：新增 kind_changed 测试的同项目分支实际命中的是 duplicate_in_request。mcp-memory-sync.test.ts:416-428 同项目同编号的第二条被 production-mcp-sync.ts:252-256 判成 duplicate_in_request，没有覆盖 note 变 owner 的 kind_changed 分支；只是测试覆盖，代码本身没错
- 6（deepseek-v4.1-flash）成立，会出错，低：### 6、低：schemaCatalog 说"正文随条目一起删除"，与迁移的 ON DELETE RESTRICT 不符。schema-catalog.ts:728 写“正文随条目一起删除”，迁移 20261115124342_mcp_memory_sync.sql:43 是 ON DELETE RESTRICT，不级联；文字不准，会让写删除逻辑的人误判；触发：后续写删除或审计逻辑的人按目录文字以为删条目会带走正文；后果：按错误说明实现会留孤儿或删除报错；现在没有代码依赖这句话
- 7（deepseek-v4.1-flash）成立，会出错，低：### 7、低：上一轮第 9 条（共享 proposal 只接替一条旧记忆）仍未修。沿用第 1 轮第 9 条原判：sqlite-mcp-memory-sync-operations.ts:136-146 的 replacedMemory 带 LIMIT 1，代码未改；需要两条旧记忆各自被改成同一段正文才触发；触发：两个不同稳定编号先各自存成不同的记忆，之后都改成同一段正文（共用一个待确认提议）；后果：主人确认后只接替一条旧记忆，另一条旧记忆仍留在库里，数据不丢，主人可在页面清理

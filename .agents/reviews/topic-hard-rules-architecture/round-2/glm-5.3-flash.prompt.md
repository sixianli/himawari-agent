## 二、先答两个问题

**(1) ChatGPT/Claude 怎么做，用户看到什么。** 开发者侧产品（Claude Code、Codex）把硬规矩放在模型之外的一层确定性代码里：权限规则加 hook，命中后直接拒绝并把原因告诉模型，用户看到“被拒绝及原因”或一张批准卡；多条规则冲突时取最严（P11、P12）；Codex 还要求每条规则自带“该命中/不该命中”的示例，加载时先自检。面向普通用户的聊天产品，个人规则本质是注入提示的文字，模型不照做时用户什么也看不到（愿景 3.3 表对 dots 的描述：“有个人规则……但无出处、无测试、不出平台”，我没有另行核实它们的内部实现）。Himawari 追平开发者侧的做法，再加上它们都没有的出处、历史和可携带。

**(2) 根因还是表面修补。** 根因：规则不是一等对象。同一条规矩散落成常量、提示词文字、记忆条目、设置四种载体，互不知道对方（盘点 F.1 已有 2 处对不上）。表面修补是再补一份提示词文字，或再加一个常量。根治是建一个唯一的规则登记册，让执行、提示词里的说明、测试、出处、导出都从它派生。

## 三、方案

### 1 总体：一个登记册，三个执行面，一个决策记录

```
主人一句话 ──► 规则提案（类型+参数+原话）──► 校验+回放 ──► 确认卡 ──► 登记册（带版本、出处）
                                                                   │
        ┌──────────────────────────────┬───────────────────────────┤
        ▼                              ▼                           ▼
  Agent 循环面（Pi 钩子）        流水线面（Gmail 等）         动作闸（ActionPolicyService）
  tool_call / tool_result /      同一个规则引擎，             tool_gate 类规则变成
  agent_before_settle            参数来自登记册               deterministicFacts / DENY 规则
        └──────────────────────────────┴───────────────────────────┘
                                       ▼
                    决策记录（decision_ledger.ruleIds + 规则版本号）
```

### 2 规则登记册（数据）

一条规则 = 类型 + 参数 + 范围 + 严格度（拦下、抬升、要求先做、限额、仅告知）+ 出错时怎么办（默认关闭放行即拦下）+ 状态（草稿、生效、停用）+ 出处（原话消息编号、事件、ADR，或明写“无出处”）+ 追加式修订历史。采用 ADR 0122 的做法：存服务器、带版本号；每次触发规则的决策记录写“规则编号+版本号”。把 `proactive_settings` 的静默时段、重要发件人，以及写死在代码里的公共机构后缀、金钱词表（盘点 F.4、F.5）都迁成登记册里的规则，补上历史。种子数据来自盘点 H-1…H-16、C 项；S 类规则按下面第 4 步分“能做成硬的”和“只能软”。

### 3 规则类型（代码+测试，每类一次）

只登记程序不靠模型就能判对错的类型：
- `floor`：抬升模型判断的下限（H-1…H-5）。
- `suppress`：某类事不提醒（H-6、H-10）。
- `window`/`limit`：静默时段、每天费用或条数上限、降频（H-8、H-9、H-11）。
- `tool_gate`：某类工具或动作拒绝、必须先批准、限额（S-16、S-17 的程序部分，“发帖逐条批准”）。
- `evidence_before_conclusion`：对某类问题下结论前，本轮必须已做过指定的读取或搜索（愿景 Jarvis #6：退款、预订必须读完线程并搜后续确认）。
- `claim_requires_effect`：回答里说“已设好提醒/已发送”，本轮必须有对应工具成功（S-14、S-18，Jarvis #8）。
每个类型带：参数结构、适用的钩子、纯函数 `evaluate`、内联示例（match/not_match，加载时自检，借鉴 Codex）、反向测试。新增类型才加代码。

### 4 执行面（Pi 怎么用，Pi 管不到的怎么办）

- 引擎放 `packages/application`，不引用 Pi；`packages/runtime-pi` 只加一个很薄的隐藏扩展 `himawari-rules`（与现有三个并列）。
- `tool_call`：调用引擎做“先决条件”类判断（本轮证据账本里是否已读线程等），命中则 `{block, reason}`，reason 带规则编号和一句话，模型下一步就能照做。拦下写进 `tool_result`/决策记录，都是末尾追加，不碰缓存。
- `tool_result`：把工具成败写进每轮的“证据账本”（供 `evidence_before_conclusion`、`claim_requires_effect` 查）。
- `agent_before_settle`：检查最终回答；违规就追加一条纠正消息并请求一次继续；再违规就由 Himawari 在展示层标记“该说法未经验证”。没违规时零额外请求。
- 不用 `context`/`context_with_system` 改历史：会破坏只追加（P10）。不用 `before_agent_start` 改系统提示放规则。
- Pi 的并行工具调用依次预检，所以限额类要在数据库里原子预留（沿用授权额度预留的做法）。
- 其他事件扩展出错只记日志继续（P6），所以适配层给每个处理器包一层：出错按规则的“出错怎么办”处理，默认当作违规，不放行。
- 动作闸只有一个：`tool_gate` 类规则交给 `ActionPolicyService`，作为 DENY 规则/deterministicFacts，不另建第二套（P9、P11：规则只能收紧，不能放松已有的批准要求）。
- Gmail 等流水线（不是 Pi 的 Agent 循环，Pi 管不到）调用同一个引擎。

### 5 模型怎么知道

登记册派生一份“生效的规则”短列表，放最后一条用户消息里（会变，所以只放末尾；和现有“主人的要求”块并存，但来源改为登记册）。作用是让模型少撞墙，不是执行手段，所以不受 2000 字预算和模型归类影响。提示词里关于硬规则的文字（如 S-8、S-9）改为从登记册参数生成，消除重复和不一致（F.1）。软偏好继续走记忆/档案，界面和文档明确标“软：靠模型自觉”。

### 6 一句话怎么变成硬规则

主人说一句话 → 模型只做“翻译”：产出规则提案（类型、参数、原话引用），不决定生效 → 程序校验参数、跑内联示例、用决策记录和邮件历史回放过去 30 天“这条规则会改变几次结果” → 弹确认卡（用大白话写规则、2 个例子、回放数字）→ 主人确认才写入登记册，出处=这句话的消息编号。对不上任何已有类型：存成软偏好并明说“这条我不能保证必定执行”，同时记一条“需要新类型”的待办。一次性的话不成规则（P3）。成规则的人工介入只有这一张确认卡，常规判断由已生效规则预授权，不再逐次问（愿景原则 2）。

### 7 测试

- 类型测试：真引擎、不用假替身，正向+反向用例（反向：不该命中的输入结果为空）。
- 规则内联示例：每条生效规则自带至少一个命中、一个不命中，激活前必须通过；`npm run check:rule-registry` 检查：生效规则有出处或明写无出处、类型存在、示例通过、导出文档与登记册一致、硬规则声称的执行钩子真实存在。
- Pi 集成测试：真 Pi 会话+脚本化模型，验证拦下后模型拿到 reason、`agent_before_settle` 继续一次、扩展抛错时不放行。
- 事故门槛：F.1 那类“两处各写一份”由“提示词从登记册生成+一致性检查”挡住。

# 复核结论：PR 405（苹果设备端设计修订）

先说总体：这个改动确实只有文档和设计素材（`git diff --stat`：3 个 md + 14 张 PNG + 6 个 source 文件），没有代码。文档对现有代码的引用我逐个核对，绝大多数属实；发现 3 处文档间不一致和 2 处小引用错误，没有发现安全漏洞级的矛盾。

## 按严重度排列的发现

**1.（中）docs/execution/specs/2026-11-11-apple-device-body-design.md:867 — 交叉引用「那 25 条」已过时**
- 问题：本 PR 在「还没核实的事」表里新增了第 26 条（Face ID 认证结果可重复使用时长），但「真机验收」一节仍写「和还没核实的事那 **25** 条不是一回事」。
- 证据（读代码证实）：design.md:867 「…那 25 条不是一回事…」；同一文件「还没核实的事」表第一列编号到 26（本 PR diff 新增行：「| 26 | 连续改几处设置时，能不能几分钟内只刷一次面容…」）。现有自动检查（check:docs-links、check:markdown-tables）只查链接和表格列数，查不出这种计数漂移。
- 建议：把「25 条」改成「26 条」或删掉数字。

**2.（中）手机端「感知到的」页没有任何批次认领，三处清单不一致**
- 问题：设计把「感知到的」列入全部原生页面，但实施计划第 11 批和 ADR 0229 决定 3 的原生页面清单都没有它。
- 证据（读代码证实）：design.md:190 「记忆、规则、设置、审批、提醒记录、文件、用量、**‘感知到的’**、设备管理、数据导出，全部做成原生页面」；plan.md:46 第 11 批只列「记忆、规则、设置、审批、提醒记录、文件、用量、设备管理、数据导出的原生页面」；ADR 0229:95 决定 3 的清单同样没有「感知到的」。plan.md:49 第 3 批的「‘感知到的’页」是旧设计的网页页（`Where=云端`）。
- 建议：在第 11 批（或第 3 批改注）里补上手机端「感知到的」页，并同步 ADR 0229 决定 3 的清单。

**3.（中低）「收紧」档的放行判据存在缺口：档是按消息类型标的，但「收紧/重新打开」是方向不是类型**
- 问题：能力表「每种消息类型标一档」（design.md 能力表），而同一个设置类消息类型往往既能关也能开。ADR 0229 补充说「关掉或暂停…只用设备密钥签名…重新打开仍属于‘改’」，但四份文档都没有写明「收紧」和「重新打开」必须是两个不同的消息类型，也没写 `POST gateway` 怎样判断一次收紧档请求实际是收紧还是放宽。
- 证据（读代码证实档位结构）：ADR 0229:95 「分‘读’…‘改’…‘手机上不做’三档…（2026-11-12 补充：另加‘收紧’一档，关掉或暂停某一项感知只用设备密钥签名…重新打开仍属于‘改’）」；design.md 能力表「收紧 | 关掉或暂停某一项感知 | 设备密钥签名，不用面容；重新打开和恢复属于‘改’」。设计同时说「设备接口按能力表查这种消息类型是哪一档，够格就交给和网页同一个处理程序」——按类型放行时，类型内混有开/关两个方向就无法只靠表保证「收紧档不放宽」。（由文档结构推出的缺口，属半推测：具体消息类型清单还没定。）
- 建议：在设计里写明——感知开关必须拆成「收紧」与「恢复」两种消息类型（或 gateway 对收紧档请求按正文校验方向、放宽的一律拒绝），并把这条写进两端校验。

**4.（低）`check:client-parity` / `device-gateway.test.ts` 的反向用例清单缺「收紧档实际放宽」一例**
- 问题：能力表那行的反向用例只有四条：「‘改’档只用设备密钥签被拒；挑战值重复用被拒；没登记的类型被拒；正文被改后签名对不上被拒」。没有「登记为收紧的类型，请求实际把感知打开/恢复时被拒」的反向用例——正好是第 3 条缺口要守的东西。
- 证据（读代码证实）：design.md 值清单「客户端能力表里每种消息类型的档…自动检查」列（本 PR diff 新增行）。
- 建议：随第 3 条一起补一条反向用例。

## 背景

[ADR 0229](0229-native-apple-clients-and-device-api.md) 决定第 3 条写的是“聊天和语音用原生界面做，不常用的页面嵌网页”，第 4 条里写嵌入的网页用确认密钥换一个短期网页会话。Andy 第二天否定了嵌网页。这份 ADR 修订 ADR 0229 的这两处，其余决定不变。

<a id="premises"></a>

## 前提

1. 网页的查询和命令都是带类型的网关消息，类型的全集在代码里。来源 `packages/gateway-contracts/src/contracts-v2.ts:22` 原话：`export const GATEWAY_V2_MESSAGE_TYPES = [`；`packages/gateway-contracts/src/thread-contracts-v3.ts:19` 原话：`export const THREAD_GATEWAY_MESSAGE_TYPES = [`。
2. 网页有一份页面清单，16 个页面，每个列出它的查询和命令，但不全。来源 `apps/control-center/src/app/control-center-inventory.ts:23` 起的 `id` 联合类型（`"threads"` 到 `"health-deployment"`）；`memory` 一项只列了 `queries: ["memory.overview.read"]`、`mutations: ["memory.mutate"]`（同文件第 198、199 行），没有 `memory.settings.set`。
3. 同一个开关命令管两个方向。来源 `packages/gateway-contracts/src/contracts-v2.ts:1494` 起，`memory.settings.set` 的正文是 `payload: object({ capturePaused: booleanValue })`。
4. 每台设备有两把密钥，确认密钥每次使用都要面容或解锁。来源 ADR 0229 决定第 4 条原话：“设备密钥（平时签请求）和确认密钥（每次用都要面容或解锁……）”。
5. 设备密钥本来就能发消息。来源 ADR 0229 决定第 4 条原话：“设备能调用的命令是一张白名单（发消息、回答审批、提交感知记录、回报动作结果等）”。

[↑ 回到阅读导航](#contents)

<a id="decision"></a>

## 决定

1. **App 里全部页面都用原生界面做，不嵌网页。** 聊天、语音、记忆、规则、设置、审批、提醒记录、文件、用量、“感知到的”、设备管理、数据导出，以及网页上的能力、授权、帮手、待采纳的改进、工作区、服务器状态，在 iPhone 上都是原生页面，按手机的用法重新设计。只有第三方授权（例如 Gmail）按苹果的要求用系统登录面板打开。ADR 0229 决定第 3 条里“不常用的页面嵌网页”和“嵌入的网页用设备凭据换短期网页会话”不再执行。
2. **原生页面不另写业务逻辑。** 网关的每一种消息类型登记进一张客户端能力表，设备接口 `POST gateway` 验签后按表放行，交给和网页同一个处理程序。表里每种类型标一档：
   - 读：设备密钥签名。
   - 日常：对话里的日常操作（新建、发消息、改名、置顶、归档、恢复、移到废纸篓等），设备密钥签名。依据前提 5：这些都比发消息轻，而且能撤回。
   - 收紧：关掉或暂停某一项感知、暂停记忆、让正在跑的一轮停下，设备密钥签名。依据前提 3，这一档的每一行除了类型还写明正文必须恰好是什么；正文不符的请求按“改”处理。
   - 改：改规则、删记忆、改设置、导出、移除设备、配对新设备、重新打开感知等，每次用确认密钥签一个一次性挑战值（依据前提 4）。
   - 手机上不做：写明原因，设备接口拒绝。
3. **两边不能悄悄不一致。** 第 11 批新增 `npm run check:client-parity`：网关消息类型全集（前提 1）里的每一种、页面清单（前提 2）里的每个页面，都要在能力表里登记，否则检查失败；Swift 那边的消息类型清单由能力表生成。这道检查落地之前，不得声称两边已有自动检查保护。
4. **确认密钥不再用来换网页会话。** ADR 0229 决定第 4 条里“给高风险审批和换网页会话用”改为“给高风险审批和‘改’这一档的命令用”；“App 里嵌的网页要另换一个短期网页会话”一句不再执行。只拿到设备密钥、主人不在场时，仍然做不了改规则、删记忆、导出这些事。
5. **客户端界面先出原型，Andy 批准后才动工。** 已批准的一版存在 `docs/assets/apple-clients/2026-11-12-v1/`；原型没画到的页面由设计线程补原型给 Andy 看过再做。

原则取舍：第 2 条“收紧”不用面容，依据的是用户主权（想让它少看少听时不该被拦）；往回打开要面容，依据的是边界与可逆性。

<a id="industry"></a>

## 业界怎么做

苹果的人机界面指南要求 App 用系统的导航和控件，而不是包一层网页；App Store 审核指南 4.2 写明只是把网站包起来的 App 会被拒（<https://developer.apple.com/app-store/review/guidelines/#minimum-functionality>）。敏感操作前再验一次身份（step-up）是银行类 App 和苹果自己“设置”里的通行做法，苹果用 `LocalAuthentication` 加安全芯片里带访问控制的密钥来做（<https://developer.apple.com/documentation/localauthentication>）。我们照这个做，并且把“哪些操作要再验一次”做成一张服务器说了算的表，而不是写在客户端里。

<a id="options"></a>

## 放弃的做法

- 不常用的页面嵌网页（ADR 0229 原决定）：省开发量，但 App 里要另外登录一次、打开慢、离线看不了，Andy 明确否定。
- 给手机另写一套接口和业务逻辑：两端行为迟早不一样。
- 能力表只按消息类型分档：同一类型管开和关两个方向时（前提 3），只凭设备密钥就能把感知重新打开。
- 对话的改名、置顶也每次刷面容：比发消息还重，没有道理。

<a id="consequences"></a>

## 后果

- 实施计划多一批（第 11 批原生管理页面），共 11 批。
- 服务器多一个入口 `POST gateway`，安全依赖能力表登记正确；所以表里没有的类型一律拒绝，并有反向测试（只用设备密钥签“改”档被拒、签恢复方向的开关被拒、正文多带字段被拒）。
- 网页每加一种消息类型，都要决定它在手机上是哪一档，否则检查失败。
- 没验证：连续改几处设置时每次都刷面容是否太烦，要真机上试（详细设计“还没核实的事”第 26 条）。

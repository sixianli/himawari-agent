# PR 444 第 1 轮复核：逐条判断

复核的提交 4bcdddedc，两个模型，花费 0.30 美元。下面每条：编号、成立与否、类别和严重度、依据。

- **D1**（deepseek-v4.1-flash）会出错（中、高）：「超出每日记录上限的文字仍会先写进内容存储，上限挡不住磁盘增长」。成立。perception-service.ts 在入库前先 protectText。改法：入库后调用新的 releaseContent，在一条语句里删掉没有感知记录引用的那几条；测试 usage-limits「keeps no stored text…」在改前失败、改后通过。 触发：记录数到了每日上限后，设备继续交带文字的新记录；后果：被挡下的文字留在 payloads 表里，没有任何记录引用，也没有清理；模型给的严重度：高。

- **D2**（deepseek-v4.1-flash）会出错（中、高）：「原始媒体文件和 `perception_media_items` 从不清理，吊销设备也不删文件」。前半成立：没有任何清理。改法：新配置 mediaRetentionDays（默认 7，1 到 90），prune 删超期的行，再删 media 目录里没有行指向的文件。后半不准确：吊销只把设备标成 revoked，不删行（sqlite-paired-device-operations.ts），所以不存在“行级联删了而文件留下”；吊销设备的待处理媒体同样到期删除。测试 device-upload「deletes raw media past its retention…」改前失败。 触发：设备每天上传原始音频或图片；后果：media 目录和 perception_media_items 只增不减；模型给的严重度：高。

- **D3**（deepseek-v4.1-flash）会出错（中、高）：「`perception.images.daily` 从未被占用，图片张数上限实际不生效」。成立。改法：image、screen 上传各占 1 张。测试 usage-limits「counts every image…」改前失败。 触发：上传图片或屏幕画面；后果：用量页上图片张数一直是 0，设了上限也不拦；模型给的严重度：中。

- **D4**（deepseek-v4.1-flash）会出错（低）：「去重查询漏了 owner/agent，跨主人可探测甚至吞掉数据」。成立但判低：两处查询都加了 owner_id、agent_id 条件。记录编号那一处有回归断言（perception-records 第一条用例：换一个主人查同样的编号得到空）；媒体那一处没有单独用例，因为夹具和生产一样一个库只有一个主人，造不出第二个主人的上传。 触发：同一个数据库文件里有两个主人，并且用了同一个记录编号或上传了字节完全相同的媒体；后果：第二个主人得到 duplicate。按 ADR 0234 每人一个数据库文件，生产里一个库只有一个主人，正常使用碰不到；模型给的严重度：中。

- **D5**（deepseek-v4.1-flash）会出错（中、高）：「一段经历跨主人日时，后一天的列表和 `todayCount` 会漏掉记录」。成立。改法：一段经历只并入同一个主人日的记录，零点切段。测试 perception-records「ends an episode at the owner's midnight…」改前失败。 触发：一段对话从 23:59 说到 00:01；后果：零点后的那几句不出现在第二天的列表和今日件数里；模型给的严重度：中。

- **D6**（deepseek-v4.1-flash）会出错（中、高）：「上传和解压内容整包读入内存，且没有全局/每设备并发上限」。单行过大成立，已改：单行不得超过 device.request.body_bytes，超过返回 413，测试改前失败。行数本来就受批量上限限制。“没有并发上限”“镜像没有总量上限”这次不改：每次上传都要先有签名请求换来的凭据，文件大小受 device.upload.file_bytes 限制，镜像按设备上的编号更新不是追加；要加每台设备的并发和总量上限是新的硬上限键，属于设计改动，列给 Andy 和设计线程。 触发：后台上传的文件里有一行特别长（最多到解压上限 500 MiB）；后果：整行读进内存再 JSON.parse；模型给的严重度：中。

- **D7**（deepseek-v4.1-flash）会出错（中、高）：「媒体数据库提交与文件 `rename` 非原子，失败后无法自愈」。成立。改法：先把文件放到位再写行；重复上传也会把文件重新放到位；写行被上限拒绝时删掉刚放的文件。由 usage-limits 媒体上限测试里“被拒后目录里没有多余文件”的断言覆盖。 触发：行写进库以后 rename 失败（磁盘满等）；后果：留下有行没文件的媒体，重发被判重复，文件永远补不上；模型给的严重度：中。

- **D8**（deepseek-v4.1-flash）不成立：「已完成的凭据过期后仍可重放，和“过期会拒绝”的说法不一致」。行为是有意的：设计写明苹果系统的后台上传可能拖几天并原样重发，重发必须拿到第一次的结果，重放不写任何新数据。不成立的是我在材料里“过期都会拒绝”那句话写得不准，PR 描述按实际行为写。

- **D9**（deepseek-v4.1-flash）会出错（中、高）：「现有迁移契约测试很可能因 0095 新增 kind 而失败；0095 也没有数据保留反向用例」。成立，线程判得比模型高，因为它会让 CI 红。改法：这条测试的建表语句比较去掉新增的两种类别后再比；它在迁移 88 种入决定记录等 10 张表的行，应用到 0095 后要求行、索引、触发器完全相同，所以同时就是 0095 的数据保留用例。 触发：跑 packages/persistence-sqlite/test/consolidation-hold-migration.contract.test.ts；后果：测试失败（实际跑过，确实失败），CI 会红；模型给的严重度：低。

- **D10**（deepseek-v4.1-flash）会出错（低）：「文档、用法清单与实现有若干不一致」。导出说明那一条成立，已改成“最多保留到配置的天数就删”。另外两条不成立：docs/execution/specs 下的设计文档讲的是全部 11 批，perception.read.result 和 device_action 属于后面的批次，不是这个 PR 的范围。 触发：读数据导出的说明；后果：说明写“原始材料处理完就删”，而这一批还没有处理这一步；模型给的严重度：低。

- **G1**（glm-5.3-flash）会出错（中、高）：「对单行没有字节上限」。同 D6，已改。 触发：同 D6；后果：同 D6；模型给的严重度：中等。

- **G2**（glm-5.3-flash）不成立：「如果 Fastify 对自定义流式 parser 也执行路由级 bodyLimit」。实际运行否定：新测试上传 17 倍 device.request.body_bytes 的媒体文件成功入库（device-upload「takes a file larger than a signed request may be…」）。

- **G3**（glm-5.3-flash）会出错（低）：「媒体条目 id 只由内容摘要构成，是全局唯一主键，而所有查询（listMedia、usage）都按 owner/agent 过滤」。同 D4，判重查询已加 owner、agent 条件。 触发：同 D4；后果：同 D4；模型给的严重度：低。

- **G4**（glm-5.3-flash）不成立：「不再查 expires_at」。凭据在请求开始时验过期，这是定义好的检查点；后台上传一个大文件可能要很久，收完正文再因为刚过期而作废只会让设备白传一遍，凭据仍是单次有效。

- **G5**（glm-5.3-flash）会出错（中、高）：「episode 的 local_day 只在记录把 episode **向前**扩展时更新」。同 D5，已改。 触发：同 D5；后果：同 D5；模型给的严重度：低。

- **G6**（glm-5.3-flash）不成立：「没有任何执行点**消费它」。perception.model_cost.daily 是设计里给感知抽取的模型调用设的上限，这一批没有任何感知模型调用，所以已用一直是 0 是真实的；占用点由做模型调用的那一批加，已通知第 4 批线程。

- **G7**（glm-5.3-flash）可以更好：「新锚点在候选 episode 里只并入**距离最近的第一个**就返回」。不会出错：两段都在静默期内时并入最近的一段，另一段保持独立，记录不丢、计数一致；要不要把两段再合并成一段是切段规则的取舍，列给设计线程。

- **G8**（glm-5.3-flash）可以更好：「测试名夸大了它证明的东西」。只改测试名：concurrent 改成 overlapping，行为不变。

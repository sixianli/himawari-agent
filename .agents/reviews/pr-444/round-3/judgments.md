# PR 444 第 3 轮复核：逐条判断

复核的提交 e0b7b9d17（增量自 d0bfe3669），只用 DeepSeek，花费 0.16 美元，累计 0.57 美元。

- **R3-1** 会出错（中、高）：「高：媒体无主文件清扫可在上传提交后删掉刚入库的文件」。成立。改法：清扫对每个库里查不到的文件，先排进和上传同一条按摘要的队列，轮到时再查一次库，仍然没有行才删；原来的“放置中”集合不再需要，已删。新测试「keeps a stored file when the same bytes are refused by a limit or swept at the same moment」每一轮让上传和清扫同时发生。 触发：清扫列完目录、查完库之后，同一份文件的上传才提交并结束；后果：库里有行、上传返回成功，文件却被清扫删掉；模型给的严重度：高。

- **R3-2** 会出错（中、高）：「中：`proposal` 没有补齐控制中心的文案与测试，现有自动检查会失败」。成立，实际运行确认 3 条失败。三种语言的 decision.chain.kind 和 weekly.check.rowsMissing 都补了这三种类别的名字，测试通过。这条测试不在 layer-0 推导的清单里，所以之前没跑到；合并前的完整 npm test 会跑到。 触发：跑 test/integration/calibration-group-copy.test.ts；后果：三条用例失败（缺 limit_change、delivery_timing、proposal 的文案）；模型给的严重度：中。

- **R3-3** 会出错（低）：「中：新增的同字节并发测试不是真正的反向用例，其他并发修复也没有对应测试」。并发用例那一点成立。新加一条用例：同一份字节一张凭据按图片（上限设为 0，会被拒）、一张按音频，同时上传并同时清扫，重复 8 轮；临时去掉排队后实际运行，这条用例失败（文件不见了），恢复后通过。写行抛错那条路径没有用例，原因同第 2 轮 R2-3、R2-6：要让真实 SQLite 在这一步出错只能换掉存储实现，仓库规则不许用假替身。 触发：去掉按摘要的排队；后果：原来的并发用例照样通过；模型给的严重度：中。

- **R3-4** 不成立：「低：`0095` 迁移被原地修改，已应用旧版本的环境会因摘要不一致拒绝启动」。不成立。这个迁移还没合并，文件号本身就是占位，合并前还要改号；没有任何环境应用过它（Hermes 实测用新建的库）。已合并的迁移才不许改。

- **R3-5** 会出错（低）：「低：设计说明和运维清单元数据仍引用已删除的“建议”」。待接清单那一条成立，已改成“感知记录和用量的查询与命令”。设计文档由设计线程更新（建议表并入通用提议机制是它定的），不在这个 PR 的范围。 触发：读 ci/operations-pending.json 里五个感知操作的说明；后果：说明里还写着“建议”；模型给的严重度：低。

- **R3-6** 不成立：「低：`releaseContent` 在 `finally` 中失败会把成功的入库变成错误响应」。不成立，是有意的。清理失败意味着库里可能留着没有记录引用的主人文字，这时不能报成功；设备按失败重发，重发时记录判为重复、文字再清一次，不丢数据也不重复计数。

# PR 441 第 1 轮逐条判断

## DeepSeek

1. 高：只显示 `.log`，vitest 失败的用例名在 JSON 报告里，`.log` 里很可能没有。成立，会出错，中高。实测证实：用 CI 的同一组参数（`--reporter=json --reporter=junit`）跑一条失败用例，`.log` 只有两行“report written to”，没有用例名。修法：失败时从 `result.json` 登记为 `json` 的 vitest 报告里取失败用例的文件、名字和报错前 20 行（最多 30 条），放在命令日志前面。用真实 vitest 输出手动跑过 `ci-summary.mjs`，日志里能看到“x.test.mjs > 真实失败样本”和断言信息。
2. 中：64 KiB 总上限会把排在后面的失败日志挤掉，说明文字不报名字。成立，会出错，中高。修法：`details.json` 里退出码非 0 的命令的日志排在前面；失败用例一段最多占一半上限；放不下时列出前 5 个文件名。
3. 低：按扩展名选 `.log`，将来若有登记为 artifact 的 `.log` 会原样打印。成立，会出错，低。触发：以后某个检查把 `.log` 登记为 artifact；后果：没有经过遮盖管道的内容被显示（发布前的密钥扫描仍会拦）。修法：只显示 `result.json` 里登记为 `diagnostic` 的 `.log`；`result.json` 读不出来时不显示任何文件，只写一句说明；指向目录外的路径不读。
4. 低：U+2028/U+2029 没清理。成立，会出错，低。触发：测试输出里带这两个字符；后果：某些查看器里看起来像没有前缀的新行，不影响命令解析。已一并换成 `?`，加了用例。
5. 低：用例是合成的，缺真实输出。成立，会出错，低。新用例按 vitest JSON 报告的真实结构（`testResults[].assertionResults[].failureMessages`）构造，并用真实 vitest 输出手动验证过（见第 1 条）。没有加跑真实 vitest 的自动用例：那要在测试里再起一个 vitest 进程，耗时且脆弱。
6. 低：文档小不一致（ADR 标题、诊断在成功时也显示、目录不存在时的行为）。成立，会出错，低。ADR 补充里写明标题不再准确、诊断不论成败都显示；设计文档同步。

## GLM

1. 低：“reports/ 里的文件已遮盖”不准确，artifact 是原样复制。成立，会出错，低。和 DeepSeek 3 一起修，ADR 补充写明 artifact 不会被显示。
2. 低：设计文档第 320 行没提 120 行。成立，会出错，低。已补。
3. 信息：`logLines` 末尾多打一行 `| `。成立，可以更好（只影响外观）。顺手改成去掉末尾所有空行。

## 一、发现（按严重度）

### 1. 中：代码对“`…` + 分号”的混合引文也查先后，和文档、作者说明都不符

- 文件：`scripts/model-review/plan-claims.mjs:143-150`、`.agents/instructions/model-review.md:37`
- 问题：作者说“用‘…’省略中间的原有行为不变（原来就不查先后）”，文档也写着“用 `…` 省略中间时不查先后”。但代码只有在“按 `…` 拆开的各段都能整段逐字命中”时才走不查先后那条路；一旦这些段里还夹着没有逐字出现的分号，第一条路失败，就会落到 `fragmentsInOrder(...)`，对含 `…` 的引文强制查先后。这是行为变化，不是“原有行为不变”。
- 证据：

```js
// plan-claims.mjs:145-150
const elided = quoteFragments(quote, /…|\.\.\./);
return (
  (elided.length > 0 &&
    elided.every((fragment) => fragment.length >= 4 && haystack.includes(fragment))) ||
  fragmentsInOrder(quoteFragments(quote, /…|\.\.\.|；/), haystack)
);
```

```js
// plan-claims.mjs:133-141：第二条路确实强制先后
const at = fragment.length >= 4 ? haystack.indexOf(fragment, from) : -1;
if (at === -1) return false;
from = at + fragment.length;
```

真实例子：第 7 轮答案 `CLAIM|23` 同时用了“……”和“；”，引文顺序是先“作业时长”后“同一个 PR”。在 `fc70adc` 的旧证据文件里，9 行是“同一个 PR”、10 行是“作业时长”，旧代码两条路中第二条是“每段出现过即可”，能过；新代码会因先后颠倒而失败。`e22c9fa` 恰好把这两行对调，才能让它继续过。这直接证明含 `…` 的引文行为变了。
- 建议二选一，并让文档只保留一种说法：
  - 保持文档承诺：显式分成两支，只有纯分号引文才查先后，含 `…` 的走原来的“每段出现即可”；
  - 或者承认混合引文也查先后，改文档和作者说明，并对第 7 轮记录重跑/重核，而不是靠改证据文件顺序迁就旧答案。建议前者，并补“`…` + 分号、顺序颠倒”这条用例。

### 2. 中：为迁就旧答案改了证据行序，导致第 7 轮记录里的“文件:行”指错行

- 问题：第 7 轮答案的 `CLAIM|9` 引用证据第 10 行（内容是“作业时长”），`CLAIM|11` 引用第 9 行（内容是“同一个 PR”）。`e22c9fa` 把这两条对调后，当前文件第 9 行是“作业时长”、第 10 行是“同一个 PR”，两条引用的行号正好互换。脚本只检查“行号在范围内 + 引文在文件某处出现”，所以发现不了（`plan-claims.mjs:157-161`），但记录的“文件:行”已经不准。

而在 `fc70adc` 的同一文件里，第 9 行是“同一个 PR”、第 10 行是“作业时长”。作者说“内容没变”是对的，但这两条记录的引用位置因此失配。
- 建议：不要用改证据顺序来保住旧答案。先修上面的代码/文档，再对第 7 轮重新跑一次 `plan-claims`（或至少在 `judgments.md` 里记下第 9/11 条行号已移动并重核过）。如果保留这次对调，应明确记录“旧答案的行号已过期”，不能让它静默通过。

### 3. 低：“两段互换”这条反向断言是空转的

- 文件：`test/tooling/plan-claims-gate.test.mjs:223`、`scripts/model-review/plan-claims.mjs:136`
- 问题：新增的 `quoteInText("第二步；note: 第一步", text)` 期望 `false`，但它不是因为顺序颠倒才失败，而是因为“第二步”只有 3 个字符，被 `fragment.length >= 4` 直接判掉。也就是说这条用例在旧代码上也会通过，不能证明新的先后检查起作用。作者说“加了三条反向断言：顺序颠倒、同一段重复两次、两段互换”，实际只有“顺序颠倒”“同一段重复”两条真正覆盖新逻辑。
- 证据：

```js
// test:223
expect(quoteInText("第二步；note: 第一步", text)).toBe(false);
// “第二步”长度为 3，走不到顺序判断
const at = fragment.length >= 4 ? haystack.indexOf(fragment, from) : -1;
```

- 建议：把互换用例的片段都换成 ≥4 个字符，例如 `"第一步骤；note: 第一步骤"` 之类的真实组合（或把片段加长到 4 字以上）。另外补一条“含 `…` 和 `；`、片段顺序与文件相反”的用例，把第 1 条的文档承诺固定下来。

### 4. 低：只查“顺序”仍挡不住“互不相干但恰好同序”的真实片段

- 文件：`scripts/model-review/plan-claims.mjs:133-141`、`.agents/instructions/model-review.md:37`
- 问题：第 2 轮指出的另一面是“互不相干的真实片段拼起来也能通过”。现在加了先后，但两段真实文本只要在文件里是这个先后，仍能拼出一条并不存在于同一处的“引文”。文档已经如实写了“把文件里真有的几段拼在一起的引文仍能通过”，所以不是隐藏缺陷，但门槛比“引文证明这句话”的目标弱。
- 建议：可以把分号片段限制在引用行号附近的一个窗口内，或要求片段之间在文件里只隔空白/允许的空隙；`…` 才表示可以跨任意距离。至少让 `；` 连接的片段不能跨整份文件拼。

## 三、侧重检查

- 错误路径：空引文、纯空白、只有分号、片段不足 4 字符都是返回 `false`，不会抛异常（`plan-claims.mjs:130、136`，测试 210、218、220）。
- 不合规范/不可信输入：`quote` 来自模型答案，`text` 来自 `git show` 的 blob。新代码只做固定正则拆分和 `indexOf`，不把输入拼进正则、不执行命令、不写文件，没有注入路径。
- 安全：本次改动只在内存里做字符串比较，不接触凭据、不落盘、不发请求，没有新的泄露面。
- 资源耗尽：`from` 单调递增，`indexOf` 的扫描区间不重叠，整体随 `haystack` 线性增长；分号很多时只增加拆分次数，不构成明显 DoS（按代码分析，未压测）。
- 不可撤销操作：没有。
- 规则/文档与代码一致性：发现第 1 条的不一致；第 2 条是记录与证据文件不一致；测试第 3 条是没有真正覆盖声称的行为。其余第 2 轮的“可以更好”判断与 `round-2/judgments.md` 一致。

## 四、必答问题

1. **会不会改变模型已经见过的请求开头？** 不会。改动落在答案校验函数 `quoteInText`，它只被 `claimEvidenceProblem` 使用（`plan-claims.mjs:161`）；`opencode-review.mjs` 从 `plan-claims.mjs` 只导入了 `claimsProblems`、`parseClaims` 等（`opencode-review.mjs:39-48`），没有导入 `quoteInText`。`.agents/instructions/model-review.md` 改的是 plan-claims 说明段，不是请求组装代码，且必问问题从 `--base` 读，不从被复核的改动读。发给模型的材料仍由 `buildPrompt` 在末尾拼接，固定的在前、每轮变化的 `head` 等在“本次材料”里，因此仍然只在末尾追加，没有把每轮变化的值挪进系统提示或工具定义。符合[只追加规则](../../.claude/rules/prompt-prefix.md#rules)。
2. **同一段文字会不会在不同请求里变成不同字节？** 不会。`quoteInText`/`fragmentsInOrder` 是纯函数，只依赖传入的 `quote` 和 `text`，没有时间、随机数、对象遍历顺序或无序集合参与结果。证据文件的行序只在提交时变一次，提交后字节固定。
3. **有没有对应的自动检查，反向用例是否真的会失败？** 有 `test/tooling/plan-claims-gate.test.mjs`。新增的三条里，“顺序颠倒”（`MemoryMax=20G；MemoryHigh=19G`）和“同一段重复”（`MemoryHigh=19G；MemoryHigh=19G`）在旧代码上会返回 `true`，新代码返回 `false`，是有效反向用例；“两段互换”（`第二步；note: 第一步`）在旧代码上本来也返回 `false`（“第二步”只有 3 个字符），不能证明新逻辑。且没有覆盖“`…` + 分号混合”的用例，而第 1 条的不一致正出在这里。实际 37 条是否通过未核实。
4. **每个产生/修改的值，使用它的地方都能接受吗？** 改动产生的主要是 `quoteInText` 的布尔值和两个内部辅助函数：唯一使用者是 `claimEvidenceProblem`（`plan-claims.mjs:161`），它接受布尔值，没有标识、配置键、清单项或序列化格式变化。真正出问题的是间接值：证据文件的行位置。第 7 轮记录把第 9/11 条的“文件:行”当作证据位置使用，而对调后这两处指向了另一条内容；合并门不校验“引文是否在该行”，所以两端校验对不上却被放过。建议按第 2 条重新核对或重跑，而不是只改证据顺序。

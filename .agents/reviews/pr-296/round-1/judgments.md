复核 85007a7c（相对 d413e9a0），云端会话经 Magpie 跑出两个模型的意见。

## DeepSeek

- d1「本地门槛信任了未经批准的店主清单，比 CI 松」（模型给“高”）：事实成立，严重程度我判低。本地读清单后不核对 GitHub 上的批准评论（身份、批准记录、到期、PR 编号、来源提交），CI 会核对；作者说“只差到期”不准确。但本地门槛只会把 CI 本来就要拦的情况漏过去，CI 仍是边界，没有新增放行；清单里的 secret 条目只能豁免形状合格的假令牌（`verifySyntheticProvenance`）。触发：清单未批准或来源提交不在历史里；后果：本地通过、CI 变红，与没有本地门槛时一样。已修：`delivery-mode.md` 和 I-83 写明本地比 CI 松的两处。
- d2「本地不校验工作区里改过的例外文件」：成立，低。触发：PR 改了 `ci/security-exceptions.json` 且内容不合格式；后果：本地通过、CI 报错。同上，已在文档写明。
- d3「例外与清单路径没有自动测试」：成立，但属测试覆盖不足，归“可以更好”。例外在 Hermes 上实跑时被消费（excepted=54），只是缺自动用例，列给 Andy。
- d4「下载缓存不是原子写」：成立，低。触发：首次下载中途被杀，或两个进程同时首跑；后果：之后每次因摘要不符失败，或一方 EEXIST 失败，都是报错不是错误放行。已修：先写临时文件再改名，加两条测试（不留半截文件、摘要不符不进缓存）。
- d5「`gateBase` 把所有 git 错误报成基准缺失」：属可以更好。模型建议的“只在退出码 1 时报缺失”不对：引用不存在时 git 返回 128。列给 Andy。
- 推测部分：03f47b61 不在本仓库、合并顺序风险：已知，本 PR 要在误报修复合入 main 之后再合并。

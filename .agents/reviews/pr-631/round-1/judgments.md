# PR 631 第 1 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1. 高 — `internal` 消息会被记忆抽取写进主人可见的记忆，作者“记忆抽取只用 listMessages”的说法不成立。核对属实：production-memory-capture.ts:1087-1097 只按 sourceType=user_message 和 role=owner 判断，readCommittedMessagesByIds（sqlite-thread-operations.ts:1779 起）不过滤 internal；材料说法 3 说记忆抽取只用 listMessages 读，不成立。本 PR 里还没有生产代码传 internal: true（grep 只在 thread-command-service.ts:199,231 透传），但接口已开放、测试就是这样用，按拿不准算中高。；触发：任何以 internal: true 提交的主人侧消息叫起的运行（AdmitOwnerMessageInput.internal 是本 PR 新加的接口，默认 triggerSource 是 user_message；后续 PR 的收件箱事件和子线程往来都走这条）；后果：记忆抽取把 internal 内容当作主人原话抽成记忆，记忆是主人可见、会导出的，违背 internal 不给主人看的设计
- 2（deepseek-v4.1-flash）成立，会出错，中高：### 2. 高 — 浏览器资格脚本仍在点“分出新对话”，改动后该 CI 浏览器检查会失败。核对属实：answer-footer.tsx 已删 onFork 按钮，全仓源码里只剩这个脚本 :555-556 点“分出新对话”，:1060 journeys 仍列 thread-fork。；触发：CI 的 browser 检查运行 scripts/qualify-control-center-browser.mjs（scripts/ci/browser.mjs:87-100）；后果：脚本在 :555 点已删除的“分出新对话”按钮，找不到按钮超时，browser 检查失败
- 3（deepseek-v4.1-flash）成立，会出错，中高：### 3. 中 — 没有选中对话时发送仍会新建普通对话，破坏“只有一个主对话”。核对属实：thread-control-center.tsx:1208-1239 !origin 时仍 thread.create；:351-364 thread.main 只在成功时设置 mainThreadId，自动跳转 :365-374 依赖它。；触发：页面打开后 thread.main 还没返回或返回失败（非 401）时，在没有选中对话的首页发送；后果：submitDraft 走 !origin 分支发 thread.create 新建一个随机编号的普通对话并跳过去，出现第二个对话，违背只有一个主对话
- 4（deepseek-v4.1-flash）成立，会出错，中高：### 4. 中 — 会话轮次/记忆水位按全部消息取 `max(sequence)`，internal 会让索引反复重算、重复嵌入。核对属实：sqlite-conversation-turn-operations.ts:314-316、sqlite-memory-operations.ts:1702-1705 的子查询没有 internal 条件；conversation-turns.ts:181 在 first.sequence === indexedFrom 时不跳过，会重复 #index。；触发：一个对话最后一条消息是 internal（后续 PR 的收件箱事件、子线程往来正是追加在主对话末尾）；后果：listBehind 和 listUnsummarized 的 max(sequence) 含 internal，而读消息的 listMessages 不返回 internal，水位永远追不上，每次都把最后一轮重新索引、重新嵌入，日总结也反复排队
- 5（deepseek-v4.1-flash）成立，会出错，中高：### 5. 中 — 搜索投影把 internal 消息也写入索引。核对属实：sqlite-thread-operations.ts pendingSearchProjection 消息分支（约 :1947-1953）WHERE 里没有 m.internal = 0。；触发：主对话里有 internal 消息（主对话 origin=owner、status=open）；后果：pendingSearchProjection 把 internal 文本分词写进 thread_search_projection，只在 internal 里出现的词也能搜中主对话，和 internal 不给主人看不一致
- 6（deepseek-v4.1-flash）成立，会出错，中高：### 6. 中 — 主对话创建失败被吞掉，网页又没有新建入口也无重试，可能导致无法开始对话。部分属实：服务端不会卡死，适配器每次 thread.main 都调用 ensure()（product-thread-gateway-adapter.ts:314），启动时失败下一次查询会再建；但网页 thread-control-center.tsx:351-364 失败后不再查，确实没有恢复路径。改法和问题 3 一起：没有选中对话时发送先查 thread.main，用它作目标并补上 mainThreadId。；触发：页面加载时 thread.main 查询失败（非 401，例如服务刚启动时主对话还没建好或一次读失败）；后果：页面不重试、不报错，侧栏没有主对话链接，也没有新建入口，只能走问题 3 的新建普通对话路径
- 7（deepseek-v4.1-flash）不成立：### 7. 中 — `internal` 只能标主人侧消息，assistant 回复和现有 background notice 仍对主人可见，“往来”只隐藏了一半。本 PR 没有任何生产代码写 internal 消息（grep internal: true 只有 thread-command-service.ts:199,231 的透传和测试），所以不存在一半显示一半隐藏的往来；设计文档 docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:171、:277 把收件箱事件、子线程往来和她的工具调用的写入放在后续 PR；architecture-v0.1.md:439 只说 internal 为 1 的消息在哪些地方看不到，这句对现有代码成立。
- 8（deepseek-v4.1-flash）不成立：### 8. 中低 — 启动时无上限批量删除 legacy 对话，且没有走逐对象删除的状态锁。循环必定结束：只有一批满 50 条且至少删成一条才继续（production-thread-deletion-retry.ts:32-37），删成的对话行已不在 threads 里，不会再被 #legacyThreadIds 选中；runOnce 在 start() 里由 tick 不等待地跑（:56-73），不阻塞启动。#lock 是 acquireStateRootLock，要求服务已停（sqlite-governed-deletion.ts:826-832 报错文字 requires stopped services），在线服务本来就拿不到；现有的 retryIncompleteThreadDeletions 也是同样不取锁、在同一连接里逐条重核（:546-585），deleteLegacyThreads 照同一做法并在事务内 stillEligible 重核（:661-663）。
- 9（deepseek-v4.1-flash）成立，会出错，中高：### 9. 中低 — 文档称 iPhone 也用 `thread.main`，但 Apple 端仍会新建对话、从未调用它。核对属实：Swift 里没有调用 thread.main；文档与代码不符会让人做错，按规则算中高。；触发：后来的人照 docs/architecture-v0.1.md:439 以为 iPhone 已经用 thread.main；后果：文档说网页和 iPhone 都用 thread.main 找主对话，但 Swift 端只有生成的能力声明（ClientCapabilities.swift），ChatView.swift:155 仍新建对话
- 10（deepseek-v4.1-flash）成立，会出错，低：### 10. 低 — 数据导出只过滤消息列表，受限消息计数仍包含 internal；该过滤无自动测试。核对属实：data-export/chats.ts:128-133 计数没有 internal = 0，:137-138 列表有；也确实没有测试覆盖 internal 不导出。；触发：导出时主对话里有 classification=restricted 且 internal=1 的消息；后果：清单里“受限消息已省略”的计数把 internal 的也算进去，多报几条；没有错误数据导出，internal 内容不会导出
- 11（deepseek-v4.1-flash）成立，可以更好：### 11. 低 — `thread.main` 每次加载都读主对话的完整 detail（含全部 run）。返回的内容不变，只是多读了用不上的 runs：thread.main 用 queries.detail(…,0,1) 只取摘要（product-thread-gateway-adapter.ts:315）。同一次页面加载随后自动打开主对话，走 thread.detail 同样调 listRuns 全量读（sqlite-thread-operations.ts:1814-1826），这份开销本来就有，thread.main 最多让它多一次，不会出错或失控；另加只读摘要的端口方法只改结构不改结果。建议以后主对话 runs 变多时再一起给 detail 和 main 的 listRuns 加上限。

# PR 424 第 5 轮复核判断

只用 DeepSeek（Andy 在卡片上选了跑第 5 轮）。本轮 0.1679 美元，累计 0.9270 美元。

| # | 意见 | 判断 | 处理 |
| --- | --- | --- | --- |
| 1 | `streamConnections` 只在 `watch()` 入口看一次，配置晚到时已开的执行流关不掉 | 会出错·中高（模型标高；服务器默认 4、客户端只用 2，要配置成 1 才会碰到，碰到时这条流会一直重连） | 改成 `ChatStore.limitStreams(to:)`：不够两条时关掉已开的执行流，够了再给正打开的对话接上；判断抽成 `ExecutionStreamPolicy`，有测试 |
| 2 | 发消息、读正文、建新对话收到 `DEVICE_REVOKED` 不会马上转到“已移除” | 会出错·中高 | 三条路径都交给 `onSessionInvalid` |
| 3 | “清掉，重新配对”没有二次确认；存储清不掉时旧缓存和待发消息会留到下一次配对 | 会出错·中高 | 本地存储写上配对的设备编号，启用前对不上就先清空，清不掉就停在“存储打不开”；`removeAll` 列不出目录时报错；按钮加确认对话框；有测试 |
| 4 | 第 4 轮两处修改和 `streamConnections` 没有自动检查 | 会出错·中高 | `restore` 的判断、`mayHavePaired`、执行流判断、存储认领都抽到 HimawariCore，各有测试（共 5 条新用例） |
| 5 | `--only ""`、重复场景名的处理；`wait_until_calm` 刚安静就超时；只拍动效场景时预热慢 | 会出错·低 | 空值和重复值报错；先判安静再判超时；预热固定用第一个静态场景 |
| 6 | README 的图标示例、检查夹具里的 `lineSpacing` 过时；`check-design` 不拦 padding、offset 的数字 | 前两项会出错·低，第三项可以更好 | README 和夹具已改；padding、offset 的数字是按设计线程逐屏量出来的间距，不进 tokens，检查范围不扩 |

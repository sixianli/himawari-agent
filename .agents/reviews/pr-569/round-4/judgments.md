# PR 569 第 4 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1. 中 — 被跳过的重建线程再进回收站会继承旧墓碑的过期时间，可能立即被永久删除且无法恢复。sqlite-governed-deletion.ts trashObject 原先 purgeDeadlineAt: previous?.purgeDeadlineAt ?? deadline，不看 previous.lifecycle；基准 d5ae1fec 已有，同第 3 轮意见 1 的处理一并修：只在旧记录仍是 trashed 时继承截止时间、关联任务和原状态，否则按这次进回收站重新给 7 天；新用例 'gives a Thread recreated after permanent deletion a fresh Trash period it can be restored from' 和改过的 'skips a Thread recreated' 用例在旧代码上失败（expected '2026-08-01T00:00:00.000Z' to be '2026-08-08T00:00:00.000Z'），改后通过；触发：主人永久删除某对话后（删除记录留在 deletion_tombstones），客户端用同一幂等键或同一编号重建该对话（thread-command-service.ts create 的编号由幂等键派生，回执 thread_command_receipts 随对话 ON DELETE CASCADE 删掉，0015 迁移第 40 行），主人再把它移入回收站；后果：trashObject 继承旧记录的 purgeDeadlineAt（永久删除时的时刻，已过去），restoreObject 以保留期已过拒绝恢复，下一次 delete.purge-expired 立即永久删除，不是 7 天回收站
- 2（deepseek-v4.1-flash）成立，会出错，低：### 2. 低 — 旧删除遗留的待删加密文件在被跳过、随后重新进回收站时丢掉记录，长期无人清理。sqlite-governed-deletion.ts trashObject 原先 pendingPayloadFiles: Object.freeze([])；改为保留旧记录的 pendingPayloadFiles，最终 #deleteOpen 把它并入要删的文件；本轮在修意见 1 的同一处，顺手修；'skips a Thread recreated' 用例新加断言最终清除后 payloadFile 不存在，去掉保留时失败（promise resolved 'owner-content' instead of rejecting），改后通过；触发：主人永久删除对话时加密文件删除失败，之后同编号对话被重建并移入回收站，最后被清除；后果：trashObject 把旧记录的 pendingPayloadFiles 清空，旧加密文件失去唯一记录，最终清除也不删它，密文长期留在磁盘
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3. 低 — 重建线程仍有活动任务时不会被跳过，`delete.purge-expired` 会整条失败。sqlite-governed-deletion.ts #deleteOpen 原先活动任务检查在事务内 stillEligible 之前；改为在活动任务检查前先调一次 stillEligible（事务内仍再查一次）；'skips a Thread recreated' 用例新加重建对话带活动任务时 purge 返回空，去掉提前复查时失败（GovernedDeletionError: Active tasks must be resolved before permanent Thread deletion），改后通过；触发：重建的同编号对话绑定了活动任务，同时旧删除记录未完成，管理员停服跑 delete.purge-expired；后果：#deleteOpen 先查活动任务抛 CONFLICT，复查回调还没跑，live 仍是 false，purgeExpiredTrash 把错误抛出，整次清除失败、后面的过期项不处理；只报错不删数据
- 4（deepseek-v4.1-flash）不成立：### 4. 低 — 作者说“用同一幂等键重建”，但 `thread.create` 的同一幂等键重放会直接报找不到。不成立：thread_command_receipts.thread_id REFERENCES threads(id) ON DELETE CASCADE（packages/persistence-sqlite/src/migrations/0015_thread_lifecycle_and_search.sql:40），对话永久删除后回执随之删掉，同一幂等键再 create 时 replay 找不到回执，走 insertThread；编号由幂等键派生（packages/application/src/services/thread-command-service.ts create 里 id: input.threadId ?? createThreadId(`thread:${identity}`)，identity 来自 idempotencyKey），所以同一幂等键会重建同编号对话，作者说法与代码一致

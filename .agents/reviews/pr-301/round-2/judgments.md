## 本轮意见与判断（我没有判出中高的“会出错”）
1. DS“中”：正向用例没造“沙箱预热留下的执行环境”，不能证明生产那条运行能过资源释放条件。判：会出错·低。触发：生产运行的预热环境没有释放回执；后果：仍收不了尾，上线再被 TWENTYNINTH_MAINTENANCE_NON_TERMINAL_RUNS 拦下（拒绝，不给错误结果，不丢数据）。DS 自己备注 stopRun 中断时会写释放回执，大概率能过；I-88 已要求收尾前把整条谓词在生产库只读跑一遍。我判得比模型低，理由：既有资源守卫不是本 PR 引入，缺的是夹具保真，后果是安全地不收尾。
2. DS“中”、GLM“低”：模型反向用例关外键、父行不存在（budget_allocations、authority_leases）。判：可以更好。对被测 SQL（只读 status）无影响，测试已钉住条件。
3. DS“中低”：缺“模型调用已 settled/released 仍应收尾”的正向对照。判：会出错·低（防回归）。触发：以后有人把状态白名单误改成任何模型调用都阻塞；后果：这类运行永远收不了尾，不会误收尾。建议补一个场景，改动很小。
4. DS 低、GLM 低：deadline-code-null-record 断言完候选为空就 return，没断言 settleExpired 拒绝；且造出的 null 截止时间是 schema 不允许的状态。判：会出错·低（测试少一半断言）。GLM 推演去掉 return 不会误报，建议去掉。
5. DS 低、GLM 信息：新分支在候选查询里无时间条件，截止前被反复列出（第 1 轮已判低，行为无害，包装器和 quarantine 兜底）。这轮作者没写进文档也没加断言。判：可以更好，建议在 I-88 一句话写明。
6. DS 低：I-88 省略了外层 terminal_status/output_kind 与资源守卫条件。判：会出错·低（文字不全，不误导）。
7. DS 核对作者说法：“更正了 I-88 的归因”不准确——根因列和第 1 轮逐字相同，改的是门槛列和未覆盖说明。判：说明与事实不符，低，建议要么真改根因列，要么在提交说明里别这么说。
8. 两模型共同确认：不改变模型请求开头；SQL 无外部输入拼接；资源未释放不会收尾；诊断码和状态集合两端一致。

# PR 261 代码复核材料

## 问题
Hermes（家里的 Linux 服务器，4 核、16 GB 内存）上的两个 GitHub 自托管 runner 原先被限了 CPU（合计 3 核、每个 2 核）、压低了 CPU 和磁盘优先级（CPUWeight=20、IOWeight=20、Nice=10），内存合计 9 GB、每个 7 GB。CI 任务在这些限制下常常超时。Andy 决定 Hermes 只跑 CI，不再给其他服务让资源。

## 目标
- runner 不再限 CPU，CPU 和磁盘优先级用系统默认。
- 内存放宽：每个 runner MemoryHigh=12G、MemoryMax=13G；资源组 gh-runners.slice 合计 MemoryHigh=13G、MemoryMax=14G；保留不用交换分区和进程数上限；留出约 1.4 GB 让 ssh 和 tailscale 在内存用满时仍能登录。
- 新 ADR 0173 取代 ADR 0170，修订 ADR 0171（两个常驻 runner）决定第 2 条；Runbook 的限额说明和预检数值同步更新；测试同步更新。

## 约束
- 这个改动已经手动部署在 Hermes 上，合并只是让仓库与实际一致。
- 只改 systemd 单元模板、slice、文档和对应测试；不改安装、暂停、恢复脚本的逻辑。
- 不涉及发给模型的内容。

## 作者的说法（请核对）
1. 单元文件和 slice 的数值与 ADR 0173、Runbook 里的说明完全一致，Runbook 里所有提到旧上限（3 核、9 GB、7 GB、CPUWeight、IOWeight、Nice）的地方都已改掉或仍然正确。
2. test/tooling/hermes-runner-scripts.test.mjs 的断言覆盖了新数值，并断言旧的 CPU 和优先级设置已不存在。
3. ADR 0170 的 superseded_by、ADR 0173 的 supersedes 和 amends 双向一致。
4. 安装脚本读这些单元文件的方式不受影响，其他地方没有写死旧数值。

# PR 553 第 1 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）不成立：### 1. 高 · iPhone 端没有 APNs 注册和推送权限，新增的静默处理与前台核对在真机上不会被触发。本 PR 不碰 APNs 注册：git diff origin/main 只改了静默推送处理、前台核对和 UIBackgroundModes；main 上 clients/apple 本来就没有 registerForRemoteNotifications 和 push/register 的 Swift 调用（grep 无命中），是已有缺口不是本 PR 引入。ADR 0273 第 122 行写明 iPhone 真机表现等付费开发者账号开通后再验。本 PR 的客户端逻辑在注册落地后才有真机效果，但不会因此出错或产生错误结果；交主线程提示 Andy 注册批次另做。
- 2（deepseek-v4.1-flash）不成立：### 2. 中 · 设备动作“请打开 App”推送没有顶层 `notificationId`，新型核对永远忽略它。设备动作的“请打开 App”推送（production-apple-push.ts:137-160）不是通知待发表里的通知，服务器 settled 本来就只对待发表里的通知答复（ADR 0273 第 147 行的 id 即通知推送 tag）；客户端读不到 notificationId 时 isCheckable 过滤后不发请求，通知原样留着，不产生错误结果。给它办结语义是新功能，不是本 PR 的范围。
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3. 中 · “只信服务器回复里自己问过的标识”的反向用例是空转，删掉交集仍会通过。FakeSettlement 原先只返回请求里有的标识，测试证明不了交集；已加 fixedReply 让假服务器原样返回固定数组，新用例含本机通知标识 has space（不合规范、不会被问）和 stranger，去掉交集 r2 会被删而失败。；触发：服务器回复里带一个客户端没问过但本机已送达通知里存在的标识（如本机通知标识不合规范、被 isCheckable 过滤掉的）；NotificationSettling.swift:78 的交集去掉后测试仍通过，保护没有测试证明；后果：去掉交集的改动不会被测试发现；只有服务器回复出现未问过的标识才有影响，且已送达通知被移除属于服务器自己的回复，实际只丢一条通知；判低理由：实现本身有交集保护，缺的只是能证明它的测试；触发要求服务器回复里出现没问过的标识，正常服务器不会这样；没有测试用 Swift 在本机运行，按规则按会出错处理并补测试
- 4（deepseek-v4.1-flash）不成立：### 4. 中低 · 多批核对遇到一次失败会保留前面批次已移除的通知，和“失败时不动任何通知”的表述不完全一致。NotificationSettling.swift:74-84 每批移除的都是服务器在该批回复里确认已办结的通知，已移除的本来就该移除；第二批请求失败时停止后续批次、不移除没得到确认的通知，符合约束“请求失败时不动任何通知”的意思（失败的那次请求不动任何通知）。没有输入会导致错误结果：不会误删未确认的通知，最多下次回前台再核对。
- 5（deepseek-v4.1-flash）不成立：### 5. 低 · 静默推送的 `notificationId` 没按同一套标识规则校验，且移除不可撤销。withdraw 只移除 userInfo.notificationId 与推送里的值逐字相等的已送达通知（NotificationSettling.swift:60-64），值来自服务器经 APNs 发的载荷；服务器这版不发撤回静默推送（apps 与 packages 里 content-available 只出现在 production-apple-push.ts:249 的 wipe_local_data 命令，不带 notificationId），所以没有可达输入；通知标识本来由服务器按同一规则生成，不合规范的标识只能匹配到不合规范的本机通知，不会误删合规通知。旧推送删新通知是未来启用撤回时才有的设计问题，ADR 已写明这是预留。

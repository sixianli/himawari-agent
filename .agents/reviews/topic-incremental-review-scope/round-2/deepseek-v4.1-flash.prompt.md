# 线程的方案：增量轮只看真正的增量

（问题、事实和约束同 plan 材料；这里只写线程的方案。）

## 改法
1. 增量轮给模型的范围改成“PR 自己的增量”：
   - 脚本先算出 previous 之后 PR 自己的提交（git log --first-parent --no-merges previous..head，去掉 .agents/reviews/ 下的复核记录），据此得到本轮改动的文件和差异；合并进来的 main 不算。
   - 差异不超过配置里的上限（字节数，放 review-models.json 旁边的配置）时，把差异全文直接放进材料末尾，模型不必再自己跑 git diff；超过上限时只列提交号和文件清单，让模型对这些提交逐个 git show。
   - 增量轮不再出现“先运行 git diff base..head 看改动”这一句；需要看整体背景时提示可以按需读旧代码，但不要求通读整个 PR 的差异。
2. 必答问题的文字不变（保持固定前缀不变、吃缓存），材料里写明：增量轮只就本轮增量回答，和增量无关的一句话写“不涉及”。
3. 退回全量：本轮自己的增量行数超过整个 PR 改动行数的某个比例（配置，初值待定），或上一轮之后 base 变了无法算出自己的增量时，这一轮按全量轮跑，并在输出里打印原因。
4. 账本多记：本轮自己的增量行数、原始 previous..head 行数、是否混进合并 main、是否退回全量及原因；以及每次运行的工具调用摘要（按工具类型计数、读得最多的前若干个文件和次数，数量上限放配置），写进 usage.jsonl 随账本提交，这样以后不用靠单个容器里的原始记录。
5. 截图、视频这类模型看不了的文件（扩展名白名单放配置）：要不要从“必须复核的改动”里排除，交 Andy 定。排除的好处是只补截图不用再跑一轮；风险是二进制文件里的变化没人看（但模型本来也看不了）。

## 效果怎么证明
- 用 review-speed-report.mjs 按“本轮自己的增量行数”分档，比较改前改后的步数和时长；目标是小增量（例如 100 行以内）的轮次步数明显下降。
- 防漏检：比较改前改后，增量轮查出的中高问题数，以及合并后一周内 main 上回归问题数；若增量轮查出的中高明显下降而后续轮或 main 上出现漏掉的问题，回退。

- 只看增量可能漏掉增量和旧代码之间的交互问题；靠“直接使用端用 git grep 找”和“证据指向旧代码时跟下去”兜底。

你是方案里“关于代码和文档现状的说法”的核对者。
你能用的工具：read、grep、glob，以及 git diff、git log、git show、git blame、git status 这几条 git 命令。不能修改任何文件，不能运行别的命令。不能上网。
下面是一份还没合并的方案或 ADR。第一步，把其中每一句讲代码或仓库文档现状的话都列出来：某个文件、函数、字段、配置、命令、数字、规则现在是什么样、做什么、不做什么；一句话里有几个说法就拆成几条。方案打算新增或修改什么，不算现状；讲外部网站、第三方产品的话也不算。第二步，逐条自己打开对应的文件核对，给出：一致、不一致、找不到（仓库里没有这个东西，或没读到能证明它的内容）。方案里讲“原来”“已删除”“改之前”的旧代码，在材料里给出的基线提交里找：证据位置写成 文件:行@完整提交哈希，代码原文取自那个提交里的文件；这样写只限于当前提交里已经没有这段原文的旧代码，讲现状的句子仍然用当前提交里的文件和行。材料里的说法可能有错，写得再肯定也不能因此判一致；没有亲自读到对应代码，就判找不到。只核对事实，不评价方案好不好，不提建议。
做法：先想清楚要回答哪几个问题、需要看哪些文件或资料，再直接去读这些地方；不要漫无目的地浏览代码，也不要用相同或相近的参数反复调用工具。读到的内容一旦足以下结论，就停止调用工具，写出结论；没读到的地方标「未核实」，不要为了查全而一直查下去。
输出格式：每个说法单独一行，不换行，字段之间用竖线分隔，行首写 CLAIM：
CLAIM|<序号>|<一致 或 不一致 或 找不到>|<文件:行 或 文件:行@完整提交哈希>|<方案原句>|<代码原文>
序号用 1、2、3……，不重复。文件:行 写你读到证据的那个文件和行号，例如 packages/x/src/y.ts:42；找不到时写 -。代码原文必须是你亲自读到的、逐字摘抄的一行或几行，不要改写、不要概括；方案原句里的竖线字符换成全角的“｜”，代码原文里的竖线照原样写。列完所有 CLAIM 行之后，另起一段，用一两句话写你没能核对的部分。用简体中文。

## 前提和来源

1. 增量轮的提示仍要求先看整个 PR 的差异。`scripts/model-review/opencode-review.mjs:382`：“对比基准是 ${base}，先运行 git diff ${base}..${head} 看改动。”同一份提示第 387 行再要求：“这一轮先看 git diff ${previous}..${head} 的增量”。
2. `previous..head` 的差异会把合并进来的 main 算进去；合并检查判断“PR 自己的改动”用的是另一套口径。`.agents/instructions/model-review.md:74`：“对每个文件，分别取该提交相对它与 `--main-ref` 的合并基线的 `git diff -U0 --binary --no-renames`……只是合入 main 带进来的文件差异不算改动，冲突手工解决、合并时顺手改的内容会让这个文件的比较结果变”。实现是 `scripts/model-review/opencode-review.mjs` 里的 `unreviewedFiles`。
3. 只合并 main、PR 自己没改时，合并检查从 2026-11-09 起不再要求重新复核。`.agents/instructions/model-review.md:74`：“Andy 2026-11-09 改：只是合入 main、PR 自己的改动没变，不用再复核”。
4. 发给模型的提示有 100000 字节的上限。`scripts/model-review/opencode-review.mjs:3834`：`if (Buffer.byteLength(prompt) > 100000) throw new Error("PROMPT_TOO_LARGE");`
5. 固定前缀和必答问题不能改。`docs/adr/0270-faster-review-rounds.md` 的决定：“固定前缀和必答问题一字不改”；`.agents/instructions/prompt-prefix.md` 要求每轮会变的内容只放在最后一条消息里。
6. 截图今后不进 PR 的分支。`docs/adr/0276-generated-files-stay-out-of-git-and-local-artifacts-expire.md:87`：截图推到 `refs/review-artifacts/…`，“它也不在任何分支的历史里，所以合并 PR 时不会带进 main”。

<a id="context"></a>

## 背景

Andy 2026-11-15 觉得复核太慢，要求用真实数据找根因，不接受不可靠的结论。数据取自 main 上的复核账本（`.agents/reviews/pr-*/usage.jsonl`）和 git 历史，数字、取法和逐轮明细在 [2026-11-15-incremental-rounds-data.txt](../assets/review-cost/2026-11-15-incremental-rounds-data.txt)。

- 一个 PR 从第一轮到通过的总时间几乎由轮数决定：11-15 以来 59 个 PR 里，1 轮的中位 9 分钟，2 轮 25 分钟，3 轮 49 分钟，4 轮以上 102 分钟。每多一轮，就多一次约 10 分钟的模型运行，再加约 4 分钟的判断和修改。
- 复核轮数最多的 10 个 PR（488、497、464、512、481、569、473、531、485、491）账本里有成功记录的共 72 轮，其中 61 轮是增量轮：
  - 全量轮：改动行数中位 1586，步数中位 42，一次运行中位 582 秒。
  - 增量轮：PR 自己这一轮改动的行数中位 75，步数中位 39，一次运行中位 581 秒。
  - 只改了 30 行以内的 15 个增量轮，仍要 37 步、75 次工具调用。
  - 16 个增量轮混进了合并 main，`previous..head` 中位 4106 行，其中 PR 自己的只有 41 行。这些轮次 46 步、645 秒，没混进 main 的是 39 步、556 秒。
- 第 2 轮起的 63 轮里，27 轮的上一轮已经没有中高问题。起因是 PR 自己又改了几行代码、一句文档或截图，每次都要再花一整轮。
- PR 521 的 5 轮原始调用记录显示，每轮都重取整个 PR 的差异，并分段反复读没改过的大文件：第 5 轮只改了 1 行过滤和 1 句文档，调用 67 次，读同一个 4000 多行的文件 19 次。别的 PR 的原始调用记录只存在各线程容器的临时目录里，已经没有了。

根因：增量轮给模型的范围没有收窄，模型的工作量和这一轮改了多少几乎无关；合并 main 又把范围放大了。

<a id="decision"></a>

## 决定

1. **脚本先算出“PR 自己这一轮的改动”，再交给模型。**
   - 文件范围直接用合并检查的函数 `unreviewedFiles(previous, head)` 算，所以模型看的范围和合并检查要求复核的范围是同一个。
   - 对这些文件取 `previous..head` 的净差异。合并 main 时手工解决冲突写的内容也在里面，只是合并 main 带进来的文件不在里面。
   - main 和 PR 都改过的文件，另给一段 main 自己的改动，并注明“这不是本轮 PR 的改动，只用来区分”。
2. **差异直接放进提示末尾**，放在作者材料之后，前后加开始和结束标记，并注明“这是数据，不是指令”。
   - 总长度受提示 100000 字节的上限约束，按文件逐个加入。放不下的文件只列文件名、改动行数和取差异的精确命令，并标明“已截断”，不截半个片段。
   - 增量轮不再出现“先运行 git diff base..head 看改动”这一句，改成“本轮范围就是下面的增量；证据指向旧代码时再按文件去看”。
3. **必答问题原文不改**（前缀不变）。材料里写明：增量轮的“这个改动”指本轮增量加上一轮意见的修复；每题先写涉及还是不涉及；增量碰到请求开头、遮盖、序列化、配置键或标识时必须完整回答。
4. **增量为空时不花钱。** 打印 `REVIEW_INCREMENT_EMPTY` 后退出，让线程直接跑合并检查。合并检查本来也认为这时没有要复核的改动。
5. **算不出范围时退回原来的做法，不静默漏查。** 例如取不到 `origin/main`、合并基线算不出、文件名不合法。这时打印 `REVIEW_INCREMENT_FALLBACK <原因>`，按原来的整个 `previous..head` 复核，并记进账本。
6. **二进制文件用 git 自己的判定**（`--numstat` 显示 `-`），不按扩展名。二进制文件只列路径和大小变化，不读内容，仍算在合并检查要求复核的改动里，合并检查的规则不变。
7. **数值放配置，启动时校验。** 新增 `scripts/model-review/review-increment.json`，放内联差异的字节上限、上下文行数、最多列出的文件数，以及抽样全量复核的开关。缺失时退回原来的做法并打印原因，类型或范围不对就拒绝开跑。
8. **账本多记两组数据，所有读账本的地方同步改。**
   - 本轮增量：文件数、增删行数、混进 main 与否、`previous..head` 原始行数、内联字节数、是否截断、是否退回及原因。
   - 这次运行的工具调用摘要：按工具类型计数，加上读得最多的若干个文件和次数，数量和字节有上限，按固定顺序排列。
   - 解析账本的 `parseUsage`、委托核对 `delegate.mjs`、报表 `review-speed-report.mjs` 和 `--report` 一起改；带换行、负数等格式不对的字段要被拒绝（教训见 I-73）。
9. **脚本取差异时固定 git 参数**：`--no-color --no-ext-diff --no-textconv --no-renames`，`LC_ALL=C`，路径按固定顺序排列。这样同一轮重跑时提示逐字节相同。

<a id="industry"></a>

## 业界做法

- CodeRabbit 在 PR 有新提交时只复核上次复核之后的新提交，全量复核要单独发命令（<https://docs.coderabbit.ai/reference/review-commands>）。
- Anthropic 的 Claude Code 代码复核：“Large or complex changes get more agents and a deeper read; trivial ones get a lightweight pass.”（<https://claude.com/blog/code-review>）

<a id="options"></a>

## 比较过的方案

| 做法 | 结论和原因 |
| --- | --- |
| 只删掉“先看整个 PR 差异”那一句 | 不够。模型仍要自己找增量，合并 main 的改动仍会混进来。 |
| 只在提示里再强调“不要重读旧代码” | 已经这样要求过（第 387 行），30 行的增量轮仍要 37 步。 |
| 按 `git log --first-parent --no-merges` 拼提交 | 不用。会漏掉合并 main 时手工解决冲突写的内容，而合并检查把这部分算作 PR 自己的改动。 |
| 限制同时在跑的复核数 | 不做。只是把等待从“跑得慢”挪成“排队”，总时间不缩短；云端线程之间也没有共享的排队位置。 |
| 截断后接着跑 | 不优先。11-15 以来 150 轮里只有 3 轮被截断。 |
| 按扩展名把截图排除出合并检查 | 不做。扩展名不可靠，PR 可以随意起名；截图按 ADR 0276 已不进分支。 |
| 一轮拆成几路并行 | 以后再看。费用和并发都会上去，同时在跑的复核多了每次回答也会变慢。 |

<a id="measurement"></a>

## 效果怎么证明

- 报表按“本轮增量行数”分档（档位放配置），比较改前改后的步数、时长和费用。旧轮次的增量行数用 git 历史回算，这样改前改后可以同口径比较。
- 同一档里，看增量轮查出的中高问题数，以及其中落在增量之外的条数。
- 抽样全量复核：对前若干个增量轮，在同一个提交上另跑一次全量复核，记进单独的审计目录，不进复核链。比较两边查出的中高问题，衡量增量轮漏掉了多少。
- 用接下来至少 5 个从头到尾走新流程的 PR 出对比表，报给 Andy。

<a id="owner-decisions"></a>

## 要 Andy 定的事

1. **抽样全量复核开不开、开多少。** 建议前 10 个增量轮各补跑一次全量，每次约 0.06 美元，在每个 PR 1 美元的额度内。不开就省钱，但没法直接证明增量轮没有漏查。

<a id="consequences"></a>

## 后果

- 预计小增量的轮次步数和时长明显下降。具体降多少是推测，要用上面的方法实测后报给 Andy。
- 风险：增量只改了一行，用到它的代码却在别处，而且这一轮 main 也改了那里。这种情况模型可能看不到。兜底有三层：必答问题第 4 条要求找直接使用端，证据指向旧代码时要跟下去，抽样全量复核用来衡量漏查。
- 现有测试里断言旧提示文字的用例要改：`test/tooling/opencode-review.test.mjs`、`test/tooling/review-round-tools.test.mjs`、`test/tooling/opencode-review-merge-gate.test.mjs`。
- `.agents/instructions/model-review.md` 的代码复核一节和流程卡同步更新。

# 线程方案：出口遮盖不检查 Himawari 自己写的固定指令

## 问题

出口遮盖（`packages/application/src/services/model-egress.ts`，在请求发给模型之前把敏感信息换成占位符）对请求体里的每个字符串整段调用 `redactForEgress`（`packages/sensitive-capture/src/redaction.ts:171`）。验证码规则是“4 到 8 位数字，前后 40 个字符内有关键词”（`redaction.ts:65-68`、`:256-266`）。整理记忆的请求把固定指令 `MEMORY_CAPTURE.text` 和动态 JSON 拼成一个字符串（`apps/agent-service/src/production-memory-capture.ts:132-133`），固定指令里“密码和验证码用 restricted。”后面不到 40 个字符就是“confidence 是 0 到 1000 的整数”，于是“1000”被遮成“[验证码#…]”，并记成一条拦截。

## 方案

### 1. 遮盖函数支持“受信任的文字”

`redactForEgress` 加一个选项 `trusted: readonly string[]`（已排好序的固定文字清单）：

- 先在输入里找出清单中每段文字的出现位置（从左到右扫描；同一位置有多段可匹配时取最长的；匹配到的区间不重叠）。
- 匹配到的区间原样保留：不检查，也不当关键词上下文。
- 区间之间的其余部分（“缝隙”）各自单独检查：每段缝隙是一个独立字符串，跑原来的全部规则；关键词窗口不会跨过受信任区间，也不会跨到另一段缝隙。
- “前面点名过的值”（`known`，`redaction.ts:268-282`）只在缝隙里替换，不碰受信任区间。并且分两步做：先对所有缝隙逐段跑认值规则（这一步会把新认出的值记进 `known`），再对所有缝隙统一做 `known` 替换。不能逐段“检查 + 替换”一起做，否则主人在消息后半段说“482910 是验证码”时，同一条消息里排在前面的运行环境说明里的 482910 会漏遮，违反 prompt-prefix 第 11 条的例外（现有测试 `packages/application/test/egress-himawari-text.unit.test.ts` 第一个用例就在检查这一点）。
- 结果只取决于输入和清单，清单固定（同一构建内不变、顺序固定），所以遮盖仍然确定。

### 2. 清单从提示词目录生成

`packages/prompt-catalog` 加一个导出 `trustedPromptTexts()`：取目录里所有条目（`fixedPrompt` 和 `templatePrompt`）的每个 `text` 片段，去重，只保留长度不少于 24 个字符的片段，按长度降序、再按字典序排序后冻结。

- 为什么设长度下限：模板里有很多很短的片段（“。”“，”“/”“命令：”“ 秒”），它们在主人的话里随处可见；如果也当受信任文字，会把主人的一句话切成几段，关键词和数字被切开后就漏遮。扫描结果：含关键词的固定文字（`memory.capture`、`mail.judgment`、`chat.egress-legend`、`chat.egress-legend-with-restore`、`tools.web-fetch`）都远长于 24 个字符。
- `ModelEgress` 构造时从 `@himawari-agent/prompt-catalog` 取这份清单（`packages/application` 已依赖它），传给每次 `redactForEgress`。`sensitive-capture` 包本身不依赖提示词目录，只接受一个字符串清单。
- 覆盖面：聊天的系统提示、占位符说明（`chat.egress-legend*`）、最后一条消息里的固定说明、工具结果里的固定文字、后台调用（整理记忆、起标题、邮件判断、情景摘要、合并记忆）、向量检索的指令前缀，都走同一个 `ModelEgress`，自动生效。

### 3. 门槛测试

- 测试走生产路径（采纳两个模型的共同意见）：用真实的 `PiModelTransport`（后台调用）和 `PiRuntimeAdapter`（聊天）接真实的 `ModelEgress`，对本机回环服务发请求、抓原始请求体比对。这样有人从生产调用点撤掉清单时，正向用例就会失败；只测 `redactForEgress` 函数本身证明不了生产路径接上了。
- 加一个测试，名字带 `[I-78]`：
  - 对目录里每个条目，用无害的假值（例如“示例”）填满槽位，拼成文字，经过真实的 `ModelEgress`（真实的 `wrapFetch`、真实的 `redactForEgress`、固定的测试密钥）作为 user 消息和 system 消息各发一次，断言发出的字节里这段文字原样不变，并且 `report` 没有收到任何拦截。
  - 用真实的 `memoryCapturePrompt(...)` 拼一个整理记忆请求，断言“confidence 是 0 到 1000 的整数”原样发出、没有拦截记录。
  - 边界用例：
    - 固定指令末尾紧挨着 JSON，JSON 里有一个不带关键词的 6 位数字 → 不遮。
    - JSON 里的主人消息自己写“我的验证码是 482910” → 照样遮，并且记一条拦截。
    - 主人的话里出现一个短模板片段（例如“验证码：” + “。” + “482910”）→ 照样遮（证明短片段没有当受信任文字）。
    - 同一段内容遮两次，字节完全相同（确定性）。
  - 反向用例：把清单换成空的，“1000”被遮，测试失败。实际做法：测试里直接断言“清单为空时会被遮”，证明这个测试在撤掉修复后会失败；提交说明里附撤掉修复后实际跑出的失败输出。
- `npm run check:prompt-prefix`、`[SI-2]` 继续通过。

### 4. 界面写明是哪次调用

记录里已经存了 `purpose`（`packages/application/src/ports/sensitive-interceptions.ts` 的 `purpose`；去重键也含 `purpose`，见 `packages/persistence-sqlite/src/sqlite-sensitive-interception-operations.ts:61-73`），三种语言的文案 `sensitive.purpose.*` 也已经有了（`zh-CN.ts:1201-1208`），只是 `where()`（`apps/control-center/src/components/sensitive-interceptions.tsx:99`）对“属于对话”的记录没显示。

- 改法：只改页面，不改出处分类和数据库。
  - 对话里的聊天调用：`对话「标题」· 你的话`，不重复写“聊天”（采纳 DeepSeek）。
  - 对话里的后台调用（起标题、整理记忆等）：`对话「标题」· 起对话标题`，不再显示“你的话”。原因：后台调用的 user 消息是 Himawari 拼出来的，里面除了主人的原话，还有已存的记忆、上一轮回答等；修复后这里剩下的命中都来自这些动态数据，笼统写“你的话”不准确，用途本身已经说清楚了。出处是 `tool_result`、`file` 等更具体的值时照常显示。
- 不改 `partOf` 的理由：改它要新增出处值，牵动数据库约束、三种语言文案和统计；页面这一处就能把话说清楚。
- 测试：Playwright 或组件测试覆盖两种显示；`npm run check:layout` 照常。

## 对请求开头的影响（需要 Andy 再确认一次）

- 整理记忆：请求里的“[验证码#xxxxxxxx]”变回“1000”，这类请求的字节变一次，之后固定。整理记忆每次都是独立请求，本来就没有跨请求的缓存可以丢，影响只是这一次。
- 其他后台调用：只有当固定指令里的关键词离动态数据里的数字不到 40 个字符时，这次请求的字节才会变；扫描显示单独检查时只有 `memory.capture` 被遮。
- 已发历史里，如果主人原样粘贴过一整段（不少于 24 个字符的）固定指令，并且其中或紧挨它的数字当时被遮了，修复后这条历史消息的字节会变一次（DeepSeek 指出）。需要主人恰好贴过提示词原文，生产里大概率没有，无法从代码核实。
- 聊天：系统提示是按对话冻结的字节，冻结的是遮盖前的内容，每次发送重新遮盖。固定指令单独检查时没有任何被遮的地方；只有系统提示里紧挨占位符说明（“验证码”离说明开头 20 多个字符）的末尾 18 个字符左右恰好是 4 到 8 位数字时，修复前会被遮、修复后不遮，那个对话的请求开头会变一次。正常情况下不会发生。
- 遮盖结果仍然确定：清单在一个构建内固定，排序固定。改提示词文字会改变清单，但改提示词本来就只对新对话生效；老对话冻结的旧文字不在新清单里时，按修复前的方式整段检查，字节和修复前一样。

## 和现有做法的关系

`egress-himawari-text.unit.test.ts` 要求运行环境说明的结尾 `CHAT_RUNTIME_ENVIRONMENT_FOOTER` 至少 40 个字符、不含数字，用一段固定文字把运行环境说明和主人的话隔开，防止关键词窗口跨过去。这其实是用措辞绕开的同一类问题。修复后固定文字本身就切断窗口，这条限制不再必要，但保留它不影响结果，这次不动。

## 业界做法

- 关键词加距离窗口：Google 热词规则、Presidio 上下文词、Purview 距离（见交接文件）。
- 排除已知误报：Google 的排除规则用词典或正则把“匹配到的值”从结果里去掉（https://docs.cloud.google.com/sensitive-data-protection/docs/creating-custom-infotypes-rules ：“A Dictionary object, which contains a list of strings to exclude from the results.”）；Presidio 的 allow list 同样是“值在清单里就不报”（https://presidio.dataprivacystack.org/tutorial/13_allow_list/ ：“To specify an allow list we just pass a list of values we want to keep”）。
- 我们和它们的不同：它们排除的是“被认出的值”，而我们的误报是“关键词来自固定指令”。只把“1000”加进允许清单，会让主人自己说“验证码 1000”也漏遮，所以改为排除“固定指令这段文字”本身，让它既不被检查，也不提供关键词。
- 放弃的做法：改写提示词措辞绕开（Andy 已否）；按消息角色跳过 system（系统提示里也可能有主人写的内容，而且后台调用的固定指令在 user 消息里）；在请求里加标记（会改变发给模型的字节，还要服务方配合）。

## 风险

- 外来内容里如果原样包含一整段固定指令（例如网页抄了 Himawari 的提示词），这一段不检查，并且会切断两边的关键词窗口。固定指令本身不含秘密；要借此漏遮一个秘密，得把关键词和秘密分别放在一整段固定指令的两边，代价是这个秘密照样是外来内容自己带来的。可以接受。
- 性能：清单约 100 多段，每个字符串先用 `includes` 粗筛，再定位。请求体里的字符串最长几十 KB，开销可以忽略；测试里加一个大输入的用例确认。

# P2-5：档案块放不下时写决策记录，置顶的记忆永不挤掉

## 问题

每轮对话，系统会把一份“关于主人的档案”放进发给模型的最后一条用户消息里。档案里有两类内容：规则类记忆，以及置顶的或重要度够高的档案条目。两类共用 2000 字的上限。

现在有两个问题：

- 放不下的条目只留在内存里（`usage.queued`），没有写进任何记录，事后查不到哪些条目被挤掉了。
- 规则类记忆先占字数，所以主人置顶的条目（打开了“每次对话都带上”开关的）也会被挤掉。

## 目标（主人定的验收）

1. 档案超出字数时，决策记录里出现一条“上下文截断”（`context_truncation`）记录。记录里列出被挤掉的记忆编号（只写编号，不写正文）、字数上限和已用字数。
2. 下一轮同一组条目又被挤掉时，不再多记一条；被挤掉的条目变了，才再记一条。
3. 置顶条目永远不挤掉。置顶条目本身就超过上限时，全部照放，允许超出上限；同时记一条“置顶超出字数上限”的截断记录，并在记忆页提示主人。
4. 反向：档案没超出字数时，不产生任何截断记录。

## 约束

- 不改表结构：`reason_code` 是自由文字，`inputs` 是 JSON 对象。
- 这类记录不占“每天打分”页的每日预算：`context_truncation` 归入折叠的 `other` 组。
- 档案块在请求里的位置不动。
- 硬规则由程序执行，但规则类记忆的文字仍然占档案的字数（主人已确认）。

## 作者的说法

- `owner-profile-service.ts` 的 `#select` 先把置顶条目的字数全部预留，再把剩下的字数按原来的顺序分给非置顶条目。`compose()` 返回用量 `usage {limit, used, pinned, queued}`。
- `context-formation-service.ts` 在 `queued` 非空、或 `pinned > limit` 时，调用新的存储操作 `appendIfChanged`。原因码是 `profile_budget_exceeded`（被挤掉）或 `profile_pinned_over_budget`（置顶超出上限）。
- `sqlite-decision-ledger-operations.ts` 的 `appendIfChanged` 在一个事务里，取同一主人、同一类型、原因码在给定集合内的最新一条记录。原因码相同且编号集合也相同时，就不写。
- 去重以数据库为准，所以服务重启后不会重复记录。已知的取舍：两次之间隔了没超字数的轮次后，同一组条目再被挤掉，不会重新记一条。这个取舍写在 ADR 0214 的“放弃的做法”里。
- 记忆页 `memory-page.tsx` 在 `pinned > limit` 时显示提示；网关契约的 `profileUsage` 加了 `pinned`。

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1. 【高】两个相同的提交并发进来时，第二个会在写载荷时抛 PORT_DUPLICATE，而不是返回已有条目。production-think-inbox.ts 原 submit 先 get 后 put，两步间有 await；sqlite-durable-operations.ts:1827 putPayload 对已有 ref 抛 PORT_DUPLICATE。已改：put 失败后再查一次，载荷已存在就当作别人写的继续入队；新增并发测试；触发：两个相同来源版本的 submit 同时进入，都读到载荷不存在；后果：后到的 put 抛 PORT_DUPLICATE，调用方拿到异常而不是已有条目
- 2（deepseek-v4.1-flash）成立，会出错，中高：### 2. 【高】失败分支删除的是“这次开始时还没有的载荷”，不是“这次新建的载荷”，可能删掉另一个成功提交刚建立引用的摘要。原代码用开始时的 !known 决定删除，不看现在有没有条目引用（production-think-inbox.ts 失败分支）。已改：新增 summaryReferenced，只在本次新写且没有条目引用时删；检查和删除之间仍有极窄间隙，需要入队拒绝与另一提交的入队交错，已在文档写明；触发：A 新写载荷后入队被拒，B 读到载荷已存在并随后入队成功，A 再删载荷；后果：FK ON DELETE SET NULL 把 B 已接受条目的摘要指针置空，摘要丢失
- 3（deepseek-v4.1-flash）成立，会出错，中高：### 3. 【中】条目结束后摘要被清掉，再提交同一来源版本会重新写一份没有任何行引用的载荷。原代码 duplicate 分支直接返回不删。已改：本次新写的载荷在 duplicate 时同样走 summaryReferenced 后删除；新增测试断言重提后载荷数为 0；触发：条目结束并被 maintain 清掉摘要后，来源再次扫描同一版本；后果：重新写入一份没有任何行引用的加密载荷，settledSummaries 找不到它，永久残留，每次重扫都新增

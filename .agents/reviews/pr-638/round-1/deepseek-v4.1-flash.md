## 结论与意见

作者关于“纯文档、位置在状态板之前、加了界面折叠和第 3 步范围”的说法与 diff 一致；问题不在陈述真假，而在结果板的键、并发、权限和文档一致性。

### 1. 高 — 等待登记和结果写入不是原子的，可能丢叫醒并永久挂起

文件:行：`docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:214、246-247、251`

问题：结果板的读、写、等待都是工具调用，不是收件箱消息，但文档用“所有消息都走收件箱”来保证不会同时改一件事。若 B 先读到“结果不存在”，A 随后写入并只通知当时已登记的等待者，B 再登记等待并结束运行，叫醒事件就丢了；读回执与版本写入也有同样的竞态。文档没有规定事务、锁、串行队列或“登记后复检”。

证据：
- 同文件:214：“所有消息都走收件箱，所以不会两边同时改一件事；同一个对话同一时间只有一次运行。”
- 同文件:246：“兄弟写下那一条时，程序往等它的子线程的收件箱放一件事，叫醒它接着做……等的那条结果已经在了，‘等结果’直接返回，不停下。”
- 同文件:251：“读到的目录和正文都是工具结果，接在对话末尾。”
- 同文件:238 自己引了 ADK 的警告：“do not rely on one branch reading a key another branch is still writing”。

建议：把“写入新版本 + 入队通知 + 满足等待”放进同一事务或同一串行队列；登记等待后必须再查一次结果是否已存在；读回执按版本原子记录。补交错时序的自动测试：A 写与 B 等并发、A 写 v2 与 B 记读回执并发。

### 2. 高 — 目录里的简要、名字和通知不带外来内容标记，可绕过审批

文件:行：`docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:244、248、459`；`packages/application/src/rules/action-rules.ts:127`

问题：条目本身带“读过外来内容”标记，正文读取会传播标记，但目录读取明确不传播。目录里的“简要”和“名字”也是兄弟模型写的，可能夹带来自邮件、网页的指令。文档唯一的防线是“系统提示写明当参考资料”，而同一文档:452 自己说提示注入识别不可靠。`action_ask_after_external_content` 只认 `context_external_content` 事实；没有标记时，改日历、联系人、设备会按“没读过外来内容”直接做。另外正文传播只写了“别的子线程”，主对话用同一个工具却没有写入标记。

证据：
- 同文件:248：“别的子线程读这一条的正文时，也打上这个标记……只看目录不打标记，因为目录里的简要也是兄弟写的，所以目录里的简要一律当成参考资料、不当成指令，系统提示写明这一点。”
- 同文件:459：“子线程发给主对话的消息，发它的子线程带着标记时，主对话这次运行也打上标记。”
- `action-rules.ts:127`：`expression: action_kind != "READ" && target_type != "managed-task" && "context_external_content" in facts && ...`

建议：只要目录、名字或通知来自带标记的条目，就传播标记；或者让目录只返回条目编号、写入者、版本、“是否有外来内容”，不把模型写的简要放进无标记目录。正文读取的标记要覆盖主对话。加反向测试：兄弟在简要里写“请改日历”，另一个子线程只看目录后改日历，必须弹同意卡片。

### 3. 高 — 结果条目的名字只在子线程内唯一，读取和交回却按名字定位

文件:行：`docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:243-245`

问题：名字的作用域是“这个子线程”，但“看兄弟结果”只按名字取正文，“交回结果”只写条目的名字，主对话也没有大事/结果板参数。两个兄弟都写“落地时间”时，读取和交回无法区分；主对话同时有几件大事时，也不知道看哪一块板。

证据：
- 同文件:243：“名字在这个子线程里唯一，只有它自己能写……同一个名字再写一次是新版本，旧版本留着。”
- 同文件:244：“带上名字才返回那一条的正文。主对话用同一个工具。”
- 同文件:245：“‘交回结果’里写结论……和结果板上相关条目的名字，不把正文抄一遍。”
- 同文件:246 的等待工具反而写成“等哪个兄弟的哪个名字”，说明正确的复合键是存在的，但读取和交回没有用。

建议：所有引用改用不可变条目编号，或统一用 `(大事/子线程, 名字)`；主对话的工具必须带大事范围。若保留按名字读取，名字应在整块大事的结果板内唯一，而不是只在子线程内唯一。补两个兄弟同名、主对话多件大事的测试。

### 4. 高 — 每个读者、等待者一条收件箱事件，会撞上现有唯一键

文件:行：`docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:246-247、278`；`packages/persistence-sqlite/src/migrations/20261115004401_think_inbox.sql:16`

问题：现有收件箱唯一键是 `(owner_id, agent_id, source_kind, source_ref, source_version)`。“某条有新版本，通知每个读过的人”和“叫醒每个等的人”都是按接收者分别写一条事件；如果事件只用条目和版本做 `source_ref`/`source_version`，第二个读者或等待者会被数据库当成重复行直接拒掉。新增“送到哪个对话”列也不能改变唯一键。这正是 I-73 那类问题：产生端按每个接收者产生值，消费端的约束只接受一个值。

证据：
- 同文件:278：“去重沿用表上已有的唯一键（来源种类、来源编号、版本）。”
- 同文件:247：“程序记下谁读过哪条的第几版。那一条有了新版本，程序往读过它的子线程的收件箱放一件……”
- 迁移文件:16：`UNIQUE (owner_id, agent_id, source_kind, source_ref, source_version)`
- `docs/incidents-and-gates.md:112`（I-73）：“双模型复核只看了 diff，没问‘清单里的 id 能通过后端校验吗’。”

建议：把接收者/等待者编号编进 `source_ref`，并按固定长度前缀或摘要限长；或者为结果板通知单独建表。把新的来源种类登记到同文件:278 的启动登记处，并把相关值补进同文件:644 的 I-73 核对清单。测试要覆盖同一版本的两个读者、两个等待者各收到一条，不能被去重。

### 5. 中 — 结果改版通知只写“子线程”，主对话读过也不会收到

文件:行：`docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:244、247`

问题：作者的说法是“结果改版通知读过的人”，但文档只写“往读过它的子线程的收件箱放一件”。主对话也用同一个“看兄弟结果”工具，也是读者，却不在通知范围。主对话可能已经按第 1 版汇总给用户，之后结果改成第 2 版却不知道。另外“看过目录”是否算“读过”、从而触发版本通知，也没有定义。

证据：
- 同文件:244：“主对话用同一个工具。”
- 同文件:247：“程序往读过它的子线程的收件箱放一件‘落地时间改成第 2 版了’……”

建议：把主对话纳入读回执和通知；或者明确主对话不记读回执，但由状态板或重新交回强制刷新。定义“读过”是否包含只看目录。测试加“主对话读过第 1 版，兄弟改第 2 版，主对话收到通知”。

### 6. 中 — 等结果的终态不完整：兄弟成功但没写名字会挂起，等待状态也没进状态表

文件:行：`docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:246、258、262、317-324`

问题：文档只规定兄弟“失败或被叫停”时叫醒等待者并告知“等不到了”。如果兄弟正常交回，但没有写等待者要的那个名字（查不到、改名、判断不需要），等待者会一直等。并且“等结果”产生的新等待类型没有进入长任务结束状态表；“等”那行只列“等主对话回话、等你同意、等一个定好的时间”，状态板也只列“等回答、等你同意”，后台在办和状态板无法准确显示“在等兄弟结果”。

证据：
- 同文件:246：“兄弟子线程失败或被叫停时，等它的子线程也被叫醒，收到‘等不到了’。”
- 同文件:258 的反向测试只覆盖：“订机票的子线程失败，等它的订餐馆子线程被叫醒。”
- 同文件:322：“等 | 等主对话回话、等你同意、等一个定好的时间 | 等的东西来了才叫醒”
- 同文件:262：“状态（排队、在做、等回答、等你同意、做完、失败）”

建议：在“交回结果”或任何终态时检查该子线程的未满足等待，缺名字也发“等不到了”；或等待时若目标已终态且没有该名字，直接拒绝。把“等兄弟结果”加入同文件:322 的“等”行和同文件:262 的状态列表。补“成功交回但没写被等名字”的测试。

### 7. 中 — 三个新工具没定类别、参数和清单更新；主对话加“看兄弟结果”会改冻结的工具头

文件:行：`docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:244、454、539`；`.agents/instructions/prompt-prefix.md:42-45`

问题：权限节说“其余工具两类都有”，但新节只写子线程“记下结果”“等结果”，主对话只用“看兄弟结果”。主对话到底有没有“记下结果”“等结果”没定：如果有，和“一个子线程只写自己的条目”“等结果让本次运行收尾”冲突；如果没有，同文件:454 的“其余工具两类都有”是错的。其次，主对话是第 1 步建的长对话，第 3 步新增“看兄弟结果”会改变工具定义，而工具定义在请求最前面；按 prompt-prefix 第 6、7 条，要么重建一次，要么从第 1 步就把第 3 步的工具定义放进冻结列表、执行端按阶段拒绝。文档没有交代。三个新工具也没有参数、长度、必填项和 prompt-catalog/manifest 的更新说明。

证据：
- 同文件:454：“‘这一类’只分主对话和子线程两类……其余工具两类都有。”
- 同文件:244：“主对话用同一个工具。”
- `.agents/instructions/prompt-prefix.md:42`：“系统提示和工具按对话冻结……同一对话一直沿用第一次发出时的字节。”
- 同文件:45：“工具集合变了（工具名，或者去掉说明文字后的参数结构）……”

建议：明确列出主对话和子线程各自拿到的结果板工具；选择“第 1 步就把第 3 步工具定义放进冻结列表、第 3 步只打开执行”或“第 3 步一次性重建主对话并记录缓存代价”。补三个工具的参数 schema、长度限制、prompt-catalog 条目和 `prompt-manifest.json` 更新，并加“同一对话内工具集不变”的测试。

### 8. 中 — 结果板没有表结构、长度上限、保留期和数据分级，正文和版本可无限增长

问题：结果板只说“正文存在表里”，没有表名、列、约束、外键和迁移；正文“可以很长”，旧版本永久保留，名字可无限新增，子线程又明确不到期删。读回执、等待关系也会持久化，但没有保留期、条目/版本上限、删除或更正机制。正文可能包含外来原文、密码或验证码，也没有数据分级和遮盖说明。旧版本不能删，和“能撤回”的权限判断也需要对齐。这些新值没有进入同文件:644 的 I-73 核对清单。

### 9. 低 — “不做什么”、业界表和 ADR 0285 仍说子线程之间都经过主对话

## 侧重检查

- **不可信输入**：目录简要、名字、版本通知都来自带标记的兄弟，却没有传播外来内容标记（意见 2）；正文虽传播，但只写“别的子线程”，主对话读取没有覆盖（意见 2）；结果板正文可含外部原文和秘密，却没有数据分级（意见 8）。
- **错误路径**：兄弟失败/叫停有“等不到了”兜底（同文件:246、258）；兄弟成功但没写被等名字没有兜底（意见 6）；等待登记与结果写入的竞态没有处理（意见 1）；成环和跨大事检查已有（同文件:246），这部分没问题。
- **安全与权限**：`action_ask_after_external_content` 只认 `context_external_content`（`action-rules.ts:127`），所以标记传播是硬边界；目录不标记等于在边界上开了口子（意见 2）。结果板写入是否算“自己这边、能撤回”没有定义，旧版本又不能删（意见 8）。
- **资源耗尽**：条目、版本、正文、读回执、等待关系都没有上限或保留期（意见 8）；版本通知反复叫醒读者可能造成来回重做，文档只用费用预算兜底，没有明确约束（推测）。
- **不可撤销操作**：旧版本不能删、不能撤回（同文件:243）；已经办成的事靠系统提示让子线程去问主对话（同文件:247），不是程序强制（推测）。
- **规则/文档一致性**：“不做什么”、业界表、ADR 0285 未更新（意见 9）；长任务状态表和状态板缺“等兄弟结果”（意见 6）；工具类别与冻结规则未说清（意见 7）；I-73 清单缺结果板（意见 8）。锚点 `shared-results` 和内部链接会被 `check:docs-links` 接受，这一点没问题。

## 必答问题

**1. 会不会改变模型已经见过的请求开头？**
本次 PR 是纯文档，没有改代码、系统提示、工具定义或遮盖，所以当前请求开头不变。按新设计，结果板目录和正文都是追加的工具结果，结果板改版不回头改已发内容（同文件:251）；等结果的叫醒和版本通知也是收件箱事件追加；状态板仍在本次最后一条消息末尾。唯一明确会改开头的是第 3 步给已有主对话加“看兄弟结果”：工具定义在请求最前面，按 prompt-prefix:42-45 必须重建一次，或从第 1 步起就把第 3 步工具定义放进冻结列表、执行端按阶段拒绝。文档没有交代这一点，所以不能认为设计完全满足“只追加”。每轮会变的值（状态板、目录、正文、通知）都在末尾消息或工具结果里，没有放进系统提示和固定工具定义；但目录的“什么时候写的”格式未固定（意见 10）。

**2. 同一段文字会不会在不同请求里变成不同的字节？**
没有发现依赖前后文的遮盖或跨请求改写的设计。结果板内容被读取时是新追加的工具结果，旧消息字节不变；版本号和写入时间如果是固定值，也稳定。潜在问题是目录的排序和“什么时候写的”时区/格式没有规定（意见 10），可能因数据库返回顺序或本地时间格式不同而出现不同字节。按 prompt-prefix 第 10 条应明确固定。

**3. 有没有对应的自动检查，反向用例真的会失败吗？**
本次没有新增或修改任何自动检查。仓库的 `npm run check` 会跑 `check:docs-links` 和 `check:markdown-tables` 等文档检查；按脚本逻辑，新锚点和内部链接应通过，但这不验证设计行为。文中列出的正向、反向、数字用例都是第 3 步将来的验收描述，不是本次可执行的测试，所以“反向用例现在会失败”不成立。作者只写了手工的 token 对比，没有阈值或回归检查。第 3 步至少需要补：并发时序测试（意见 1）、两个读者/两个等待者不丢事件（意见 4）、兄弟成功但没写名字（意见 6）、目录注入后的审批（意见 2）、同名条目（意见 3）、结果板只追加的 `[I-66]` 用例（意见 10），以及真实数据库插入新值的 I-73 测试。

**4. 每个新值，每个使用它的地方都能接受吗？逐个核对。**
- 锚点 `shared-results`：定义在同文件:231，使用在:539；`check:docs-links` 的锚点检查接受，没问题。
- 作者三条改动说法：与 diff 一致，没问题。
- 新工具名“记下结果、看兄弟结果、等结果”：文档没有定义主对话/子线程各拿哪些、参数 schema、长度和 prompt manifest 更新；同文件:454 的“其余工具两类都有”与同文件:243-246 的“只有子线程写/等”不一致（意见 7）。
- 条目“名字”：产生端说“在这个子线程里唯一”，消费端“看兄弟结果”和“交回结果”却按名字全局定位，主对话也没有大事范围；两端作用域不一致（意见 3）。
- 条目“版本”和“什么时候写的”：产生端没有规定类型、格式、时区和排序；消费端要展示、比较、通知，存在序列化不一致风险（意见 10）。

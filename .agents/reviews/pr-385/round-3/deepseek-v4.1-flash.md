## 结论

作者列出的五条改动在文件里基本都能找到对应文字，但“上面的改动没有引入新的矛盾”不成立。最严重的是三处：nonce 保留时间前后矛盾会留下重放窗口；分批抽取不携带 `known` 会让前一批点名的密码在后一批漏遮；吊销时删设备索引行会让“已吊销回答/本地自清/状态检查”落空。其余是共享层设备索引的重建与删除、硬上限测试文件冲突、track 上传凭据绑定不到记录编号等跨端问题。

以下按严重度排列。凡标“读文档证实/读代码证实”的都是我亲自读到的原文；标“推测”的是设计没写死、需要实施时确认的路径。

## 问题

### 高 1：nonce 保留时间两处直接矛盾，按新表实现会留下重放窗口

- **文件:行**：`docs/execution/specs/2026-11-11-apple-device-body-design.md:585` 与 `:178`
- **问题**：新硬上限表说“过了签名的容许时间差就删”，但验签段说“随机值保留两倍容许时间”。签名允许创建时间与服务器时间相差 ±60 秒。若只保留 60 秒，攻击者可以用“未来时间”的签名在 60 到 120 秒之间重放：第一次请求时 nonce 还在，第二个窗口里 nonce 已被删，签名仍可能被接受。
- **证据**：
  - `:178`：“随机值出现过的（随机值保留两倍容许时间）”
  - `:585`：“`device.nonce.retained` | 每台设备保留的防重放随机值（过了签名的容许时间差就删）”
- **建议**：把 `:585` 改成“保留两倍容许时间差后删”，并在 `device-api.test.ts` 加反向用例：`created` 在未来的签名第一次通过，超过一个容许时间但不到两个容许时间时重放必须被拒。
- **标签**：读文档证实（同一文件两处直接矛盾）；重放窗口是安全后果。

### 高 2：分批抽取不携带 `known`，点名密码在后一批会漏遮

- **文件:行**：设计 `:655`；ADR 0230 `:122`；代码 `packages/sensitive-capture/src/redaction.ts:317-327`、`:411-425`；`packages/application/src/services/model-egress.ts:220-224`
- **问题**：设计先说“一条记录里点了名的密码，在同批后面的记录里单独出现时也会被遮（为了不漏）”，随后又说按 `perception.extract.max_chars` 分成几次抽取时，“每一次请求各是一个遮盖单位，‘已经点名的值’不带到下一次请求”。如果密码在第 1 批被点名、同一个值在第 2 批单独出现（或一条长记录被切开跨批），第 2 批不会遮，直接泄露。
- **证据**：
  - 设计 `:655`：“……为了不漏……每一次请求各是一个遮盖单位，‘已经点名的值’不带到下一次请求。”
  - 代码 `:317-327`：
    ```ts
    const placeholder = tag === undefined ? `[${label}]` : `[${label}#${tag(kind, identity)}]`;
    if (tag !== undefined) {
      if (table !== undefined && !table.has(placeholder)) table.set(placeholder, original);
      if (
        rememberValue &&
        known !== undefined &&
        original.length >= KNOWN_VALUE_MINIMUM_LENGTH &&
        !known.has(original)
      )
        known.set(original, placeholder);
    }
    ```
    这表示：只传 `known`、不传 `tag` 时，`known` 根本不会写入，跨记录遮盖等于没做。对话出口正是同时传了 `tag`、`known`、`table`（`model-egress.ts:220-224`）。
  - 代码 `:411-425`：只有 `known` 里已有的值才会被额外遮。
- **建议**：把上一批的 `known` 作为下一批的种子（只向前依赖，仍然确定），或者保证不在请求之间切开一条记录/一段经历并携带 `known`。实现时必须同时传 `tag`（和需要的 `table`）。加测试：第 1 批点名密码、第 2 批单独出现，必须遮；再测“只传 `known` 不传 `tag`”的反例。
- **标签**：读文档证实（设计规定直接推出）；读代码证实（`known` 需要 `tag` 才生效）。具体跨批是否会出现同一值是推测，但设计明确允许这条路径。

### 高 3：设备索引在吊销时删行，和“已吊销回答 / 本地自清 / 状态检查”矛盾

- **文件:行**：设计 `:165` 与 `:184`、`:734`、`:755`
- **问题**：新规则说“设备吊销时删它的行”。设备索引是服务器在打开任何个人库之前找到“这是谁”的唯一入口。删行后，服务器无法打开该人的库去读 `devices.status = revoked`，也无法返回“已吊销”的回答；丢失设备可能保留本地缓存（对话、记忆副本），与“设备一联网就自清”矛盾。
- **证据**：
  - `:165`：“设备吊销时删它的行”
  - `:184`：“设备下次联网收到‘已吊销’的回答时也会清掉本地缓存和还没执行的动作。”
  - `:734`：“设备状态 `pending`、`active`、`revoked`……只有 `active` 能通过验签”
  - `:755`：“设备被吊销 | 连接掐断，请求一律拒绝 | App 显示‘这台设备已被移除’，要重新配对”
- **建议**：吊销时保留一行墓碑（设备编号 → 人，状态 `revoked`），直到设备确认清空或保留期结束；或者明确“未知设备编号也返回同样的已吊销回答”。加反向用例：吊销后设备带合法签名请求，必须收到“已吊销”而不是普通未知设备错误。
- **标签**：读文档证实（同一设计多处矛盾）；安全/隐私后果是读文档推断。

### 中 4：设备索引从 `devices` 表重建不完整

- **文件:行**：设计 `:165`、`:169`、`:196`、`:199`
- **问题**：索引有两种行：设备编号 → 人、配对码哈希 → 人。设计说可以从各人库的 `devices` 表重建。但配对码哈希存在 `device_pairing_codes`，不在 `devices`；配对码在设备行创建之前就生成。索引丢失后，正在进行的配对无法重建。另外，`devices` 表仍保留 `revoked` 设备，按它重建会把吊销时删掉的行又恢复回来，除非明确过滤。
- **证据**：
  - `:165`：“设备索引……可以从各人库里的 `devices` 表重建。”
  - `:169`：配对码先生成，库里只存哈希。
  - `:196`：`devices` 的字段是编号、种类、名字、公钥、状态、发布渠道等，没有配对码哈希。
  - `:199`：`device_pairing_codes` 才有“配对码哈希、过期时间、使用时间、发起的会话”。
- **建议**：明确重建要同时扫描 `devices` 和 `device_pairing_codes`，并说明是否过滤 `revoked`；或声明未完成配对的配对码允许丢失、必须重新生成。加测试。
- **标签**：读文档证实（表字段直接对比）。

### 中 5：新增共享层设备索引没有进入 ADR 0234 的“彻底删除一个人”清单

- **文件:行**：`docs/adr/0234-one-program-per-person-database-file.md:82`；设计 `:165`
- **问题**：ADR 0234 的删除流程列了名册、Gmail 授权、目录、执行账号、Access 名单，但没有删共享层设备索引行。删人后，设备编号 → 人的映射仍留在共享层，既不是“彻底删除”，也可能让被删人的设备请求继续找到（不存在的）库。
- **证据**：
  - ADR 0234 `:82`：“彻底删除一个人，按顺序、每步可重试：名册停用并断开连接和后台任务；撤销 Gmail 授权；删目录和执行账号；删名册和 Access 名单里的邮箱；逐项核对并出回执……”
  - 设计 `:165`：“共用层加一张‘设备索引’表”
- **建议**：在 ADR 0234 决定 10 和设计的删除/保留一节加“删除该人的设备索引行”，并加测试：删人后共享层没有指向他的设备索引行。
- **标签**：读文档证实（跨文档 I-73 类）。

### 中 6：硬上限的测试文件两处写法不一致

- **文件:行**：设计 `:706` 与 `:800`
- **问题**：新值清单说九个硬上限键的自动检查在 `device-api.test.ts` 和 `perception-extraction.test.ts`；验收表说在 `device-limits.test.ts`。当前仓库中这三个文件都不存在（未实现），但实施时会不知道把反向用例放哪，容易漏测。验收表的硬上限清单也没有点名新增的 `device.track.batch_points` 和 `device.nonce.retained`。

- **标签**：读文档证实（两处矛盾）；测试文件不存在是读仓库/glob 证实。

### 中 7：`track` 批次用上传凭据，但凭据绑定“记录编号范围”，轨迹点表没有编号

- **文件:行**：设计 `:180`、`:233`、`:337`
- **问题**：上传凭据绑定“文件里的记录编号范围”；`track` 也接受文件上传、用上传凭据；但 `location_track_points` 只有时间、经纬度、精度、速度，没有记录编号。实现时无法按文字绑定。

### 低 8：发布渠道“只用于显示”与编译开关的用途不一致

### 低 9（推测）：镜像条目排序键缺设备，“编号都是唯一的”可能不成立

  - `:393`：“镜像条目按‘种类、再按条目编号’；……编号都是唯一的，所以不会有并列”
- **建议**：把设备加入排序键（种类、设备、条目编号），或定义全局唯一镜像编号；测试用两台设备同种类同本地编号。
- **标签**：推测（设计没有说明集合是否跨设备）；代码未实现，不能证实。

### 低 10（推测）：解压临时文件在进程崩溃时可能残留

- **问题**：新说明“先解到临时位置，作废时整份删掉，不留半个文件”只覆盖正常错误路径；若进程在解压/写临时文件时崩溃，临时文件可能残留，反复崩溃会耗尽磁盘。

## 必答问题

### 1. 这个改动会不会改变模型已经见过的请求开头？

**这个 PR 本身不会**：我看到的 diff 只有文档、指令文件和复核记录，没有代码；运行时不会改变任何已发请求。

**按设计实施时会一次性改变工具定义**：新增 `device_action`、`perception_read` 会改变工具集合，按 `.claude/rules/prompt-prefix.md` 第 6 条和第 4 条例外，老对话在下一轮重建一次请求开头；ADR 0229 `:117` 和设计 `:657` 已写明，并要求全部新提示词文字和两个工具同一版本上线。代码 `thread-prompt-bundle-service.ts:89` 的 `tool_set_changed` 证实工具名变化会触发重建。

除这一次工具集合变化外，设计把感知内容限制为“本轮末尾追加的工具结果”（`:653`），`perception_read` 结果追加在末尾，后台抽取的当前时间/日历表放在最后（`:645`、`:393`）。因此没有把每轮变化的值放进系统提示或工具定义。

**需要盯住的风险**：规则第 6 条还写着“改了提示词文字，只对新对话生效；要让老对话也用上，必须手动换新”。设计靠“工具集合变化”顺带让老对话拿到新提示词；如果实施时把工具和提示词分开发版，老对话不会自动拿到新提示词，会变成多次重建。这一点必须作为硬门槛检查。

### 2. 这个改动会不会让同一段文字在不同请求里变成不同的字节？

**排序键方向正确**：记录按发生时间毫秒 + 编号、日历事件按开始时间毫秒 + 事件编号、镜像按种类 + 条目编号、建议按编号；失败重试时日历表和当前时间排最后。这些能保证同一份输入的大部分前缀稳定。

**但有三条会让字节/遮法不一致的实际路径**：
1. **`known` 需要 `tag` 才生效**：`redaction.ts:317-327` 明确只有 `tag !== undefined` 才把点名值写进 `known`。设计只写了“共用 `known`”，没有写 `tag`；实施若只传 `known`，跨记录遮盖不会发生。对话出口在 `model-egress.ts:220-224` 同时传了 `tag`、`known`、`table`。另外，`tag` 若是按序号生成而不是按值稳定，同一段文字的占位符会随请求变化；对话出口用的是按值稳定的 `placeholderTag`。
2. **分批抽取不携带 `known`**（高 2）：同一个值在第 1 批被点名、第 2 批单独出现时，遮法不同且漏遮。这是设计明确接受的，但从安全角度不应接受。
3. **镜像排序键可能并列**（低 9，推测）：若集合跨设备，种类 + 设备内编号不保证唯一；日历事件若在发送时才按时区格式化，也可能变。设计应写明“入库时统一毫秒整数”，并把设备加进镜像排序键。

### 3. 改动有没有对应的自动检查，反向用例是否真的会失败？

**这个 PR 没有新增可运行的自动检查**：只有文档/指令改动。仓库现有的文档门槛（`check:docs-links`、`check:instruction-links`、`check:markdown-tables`、`check:adr-numbers` 等）会检查链接、表格和 ADR 编号；我核对了新增的 `#to-memory`、`#limits`、`#unverified` 等锚点都存在，但**没有运行这些脚本**（本次只能用 read/grep/glob 和 git 命令），所以不能声称通过。

**设计里的测试是未来计划，不是本 PR 的检查**：`test/integration/device-api.test.ts`、`device-limits.test.ts`、`perception-extraction.test.ts` 在当前仓库都不存在（glob 未找到），所以现在没有任何反向用例会因为缺守卫而失败。

**已发现的覆盖缺口**：
- 硬上限测试文件两处写法不一致（中 6），实施时容易漏测新增的 `device.track.batch_points`、`device.nonce.retained`。
- 跨批点名密码漏遮（高 2）没有对应测试；验收表只测“打乱到达顺序/换时区后字节相同”，不测“第 1 批点名、第 2 批单独出现必须遮”。
- `known` 必须同时传 `tag` 的契约没有测试；建议直接在 `packages/sensitive-capture` 或新的抽取测试里加反例。
- `check:prompt-prefix` 的 `REQUIRED` 只核对 `[I-66]` 用例数量（`scripts/check-prompt-prefix.mjs`），不覆盖设备/感知的新测试；设计里说要加 `REQUIRED`，这是对的，但只适用于 prompt-prefix 的用例。

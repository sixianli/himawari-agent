# PR 311 第 4 轮意见分类（复核线程，逐条核对源码）

基准 5530765e，head 017b1c37，上一轮 5d56e63a，DeepSeek，经 Magpie，本轮 0.0847，累计 0.4712 美元。Andy 已同意这一轮（原话经协调者转："同意跑完之后直接合并"）。

模型给的 1、2 标"中"，我核对后降为"会出错·低"，理由如下，请协调者和作者复看。

1. 点击重读时读取失败、返回非快照、新快照里没有这条记忆，缺针对性反馈：成立（memory.ts:131-141、memory-page.tsx:524-529）。降为低：读取失败时顶部已显示"当前不可用"（不是完全静默）；非快照返回在真实网关里不会出现；新快照里没有该记忆，说明这条记忆已不在可见集合里，抽屉关闭是合理的。建议小改：fresh 为 null 时不要完全无动作，让详情留着并显示"来源已不可查"，补一条"查询失败不跳转且有可见反馈"的用例。
2. 重复点击、乱序响应可能让旧概览覆盖新概览：成立但影响小。两个快照都来自同一个库、相隔几秒，后返回者覆盖前者最多让界面短暂落后到下一次刷新；没有写操作。降为低，可给 checkSource 加"请求进行中禁用"。
3. "512 合成一个共享常量"只对网关侧成立，脚本仍有独立的 SOURCE_REF_MAX_LENGTH，ADR 写"同名常量"不准：成立，低，改 ADR 措辞为"脚本保留独立常量，由测试锁定数值相等"。
4. SQL length()（字符）与 JS .length（UTF-16 单元）口径不同：成立，只对非 BMP 字符且接近 512 才有影响，现实中引用是 ASCII。低，可只在 ADR 已知局限写一句。
5. takeMessageFocus 先清请求再找 DOM，详情已就绪但目标消息还没渲染时会丢：推测，场景窄（详情在 ChatHistory 挂载前已拉完全部分页）。低。
6. ADR 决策 1 仍硬写"512"：低，改措辞。

可以更好、不强求：每次点击发一次全量概览读取；点击路径会顺带触发既有的回收站过期清理（不是本次新增）。

核对项：浏览器夹具 NODE_ENV=production 只作用于 spawn 的构建子进程，不影响其他测试；MEMORY_SOURCE_REF_MAX_LENGTH 网关侧只剩一处；新增反向用例静态上都会失败。

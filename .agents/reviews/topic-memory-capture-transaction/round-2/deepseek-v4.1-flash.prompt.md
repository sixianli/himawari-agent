# 每轮记忆抽取做成一个事务：整合方案

## 前提（均已对照代码，行号以 main b66ed748 为准）

## 对标
- ChatGPT/Claude 没有公开记忆写库细节，无可对标；业界通用做法是「工作单元 + 单事务 + 确定性键重试」（Prisma 交互式事务、Fowler Unit of Work、Stripe 幂等键）。
- 根因：不是某个写错了，而是「一轮」没有事务边界，靠重试去补残留；做梦记忆 PR 395 的「重试时补做取代」就是这种补丁。

## 两个模型的意见和我的判断
两个模型都独立选了同一条路 B：应用层把整轮写成一份「数据计划」，持久化层新增一个写操作，在 worker 里一次同步跑完。理由：事务不跨消息、不会占住写通道。DeepSeek 另加「本轮已提交标记表」、GLM 另点出两条真问题（载荷 get→put 有空隙；提交后才发审计）。

我自己的方案 A：在写通道上开一个「事务范围」，范围内的调用照旧走现有端口，读也改走写连接，别的写请求在主线程排队等它；失败就回滚。

| | A 事务范围（我） | B 数据计划（两个模型） |
|---|---|---|
| 改动量 | 小：执行上下文加一个范围；抽取提交包进去；现有 create/取代/确认/提醒/人物逻辑一行不重写 | 大：把 applyProposal（create/update/merge/unchanged/取代/确认/投影任务）在 worker 里再实现一遍，两处逻辑要长期保持一致 |
| 改表 | 不用 | 要一张「本轮已提交」标记表（排队改表） |
| 风险 | 范围内主线程卡住会让其他写等着；用超时（默认 5 秒）到点回滚兜底，一轮实际只有毫秒级 | 逻辑分叉 |
| 其他写入口（敏感批准提交、MCP 写入、提醒写入等）| 以后同样一行包进范围 | 每个都要重做一套计划 |

判断：采纳 A，不采纳 B 的「数据计划 + 标记表」。理由是 B 为了避开一个可控的风险（范围占用写通道），付出重写核心逻辑和改表的代价，而这条逻辑刚被做梦记忆线程改过，分叉风险最高。采纳两个模型的细节：审计回调攒到提交成功后才发；载荷 get→put 空隙并入范围后自然消失；失败后留队重试。

## 方案
1. **事务范围**（`SqliteExecutionContext`）：`transaction(fn)`：拿写通道独占（别的写请求排队），发 `BEGIN IMMEDIATE`，用 AsyncLocalStorage 标记 fn 里的调用：范围内的 `read` 改走写连接（看得到自己刚写的），范围内的 `write` 直接放行；fn 成功 `COMMIT`，抛错或超过期限 `ROLLBACK`。现有操作里的 `transaction().immediate()` 在外层事务里自动变保存点。
2. **应用端口** `UnitOfWorkPort.run(fn)`；生产里 `#commit` 把 `generations.request` + `processCommittedRun` + 出队（`backlog.remove`）包进同一个范围，`resolveSensitive`（批准后提交）同样包进去。范围内不做模型调用、网络；密文载荷在范围内的 `payloads.put` 前由 protector 生成（毫秒级）。
3. **审计**：`onAudit` 在范围内先攒起来，提交成功后一次发出；回滚则丢掉并记一条失败。
4. **失败与重试**：回滚后库里没有本轮任何东西；`#save` 失败不再 `capture_gave_up`，保留在待补队列，按现有最大次数重试，超次数才放弃。出队和写记忆在同一事务，所以「已提交又被重放」只会发生在出队之后不存在的条目上，reaffirmed 历史不会重复。
5. **根治版本空隙**：范围内读和写在同一写事务里，读到的版本在提交前不会被别人改。做梦记忆那两处补丁（重试补做取代）等它合并后评估是否可删，不在本 PR 里改它的文件。

## 测试（真实 SQLite + 真实 worker，无假替身）
- 回滚反向用例：3 个候选，第 2 个因分级不一致被现有校验拒绝 → 第 1 个的记忆、载荷、决策记录、投影任务、提醒、人物一行都没有；队列条目还在。
- 崩溃反向用例：用现有 `crashAt` 钩子在第一个候选写完后让进程退出，重开库零残留。
- 超时反向用例：范围内故意不返回，到期回滚并放开写通道，其他写请求不被卡死。
- 幂等：同一轮提交两次，行数不变；`unchanged` 不重复追加历史。
- 隔离：范围进行中，范围外的写请求排队、范围外的读看不到未提交数据。
- 审计：回滚时没有 `auto_committed` 日志。

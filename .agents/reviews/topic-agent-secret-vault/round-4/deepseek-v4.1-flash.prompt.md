# 密钥保险箱方案 v4：钥匙在 iPhone，出口统一守门

（本轮审核请特别从攻击者角度找安全漏洞：服务器被攻破、手机或 Apple ID 被盗、网页注入、批准被伪造或重放、内存和日志泄露、出口守门程序本身。也请指出方案里对苹果平台能力的说法哪些可能不成立。）

v3 之后 Andy 11-24 的三个问题带来的改动：
1. “服务器被黑会不会泄露”→ 解密钥匙改放 iPhone，服务器只存解不开的密文。
2. “对用户要没有门槛”→ 钥匙走 iCloud 钥匙串自动同步；密码从苹果“密码”一次导入或用到才选。

## 一句话
密码锁在箱子里，箱子在服务器，钥匙只在你的 iPhone。她要用时，你在锁屏点批准、刷脸，手机只把这一项的钥匙递过去，用完就收回。

## 1. 东西放在哪
| 东西 | 放在哪 | 谁能看到真内容 |
|---|---|---|
| 总钥匙（保险箱主密钥，256 位随机数） | iPhone 的 iCloud 钥匙串（同步、端到端加密，苹果也解不开） | 只有你的苹果设备，用前 App 要求 Face ID |
| 每一项的小钥匙 | 用总钥匙加密后存服务器 | 只有手机能解开 |
| 每一项的密码 | 用它的小钥匙加密后存服务器 | 没有小钥匙谁都解不开 |
| 每一项的名字、允许的网站 | 服务器存明文给模型看；同时用总钥匙算一个防篡改签名，手机核对 | 模型能看到名字和网站，看不到密码 |
| 设备签名钥匙 | iPhone 安全芯片（Secure Enclave，拿不出来） | 用来证明“这个批准确实是这台手机发的” |

## 2. 请求一个密码的流程
1. 你说“帮我登录招商银行看余额”。
2. 她列出保险箱（只拿名字和网站）。
3. 她打开 ebank.cmbchina.com 登录页（浏览器在隔离沙箱里）。
4. 她说“用招商银行网银填密码框”。
5. 服务器上的保险箱程序先检查：这一项允许这个网站吗？浏览器真实地址对吗？密码框看得见、在页面本身里（不在嵌入框和 Shadow DOM 里）？
6. 不对就拒绝；对就生成一个这次办事专用的临时公钥，推送到手机：“这次要用：招商银行网银（ebank.cmbchina.com）”，带上是哪段对话、她要做什么。
7. 你在锁屏点“批准”，系统要求 Face ID 解锁。手机自己再核一遍：这一项的允许网站（用总钥匙验签，服务器改不了）里有没有请求里的网站；不一致就拒绝并提醒你。
8. 手机用总钥匙解开这一项的小钥匙，用第 6 步的临时公钥加密后发回，并用设备签名钥匙签名（绑定这次办事、这一项、这个网站、过期时间，只能用一次）。
9. 保险箱程序验签，在内存里解开密码，交给浏览器填进密码框。填的时候她看不到页面，页面往别的网站发的请求全部拦下。
10. 提交登录。
11. 收尾：清掉内存里的密码、小钥匙和临时私钥；页面上出现密码（原样或编码过）全部遮掉；失败就清空填过的框。
12. 她只拿到“已登录成功”，告诉你结果。付款、转账、改密码、发出去这类动作，照收件箱方案定的权限规则每次单独问。

API key 和沙箱程序：程序手里只有替身值（例如 `HIMAWARI_SURROGATE_xxx`），请求出沙箱时经过出口守门程序。守门程序查去哪个网站、什么方法、是不是这一项允许的地方，再按同样的批准流程拿到真值替换进请求头或请求体；响应里出现真值就遮掉。守门程序在沙箱外，用自己的证书解开沙箱发出的 https（沙箱只信任这一张证书），这是 Muse 的 Sentinel、Claude 托管 agent、Docker 沙箱的同一做法。

## 3. 放密码进来
- 一次导入：iOS 26 苹果“密码”App 的“导出到其他 App”选 Himawari（苹果和 FIDO 的凭据交换标准，ASCredentialImportManager）。每项自带它保存过的网站，直接作为允许的网站。未核实：论坛报告第三方 App 不出现在列表里。
- 用到才问：她遇到没存过的网站，推送“需要 xx 的密码”。弹框里只列网站相符的已存项；从苹果“密码”选一个时，如果选中项保存的网站和她要去的网站不一致，大字警告“这个网站和这条密码原来的网站不一样”，要再确认一次（防钓鱼网站骗你把银行密码绑上去）。
- 手动加：API key 这类。
- 值只在手机上加密后再发给服务器，服务器从头到尾只收到密文。

## 4. 安全风险和对策
| 风险 | 会怎样 | 对策 | 剩下的风险 |
|---|---|---|---|
| 服务器被完全攻破（平时） | 只拿到密文 | 钥匙不在服务器 | 无 |
| 服务器被完全攻破（你正好批准使用时） | 能拿到你这次批准的那几项真密码 | 每次办事只解开用到的项；临时钥匙用完即删 | 这几项会泄露；这是“浏览器在服务器上替你填”必然的代价 |
| 被攻破的服务器伪造批准请求 | 推送假的“这次要用：招商银行网银” | 卡片写明哪段对话、她要做什么；手机自己核对网站；你没在让她办事时收到就别批 | 你在正常办事时被骗批了一个假请求 |
| 网页里藏指令骗她去钓鱼网站填密码 | — | 允许网站由你定，程序和手机双重核对真实地址 | 无 |
| “用到才问”时把银行密码绑到钓鱼网站 | — | 网站不一致大字警告、再确认 | 你无视警告 |
| 允许的网站自己有恶意脚本 | 能读到刚填的密码 | 登录本身固有，1Password 同样列为接受的风险 | 有 |
| 网站把密码编码后回显给她 | — | 原样和常见编码都遮；填值期间不让她看页面 | 少见的自定义编码 |
| 批准被重放 | — | 签名绑定办事编号、项、网站、过期时间，只能用一次 | 无 |
| 偷听网络 | — | 小钥匙用临时公钥加密，录下来以后也解不开 | 无 |
| 手机丢了 | — | 没有锁屏密码或 Face ID 用不了钥匙；远程抹掉 | 对方知道你的锁屏密码 |
| Apple ID 被盗 | 对方想把 iCloud 钥匙串同步到他的设备 | 苹果要求用你已有设备的锁屏密码才能加入同步 | 同时拿到 Apple ID 和你的锁屏密码，这时你的苹果“密码”也一起丢了 |
| 服务器内存里的明文 | 被抓内存快照 | 生产机无 swap；关核心转储；用可清零的 Buffer；只在一次办事内存在 | Node 和浏览器进程不能保证每一份拷贝都被清掉 |
| 出口守门程序本身 | 它能看到沙箱发出的所有 https 内容 | 放沙箱外、代码最小、单独进程和用户 | 它被攻破等于服务器被攻破 |
| 依赖库被投毒（Playwright、Stagehand） | — | 锁定版本、只在沙箱里跑、不给它们钥匙 | 有 |
| 你习惯性一直点批准 | 批准失去意义 | 一次办事只问一次，不滥问；卡片写清楚 | 有 |

## 5. 和别家比
- 1Password for Claude：钥匙在你的 Mac，每次会话批准，浏览器在你本机。比我们少一处风险（不用把密码交给服务器），但要求浏览器跑在你自己的电脑上。
- Meta Muse：真密码由 Meta 的服务存，出口 Sentinel 换真值。和我们出口那一层一样，但钥匙在 Meta 手里。
- Claude 托管 agent / Docker 沙箱：出口代理塞 key，长期放行，只管 API。

## 6. 要你点头
1. 钥匙放 iCloud 钥匙串（推荐，换手机自动带走，安全程度和你的苹果“密码”一样）；还是只放这台手机的安全芯片（更硬，但换手机要靠打印的恢复码）。
2. 每次办事批一次（推荐；和收件箱方案“碰外面账号先问、以后都行不算数”一致）。

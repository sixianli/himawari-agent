# PR 383 第 3 轮逐条判断

- **r3-1**「并发用例的断言依赖请求到达顺序，正确实现也可能假失败」：成立：outcomes 顺序是数组顺序，先处理的不一定是第一个。已改为排序后整体比较（保存时 1 个已保存 + 3 个之前已保存，拒绝时 4 个已拒绝），连跑 5 次通过；去掉排队仍失败（行数断言）。
- **r3-2**「`normalizeProposalText` 在 `try` 之外调用，异常不会走 `onFailure`/`FAILED`」：可以更好：String.prototype.normalize('NFC') 和固定正则替换对字符串输入不会抛（args.text 已先做类型检查），现在没有可达的异常；模型自己也写了「这条路径目前应该不会失效」。
- **r3-3**「“对方自称”的客户端名没有写进签名状态，重发时可以变化」：成立，低。已把客户端名放进签了名的状态，决策记录用状态里的名字；新用例 records the client name the owner saw…，改回用重发时的名字后失败。
- **r3-4**「测试覆盖缺口与文档措辞」：部分成立：ADR「先去掉」已改成「先换成空格」。其余三条（排队里 work 抛错后的清理、同值不同 ref 的写密钥、确认框和存储正文的端到端断言）是补测试建议，不改行为，列为可以更好。

推测部分（可信清单扩大、生产是否单进程）：可信清单同第 2 轮 r2-7，不成立；单进程见 ADR 0225 决定 3，跨进程重发会因签名验不过被拒，不会重复落账，模型自己也这样写。

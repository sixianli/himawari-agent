# PR 372 第 3 轮判断

本轮没有成立的中、高意见。模型标“中”的三条，核对后都是低：

- r3-1（低，成立，模型标中）：`check:egress-redaction` 管的是 Himawari 向外发出的请求，本来就不管入站请求的响应；MCP 响应的遮盖由 `test/integration/mcp-read.test.ts` 的密码用例把关，第 1 轮提交前实测去掉遮盖时 3 条用例失败。没有错误行为，只是 ADR 没说清由谁把关，已在 ADR 写明。
- r3-2（低，成立，模型标中）：一条只写了值、没有“密码”字样的记忆单独返回时不遮，这是检测规则本身的限制，Himawari 自己的模型出口同样只遮点名过的值。不是本 PR 新引入的漏洞，已在 ADR 写明这个限制。
- r3-3（低，成立，模型标中）：第 2 轮“两路都结束才报失败”缺能区分旧写法的用例。`production-memory-recall.unit.test.ts` 加用例：确认检索立即失败、待确认检索延迟结束，断言报错时待确认检索已经结束；换回旧的 `Promise.all` 写法时这条用例失败。
- r3-4（可以更好，不改）：启动失败分支的用例要搭整套服务启动夹具，收益小于代价；两处检查都只是一行条件判断。
- r3-5（低，成立）：京都提醒改到现在之后 49 小时，48 小时窗口刚好排除它，改成 72 小时窗口时用例会失败；ADR 的 72 改为 49。
- r3-6（低，成立）：ADR 写明银行卡保留尾号四位。
- r3-7（可以更好，不改）：GET、DELETE 已实测由 SDK 立即回 405，不是长连接；三个工具都是只读、很快结束，客户端断开后服务端多写一条决策记录是可接受的。
- r3-8（可以更好，不改）：ADR 第 105 行已写明没有单独的每日上限、靠每分钟 30 次限流兜底，是第 1 版变更清单里 Andy 同意过的取舍。

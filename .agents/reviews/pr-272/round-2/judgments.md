# 第 2 轮复核：线程逐条判断

复核提交 `67684cdb`，增量从 `61c9f35a` 起，只跑 DeepSeek（0.0395 美元），账本累计 0.2545 美元。

## 会出错（已改）

| 严重度 | 意见 | 改法 |
|---|---|---|
| 中 | 登记行缺 `calls` 或写成 `null` 时，`sameCounts` 抛 TypeError，而不是给出新加的报错 | 校验和比较都用同一个 `gateCalls(entry)`，缺失时按空对象处理；补用例断言给出报错而不是崩溃 |
| 低 | 改名检查在整段源码上匹配，`as` 类型断言会被误报 | 只在 `import { … }`、`export { … }` 的花括号里找 `名字 as 别名`；补用例：类型断言不报、导出改名报 |
| 低 | 读目录出错时被静默跳过，会得到假通过 | 只放过目录不存在（ENOENT），其他错误照常抛出 |
| 低 | 同一文件重复登记时，后一行静默覆盖前一行 | 重复登记直接报错；文件路径不能为空 |

反向验证：换回 `67684cdb` 的脚本，“缺调用数和重复登记”“只把导入导出里的改名当改名”两条新用例失败。

## 不改

| 严重度 | 意见 | 判断 |
|---|---|---|
| 低 | 注释和字符串里的“函数名 (”会被计数 | 和第 1 轮同样的判断：项目禁止代码注释，源代码里以字符串写这类调用的情况目前没有；真出现时检查报“数量不一致”，人看得出来，不会漏报 |
| 低 | Unicode 别名、注释隔开的改名、解构改名、`const scan = scanMachineSecrets` 仍会数漏 | 这是一道靠正则的粗检查，不追求覆盖所有写法；目前仓库里没有这些写法。要彻底防住需要语法分析，代价和这道检查的作用不相称 |

# PR 309 第 2 轮复核逐条判断

复核提交 87636974（接第 1 轮 d911557a），经 Magpie，只 DeepSeek。本轮费用 0.0758 美元，累计 0.2041。

结论：第 1 轮的 5 个中高问题修复方向正确，模型确认 D1 没送达不计、D2 按推送聚合、D3 条件写入、D4 断开清理、D5 上限都对上了读写两端。本轮新增 1 个中高（D2）、2 个低（D1 测试、D3/D5 说明），1 条可以更好。需要作者再改一次。

必答问题“会不会改变模型已见过的请求开头”：不会。改动都在模型判断之后，提示词、系统提示、工具定义、历史未动。

## 会出错，中高

- D2：聚合后优先级与 ADR 矛盾。`proactive-push-backoff.ts:66` 先判“不需要”再判“点开”，一条推送里一条被点开、一条被评“不需要”时算忽略且不清零更早的计数，而 ADR 第 3 条写“有一条被点开就算被点开……遇到一条被点开的就停”。已读代码和 ADR 核实。建议点开优先，并补混合推送的反向用例。

## 会出错，低

- D1：无 @ 地址的用例去掉修复也不会失败（新类忽略数为 0 本来就推送）。产品行为正确，缺能证明它的用例；改成直接查 `push_class` 为 NULL，或连续 3 次同一无 @ 地址后断言第 4 次仍推送。
- D3：ADR 说“确实发到设备上”，代码只证明推送服务返回 2xx。改措辞。
- D5：catalog 说 `push_class` 是“发件人域名”，实际是 `due:<域名>`。改一句话。

## 可以更好（不改，列给 Andy）

- D4：断开来源时清整张表、表无 source 列。现在只有 gmail，行为正确；接第二个来源时再加维度。

## 模型的推测项（线程未单列）

- 计数查询没有 LIMIT，历史大了会线性变慢；恢复只对后续检查生效；条件写入依赖读写同一快照。三条都是推测，无复现，不单列。

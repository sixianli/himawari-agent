证据（读代码/文档证实）

### 2. 中：新句“仍要先问 Andy 的只有合并以外的事……”用了“只有”，与仍有效的大改动、凭据、删 Mac 文件等先问规则冲突

文件:行
- `.claude/rules/owner-standing-rules.md:44`（新句）
- `.claude/rules/owner-standing-rules.md:17-18、26-29、42、45`
- `.claude/rules/owner-global-instructions.md:67`

问题
新句把“仍要先问 Andy 的事”写成一个封闭清单：上线生产、动生产数据、花钱超过先问线。但仓库里还有多条仍然有效的“先问 Andy”要求不在这个清单里。用“只有”会把它们读成已被放开。

证据（读代码/文档证实）
`owner-standing-rules.md:44`：

> 合并本身不再需要 Andy 点头；仍要先问 Andy 的只有合并以外的事：上线生产、动生产数据，以及花钱超过上面“钱和模型”一节的先问线。

同文件仍写着：
- 第 26–29 行：动到模型调用和路由、权限和授权、数据存储结构、改机制或规则，属于大改动，“他同意之后才能改代码、改文件或开 PR”。
- 第 18 行：评测用哪个 key，评测之前先问 Andy。
- 第 42 行：删除 Andy Mac 上的文件，只认他在 Mac 线程亲手打的字。
- 第 45 行：合并前的模型复核由 Andy 控制，他说跳过就跳过、说停就停。

`owner-global-instructions.md:67` 还写着：

> 破坏性操作、删除任务归属范围之外的用户数据或资源、生产环境变更，以及更改账号权限、凭据、安全设置或资金，都需要针对具体对象和影响的授权。

`model-review-card.md:57`：

> 需要 Andy 定的事：中高问题的修法会改产品行为或规则、要花别的钱……

推测
读者可能把第 44 行的“只有”当成全局结论，从而认为改规则/改权限的方案不必先问 Andy，或认为删 Mac 上的文件、评测 key、复核控制也不在必须问的范围内。这里不一定是作者本意，但文字确实制造了歧义和冲突。

建议
把“只有”收窄到合并本身，例如：“合并这一步仍要先问 Andy 的只有：Andy 点名要过目的 PR；其他需要 Andy 先同意的情形（大改动方案、凭据、删除 Mac 文件、生产配置、复核控制等）按各自规则照旧。”或者把清单改成“例如”，并明确“本节不改变其他先问要求”。

### 3. 中：权限、授权和规则类 PR 改成线程自合并后，唯一的独立关卡只剩可自证的复核记录；安全/治理上少了一道人工门

文件:行
- `.claude/rules/owner-standing-rules.md:44`
- `.agents/instructions/model-review.md:75-76`

问题
旧规则里，改模型调用的大改动、动生产或上线的 PR 仍要等 Andy 说“合并”，这实际上是复核被跳过或被线程自行判“不成立”之外的最后一道人工门。新规则把“权限和授权”“规则”也纳入线程自合并；而复核覆盖记录本身是线程可写的、脚本无法验证原话真伪，合并脚本也拦不住线程不跑它。对改授权规则或改复核/合并规则本身的 PR，等于没有任何独立关卡。

证据（读代码证实）
`owner-standing-rules.md:44` 明确包括：

> 这包括改模型调用、提示词和工具、权限和授权、数据库表、设计文档和规则的 PR……

`model-review.md:75`：

> 脚本验证不了原话是不是真是 Andy 说的：已提交的覆盖记录本身被信任，能往分支写账本的人都能写一条……

`model-review.md:76`：

> 局限：合并由线程执行，这条检查拦不住线程不跑它……

推测
一个有意的线程，或一个被篡改的分支，可以先写一条“Andy 说跳过复核”的覆盖记录，提交后通过 `--assert-reviewed`，再按新规则自合并改授权/复核规则的 PR。旧规则下，这类 PR 仍要 Andy 说“合并”，这条路径走不通。现在生产上线仍要 Andy，所以影响主要停在 `main` 和后续上线包，不是立即改生产；但作为“权限和授权”变更，缺少独立确认是实质风险。

建议
- 至少把“改复核/合并/授权规则本身”从自合并清单里排除，保留 Andy 看一次再合；或者要求这类 PR 的复核记录必须由 CI/独立通道签出，不能只靠线程提交的账本。
- 如果 Andy 明确接受这个风险，应在新规则或 ADR 里写明“复核覆盖记录可被写账本的人伪造，规则类 PR 自合并接受此风险”，不要让它只隐含在实现细节里。

### 4. 低：代码复核流程卡仍写“修法会改规则要 Andy 定”，和新规则把规则 PR 列为可自合并不一致

文件:行
- `.agents/instructions/model-review-card.md:57`

问题
复核子代理的停止条件仍写着：中高问题的修法如果会改产品行为或规则，属于“需要 Andy 定的事”。新规则却说改规则的 PR 在复核无中高、过合并条件后线程自己合并。两处对“规则改动要不要 Andy”不一致。

证据（读代码证实）
`model-review-card.md:57`：

> 需要 Andy 定的事：中高问题的修法会改产品行为或规则、要花别的钱（改表不用问，Andy 2026-11-14 已说不需要他点头）。

推测
这句话可以解释为“修法本身”而不是“合并”，所以未必与第 44 行直接矛盾；但它会让子代理在遇到改规则的修法时停下来等 Andy，和“规则 PR 可自合并”的预期不一致，也容易让线程误以为改规则仍需逐次批准。

建议
把它改成“中高问题的修法会改产品行为或规则时，先按大改动规则确认；规则 PR 的合并按授权、上线和合并规则处理”，或至少加一句指向新规则，避免读者把它当成合并条件。

## 必答问题

1. **会不会改变模型已经见过的请求开头？**
   不会改变产品发给模型的请求开头。这两份文件是开发者/线程规则，不是 Himawari 运行时组装系统提示、工具定义、历史或遮盖的代码；仓库里也没有代码在运行时读取 `owner-standing-rules.md` 或 `model-review.md` 来拼模型请求。改动只在新建会话读取规则时体现，不是往已有请求末尾追加，也不引入“每轮会变的值放在最后一条消息”的问题。Claude Code/OpenCode 自身如何加载这些规则，仓库外，**未核实**。结论：不违反“只追加”。

2. **会不会让同一段文字在不同请求里变成不同的字节？**
   不会。改动是固定文字，引用的日期和原话都是常量，不依赖时间、前后文、遮盖、对象遍历顺序或数据库顺序。没有可比对的序列化值。

3. **有没有对应的自动检查？反向用例会不会真的失败？**
   没有针对规则语义的自动检查。`check:instruction-links` 和 `check:docs-links` 只验证链接和锚点存在；本次新增/保留的链接目标都存在，所以这些检查会通过。反向用例不会失败：把“不等 Andy 说合并”改回“等 Andy 说合并”，或者保留意见 1 里仍在生效的规格第 484 行，现有检查都不会报错。这也是意见 1 能留在 `main` 上的原因。

4. **改动产生或修改的每个值，使用它的地方都能接受吗？**
   本次没有新增标识、字段、配置键、清单项或序列化格式。需要核对的“值”只有：`#authorization-deploys-and-merges` 锚点（存在于 `owner-standing-rules.md:38`）、`delivery-mode.md#fast-mode`（存在于 `delivery-mode.md:11`）、ADR 0268（存在）、`merge-queue` 标签（交付模式第 27–28 行仍在用同一机制）。两端都能接受，未发现断链或消费者校验失败。
   但语义层面有两端不一致：新规则与现行规格第 484 行、方案第 67 行、流程卡第 57 行不一致（意见 1、4）；新规则的“只有”与其他仍有效的先问规则不一致（意见 2）。另外，Andy 原话的真实性无法在仓库内校验，只能依赖现有“已提交覆盖记录被信任”的取舍。

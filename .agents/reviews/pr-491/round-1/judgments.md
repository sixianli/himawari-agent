# 第 1 轮判断

复核模型：DeepSeek v4.1 flash。十条意见全部成立，全部是“会出错”，没有“可以更好”。

## 1. 高 — 冲突检查只看 schema 结构，检测不到数据改动和 CHECK 取值被删；ADR 里点名的 `perception_records` 场景实际会通过

- 判断：成立，会出错，严重度 中、高（模型：高）
- 触发：有人写一个重建 decision_ledger 并去掉 memory_review 取值的迁移，.meta.json 里只写 alters，或迁移只改已有行数据
- 后果：冲突检查放行，合并后这个取值静默丢失，上线时用到该取值的写入失败
- 处理：已修：analyze.mjs 逐表比较行、比较建表语句里消失的带引号取值，去掉的取值要写进 removes；测试 test/tooling/migration-conflicts.test.mjs 的 reverse cases

## 2. 高 — 冲突检查只对“本分支新增”的迁移两两比顺序，不检查新增迁移与 main 已有迁移的顺序；打包重放也只跑一个顺序

- 判断：成立，会出错，严重度 中、高（模型：高）
- 触发：合并前把 main 并进分支后，晚合的小编号迁移与 main 里编号更大的迁移顺序不同
- 后果：新库按编号顺序、生产库按应用顺序，结构可能不同而检查通过
- 处理：已修：额外比较“按编号排序的全集”和“生产顺序（已有的在前、新增的在后）”两种结果；测试里用 CREATE TABLE AS 构造

## 3. 高 — 禁止语句正则漏掉合法写法 `ATTACH 'file' AS x`，影子库可逃逸访问宿主机文件

- 判断：成立，会出错，严重度 中、高（模型：高）
- 触发：迁移里写 ATTACH '路径' AS x（不带 DATABASE）或 VACUUM/**/INTO
- 后果：影子库逃出内存库，读写运行检查的机器上的文件
- 处理：已修：去掉注释后拒绝 ATTACH、VACUUM、load_extension、writable_schema；测试覆盖三种写法

## 4. 中 — 没有待跑迁移时提前返回，永远不会补 `migration_id` 列/索引，也不写 `schema_fingerprint`

- 判断：成立，会出错，严重度 低（模型：中）
- 触发：读 ADR 的人以为第一次上线就会加列和写指纹
- 后果：实际在第一个新迁移时才加；缺列时按 sequence 推编号、缺指纹时现算，功能不受影响
- 判低的理由：模型给“中”，但只是 ADR 文字与实现不符，运行结果不受影响，不会误导人做危险操作
- 处理：已修：改 ADR 第一次上线一条，写明什么时候加列和写指纹

## 5. 中 — 沙箱预留管理命令的写路径仍只比数量，没有用指纹；与“管理命令用 `bundledSchemaFingerprint()`”的说法不符

- 判断：成立，会出错，严重度 中、高（模型：中）
- 触发：同数量但集合不同的库调用沙箱预留管理的写命令
- 后果：该命令写 audit_records 等表，却通过了版本检查
- 处理：已修：写时额外核对 bundledSchemaFingerprint；现有 ADMIN-SCHEMA-RANGE 用例通过

## 6. 中 — 恢复点、权限转移、导出清单仍只比整数版本，`schema_fingerprint` 只写不读；同数量不同集合的备份仍可能被恢复/转移

- 判断：成立，会出错，严重度 中、高（模型：中）
- 触发：同数量但集合不同的备份被恢复或转移进来
- 后果：恢复先替换数据，下次启动才被 applyMigrations 拒绝
- 处理：已修：恢复点增加 expectedSchemaFingerprint（admin-cli 传 bundledSchemaFingerprint），权限转移导入在数量相等时核对指纹；恢复点加反向用例。导出清单记的是程序的编号数量，不是库的身份，不动

## 7. 低/中 — 冲突检查不 fetch `origin/main`，找不到基准时静默用 `null`；与 ADR 要求不符

- 判断：成立，会出错，严重度 低（模型：低/中）
- 触发：本地没有 origin/main 时运行冲突检查
- 后果：旧版本静默把所有新编号迁移当本分支新增，结果不可靠
- 判低的理由：只发生在没有 origin/main 的本地环境，且结果是检查结果不准，不会放行有害迁移的合并（合并前还有 CI 上的同一检查）
- 处理：已修：先 fetch，仍找不到基准就以 BASE_UNKNOWN 失败

## 8. 低 — 顺序比较的 forward 重放不在 `try` 里；大量新迁移时是 O(n²) 全量重放且没有超时

- 判断：成立，会出错，严重度 低（模型：低）
- 触发：两个迁移插入相同主键等两种顺序都失败
- 后果：脚本抛异常堆栈而不是给出问题项，仍然非零退出
- 判低的理由：退出码仍是失败，只是输出不友好；无超时的说法只在迁移数量很大时才有影响
- 处理：已修：正反两个顺序一起放进 try/catch

## 9. 低 — 文档与代码不一致：meta 的 phase/changeSet、生成器对 `origin/main` 的检查、审计脚本按版本号开关

- 判断：成立，会出错，严重度 低（模型：低）
- 触发：读 ADR 的人
- 后果：ADR 写了 meta 里的 phase/changeSet、生成器对照 origin/main、审计脚本改查表结构，实现不一致
- 判低的理由：文字与实现不符但不影响运行
- 处理：已修：生成器对照 origin/main；ADR 其余三处改成与实现一致

## 10. 低 — 打包脚本接受新的四位号迁移，而运行时冻结清单会拒绝它

- 判断：成立，会出错，严重度 低（模型：低）
- 触发：目标提交里出现 0096_x.sql 这种新的四位号文件
- 后果：打包脚本把它计入目标，运行时引擎拒绝；CI 的 check-audit-schema-range 已拦住
- 判低的理由：合并前 CI 已拦；打包是第二道，仍然补上
- 处理：已修：冲突检查在 --commit 模式下要求老清单文件数等于 LEGACY_MIGRATION_COUNT，打包前的重放会因此拒绝

## 推测部分

- 构建产物是否带上新迁移：`scripts/package-node-runtime.mjs:138` 复制整个 `src/migrations` 目录，包含新文件；引擎加载时跳过 `.meta.json`。不成立。
- 打包刷新旧审计副本：未改动，沿用现有机制。

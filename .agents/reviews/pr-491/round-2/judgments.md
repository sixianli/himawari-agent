# 第 2 轮判断

复核模型：DeepSeek v4.1 flash。七条意见都成立，都是“会出错”，没有“可以更好”。必答问题里还提到两处：`describeMigrationSet` 的 `ids` 没排序（没有任何地方序列化它，不改）和 `bundledSchemaFingerprint` 忽略不认识的文件（已修，见第 7 条）。

## 1. 高：合并后 main CI 与打包“兜底”没有执行顺序等价检查

- 判断：成立，会出错，严重度 中、高（模型：高）
- 触发：PR 检查跑过后 main 又变了，且两个迁移顺序不同结果不同
- 后果：打包前只按编号跑一遍，生产按“已有+待跑”顺序升级后结构与新库不同
- 处理：部分成立，已修：打包时用 S0 读出的已应用编号做“生产顺序对新库”的结构和数据比较（--applied，compareOrders），不过就拒绝打包；ADR 写明 main 上的常规检查只做按编号完整重放，不做从 git 历史取顺序的比较

## 2. 中高：顺序比较只比 `sqlite_master`，没有比行数据，ADR 要求的参照表数据检查未实现

- 判断：成立，会出错，严重度 中、高（模型：中高）
- 触发：两个新迁移对同一参照表写同键不同值，或一个删掉另一个插入的行
- 后果：两种顺序结构相同，检查通过，生产与新库的参照数据不同
- 处理：已修：顺序比较和整批比较带上迁移写过的表的行内容，补 integrity_check 和 foreign_key_check；加同键不同值、删除他人插入行两个反向用例

## 3. 中高：已有迁移文件被改写/改名没有任何自动检查，能通过冲突检查和打包，却会让新二进制启动失败

- 判断：成立，会出错，严重度 中、高（模型：中高）
- 触发：有人原地改了某个已有迁移文件或改名
- 后果：冲突检查和打包都通过，上线时账本摘要对不上，部署失败（失败关闭，但卡住上线）
- 处理：已修：冲突检查对 base 里每个迁移文件按内容对比，改、改名、删都失败；用临时 git 仓库做反向用例

## 4. 中：数据导出/导入仍只比整数 `migrationSequence`，ADR 承诺的 `schemaFingerprint` 没有加进清单

- 判断：成立，会出错，严重度 低（模型：中）
- 触发：读 ADR 的人以为导出清单也带指纹
- 后果：导出来源库在管理命令里已按指纹核对，在服务里已通过启动时的迁移核对，清单只记写出它的程序
- 判低的理由：模型给“中”；导出的来源库已被指纹核对过，清单里的整数描述的是写出它的程序，不是库，所以不会放过同数不同集合的数据，只是 ADR 文字与实现不符
- 处理：已修：ADR 写明导出清单不加指纹及原因

## 5. 中：新增的权限转移、沙箱预留管理指纹校验没有失败反向用例

- 判断：成立，会出错，严重度 低（模型：中）
- 触发：以后有人重构删掉权限转移或沙箱管理里的指纹判断
- 后果：没有测试失败，防线被悄悄去掉
- 判低的理由：模型给“中”；代码当前行为是对的，缺的是测试；已补并验证删掉判断后测试会失败
- 处理：已修：权限转移导入和沙箱预留写命令各加“同数不同集合必须被拒”的用例，并在去掉对应判断的旧代码上确认用例失败

## 6. 低：审计脚本不再对“未来的时间戳迁移”失败关闭，唯一防线变成 CI 的复核清单

- 判断：成立，会出错，严重度 低（模型：低）
- 触发：在生产机上直接跑审计脚本，库里有带编号的新迁移
- 后果：不再因版本太高而拒绝，仓库检查才是复核点
- 处理：已修：ADR 写明这是有意取舍及代价；加用例固定当前行为

## 7. 低：`schema_metadata.schema_fingerprint` 只写不读；禁止语句扫描可被注释字符绕过且无超时

- 判断：成立，会出错，严重度 低（模型：低）
- 触发：A：没人读的 schema_fingerprint；B：字符串里的注释符号干扰禁用词扫描、检查没有超时
- 后果：A：存下的副本会过期；B：字符串里的 /* 可能让真正的 ATTACH 被当作注释剥掉
- 处理：已修：A 不再存指纹，每次现算；B 改成认字符串的扫描，字符串里的字不算；打包脚本调检查加 5 分钟上限，ADR 写明其余靠 CI 作业超时；另让 bundledSchemaFingerprint 对不认识的文件同样报错（必答问题 4 末尾提到），加用例

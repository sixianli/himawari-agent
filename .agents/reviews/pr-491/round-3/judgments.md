# 第 3 轮判断

复核模型：DeepSeek v4.1 flash。七条意见都成立，都是“会出错”，没有“可以更好”。第 3 轮仍有中、高意见，按 Andy 的规则改完后不再自动复核，停下报告。

推测部分：生成器溢出、时间戳以 0000 开头排在旧编号前，都要 14 位全 9 或不合理的编号才触发，不处理；指纹不含 name 和 phase，引擎启动时的 validateLedger 会查，不处理。

## 1. 严重度：高（生产/新装数据可能不一致，打包硬门槛会放过）

- 判断：成立，会出错，严重度 中、高（模型：高）
- 触发：晚合的小编号迁移只删行、不插行
- 后果：顺序比较的数据部分漏检，生产与新库数据不同
- 处理：已修：写过的表也包括行变少或变化的表，行按多重集（含重复）比较；加只删行和重复行的反向用例

## 2. 严重度：中高（下一次新增迁移会直接打断现有测试，违背本 PR 目标）

- 判断：成立，会出错，严重度 中、高（模型：中高）
- 触发：下一次新增迁移文件后
- 后果：三个测试文件里写死 95 的断言失败，违背不改共用行的目标
- 处理：已修：三个测试文件改为从 LATEST_MIGRATION_SEQUENCE 推算

## 3. 严重度：中（打包是“完整重放”，不是“重跑冲突检查”，已有迁移改动也查不到）

- 判断：成立，会出错，严重度 中、高（模型：中）
- 触发：有人改了已有迁移文件或同批两个迁移冲突
- 后果：打包阶段只做重放，问题推迟到生产启动
- 处理：已修：打包把 S0 读到的已应用编号和摘要传给检查，核对已应用迁移文件没被改，并对待跑迁移做完整冲突分析；加用例。本地检查的基准仍是与 main 的合并基点，ADR 流程要求先把 main 并进分支再检查，不改

## 4. 严重度：中（冲突检查与生产的外键行为不一致）

- 判断：成立，会出错，严重度 中、高（模型：中）
- 触发：迁移在同一文件里先插子行再插父行
- 后果：影子库放行，生产库开着外键，执行时失败
- 处理：已修：影子库按生产设置开外键；加反向用例

## 5. 严重度：中低（说明文档/作者说法与最终代码不一致）

- 判断：成立，会出错，严重度 低（模型：中低）
- 触发：读 ADR 的人
- 后果：ADR 与实现不一致（指纹存不存、清单加不加字段、没有待跑迁移时是否写）
- 判低的理由：文字与实现不符但不影响运行结果
- 处理：已修：ADR 对应几处改成与实现一致

## 6. 严重度：中低（文档声称的消费者实际没改，防护只剩启动顺序）

- 判断：成立，会出错，严重度 低（模型：中低）
- 触发：读 ADR 的人
- 后果：ADR 说所有读版本的地方改用身份，实际 worker、S9、raw-copy 仍比整数
- 判低的理由：启动路径已核对集合，文字不准但不误导人做危险操作
- 处理：已修：ADR 写明哪些地方用、哪些不用及原因

## 7. 严重度：低（ADR 描述的目标产物未实现）

- 判断：成立，会出错，严重度 低（模型：低）
- 触发：读 ADR 的人
- 后果：ADR 写了 TARGET_MIGRATION_IDS 和每项带编号，实现没有
- 判低的理由：文字与实现不符，当前消费方不受影响
- 处理：已修：ADR 删掉，改写成 S0 带编号和摘要用于核对

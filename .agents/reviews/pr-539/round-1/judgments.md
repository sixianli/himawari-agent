# PR 539 第 1 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1. 中：启动时 `webPush` 早于 `http` 启动，送达时机预算必然失败，到期通知会被直接放行。service-main.ts 原 2943 行 webPush.start() 早于原 3288 行 http = await createProductionHttpComposition；已把 start 移到 http 创建之后（assertIdentityReady 之前）；触发：服务重启：webPush.start() 在 http 赋值之前，首个 tick 里 reserve 恒为 false；后果：重启时已到期的忙状态通知被判 timing_budget 直接送出，没有扣住
- 2（deepseek-v4.1-flash）成立，会出错，低：### 2. 中：每个感知窗口只取最早 500 条，超过 500 条时最新状态被丢掉，可能把“已经停下”误判成“还在开车”。production-delivery-timing.ts 的 listRecordsBetween 升序 LIMIT 500、after 固定 null；新增 apps/agent-service/test/production-delivery-timing.unit.test.ts 600 条旧记录后一条新记录的用例；触发：同一类型在窗口内超过 500 条记录（高频上报或故障设备）；后果：取到最早 500 条，沿用旧的忙状态，通知被扣到最晚送达时间（不丢）；判低理由：需要异常高频上报才触发，后果只是延后到最晚送达时间，不丢通知；已改成按游标翻页，翻满 20 页仍超出就抛错走失败时发
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3. 低：限流路径没有诊断，且送达时机的失败会被统一记成“规则闸门失败”，与 ADR 不一致。ADR 0273 第 5 条把每分钟超限列入要记诊断的情形，代码 production-web-push.ts #timed 漏了 timing_rate；已补，push-channels.test.ts 加限流反向用例。模型说的 code 名与规则闸门失败混用，ADR 第 5 条明写“发送闸门失败的诊断”，与 ADR 一致，不改；触发：每分钟超过 30 次判断后的通知；后果：照常送出但没有 ADR 第 5 条写的诊断
- 4（deepseek-v4.1-flash）成立，会出错，低：### 4. 低：`delivered` 判断后不清掉 `defer_rule_refs`，跨过 deadline 重试会再写一条 `deadline_reached`。已在 sqlite-web-push-operations.ts recordDeliveryTiming 非 deferred 结果时清掉 delivery_timing 标记；push-channels.test.ts 加反向用例，撤掉修复时该用例失败（已验证）；触发：判了可以送、发送失败、之后越过最晚送达时间；后果：账本多一条 deadline_reached，与 delivered 并存
- 5（deepseek-v4.1-flash）成立，会出错，低：### 5. 低：概率阈值先取整，0.6995 这类低于 0.7 的值也会被扣住。delivery-timing.ts 先 Math.round 再比较；已改成 probability*1000 与门槛直接比，delivery-timing.unit.test.ts 加 0.6995 和 0.7 边界用例；触发：模型给出 0.6995 到 0.6999 的概率；后果：低于门槛 0.7 也被扣住
- 6（deepseek-v4.1-flash）成立，可以更好：### 6. 低：每个到期通知先做 5 次感知查询再查缓存/限流，批量到期时数据库读放大。judge() 在查缓存前先读 5 个窗口，是多余读取；本地 SQLite 带索引读，每个 tick 最多 50 项，不会出错，只是可以更省，不在本 PR 改
- 7（deepseek-v4.1-flash）不成立：### 7. 低：作者关于评测费用和“40 忙/40 闲”的说法与产物不一致。说的是作者材料而非仓库内容；ADR 0273 评测一节写的是数据集 40 条、每条 2 遍共 80 次，现用问法忙 40 次和不忙 40 次与 result.json 的 busyTotal/clearTotal 一致，费用写“两版一共约 0.007 美元”与合计 0.0065 相符，无误导

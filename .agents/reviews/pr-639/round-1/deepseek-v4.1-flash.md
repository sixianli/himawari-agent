## 读代码证实的问题

### 1. 中 — 新增的“往来”没有写数据来源和读取边界，现有读取路径会把这类消息过滤掉

文件：`docs/execution/specs/2026-11-11-apple-device-body-design.md:1005`、`docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:171-175`、`docs/architecture-v0.1.md:439`、`packages/persistence-sqlite/src/sqlite-thread-operations.ts:1568`

问题：新设计要求子线程详情显示“和别的子线程、主对话的往来”，但按现有规格，这类内容会被存成主对话里的 `internal` 消息；现有消息读取路径明确只读 `internal = 0`。设计没有说子线程详情从哪里读这些内部消息、用什么权限读。

证据：

- 规格原文：“下面这些都存进主对话，她看得到，但 App 的聊天记录里不显示……子线程发来的进展、问题和结果原文，她转给子线程的话”。
- 架构文档：“`thread_messages.internal` 为 1 的消息……对话详情、按页读消息、数据导出……搜索索引和对话轮次、日总结的进度水位里都没有”。
- 实际代码 `listMessages` 的查询条件含：`AND message_status = 'committed' AND internal = 0`。
- 新设计却写：“点一个子线程进详情……最后是‘和别的子线程、主对话的往来’”。

推断的后果：按现状实现，子线程详情会读到空列表；如果为了让这里显示而直接去掉 `internal = 0`，内部消息会同时出现在主对话详情、分页读取、搜索和导出里，违反 ADR 0285 决定第 5 条和“主对话里不显示”的约束。

建议：在详细设计里写明这是“后台在办 → 子线程详情”专用读取路径，只按当前 owner/agent 和该子线程范围读取，默认不进入主对话聊天详情、按页读消息、搜索、导出；并补一条集成测试：内部消息只在该详情接口出现，主对话和导出里不出现。

### 2. 中 — 基线出处、tokens 来源和画板标题没有全部跟着换到第 66 版

文件：`docs/execution/specs/2026-11-11-apple-device-body-design.md:84`、`docs/assets/apple-clients/2026-11-25-v4/README.md:10`、`docs/assets/apple-clients/2026-11-25-v4/tokens.json:2`、`docs/assets/apple-clients/2026-11-25-v4/source/canvas.json:7`

问题：README 已经写明“第一排在第 66 版加了一屏”，源文件和图片也按第 66 版换，但详细设计的前提 S12 仍说基线“对应在线原型第 64 版”；`tokens.json` 的 `source` 仍写“在线原型第 64 版”；`canvas.json` 第一块画板的标题仍是旧概述，没有“展开往来”。目标的“图、源文件和画板清单一致”没有完全做到。

证据：

- `README.md:10`：“取自在线原型第 64 版（第一排在第 66 版加了一屏）”。
- `2026-11-11-apple-device-body-design.md:84`：“对应在线原型第 64 版（第 62 版……第 63、64 版……）”，没有第 66 版。
- `tokens.json:2`：“在线原型第 64 版……source/ 下各 .dc.html 的 CSS”。
- `canvas.json:7`：“1 主对话：可点的选项、后台在办、子线程、同意卡片、锁屏”。

建议：把 S12 改成“第 64 版，第一排第 66 版补一屏”或直接写第 66 版；`tokens.json` 要么换成第 66 版，要么明确“数值仍取第 64 版 CSS，第 66 版只加了画板”；`canvas.json` 的标题按需要补上“展开往来”或说明标题只是粗粒度概述。

### 3. 中 — 图、源文件、画板清单的一致性没有自动检查，反向用例不会失败

文件：`package.json:36`、`clients/apple/scripts/check-design.mjs:20`、`.agents/instructions/document-governance.md:29`

问题：作者列的 `format:check`、`check:docs-links`、`check:glossary`、`check:markdown-tables` 都不会读 `canvas.json`、`NextChat.dc.html` 或 PNG 的尺寸；`check:apple-design` 目前只校验第 2 版的 `2026-11-12-v2/tokens.json`，不校验第 4 版基线。因此把 `canvas.json` 的 `w` 改回 3436，或把 HTML 的 board 改回 3436，现有检查不会失败。

证据：

- `clients/apple/scripts/check-design.mjs:20`：`export const TOKENS_SOURCE = "docs/assets/apple-clients/2026-11-12-v2/tokens.json";`
- `document-governance.md:29`：“仓库没有对 `docs/` 做全面校验的自动检查……`npm run check` 里有几步只检查 `docs/` 的特定部分”，列出的只有链接、表格、词表等。
- 全仓搜索没有脚本引用第 4 版的 `canvas.json` 或 `NextChat.dc.html`；只有 README、`canvas.json` 自己和 `tokens.json` 的说明文字。

建议：增加一个 `check:apple-baseline` 工具检查：解析 `canvas.json` 的 `w`/`h`、每个 `.dc.html` 的 `board` 宽高和 `$preview`、每张 PNG 的 IHDR 宽高，要求三方一致；再加反向用例：只把 `canvas.json` 改成旧宽度时必须失败。这样才能挡住 I-73 那类“清单值没被真正消费者校验”的问题。

### 4. 低 — “后台在办面板里不显示这些往来”和“子线程详情显示往来”字面冲突

文件：`docs/execution/specs/2026-11-11-apple-device-body-design.md:1005`

问题：同一段先说“点一个子线程进详情……最后是‘和别的子线程、主对话的往来’”，后面又说“主对话和‘后台在办’面板里不显示这些往来”。子线程详情正是从“后台在办”面板点进去的；如果读者把“面板”理解为包含详情页，就会得出“这个功能不能做”的相反结论。

证据：原文：“点一个子线程进详情……最后是‘和别的子线程、主对话的往来’……主对话和‘后台在办’面板里不显示这些往来。”

建议：改成“主对话和‘后台在办’的列表/卡片层不显示这些往来；子线程详情最后一行默认收起，可展开”，把“列表/卡片层”和“详情页”分开写。

### 5. 低 — 展开后的往来列表没有排序、去重、条数上限和空状态

文件：`docs/execution/specs/2026-11-11-apple-device-body-design.md:1005`、`docs/assets/apple-clients/2026-11-25-v4/source/NextChat.dc.html:78`

问题：设计只写“默认收起，只占一行写条数；点开后每条一行……再点收起”，没有写按什么顺序排、按什么去重、条数怎么算、0 条时是否显示、很多条时是否分页或只显示最近 N 条。子线程可能跑很久，往来一多，展开时一次渲染全部行会有性能和内存风险；0 条时还会出现一个可点的“0 条”空行。

证据：原文只写：“默认收起，只占一行写条数；点开后每条一行，写她看了哪个子线程的什么计划或结果、主对话转来的哪句话、留给哪个子线程什么，带时间，再点收起。”原型里是静态的 3 条示例。

建议：明确按时间正序、同一时间按事件编号排序；说明是否去重；条数等于实际可展示行数；0 条时整行不显示；超过一屏时按页或“查看更多”加载，避免一次渲染无上限的列表。

## 推测和未核实

- **PNG 的实际尺寸和内容未核实**：本模型不能读图，也不能联网或运行 `file`/图像工具；只能确认 `01-chat.png` 二进制变了，以及 HTML/`canvas.json` 的宽度都是 3862。若导出的 PNG 仍是 3436 宽或仍是旧 8 屏，现有检查不会发现（见问题 3）。这是目前最大的未核实风险。
- **“取自在线原型第 66 版”无法离线核实**：只能确认源文件里确实加了第 6 屏“展开往来”，且宽度从 3436 变为 3862；无法确认它和线上第 66 版逐字节对应。
- **“往来”行的内容安全**：设计只说写“她看了谁的什么计划或结果、转来或留下了什么”，没有规定只显示程序生成的一行摘要、限制长度或脱敏。若实现直接展示内部消息原文，可能把子线程读到的外部内容或敏感信息在展开时暴露出来。这是实现风险，不是本次改动已经发生的漏洞。

## 侧重检查

- **错误路径**：0 条往来、很多条往来、读取不到内部消息这三种路径都没写清楚；其中 0 条和长列表见问题 5，读取路径见问题 1。
- **不合规范或不可信的输入**：新视图展示的是模型/子线程产生的内部文本，可能夹带外部内容；设计没有写摘要化、转义或长度限制。未核实实际实现，因为本次没有代码改动。
- **安全**：没有新增网络、凭据或不可逆操作；主要风险是为了显示“往来”而放宽 `internal = 0`，把内部消息泄漏到主对话、搜索或导出。问题 1 已给隔离建议。
- **资源耗尽**：展开列表没有分页或上限，长时间运行的子线程可能产生大量行；见问题 5。
- **不可撤销的操作**：没有。这里只有展示和展开/收起。
- **规则、说明文档和代码一致性**：ADR 0285 决定第 5 条说内部往来“聊天记录不显示”，规格明确把“后台在办”定义为聊天记录之外的入口，所以在子线程详情展示本身不直接违反 ADR；但现有代码 `internal = 0` 的读取路径和 `architecture-v0.1.md:439` 的说明必须一起处理。S12、`tokens.json`、`canvas.json` 标题的不一致见问题 2。

## 必答问题

1. **会不会改变模型已经见过的请求开头？** 不会。`git diff --name-only` 只改了 `docs/` 下的设计文档、基线图片、HTML 原型源文件和 `canvas.json`；没有改系统提示、工具定义、历史消息、遮盖或上下文组装代码，也没有代码引用第 4 版基线。发给模型的内容仍然只在末尾追加，每轮会变的值仍然只在最后一条消息里；本次没有新增会进入模型请求的值或字段。

2. **会不会让同一段文字在不同请求里变成不同字节？** 对模型请求不会。本次没有运行时序列化改动。新的“往来”行带时间，但那是界面显示；需要注意问题 5 的排序/去重/上限还没定义，将来若把这批数据用于模型上下文或逐屏快照，必须先固定顺序，不能依赖数据库返回顺序。

3. **有没有对应的自动检查，反向用例是否真的会失败？** 没有针对本次一致性的自动检查。作者列出的四个检查只查链接、词表、Markdown 表格和格式；`check:apple-design` 只读第 2 版 tokens。把 `canvas.json` 的第一排宽度改回 3436、把 HTML board 改回 3436，或把 PNG 换成旧图，现有检查都不会失败。因此目前不存在能失败的反向用例，建议按问题 3 补一个并带反向测试。

4. **改动产生或修改的每个值，使用它的地方都能接受吗？**
   - `3862` 出现在 `NextChat.dc.html:77` 的 board、`:81` 的 `$preview`、`canvas.json:8` 的 `w`，三处一致；9 屏计算为 `9×390 + 8×36 + 64 = 3862`，高度仍为 958，`x`/`y` 不受影响。同一 `canvas.json` 的 `NextMemory`、`NextVault` 本来就是 3862，说明这个值不是新格式，在线阅读器已有先例。
   - 第一排原来的 3436 对应 8 屏；新屏插在“同意卡片、不花钱的同意、锁屏”三屏之前，所以新屏确实是第 6 屏，README 的“第 6 屏”与插入位置和宽度算术相符。
   - `3436` 仍出现在 `NextEars.dc.html` 和旧版本资产里，和第一排无关，没有发现漏改的第一排宽度。
   - 版本和清单文字没有全部接受新值：S12 仍写第 64 版、`tokens.json` 来源仍写第 64 版、`canvas.json` 标题仍是旧概述；见问题 2。
   - `01-chat.png` 的实际宽高和内容未核实；仓库内没有消费者校验它，见问题 3 和“推测”。
   - 没有新增标识、字段、配置键或序列化格式，因此没有后端 schema/校验接受问题；但“往来”这个新视图需要的数据读取路径没有写，见问题 1。

# PR 621 第 5 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，低：### 1. 中低：skip 列表被按 `MAX_BATCH`（1000 个对话）硬上限校验，积压超过 1000 个对话时同一轮会抛错并提前停。代码与模型描述一致：production-inbox-worker.ts:286、:306 把本次检查取过的对话全部作为 skip 传下去，sqlite-inbox-operations.ts:228 用 MAX_BATCH 限长，:237-239 每个对话拼一段 AND NOT；实测表达式深度上限 1000 在约 1000 段时报错；触发：同一次检查里已取过的不同对话超过约 1000 个（同一时刻排队的不同对话数达到这个量级）；后果：claimBatch 拒收 skip（sqlite-inbox-operations.ts:227-236 的 MAX_BATCH），且在此之前约 998 个时 SQLite 自己就报 Expression tree is too large（实测 better-sqlite3：900 个 AND NOT 正常、1000 个报错）；InboxLoop 记一次 inbox.loop_failed 并结束本次检查；判低理由：只在同一时刻有约一千个不同对话排队时触发（只有一位主人，正常使用远达不到）；后果只是报一次失败、本次检查提前结束，已交出的批次照常处理，下一次检查从空的 skip 重新开始（运行中的对话由 busy 条件排除），不丢事件、不产生错误结果；本 PR 生产不接 delivery，循环不启动
- 2（deepseek-v4.1-flash）成立，可以更好：### 2. 低：skip 元素校验不是 null-safe，坏元素会抛原生 TypeError 而不是可识别的端口错误。skip 唯一的来源是 InboxLoop#tick 用 claim 结果构造的 {threadId, fromOwner} 对象（production-inbox-worker.ts:306，经 ProductionInboxWorker.claim 和 durable-adapters.ts:1090 原样透传），threadId 取自已入库的行（入库时已限长），没有可达输入能放进 null 元素或超长 threadId；改成先判对象再校验字段只是让契约更严
- 3（deepseek-v4.1-flash）成立，可以更好：### 3. 低（推测）：`InboxLoop` 的终止现在依赖 `claim` 真的实现 skip，旧代码的“重复即 break”保护被完全删掉。模型自己标了推测：唯一生产实现 ProductionInboxWorker.claim 把 skip 传给 store.claimBatch，SQL 按 skip 排除（sqlite-inbox-operations.ts:237-252），测试 inbox.test.ts:509-549 覆盖；只有将来忽略 skip 的替身或实现才会在同一次检查里反复取同一对话。可加一行防御：claim 返回的对话已在 started 里就结束本次检查

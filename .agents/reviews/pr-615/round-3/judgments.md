# PR 615 第 3 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，低：### 1. [中] 手机上传的 PDF 现在把“原 PDF 文件大小”写进 artifact 的 sizeBytes，Web 文件预览会按 2 MB 门槛误判“太大不给看”。代码核实属实：AttachSources.swift:42 记 originalBytes=文件大小，ChatAttachments.swift:135 写进 <file bytes>，production-uploaded-files.ts:115 当 sizeBytes 落库，content-preview.tsx:84 按 2 MiB 判太大。但这是 ADR 0090:76 约定的“原始大小”，Web 自己上传 PDF 时 chat-composer.tsx:131 也是 bytes: job.bytes（=file.size），所以同样的误判在 base 上的 Web 上传就已存在，根因在服务端把抽出文字的产物登记成原文件大小（production-uploaded-files.ts:46-47、115），不是这个 iPhone PR 引入的；修它要改服务端或 Web，另开 PR；触发：服务端支持附件后，在 iPhone 上传一个大于 2 MB 的 PDF，再在 Web 文件库里打开它；后果：Web 文件预览按 sizeBytes > 2 MiB 显示“太大”，不给看抽出的文字；不丢数据，文件仍在；判低理由：手机路径现在到不了：服务端没有设备端附件路由和 /config attachments，ChatView.swift:135 的 canAttach 为假时“+”不显示，手机无法上传；Web 上的同一问题在 base 上就有、与本 PR 无关；触发后果只是预览显示“太大”，不丢数据、不出错误结果到模型
- 2（deepseek-v4.1-flash）成立，会出错，低：### 2. [低] 相册选图仍把整份原始文件读进内存，降采样只限制了缩略图的解码尺寸。AttachSheet.swift:99 loadTransferable(type: Data.self) 整份读入，AttachSources.swift:24-26 之后才降采样，相册分支没有 fileFits 检查；解码像素已由 ImageDownsampling 限到 4096，这是残留的原文件读入峰值，模型也说不是本次回归；触发：在相册里选一张体积极大的照片（如超大全景或 RAW）；后果：loadTransferable 先把整份原文件读进内存，可能内存峰值过高被系统结束应用；不丢数据
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3. [低] 相机照片没有记录原始字节，`<file bytes>` 仍是重编码后的大小，和“图片记原始大小”的说法不完全一致。AttachSources.swift:19-21 相机分支只有 UIImage，没有 originalBytes，ChatAttachments.swift:128 回落到 data.count；相机经 UIImagePickerController 只交回 UIImage，本来就没有原始文件，重编码大小是唯一能给的数，只影响显示的大小；触发：用相机拍照作为附件发送；后果：<file bytes> 记的是 jpegData 重编码后的大小，文件卡片显示的大小不是“原图大小”
- 4（deepseek-v4.1-flash）成立，可以更好：### 4. [低] 新增自动检查没有覆盖生产接线，默认 4096 上限和 `AttachReader` 是否真的降采样/记录原始大小不会被现有测试拦住。沿用第 2 轮意见 4 的判法：缺测试不是照现在代码会出错的输入；AttachReader.image(data:) 已核对确实调用 ImageDownsampling.jpeg 并记 data.count（AttachSources.swift:24-26），默认上限 ChatAttachmentPlanner.maxImagePixels=4096；AttachReader 在 HimawariChat（UIKit/SwiftUI）里，Linux 编译不了，钉默认值和接线要把它挪进 Core，属于重构取舍

# PR 615 第 4 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，低：### 1. [中] 上一轮意见 1 未改：PDF 仍把原文件大小写进 artifact 的 sizeBytes，超过 2 MB 的 PDF 在网页仍被判“太大”。沿用第 3 轮意见 1 的判断：59c29967c..e88a48d1c 在 clients/apple 只改了 HerPage.swift 一行，相关代码没动，模型也没给新证据。代码核实属实：AttachSources.swift:42 记 originalBytes=文件大小，ChatAttachments.swift:135 写进 <file bytes>，production-uploaded-files.ts:115 当 sizeBytes 落库，content-preview.tsx:84 按 2 MiB 判太大。但这是 ADR 0090:76 约定的“原始大小”，Web 自己上传 PDF 时 chat-composer.tsx:131 也是 bytes: job.bytes（=file.size），所以同样的误判在 base 上的 Web 上传就已存在，根因在服务端把抽出文字的产物登记成原文件大小（production-uploaded-files.ts:46-47、115），不是这个 iPhone PR 引入的；修它要改服务端或 Web，另开 PR；模型新提到 ChatAttachmentTests.swift:90 把原文件大小写成期望值，这正是 ADR 0090:76 约定的语义，不改判；触发：服务端支持附件后，在 iPhone 上传一个大于 2 MB 的 PDF，再在 Web 文件库里打开它；后果：Web 文件预览按 sizeBytes > 2 MiB 显示“太大”，不给看抽出的文字；不丢数据，文件仍在；判低理由：手机路径现在到不了：服务端没有设备端附件路由和 /config attachments，ChatView.swift:135 的 canAttach 为假时“+”不显示，手机无法上传；Web 上的同一问题在 base 上就有、与本 PR 无关；触发后果只是预览显示“太大”，不丢数据、不出错误结果到模型
- 2（deepseek-v4.1-flash）成立，会出错，低：### 2. [低] 上一轮意见 3 未改：相机照片仍不记录原始字节，`<file bytes>` 仍是重编码后的大小。沿用第 3 轮意见 3 的判断：59c29967c..e88a48d1c 在 clients/apple 只改了 HerPage.swift 一行，相关代码没动，模型也没给新证据。AttachSources.swift:19-21 相机分支只有 UIImage，没有 originalBytes，ChatAttachments.swift:128 回落到 data.count；相机经 UIImagePickerController 只交回 UIImage，本来就没有原始文件，重编码大小是唯一能给的数，只影响显示的大小；触发：用相机拍照作为附件发送；后果：<file bytes> 记的是 jpegData 重编码后的大小，文件卡片显示的大小不是“原图大小”
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3. [低] 上一轮意见 2 只改了一半：相册和文件选图仍把整份原文件读进内存。沿用第 3 轮意见 2 的判断：59c29967c..e88a48d1c 在 clients/apple 只改了 HerPage.swift 一行，相关代码没动，模型也没给新证据。AttachSheet.swift:99 loadTransferable(type: Data.self) 整份读入，AttachSources.swift:24-26 之后才降采样，相册分支没有 fileFits 检查；解码像素已由 ImageDownsampling 限到 4096，这是残留的原文件读入峰值，模型也说不是本次回归；触发：在相册里选一张体积极大的照片（如超大全景或 RAW）；后果：loadTransferable 先把整份原文件读进内存，可能内存峰值过高被系统结束应用；不丢数据
- 4（deepseek-v4.1-flash）成立，会出错，低：### 4. [低] 语音对话启动失败时，已启动的识别流水线没有停止，麦克风可能一直占着。代码核实属实：ChatTalkSession.swift:44-48 pipeline.start 成功后 audio.start() 抛错直接跳出，self.audio/self.pipeline（54-55 行）未赋值，下一次 begin 的 end()（35、92-102 行）找不到它们；ChatDictation.swift:42-46 同样模式。但麦克风不会一直开着：TalkAudio.swift:21-36 抛错时 engine 没在运行，SpeechPipeline.swift:113-135 只读喂进的缓冲，不自己开麦克风；下次进入新建 TalkAudio/AVAudioEngine 并重新 setActive，能正常进去；触发：点声波进语音对话时 TalkAudio.start() 抛错（如 setVoiceProcessingEnabled 或 engine.start 失败，音频输入暂时不可用）；后果：已 start 的 SpeechPipeline 没有 cancel，分析任务留在内存里；若 setActive(true) 已成功，音频会话保持激活，别的应用的声音要到下一次语音对话或听写结束时才恢复；界面已回到普通输入框并提示失败，不丢消息；判低理由：只在音频硬件启动失败这条少见错误路径上触发，后果是一个闲置的分析任务和可能未释放的音频会话，下次成功的语音对话或听写结束时会话会被关掉；不出错误结果、不丢数据、不影响下次进入

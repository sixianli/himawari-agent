# PR 615 第 1 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1. [高] 安静时段的读写命令没有登记到客户端能力表，服务端合约也没有，功能和新增测试都不可达。ClientCapabilities.swift 本分支无 quiet_hours；ManageGateway.swift:150-152 查不到就抛 unknownType。PR 617（未合并）的 contracts-v2.ts 定义 quiet_hours.read/set，payload expectedVersion 为 boundedString(64)、start/end 为时钟串，Generated/ClientCapabilities.swift:118-119 为 query/read 和 command/change，与本 PR 的 QuietHours.swift 一致，所以修法是合并顺序：617 先合进 main，再把 main 合进本分支，本分支不重复 617 的契约；触发：本分支在 PR 617 合并之前合进 main；后果：ClientCapabilities 里没有 quiet_hours.read/set，通知行永远不显示，HimawariManageTests 的 QuietHoursStoreTests 在 Mac 上失败
- 2（deepseek-v4.1-flash）成立，会出错，中高：### 2. [高] 附件功能对当前仓库的服务端不可用：`/config` 不返回附件限额，也没有 `POST attachments` 设备路由。device-api-routes.ts:88-128 无 attachments 路由，全仓库服务端无 textCharacters/imageCharacters；ChatAttachments.swift:90 在 attachments 为空时抛 serverOutdated；而 ChatView 的“+”只看平台。已改：DeviceConfiguration.acceptsChatAttachments，RootView 按它设 chatCanAttach，服务器不支持时不显示“+”（与“服务器还没支持的行不显示”一致），ChatAttachmentTests 新增用例；触发：对当前服务端正常使用：点“+”选照片或文件后发送；后果：compose 因 /config 没有 attachments 抛 serverOutdated，每次都弹“服务器还不支持”，选好的东西发不出去
- 3（deepseek-v4.1-flash）成立，会出错，中高：### 3. [中] “一开口就停”只在 `phase == .herTurn` 时触发，句间空隙开口会继续朗读。ChatTalkSession.swift:132 只在 phase == .herTurn 时 interrupt；settlePhase 在句间把 phase 置 listening。已改：打断判断移到 HimawariCore 的 HerReply（回答未结束且未被打断时也算），TalkTurnTests 新增句间开口用例；触发：语音对话中她读完一句、下一段流式文字未到时主人开口；后果：phase 已是 listening 不触发打断，下一句到达后照读，压过主人说话
- 4（deepseek-v4.1-flash）成立，会出错，低：### 4. [中] 照片相册隐私说明与代码不一致：说明写“不传照片”，新功能实际会把照片上传。InfoPlist.strings:14 三种语言；AttachSheet 用 PhotosPicker。已在三种语言补一句“+”里选的照片会发给 Himawari；触发：主人读相册权限说明；后果：说明只说不传照片本身，没提“+”里选的照片会发出去，说明不完整；判低理由：PhotosPicker 在独立进程运行、不需要相册权限，所以这条权限说明描述的用途（感知采集不传照片）本身是对的，只是没交代另一条与权限无关的发送路径，不会让人照着做错事
- 5（deepseek-v4.1-flash）成立，会出错，中高：### 5. [中] 文件附件读取没有大小上限，整份文件先读进内存，存在资源耗尽风险。AttachSources.swift:34、:41 无大小检查，fileImporter 允许 .item。已改：读前取 fileSizeKey，超过 ChatAttachmentPlanner.maxFileBytes（20 MB，与 ADR 0090 网页端一致）提示“太大了”，取不到大小按读不了；ChatAttachmentTests 新增用例；触发：在“+”的文件里选一个几 GB 的视频或大文件；后果：Data(contentsOf:) 在主线程把整份文件读进内存，界面卡住或被系统杀掉
- 6（deepseek-v4.1-flash）成立，会出错，中高：### 6. [中] 安静时段保存的 600ms 防抖会用旧值覆盖刚改的另一个字段。NotificationsPage.swift:28-29 从 store.hours 现算 start/end，save 取消上一个任务。已改：QuietHoursStore 加 draft/edit/saveDraft，页面显示草稿、防抖后提交草稿当前值并等上一次写完；QuietHoursStoreTests 新增两次快速修改都送达的用例（Mac 上跑）；触发：600 毫秒内先改“从”再改“到”，或关开关后马上改时间；后果：第二次保存用的是服务端旧值，先改的那项被覆盖丢失
- 7（deepseek-v4.1-flash）成立，会出错，低：### 7. [低] `<file>` 标签的 `bytes` 传的是 base64/裁剪后长度，不是文档约定的“原始大小”。ChatAttachments.swift:124 用 Data(content.utf8).count；ADR 0090:76 约定原始大小。已改为图片取实际传送的图片数据长度、文本取原文长度，测试更新并新增截断用例；触发：发图片或被截断的文本附件；后果：<file> 的 bytes 是 data URL 或截断后长度，导出和文件卡片显示的大小不对
- 8（deepseek-v4.1-flash）成立，会出错，中高：### 8. [低] 会话列表缩略仍显示原始 `<file .../>` 标签。ChatStore.swift:162-166 直接返回原文，ChatListView.swift:36 当摘要显示；正常使用就会出现，按中高。已改：MessageAttachments.preview，正文为空时显示第一个附件名；ChatAttachmentTests 新增用例；触发：只带附件发一条消息后回到会话列表；后果：列表摘要显示整行 <file name=... ref=.../> 内部格式
- 9（deepseek-v4.1-flash）不成立：`CurrentPlace.attachment` 的定位请求没有超时。Apple CLLocationManager.requestLocation 文档：请求只返回一次，结果必定经 locationManager(_:didUpdateLocations:) 或 locationManager(_:didFailWithError:) 之一回调；AttachSources.swift:99-107 两个回调都 resume 并清空 locationWaiter，:69 再次请求时先把旧的 resume，不存在永久挂起的路径
- 10（deepseek-v4.1-flash）成立，会出错，中高：如果 `compose` 上传到一半失败，用户在重试前换掉附件，下一次仍用同一个 `requestId`。ChatView.swift 只在发送成功后换 sendRequestId，ChatAttachments.swift 用 requestId-序号 作上传键；服务端路由尚不存在，无法证明不会去重，拿不准按中高。已改：附件集合一变就换新 sendRequestId；触发：带附件发送上传失败后，换掉附件再发；后果：新内容用旧的幂等键上传，服务端若按键去重会返回旧内容的引用，发出去的附件和看到的不一致

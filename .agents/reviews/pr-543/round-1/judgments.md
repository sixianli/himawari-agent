# PR 543 第 1 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1【高】运行已经结束后才被批准的设备动作会在重新 `decide` 时预留失败，从而被当成拒绝。新增测试 device-action-approval.test.ts 完成运行后批准：修前在 respond 处抛 A terminal Run cannot acquire new approval authority；修后 resolve 返回 allow，failed 运行仍拒绝；terminalRunStatuses 对 device.action 放行 completed（sqlite-authorization-reservations.ts，resolveApproval 与 live 共用）；触发：设备动作 ASK 现在返回 waiting_owner 工具结果，运行随模型回合结束；主人稍后在首页点同意；后果：ApprovalService.respond 因终态运行直接拒绝（sqlite-durable-operations.ts resolveApproval 的 terminal Run 检查），即使放行预留也因 live() 的终态检查失败，动作被记成 owner_denied，等你点头的动作点不了
- 2（deepseek-v4.1-flash）成立，会出错，中高：### 2【中】不可撤销的设备动作在审批快照里被写成“可撤销”，首页和审批卡会向主人显示错误的后果。production-device-action-authorization.ts 覆盖 sideEffect 为 intent.reversible 推出的值；新增测试断言不可逆动作快照 sideEffect=irreversible；触发：home.control 等不可逆设备动作要主人确认；后果：审批卡和首页显示“可撤销”，主人在错误的后果提示下点同意；执行仍由 ownerPresence 兜底
- 3（deepseek-v4.1-flash）成立，会出错，低：### 3【中】`reconcile` 只扫描最老的 100 条 `waiting_owner`，审批回调又不使用刚批准的 approval id，排在后面的已批准动作可能永远不被处理。list 增加 approvalId 过滤，reconcile(approvalId) 按审批号定位，生产回调传 approval.id；新增 device-actions.test.ts 101 条等待用例，修前最后一条仍 waiting_owner；触发：同时有超过 100 条未回答的 waiting_owner 设备动作，之后批准排在后面的那条；后果：那条动作要等前面的被处理后才放行，不丢数据不放行错误的动作；判低理由：需要 100 条以上同时等待才触发，只是延迟
- 4（deepseek-v4.1-flash）成立，会出错，低：### 4【中】新测试没有走真实的 `DeviceActionService` 路径，“读过外来内容后问主人”这个场景在真实链路上会直接拒绝，测试给的是假信心。询问类用例改用 untrustedOriginAllowed:true 且 readUntrustedContent:true 的真实意图，保留 untrusted 不允许时直接拒绝的反向用例；回调装配用例由意见 3 的用例覆盖 reconcile(approvalId)。integration 不在 npm run check 里属 CI 配置，不在本 PR 范围；触发：有人依赖该测试标题认为 calendar 类动作读过外来内容后会问主人；后果：只是测试与真实链路不符、覆盖假象，生产行为本身符合 ADR 0257；判低理由：生产行为没错，是测试夹具不真实
- 5（deepseek-v4.1-flash）成立，会出错，低：### 5【中低】`DeviceActionResolution.reasonCode` 被产生但被消费端丢弃，所有拒绝都会被记成“主人拒绝”。device-action-service.ts reconcile 只传 approved；sqlite-device-action-operations.ts decide 写死 owner_denied；运行已结束这条最常见的路径已由意见 1 修掉；触发：批准后审批记录消失或来源不可用等异常路径；后果：动作被记成 owner_denied，模型会以为是主人拒绝；正常路径不触发；判低理由：只在异常路径触发且只是原因标签不准，不影响放行与否；修需新增 reason 码和 prompt-catalog 工具结果文案，超出本 PR
- 6（deepseek-v4.1-flash）不成立：### 6【低】`approvalOutcome` 读运行来源时没有像 `authorize` 那样核对 runId/ownerId/agentId，且只检查近期认证引用非空。approvalOutcome 读的是审批自己记录的 runId，校验 owner/agent 已在 approval 上做；近期认证时效由 Gateway 的 assertRecentAuthentication 在 respond 时校验并写入引用，设备动作只在 approved 后才读，不存在不经过它的生产入口；意见自己也承认当前风险有限
- 7（deepseek-v4.1-flash）成立，可以更好：### 7【低】设备动作绕开了工具层统一出口的错误诊断路径，且处理中会吞掉审批回调错误。只是排障信息：回调失败会在下一次 settle 的 reconcile 重试，设备动作异常走 DEVICE_ACTION_UNAVAILABLE 仍是拒绝，不放行；建议采纳与否留给 Andy，倾向不改

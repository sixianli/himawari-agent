# PR 369 第 2 轮复核判断

R2-1 模型判中，线程判不成立（理由见下）；其余成立的“会出错”都是低。

- R2-1：### 1. 中：失败清理的“并发时会被外键挡住”高估了实际保证，且没有对应测试
  - 不成立。模型设想的“另一次本该成功的恢复被误删副本而失败”要求：A 失败而 B 仍能成功。两者针对同一记忆、同一 revision；A 在保存时失败只有三种原因：版本号已被别人推进（则 B 也会因版本号冲突失败）、B 已先提交（则副本已被引用，删除被 memory_records.content_ref 的外键挡住，sqlite-memory-operations 的连接开着 foreign_keys，migration-engine.ts:1000），或磁盘余量等共同原因（B 同样失败）。所以不存在 B 本可成功却因 A 的删除失败的时序。外键挡删已补测试：替身先真正保存再抛错，副本仍在、记忆正文正确（production-memory-capture.test.ts 的 SAVED_THEN_FAILED 断言）。
- R2-2：### 2. 低：`historyId` 直接用 `rowid`，导出/导入或恢复备份后会重新编号
  - 会出错，低。触发：导入到全新实例（import.ts 要求目标表为空）后，旧页面不刷新直接点恢复。后果：控制中心在 connected 变化时重新拉快照（apps/control-center/src/memory.ts:96 的 useEffect 依赖），旧编号被替换；同第 1 轮 D1，不改。
- R2-3：### 3. 低：祖先记忆的状态与 `reaffirmed` 的规则，网页和服务端不一致
  - 会出错，低。触发：旧记忆已归档或进了回收站，仍挂在当前记忆的替换链上。后果：已改：服务端沿链要求每条都是 active，网页同样只对 active 的记录显示按钮；补了服务端和网页两条反向测试。reaffirmed 经 API 恢复时文字等于某个已有版本，无害，不改。
- R2-4：### 4. 低：清理吞掉所有删除错误；`DUPLICATE` 分支可能留下孤儿 payload
  - 会出错，低。触发：删除副本时数据库报非外键错误，或上一次失败的副本删除也失败后同一 revision 重试。后果：留下一份没有引用的加密正文，不影响数据正确性；需要连续两次故障才出现，不改。
- R2-5：### 5. 低：ADR 的“不涉及发给模型的内容”不精确
  - 会出错，低。触发：读 ADR 0217 后果一节。后果：可能误以为恢复后的正文模型看不到；已改写措辞。
- R2-6：### 6. 低：`memory.mutate` 的 `historyId` 变成必填是破坏性的网关变化
  - 会出错，低。触发：同第 1 轮 D5。后果：同第 1 轮 D5，不改。

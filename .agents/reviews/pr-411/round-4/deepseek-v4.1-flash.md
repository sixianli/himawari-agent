## 读代码/文档证实的问题

### 1. 高 — `docs/adr/0242-external-agents-join-the-memory-hub-through-one-entry.md:221`
**问题：** 新增的“目录变了”刹车和后果里的用例互相矛盾，而且按用例实现会破坏刹车。

**证据：**
- 决定 6 写的是目录变了就不附名单：`:107` “目录变了就不附名单，在统计里记一次“目录变了”，页面上提示主人。”
- 但同一节又写没有完整名单就什么都不删：`:105` “服务端没收到写明完整的名单，就什么都不算删除。”
- 后果里的用例却把“目录变了”和“目录清空”合在一起，并要求出现“少了 N 条”：`:221` “记忆目录清空或设置指到别的目录之后同步：库里什么都不自动删，待确认页面出现一条“少了 N 条”……”
- 另一条用例又写不带完整名单时什么都不删：`:224` “助手程序扫描超时或只扫了一半：请求不带完整名单，库里什么都不删，待确认的也不撤下。”

**建议：** 拆成两种用例：
1. 目录没变但为空：助手程序发“完整但为空”的名单，服务端触发“少了 N 条”的待确认。
2. 目录变了：助手程序不附名单，服务端不得判断删除，也不得生成“少了 N 条”，只显示“目录变了”的提示。
同时明确“完整但为空”的名单怎么发（空块或最后一个标记），否则服务端无法区分“空完整名单”和“没有名单”。

### 2. 中（若按 SQL NULL 实现则高）— `docs/adr/0242-...md:102-104、123`
**问题：** 项目名“可空”，唯一键是“接入编号 + 项目 + 稳定编号”，但没写空项目怎么存，也没写这里用的是项目名还是项目编号。若项目直接存 SQL NULL，联合唯一约束不会阻止重复；若存项目名，页面“改名、合并”会改变键。

**证据：**

- `:123` “服务端规范化成项目编号”“页面上可以改名、合并”

**建议：** 明确唯一键用服务端生成、稳定的项目编号，空项目用非 NULL 的哨兵值（例如空字符串），并在写唯一键前完成 NFC 和项目编号规范化；补“无项目时重复推送不新增”和“项目改名/合并后同一稳定编号仍命中”的用例。

### 3. 中 — `docs/adr/0242-...md:106-107、158`

**证据：**

## 推测（未运行验证）

- **SQL NULL 的唯一约束：** 上面第 2 条若把空项目存成 SQL NULL，按 SQL 标准/SQLite 语义，多行 `NULL` 不相等，联合唯一键挡不住重复。未运行数据库验证。
- **旧完整名单重放：** 第 3 条若客户端重试旧名单，而库里已有之后新推的待确认/项目笔记，删除门槛可能仍允许把新记录算成“对方删了”。影响主要是待确认和项目笔记，已确认记忆不由全量名单删除；具体取决于重试和幂等实现。
- **换密钥时索引写失败：** 本人库成功、索引失败时，旧密钥在索引里但本人库已无，新密钥本人库有但索引里无，于是两条路都可能被拒，直到索引重试。这是从 `:164` 的两边都必须匹配推出来的，未核实重试机制。
- **删除门槛边界：** “超过现有条数的一半”意味着正好一半时不触发确认；`:221` “要删的没到门槛时照常处理”也需要明确“正好一半”算不算到门槛。

## 侧重检查

- **错误/不可信输入：** 接入编号的 1–128 和 `machineString` 校验与代码 `packages/gateway-contracts/src/validation.ts:49-59` 一致；稳定编号/项目名的 `INVISIBLE_FORMATTING` 字符集与 `production-mcp-memory-writer.ts:39` 一致（控制字符、Cf、Cs、U+2028/U+2029）。但同步编号、空项目、项目编号、名单总条数没有定义校验或上限。
- **不可撤销操作：** 删除有两道刹车，但“目录变了”用例写错，见第 1 条；旧名单重放和门槛边界见推测。换密钥的失败语义和正反向用例不完整，见第 7 条。
- **资源耗尽：** 名单分块没有总条数、分块数、待处理同步数上限，见第 3 条；已有的通用上限列表也没有覆盖它。
- **安全：** 密钥不出现于日志/错误/决策/指标的目标是对的，但当前只有静态 `scan-machine-secrets`，没有运行时检查，见第 6 条。ADR 0227 前提 2 的 `static_headers` 引法核对后与 `docs/adr/0227...md:47` 一致。
- **规则/文档/代码一致：** PR 413 的说法基本准确：`start_here`、服务使用说明、`auto` 已做；`project` 参数和另外三个读工具的上限没做；`start_here` 默认 private；`start_here` 的 today 段会读摘要并写 `summaryRead`。ADR 0219 的注、执行规范里 `start_here` 摘要那一行也与代码一致。不准确的是：决策记录“随机编号”、前提 7 的现状、以及“已有自动检查守密钥”的现在时说法。

## 必答问题

1. **会不会改变模型已经见过的请求开头？**
   PR 411 自身只改文档，不改任何模型请求。合入的 PR 413 只把新工具、服务使用说明和工具描述注册到对外的 MCP 服务上，代码里这些文字的 `usedBy` 只有 `production-mcp-read.ts`，没有进入 Himawari 自己的系统提示或工具定义。每轮会变的值（`now`、提醒、摘要）都在工具返回内容里，由客户端作为新的工具结果追加，不在系统提示/工具定义/历史开头。ADR 也明确写“Himawari 自己发给模型的请求不变”（`:206`）。对外部 agent 而言，工具清单和服务说明会变一次，但这是 ADR 已写明的、一次性的变化，不是每轮变。结论：没有发现新的请求开头改写；仍是末尾追加，变化值在最后的消息/工具结果里。

2. **会不会让同一段文字在不同请求里变成不同字节？**
   没有发现新的模型可见不确定性。决定 14 继续用“整段一起遮”，代码 `maskForExternalRead` 先收齐所有字符串再统一遮；提醒有固定排序，摘要 SQL 有 `ORDER BY e.day DESC, e.ended_at DESC, e.id ASC`，规则按编号排序，`profile.version` 只对遮过的概况内容做哈希。新增的 NFC 规范化反而让同一文字更稳定。新增的同步编号/统计表/换密钥都不是模型可见内容。注意：`start_here` 的 `today.now` 每轮不同，但这是预期中的末尾变化值，不是开头字节变化。

3. **有没有对应的自动检查，反向用例真的会失败吗？**
   这次是纯文档改动，没有新增可执行检查；`validate_docs.py` 等文档检查不能验证“ADR 对代码现状的说法”是否正确。ADR 里新增的删除、分次名单、换密钥、空项目、密钥泄漏等用例都还只是“要补”的要求，没有实现。现有相关反向用例只有 `production-mcp-read.unit.test.ts:36-45`：它确实能抓住“把 `maskForExternalRead` 改成按字段分别遮”的改法；但它不覆盖在 `#call` 调用点按段遮，所以 ADR 那句“这条用例必须失败”只部分成立。目录变化的用例（`:221`）本身写错，不能作为有效反向检查；失败同步计数、同步编号重放/上限、换密钥新钥可用、空项目唯一键也都还没有测试。

4. **改动产生或修改的每个值，两端都接受吗？**
   - **接入编号**：生成端要求 1–128、字母或数字开头、只含 `._:-`，与 `machineString` 的 `packages/gateway-contracts/src/validation.ts:49-59` 一致，消费端可用。
   - **稳定编号/项目名**：字符集和 NFC 要求与现有 `INVISIBLE_FORMATTING` 一致，但没有写出具体长度上限；项目名与“项目编号”的关系、空项目怎么存、项目改名/合并后键是否变化都没定义，见第 2 条。
   - **同步编号**：由助手程序产生、服务端消费，但没有格式、长度、字符集、作用域、过期、一次性使用和总量上限，见第 3 条。
   - **触发方式**：按进门方式产生的两种值，和 `auto` 参数不是一一对应，模型可以通过 OAuth 调 `auto`，见第 8 条。
   - **删除门槛配置**：只有“默认一半、可改、页面显示”，没有配置键、单位、范围、按接入还是按项目，见推测。
   - **“目录变了”统计值**：由助手程序产生，但没有对应的统计表键或存储位置，见第 4 条。
   - **决策记录字段**：`DecisionInputs.relatedStats` 确实存在且是单次决策自己的数字，这点与代码一致；但“编号是随机的”不成立，`ON CONFLICT` 也只覆盖非 proactive 路径，见第 5 条。
   - **换密钥**：`接入编号/设置/统计不变` 与身份模型一致，但本人库/索引失败时的中间状态和测试不完整，见第 7 条。
   - **密钥不得出现的位置**：目标清单合理，但当前没有运行时自动检查，静态扫描不能替代，见第 6 条。

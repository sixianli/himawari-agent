# PR 637 第 1 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1. 高：NotificationRouter 在 nonisolated 回调里同步调用 @MainActor 静态方法，iOS 目标很可能编译失败。属实，Mac 实际编译报错；已在复核之后的提交 c32281575 把 NotificationRouter.swift:39 presentation 标成 nonisolated static，分支当前代码已修；触发：编 iOS 目标时 nonisolated 的 willPresent 同步调用 @MainActor 的 presentation；后果：iPhone 目标编不过
- 2（deepseek-v4.1-flash）不成立：### 2. 高：选项点选在当前代码里必定被手机端自己拒掉，而且失败没有提示。本机拒掉是作者已知、材料里写明的过渡状态；现在没有任何服务器会发 options（服务器 PR 未出），选项按钮在生产里画不出来，没有可达输入；服务器登记 thread.option.choose 时同一仓库会重生成 ClientCapabilities.swift。失败只有触感、没有文字提示属于界面可以更好，不是错误结果
- 3（deepseek-v4.1-flash）成立，会出错，中高：### 3. 高：选项点选没有稳定去重编号，网络失败后重试可能重复执行不可撤销动作。读代码属实；已改为带动作的选项用由对话、消息、选项组、选项编号算出的固定去重编号（MessageOptions.choiceKey），不带动作的选项仍每次新编号以保持规格说的一直能点；触发：点一个带动作的选项，服务器已执行但手机没收到回应（网络断），按钮复位后再点一次；后果：ManageGateway.command 每次生成新的随机 idempotencyKey（ManageGateway.swift:63），同一个发邮件或花钱的动作可能执行两次，违反设计规格 main-thread-subthreads-inbox-design.md:375
- 4（deepseek-v4.1-flash）成立，会出错，中高：### 4. 中：未知 state 被兜住了，但其他选项字段仍会让整段对话解码失败。Models.swift 原来只有 state 有兜底，其余字段必填；格式是暂定的，服务器 PR 未出，拿不准按中高。已让 options 和 chosenFrom 解不出时丢弃，其余消息照常显示，反向测试去掉兜底会失败；触发：服务器按暂定格式发的选项少了一个字段或类型不对；后果：ThreadMessage 整条解码失败，整段主对话读不出来，而 iPhone 只有这一个对话，ChatStore.load 静默吞掉错误
- 5（deepseek-v4.1-flash）成立，会出错，中高：### 5. 中：客户端页面清单和生成的 NativePage 仍指向已经删掉的页面。client-capabilities.ts:386-396 属实；已按详细设计页面表改为 approvals、suggestions 对 chat，capabilities-adapters、improvements 登记为这一版手机上不做，重生成 Swift，并加契约测试；触发：照客户端能力表判断 iPhone 有哪些页面；后果：表里 approvals、suggestions 指向已删掉的今天页，capabilities-adapters、improvements 指向已删的设置页，和 ADR 0258 第 108 行、计划第 109 行要求本 PR 一起改的不符，会让人以为这些页还在
- 6（deepseek-v4.1-flash）成立，会出错，低：### 6. 中：ownerPresence 缺失时默认 false，安全缺省方向相反。ApprovalPush.swift:34 属实；顺手改成缺省按要本人在场处理，加了反向测试；触发：推送里的按钮缺 ownerPresence 字段；后果：手机会从锁屏直接发 token，服务器 device-api-routes.ts:1550 对要本人在场的仍按 change 档要求 confirmed，所以只会被拒，退回打开 App；判低理由：服务器 production-apple-push.ts 总带这个字段，而且服务器自己会拒没有本人确认的请求，不会被绕过

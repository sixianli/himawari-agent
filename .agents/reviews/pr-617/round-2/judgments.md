# PR 617 第 2 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，低：### 1. 中高 — 第 1 轮意见 4 没有改好：一条「她的话」读取失败仍会让整个推送 tick 反复失败。production-web-push.ts #deliver 里 contentOf 原先没有逐条 try/catch，listDue 只排除非 pending 的尝试（sqlite-web-push-operations.ts:360-361）；本轮已改为逐条捕获、记 failed 后继续，测试 [SAID-1] REVERSE unreadable 覆盖；触发：某条回答的加密载荷永久读不出（解密密钥丢失或密文损坏）；后果：readText 抛错，整次 #deliver 中断，那条推送到过期前每次都排在前面卡住后面的推送；判低理由：沿用第 1 轮意见 4 的原判：只有存储损坏才触发，没有新证据；本轮顺手改了
- 2（deepseek-v4.1-flash）成立，会出错，中高：### 2. 中高 — 自动给“明写 classes 且含 run_result”的旧规则加上 her_words，与规格和作者自己的说法相反。rule-types.ts:66-73 pushQuietClassesOf 对含 run_result 的规则加 her_words（主线程按第 1 轮意见 1 定的修法）；规格 docs/execution/specs/2026-11-24-main-thread-subthreads-inbox-design.md:350、:351 仍写明写 classes 的不加。代码是定下的行为，本轮改规格两处与代码一致，不改代码；触发：上线前按规格第 350 行清点“明写 classes 的旧规则”；后果：规格说这些规则不管她的话、要列给 Andy 选，代码实际已经让含任务完成的规则管她的话，清单和说明会把实际行为讲错
- 3（deepseek-v4.1-flash）成立，会出错，中高：### 3. 中 — 安静时段的“版本号防并发”不是原子的，两个并发 set 会留下两条生效规则。production-owner-rules.ts setQuietHours 先 quietHours() 比版本，再 #activate、逐个 undo，中间没有串行或事务；本轮让同一写入器内的保存排队执行（#quietHoursWrites），并发测试在去掉排队时失败、加上后通过；触发：通知页连点两次保存，或两台设备同时用同一版本号保存；后果：两次都通过版本检查，各建一条规则，留下两条生效规则，此后通知页只读，只能在聊天里改
- 4（deepseek-v4.1-flash）成立，会出错，中高：### 4. 中低 — 通知页保存会把只静默部分类别的规则扩成四类，并额外静默主人自己定的到点提醒。production-owner-rules.ts setQuietHours 写死 classes: [...PUSH_QUIET_CLASSES]，原 SAID-5 测试断言改时间后变成四类；本轮改为编辑已有规则时保留它原写的 classes（没写的仍不写），说明文字按实际类别写，只有通知页新开时才用四类；触发：主人在聊天里立了只管邮件提醒（或默认三类）的安静时段，再到通知页只改时间；后果：规则被换成四类，主人自己定的到点提醒夜里也被延后，主人没要求；与 ADR 0244 第 53 行“主人明说才含到点提醒”不符；判低理由：判得比模型高：正常操作（只改时间）就触发，结果是主人的到点提醒被静默
- 5（deepseek-v4.1-flash）成立，会出错，低：### 5. 低 — 导出的规则文字没有按实际生效类别写，会漏报 her_words。data-export/rules.ts pushQuietWording 原先直接用存储的 classes；本轮改用 pushQuietClassesOf，标签表提到 rule-types.ts 的 PUSH_QUIET_CLASS_LABELS 共用，data-export-rules 测试断言“推送类别 任务完成、她的话”；触发：导出含 classes: ["run_result"] 的安静时段规则；后果：RULES.md 写“推送类别 任务完成”，实际还管她的话
- 6（deepseek-v4.1-flash）成立，可以更好：### 6. 低 — 规格说“正在看主对话时不弹”，实际是任何控制台标签页可见就压掉。沿用第 1 轮意见 3 的原判：可见即压下是本 PR 之前就有的行为（production-web-push.ts 可见分支），“由 App 判断是否正在看主对话”是规格第 3 条后续步骤（规格第 357 行写明 App 端编码时再核实），本 PR 没有新证据表明更坏
- 7（deepseek-v4.1-flash）成立，会出错，中高：### 7. 低（推测）— 挂起/损坏的安静时段规则会让通知页显示“已开启”但实际不生效。quietHours() 原先只按 includeRetired:false 列规则就算 enabled；本轮只把 ruleIsEnforced 的规则算作开启和可编辑，挂起的规则仍列在 rules 里、保存时一并退休；测试 [SAID-5] REVERSE suspended 覆盖；触发：规则复核（rule-review-service.ts:99、:139、:145）因来源记忆被删或改而把安静时段规则置为 suspended；后果：通知页显示安静时段已开启，推送闸门实际不执行（rule-book.ts:18-20 ruleIsEnforced），主人以为夜里安静，手机照响；判低理由：判得比模型高：规则复核是正常运行的后台流程，可达；页面显示和实际行为相反

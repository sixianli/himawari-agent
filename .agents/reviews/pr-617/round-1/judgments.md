# PR 617 第 1 轮判断（deepseek-v4.1-flash）

- 1（deepseek-v4.1-flash）成立，会出错，中高：### 1. 高 — 旧有安静时段规则不会默认管住「她的话」，作者说法与生产写库路径不一致。rule-types.ts:276-294 未写 classes 时把 PUSH_QUIET_DEFAULT_CLASSES 填进返回的 params；production-owner-rules.ts:857-861 把 parsed.params 原样存进 rules.create；ownerRuleRecord（rule-types.ts:405-418）读回时重新 parse 存下的 params。所以库里每条规则都带 classes，规格第 343 行“只有没写 classes 时才用默认清单”的前提对已存规则不成立；触发：主人说“夜里别提醒我”且没点名类别，或者升级前就有的任何一条 push_quiet_hours 规则；后果：规则存进库的 params 里已经带着当时的默认 classes，读回时 rawClasses 不为空，永远不走新默认：升级前的旧规则全部不管“她的话”，主人消息叫起的回话夜里照响（以前这类运行完成推送属于 run_result，被旧规则压住）；规格说“只有明写 classes 的旧规则不加”，按这个说法上线前清点会漏掉全部旧规则
- 2（deepseek-v4.1-flash）成立，会出错，中高：### 2. 高 — 「她的话」推送完全无视消息的数据分级，sensitive/restricted 原话会直接上锁屏。production-web-push.ts:856-869 新分支只看 role 和非空文本；service-main.ts:3027-3040 的 readMessageText 不返回分级，而 ProductThreadMessage 有 dataClassification（packages/domain/src/durable-state.ts:135）；对照 production-web-push.ts:905-917 提醒分支对 sensitive/restricted 隐藏正文；触发：主人消息叫起的运行，她的回答被标成 sensitive 或 restricted（commitAssistantMessage 的分级取自答案 payload）；后果：回答原文直接作为推送正文显示在锁屏和通知中心，同一文件里提醒推送对这两级已改用“私密提醒”文案
- 3（deepseek-v4.1-flash）成立，可以更好：### 3. 中 — 新增的 `visible` 短路对所有推送类别生效，静默期内的定时提醒/任务结果会被永久丢弃，且与 ADR「由 App 决定不显示、服务器照常发」不一致。不算会出错：改动前在安静时段以外，可见时所有类别本来就记成 suppressed（production-web-push.ts:610-613，这段不是本 PR 加的），本 PR 只是让安静时段里也一样，结果与平时一致，没有新的丢失路径；“只对 her_words 生效”或“由 App 判断是否正在看主对话”是规格第 3 条后续步骤的写法（规格第 351 行写了 App 端编码时再核实），可以更好，不在这一步
- 4（deepseek-v4.1-flash）成立，会出错，低：### 4. 中 — 单条「她的话」内容读取失败会让整个推送 tick 反复失败，最长 24 小时阻塞其它推送。service-main.ts:2883-2893 readPlain 解密或 UTF-8 非法时抛错；#deliver 的 contentOf 没有逐条 try/catch（production-web-push.ts:604），tick 只有全局 catch（:315-321）；触发：某条回答的加密载荷永久读不出（解密密钥丢失或密文损坏）；后果：readPlain 抛错，这一次 tick 中断并记 onFailure，那条推送到 24 小时过期前每次都卡住后面的推送；判低理由：只有存储损坏这种非正常情况才触发，正常使用不会出现；同样的失败方式本来就存在：被本 PR 替换的“已完成”推送每次都经 #title 调 readPlain 读对话标题（production-web-push.ts:961-965、service-main.ts:2903），提醒推送也经 readMemoryText 调 readPlain，本 PR 没有增加新的暴露；与 PR 的前例（解密失败判低）一致
- 5（deepseek-v4.1-flash）成立，可以更好：### 5. 低 — `replyMessageId` 的相关子查询没有 `run_id` 索引，长主对话上每个 tick 可能退化为 O(批次 × 线程消息数)。不算会出错：listFinishedRuns 按游标只取新结束的运行（sqlite-web-push-operations.ts:735-737），每条运行只算一次；刚结束的运行的回话就在该对话消息的末尾，按 UNIQUE(thread_id, sequence) 倒序扫几行就碰到，不会每个 tick 扫长对话；加 run_id 索引要新迁移，收益小

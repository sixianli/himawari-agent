## 会出错（中、高）：全部已改

| 编号 | 意见 | 判断 | 怎么改的 |
| --- | --- | --- | --- |
| r1-1 | 编号可能超过 128 字符 | 部分成立。agent-service 里 `createMemoryId` 只是类型断言，不会抛错；但回看编号会进记忆页概览的 `reviewId`（网关限 128），超长时整个概览失败 | 回看编号改为 `memory-review:` 加 sha256 前 32 位；生成编号同样取哈希，记忆编号因此固定在 60 字符以内；表的 id 上限改为 128；测试用 128 字符的 thread id 和 256 字符的消息 id 验证 |
| r1-2 | 失败或进行中的批次可以撤销，撤销后还会重试写入 | 成立 | 只有 `completed`、`gave_up` 的批次能撤销（`UNDOABLE_REVIEW_STATUSES`）；记忆页列表只列这两种状态；反向测试：失败的批次不显示、撤销报 `Conversation review not finished` |
| r1-3 | 撤销中途失败后永远停在一半 | 成立 | 每改回一条就记下它改回后的版本号（新列 `undone_revision`）；再点撤销时，已改回的跳过、其余照常；测试让第二条改回失败，再撤销一次能完成 |
| r1-4 | 写入后、记改动前失败，留下不在任何批次里的新记忆 | 成立 | 写记忆之前先记下“打算改哪些记忆”（`after_revision` 为空的行）；写完、失败时、下次重试开始时都按记忆的实际状态补记版本号，没发生的删掉。新建记忆在写入前还不存在，所以改动表不再对 `memory_records` 用外键，改用删除触发器保持“记忆删除时一并删除改动行” |
| r1-5 | 重试时改动前的值取自已被改过的当前记录 | 成立 | 改动前的值在写入前、从这次回看的快照里取，随“打算改”的行一起存；重试时不覆盖第一次存的值 |

## 会出错（低）

## 不成立

- r1-8（日期和时间戳按字符串比较）：`"2026-11-10"` 是 `"2026-11-10T…"` 的前缀，字符串比较的结果和“把日期当作那天 UTC 零点”完全一样，前后一致，不会“判断反”。唯一的偏差是按 UTC 而不是主人时区算零点，只影响同一天里“取代还是先存为待确认”，待确认的记忆主人可以再确认。这个函数也被每日整理用，不在本 PR 改。

## 可以更好（已顺手改，因为改动小且和上面的修改在同一处）

- r1-9：相关记忆按编号排序后再放进提示词，同样的数据每次字节相同。
- r1-10：原来“重试不重复写入”的测试在写入前就失败了。新增两条测试：写完后补记失败，重试时补齐；写入前失败，“打算改”的行被删掉。
- r1-11：导入的回看记录没有对应的对话摘要，游标改为只看摘要还在的回看记录；导出测试验证导入后游标为空。
